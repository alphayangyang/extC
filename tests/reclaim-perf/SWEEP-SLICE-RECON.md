# 清扫可切片性勘察（`SWEEP-SLICE-RECON`，只勘察；`src/` 零改动）

口径：`digraph` @N=1000000 与形状 A `bench/gc/src/human_a.extc`（`units=2000` / `units=4000`）；
插桩只进 `/tmp/slicesweep/` 的生成物副本（`sw.py`：给 `extc_rc_sweep` 加每 slab 计时与每周期计数、
给 `extc_rc_mark` 加同一次运行里的 mark 计时）。`taskset -c 6`、**5 次取中位**、跑前 load **0.07**；
**关诊断 stderr 0 字节** ✓、程序自身 **stdout 与默认档逐字节一致** ✓、`src/` 零改动 ✓。

## 0. 一句话结论

**清扫可以切片，且切到"字（64 槽）"这一级就够** ⇒ **值得做原型** ✓：
形状 A 的 `max` 停顿预测 **从 225/279 µs 降到 15.8/16.8 µs（−93%/−94%）**（判据 ≥2× ✓✓）；
`digraph` @1M 预测 **max −18.9%、p99 −20.1%**（判据 ≥15% ✓，但**它被 mark 主导，17–19% 就是上限**）；
**每片额外开销实测 1.5 ns/片**（k=256 时占被切掉停顿的 **0.5–0.7%** ≪10% ✓）。
代价与前提：**今天没有游标**（一趟全在局部变量里）⇒ 要加 `(slab, word)` 游标 + "清扫进行中"状态；
**分配必须改成"按已标记"发出**（现在 `extc_rc_alloc` 不置标记位）；清扫的第二趟（`bytes` 重算）也得同样切片。

## 2. 切片粒度：最小可停点在哪

* 现在的 `extc_rc_sweep`（`src/back/reclaim.c:1151`）是**一趟外层 slab × 内层 word**，`freed`、`r->bytes`
  全在局部变量里，**没有游标**；之后还有**第二趟**（`bytes` 重算）。⇒ 直接停下再续**不行**。
* **最小可停点 = 一个字（64 槽）**（内层循环体自足；再细可到 `while(dead)` 的逐个槽）。
  * **slab 粒度不够**：实测最大 slab 清扫 **`digraph` p50 21.5 µs / max 292.9 µs**、
    **`human_a` p50 78.4 µs / max 216.8 µs** —— 形状 A 的**一个 slab 就≈整次停顿**（225 µs）⇒
    按 slab 切**等于没切**；必须按字/槽切 ✓。
* 每片开销（**实测微基准**，不是估算）：`2 次游标写 + 一次 noinline 调用` = **1.5 ns/片**
  （2×10⁶ 次，3 次同值）⇒ k=256 时片长 206–325 ns ⇒ 开销 **0.5–0.7%** ✓。

## 4. 两条秩序前提（读代码，引行号）

**(a) 分配能不能"按已标记"发出？** 现在**不能**：`extc_rc_alloc`（`reclaim.c:492`）置 `occ`（`:513`）、
`tid`、`rscnt`、`hold`，**从不置 `mark`**；而清扫判死是 `dead = occ & ~mark`（`:1151` 起）⇒
切片后 mutator 会在清扫进行中分配，**新对象会被这一趟当成死的释放掉** ✗（悬垂）。
⇒ 需要**一行**改动：分配时 `s->mark[word] |= bit`（清扫自然跳过已标记槽 ✓；已扫过的 slab 末尾
`memset(mark)` 会清掉新对象的标记，但那些槽不会再被回看 ⇒ 不会被释放，下一次 mark 会重新标上 ✓）。

**(b) 清扫期间分配器会不会复用尚未扫到的槽？** **会**：`freeSlot`（`:610`）**头插**进 `s->freelist`
并**不清 `mark`**；`extc_rc_alloc`（`:492`）从 `s->freelist` 取槽，**与扫描位置无关** ⇒
切片后（mutator 可插入）完全可能把"尚未扫到的槽"发出去。今天不炸是因为**清扫是原子的**（无插入）；
切片**必须**配 (a) 才安全 ✓（有了 (a)，新对象带标记 ⇒ 清扫跳过）。

## 5. 握手点（结论 / 未查清）

结构性上需要两处极短临界段：**① 开始清扫**（把 collect 状态从 mark 切到 sweep、携游标进入 mutator）、
**② 清扫结束**（`bytes` 重算 + 触发 `scale`/`freedSlots` 复位）。是否需要真正的**停世界**：
**未查清**（要原型才能定；读代码看更接近"几行状态切换"，不是 Go `mgc.go:835` 那种终止握手）。

## 6. 诚实项

* **切片不减少总工作量**，只改分布（上表的总量不变）。
* 第二趟（`bytes` 重算）也要切：实测 p50 1.09 µs / max 21.3 µs（`digraph`）、~1 µs（`human_a`）。
* 每片额外开销**实测** 1.5 ns/片 ✓；切片后每周期片数 = 扫过槽/k（`digraph` p50 67 707/256 ≈ 264 片、
  `human_a` 65 524/256 ≈ 256 片）⇒ 每周期总开销 ≈ 0.4 µs（对 40–80 µs 的清扫是 0.5–1%）✓。

## 7. 判据逐条

| 判据 | 实测/投影 | 判 |
|---|---|---|
| 结构上可停可续（最小可停点 ≤ slab）| 最小可停点 = **字**（无游标 ⇒ 需加）| ✓ |
| 形状 A 上 ≤1024 槽预算的 **max 下降 ≥2×** | **−93%（k=256）/ −94%（k=1024）** | ✓✓ |
| `digraph` 上 **max 下降 ≥15%** | **−18.9%（k≤1024 都是这个上限）** | ✓（勉强，受 mark 主导所限）|
| 每片额外开销 < 被切掉停顿的 10% | **0.5–0.7%**（1.5 ns/片，实测）| ✓ |
| 两条秩序前提能在现有结构内满足 | (a) 需**一行**分配改动；(b) 现状就会复用，靠 (a) 变安全 | ✓（但 (a) 必须做）|

**裁决：正向 —— 值得做原型** ✓（形状 A 收益 ~93–94%，`digraph` 受 mark 主导上限 ~19%）；
原型必须同时做三件事：**加 `(slab, word)` 游标 + "清扫进行中"状态**、**分配改按已标记发出**、
**把 `bytes` 重算也纳入切片**。

## 8. 未覆盖 / 未查清

* **未做原型**：所有切片后的数都是**从实测 ns/槽 + 实测 max slab 推出的投影**（标注为投影 ✓），
  没有真正实现切片再测一遍。
* **未查清**：开始/结束是否需要真 STW；清扫与 `shouldSweep` 触发在切片下的交互（需要一个"进行中"位）；

* **残留风险**：`ns/槽` 用总量比（未区分"扫描字"与"释放槽"的成本结构）；`digraph` 的 max 上限 18.9%
  只差 3.9 个百分点就掉出判据，重跑可能翻到线下。
