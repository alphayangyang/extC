# 回收成本总表 —— 谁发射 rc · 为什么 · 付多少 · 买到什么

**口径**（本目录的条例：只做归因，不做门禁）

* **绑定**：`build/extc` md5 `57f6b8ccd7c16100d12e5b51b26849e8` · `HEAD` `ad5f063`（干净工作树）。
* **判据**：默认档与 `EXTC_RECLAIM=0` 的生成物**逐字节相同** ⇒ 该程序**不发射回收运行期**
  —— 结构性事实，不是"测出来 0 ns"（与 `bench/app/STALL.md` 同一把尺）。
* **计时**：墙钟与峰值 RSS 由 `fork` + `wait4` 取（两次取"最小墙钟 / 最大 RSS"）。
  **不使用 `timeout(1)`**：它自身在这台机器上要 ~104 ms（`timeout 90 /bin/true` 量到 104 ms，
  裸跑 2 ms），会把毫秒级形状全部抬成同一个常数 —— 本表第一版就被它污染过，见 §5.3。
* **复现**：`python3 tests/reclaim-perf/taxmap.py {census|reasons|probe|report}`；
  原始 TSV 在 [`out/`](out/)。生成的 C 与二进制只落 `/tmp/taxmap/`，`src/` 一个字节没动。
* **未 pin 核、未记 load**；单机单次会话；结论只覆盖量过的形状与规模。

## 0. 结论

1. **结构上，回收只出现在专用语料里**：1234 个 `*.extc` 中 618 个不发射 rc、234 个发射、
   382 个编不过（反例与片段）。**234 个发射的全部**是回收/逃逸立项语料（220）+ `bench/gc`
   与 `bench/stress`（6）+ `examples/` 的 8 个内存模型演示。**291 个能编过的普通测试和其余
   104 个 `examples/` 一个都不发射。**
2. **挡住它们的理由高度集中**：`D 引用写进栈上槽`（119 个形状）> `E 循环里写 ref 字段`
   （80）> `C 宿主不是本帧 new 的局部量`（48）。这三条全是引用图的普通写法：游标、追加、容器插入。
   —— 本目录既有勘察件按"命中集合内的单规则净收益"排序，把人造的环压力形状排在前面；
   在**完整语料**上，D/E/C 才是前三位。
3. **付多少 / 买到什么**：12 个引用图原型里 6 个是**纯税**（开档不比关档省内存，反而多占 2–27%，
   墙钟 1.3–2.6×），4 个是 **GC 挣到**（开档峰值平、关档随规模涨），3 个是**悬崖**。
4. **【缺陷】悬崖的根因是覆盖点定点释放（release）的发射**：`(*tail).f = p` 之后 `tail = p`
   会发射 `extc_rc_storeRefOwnedRelease`；运行期每次覆盖都从其余根出发**完整标记一遍**，
   而旧 tail 经 `head` 可达 ⇒ 标记整条已建成的链、**释放 0 个槽** ⇒ **O(N²)**
   （`rg_grow_tail` N=40000：开档 5.08 s / 关档 2.4 ms）。注入 `release-off` ⇒ 三个形状全部回线性。
5. **现有闸门看不见它**：`gate-release` 的形状 `ring_per_round` 只用 N=20/80，断言的是清扫次数、
   峰值与释放槽数 —— **没有时间判据，也没有"释放 0 槽"的判据**。

## 5. 发现

### 5.1 只读遍历族付税，却买不到东西

`rg_walk_chain` / `rg_walk_buckets` / `rg_walk_tree` / `rg_scan_parent` / `rg_insert_hash`
五个形状里**所有对象从头活到尾**，关档本来就有界；开档的峰值反而更高（槽元数据），
墙钟 1.3–2.6×。⇒ 这些形状上回收是**纯开销**：没有可收的东西，判据却因为 D/E/C 不能证明这一点。
现实对应是最普通的写法：链表遍历、树遍历、哈希查找、数组迭代、容器插入。
（`bench/gc` 的 P4 与 `bench/stress` 也落在这一档：P4 开档 1.51×、峰值与关档相同。）

### 5.2 【缺陷】尾插建链在默认档是二次的

**触发写法**（`rg_grow_tail` 的最小形态）：

<!-- fragment -->
```extc
var tail: mut ref node = head          // 声明在循环外 ⇒ 进本帧静态根表
while i < n {
    var p = new node                   // 本帧 new、从不被重新赋值
    (*tail).next = p                   // p 被写进堆对象的 ref 字段
    tail = p                           // ← 覆盖点：发射定点释放
    i = i + 1
}
```

生成物（`rg_grow_tail`）在该行发的是
`extc_rc_storeRefOwnedRelease(&tail, p, 0, r0, {head, p}, 2)`。运行期先按"其余根 + 跨区种子"
标记，再沿旧值走；旧 tail 经 `head` 可达 ⇒ **每次都标记整条已经建好的链**，而
`release_slots` 一直是 **0**。

**量级**：

| 形状 | N | 开档 | 关档 | 倍数 |
|---|---|---|---|---|
| `rg_grow_tail` | 1e4 / 4e4 | 323 ms / **5083 ms** | 2.4 ms | 134× / **2118×** |
| `rg_scan_graph` | 1e4 / 4e4 | 1562 ms / **25037 ms** | 2.4 ms | 651× / **10886×** |
| `rg_relink_delete` | 1e5 / 4e5 | **31775 ms** / >90 s | 2.4 / 6.6 ms | **13240×** / 超时 |
| 最小尾插（无哨兵，30 行）| 3e4 | 3009 ms | — | — |

**归因**（`rg_grow_tail` N=1e4，callgrind）：总计 **4.77 G Ir**；`extc_rc_mark` 65.7% ·
`extc_rc_ownSlab` 22.0% · `extc_rc_markPush` 10.5%。`EXTC_RC_STATS=1`：
`releases=10000 release_slots=0`（N=10000）—— 发射一次不少，一个槽都没放掉。

**注入对照**（把发射入口改成恒 `return false`，副本树手工打，`/tmp/taxmap/injtree`）：
三个形状的 `storeRefOwnedRelease` 调用点归 0，且

| 形状 | 注入后 N=4e4 | 注入后 N=1.6e5 | 注入后 N=6.4e5 |
|---|---|---|---|
| `rg_grow_tail` | 0.00 s | 0.00 s | 0.00 s |
| `rg_scan_graph` | 0.00 s | 0.00 s | 0.04 s |
| `rg_relink_delete` | 0.00 s | 0.00 s | 0.01 s |

⇒ **根因确认**：成本全部来自定点释放的发射，不是尾插本身。

**修法方向**（未实现，两条都不互斥）：

* **编译期**：覆盖点的旧值若能**从别的活根可达**（`tail` 是 `head` 那条链的投影），就不该发射
  —— 这与"不发射 rc"要的是同一份"根 / 投影"事实。判错的失效方向是**少收**（内存涨，不悬垂），
  已有 `gate-release` / `gate-idle-bounded` / `gate-reclaim-switch` 把着。
* **运行期**：给"释放 0 槽"留一条早退或计数 —— 现在只有跑完整标记才知道没事可做。

**为什么闸门没看见**：`gate-release` 的形状 `ring_per_round` 用 N=20/80（平方在小规模上不可见），
断言的是清扫次数 ≤1、N vs 4N 峰值 <1.5×、释放槽数 >0 —— **没有时间判据**。

### 5.3 计时口径：`timeout(1)` 自身 ~104 ms

`timeout 90 /bin/true` 量到 104 ms（裸跑 `/bin/true` 2 ms）。本表第一版用 `timeout` 计时，
于是 12 个形状在两个规模上都恰好"105 ms"——看起来像共同的固定成本，实际是工具开销。
改 `fork`+`wait4` 后同样的形状是 2.4–150 ms。**任何毫秒级的形状对比都不能经过 `timeout`。**

### 5.4 取样教训：对象落在每轮 arena 里就测不到环垃圾

`rg_drop_component` 第一版把 `var h = buildGroup(...)` 声明在**循环体内** ⇒ 那一组随每轮 arena
释放，开档与关档的峰值都不涨（10.4 / 10.6 MB），看着像"环垃圾被收了"，其实没有环垃圾。
把 `keep` 挪到循环**外**（对象提权到函数 arena）后才是真形状：开档 **10.3 MB 平**、
关档 **15.5 → 57.9 MB**。**造形状时，"哪个 arena 层"决定它到底在测什么。**

## 7. 事件档（原型 `ev` 那条路）：现在卡在哪、修了什么

**口径**：事件档 = `EXTC_RC_SWEEPFREE=1`（计数开、清扫关）。判据脚本
[`gate-event-bounded.py`](../reclaim-acyclic/gate-event-bounded.py)（电池项 `gate-event-bounded`，
已知欠账在 `tools/gate-event-bounded-known-bad.txt`，棘轮只许缩）。

### 7.1 自动档从不生效（粒度）

默认档下 12 个原型全是 `EXTC_RC_NOCOUNT=1 SWEEP_FREE=0`。自动进事件档的门是
`unitAllAcyclic`（**整单元合取**：被发射的每个函数都要无环）⇒ 实际等于永不触发。所以事件档
今天只能手工强制，这也是它从没在真实程序上兑现过的原因。

### 7.2 强制事件档下的三条实测

| 现象 | 数据 |
|---|---|
| 覆盖/淘汰/窗口四类**漏** | `rg_overwrite_ring` 400k→3.2M 峰值 10.1→**71.8 MB**（≈20 B/结点，线性）；4N/N = **3.3–3.7×** |
| 三个悬崖**平方** | `rg_grow_tail` 40k = 5.10 s · `rg_scan_graph` 40k = 25.0 s · `rg_relink_delete` 100k = 31.8 s |
| 语义 | 事件档与关档逐字相同（上表全部形状） |

### 7.2.1 在它的**本命形状**上量：直接炸（决定"留不留"）

事件档本来是为了"环垃圾不等清扫"那条路（原型 `ev`）。拿它针对的形状试：

| 形状 | 档 | N=2000 | N=8000 |
|---|---|---|---|
| `ring_per_round` | 默认（清扫）| 0.14 s / **7.6 MB** | 0.20 s / **7.5 MB** |
| `ring_per_round` | 事件档（计数 + 关清扫）| 5.11 s / **2 093 MB** | 12.41 s / **8 369 MB** |

原因正当、也正是它被门挡住的原因：这个形状的垃圾是**闭环** ⇒ 计数永不归零，而清扫被关掉了 ⇒
无界。事件档只在**无环**单元上成立，`unitAllAcyclic` 因此拒绝它（§7.1：实际从不触发）。

**结论：事件档在语料里没有一个能赢的形状** ——
① 有环形状（`ring_per_round`、`digraph`）上它不成立（上面这条）；
② 无环形状上它会**漏**（§7.4，4 条已知欠账）；
③ 无环形状上就算不漏，计数的代价也是清扫侧的 **+100%~+455%**（§9）。
⇒ 建议**删掉事件档**（保留无环性分析本身 —— `applyCycleMerges`/区域划分还在用），
连带删掉 `gate-acyclic`、`gate-event-bounded`、`acyclic-always` 注入与 4 条已知欠账。

### 7.3 平方的根因与修复（已落地）

`releaseOld` **不看计数**，事件档下照样从其余根做一遍全活集标记。而事件档只用于被证明**无环**
的单元 —— 那里每个不可达对象都会被计数归零当场释放，所以定点释放只有成本没有收益。

修复：`rcEmitStoreRelease` 在 `rcSweepFree == 1` 时直接不发（`src/back/codegen.c`）。
验证：

* 三个悬崖的事件档墙钟 **5.10 → 0.10 s**、**25.0 → 0.10 s**、**31.8 → 0.10 s**；
* 默认档 **12/12 逐字节不变**（对照普查期副本）；
* 事件档与关档输出一致（三个悬崖 + 覆盖/淘汰形状）。

### 7.4 漏的根因（未修，就是那 4 条已知欠账）

`var p = new node` 的**局部绑定**在 `initRef` 里算一个持有者（+1），而**作用域退出 / 每轮 arena
归还 / 函数返回都不销账** ⇒ 每个对象带一个幽灵持有者，计数永不归零。生成物证据（事件档）：

```c
node * p = extc_rc_alloc(__extc_rcr0, sizeof(node), 0);
extc_rc_initRef((void **)&p, (void *)p);   /* +1：这笔账永不减 */
p->v = i;
extc_rc_storeRefOwned(&cells[slot], p, 0); /* 旧值减、新值加 */
extc_arena_release(&__extc_a[2]);          /* 这一轮结束 —— 没有 dec(p) */
```

⇒ 覆盖掉的旧对象账只减到 1（幽灵那笔）就停住，事件档又没有清扫兜底 ⇒ 垃圾线性涨。
修法方向：给"引用局部量离开作用域"补 `dec`（只给会逃逸、可能成为最后持有者的那些），并立一条
`inc/dec` 配对判据（配不平的区域不许关清扫）。

### 7.5 量法教训：别在大进程里 fork 之后用 `ru_maxrss`

子进程在 `exec` 之前继承父进程的页表，`wait4` 的 `ru_maxrss` 会把**父进程的峰值**一起记进来。
实测：Python 父进程读过生成物文本（RSS ≈15 MB）后，200k 的 5.7 MB 被读成 **15.7 MB**，
把 **3.3× 的泄漏压成 1.20×** —— 判据"看不见红"。用 `/usr/bin/time -f %M` 直接包住被测程序
（父进程小），或用专门的 C 垫片。

> **回溯修正（已处理）**：**上一版 §4/§7.2 的峰值列正是用带这个污染的 `taxmap.py probe` 量的**
> （地板 ≈7.6 MB），比值被**压缩**：`rg_overwrite_ring` 当时读作 7.4→18.9 MB（2.54×），
> 用 `/usr/bin/time` 重量是 **5.7→18.9 MB（3.34×）** —— 泄漏比表里更严重。**§4 已按修好后的
> 量法（Python 计时 + `/usr/bin/time -f %M`）重取**，`taxmap.py` 也同步修了。绝对峰值（大规模
> 那一档）不受影响，因为真值在那时就超过了地板。`gate-event-bounded` 用的是同一套修好的量法。

## 8. 静态定价诊断（`EXTC_DBG_RCCOST=1`）：一条负结果

想回答的问题：能不能**静态**算出"这只区域该靠计数还是靠清扫"，从而免掉代价模型？

诊断（默认关、**逐字节不改产物**，12/12 已核）按块层级数 rc 站点：引用存储 / 分配 / 是否在循环里 /
触发点上根表槽数的最大值。跑一批形状（实测税取 §4）：

| 形状 | 实测税× | ref | refInLoop | alloc | allocInLoop | rootMax |
|---|---|---|---|---|---|---|
| `rg_walk_chain` | 1.61 | 6 | 4 | 1 | 1 | 1 |
| `rg_walk_buckets` | 2.53 | 6 | 5 | 2 | 1 | 1 |
| `rg_walk_tree` | 1.40 | 8 | 3 | 1 | 0 | 0 |
| `rg_walk_array` | 0.99 | 3 | 3 | 1 | 1 | **64** |
| `rg_scan_parent` | 1.64 | 8 | 5 | 1 | 1 | 2 |
| `rg_grow_tail` | **2118** | 7 | 4 | 2 | 1 | 3 |
| `rg_insert_hash` | 0.91 | 6 | 2 | 2 | 1 | 1 |
| `rg_relink_delete` | **13240** | 11 | 7 | 2 | 1 | 3 |
| `rg_overwrite_ring` | 1.00 | 3 | 3 | 1 | 1 | **64** |
| `rg_evict_cache` | 2.25 | 13 | 8 | 2 | 1 | 1 |
| `spectrum_p4` | 1.51 | 12 | 7 | 3 | 1 | 3 |
| `spectrum_p5` | 2.61 | 11 | 5 | 4 | 1 | 3 |
| `digraph` | 0.96 | 132 | 93 | 7 | 3 | 15 |

**结论：静态站点数预测不了税，这条路不通。** 三条理由：

1. **站点数不含执行次数**。`rg_grow_tail`（ref=7）与 `rg_walk_chain`（ref=6）同量级，税却是
   **2118× vs 1.61×** —— 前者的成本在"每次赋值跑一遍全量标记"，站点数看不见它。
2. **`rootMax` 不是清扫成本的代理**。`rg_walk_array` / `rg_overwrite_ring` 的 `rootMax=64`
   （根表里有一整条 64 格数组）税却是 **1.00×**；`digraph` `rootMax=15` 是 0.96×；
   `spectrum_p4` `rootMax=3` 反而是 1.51×。**根表"宽" ≠ 活集"大"。**
3. 静态计数只能说明"哪里有引用流量"（`digraph`：132 个站点、93 个在循环里、7 个分配 ⇒ 引用写
   密集，计数在那里会贵），给不出"计数 vs 清扫"的收支。

要判定，必须补**动态**维度：每只区域**实际执行**的引用存储次数、分配次数、清扫时的活字节。
⇒ 下一步不是继续静态化，而是把每区域的动态台账做出来（`EXTC_RC_PROFILE=1`），用实测标定
"每次引用存储 ≈2.8 Ir"（§4 的 `bt` 三档差）与清扫摊销，再决定自动选择值不值得做。

## 9. 计数 vs 清扫的收支（callgrind，同形状两档）：计数侧贵一个数量级

`EXTC_RC_NOCOUNT=0` 打开计数（清扫照旧），与默认档在同一形状同一规模下比总指令。
**清扫侧** = 默认档里 `collect`/`maybeCollect`/`mark`/`markPush`/`sweep`/`freeSlot`/`unlinkChildren`
的自身指令和；**计数价** = 计数档总指令 − 默认档总指令。

| 形状 | N | 默认档 Ir | 计数档 Ir | 清扫侧 | 计数价 |
|---|---|---|---|---|---|
| `rg_walk_chain` | 200000 | 23,853,569 | 90,537,024 | **0（0.0%）** | +66,683,455（**+279.6%**）|
| `rg_walk_buckets` | 200000 | 31,067,737 | 96,948,156 | 3,956,404（12.7%）| +65,880,419（+212.1%）|
| `rg_walk_array` | 200000 | 16,927,943 | 49,661,946 | 0（0.0%）| +32,734,003（+193.4%）|
| `rg_overwrite_ring` | 200000 | 16,933,825 | 49,655,556 | 0（0.0%）| +32,721,731（+193.2%）|
| `rg_evict_cache` | 200000 | 59,828,160 | 295,654,919 | 7,415,918（12.4%）| +235,826,759（**+394.2%**）|
| `spectrum_p4` | 5000 | 897,960,627 | 2,340,313,416 | 151,576,112（16.9%）| +1,442,352,789（+160.6%）|
| `spectrum_p5` | 300000 | 124,919,742 | 250,986,631 | 27,480,330（22.0%）| +126,066,889（+100.9%）|
| `digraph` | 25000 | 27,301,125 | 151,576,072 | 0（0.0%）| +124,274,947（**+455.2%**）|

**结论：今天"用计数换清扫"是赔的，而且赔得很多。** 清扫侧只占 0–22%，计数价却是 100–455%；
最好的一档（`spectrum_p5`）也是清扫 22% vs 计数 101%。

**钱花在哪**（`rg_walk_chain` 计数档，自身指令前三）：

| 入口 | 自身 Ir | 占比 | 调用次数 |
|---|---|---|---|
| `main` | 35,187,202 | 38.9% | — |
| `extc_rc_ownSlab` | 26,576,402 | 29.4% | **799,997** |
| `extc_rc_holdUpdSlab` | 22,799,932 | 25.2% | — |
| `extc_rc_holdUpd` | 5,000,030 | 5.5% | 200,001 |

⇒ 每次计数要走**两次地址→槽查表 + 一次旁路元数据读改写**：`ownSlab` 约 **33 Ir/次**，
`holdUpdSlab` 同量级。默认档里 `ownSlab` 只有 1.38M（分配用），计数档涨到 26.6M。

**与原型差在哪**：原型 `writes.c` 量的是 **0.11 ns/次指针赋值（≈1 Ir）** —— 那里的计数是
**对象里的一个字段，直接改**。我们的持有者计数住在**旁路元数据**（`rscnt` 2 B + 位图 + 每块
小类型表），每次操作先要把对象地址映射回槽（`ownSlab`），单价因此高两个数量级。

**这对路线的含义**（比 §8 更重要）：计数路线成立的前提不是"完备性证明"，而是**先把每次计数
变便宜**（计数进对象头，或更便宜的槽映射），否则 M1/M2 做得再对，打开计数照样赔。
在这之前，"计数优的给计数"没有可赢的空间；清扫侧 0–22% 就是换计数能省的**上限**。

### 9.1 发射层特化（守卫/内联缓存）的上界：不够，不做

设想的做法：把"上次验证过的 slab"从运行期全局挪到**每个调用点**（monomorphic inline cache）、
给 `old == null` 加守卫、对已知区域的对象直传 slab —— 都打在同一块成本上（`ownSlab`）。

上界算法：**把 `ownSlab` 的自身指令整个减掉**（比任何真实特化都乐观），看剩下的计数价还差多少。

| 形状 | 清扫侧 | 计数价 | 其中 `ownSlab` | 砍掉查找后 | 仍是清扫侧的 |
|---|---|---|---|---|---|
| `rg_walk_chain` | 0 | 66,683,455 | 26,576,402 | 40,107,053 | **∞**（清扫侧为 0）|
| `rg_walk_buckets` | 3,956,404 | 65,880,419 | 26,580,063 | 39,300,356 | 9.9× |
| `rg_evict_cache` | 7,415,918 | 235,826,759 | 110,170,602 | 125,656,157 | 16.9× |
| `spectrum_p4` | 151,576,112 | 1,442,352,789 | 597,396,555 | 844,956,234 | 5.6× |
| `spectrum_p5` | 27,480,330 | 126,066,889 | 56,468,407 | 69,598,482 | 2.5× |
| `digraph` | 0 | 124,274,947 | 55,424,784 | 68,850,163 | **∞** |

⇒ **发射层特化翻不过来**：查找只占计数价的一部分，剩下的"更新那笔账"还在。
（另：试过把 `ownSlab` 直接换成"永远信热缓存"的消融 —— 它写坏元数据、当场段错误，
那组数字作废，不做读数用。）**所以 A 不做。**

### 9.2 什么条件下计数才会赢（前置条件指向槽布局）

计数价里真正消不掉的是"每次引用存储动一次账"。若把计数放进**对象头**（原型 `writes.c` 的
做法：约 1 条指令），按当前实测的**计数操作次数**估：

| 形状 | 计数操作次数 | ×3 Ir 估计 | 清扫侧 | 内联计数会赢? |
|---|---|---|---|---|
| `spectrum_p4` | 5,220,296 | 15,660,888 | 151,576,112 | **赢 9.7×** |
| `spectrum_p5` | 3,449,491 | 10,348,473 | 27,480,330 | **赢 2.7×** |
| `rg_walk_buckets` | 2,399,685 | 7,199,055 | 3,956,404 | 输 |
| `rg_evict_cache` | 9,196,107 | 27,588,321 | 7,415,918 | 输 |
| `rg_walk_chain` / `digraph` | 200,001 / 155,599 | 600,003 / 466,797 | 0 / 0 | 输（清扫本来就不跑）|

⇒ 判据可以写成：**`sweep_side > 计数操作数 × 单价`** 才选计数。两条结论：

* **只有在"清扫真的在跑"的形状上才可能赢**（P4 9.7×、P5 2.7×）；清扫本来就不跑的形状
  （`walk_chain`、`digraph`）**必输** —— 那里没有可省的东西。
* 要让它赢，单价必须先降到 ~3 Ir ⇒ **前提是槽布局改动（计数进对象头）**，不是发射层优化。

## 10. A′：全量遍历的信用（默认档拿到 O(n) 保证）

**规则**：一次 O(活集) 遍历（区域清扫**或**覆盖点定点释放）必须由"自上次遍历以来的新分配"偿付
—— `allocBytes - visitedBytes ≥ max(live, floor)`。清扫本来就满足（触发线是 `max(2·live, floor)·scale`），
**破口只在释放**：它由赋值触发、没有分配垫着，于是"赋值 N 次"变成 N 次全活集标记。

**改动**：区域加只增的 `allocBytes` 与 `visitedBytes`；分配时记账；清扫末尾把 `visitedBytes`
推到当前值；`releaseDead` 在预算不够时直接返回（`skip:release-budget`，已进
[`RECLAMATION.md`](../../docs/RECLAMATION.md) 的跳过表）。

**默认档实测（修前 → 修后）**：

| 形状 | N | 修前墙钟 | 修后墙钟 | 修前峰值 | 修后峰值 |
|---|---|---|---|---|---|
| `rg_grow_tail` | 1e4 / 4e4 | 0.32 s / **5.08 s** | **0.00 / 0.00 s** | 10.4 MB | 1.6 / 2.0 MB |
| `rg_scan_graph` | 1e4 / 4e4 | 1.56 s / **25.04 s** | **0.00 / 0.00 s** | 10.4 MB | 2.0 / 4.7 MB |
| `rg_relink_delete` | 1e5 / 4e5 | **31.8 s / >90 s** | **0.00 / 0.00 s** | 10.4 MB | 3.4 / 9.3 MB |
| `ring_per_round`（本命形状）| 2e4 / 8e4 | 0.38 / 1.52 s | 0.36 / 1.51 s | 4.5 MB 平 | 4.6 / 4.5 MB |

**保证**：总遍历量 ≤ Σ信用 ≤ 总分配量 ⇒ **线性**；代价是信用不够时少收一次，垃圾晚一步、
峰值有常数上界（每个区域至多 `max(live, floor)`），失效方向仍是**少收**。
**闸门**：`smoke` 16/0、`nobench` **101/0**（含 `gate-release`：`ring_per_round` 的释放槽数仍 >0、
清扫 ≤1、峰值比 <1.5×）、`gate-skip-table`、`gate-reclaim-{switch,idle,count,ledger}` 全绿。
