## 0. 量化手段与实测（机制证据，不是只有时间）

`callgrind --cache-sim=yes --branch-sim=yes`（callgrind-3.26.0；I1 64 KiB/16 路、D1 48 KiB/12 路、
LL 36 MiB/18 路，均 64 B 行）。**缓存/分支模拟与机器负载无关**（跑时 load 7.6，不影响计数）。
两臂 = 开回收 / `EXTC_RECLAIM=0`；两形状 = `human_a u=4000`、`digraph @100000`（callgrind ≈50× 慢，
故 `digraph` 用 1e5 而非 1M，**规模已注明**）。
`perf stat` 在本容器**不可用**（`No supported events found`）⇒ **IPC 未查清**（callgrind 不建周期模型）。

**读法（与本审计的结论直接相关）**：
1. **rc 运行期的代价主要是"指令条数/分支"，不是 D1 缺失**：`human_a` 开档 Ir 是关档的 **2.91×**
   （+718 M），而 D1 缺失率反而**更低**（1.50% vs 2.31%）——它做的是大量顺序位图扫描。
2. **最差的一格是 `digraph` 开档的分支误预测 5.05%**（1.63 M 次/32.2 M），比关档（4.41%，形状自身
   的哈希/probe 造成）更差 ⇒ 运行期里有可预测性差的短分支。
3. **每函数归因**（`human_a` 开档，按 Ir）：
   **`extc_rc_ownSlab` 一项 = 390.6 M Ir = 35.74%**（Dr 41.18%、Bc 51.72%、Bcm 5.34%），
   其中 inlined 展开的 `slotOfOff` 37.2 M、`offOf` 55.9 M、`bit` 21.6 M、`word` 12.3 M。
   它的 **D1mr 只有 19 900（0.53%）** ⇒ **ownSlab 的贵不在缺缓存，在指令条数与分支**
   （与 Lead 给的"ownSlab 52%"同向，形状/规模不同）。
4. `digraph` 开档的 Ir 头名是形状自身的 `handleAt`（20.7%），运行期不占前几名。

## 1. 七条"味道"逐条审

### ① 别对同一个指针追两次 —— **确认存在，且是最大的一项**
* 机制：标记队列存**裸指针**（`void **mstk`，**reclaim.c:166-167**；入队 `r->mstk[r->msp++] = o;`，
  **:969**）；出队只拿到裸指针，于是**每次出队都要再查一次 `ownSlab`**
  （`void *o = r->mstk[--r->msp];` **:1032** → `ownSlab(o)` **:1033** → `slotOf` **:1035** → `typeOf` **:1041**）。
  入队侧的那些指针**本来就在手边**（追字段时来自父对象的槽，`ownSlab(child)` 在语义上不可避免；
  但**出队侧这一查完全可以省**）。
* 证据：`ownSlab` 占 `human_a` 开档 **35.74% Ir / 51.72% Bc**；`mark` 里每个被标对象一次出队查询
  ⇒ 与"每对象一次多余查询"吻合（`task-24` 量到 `mark` ≈13–14 ns/对象，与一次额外查询+一次类型表读一致）。
* 建议形态：队列元素改存 `(ExtcRcSlab *s, uint32_t slot)`（或 `s` + 槽号），出队直接用
  ⇒ **一次查询换掉两次**里的第二次。代价：队列条目 8 B → 12/16 B（RSS 可忽略）。
* **保语义** ✓（集合与遍历顺序不变）。**怎么量**：`EXTC_RC_TIME` 的 `mark` 计数 + callgrind Ir/D1/Bcm
  + 墙钟（`human_a u=4000`、`digraph @1M`）。**风险**：队列变宽、DFS 顺序不变但在同一缓存行内的
  `(s,i)` 更好；风险低。

### ② 元数据别摊在多个数组里 —— **确认，但缺缓存不是主因（见 §0.1）**
* 现状：每槽要碰 **3 张位图**（`occ`/`mark`/`rsbit`，**reclaim.c:131-133**）+ `rscnt`/`tid`
  （**:135/:139**）+ 计数档的 `hold`（**:134**）。位图每 64 槽 1 个 `uint64_t`，但三张位图是**三块不同内存**；
  `rscnt`/`tid` 是两块 `uint16_t` 数组 ⇒ 一个槽的"占用/标记/登记/类型/计数"分散在 **5 条不同缓存行**
  （甚至不同页）。
* 证据：D1 缺失率 1.50%（开档）**不高**，但 `human_a` 开档 **Dw=114 M / Dr=271 M**，其中位图与
  每槽数组的写占大头；LL 缺失 48 k（0.86%）。⇒ **打包的收益主要在"指令数/写流量"**，不是"降缺失率"。
* 建议形态：**每 64 槽一组连续字**（一组里含 occ/mark/rsbit 三张位图 + 每槽 1 B 的类型号 + 1 B 计数），
  或"每槽一个 64 位字"（位数不够就分档：类型号 8 bit、计数 8 bit 饱和、三个标志 3 bit）。
  **保语义** ✓（只是布局）。**怎么量**：callgrind `Dw/D1mw/ILmr` + `EXTC_RC_TIME` 的
  `alloc`/`freeSlot`/`mark` 计数 + 墙钟 + `gate-shapes`/`gate-tax`。**风险**：中（动 `slabNew`/所有访问器，
  位宽与饱和语义要逐条对齐，容易在计数溢出方向出错）。

### ③ 地址 → slab 能不能更便宜 —— **算法已经是最便宜的形状，问题在"内联展开的条数"**
* 现状：`slabOf` 就是 **一次 AND**（`(uintptr_t)p & ~(EXTC_RC_SLAB_SIZE-1)`，**reclaim.c:186-187**，
  slab 由 `aligned_alloc(1 MiB)` 保证对齐）；`ownSlab`（**:335**，`static inline`）在 AND 之后走
  **热缓存（ownHot）→ ownMap 哈希 → 二分回落**三段（**:337-370**），`slab->region` 是对 slab 头的一次解引用。
* 证据：**D1mr 只有 0.53%** ⇒ 三段结构在缓存上没问题；但 `ownSlab` 的 Ir 35.74%、Bc 51.72%
  ⇒ 贵的是"被 inlined 进 5 个调用点（`alloc` 约 5 次/分配 + `mark` 每对象 + store 路径）"的**指令体量**。
* 建议：**别动算法**，动**调用点的次数**（①）与**体积**（把二分回落 `noinline` 拆出去，见⑥）；
  可选：把 `region` 指针改成 slab 头第一个字并与 `nslots/ss/rcp` 同一条缓存行（现在它们同结构体，
  但要确认编译器没有把热字段分散到多行）。
* **保语义** ✓。**怎么量**：callgrind Ir/I1mr（icache）+ 墙钟。**风险**：低。

### ④ 热循环的依赖链 —— **确认是串行链，建议"批量+预取"要谨慎**
* 机制：drain 每轮 = `读 mstk 条目 → ownSlab（内存读 slab 头）→ slotOf → 读 occ → 读 mark →
  写 mark → 读 tid（另一块）→ 读 ttab[k] → 读对象字段 → 压栈`（**reclaim.c:1032-1056**）。
  这是**每对象一条 ~8 次依赖的内存链**。
* 证据：`mark` ≈13–14 ns/对象（前轮实测）；本审计里 `human_a` 开档 LL 缺失 48 k（少量但每次贵）；
  `digraph` 开档 LL 2.11%（比关档的成分更集中）。
* 建议（**外推**）：把"读类型描述符/孩子"与"压栈"重叠：出队后先预取下一条队列条目与目标对象头
  （`__builtin_prefetch`），并把 `tid` 与位图放近（②）以减少链上的独立内存跳。
  **按地址排序**（把队列当优先队列）会破坏 DFS 的局部性、且排序本身要钱 ⇒ **不建议**。
  **保语义** ✓（预取不影响语义）。**怎么量**：callgrind LL 缺失 + `mark` 的 ns/对象 + 墙钟。
  **风险**：中（预取可能把有用的行挤出去，必须量）。

### ⑤ 清扫的位图扫描 —— **已经用了 `ctz`/`popcount`，还能省"趟数"与"空 slab"**
* 现状：逐字扫、`dead = s->occ[w] & ~s->mark[w]` + `ctz` 跳零（**reclaim.c:1155-1160**）；
  每 slab 扫完再 `memset(mark)`（**:1163**）；随后**第二趟**全表 `popcount` 重算 `bytes`（**:1166-1171**）。
* 证据：清扫占 `digraph` collect 的 **22.1%**（前轮同 run 拆分）；本审计里开档的 Dw 大头来自
  位图清零与第二趟。
* 建议：**一个"本 slab 有位/无位"的字级摘要**（扫 slab 前先看 `occ|mark` 的按字聚合，空 slab 整片跳过）；
  第二趟可以并入第一趟（每扫完一个 slab 就把它的 `popcount(occ)` 累加）⇒ **少一趟**。
  **保语义** ✓。**怎么量**：`rc-sweep-census.py` 的 `slots_scan`/时长 + 墙钟。**风险**：低。

### ⑥ 分支与 icache —— **确认：运行期里 `__builtin_expect` 0 处、`noinline` 0 处**
* 证据：`grep -c '__builtin_expect' src/back/reclaim.c` = **0**；`noinline` = **0**；
  `digraph` 开档 **Bcm 5.05%**（全场最差指标）。
* 建议：把冷路径拆出去（`owner == 0`、`partN > 1` 的跨区分支、`storeRefUnknown`、`noSweep`、
  计数档整段），热路径用 `__builtin_expect`（在**发射的 C** 上加）。**保语义** ✓。
  **怎么量**：callgrind `Bcm`（目标：`digraph` 5.05% → <4.5%）+ 墙钟 + `gate-tax`（只许压）。
  **风险**：低（但 `__builtin_expect` 用错会把热路径变慢 ⇒ 必须 A/B 计）。

### ⑦ 对齐与别名 —— **确认缺失：没有 `aligned(64)`、没有 `restrict`**
* 证据：`grep -n '__attribute__((aligned\|restrict' src/back/reclaim.c` = **无匹配**。
  位图/每槽数组来自 `calloc/malloc`（仅保证 16 B 对齐）⇒ **一个 64 B 缓存行里混着两张位图/两个数组**。
* 建议：`aligned_alloc(64, ...)` 给位图与每槽数组（或至少 `occ/mark`）；热辅助函数
  （`ownSlab`/`slotOf`/`typeOf`/`freeSlot`）加 `restrict` 帮编译器消重载。
  **保语义** ✓。**怎么量**：callgrind `D1mr/ILmr` + 墙钟。**风险**：低（RSS 略涨，页边界对齐可能多占一点）。
