# `tests/reclaim-elide/` —— 「计数按编译期收窄」的**红判据语料**

配套机制文档：[`docs/RECLAMATION.md`](../../docs/RECLAMATION.md) 第五节最后一条。
度量口径：[`prototype-reclaim/README.md`](../../prototype-reclaim/README.md)「写密集形状：计数这块的代价」。

## 这个目录的语义

**记录现状 + 一个棘轮。** 它把「计数按编译期收窄」要处理的现实形状写成小的 `.extc` 程序，
逐条记录**当前的实际计数发射情况**：哪些判据已经成立（绿），哪些还没有（红）。

* `bash run.sh` **永远返回 0**，红条目在表里标出来（同 `tests/reclaim-shapes/`、
  `tests/arena-soundness/` 的口径：这是证据，不是回归判据）。
* 但红绿**不许悄悄漂移**：`gate.py`（`check.sh` 的 `gate-reclaim-elide` 项）把判定表当棘轮比 ——
  见下面「门禁」一节。
* 每个形状 = 一次 `extc`（`EXTC_RECLAIM=1`）+ 一次 `gcc` + 一次运行，整体 ≈1.2s。
* 判据是**计数调用在生成 C 里的出现位置与次数**：`extc_rc_initRef` / `extc_rc_storeRef`
  的**调用点**（运行期 prelude 里的 `static void ...` 定义行不计）。

### 判据的红绿怎么读

| 期望 | 判据 | 现在（无分析） |
|---|---|---|
| **该省** | 生成 C 里**不该出现**计数调用；出现即红 | 红（接线生效后：该省却出现计数；接线生效前：计数未发射，同样标红）|
| **不该省** | 生成 C 里**该出现**计数调用；不出现即红 | 红（接线缺位）→ 绿（接线生效后）|

⚠️ **本表依赖 codegen 的计数接线（task-3）**。接线未生效时生成 C 里一处计数调用都没有，
`run.sh` 会把**全部行标红**并注明原因 —— 此时「该省」行的 0 处是**计数还没发射**，
不是「省掉了」，不要读成绿。接线落地后 `run.sh` 会自己重新判定（判据逻辑在两侧都验证过：
把接线「模拟成生效」后，该省行转红、不该省行转绿；把计数塞到数据字段赋值行上，粒度那行转红）。

## 计数挂在哪（度量口径）

`prototype-reclaim/README.md`「写密集形状」：

* **计数只挂在"指向关系改变"上**：`p.val = x` 不记，`p.next = q` 记两次（`extc_rc_storeRef`
  里 `inc 新值 + dec 旧值`），`p.next = p.next` 可以不记。单价 ≈ **0.11 ns / 指针赋值**
  （≈1/3 周期），成本按**指针赋值**计，不按「写」计。
* 对比写屏障：单价更贵，但**只在标记期间开**；本设计的计数更便宜，但**常开** ⇒
  **分配密集时赚、写密集时赔**。
* 相对税随"指针赋值占总工作量的比例"下降（3 轮取最小）：

  | 数据写 : 指针写 | 不计数 | 计数 | 相对税 | 绝对差 |
  |---|---|---|---|---|
  | 0（纯指针改写）| 2.80 ns | 3.47 ns | **+24%** | 0.67 ns |
  | 5 | 2.95 | 3.69 | +25% | 0.74 ns |
  | 20 | 8.28 | 9.74 | +18% | 1.46 ns |
  | **100** | 62.54 | 66.83 | **+6.9%** | 4.29 ns |

所以「按编译期收窄」的收益**集中在大量指针赋值、极少分配的形状**上 —— 本目录的
`writes_dense.extc` 就是这个形状；而 `keep_count_granularity.extc` 把「数据写不记」这条
口径单独钉住。

## 三类「该省」与三个反面对照（**外加第四类：跨过程"本帧不会销账"**）

> **第四类已经落地**（2026-10-13）：`rcNoDec(F)` 的调用图最小不动点 ⇒ 纯读函数里
> `var p = t` 的 `+1` 改发 `extc_rc_initRefNoHold`。判据是 `elide_readonly_recursion.extc`
> （`bt` 的 `check()` 最小化，用户区 **0 处计数**）；两条健全性反例
> `keep_callee_writes.extc`（钉**传递闭包**）、`keep_indirect_callee.extc`（钉**解析不到的调用**）
> 都语义敏感：正确计数 `v=0`，误省 ⇒ `v=1`。


判据来源：`docs/RECLAMATION.md` 第五节最后一条（**已按实测收紧**，见那一节的现文）。原先那句
"能省的情形：区域反正要被清扫 / 全新分配 / **还有别的持有者**"按字面读**不健全** ——
第三类被实测推翻：持有边自己可能先死，省掉那条 `inc` 会读到坏值
（`keep_other_holder_dies.extc`：省了 ⇒ `v=2`，基线 `v=7`）。正确的判据是**对象级**的
"账本只增不减"：该对象的**每一条**入边都不会有 `dec` 落下来。

> ⚠️ 下表的「该省/不该省」是**策略判据**（计数该不该发），它**测不到健全性**：
> 实测把全部计数从 8 个形状里删干净，8 个程序的输出**全都还是对的**（每个对象都被一个
> 从不重新赋值的局部绑定持着，那条 `+1` 永不销账）。真正钉健全性的是
> `keep_other_holder_dies` / `keep_two_edges` 这两条（省错 ⇒ 输出变化）。

| 情形 | 该省形状 | 为什么该省 | 反面对照 | 为什么反面对照不该省 |
|---|---|---|---|---|
| ① 对象所在区域**整片活到帧销毁**、入边**统一决定** | `elide_swept_region.extc` | 链只在一个块里建、只在块里走完；要省就**整条对象的入边全省**，死期由区域兜底 | `keep_unknown_region.extc` | 对象是**被调者返回的**、存储已提到调用者这一层：没有"随某个整片死的区域"可依，计数是唯一的早回收手段 |
| ② 赋的是**全新分配**的对象（计数从零起、不可能归零） | `elide_fresh_alloc.extc` | `head = fresh` 里的 `fresh` 是上一行 `new` 的，而且是这个对象第一条也是唯一一条入边：之后再无 dec ⇒「归零即释放」的触发点永远不落在这里 | `keep_shared_overwrite.extc` | **覆盖**一个已持有旧值的槽：新值一侧也许全新，但还带一次对**旧值**的 dec —— 旧值不是全新对象，那次 dec 可能正是它最后一个持有者的消失 |
| ③ 编译器能证明该对象**还有别的持有者** | `elide_other_holder.extc` | `keep` 这个函数层绑定持有对象，且在下面那条边之后**仍然被读** ⇒ 有条活得更久的持有者，新写进 `b.head` 的边不改变对象的存活 | `keep_sole_holder.extc` | 槽是**唯一**持有者，`cur = null` 就是最后一次 dec（计数归零当场释放）—— 省掉它 = 对象只能等清扫，机制白做 |

两个补充形状（不属于三类之一，但同属这张表的判据）：

| 形状 | 期望 | 覆盖 |
|---|---|---|
| `writes_dense.extc` | **该省** | `prototype-reclaim`「写密集形状」：8 个节点串成双向链，之后每轮 4 次指针改链 + 2 次数据写，每 1024 轮才 `new` 1 个节点；所有节点在同一层区里（函数退出整片释放）⇒ 情形①，且是收窄收益**最大**的形状 |
| `keep_count_granularity.extc` | **不该省（粒度）** | 同一个结构上并排放一次数据写（`hot.val = ...`）与一次指针写（`hot.next = tail`）：指针写**该**出现计数，数据字段赋值行上**不该**出现任何计数调用 |

反面对照只否认**对应那一条**证明（不构成三类情形的划分）：例如 `keep_unknown_region.extc`
也是"没有别的持有者"的形状，但它钉的是情形①的缺位。

## 现在的状态

接线（task-3）**已生效**（`run.sh` 会报出计数调用点的总数）。当前的红绿分工正是判据想看到的形状：

| 形状 | 期望 | 现在 |
|---|---|---|
| `elide-swept-region` / `elide-fresh-alloc` / `elide-other-holder` / `writes-dense` | 该省 | **红**：计数照样发射（还没有分析）⇒ 收窄未实现 |
| `keep-unknown-region` / `keep-shared-overwrite` / `keep-sole-holder` / `keep-count-granularity` | 不该省 | **绿**：计数都在（K4 另钉"数据写行上不许有计数"）|

具体处数会随 codegen 变，**不抄进本文件**：跑 `bash tests/reclaim-elide/run.sh` 取当前值。

## 门禁（`gate.py`）

`run.sh` 自身仍是"只记录"的基线（exit 0），但红绿不许悄悄漂移 ——
`gate.py`（`check.sh` 的 `gate-reclaim-elide` 项）把判定表变成棘轮，基线 `red-known-bad.txt`：

* **新增红** ⇒ 红。两类：①「不该省」的形状丢了计数（= 被误省，健全性方向）；② 新口径下仍红。
* **基线里已不再红** ⇒ 也红（收窄实现一条、基线删一条，棘轮只许缩）。
* **接线未生效**（生成 C 里 0 处计数调用）⇒ **rc=2**：那时「该省」的红是"判据还测不到"，
  闸门在这种状态下**不允许绿**。

四个红向都注入验过：基线少一条 / 基线多一条 / 一个「不该省」行变红 / 接线未生效。
另外**判据自身**也有自检：`run.sh --selftest` 在合成样本上断言"运行期 prelude 体内那两行不计、
用户区三种发射形状都数到"（`gate.py` 每次先跑它）。这一条不是洁癖 —— 本目录的上一版就是被它
抓出来的：口径把 prelude 的 2 行算成计数、又漏掉全部 `storeRefOwned`，于是「该省」的行
**永远不可能转绿**、「不该省」被误省也**永远看不出来**（判据两个方向都是死的）。
`run.sh` 要导出判定表就设 `ELIDE_TSV=<路径>`（列：形状 期望 计数 颜色 判定 备注 wired）。

最后两行是**健全性判据**（跟上面八行不同）：它们对"省错计数"敏感 —— 把对应那条 `inc`
拿掉，程序**输出就会变**（两条都实测：`7→2`、`5→1`），`run.sh` 的语义断言因此变红。
上面八行只钉策略，见前面那个 ⚠️。

## 复现一条（手工）

```bash
cd <repo>
EXTC_RECLAIM=1 ./build/extc tests/reclaim-elide/elide_swept_region.extc -o /tmp/e1.c
grep -n 'extc_rc_initRef\|extc_rc_storeRef' /tmp/e1.c   # 看调用点（今天只有 prelude 里的定义）
gcc -fwrapv -O1 /tmp/e1.c -o /tmp/e1 && /tmp/e1          # 语义面：swept=28

# 整张表 + 每个形状的调用点行号：
bash tests/reclaim-elide/run.sh
# 只想看红绿（管道里颜色已关，但「红」「绿」两字始终在文本里）：
bash tests/reclaim-elide/run.sh | grep -E '红|绿'
```

`EXTC=<别的 extc>` 与 `CC=<别的 C 编译器>` 都能覆盖（默认 `./build/extc` / `cc`）。

## 怎么转绿

1. ~~**先接线**（task-3）：codegen 在指针赋值处发射 `extc_rc_initRef` / `extc_rc_storeRef`~~
   —— **已生效**（「不该省」四行因此为绿）。
2. **再收窄**：实现第五节最后一条的编译期判定 —— 满足上述三类情形之一时**不发**对应的计数。
   「该省」四行从红转绿，`run.sh` 会自己重新判定，不需要改判据代码；
   每转绿一条就把 `red-known-bad.txt` 里那行删掉（棘轮只许缩）。
3. 收窄时期望与 `keep_count_granularity` 对齐：省的是**指针赋值**上的计数，数据字段赋值
   本来就不带计数 —— 别把口径做错（`run.sh` 对这条有结构断言）。

> **量出来的优先级**（`tests/reclaim-perf/README.md` §10）：真实形状 `bt` 上 **92% 的
> `ownSlab` 调用来自 `initRef`**，而 `initRef` 绝大多数是**局部引用绑定的拷贝**
> （`var p = t`）；又因为 codegen 从不为局部发 `dec`，这些计数**只增不减**。
> ⇒ 收窄的收益集中在"大量读式拷贝、极少写指针"的遍历形状上；动手前先看那一节的归因。
