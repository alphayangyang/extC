# bench/app 用户视角停顿：三个业务形状的逐单位实测（**全默认档**）

> **状态**：**3 形状 × 6 臂 × 5 rep = 90 次插桩跑全部完成**（另加 90 次 **canon**
>（无插桩）跑做 stdout 与墙钟基线 ⇒ 合计 **180 次进程运行**）；自检 **全过**
>（戳数 **90/90** == 单位数+1；stdout 在**三语言 × canon/插桩 × 5 次**里只有 **1 个逐字节变体**；
> `child_rc != 0` 的行 **0/180**；孤儿进程 **0**）。全部数字由
> `bench/app/appstall_analyze.py` **从原始戳文件重新解码算出**（`/tmp/appstall/stamps/`），
> 不是任何工具的控制台汇总里抄来的。
>
> **口径（写死在本文件 §1，不随结论改）**：停顿**只**由应用侧单调戳定义；
> `extc_rc_*` / Go `gctrace` / `MemStats` 的 Pause **一行都没有**参与停顿定义或命中判定；
> 零调优旗标、**不 pin 核**、不设堆上限、不开关 GC；异常值**不剔除**；拿不到写「未测到」；不估算。
>
> **一句话结论**：三个形状的**单位延迟分布（p50–p99.9）**可复现（同一份生成物跑两遍差 < 1%）；
> **长尾 `max` 与 0.1 ms 超预算计数在这台机器上不可复现**——两个**生成物逐字节相同**的 extC 臂
> 之间，log 的「最长一笔」差 **89.6 ms**、「超 0.1 ms 单位数」差 **54 个**（§6.1 / §6.5）。
> 因此本报告只对 p50–p99.9 与**远超噪声地板**的量下结论。
> **没有测到任何「回收导致业务停顿」的证据**：extC 的回收运行期在这三个形状上
> **根本没有发射**（§6）；Go 关掉 GC（`GOGC=off`）后分布没有可辨认变化（§6）。

## 1. 口径

### 1.1 停顿只由应用侧时间戳定义

1. **打戳位置**：每个**业务单位的边界**。戳打在**形状源码**里（不是在生成物上打补丁），
   三语言各用自己的单调钟：

   | 运行期 | 应用侧时钟 | 语义 |
   |---|---|---|
   | extC | `time::now()`（`extc_time_mono_ns` ⇒ `clock_gettime(CLOCK_MONOTONIC)`） | 单调、不倒退 |
   | C++ | `std::chrono::steady_clock` | 单调、不倒退 |
   | Go | `time.Since(base)`（`time.Now()` 的**单调部分**，**不是** `UnixNano` 的墙钟） | 单调、不倒退 |

2. **戳数 = 单位数 + 1**：第一次 `us()` 记 `t0`，其后每次 `us()` 记一个增量，
   **循环结束后补最后一次**（这一条是打戳实现里最容易漏的：第一版漏了，自检当场抓到
   「戳数 200000 != 200001」）。
3. **单位延迟**`[i] = t[i+1] − t[i]`；报告 **p50/p90/p99/p99.9/max**、
   **超预算单位数**（0.1 ms / 1 ms / 16.7 ms，判据 `单位延迟 > 预算`，**严格大于**）、
   **最长一次停滞**及其相对 **p50** 的倍数。
4. **禁用（写死）**：`extc_rc_collect` 入口戳、Go `gctrace` 的 Pause、任何 GC 日志 ——
   **不得**用于命中判定或停顿时长。本报告**没有任何一行停顿数据来自它们**。
   `EXTC_RECLAIM` 只作**编译期**对照（它是代码生成开关，不是运行期开关）。

### 1.2 业务单位是什么（三形状）

| 形状 | argv（= 程序自带默认规模） | 业务单位 | 单位数 | 为什么是这个单位 |
|---|---|---|---|---|
| `session` | `2000000 65536` | **一次会话事件**：主循环一次迭代（查 / 建更 / 断连，由 `i%977%5` 定） | 2,000,000 | 一次连接事件就是服务端能感知的最小业务步；`run.sh` 里也是"每个 op 一次" |
| `route` | `2000000` | **一次路由表操作**：四个阶段循环各一次迭代（插入/前驱查找/区间扫描/删除） | 5,500,000 | 四种用法在一次操作里等价；总单位数 `= ops + ops + ops/4 + ops/2`（与源码里的四个循环边界**逐字对应**） |
| `log` | `2000000` | **一次请求处理**：主循环一次迭代（追加 24 B + 可选 find + 可选截断） | 2,000,000 | 一次请求 = 追加 + 也许查一次 + 也许截断，不能拆 |

> **与 `run.sh` 的口径差异（显式标注）**：`run.sh` 的 session 规模是 `ops = 30 × active`
> （`active=65536` ⇒ `ops=1966080`）。本报告按任务给的**程序默认** `2000000 65536`。
> 两者的**单位定义相同**（一次迭代），但**规模不同** ⇒ 本报告的数**不可**与 `RESULTS.md`
> 的 session 行逐格对比。`route` / `log` 的 argv 与 `run.sh` 的中间档一致。
> 另注：`RESULTS.md` 本身是 **2026-09-25 的旧产物**（比 `log.extc` 和 `string.extc` 都旧）⇒
> 本报告只沿用它的**口径**（编译管线、单位定义、校验和判据），**不沿用它的数字**（§8）。

### 1.3 打戳怎么实现（每处锚点唯一，否则整体失败）

`bench/app/make_stamped_app.py` 从 `bench/app/*.{extc,cpp,go}` 派生
`bench/app/stamped/{extc,cpp,go}/*_us.*`：**只读**形状源码，每处替换都断言锚点在原文里
**恰好出现一次**（`sub1()`；少一次或多一次就 `SystemExit`）。

| 形状 | 锚点（原文，唯一） | 插入 |
|---|---|---|
| session | extC `while i < ops {` / C++ `for (int64_t i = 0; i < ops; i++) {` / Go `for i := int64_t(0); i < ops; i++ {` | 循环体第一行 `us()` |
| route | 4 个循环头；前两个同形，用**紧随其后的判别行**（`let key = …` / `let q = …`）区分 | 每个循环体第一行 `us()` |
| log | extC `while i < ops {` / C++ `for (int64_t i = 0; i < ops; i++) {` / Go `for i := int64_t(0); i < ops; i++ {` | 循环体第一行 `us()` |
| 三形状 | 末行打印语句原文（`io::cout << "a.len="` 等） | 前面插 `us()` + `usDump()` |

**戳文件格式**（三语言逐字节同一套）：40 字节小端头（magic `USAPPST1` · `u64 nstamps` ·
`i64 t0` · `u64 nneg` · `u64 novf`）+ `nstamps−1` 个 unsigned-LEB128 增量。
选二进制不选文本是因为 `/tmp` 是 1.4 G 的 tmpfs 且**并行有别的任务在用**：文本戳在 route
上要 ~77 MB/次（30 次插桩跑 ≈ 2.3 GB），二进制只要 ~8 MB/次。`nneg`（负增量）与 `novf`（缓冲溢出）
两个计数器在头里；**自检要求两者都是 0**（90/90 臂次实测都是 0）。

### 1.5 量具与统计口径

* **墙钟 / 峰值 RSS**：`bench/gc/digraph_run`（只读复用，**未改**）——
  fork→exec→`wait4`，墙钟是 `CLOCK_MONOTONIC` 包住被测程序，RSS 是 `wait4.ru_maxrss`（内核值）。
  **不传 `--pin`**（任务点名不 pin 核）。每臂 **5 次**。
* **分布**：逐 rep 各算一遍分位，再取 5 次的**中位**；`max(中位)` = 5 次各自 max 的中位；
  **`最长` = 5 次里最大的那一次**（异常值不剔除）。
* **超预算计数**：逐 rep 各算，报 5 次的**中位**，并给逐次列表。
* **轮转（rep 主序）**：同一个 rep 里把 6 条臂紧挨着跑完 ⇒ 外部负载在各臂之间均摊。
  **第一遍（arm 主序）已作废**：它让 session 在 load≈3.8 时跑、log 在 load≈1.0 时跑，
  route 的 extC 在 load 2.3–3.4、Go 在 1.0 ⇒ 尾部被负载混杂。作废那遍的日志留档在
  `/tmp/appstall/logs/runA_noninterleaved/`。轮转后各臂的 `load_pre` 几乎相同（下表）。

```

        session: extc_def/canon=0 · extc_def/us=0 · extc_norec/canon=0 · extc_norec/us=0 · extc_force/canon=4 · extc_force/us=4   [默认 vs EXTC_RECLAIM=0：产物逐字节相同]
        route: extc_def/canon=0 · extc_def/us=0 · extc_norec/canon=0 · extc_norec/us=0 · extc_force/canon=4 · extc_force/us=4   [默认 vs EXTC_RECLAIM=0：产物逐字节相同]
        log: extc_def/canon=0 · extc_def/us=0 · extc_norec/canon=0 · extc_norec/us=0 · extc_force/canon=4 · extc_force/us=4   [默认 vs EXTC_RECLAIM=0：产物逐字节相同]
        正对照（bench/gc/src/digraph.extc，有受管分配点）：默认 4 处、EXTC_RECLAIM=0 0 处、产物不同
        ⇒ 本判据**能红**；上面三个形状全 0 是真实的结构性结论，不是量具坏了。
```

* 三个形状的默认生成物里 `extc_rc_collect` 出现 **0 次**；`EXTC_RECLAIM=0` 的产物与默认
  **逐字节相同**（md5），**`.text` 段的 md5 也相同**（6/6 组合：3 形状 × canon/插桩）。
* **这个判据能红**（正对照 `bench/gc/src/digraph.extc`，有受管分配点）：
  默认 **4** 处、`EXTC_RECLAIM=0` **0** 处、产物**不同**、`nm` 里 `extc_rc_*` 符号
  **44 vs 0**。
* 另一条独立证据：编译同一个 `.c` 到**两个不同的输出名**会得到不同 md5 的二进制，
  但 `.text` 段 md5 相同（GCC 用输出文件名做局部符号名的种子）
  ⇒ 所以「二进制 md5 不同」**不**能推翻「代码相同」；我们就用 `.text` md5 作判据。

⇒ **正解**：在这三个形状上，回收让业务多付的是 **0 条被执行的回收指令**——
因为编译器的受管分配点判据**没有找到任何受管分配点**（三个形状自己一个
`new`/`alloc<>`/`@overwrite` 都不写；存储都来自 `stl` 容器的 `@poolObject` 池）。
这不是「回收很便宜」的证明，是「**回收运行期压根没发射**」的结构性事实。
（机制解释止于 `src/back/codegen.c` 的注释 + 上面的实测判据；**未逐行复核**那个 pass。）

### 6.2 extC：`EXTC_RECLAIM=1`（非默认·强制发射）

* `session` / `route`：生成物有 4 处 `extc_rc_collect`，但 **`.text` 与默认仍然逐字节相同**、
  `nm` 里 `extc_rc_*` 符号 **0 个** ⇒ 回收运行期被 `-O2` 当死代码**全部删除**，运行期代价
  **仍是 0**。
* `log`：`.text` **不同**，`nm` 里 **7 个**符号存活（`extc_rc_ownSlab` / `ownBig` /
  `storeStructCons` 等**归属登记**路径）⇒ 这一格**确实多了活代码**；
  但它的 `canon 墙钟` 与默认**一样**（177.2 ms vs 177.2 ms 中位）⇒ 代价**低于噪声地板（未测到）**。
* 所以 `log` 的「回收成本 = 0」只能说成「**未测到**」，不能说成「是 0」。

### 6.3 Go：默认 vs `GOGC=off`（非默认·关 GC，与 `go` 共用同一份二进制）

* `session`：Δp50 **−0.001 µs**、Δp99.9 +0.016 µs；`>0.1 ms` / `>1 ms` / `>16.7 ms` 计数
  **完全相同**（3 / 0 / 0）。
* `route`：Δp50 **−0.001 µs**、Δp99.9 **−0.016 µs**；`>1 ms` 与 `>16.7 ms` 计数相同（1 / 1）；
  相位过渡那一笔两臂都是 ~200 ms（§4 的相位过渡表）⇒ 差别与 GC 无关。
* `log`：Δp50 **0.000 µs**、Δp99.9 **0.000 µs**；只有 `最长` 从 5.6 ms 变成 93.7 ms、
  `>0.1 ms` 从 3 变 14 —— 而 log 的噪声地板（§6.5）恰好是 **89.6 ms**，
  即这个差**整个落在噪声里**。

**判词**：三形状的 Δp50 / Δp90 / Δp99 / Δp99.9 全部 ≤ 0.02 µs，`>1 ms` 与 `>16.7 ms` 计数相同；
只有 `max` 与 0.1 ms 计数在噪声里晃（两个方向都有）。
⇒ **没有测到 GC 归因的停顿增量**。这是**负结果**，不是「GC 很快」的证明：
`GOGC=off` 同时改变内存占用，"少一次暂停"与"多占内存"分不开（§1.4 的 ⚠️）。

## 7. 每档一句话判词

**`session`（会话/连接表）**
* extC：p50 **0.033 µs**、`>1 ms` **5/5 次全 0**；最长 135.0 µs 是外部噪声（每次序号都不同）；
  回收运行期**没发射**（§6.1）⇒ 用户看不到停顿。
* C++：p50 **0.027 µs**（三语言最快）、p99.9 0.085 µs；最长 180.7 µs 也是噪声 ⇒ 无回收器的基线最紧。
* Go：p50 **0.042 µs**（三语言最慢，+27%）、p99.9 0.262 µs（最厚）；`GOGC=off` 后无变化 ⇒ 差的是**每单位固定成本**，不是 GC。
* 0.1 ms 档：六臂中位 1–3 个/跑；而两个**逐字节相同生成物**的臂之间计数差就有 **1 个**
  ⇒ 这个跨度只比噪声大一点，**不作结论**。

**`route`（路由表）**
* extC：p50 **0.569 µs**、p99 1.113 µs、`>1 ms` **5/5 次 0**；最长 **921.6 µs** 且
  **5/5 次落在同一个单位序号 i=1942311** ⇒ **确定性的数据结构事件**（某把特定的键），
  不是 OS、不是回收；这是本报告里**唯一一个能把"最长一笔"钉到具体单位的形状**。
* C++：p50 0.910 µs（1.6×）、p99 6.089 µs（**5.5×**）、scan 相位 p50 **4.896 µs**（extC 的 7.1×）；
  最长 **68.2 ms**、`>1 ms` 每跑 0–5 个 —— **远超噪声地板的真长尾**，且最长笔序号每次不同。
* Go：p50 **0.184 µs**（最快）、p99 0.559 µs；名义最长 **252.9 ms** 但那是
  **相位过渡的 setup**（建+排序 100 万键）；剔除后最长 **2.06 ms**、`>16.7 ms` **0**；
  `GOGC=off` 无差别 ⇒ 长尾不是 GC。
* 1 ms 档：extC **0**（`norec` 5 次里 1 次为 1、`force` 5 次里 1 次为 20——两个都在噪声里）·
  C++ 0–5 · Go 1–2（`go_nogc` 1–5）⇒ 只有 C++ 的 1 ms 命中是稳定的。
* 16.7 ms 档：extC **全 0** · C++ 0（5 次里 1 次为 2 个）· Go **1/跑**（**全部是相位过渡那一笔**，
  剔除后 **0**）。

**`log`（请求日志/动态缓冲）**
* extC：p50 **0.099 µs** 但 C++/Go 只有 0.029/0.032 µs（**3.1–3.4×**）；
  尾部**不可复现**——两个逐字节相同生成物的臂，最长一笔差 **89.6 ms** ⇒ 尾部数字全部作废。
* C++：p50 0.029 µs、p99.9 0.092 µs、最长 312.8 µs ⇒ 三语言里分布最紧。
* Go：p50 0.032 µs、p99.9 0.088 µs，与 C++ 几乎相同；`GOGC=off` 的差（88 ms）落在噪声地板内。
* 0.1 ms 档：extC 5–87、C++ 0–5、Go 3–71 个/跑，**逐次波动比臂间差还大** ⇒ 不作结论。

## 9. 未覆盖与风险

**未覆盖（明确没做的）**
1. **没有做时间域对齐** ⇒ 没有任何「第 k 个单位撞上第 j 次 GC」的断言；GC 侧计时一行都没用。
2. **没有 Java**：`bench/app` 没有 Java 移植 ⇒ 「JVM `Using <GC>`」这一栏不适用。
3. **只有一个规模**（程序默认 argv）⇒ 「停顿随规模怎么变」未测。
4. **0.1 ms 档的超预算计数不下任何结论**：噪声地板（两个逐字节相同生成物的臂之差）在
   log 上达到 54 个单位 / 89.6 ms，比任何"臂间差"都大。
5. **route 的相位过渡只做了"剔除后"这一种处理**，没试过把 setup 单独打一个戳。
6. **未查清**：C++ route insert 的单笔 68.2 ms 是什么（堆增长/缺页/compaction？）；
   Go route lookup 的单笔 29–39 ms 是什么（GC？未对齐不能说）；extC log 相对旧树的
   3.6× 变慢机制。
7. **extC 回收的机制解释**只到「生成物有没有回收运行期」这一层实测判据；
   `codegen.c` 的受管分配点 pass **未逐行复核**。
8. **`EXTC_RECLAIM=1` 对 log 保留了 7 个活符号** ⇒ log 的"归零"只到「未测到」。

**风险**
1. **插桩扰动的方向与幅度随语言不同**（route：extC +55 ns/单位、C++ +223、Go +121）⇒
   **跨语言的绝对分位比较**受污染；本报告用 §10 的 canon 均值作为无扰动的补充，
   但 canon 只有均值、没有分位数。这是最大的方法学弱点。
2. **`max` 天然不稳**：它是 5 次里最大的一次；已并列 5 次中位的 max，但两者都可能被
   一次调度尖峰拉动。
3. **未 pin 核 + WSL2 + 共享机器**：`load_pre` ∈ [0.76, 1.76]；轮转让各臂相近，但
   **跨形状**（session 在 load≈0.78、log 在 load≈1.1–1.76）仍有差异 ⇒ 跨形状的
   尾部对比要打折扣。
4. **只有 5 次**；p99.9 在 2M–5.5M 个单位上还算稳，`>16.7 ms` 这种极稀事件只有 0–3 次，
   不具统计意义。
5. 结果只对 **Linux/x86-64 + 本机 + 当前 extC 绿点 `57f6b8cc`** 成立；换编译器版本、
   换 `stl` 容器版本都可能变（log 的 3.6× 就是活例子）。
6. 本报告**没有改** `src/`、`tests/`、`tools/`、`docs/CHANGELOG.md`、`bench/gc/**`、`RESULTS.md`；
   新增的文件只有 `bench/app/` 下的 `STALL.md`、`make_stamped_app.py`、`appstall.py`、
   `appstall_analyze.py` 与 `bench/app/stamped/**`。**不承诺"没有任何新风险"。**
