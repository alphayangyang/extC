# bench/app —— 综合应用场景横评（extC STL vs C++ STL vs Go）

> **自动生成**（`bash bench/app/run.sh`），别手改。
> 口径：三种语言**同算法同参数**，跑同一串操作，打印出来的校验和**逐字节相同**才算数；
> 时间与峰值 RSS 都是 `best of 3`（时间用 bash 内建 `EPOCHREALTIME`，每样本重复 K 次凑到约 0.2 s）。

机器：Intel(R) Core(TM) Ultra 9 275HX · kernel 6.18.58.1-microsoft-standard-WSL2

## 三套实现与编译口径

| | extC | C++ | Go |
|---|---|---|---|
| 编译 | `extc` 生成 C，`cc -O2 -std=c11 -fwrapv` | `g++ -O2 -std=c++17` | `go build`（默认） |
| 会话表 | `stl::hashMapI64<session>` | `std::unordered_map` | `map[int64]Session` |
| 路由表 | `stl::map<i64,i32>`（B+ 树） | `std::map`（红黑树） | `map` + 排序切片 + 二分 |
| 日志缓冲 | `stl::string`（地址预留底） | `std::string` | `[]byte` |

`-fwrapv` 不是「多加的旗子」：extC 把有符号溢出定义成绕回（`docs/MANUAL.md` §8），
编译器驱动自己也是这么编的（`src/main.c`）⇒ 这是生成的 C 的既定编译契约。

## 场景 B：路由表（前驱查找 + 区间扫描）

键是 /24 前缀，值是下一跳。四个阶段：插入/更新 ops 条 → **前驱查找**（最长前缀匹配的
实质：最后一个 ≤ q 的前缀）ops 次 → **区间扫描** ops/4 次（数一个 /16 段里有多少条）→
删除 ops/2 条。数据结构**本来就是三种**（B+ 树 / 红黑树 / map+排序切片）—— 这是
「各语言里最自然的那个有序表」的对比，不是同一个结构的对比。表里的 `ns/op` 分母是
**真实操作数**（插入 + 查找 + 扫描 + 删除 = 2.75 × ops），不是规模参数。

## 场景 C：请求日志 / 动态缓冲

定长 24 字节的记录追加进去；每 512 轮在缓冲里 `find` 上一条记录的前 4 字节
（它只可能出现在**末尾** ⇒ find 扫满整条缓冲）；缓冲到 16 KB 就**截断**掉最老的一半。
extC 的 `string` 没有 `erase`，截断是**字节循环**（`dropFront`：缓冲区字段是公开的
`mut slice<u8>`）；C++ 用 `erase(0,n)`（memmove）、Go 用 `copy` + 重新切片 ——
逻辑同一件事，机制各语言不同，这一格本来就是「缺什么就付什么」。

## 结论与分析（2026-09-26 成文；2026-12 按本轮数字重述）

> 数字来自上表（本轮 `bash bench/app/run.sh`，`RUNS=3`，best of 3）；标注日期的消融数字是历史证据，
> 不随本轮跑动漂移。

**A 会话表 —— 三格仍全输 C++，但缺口在缩小。** 1M 活跃集约 **24 ns/op**，是 C++ 的 **3.8–4.4×**（C++ 在 5.5–6.3 ns/op 之间跑动，同机约 ±15%），
比 Go 快 1.6×；几何平均 extC/C++ 约 0.41–0.43×。
2026-09 的同一格是 30.52 ns/op / 5.32×，那时 `hashMap` 还是四列 SoA 的池版；本轮的三列平坦存储 +
按机器字打包的控制字节把它压到 4× 上下（见 `docs/design/HASHMAP.md`）。

**历史对照（2026-09-26 消融，池版四列 SoA，只作机制证据）**：

| | ns/op | |
|---|---|---|
| extC 生成代码（当时） | 41.1 | |
| **手写 C · 同样的四列 SoA / 同样的 hash / 同样的负载** | **24.8** | ⇒ 生成代码这一半 ≈ 16 ns/op |
| 手写 C · cap 从 2× 降到 1×（表小一半） | 20.7 | 表尺寸只值 17% |
| 手写 C · keys+slot 合并成 AoS（三列） | 25.8 | **更慢** ⇒ 「少碰一条 cache line」不是答案 |
| C++ `unordered_map` | 5.7 | 剩下的 4.4× 在数据结构/算法 |

两条账当时的结论：① 生成代码那一半被「每条 `hashMap::get` 都被当成会建池」带来的 zone 钩子占掉
23.8% 指令，谓词拆分（`calleeCreatesPool`）做掉了这一半；池退场（2026-12-01 至 12-04）之后生成物里
已经不再有任何 `extc_place_`/zone 钩子被容器程序拉进来。② 数据结构那一半没法靠微调布局消掉 ——
「合并两列更慢、表减半只拿回 17%」——必须换设计；2026-11/12 的 hashMap 重写（值内联三列、装载
17/20、乘取高位索引、无墓碑、按字打包控制字节）就是那一轮。指令条数上 extC 仍比 C++ 多（每条切片
下标带边界检查，这是安全承诺的明账）。

**B 路由表 —— extC 三格全胜 C++**：0.92–0.94× / 0.44× / 0.35–0.36×，200 万条时约 2.8 倍；几何平均
约 0.48 s 对 0.92 s（**1.9×**）。机制与 `bench/stl` 里「B+ 树 vs 红黑树」同向：cache miss 少、
遍历走叶子链线性扫描。Go 最快，但它用的**不是**同一棵树（`map` 负责点操作、排序切片负责区间），
是「各语言最自然的做法」的对比。

**C 日志缓冲 —— extC 是 C++ 的 1.5–1.8×、Go 的 1.4–1.7×**（2026-09 记录是 1.9–2.0×；`string`
迁到地址预留之后每一格的绝对值都降了）。两处都是明账：`string` 没有 `erase` / memmove 原语，截断
是**字节循环**（C++ 一条 `erase`、Go 一条 `copy`）；`find` 是朴素扫描。这一格是「缺什么就付什么」的
直接体现。

## 读这张表前要知道的三件事

1. **extC 的容器是有界检查的**：切片索引越界会带源位置 trap，而 C++/Go 那边是裸索引。
   这一项算 extC 的明账（也是它安全承诺的价格）。
2. **RSS 不是同一种口径**：Go 运行时（GC 预留、栈池）本身就占几十 MB；extC 与 C++ 更接近。
   看**比值**，不要读单个数。
3. **WSL2 + 笔记本 CPU 有 3~5% 波动**：看量级与排序，不要读最后一位小数。
