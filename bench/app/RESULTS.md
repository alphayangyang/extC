# bench/app —— 综合应用场景横评（extC STL vs C++ STL vs Go）

> **自动生成**（`bash bench/app/run.sh`），别手改。
> 口径：三种语言**同算法同参数**，跑同一串操作，打印出来的校验和**逐字节相同**才算数；
> 时间与峰值 RSS 都是 `best of 3`（时间用 bash 内建 `EPOCHREALTIME`，每样本重复 K 次凑到约 0.2 s）。

机器：Intel(R) Core(TM) Ultra 9 275HX · kernel 6.18.33.2-microsoft-standard-WSL2

## 三套实现与编译口径

| | extC | C++ | Go |
|---|---|---|---|
| 编译 | `extc` 生成 C，`cc -O2 -std=c11 -fwrapv` | `g++ -O2 -std=c++17` | `go build`（默认） |
| 会话表 | `stl::hashMapI64<session>` | `std::unordered_map` | `map[int64]Session` |
| 路由表 | `stl::map<i64,i32>`（B+ 树） | `std::map`（红黑树） | `map` + 排序切片 + 二分 |
| 日志缓冲 | `stl::string`（池底） | `std::string` | `[]byte` |

`-fwrapv` 不是「多加的旗子」：extC 把有符号溢出定义成绕回（`docs/MANUAL.md` §8），
编译器驱动自己也是这么编的（`src/main.c`）⇒ 这是生成的 C 的既定编译契约。

## 场景 B：路由表（前驱查找 + 区间扫描）

键是 /24 前缀，值是下一跳。四个阶段：插入/更新 ops 条 → **前驱查找**（最长前缀匹配的
实质：最后一个 ≤ q 的前缀）ops 次 → **区间扫描** ops/4 次（数一个 /16 段里有多少条）→
删除 ops/2 条。数据结构**本来就是三种**（B+ 树 / 红黑树 / map+排序切片）—— 这是
「各语言里最自然的那个有序表」的对比，不是同一个结构的对比。表里的 `ns/op` 分母是
**真实操作数**（插入 + 查找 + 扫描 + 删除 = 2.75 × ops），不是规模参数。

## 场景 C：请求日志 / 动态缓冲

定长 24 字节的记录追加进去；每 512 轮在缓冲里 `find` 上一条记录的前 4 字节
（它只可能出现在**末尾** ⇒ find 扫满整条缓冲）；缓冲到 16 KB 就**截断**掉最老的一半。
extC 的 `string` 没有 `erase`，截断是**字节循环**（`dropFront`：缓冲区字段是公开的
`mut slice<u8>`）；C++ 用 `erase(0,n)`（memmove）、Go 用 `copy` + 重新切片 ——
逻辑同一件事，机制各语言不同，这一格本来就是「缺什么就付什么」。

## 结论与分析（2026-09-26）

> 下面引的**精确数字**来自**独立测量**（callgrind、以及"手工改一处、其余逐字节相同"的 A/B），
> 不随上面那张表 3~5% 的跑动漂移；表里能读到的量级一律写「见上表」。

**A 会话表**：活跃集小（4096）时三个语言在同一条线上（extC 约为 C++ 的 1.7 倍）；活跃集一大
（1M），extC 掉到 C++ 的**近 9 倍**（见上表），而 Go 与 extC 只差一成上下。这一格**不是**
「extC 的哈希函数慢」——三个原因都量过：

1. **zone 钩子在热循环里多发（约 15%）**。`@poolObject` 让 `calleeMakesPool` 把
   `hashMap::get` 也算成「会建池」⇒ 每轮压/弹一次 zone。callgrind（n=2M、active=1M）：
   `zoneEnter` 占 9.87% + `zoneLeaveTo` 占 13.91% = **23.8% 的指令**；A/B（手工去掉那两行、
   其余逐字节相同）实测 **48.42 → 41.12 ns/op（差 15.1%）**。这一条已记在 `docs/PLAN.md` §4
   （量了、暂不动）与 DEVLOG 2026-09-26（第十一段续二）。
2. **指令条数整体是 C++ 的 2.1×**：callgrind **223 对 105 条/操作**。其中每一条切片下标都带
   边界检查 —— 这是 extC 安全承诺的**明账**，不是实现失误。
3. **每条指令更贵（cache）**：`hashMap` 是**四列分离**（tag / keys / slot / bucketOfDense）
   的开地址表，一次命中要碰 3~4 条 cache line；`std::unordered_map` 是「桶数组 + 节点」，
   一次 miss 只碰 1 条。callgrind cache-sim（同为 2M 次操作）：D1 miss **4.05M 对 1.15M**、
   LL miss **0.81M 对 0.41M**。

   顺带**排除两个候选**（都实测过）：**按值返回 `?session`** —— 把 32 字节的会话换成 8 字节
   重跑（校验和不变），extC 47.35 对 49.55 ns/op，几乎不动 ⇒ 不是拷贝的账；**墓碑重建** ——
   把触发线整个关掉，49.47 对 49.62 ns/op（0.16 ns/op）⇒ 也不是它的账。

**B 路由表**：extC **赢 C++**（200 万条时约 1.9 倍，见上表）—— 与 `bench/stl` 里
「B+ 树 vs 红黑树」同向（cache miss 少、遍历是叶子链线性扫描）。Go 最快，但它
用的**不是**同一棵树：`map` 负责点操作、排序切片负责区间 —— 这是「各语言最自然的做法」的
对比，不是同一个数据结构的对比。

**C 日志缓冲**：extC 稳定在 C++/Go 的 **1.9~2.0×**。两处都是明账：`string` 没有 `erase` /
memmove 原语，截断是**字节循环**（C++ 一条 `erase`、Go 一条 `copy`）；`find` 是朴素扫描。
这一格是「缺什么就付什么」的直接体现。

## 读这张表前要知道的三件事

1. **extC 的容器是有界检查的**：切片索引越界会带源位置 trap，而 C++/Go 那边是裸索引。
   这一项算 extC 的明账（也是它安全承诺的价格）。
2. **RSS 不是同一种口径**：Go 运行时（GC 预留、栈池）本身就占几十 MB；extC 与 C++ 更接近。
   看**比值**，不要读单个数。
3. **WSL2 + 笔记本 CPU 有 3~5% 波动**：看量级与排序，不要读最后一位小数。

校验和：场景 A 3 项 · B 3 项 · C 3 项，**合计 9 项通过 / 0 项失败**。
