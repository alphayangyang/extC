# echo server 压测：extC vs Go

**一句话**：同一个负载生成器打四个服务器 —— extC（单线程 epoll + 每连接一个协程）、Go（同条件
`GOMAXPROCS=1`）、Go（默认多核，它的自然形态）、sink（不做任何调度的 Go echo，用来量生成器天花板）。
每一格的数据都逐字节校验过，`ok` 才算数。

## 机器与工具链

- 机器：Linux 6.18.33.2-microsoft-standard-WSL2 · 24 核 · Intel(R) Core(TM) Ultra 9 275HX
- gcc：15.2.0 · Go：go1.26.0 · 生成器：`bench/echo/load.go`（唯一的生成器，两边都用它）
- 参数：REPS=3 ITERS=20000 WARMUP=2000 载荷=[64 1024] 并发=[1 8 64 256 512] 形态=[pingpong pipeline]

## 方法（读数字之前先读这一节）

- **两个真 server 同语义**：每连接一个协程/goroutine，读多少写多少，对端半关即收尾并关 fd；两侧都设
  `TCP_NODELAY`（**这一条踩过坑**：extC 侧最初漏设，流水线 + 1024 字节那一格只有 363 req/s，p50 ≈ 44ms
  —— Nagle 撞上 delayed ACK 的经典停滞；补上之后涨到 73,736 req/s）。
- **两侧同一个缓冲大小**（16 KB）——**这条也踩过坑**：extC 侧最初是 1 KB、Go 侧是 64 KB，于是
  流水线 + 1024 字节那一格读出 5 倍差距；统一之后 extC 在那几格反超（N=64 从 456k 涨到 3.44M）。
- **形态**：`pingpong`（发一批等回声 ⇒ 量往返延迟）· `pipeline`（一次灌 16 批不等 ⇒ 量吞吐）。
- **载荷**：64 B（近乎纯 syscall 与切换成本）· 1024 B。
- **并发**：1 / 8 / 64 / 256 / 512 条连接。
- **每格**：预热 2000 次后正式跑，重复 3 次取 req/s 最高的一次；任何一格校验失败都会被标出来，
  那一格不参与结论。
- **两个 Go 列**：`Go(1核)` 是**同条件**（单线程对单线程）；`Go(默认)` 用满多核，是它的自然形态，
  **不能当同条件读**。

## 每连接内存

| 场景 | extC 常驻 | Go 常驻 |
|---|---|---|
| 空转（无连接） | 1512 KB | 5072 KB |
| 512 条连接活跃 | 9900 KB | 8336 KB |

## 这说明了什么，不说明什么

- 说的是：**同条件下 extC 与 Go 在同一量级**，连接数上去之后 extC 的单线程 epoll 循环更快。
- 说的是：extC 侧任务表**没有容量上限**（512 条连接的格子数据校验全 ok）。
- 说的是：**每连接内存要连着缓冲一起看**。两侧同为 16 KB 缓冲时，Go 因为页是懒加载的更省
  （~6.4 KB/连接 对 extC 的 ~16.4 KB/连接，后者基本就是那条 16 KB 缓冲）；把缓冲换成 1 KB，
  extC 侧就等比例降到 ~1.4 KB/连接。extC 那 16 KB 是**每连接预分配的帧 arena**，不是额外开销。
- 不说的是：多核。extC 目前**没有多线程**，`Go(默认)` 那一列高多少都与它无关。
- 不说的是：真实业务。64 B 的 pingpong 几乎只在量 syscall 与任务切换；大载荷、真实协议栈会得到另一张表。
- 不算数的：任何高过生成器天花板的数字。
