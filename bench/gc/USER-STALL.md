## 1. 口径（本节是判据，不随结论改）

### 1.1 "停顿"的定义（**只允许应用侧时间戳**）

1. **单位**：每个形状的"业务单位"沿用 `bench/gc/APP-STALL.md` §0 的冻结定义（§2.1 表）。
2. **打戳**：在每个单位的**边界**（单位循环体第一行）打一次戳；循环结束后再补一次戳
   ⇒ **戳数 = 单位数 + 1**，`单位延迟[i] = t[i+1] − t[i]`。
   打戳**写在形状源码里**（`bench/gc/stamped/`，由 `make_stamped.py` 从 `bench/gc/src/` 派生，
   每处替换都断言锚点唯一），三语言各用自己的单调钟：

   | 运行期 | 应用侧时钟 | 语义 |
   |---|---|---|
   | extC | `time::now()`（= `extc_time_mono_ns` ⇒ `clock_gettime(CLOCK_MONOTONIC)`） | 单调、不倒退 |
   | Go | `time.Since(base)`（`time.Now()` 的单调部分） | 单调、不倒退 |
   | Java | `System.nanoTime()` | 单调、不倒退 |

3. **停顿 = 单位延迟的长尾**：报告 **p50/p90/p99/p99.9/max**、**超预算单位数**（0.1 ms / 1 ms / 16.7 ms
   三档，判据 `单位延迟 > 预算`）、**最长一次停滞**及其相对**该单位典型延迟（p50）**的倍数。
4. **禁用（写死）**：`extc_rc_collect` 入口戳、Go `gctrace` 的 `Pause`、JVM `-Xlog:gc` 的 `Pause`
   **一律不得**用于"命中判定"或"停顿时长"。本轮**没有任何一行停顿数据来自它们**；
   它们只出现在 §5 的**事后对照**里。上一轮"拿 `extc_rc_collect` 入口戳求交算命中比例"的做法
   **本轮没有重复** ✓。
5. **异常值不剔除**；max 报的是 5 次里**最大的那一次**（不是 5 次中位），另给"5 次中位的 max"。

## 4. 每档一句话判词

**P1（纯短命分配、无引用）**
* extC：**没有任何 `>0.1 ms` 的单位**（5/5 次都是 0），p99=0.10 µs、最长 91.6 µs（复现 985×）—— 生成物不发回收运行期（结构性 0），长尾来自运行期/OS。
* Go：p99=0.15 µs 与 p50 同量级，但 5 次里有 1–3 个单位 >0.1 ms（最长 239.7 µs）—— NumGC=0（**GC 一次都没跑**），这 1–3 个长尾**不是 GC 暂停**。
* Java：**唯一在 1 ms 档命中**的一条（5/5 次各 1 个单位 >1 ms，最长 **1647 µs**）—— 而实测轮 GC 只跑了 **1 次**、`-Xlog:gc` 报的 Pause 也只有 1 次 1.125 ms ⇒ **这一档的长尾主因是 JIT/类加载，不是 GC**（JIT 编译事件 39 次）。

**P2（分块追加，活集单调长）**
* extC：p50=1.36 µs/块、p99=2.47 µs，`>0.1 ms` **5 次里 4 次为 0**（一次为 1）—— 有回收运行期但**没有可观测停顿**。
* Go：NumGC=2，`>0.1 ms` 中位 3 个（最长 399.5 µs）⇒ 这 2 次 GC 的代价**被看见了一次**。
* Java：GC 收集次数 **0**，`>0.1 ms` 中位 1 个（最长 227.6 µs）⇒ 长尾同样不是 GC（JIT 事件 42 次）。

**P3（每轮建链、轮末整片丢）**
* extC：`>0.1 ms` **5 次里 4 次为 0**，p99=0.37 µs —— 结构性 0，符合 §0 的预期。
* Go：NumGC=1，`>0.1 ms` 稳定 2–3 个/跑（最长 335.4 µs）⇒ 一次 GC 换来一次可见长尾。
* Java：GC 收集 **0**，`>0.1 ms` 1 个（最长 238.3 µs）。

**P4（长命只读符号表 + 每单元短命 AST）—— 本轮**唯一**形状里 extC 长尾被证实归因回收**
* extC：p50=7.01 µs 但 **p99=91.3 µs（=p50 的 13×）**、`>0.1 ms` 中位 **8 个/跑**（逐次 2–18）
  ⇒ **同一套应用侧戳的 `EXTC_RECLAIM=0` 对照：p99 从 91.3 µs 掉到 8.1 µs、`>0.1 ms` 从 5 掉到 0**（§5.2）
  ⇒ **这条拖尾是回收造成的，不是猜的。**
* Go：**所有形状里 GC 最勤的一条**（NumGC=15），p99=83.8 µs、`>0.1 ms` 中位 14 个/跑（最多 19）——
  与 extC 的 p99 同量级（91 vs 84 µs），但**命中数更多**（14 vs 8）。
* Java：p99=48.1 µs 反而**比 extC/Go 好**，但最长一次 **1412 µs**（96×）且 5/5 次都有 1 个单位 >1 ms
  —— GC 只跑了 1 次（1.368 ms 的 Pause），**最长那一次与 Pause 同量级**，JIT 事件 63 次。

**P5（滑动窗口 + 长命索引，写密集）—— 口径决定结论**
* extC：单次 p50=**0.02 µs**、p99=0.04 µs，但 p99.9=1.12 µs、最长 **539 µs**；
  批 256 口径 p99=**136.8 µs**、`>0.1 ms` **9 个/整跑**（单次口径是 10 个 —— 同一次长尾在单次口径下
  占了 10 个单位、凑成一个整批后只算 9 个）。
  ⇒ **同一份数据，"请求型"看是"几乎不被卡"（p99 40 ns），"吞吐型"看是"每 ~20 批卡一次"**（p99 137 µs，3400×）。
  `EXTC_RECLAIM=0` 对照：`>0.1 ms` 从 10 掉到 **0**、最长从 390 µs 掉到 66 µs ⇒ 长尾归因回收。
* Go：单次 p50=0.03 µs、批 p99=26.9 µs、`>0.1 ms` 2–3 个/跑；NumGC=2 ⇒ 2 次 GC ≈ 2 个可见长尾。
* Java：单次 `>0.1 ms` **5 次里 3 次为 0**（另 2 次各 1）、批 p99=47.2 µs、最长 146.6 µs；
  GC 收集次数 **0** ⇒ 全部长尾与 GC 无关（JIT 事件 75 次）。

**P6（digraph，单巨分量、换血 96.7%）**
* 三语言**都是"每轮都超 0.1 ms"**（64/64）—— 因为一轮本身就有 444–664 µs，0.1 ms 档对这条形状没有区分度。
* `>1 ms`：extC **0**（逐次 0–1）· Go **3**（2–3）· Java **4**（2–8）⇒ 三语言都在 1 ms 档有零星命中；
  **16.7 ms 档三语言全 0**。
* 最长一次：extC 1023 µs · Go 1276 µs · Java 1734 µs（相对典型 2.1× / 2.9× / 2.6×，**倍数最小**——
  因为 P6 的单位本身就很长，"长尾/典型"这个比值天然被压小，**不能**读成"P6 更稳"）。
* Go 的 GC 账（NumGC=9、ΣSTW=0.81 ms、max=0.234 ms）与 Java 的（收集 0 次）都**解释不了**这 1 ms 档的命中

## 7. 未覆盖与风险

**未覆盖（明确没有做的）**：
1. **没有做时间域对齐**：应用侧单调戳 ↔ Go `gctrace` / JVM `-Xlog:gc` 的进程 uptime 之间没有建立映射
   ⇒ **没有任何"第 k 个单位撞上了第 j 次 GC"的断言**；§5.1 只在**次数/量级**上对照。
2. **P6 的 p99.9 不具统计意义**（n=64）；P6 的"最长/典型"被长单位天然压小。
3. **P6 的 1 ms 档长尾未查清**：Go 的 ΣSTW=0.81 ms、Java 的 0 次收集都解释不了 2–8 个 `>1 ms` 的单位。
4. **P1 的"一次分配"是补充口径**，不是 `APP-STALL §0` 冻结的业务单位（§0 说 P1 无跨单位结构）。
5. **只有一个规模**（§2.1）：没有做规模扫描，"停顿随规模怎么变"未测。
6. **JIT 归因是解释不是判据**：只统计了 `-Xlog:jit+compilation` 的事件数（39–124），
   没有把编译事件与具体哪个单位对齐。
7. **`EXTC_RECLAIM=0` 对照只覆盖 extC**；Go/Java 没有对应的"关 GC"对照
   （那需要 `GOGC=off` / `-XX:+UseEpsilonGC` 这类旗标，属**非默认档**，本轮明确不跑）。
8. **P2 extC 的 p50 2.3× 差（默认 vs 不回收）只报了数，未定位到具体机制**（写屏障？mark 位维护？slab 元数据？）。
9. 仅 Linux/x86-64、单机、当前这个 24 核 15 GiB 环境；**不改任何 `src/`、`tests/`、`tools/`、`docs/CHANGELOG.md`**。

**风险（即使上面都过了也可能出问题）**：
* **Java 的数是"冷启动一次跑完"**（出厂默认 = 不预热）。换 WarmRunner 口径结论会变（JIT 长尾会消失），
  本报告**不主张**"Java 停顿更大"这种跨口径结论。
* **戳缓冲上限**：extC 用固定大小 `[1000002]i64`；若把 argv 规模翻 5 倍以上会静默截断 ——
  但自检 A（戳数==单位数+1）会**直接报红**，不会出假数。
* Go 的 `time.Since` 与 extC 的 `clock_gettime`、Java 的 `nanoTime` 三者分辨率/实现不同
  （实测整圈 13.4 / 19.9 / 15.0 ns），**p50 在 20–40 ns 量级时这个差本身就是 1.5×**；
  ⇒ **P5 单次口径的 p50 排序（extC 0.02 < Go 0.03 < Java 0.04）不足以支撑"谁更快"的结论**。
* 未 pin 核 + 未独占机器（其它成员可能同时在用这台机器）⇒ 长尾里混有调度噪声；
  长尾的**归因**（§5.2 的对照差）比长尾的**绝对值**可信。
* **不承诺"没有任何新风险"**。
