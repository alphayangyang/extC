# FINDINGS.md —— 形状 1、2 的实测结果与**过程中抓到的基准陷阱**

> 数据来源：`bash bench/gc/run.sh`（N=5，24 核，2026-09-24）。
> 口径见 [`SHAPES.md`](SHAPES.md)：时间 = best of N · RSS = 峰值 ·
> **5 个语言的输出必须逐字节一致，否则数字不算数** ✓

## 形状 1 · churn —— 3200 万次分配（两槽交替覆盖）

输出全部 = `511999984000000` ✓（C / C-bump / Rust / Go / Java / extC 六家一致）

| 写法 | 时间 | 峰值 RSS |
|---|---|---|
| C `malloc`+`free`（不透明） | 398.1 ms | **978 MB** |
| **C 手写 bump arena**（与 extC 同模型） | **6.9 ms** | 13.0 MB |
| Rust `Box`+drop | 115.5 ms | 13.2 MB |
| **Go 默认 GC** | **13.0 ms** | 13.0 MB |
| Go `GOGC=off` | 14.3 ms | 12.9 MB |
| Java 默认 GC（含 13–15ms 启动） | 57.2 ms | 50.3 MB |
| Java `SerialGC`（含启动） | 54.6 ms | 46.8 MB |
| **extC arena** | 364.5 ms | **13.0 MB** |

### 三个结论

**① 固定大小对象的"churn"，赢家是 freelist，不是 bump。**
Go 13ms、C bump arena 6.9ms —— 而 Go 快**不是因为 GC**：Go 对 24 字节对象走的是
mcache 的尺寸类 freelist（1–2 条指令），GC 只是偶尔扫。**这是"分配快路径"的胜负，不是"回收"的胜负** ✓
⇒ **真正该测 GC 的形状是形状 2（每轮重建、要真的回收），不是这个** ✓

**② extC 在这里慢，机制是确定的（不是"编译器不行"）：**
`extc_arena_release` 对**每个块**调 `free()`，而 `extc_arena_alloc` 的块从 **4096 字节**起。
"每轮建/每轮还"的形状下 ⇒ **每个对象一次 `malloc` + 一次 `free`**。
实测（`--wrap=malloc/free` 计数）：extC = **3200 万次 malloc + 3200 万次 free**；
而 extC 的机制本该是"每块一次 malloc 切 ~170 刀" ⇒ 块太小，退化成了逐对象分配 ✗
⇒ **可优化点（明确的）**：`extc_arena_release` 保留一个小块缓存（freelist），
   或把块大小提上去。这与"zeroed 保证"不冲突 —— 缓存块复用时 memset 照做 ✓

**③ extC 仍然比 C 的 `malloc+free` 快 1.7×**（364 vs 398）——
因为它的 4KB 块能切 ~170 个对象，不是每个对象一次 malloc ✓
而 C 的 978 MB 峰值是 glibc malloc 在这个"每对象一对 malloc/free"形状下的真实表现 ✓

## 形状 2 · rebuild —— 2 万轮 × 每轮 1000 节点链

输出全部 = `9990000000` ✓（六家一致）

| 写法 | 时间 | 峰值 RSS |
|---|---|---|
| C `malloc`+`free` | 199.3 ms | 13.0 MB |
| Rust `Box` 链 + drop | 240.2 ms | 13.0 MB |
| Go 默认 GC | 234.0 ms | 13.0 MB |
| Go `GOGC=off` | 278.9 ms | **324.7 MB** |
| Java 默认 GC（含启动） | 140.4 ms | 188.1 MB |
| Java `SerialGC`（含启动） | 108.0 ms | 105.6 MB |
| **extC arena 出块即还** | **92.9 ms** | **13.0 MB** |

### 结论

**① extC 第一（92.9ms），且内存最低（13MB）。**
比 C 的 malloc+free 快 **2.1×**，比 Go 快 **2.5×**，比 Java `SerialGC` 快 **16%**——
而且 Java 那 108ms 里还有 13–15ms 是 JVM 启动 ⇒ **扣掉后 extC 领先约 34%** ✓

**② `GOGC=off` 是这组里最有信息量的一格：**
Go 关掉 GC 从 234ms 变 **278.9ms**（更慢），峰值从 13MB 涨到 **324.7MB**。
⇒ **"GC 的代价"在这形状里不是停顿，而是内存换时间**；
关掉 GC 反而更慢，说明 Go 的分配快路径在开 GC 时也正常工作、GC 只是按时回收 ✓

**③ Java 的两档说明"GC 选择"值 30%：**
默认 GC 140.4ms / 188MB vs `SerialGC` 108.0ms / 105.6MB ⇒
**这个形状下 SerialGC 又更快又更省**（对象年轻、存活率低，分代反而多付了代价）✓

## 踩到的两个基准陷阱（**都会让数字完全失真**，写下来免得重犯）

**陷阱 1：`-O2` 会把 `malloc`+`free` 消掉或搬走。**
- 形状 1 最初写"每轮 malloc 一个立刻 free"：`objdump` 里 `with_free` 与 `no_free`
  **都是 0 个 malloc 调用** ⇒ 测出 0.4ms，假的 ✗
- 形状 1 第二版：32e6 次 malloc、**0 次 free**（GCC 证明 free 可省，结果仍正确）✗
- 形状 2：修完不透明分配后，整段**一个 malloc/free 都没有** ——
  GCC 证明这条 1000 节点链不逃逸，**整个搬到栈上**了 ✗
⇒ **规避**：分配器走 `volatile` 函数指针（挡住内建替换），
  并且**报数字时必须能回答"objdump 里还剩几个调用"** ✓

**陷阱 2：形状里"跨作用域赋值"会改变内存模型，让对比变成假对比。**
extC 版最初把两个槽声明在**循环外** ⇒ 那个 `new` 真的逃逸出块 ⇒
编译器（正确地）把它提到帧层 ⇒ 常驻内存 **13MB → 495MB** ✗
**这不是"arena 慢"，是形状写错了** ⇒ 修法：临时变量放在本轮作用域内 ✓

## 附：arena 块复用（2026-09-24 修）

**改了什么**：`extc_arena` 增加一个 `spare` 字段 —— release 时**留一块**不 free，
下次 alloc 在 arena 为空时直接接管它（`used = 0`）。函数退出改调 `extc_arena_destroy`
（release + 把 spare 也 free），否则那块就漏了。

**效果**（同一台机器，交替测量）：

| | 改前 | 改后 | |
|---|---|---|---|
| churn（3200 万次分配） | 362.7 ms | **140.9 ms** | **2.57×** ✓ |
| churn 的 malloc/free 次数 | 32e6 / 32e6 | **1 / 1** | 机制对上了 |
| rebuild（2 万轮 × 1000 节点） | 93.0 ms | 100.7 ms | **+8.3%** ✗ |

**净账**：一侧 2.57× 的收益，另一侧 8.3% 的代价。

**没查清的部分（诚实记）**：rebuild 这 8% 我用 callgrind 定位到
"总指令数 +17%，其中 `main` 多 260 万、`extc_arena_alloc` 少 60 万"，
但没有继续追到具体那几行 —— 试过五种 alloc 写法（含"只判空"这种零热路径开销的），
最小也只压到 +7.8%。**要接着查就从"`destroy` 在返回值处的展开"入手** ✓

**过程里被实测否掉的写法（别重走）**：
- `if (a->spare && a->spare->cap >= n && !(a->top && 还有空间))` —— 每次分配多 ~16 条指令，
  callgrind 实测总指令 +20% ✗（spare 本来就是一整块，`cap >= n` 恒真，这个条件白付）
- `if (!a->top && a->spare && a->spare->cap >= n)` —— 同样白付 ✗
- release 里加 `p &&`（"只有多于一块时才留"）—— 看着像省，实际把 churn 打回 389.9ms ✗
  **因为该缓存的正是一个块的那种 arena**（紧循环里每轮建/每轮还）

## 附 2：`--explain-memory` 的判据还没定（2026-09-24）

**这是什么**：`extc --explain-memory f.extc` 打印每个分配站点落在哪只 arena、
是否在循环里、以及"是否落在比它所在块更浅的层"。

**已确认能分开的**（`/tmp/mem_*.extc` 四形状 + 本目录两形状）：

| 形状 | 实测 RSS | 报告判定 |
|---|---|---|
| `mem_3`（循环里 `new`，另有 `last = n.value`）| **159,660 KB** | 标记 ✓ |
| `mem_1` / `mem_2` / `mem_4` | 1,644–1,704 KB | 不标记 ✓ |
| `churn`（本目录） | 1,008 KB | 不标记 ✓ |
| **`rebuild`（本目录）** | **1.7 MB（2000/20000/200000 轮都一样）** | **仍被标记 ✗ 误报** |

**⇒ 判据不可靠，别当成定论。** 试过两条、都被实测否掉：

1. `arenaLevel < 循环体层`（循环体层 = 该循环内站点 `lexicalLevel` 的最小值）—— `rebuild` 仍命中 ✗
2. `minAt < 循环体层` —— `mem_3` 反而不命中（它的 `minAt=1` 而非 0）✗

**卡在哪**：**"站点落在哪只 arena"与"那只 arena 在哪释放"是两套规则**。
`rebuild` 的站点落在 `__extc_a[3]`，而 `__extc_a[3]` 在**每轮末**释放（生成的 C 第 137 行）⇒ 不涨。
只看层号推不出释放点。

**下一步要做对，只能**：把"这个站点属于哪个循环体块"从**检查器**里直接记下来
（它维护 `c->scopes.len`，那是权威；从 AST 推循环体层已经错过两次），
或者干脆只报事实、不下结论（当前形态）。

**已经能用的部分**：四形状能分开，所以它足以回答"哪个站点在帧层"这类问题 ✓

## 附 3：`extc_arena_alloc` 内联 = 3.9×（2026-09-24）

**发现方式**：rebuild 比"手写一块到底"慢 2.8×，用 callgrind 看到**指令数恰好 2×**，
再 `objdump` 发现内层循环里**每次分配都有一次 `call extc_arena_alloc`** —— GCC 不肯内联它
（函数体不小 + 里面有 OOM 错误分支）。

**实测（同一份生成代码，只加 `__attribute__((always_inline))`）**：

| | 修前 | 修后 |
|---|---|---|
| `rebuild`（2 万轮 × 1000 节点）| 100.7 ms | **25.7 ms** |
| `churn`（3200 万次分配）| 140.9 ms | **38.2 ms** |
| 二进制体积 | — | **小 80 字节**（内联反而更小）|

**ISO C 的问题（重要）**：生成代码此前是**严格 ISO C99**（`cc -std=c99 -pedantic-errors` 接受），
而 `always_inline` 是 **GNU/Clang 扩展**（ISO C 只有 `inline`，没有"强制内联"）。
⇒ 已加守卫：`#if defined(__GNUC__) || defined(__clang__)` 才用属性，否则退回普通 `static inline`。
⇒ 带守卫后 `-std=c99 -pedantic-errors` **仍然通过**，性能不变 ✓
⚠️ 没用 `__has_attribute`：那本身就是扩展。

**另外试过、无效的（别重走）**：
- 跳过"从未分配过的层"的 `release`：指令数降了，**时间没变**（101.6 → 102.7ms）⇒ 已回退 ✗
- 同时内联 `extc_arena_release`：无额外增益（26.0 → 26.1ms）✗
- `__attribute__((hot))`：与 `always_inline` 同效（25.8ms），但没有"保证"语义
