# bench/zero —— 「清零值多少钱」＋「epoch 染色值多少钱」

## 0. epoch 染色 / 保留 / O(1) 清空：并排对照（**主表**）

形状：循环体 = 一个地方，每轮塞 8 条、然后清掉。**2000 万轮**（`ROUNDS`/`PER` 可调）。
四种做法：

| | 做法 | 时间 | 每轮 |
|---|---|---|---|
| **A** | 每轮重建（`drop` + `new`，板块进 malloc） | 6.949 s | 347.5 ns |
| **B** | **O(1) 清空**（`extc_pool_reset`：翻代 + 游标归零，槽表一个字节不写） | **0.209 s** | **10.45 ns** |
| **C** | 重建 + 保留池（阶段 b：板块归还时留下复用） | 0.366 s | 18.30 ns |
| **D** | 物理清空整张槽表（O(cap)，每个槽都写成空闲） | 13.429 s | 671.5 ns |

⇒ **B 是 D 的 64 倍、A 的 33 倍**。B 与 D 都是"清空"，差别只在
**逻辑清空（O(1)，翻一位）对物理清空（O(cap)，逐槽写）** —— 这就是染色那一层的全部价值。

**C++ 基线**（同一形状，`vector<pair<int,int>>`）：

| | 做法 | 每轮 |
|---|---|---|
| C++ A | 每轮重建 vector | 15.85 ns |
| C++ B | `clear()`（保容量，O(1)） | **3.70 ns** |
| C++ C | `swap` 释放再建 | 16.20 ns |

⇒ 口径：extC 的 B 是 10.45 ns 对 C++ 的 3.70 ns（**2.8 倍**）。
C++ 每轮重建只要 15.85 ns（栈上对象 + 容量复用），而 extC 的 A 要 347.5 ns ——
**那 22 倍的差就是"每轮真去 malloc/free 板块 + 摘挂池链"的代价**，
也正是 epoch 染色要消掉的那部分（消掉之后 B 只比 C++ 的 `clear()` 慢 2.8 倍）。

账（四种做法都不漏）：A/C 的 `live=0`（每轮真的 drop 了）；B/D 的 `live=49152`（池留着，这正是 O(1) 的前提）；
`keep` 只在 C 那条路上不为零（保留池命中了）。

复现：`ROUNDS=20000000 PER=8 bash bench/zero/run.sh`（`ROUNDS` 小了全是噪声 —— O(1) 那版快到测不出）。

这一组是两把尺子：**epoch 染色值多少钱**（§0 主表）与 **清零值多少钱**（§1 起）。
**所有数字都是本机、`-O1`、best of 3。**

## 1. 同一个形状，两条路

形状：循环里拿一块内存、只写首尾两个元素、丢掉（`extc_pool_drop`）。

| 块大小 | `poolSlice`（清零） | `poolSliceRaw`（不清零） |
|---|---|---|
| 400 KB（10 万 i32）× 20,000 轮 | 0.09 s | **0.00 s** |
| 32 MB（400 万 i64）× 200 轮 | 0.12 s | **0.00 s** |

⇒ 清零就是这两条路的**全部**差别，而它在大块上占满了整个时间。

## 2. 清零的价格由容量决定（C 直接测：`malloc` + `memset` + `free` 每轮）

| 块大小 | 每轮 | 吞吐 |
|---|---|---|
| 4 KB | 28 ns | 145 GB/s（缓存内） |
| 400 KB | 4,633 ns | 88 GB/s（缓存带） |
| 4 MB | 76,025 ns | 55 GB/s |
| 16 MB | 441,874 ns | 38 GB/s |
| 64 MB | 25,553,282 ns | **2.6 GB/s**（掉出缓存，mmap/页错误的代价显形） |

⇒ 400 KB 以内清零是**内存带宽**的事（每字节约 11 ps）；64 MB 那一档已经不是带宽而是
**页**的事（差 20 倍）。所以「不清零」的收益不是常数，它**随容量放大**。

## 3. 清零之后用户还要把整块写一遍 —— 那一遍是不是白花的？

形状：拿一块 10 万 i32（400 KB）的板块，然后**把每个元素都写一遍**（用户真会这么干），2000 轮。

| 路径 | 时间 | 说明 |
|---|---|---|
| `poolSlice`（先清零，再覆写整块） | 0.04 s | 清零那一遍是白花的 |
| `poolSliceRaw`（直接覆写整块） | 0.03 s | —— |

⇒ 即使"每个字节都会被用户写掉"，**先清零仍然多花 33%**。
（400 KB 略超 L2，清零还会把数据逐出缓存，所以省下的不只是那 400 KB 的写带宽。）

## 4. 「不清零还能保证第一次读是 0」在 Linux 上成立吗？（`/tmp/zeropage.c`）

| 检查 | 结果 |
|---|---|
| ① 新 `mmap` 的 16 MB 直接读，非零字节数 | **0** ⇒ 内核给的是零页 |
| ② 写脏 + `madvise(MADV_DONTNEED)` 之后再读，非零字节数 | **0** ⇒ 物理页可以丢掉、重读还是零 |
| ③ `free` 之后再 `malloc` 同一尺寸，非零**页**数 | **0/4096**（且返回的是**不同地址** ⇒ glibc 走了 mmap，没把脏数据还回来） |

价格（16 MB，每轮真的读一遍以挡住优化掉）：

| 路径 | 每轮 |
|---|---|
| `malloc` + `memset` | **414 µs** |
| `malloc` + `free`（只碰首字节） | 0.0 µs |
| `mmap` + `munmap`（只碰首字节） | **3.8 µs** |
| `calloc`（400 KB / 16 MB） | 5.84 µs / 394 µs（`calloc` 在中等尺寸上**不比** `malloc`+`memset` 快） |

⇒ 结论：**"不清零但第一次读是 0"不需要任何额外检查机制** —— 内核的零页就是那个机制
（未触碰的页永远读作 0）。所以「清零」从"每次分配都必须付费"变成"用户真去写那些页时才付费"。
这不是把承诺变弱，是把实现从"立刻兑现全部"换成"按需兑现"。

## 5. 结论（写进 POOLS.md §7.4.1 的那条）

- **池自己的簿记表**（`vals`/`slots`/`ent`）不需要清零（`pFree` 把 `low == 0` 认作空闲），
  走 `poolSliceRaw` 之后「每轮建一个 `cap=10 万` 的池」2000 轮：**1.09 s → 0.012 s**。
- **用户可见的 `new T[n]` 不走这条路**：「新分配读作 0」是语言承诺，`poolSlice` 照旧清零。
- 用户可见那一档还剩最后一个杠杆：**让清零按需兑现**（内核零页 + `madvise` 回收），
  按 4 的表，16 MB 一次分配的 414 µs 全是立刻兑现的代价。

## 6. 判据有牙（反例：`exit_cost_tooth.extc`）

`tests/pool/run.sh` 里"地方退出的代价随池数走得平"那条判据，用这个反例证明它有牙：
让每池的成本 ∝ 池数（内部多跑 n 次操作），总操作数固定 4e6：

| N | ns/次 |
|---|---|
| 200 | 50 |
| 2000 | 405 |
| 20000 | 3975 |

⇒ 比值 79 倍，判据的 1.5 倍上限必响。**真的那版三个 N 都是 10.67 ns/次（比值 1.0）。**

**真收缩那条判据的有牙证明**（在运行时里做，做完已还原）：把
`extc_pool_freeSelf` 里的 `extc_pool_releaseBlocks(r)` 改成只在该环境变量下执行，再跑判据 ——
期末字节账从 `bytes=0` 变成 **`bytes=1,600,000,000`**，峰值 RSS 从 2,336 KB 变成
**1,569,532 KB**（判据阈值 8 MB，差 650 倍）⇒ 两条判据都抓得住。

## 7. 否掉一条路：mmap 拿零页（2026-09-26 第十段）

**想法**：大块分配改用 `mmap`——未触碰的页由内核保证读作 0，于是不必 `memset`。

**测错了第一次**：用"只碰首尾字节"的探针量，得到 `mmap` 比 `malloc+memset` 快 58 倍。
那个数**是真的，但口径不对**——页根本没被分配，不代表真实容器的行为。

**逐页读一遍（编译器抹不掉 memset）之后的真数字**（`bench/zero/zero_source.c`，-O1/-O2 一致）：

| 块 | malloc+memset | calloc | mmap+munmap |
|---|---|---|---|
| 4 KB | 0.0 µs | 0.0 µs | 3.2 µs |
| 64 KB | 0.9 µs | 0.8 µs | **19.1 µs** |
| 1 MB | 20.9 µs | 18.5 µs | **251.9 µs** |
| 16 MB | 1456.3 µs | 786.5 µs | **4119.5 µs** |
| 64 MB | 29192.8 µs | 16499.4 µs | 16484.9 µs |

⇒ **只要真的读写这块内存，`mmap` 在每一个尺寸上都比 `memset` 慢 4~46 倍**（munmap + 重新
映射 + 页故障都算在里面）。**这条路否掉**，理由不只收益为负，还有两条更硬的：

1. **平台**：`mmap` 是 POSIX；Windows 要 `VirtualAlloc`。而生成的 C 到今天为止只依赖
   `stdint/stdbool/stddef/stdio/string/stdlib`，**一处平台条件编译都没有** —— 为了这个负收益
   引进仓库里第一处平台依赖，不划算。（这也是推翻它的决定性理由。）
2. 它顺带暴露了我一个真 bug：`extc_pool_take_raw` 的 malloc 分支没初始化 `mmapped` 标记
   ⇒ 垃圾值非零时走 `munmap` ⇒ 真泄漏（ASan 直接报）。**标记不写就是垃圾**这条，在任何
   "块头带来源标记"的设计里都会重复出现。

**留下的唯一候选**：`calloc`（纯标准 C）在 **≥ 1 MB** 上有 1.1~2.4 倍（1 MB 18.5 对 20.9 ·
4 MB 145.8 对 207.9 · 16 MB 786.5 对 1456.3），而 **≤ 256 KB 时没有任何收益**（0.8 对 0.9）。
两行改动、零平台依赖、零新 API —— 但因为收益小、又要记一条新阈值，**暂不做**，
留作备选（真要做的判据：`bytes >= 1 MB` 才分流，且要有一个判据钉住"小块没走 calloc"）。

**教训（写下来免得再犯）**：**先决定"这块内存会不会被读"，再选量测口径。**
"只碰首尾"和"逐页读"能给出方向相反的结论，而 memset 的作用恰恰只在后者里体现。

## 8. 为什么 extC 比 C++ 慢：callgrind 剖析（2026-09-26 第十段）

形状与主表 §0 的 B 一致（循环体 = 一个地方，每轮塞 8 条、读一遍、清掉），两边输入相同。
工具：valgrind（本机没有 perf）。复现：`N=300000 bash bench/zero/prof.sh`

| | 指令/轮 | 分支/轮 | 分支预测失败 |
|---|---|---|---|
| extC B | **261.6** | 59.2 | **3.4%** |
| C++ B | **174.2** | 38.0 | 5.4% |

墙钟是 10.45 ns 对 3.70 ns（**2.8 倍**），而指令只多 **1.55 倍**。两件事说明白了：

1. **不是 cache、不是分支的锅。** 数据布局与访问模式两边一样（都是"一张值数组 + 一张元数据
   数组 + 每轮读一遍"），而 extC 的分支预测**还更好**（3.4% 对 5.4%）。所以那 2.8 倍里，
   指令条数只解释 1.55 倍，剩下的是**每条指令更贵**。
2. **多出来的 87.4 条指令/轮，是安全检查本身。** 生成物里每轮都在跑：
   `extc_checkedIndex`（每次下标访问一次边界检查）· `extc_narrowI`（每次窄化写一次范围检查）·
   池的 `pStaleSelf`/`pPoisonSelf` 守卫 · 以及 `extc_pool_reset` 单独占 **8.04%**
   （42M/522M 条指令，21 条/轮）。

**这就是那 2.8 倍的性质**：它不是"extC 的容器写得笨"，而是**用内存安全与生命周期保证换来的**——
每一次越界、每一次从已死掉的地方里取值，在 C++ 里是 UB（可能什么都不发生），在 extC 里是
一条检查 + 一次带位置的 trap。C++ 之所以快，是因为它在这些地方**什么都不做**。

**下一步该量什么**（按收益排序，都还没做）：
- `extc_pool_reset` 那 21 条/轮：里面有没有可以省掉的重置（它是 O(1)，但常数不必然最优）；
- 守卫（`pStaleSelf`）能否在**编译期证明不必要**的地方省掉——它每次都读 `pidGen` 与
  `extc_pool_generation(pid)`；
- `extc_arena_release` 在每次下标访问前都发射一次（生成物里 40 处），虽然它只是个
  `while (top)` 检查、占了不到 1%，但它想说明的是 codegen 的**发射位置**是不是可以更省。
