# Four-axis cross-language benchmark: extC against C++, Go, and Rust

Generated by `report.py` from `RESULTS.tsv` and `out/serve-*.tsv`; regenerate with
`./run.sh && python3 report.py`. Every number below is measured on the same dataset,
the same machine, and, for the network axis, by the same client.

The dataset is `data/log.tsv`: 2,000,000 rows of a synthetic request log
(timestamp, user, site, path, status, latency, bytes), 71 MB, generated once by
`gen/gen.c` and read by every arm. The four axes are the four workloads:

- `etl` -- single-threaded scan, parse, and aggregate the whole file. The
  conventional axis: no allocation past the read buffer, one pass, tight loop.
- `sessions` -- the same scan plus a per-request message object and a session table
  keyed by user with a 300 s TTL, where expired sessions are evicted. The reclamation
  axis: roughly three quarters of the users seen go out of the window.
- `parmix` -- a parallel pass over the same records: every record goes through 64
  rounds of a mixing function and the results are folded into one checksum. The
  parallel axis, at 1, 8, and 24 threads.
- `serve` -- a TCP request/response loop over the per-site aggregates computed from the
  file, measured with the shared C client at 64 connections x 8 in flight and 200,000
  requests. The concurrency axis.

Timings separate `read_ms` (ingest the 71 MB file) from `work_ms` (the workload), and
the tables compare `work_ms` only. Single-threaded workloads are pinned with `taskset`,
`parmix` is pinned to the same number of cores as threads, and `serve` runs the server
on one core with the client on three others.

## What each arm does differently

- **C++** (`cpp/main.cpp`): a hand-written state machine over the mapped bytes; one
  `new`/`delete` message object per record in `sessions` and a `std::unordered_map` of
  session pointers; epoll for the server; `std::thread` over fixed offsets for `parmix`.
- **extC** (`extc/main.extc`): the same state machine; the record is a struct value in
  the loop body (a frame object, the same lifetime Go gets when `&Event{}` does not
  escape) and the registry is a `hashMapI64<session>`, read and written through the
  table's dense value column (one probe, then an index into the values; going through the
  value-pool handle costs a slot-array load plus generation and epoch checks and measured
  176.3 ms against 141.9 ms); eviction compacts the survivors into a fresh table, which is
  faster than 152k swap-removes (207-238 ms against ~180 ms), not a workaround --
  `hashMapI64::remove` is callable since instance-time effect summaries landed; `par` for
  `parmix`; one
  coroutine per connection on the `std::coro` scheduler for the server; replies of one
  read burst are buffered per connection and flushed with one `send` before the
  coroutine waits for more input, which is the same flush-per-burst shape as the
  C++ arm.
- **Go** (`go/main.go`): the same shape with `&event{}` per record and a `map` of session
  pointers, so the reclamation axis is the Go garbage collector; goroutines for both the
  parallel and the network axis.
- **Rust** (`rust/main.rs`): the same shape with `Box<event>` per record and a `HashMap` of
  sessions, so the reclamation axis is dropping boxes; `std::thread` for `parmix` and
  threads for the server.

Every arm prints the same checksums, which is what makes the table comparable: a row
that disagreed on `cs=` would be measuring a different amount of work. The `serve`
checksums are the server's own, and the client independently verifies every reply.

## Caveats

- `read_ms` is excluded from the comparison, but it is in the logs: it is dominated by
  the syscalls, not by the language.
- WSL2 does not expose CPU frequency or power state, so absolute times drift between
  runs; only ratios taken in the same session should be compared.
- The `sessions` axis is deliberately not symmetric: it measures what each language's
  ordinary allocation discipline costs on the same workload, not one allocation strategy
  ported four times.
