# 协程微基准（bench/coro）

机器：Intel Ultra 9 275HX，24 核，Linux。编译器：本项目 `-O2`（生成物合同 `-std=c11 -fwrapv`），
Go 1.26.0 `GOMAXPROCS=1`。所有数字单位 ns，取多次平均。

## 怎么跑

    ./build/extc -w --no-line-map -o /tmp/mb/deep_gen.c <程序>.extc
    cp bench/coro/deep_main.c /tmp/mb/ && gcc -O2 -std=c11 -fwrapv -DDEPTH_N=<n> -o X /tmp/mb/deep_main.c
    # 深链程序由脚本生成（见 git log），每层形如：
    #   fn Lk(n: i64) -> coroutine<i64> { var d = L(k-1)(n)  while d.next() { yield d.value() } }
    GOMAXPROCS=1 go run bench/coro/deep.go     # Go 对照

`micro.extc` / `deep1.extc` / `deep3.extc` 用 `micro_main.c` / `deep_main.c` 计时。

## 数字

| 操作 | extC（无栈 + 任务 place）| Go 1.26 |
|---|---|---|
| 普通函数调用 | 0.22 ns | — |
| 一次挂起 + 恢复（浅）| 0.77–1.4 ns | 120.7 ns（chan 交接）|
| spawn + 驱动（10 步）| 14 ns | 507.9 ns（纯 `go`，不等）|
| **深 1 层**往返 | 0.77 ns（展平）/ 1.58 ns（未展平）| 1273.6 ns |
| **深 10 层** | 0.78 / 7.2 ns | 1318.8 ns |
| **深 50 层** | 0.77 / 64.0 ns | 3027.7 ns |
| **深 200 层** | **0.77 / 267.6 ns** | **7003.0 ns** |
| 对照 `epoll_wait(0)` | 58.9 ns | — |
| 对照 `write`+`read` 各 1B | 220.5 ns | — |

## 结论

1. **深链默认免费**：`-O2` 下 gcc 把整条链**内联展平**（帧是普通值、编译器可见），200 层与 1 层同为
   0.77 ns —— 有栈做不到，它的状态必须在栈内存里。
2. **不展平时每层 ≈ 1.3 ns**：200 层 268 ns，仍是 Go 深调用往返的 1/26。需要 O(1) 任意深度时上
   trampoline + 最深层指针（见 §4.4），但**由实测决定**，不是默认。
3. **Go 在深处崩的原因是栈增长（拷贝）**：新鲜 goroutine 初始 2–8 KB，50/200 层触发拷贝 ⇒ 3 µs / 7 µs。
   注意口径：这是"spawn + 递归 + 交接"的往返，不是单次切换；**已长好的** goroutine 反复深调用不会付这笔钱。
4. 一次切换 ≈ **syscall 的 1/60**（1.4 ns vs 58.9 ns）⇒ I/O 场景里切换完全不重要；该优化的是
   **系统调用次数**（一次 `epoll_ctl` ≈ 42 次切换）。

## 冷 vs 热（Go 那一列必须分开，否则结论是错的）

| | 冷（每轮新 spawn 一个 goroutine）| 热（一个热身好的 goroutine 反复）|
|---|---|---|
| `go` spawn | 508–658 ns | **318.7 ns**（第 3 批，栈缓存与 goroutine 结构已热）|
| `go` 深 1 往返 | 1273.6 ns | **247.9 ns** |
| `go` 深 50 | 3027.7 ns | **308.7 ns** |
| `go` 深 200 | 7003.0 ns | **397.6 ns** |

**修正**：上面那个 7003 ns 不是 Go 的常态，是我的基准形状造成的 —— 每轮**新 spawn** 一个 goroutine 去深递归，
于是每轮都付"栈增长（拷贝）+ 首次 touch 页错误"。热起来之后，Go 深 200 层往返 **398 ns**。

于是三列的正确读法：

- **切换**：Go ~120 ns（chan 交接，与业界常引值一致）✓ 不拉；热深 200 层 398 ns。
- **深链每层成本**：Go ≈ 0.75 ns/层（cache 成本）· 我们未展平 ≈ 1.3 ns/层 —— **同一量级** ✓
  （200 层：Go 398 ns vs 我们未展平 268 ns；我们**展平**时 0.77 ns ⇒ 赢约 500×）
- **spawn**：Go 319–658 ns + **2–8 KB/任务** vs 我们 **14 ns + 几十字节** ⇒ **这才是持久的结构差异** ✓
  它来自"每任务一条栈"，而且**摊销不掉**（每个任务都要一条栈，栈缓存只省 malloc，不省内存与首次 touch）。

## 基准方法论（踩过的坑，别再踩）

- 工作量必须**被观察**（返回累加值 + volatile 汇总），否则整段被优化掉 —— 曾测出 0.15 ns/次这种亚周期数字。
- 外层调用过 **volatile 函数指针**，否则纯调用被提到循环外，时间成 0.00 ns。
- 生成失败时**不许跑旧二进制**（踩过一次，数字全错）。
- 引用了未初始化帧字段时数字无效（嵌套 spawn 的 bug，已修，见 git log）。

## 每任务内存与 N 个活任务（阶段四那一格）

`bench/coro/run_liveN.sh`：同形的两批（**冷** = 堆/页/malloc bin 都新；**热** = 同一进程里的第二批量）。
两边都量"把任务推到**挂起点**"的成本：extC 是 spawn + 驱动一次（跑到第一个 `yield`），
Go 是 `go` 语句（spawn 循环只计时，等它们挂到无缓冲 channel 上的等待不算 —— 不等的话量到的是
"还没分配栈的 goroutine"，数字会假）。

Ultra 9 275HX · 24 核 · gcc 13.3 · `-O2 -fwrapv` · Go 1.26.0 `GOMAXPROCS` 默认 · N = 10000：

| | extC | Go 1.26 | 倍数 |
|---|---|---|---|
| spawn+驱动到挂起 · **冷** | **77–82 ns** | 1168–1378 ns | **~15×** |
| spawn+驱动到挂起 · **热** | **75–81 ns** | 1495–1720 ns | **~19×** |
| 每任务内存 · **冷** | **192 B** | 2859 B | **~15×** |
| 每任务内存 · **热** | **172 B** | 2761–2779 B | **~16×** |
| 20000 个活任务 | 进程 RSS **3.3 MB** | `HeapAlloc` **12.7 MB** | ~4× |

extC 每任务的 172 B ≈ 帧（几十字节）+ 24 字节句柄 + 任务 place 的第一块 + malloc 头。
**它是随 N 线性涨的**（每个任务一份存储），赢在常数：**没有栈分配器、没有内核对象、没有运行期队列**
—— 驱动是调用者自己走数组。Go 那一列的 2.8 KB 是初始栈 + `g` 结构 + 调度器记帐。

### 这一格是怎么从 41.8 MB 变成 3.3 MB 的

第一次量：10000 个活任务 **41.8 MB**（4.3 KB/任务）—— 比"帧 + 24 字节句柄"高两个数量级。
原因是运行期的 arena 分块写了一行 `cap = n > 4096 ? n : 4096`：**每块下限 4096 字节**，
而一个协程的帧只有几十字节 ⇒ 每个任务白白吃掉 4 KB。

改成**自适应增长**（首块按需、下限 64 字节、之后倍增、上限 1 MB）之后同一程序 3.3 MB
（进程 RSS 差算下来 192 B/任务，**12.4×**）。倍增保证了普通程序里"循环里反复分配"的 malloc
次数和以前一样（几块之后就追上 4 KB），而协程这种**一次性分配**只付它要的那点。

判据 `tests/coro/coro_mem.extc` 把这条钉住了：10000 个活任务常驻 ≤ 8 MB，且 `extc_task_live()`
必须等于 N（确认它们真的都活着）—— 回退到 4096 下限会立刻红。
