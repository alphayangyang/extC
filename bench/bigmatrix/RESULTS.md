# bench/bigmatrix —— 六语言重负载横评

> **自动生成**（`bash bench/bigmatrix/run.sh`），别手改 ✓
> 口径见 [`SPEC.md`](SPEC.md)：数据**全部从 stdin 读**（`gen.c` 用同一个 pcg32 生成，程序里不许自己生成 ✗）·
> 每语言开满自己的优化 · 时间 = **best of 5** · RSS = **峰值**。
> 每个形状的六份输出**逐字节一致**才算数：**全部一致 ✓**

机器：Intel(R) Core(TM) Ultra 9 275HX · 24 逻辑核 · kernel 6.18.33.2-microsoft-standard-WSL2

⚠️ **同一格两次完整跑之间大约有 3~5% 的波动**（WSL2 + 笔记本 CPU 的调度）⇒
   看**量级和排序**，不要读到最后一位小数 ✓（表里已经是 5 次取最快，已经压掉一部分抖动）

## 怎么读这四张表

· **只看运行时间与 RSS**；构建时间单独一张表（extC 拆两段：前端 + 编它吐的 C）✓
· **几何平均那一行是全表的结论**：每个形状以「该形状最快者」为 1.00，再对五个形状取几何平均 ⇒
  谁的综合排名第一 ✓ extC 在六个语言里排第一，靠的是两个形状的**大幅**领先 ——
  一个把「分配 + 递归」变便宜（`bt`），一个把「分配 + 回收」变免费（`rebuild`）✓
· **extC 不是每个形状都快**：`radix` 上它比 C 慢，那是两笔明账 ——
  **切片索引带边界检查** + **`new` 零初始化**（`SPEC.md` 的坑与设计承诺）⇒ 不藏 ✓
  同一个设计在 `cdq` 上抓到了一个**真越界**（见下一节）✓
· **RSS 那列 extC 全部 ≤ C**：arena 是 bump 分配，没有每对象元数据，也没有 GC 的倍增空间；
  Java 高 1.6~100×（JVM 自身 + 堆 + GC 用空间）—— 这一列才是「语言常驻开销」的真话 ✓

## 横评途中抓到的一个真 bug（这条比数字值钱）

`cdq` 的权值树状数组下标写成 `c + 1`，而 `c` 可以取到 10^6 ⇒ 长度 1000001 的数组被写到下标 1000001：

· **C 里是静默越界写**（`calloc(V+1)` 的后面一格）⇒ 凑巧算出一个数，**看不出坏** ✗
· **extC 有边界检查** ⇒ 全规模第一跑就 `trap: index 1000001 out of range (length 1000001)`，**带源码位置** ✓

改成用 `c` 本身当下标（生成器保证 `c >= 1`）后，六语言一致 ✓
⚠️ 随机小输入**测不到**这个边界（n=2000 时命中 `c = 10^6` 的概率约 0.2%）：所以另有一条人工边界输入
   `in-small/cdq-edge.txt`（含 `c = 10^6`，真值来自**暴力 O(n^2)**），`run.sh` 每次都跑它 ✓

> Java 那列是 **`.class` 之和**（内部类另出一份）—— 它小是因为**运行时在 JVM 里**：
> 跑它要拖一个 JVM，那笔账记在 RSS 那列（46~191MB）✓
> ⚠️ **不能只跟 C 比这列**：Rust 默认静态链接 std（11.5MB）、Go 自带运行时（2.4MB）都是「打包策略」，
> 不是代码膨胀；**extC / C / C++ 才是同一种交付形态**（一个 20KB 上下的静态可执行文件）✓
> `-march=native` 四家都开（Go 不吃这个旗子）⇒ 大小都含本机指令选择 ✓

## 每语言用的命令

| 语言 | 构建 / 运行 |
|---|---|
| extC | extC 前端 → `cc -O3 -march=native -fwrapv` |
| C | `cc -O3 -march=native -fwrapv` |
| C++ | `g++ -O3 -march=native -std=c++20` |
| Rust | `rustc -C opt-level=3 -C target-cpu=native -C codegen-units=1` |
| Go | `go build`（Go 编译器默认满优化，不吃 `-march`） |
| Java | `javac` + 默认 JIT，`java -Xmx4g` |
