## 怎么读这四张表

· **只看运行时间与 RSS**；构建时间单独一张表（extC 拆两段：前端 + 编它吐的 C）✓
· **几何平均那一行是全表的结论**：每个形状以「该形状最快者」为 1.00，再对五个形状取几何平均 ⇒
  谁的综合排名第一 ✓ extC 在六个语言里排第一，靠的是两个形状的**大幅**领先 ——
  一个把「分配 + 递归」变便宜（`bt`），一个把「分配 + 回收」变免费（`rebuild`）✓
· **extC 不是每个形状都快**：`radix` 上它比 C 慢，那是两笔明账 ——
  **切片索引带边界检查** + **`new` 零初始化**（`SPEC.md` 的坑与设计承诺）⇒ 不藏 ✓
  同一个设计在 `cdq` 上抓到了一个**真越界**（见下一节）✓
· **RSS 那列 extC 全部 ≤ C**：arena 是 bump 分配，没有每对象元数据，也没有 GC 的倍增空间；
  Java 高 1.6~100×（JVM 自身 + 堆 + GC 用空间）—— 这一列才是「语言常驻开销」的真话 ✓

## 横评途中抓到的一个真 bug（这条比数字值钱）

`cdq` 的权值树状数组下标写成 `c + 1`，而 `c` 可以取到 10^6 ⇒ 长度 1000001 的数组被写到下标 1000001：

· **C 里是静默越界写**（`calloc(V+1)` 的后面一格）⇒ 凑巧算出一个数，**看不出坏** ✗
· **extC 有边界检查** ⇒ 全规模第一跑就 `trap: index 1000001 out of range (length 1000001)`，**带源码位置** ✓

改成用 `c` 本身当下标（生成器保证 `c >= 1`）后，六语言一致 ✓
⚠️ 随机小输入**测不到**这个边界（n=2000 时命中 `c = 10^6` 的概率约 0.2%）：所以另有一条人工边界输入
   `in-small/cdq-edge.txt`（含 `c = 10^6`，真值来自**暴力 O(n^2)**），`run.sh` 每次都跑它 ✓

**拆两层看**：空程序的生成 C 就是 **278 行**（运行时 preamble —— 每个程序都要）⇒
减掉它才是**算法那部分**：

| 形状 | 算法部分行数 | ÷ 手写 C 行数 | ÷ extC 源码行数 |
|---|---|---|---|
| radix | 950 | 29.7× | 17.6× |
| cdq | 1150 | 11.3× | 8.4× |
| bt | 907 | 21.6× | 17.8× |
| mandel | 879 | 29.3× | 20.9× |
| rebuild | 864 | 26.2× | 21.6× |

> ⚠️ 这就是 `PLAN.md` **#49** 记的那件事：**生成的 C 偏胖**（同形手写 C 的 10~30 倍）——
> 它**不吃运行时间**（二进制还是 20KB、跑分见上表），吃的是**编译时间**；
> extC 的构建仍然跟 C 同档，是因为 gcc 编这几十 KB 很快 ✓

> 这张表是 extC 的「中间产物」：`.extc` 源码 → **它吐的 C** → 可执行文件，三段都能看见 ✓
> 用户可以读那份 C（`#line` 指回源码行），这也是「生成 C 可调试」那条原则的兑现 ✓
