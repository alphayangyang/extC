## 口径

单核 = `taskset -c 2`（P 核）· 每次 5~9 次取最好 · extC 产物一律按契约开关
`gcc -O2 -std=c11 -fwrapv -Wall -Wextra -Werror`；对照是**同次序、同开关**的手写 C 与 C++20。
机器：Intel Ultra 9 275HX（8 P + 16 E）· gcc/g++ 15.2。
⚠️ 本文件里的数字是 **2026-09-28 手工量的**；`run.sh` 是同一套口径的可重跑脚本，**加进仓库时未再跑过**
（重跑：`bench/runtime/run.sh`）。

## 结论（含两条更正）

1. **协程 resume ≈ 0.23 ns/次**（1e6 次 3567 µs vs 纯循环 3335 µs），比 C++20 协程快 29%。
2. **边界检查在这个热循环里测不出开销**（checked 10195 µs vs `@unchecked` 10519 µs，差在噪声里，
   连符号都是反的）⇒ 不要拿"边界检查开销"当解释。
3. **arena**：新鲜分配比 `calloc` 慢 ~55 ns/次（arena 记账 + **保证清零**），复用比手写 C 复用快 ~11%。
4. **矩阵乘法是本轮最有价值的发现**：同次序同开关下，extC 的 `-O2` 产物 **9.12 GFLOP/s**，手写 C 是
   **22.26**（慢 **2.4x**）；但 **`@unchecked` 无效**（8.70）⇒ **差距不是边界检查**；而
   `-O3 -march=native` 下 extC 到 **26.34**（反超手写 C 的 `-O2`，达其 `-O3` 的 93%）⇒
   差距出在 **`-O2` 下的向量化/优化决策**。**待查**：生成物经 struct 取 `data` 指针可能破坏别名分析；
   候选修法是把 view 基址提到局部变量或加 `restrict`。
5. **更正一条旧结论**：此前记的"extC == 手写 C（9.54 vs 9.60 GFLOP/s）"不可信 —— 那份手写 C 要么
   绑了单核却在跑 16 线程，要么次序不同。按同次序同开关重测，真实差距就是上面的 2.4x。

## 本轮踩到并修掉的两个"表格会骗人"的坑

1. **把程序自己打印的校验和当性能数** —— 手写 C 会打印 `c0=143.375 clast=143.625`，第一版直接 grep
   数字 ⇒ 三个不同二进制"恰好一样"全是假的。改成**计时换算**。
2. **给并行基线绑单核** —— 那份手写 C 自身开 16 线程，`taskset -c 2` 跑它 ⇒ 0.82 GFLOP/s。
   口径必须匹配：单核比单核、全核比全核。
