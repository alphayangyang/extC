# 矩阵乘法为什么在 `-O2` 下慢 2.4x —— 归因实验（2026-09-28）

被测对象：`bench/runtime/matmul.extc`（extC，i-k-j 次序，`aik` 已提升）的 `-O2` 产物 vs
`analysis/mm_fair_baseline.c`（**同次序同开关**的手写 C）。基线 21.9~27.7 GFLOP/s，extC 产物 9.1~9.6。

## 结论：触发条件是 **"经 struct 取基址" + "下标外套 `(int64_t)(…)`" 的组合**

| 文件 | 形状 | GFLOP/s | 内层向量化 |
|---|---|---|---|
| `mm_fair_baseline.c` | `float*`，循环在 `main` | 21.9~27.7 | ✓ |
| `mm_m9_while_pointers.c` | `while` + `float*` **参数** + **带**强转 | **24.5** | ✓ |
| `mm_m11_for_slice.c` | `for` + `slice` 结构体 `.data[…]`，**不带**强转 | 21.5 | ✓ |
| `mm_m13_while_slice_nocast.c` | `while` + `slice`，**不带**强转 | **20.5** | ✓ |
| `mm_m15_while_hoist_nocast.c` | `while` + 基址已提升，**不带**强转 | **22.4** | ✓ |
| `mm_m4_casts.c` | `while` + `slice` + **带强转**（≈生成物） | **8.9** | ✗ |
| `mm_mimic.c` | 40 行最小复现（照抄生成物形态） | 8.97 | ✗ |
| `mmext_hoist_real_product.c` | **真实产物**只做基址提升，强转**保留** | **9.02** | ✗ |

⇒ **每一半单独看都不慢**；**两者同时出现**才让 gcc 的向量化器放弃（`-fopt-info-vec-all` 报
`not vectorized: no vectype for stmt`）。gcc 自己的判决：手写 C
`optimized: loop vectorized using 16 byte vectors`，extC 产物 `missed: not vectorized`。

## 已经排除的假设（都做过实验）

- ❌ **下标助手没内联**：它本来就是 `static inline`；加 `__attribute__((always_inline))` 无效（9.50），
  `-O2 -finline-functions` 也无效（9.63）。
- ❌ **边界检查**：`@unchecked` 反而略慢（8.70），且本实验里把助手整个去掉（`mm_m4_casts.c`）仍 8.9。
- ❌ **别名**：三个 `float*` 参数版本（`mm_m5.c`）23.8；`restrict` 无差别（25.3）。struct 里 `data` 带
  `restrict`（`mm_m7.c`）也没用（8.3）。
- ❌ **按值传 struct**：改成按指针传 slice（`mm_m8.c`）仍 9.36。
- ❌ **基址没提升**：真实产物手工提升基址后仍 9.02（`mmext_hoist_real_product.c`）。

## 修复方向（下一步验证）

生成物里的下标一律写成 `(int64_t)(((i * n) + j))`，即使子表达式**本来就是 i64**。候选：在 codegen 里
**当操作数类型已经是 i64 时不再套这层强转**（或把强转换成不影响向量化的形式）。已验证这条路在 C 层面
能把 8.9 抬到 20.5+（`mm_m13`），且不影响正确性（所有变体校验和一致）。
`-O3 -march=native` 下本来就恢复（26.34 GFLOP/s），所以这是**纯粹 `-O2` 的代价**。

## 追加实验（2026-09-28，同一天，推翻上面一部分归因）

把 codegen 真改了（下标类型已是 i64 时不再套 `(int64_t)`），生成物里强转**确实消失**：

```c
改前： float aik = (*slice_f32_index(a, (int64_t)(((i * n) + k)), "../mmext.extc", 7));
改后： float aik = (*slice_f32_index(a, ((i * n) + k), "../mmext.extc", 7));
```

**性能一点没动**（交替测量，5 轮，GFLOP/s）：

| 轮 | 手写 C | 旧产物 | 改了强转的产物 |
|---|---|---|---|
| 1 | 16.57 | 9.32 | 9.10 |
| 2 | 21.51 | 8.91 | 9.22 |
| 3 | 19.95 | 9.39 | 9.13 |
| 4 | 20.43 | 8.87 | 8.97 |
| 5 | 20.04 | 8.84 | 8.84 |

⇒ **改错了**。回看上面的 2×2 就明白：`mm_m4`（直接 `.data[… ]` + 强转）8.9 与 `mm_m13`（直接
`.data[…]` 不带强转）20.5 差的是强转 —— 但那是**直接访问**那一支；**真实产物走的是助手调用**
`slice_T_index(v, i, file, line)`（它把 view **按值**收下、里面做空指针 + 范围检查）。新的数据点：
**助手 + 不带强转 = 9.0**（上表第 3 列）⇒ 真正的开关是 **"每元素过一遍 view 下标助手" vs "直接
`.data[…]` 访问"**，强转只是直接访问那一支里的第二个开关。

**正确的修法方向**（尚未实现）：热访问别走按值收 view 的助手，改成
`obj.data[extc_checkedIndex(idx, obj.len, "file", line)]` —— 检查仍然在（`extc_checkedIndex` 是既有
的检查原语，数组那条路就是这么发的），但省掉每元素的 view 传递。落地后必须**交替测量**验证，
并按仓库规矩：**改了没效果就回退**（本次这一版已回退，`src/codegen.c` 恢复原状）。

## 再追加：同一份产物上 `-O2` vs `-O3` 的逐开关对照（用户建议的方向，很有用）

对象：**同一份** `mmext.c`（extC 产物，未改任何源码）。交替测量，单位 GFLOP/s。

| 编译开关 | 内层向量化 | 实测 |
|---|---|---|
| `-O2`（契约旗子） | **否** | 8.7 ~ 9.7 ✗ |
| `-O2 -march=native` | 否 | 7.9 ~ 8.2 ✗ |
| `-O3` | **是** | **20.2 ~ 23.3** ✓ |
| `-O3 -march=native` | 是 | 24.0 ~ 25.5 ✓ |
| `-O2 -fvect-cost-model=cheap` / `=very-cheap` / `=dynamic` / `=unlimited` | 否 | 8.8 ~ 9.7 ✗ |
| `-O2 -funroll-loops` | 否 | 9.9 ~ 10.5 ✗ |
| `-O2` + **每一个** `-O3` 独占开关（14 个，逐个试） | 否 | — |
| `-O2` + **全部** `-O3` 独占开关（一起上） | 否 | — |
| `-O2` + `-O3` 的**内联参数档**（`early-inlining-insns` 6→14、`max-inline-insns-single` 70→200、`max-inline-insns-auto` 15→30、`inline-min-speedup` 30→15、`inline-heuristics-hint-percent` 200→600，一起上） | 否 | 7.95 ~ 8.63 ✗ |
| 同上 + `-finline-functions` | 否 | 8.28 ~ 8.97 ✗ |
| 手写 C（同次序）`-O2` | **是** | 19.5 ~ 21.3 ✓ |

`-O2` 的失败理由是硬失败：`missed: not vectorized: no vectype for stmt: _202 = *_226;`（第 398 行第 90 列
= 内层赋值那一句）。`gcc -Q --help=optimizers` 的差集**只有** `-O3` 独占开关（`-O2` 无独占），
`--help=params` 的差集**只有**上面那五个内联参数 —— 但**把两者都补齐仍然不翻盘** ⇒ 剩下的差别在
**pass 流水线本身**（哪些 pass 跑、跑几轮、顺序），不是某个开关或参数。

**可直接用的结论**：这份产物在契约旗子 `-O2` 下内层不被向量化，`-O3` 能拿回 2.3 倍；手写 C 在 `-O2`
下就能向量化 ⇒ **`-O2` 下有真实的代码形状差异**（还未定位到具体那一处）。热数值代码建议用
`-O3`（`-O3 -march=native` 到 24~25 GFLOP/s）。

**下一步该做的**（未做）：拿 `-fdump-tree-vect-details` 对比"手写 C 被向量化 / extC 产物不被向量化"
两条记录，看 `_226` 到底是什么类型、以及手写 C 那边走的是哪条分析路径。

## goal 第 3 轮：**向量化器自己点名了** —— `complicated access pattern`，且基址来自 arena

对慢的产物跑 `-fdump-tree-vect-details`（dump 存为 `prod_un_vectorizer_dump.txt`）：

- 内层那句（`prod_un.c:398`）的**真实失败原因**是 `missed: not vectorized: complicated access pattern`
  ✗ —— 之前我一直盯着的 `no vectype for stmt: _212 = *_211`（`:398:62`）只是它的**连带结果** ✗；
- 同一个循环在**嫁接版**里是 `optimized: loop vectorized using 16 byte vectors` ✓（dump 里
  `got vectype for stmt: _212 = *_211` ✓ 说明类型本身没问题 ✓）；
- **数据引用的 dump 给出线索**：
  ```
  base_address: (float *) __extc_a$16$top_199 + ((sizetype) i_164 * 3072 + (sizetype) prephitmp_138)
  base_object:  *(float *) __extc_a$16$top_199 + ...
  ```
  ⇒ 产物里 `a`/`b`/`c` 的**基址是从 arena 块里 load 出来的**（`__extc_a[16].top` ✓ 一个内存里的指针 ✓），
  而嫁接/手写版用的是 `malloc` 得到的**直接指针变量** ✓ ⇒ DR（data reference）分析把前者判成
  "complicated" ✗。这与"函数文本相同、只有文件上下文不同"完全吻合 ✓。

**下一步（明确）**：在**快的嫁接版**里把数组换成"基址来自一次 load"的形式（例如从一个 `static` 结构体
字段里取指针 ✓ 或直接用 arena 的 `__extc_a[..].top` ✓）⇒ 若翻成慢 ✓ 则确认"基址来自内存 load"是触发器 ✓
⇒ 那么修法就是 codegen 在进入热循环前**把 view 的基址提到局部指针**（我早先在 m13 家族里测过"提升"
无效 ✗，但那时缺了这一层"基址来自 arena"的前提 ✗ ⇒ 需要在新前提下重测 ✓）。

**另外一个副产品**：`68 个顶层块逐个删除 ∎ 没有一个能翻盘` ⇒ 不是"某个函数的存在"造成的 ✓，
更像是"基址表达式的来源"这类**跨函数的分析输入**造成的 ✓。

## goal 第 4~5 轮：**修法找到了（已在 C 层面验证）**：`malloc` 属性 + 不内联 ⇒ 2.2 倍

第 4 轮先用最直接的一刀确认"arena 分配"就是触发器：同一份产物、同一个 `main`、同一个 `mul`、
同一套开关，**只把三处 `extc_arena_alloc(...)` 换成 `malloc(...)`**：

| 版本 | 内层向量化 | GFLOP/s（4 轮交替）|
|---|---|---|
| 产物（arena 分配）| 0 ✗ | 8.15 · 8.14 · 8.54 · 9.19 |
| 产物（改成 `malloc`）| **1** ✓ | **21.09 · 21.17 · 21.33 · 22.41** ✓ |

第 5 轮落地尝试（编译器里给 `extc_arena_alloc` 加属性）：

| 版本 | 内层向量化 | GFLOP/s |
|---|---|---|
| 只加 `__attribute__((malloc))`（保留 `EXTC_INLINE`=always_inline）| 0 ✗ | 8.87 · 8.46 · 8.49 · 8.25 |
| **属性 + `noinline`** | **1** ✓ | **16.74 · 22.60 · 18.03 · 21.33** ✓ |

**机制**：`always_inline` 把分配器函数体（从 arena 的 `__extc_a[16].top` 算返回指针）折进调用者 ⇒
基址在优化器眼里是"arena 块内存 + 偏移" ⇒ `malloc` 属性对结果失效 ✗；不内联之后调用返回的是
"带 `malloc` 属性的不透明新内存" ✓ ⇒ DR 分析不再判 `complicated access pattern` ⇒ 内层向量化 ✓。
分配是"一次分配一次调用"，这点调用开销可以忽略 ✓。

**为什么这一轮没能提交**：改运行期文本时撞上 **C99 的 4095 字节字符串上限** —— 那段运行期字面量本来就
4037 字节，加两条 `#define` 顶到 **4157** ⇒ `make` 报 `-Wstringop-overflow`-类警告（"string length
'4157' is greater than the length '4095'"）✗。缩短注释没用（注释在字符串之外 ✗）。**下一步**：把那段运行期
文本**拆成两个 `bufPuts`**（或从该字面量里砍掉 ≥70 字节）⇒ 再落地 ⇒ 然后**具名重设黄金基线**（范围：
只改 `extc_arena_alloc` 的声明/定义 ⇒ 含 arena 的产物会变）+ parrun/instimpl/quick/attack 全过 ⇒ 提交。

**仍未解决**：**checked 路径**（不带 `@unchecked` 的矩阵乘法）即使加了属性 + noinline 仍是 0 个循环 ✗
⇒ 阻塞项 A（索引里 `extc_checkedIndex` 的 trap 分支）需要单独一刀 ✓。

## goal 第 6 轮：checked 路径的第二刀 —— **harness 有效、真实产物无效**（已回退）

在快的 harness（malloc 基址 ✓ 直连访问 ✓）里把"每次访问都检查"装回去，四个组合：

于是落地：给运行期加 `EXTC_UNLIKELY(c)`（GNU: `__builtin_expect(!!(c), 0)` ✓ 非 GNU: `(c)` ✓），
把 `slice_T_index` 与 `extc_checkedIndex` 里的范围检查都套上 ✓。生成物确实变了

⇒ **按仓库规矩回退**（改了没效果 ✓），并记下这条**harness 与产物不一致**的事实：checked 路径
在真实产物里被**第三个、既不是 arena 也不是那层强转、也不是"分支没标冷"**的东西挡着 ✗ ——
harness 里同样的形状却是快的 ✓。下一刀该做的是把这个差异**反向归约**出来（像第一刀那样：从
harness 出发，逐块加回产物的上下文，直到变慢 ✓）。
