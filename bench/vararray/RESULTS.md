# bench/vararray —— **varArray vs stl::vector**（作者问：还有没有必要留 varArray）

> 结论先写：**四个形状里 varArray 一个都没赢**，内存在它最有利的形状上输 20~90 倍，时间打平或更慢。
> 判据：同一工作量、校验和必须逐位相同（`run.sh` 自己判），时间与 RSS 都是 best of 3。

形状是**故意偏向 varArray** 挑的（短命、每轮新建、随地方整块回滚 —— 这本来该是 arena 底的好处）：

| 形状 | 实现 | 时间(s) | 峰值 RSS(KB) | 校验和 |
|---|---|---|---|---|
| s1 每轮新建+填4+丢弃 ×2e6 | varArray | 0.01 | **33132** | sum=8000000 |
| | stl::vector | 0.02 | **1516** | sum=8000000 |
| s2 只构造/销毁 ×2e6 | varArray | 0.01 | **33132** | sum=0 |
| | stl::vector | 0.01 | **1516** | sum=0 |
| s3 每轮长到4096再丢 ×2000 | varArray | 0.06 | **129900** | sum=8190000 |
| | stl::vector | 0.00 | **1452** | sum=8190000 |
| s4 一个容器长到1e6 | varArray | 0.00 | **17964** | sum=999999 |
| | stl::vector | 0.00 | **9768** | sum=999999 |

## 数字为什么长这样（三条，都能对出来）

1. **s1/s2 的 33 MB = 2e6 轮 × 16 B**（cap 4 × i32）—— 一轮都没回收。varArray 的 `new T[cap]` 走
   **arena 的 home 机制**：会分配的函数把手里的分配交给调用者选的那只 arena，而调用者（`main`）
   的 home 是自己的**帧**（`__extc_a[1]`），不是循环体那一层 ⇒ 每轮的分配都留到帧结束。
   而 stl::vector 的存储是**池自己的板块**，`release`/`grow` 能立刻还回去 ⇒ 1.5 MB 平。
2. **s3 的 130 MB = 2000 轮 × 约 65 KB**（4→4096 翻倍，历代旧 buffer 之和 ≈ 2×4096×8）。
   翻倍扩容在 arena 里**旧 buffer 一个都还不了**；池底那条路用 `poolResize` 在原块上加长 ⇒ 1452 KB 平。
3. **s4 的 18 MB vs 9.7 MB**：同一个"一个容器长到 1e6"的形状，arena 留下全部历代副本
   （`POOLS.md` §1 那张动机表第三行），池底只留一代 + 1.5 倍的余量。

## 结论（对"要不要留 varArray"）——**要留，但理由不是性能**

**性能上它不占优**（上表：四个偏向它的形状里时间打平或更慢、内存输 20~90 倍），
所以"留着它是因为快"这条不成立。

**它不可替代的地方是语义**（作者 2026-09-26 指出）：

> varArray 是你唯一能够写 `varArray<ref T>` 而不会报错的方式，因为都是 arena 里的对象，
> 不会出现循环，所以还是得留着。

三条实测（`/tmp/prb/varef/`，本轮跑过）：

| 形状 | 结果 |
|---|---|
| `varArray<ref i32>` + `push(ref x)`（同地方） | 编过，`v0=5` |
| 作者那个图：`struct node { refs: varArray<ref node> }`，两个节点互相 `push` | **编过**，`a.refs[0].data=2 n=1` |
| 内层块里局部变量的引用塞进外层 `varArray` | **仍然被拒**（`argument 2 of push carries a reference into a deeper scope`）|

**为什么只有它能装引用**（这条是两种存储的语义差，不是配置差）：

- **arena 底**：元素地址**永不移动、永不复用**（没有逐对象 free、没有压实、没有纪元翻色），
  所以"引用在它的地方活着期间一直有效"是真的 ⇒ `ref T` 元素 sound，
  而且环（两个节点互指）只是普通数据结构，没有任何管理上的环问题；
- **池底**：`clear`（翻纪元）/`shrink`（压实）/`release` 都会动元素或让整块失效
  ⇒ 池里的引用是雷（`PLAN #88` 禁的就是它）。

**两条口径互不冲突**：#88 的禁令按"结构体有没有 `pid` 字段"认池底容器，
`varArray` 没有 `pid` ⇒ 天然不受约束 —— 这不是巧合，是选那个判据的理由之一。

**性能那条仍然是真账**：如果拿它当"快的数组"用，它没有任何优势（尤其是循环里反复新建：
arena 的 home 机制会把分配提到帧那一层，33 MB vs 池底的 1.5 MB）。
