## 口径（怎么读上面两张表）

- **同一份工作负载**：K=512 个惰性生产者 × M=20000 个值，`v = (i%65536)*65521 + id*40503 + 轮号`（i64，
  绝不上溢），消费者求和，R 轮 + 一轮小热身。六语言**必须算出同一个校验和**（`run.sh` 里就是闸门，
  不一致直接退出）：R=1 时 `6816033821440000`，R=3 时 `20446001335040000`。
- **每语言取各自最惯用的"协程"机制**（见上表"机制"列）—— 这**不是同一台机器**：Go 的一次收发与
  Java 的一次 park/unpark 都含**会合（rendezvous）**成本，Python 是解释器成本主导。所以"单进程"
  那张表同时给了**同语言纯循环下界**，机制开销 = 协程版 − 纯循环版，读者可以自己扣掉语言本身的速度差。
- **单进程**：不绑核，best of 3。**多进程**：每进程绑一个 P 核（0..N-1），best of 2；吞吐 =
  N × 每进程步数 ÷ 墙钟。R 按语言选到"单进程 ≈1 秒"（Java 的机制慢，R=1 就要 20 秒）。
- 只量**运行**，编译不计入。extC 产物按契约旗子 `gcc -O2 -std=c11 -fwrapv -Wall -Wextra -Werror`。

## 结论

1. **三种"编译器生成状态机"的语言里 extC 最快**：每次推进的机制开销 **+0.20 ns**，是 C++20 的 1/5、
   Rust 的 1/4。Rust 那一列要打个折看：它的 executor 每个值走 **2 次 poll**（Pending + Ready）。
2. **多进程近乎线性 —— 六语言无一例外**（4 进程 3.9~4.0x、8 进程 7.4~7.8x）。这条对 extC 尤其重要：
   多进程是它的**第一形状**（`SO_REUSEPORT` + `fork`，零编译器魔法），而 Python 也靠它绕开 GIL ⇒
   "多进程不是落后，是通用且够用的扩展手段"。
3. **单进程吞吐 extC 领先**：约 2.3x C++20 · 1.7x Rust · 282x Go · 54x Python · 3854x Java（8 进程时
   extC 到 17.8 G 步/秒）。**内存 extC 最小（1 MB）**，Java 是 197 MB 的 JVM 基线。
4. Java 的扩展只有 6.33x：虚拟线程 + `SynchronousQueue` 的交接本来就慢，197 MB × 8 进程压力也更大。

## 这一轮踩到并修掉的三个"表格会骗人"的坑

1. **把程序自己打印的校验和当性能数** —— `bench/matmul.c` 会打印 `c0=143.375 clast=143.625`，
   第一版直接 grep 数字 ⇒ 三个不同二进制"恰好一样"，全是假的。改成**计时换算**。
2. **给并行基线绑单核** —— `bench/matmul.c` 自身开 16 线程，`taskset -c 2` 跑它 ⇒ 0.82 GFLOP/s。
   口径必须匹配：单核比单核、全核比全核。
3. **优化器把整轮提出循环** —— extC 的 R=100 只花 7 ms、校验和却真是 100 倍：`run(512,20000)` 是纯函数 +
   常量参数，gcc 直接算一次乘 100。修法：把**轮号混进被计算的值**（六语言一致，顺带让每轮不同）。
   同一轮还有一个 shell 变体：`best $1` 传参错误，把 `python3` 跑成空 REPL，量出"10 ms"的假数据。
