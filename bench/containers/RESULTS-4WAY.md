# 容器四方对照：池底 old / 当前 new / C++ / Rust（收口重跑）

> 表在 `RESULTS-4WAY.tsv`（`bash bench/containers/run.sh --reps 5 --tsv RESULTS-4WAY.tsv`）。
> 形状定义与判据见 `SPEC.md`；历史三臂账（v38 之前）仍在 `RESULTS.tsv`/`RESULTS.md`，两份不混。

## 0 一句话

二十一个形状里 `new` 比池底 `old` 快的 15 个、持平（±10%）的 5 个、慢的 1 个（H5 不命中查询 1.20×）。
对 C++ 标准容器与 Rust 标准容器，除 S1/S2/LM1/LM2/LS1/LS2 这几格优化器能把小容器整个消掉的形状之外，
`new` 都在同一量级或更快；RSS 在 20 个形状上低于池底（H1 201,728→81,780 kB、H4 101,696→42,868 kB），
高的两格是 H3（墓碑混删 +36%）与 M2（B+ 树节点 churn +2.3×），绝对增量 8–13 MB。

## 1 四臂是什么

每臂编译**同一份** `.extc` 源：

| 臂 | 编译器 | 标准库 | 存储 |
|---|---|---|---|
| `old` | `git worktree add -f /tmp/ct/wt-old f910d14d` 自建 | 该树的 `stdlib`（`EXTC_STD`） | 运行期池板块（`poolSliceRaw` / `poolResizeRaw`） |
| `new` | 当前树 `./build/extc` | 当前树 `stdlib` | `buf<T>` 地址预留（vector/string/hashMap/hashSet 值列）与 `block<T>` 平坦块（B+ 树 / linMap） |
| `cpp` | `g++ -O2 -std=c++17` | libstdc++ | `std::vector` / `std::string` / `std::unordered_map` / `std::unordered_set` / `std::map` / `std::set` / 手写线性表 |
| `rs` | `rustc -O` | Rust std | `Vec` / `String` / `HashMap` / `HashSet` / `BTreeMap` / `BTreeSet` / `Vec` 上的线性扫描 |

`old` 是池基质的最后一个提交（`f910d14d`，vector 迁移之前）。同一份 `.extc` 在两边都能编过，
所以两侧的差别只有编译器与标准库，没有源级分叉。C++/Rust 臂是逐行对应的写法：同一 xorshift64
（`SEED0=0x2545F4914F6CDD1D`）、同一循环边界、同一校验和公式、同一 `n=` 行输出。

## 2 方法

- **等价工作**：四臂输出逐字相同才计时（`run.sh` 自己判，不同直接报失败）。
- **计时**：每臂每轮跑一次、**交错**（old → new → cpp → rs），取 5 轮的最小值，单位秒（`taskset -c 6`）。
- **RSS**：每臂单独一次运行，`/usr/bin/time -f %M` 的 `ru_maxrss`。
- **编译时间不进窗口**：所有臂都先产可执行文件再计时。

## 4 分组看

### 4.1 vector（V1–V4）

V1/V2/V3 是 0.66×/0.61×/0.51×：预留内增长省掉了「换板块 + 旧代变垃圾」，克隆也从「向池要新板块逐元素拷」
变成「一次预留 + 一次拷」。RSS V2 +2.0 MB 是语义差（池版本副本与原件共享板块，新版本每个副本各有一片预留），
换来的是副本能独立增长、独立释放。

V4 是 1.00×：20 万个小容器生死循环，预留 + 归还的固定成本全落在这格，与池底打平。这是刻意选的反向形状。

### 4.2 string（S1–S3）

S1 1.00×（SSO，两代都不分配）；S2 0.37×、RSS 67,328→12,004 kB（池底峰值随构造过的长串条数线性涨，新实现与条数无关）；
S3 0.67×。

### 4.3 hashMap（H1–H6）

H1/H2/H4/H6 是 0.46×–0.76×，RSS 大幅下降（H1 201,728→81,780、H2 235,256→171,728）：三列布局把桶的负载从池版的
稀疏指针结构换成 17 B/桶的平坦列，峰值不再有「旧列 + 新列 + 池板块」三层同时在世。

**H5 是唯一的退步：1.20×（0.530→0.634 s）**。把插入侧与查询侧拆开（H6 只有插入）可以看到，差距全在**不命中查询**：
插入侧 old 0.242 / new 0.126（快 1.9×），于是查询侧 old ≈ 0.288 s、new ≈ 0.508 s，即不命中路径慢 1.76×。

归因（2026-12，同轮四臂 + callgrind）：**全部来自装载率**。池底按 0.70 装载，当前实现按 17/20 = 0.85；把当前实现的装载率改到 0.70（其余一字不改）后，H5 从 0.59 s 掉到 0.40 s，反而比池底的 0.51 s 快，Ir 从 338.4 掉到 123.7 / 12M 次操作（池底 142.5）。不命中的期望探测数约 (1 + 1/(1−α)²)/2：0.85 时 22.7 次、0.70 时 6.06 次。同一装载率下当前实现的指令数仍高于手写 `flat` 表（123.7 vs 49.4），那是逐字节探测本身的成本，与存储基质无关。

装载率不能直接降到 0.70：J1 要求 h1 峰值 ≤85 MB，α=0.82 时 85,880 kB 已经贴边、α=0.70 时 98,168 kB 破界 —— J1 与 J2 是同一条权衡的两端（详见 `docs/design/HASHMAP.md` §9）。判据没放宽，这条作为**已知退步**记在这里；修法是让一次探测覆盖 8 个控制字节（字级成组扫描），属独立一步。

H3（1e6 键上 8e6 次增删查）RSS 35,728→48,464 kB（+36%）：Knuth 回移无墓碑省下了 tombstone 的槽，但装载率从池版的
0.5 提到 17/20，加上 tag 列，每元素固定开销变大；绝对增量 12.7 MB，时间反而 0.48×。

### 4.4 hashSet（HS1–HS2）

0.64×/0.60×，RSS HS1 174,460→51,060 kB。集合是 hashMap 的薄包装，这一组的数字与 H1/H3 同向。

### 4.5 linMap / linSet（LM1–LM2 / LS1）

1.01×/1.01×/1.01×：线性容器每元素只有键值两个机器字，池底的「板块 + 世代」与 `block<T>` 的平坦列在这里没有差别，
所以这一组是平等的；相对 C++ 的 1.29–1.43× 来自 extC 侧逐项边界检查与未内联的 `find`，见 `RESULTS-hash.md` 的指令数归因。

### 4.6 有序 map / set（M1–M2 / ST1）

M1 0.72×、ST1 0.69×、M2 0.92×。RSS：M1 +4.2 MB（40,836→45,020）、M2 +10.8 MB（8,208→19,004）、ST1 +3.0 MB。
B+ 树节点从池板块换成 `block<T>` 平坦列后，分裂/借用/合并的墓碑与空闲槽都留在列里直到 `shrink`，
这是 +10.8 MB 的来源；时间上没有付出（M2 反而 0.92×）。

## 5 结论

1. 池底相对当前实现**没有一格是「必须靠池才不退化」**的：唯一慢的 H5 是不命中探测路径，与存储基质无关（插入侧同一张表更快；归因是装载率 0.85 对池底 0.70，见 §4.3）。
2. 当前实现相对 C++ 与 Rust 在这批形状上总体持平或更快；C++ 的 `unordered_map` 在哈希组全面落后（0.22×–0.67×），
   有序组 `std::map` 落后 0.31×–0.66×；Rust 在哈希不命中（H5 1.97×）、S2、LM/LS、M2/ST1 上更快，与已知的探测 / 边界检查差异一致。
3. S1/S2/LM1/LM2/LS1 几格里 cpp/rs 的 0.00–0.06 s 不能当「语言更快」读：容器大小在编译期已知，优化器把分配整个提升到栈上甚至消掉。
   这几格只用来看「extC 侧没有为存储基质付额外成本」，不比跨语言。
4. varArray 的五臂对照（含池底、varArray、stl::vector、C++、Rust）在 `bench/vararray/RESULTS.md`。
