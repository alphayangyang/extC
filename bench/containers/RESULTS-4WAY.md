# 容器四方对照：池底 old / 当前 new / C++ / Rust（收口重跑）

> 表在 `RESULTS-4WAY.tsv`（`bash bench/containers/run.sh --reps 5 --tsv RESULTS-4WAY.tsv`）。
> 形状定义与判据见 `SPEC.md`；历史三臂账（v38 之前）仍在 `RESULTS.tsv`/`RESULTS.md`，两份不混。
> hashMap / hashSet 的这条表是**控制字节按机器字打包之后**的数字（J2 解法，见 `docs/design/HASHMAP.md` §9）；
> 同轮 `flat` 参考由 `bash bench/containers/run-flat.sh --reps 7` 产出，在 `RESULTS-hash-flat.tsv`。

## 0 一句话

二十一个形状里 `new` 比池底 `old` 快的 17 个、持平（±3%，或毫秒级噪声）的 4 个（S1 / LM1 / LM2 / LS1）、慢的 0 个。
对 C++ 标准容器与 Rust 标准容器，除 S1/S2/LM1/LM2/LS1 这几格优化器能把小容器整个消掉的形状之外，
`new` 都在同一量级或更快；相对 Rust 仍输的一格是 H5 不命中查询（1.16×，上一轮 1.97×）。
RSS 在 8 个形状上低于池底（H1 201,728→81,788 kB、H4 101,696→42,876 kB），5 个持平，8 个略高：
最大两格是 H3（+12.7 MB）与 M2（+10.8 MB），另有 V1–V3 与 S3 的 +1–6 MB 属语义差（副本各自持有预留）。

## 1 四臂是什么

每臂编译**同一份** `.extc` 源：

| 臂 | 编译器 | 标准库 | 存储 |
|---|---|---|---|
| `old` | `git worktree add -f /tmp/ct/wt-old f910d14d` 自建 | 该树的 `stdlib`（`EXTC_STD`） | 运行期池板块（`poolSliceRaw` / `poolResizeRaw`） |
| `new` | 当前树 `./build/extc` | 当前树 `stdlib` | `buf<T>` 地址预留（vector/string/hashMap/hashSet 值列）与 `block<T>` 平坦块（B+ 树 / linMap / hashMap 控制字节列） |
| `cpp` | `g++ -O2 -std=c++17` | libstdc++ | `std::vector` / `std::string` / `std::unordered_map` / `std::unordered_set` / `std::map` / `std::set` / 手写线性表 |
| `rs` | `rustc -O` | Rust std | `Vec` / `String` / `HashMap` / `HashSet` / `BTreeMap` / `BTreeSet` / `Vec` 上的线性扫描 |

`old` 是池基质的最后一个提交（`f910d14d`，vector 迁移之前）。同一份 `.extc` 在两边都能编过，
所以两侧的差别只有编译器与标准库，没有源级分叉。C++/Rust 臂是逐行对应的写法：同一 xorshift64
（`SEED0=0x2545F4914F6CDD1D`）、同一循环边界、同一校验和公式、同一 `n=` 行输出。

## 2 方法

- **等价工作**：四臂输出逐字相同才计时（`run.sh` 自己判，不同直接报失败）。
- **计时**：每臂每轮跑一次、**交错**（old → new → cpp → rs），取 5 轮的最小值，单位秒（`taskset -c 6`）。
- **RSS**：每臂单独一次运行，`/usr/bin/time -f %M` 的 `ru_maxrss`。
- **编译时间不进窗口**：所有臂都先产可执行文件再计时。

## 4 分组看

### 4.1 vector（V1–V4）

V1/V2/V3 是 0.63×/0.55×/0.49×：预留内增长省掉了「换板块 + 旧代变垃圾」，克隆也从「向池要新板块逐元素拷」
变成「一次预留 + 一次拷」。RSS V2 +2.0 MB 是语义差（池版本副本与原件共享板块，新版本每个副本各有一片预留），
换来的是副本能独立增长、独立释放。

V4 是 0.75×（3 ms 对 4 ms）：20 万个小容器生死循环，预留 + 归还的固定成本全落在这格；毫秒级噪声，
上一轮同形状是 1.00×。这是刻意选的反向形状。

### 4.2 string（S1–S3）

S1 1.00×（SSO，两代都不分配）；S2 0.39×、RSS 67,328→12,004 kB（池底峰值随构造过的长串条数线性涨，新实现与条数无关）；
S3 0.67×。

### 4.3 hashMap（H1–H6）

H1/H2/H4/H6 是 0.49×–0.81×，RSS 大幅下降（H1 201,728→81,788、H2 235,344→171,728）：三列布局把桶的负载从池版的
稀疏指针结构换成 17 B/桶的平坦列，峰值不再有「旧列 + 新列 + 池板块」三层同时在世。

**H5 已反超：0.71×（0.551→0.389 s）**。这条曾经是唯一的退步（1.20×）：逐字节控制字节列在 17/20 装载率下每次不命中要探
22.7 个桶，J1（峰值 ≤85 MB）与 J2（查询 ≤1.3× flat）因此互斥。2026-12 把控制字节列改成按机器字打包（`block<u64>`，
一字节一桶，用零字节检测一次判 8 个桶），装载率留在 0.85，h5 降到 0.389 s、h1 峰值不变。同轮 `flat` 参考：
h5 0.363 / 0.318 = 1.14×、h1 0.315 / 0.250 = 1.26×，两条判据同时满足。代价是 h2 +6%、h4 +16%（相对上一轮），
绝对量 +21 ms / +8 ms，细节与两次否证见 `docs/design/HASHMAP.md` §9。

H3（1e6 键上 8e6 次增删查）RSS 35,732→48,468 kB（+36%）：Knuth 回移无墓碑省下了 tombstone 的槽，但装载率从池版的
0.5 提到 17/20，加上控制字节列，每元素固定开销变大；绝对增量 12.7 MB，时间反而 0.50×。

### 4.4 hashSet（HS1–HS2）

0.79×/0.55×，RSS HS1 174,460→51,064 kB。集合是 hashMap 的薄包装，这一组的数字与 H1/H3 同向。

### 4.5 linMap / linSet（LM1–LM2 / LS1）

1.00×/1.01×/1.01×：线性容器每元素只有键值两个机器字，池底的「板块 + 世代」与 `block<T>` 的平坦列在这里没有差别，
所以这一组是平等的；相对 C++ 的 1.29–1.43× 来自 extC 侧逐项边界检查与未内联的 `find`，见 `RESULTS-hash.md` 的指令数归因。

### 4.6 有序 map / set（M1–M2 / ST1）

M1 0.72×、ST1 0.71×、M2 0.90×。RSS：M1 +4.2 MB（40,836→45,012）、M2 +10.8 MB（8,208→19,000）、ST1 +3.0 MB。
B+ 树节点从池板块换成 `block<T>` 平坦列后，分裂/借用/合并的墓碑与空闲槽都留在列里直到 `shrink`，
这是 +10.8 MB 的来源；时间上没有付出（M2 反而 0.90×）。

## 5 结论

1. 池底相对当前实现**没有一格是「必须靠池才不退化」**的：21 个形状里 17 个更快、4 个持平、0 个更慢；曾经唯一的退步
   H5 已由控制字节按字打包解决（0.71×，同轮对 `flat` 1.14×）。
2. 当前实现相对 C++ 与 Rust 在这批形状上总体持平或更快；C++ 的 `unordered_map` 在哈希组全面落后（0.24×–0.68×），
   有序组 `std::map` 落后 0.34×–0.65×；Rust 在 H3/H5/HS2/S2/M2/ST1 上更快（1.16×–1.50×），与已知的探测 / 边界检查差异一致。
3. S1/S2/LM1/LM2/LS1 几格里 cpp/rs 的 0.00–0.10 s 不能当「语言更快」读：容器大小在编译期已知，优化器把分配整个提升到栈上甚至消掉。
   这几格只用来看「extC 侧没有为存储基质付额外成本」，不比跨语言。
4. varArray 的五臂对照（含池底、varArray、stl::vector、C++、Rust）在 `bench/vararray/RESULTS.md`。
