# hashMap 的性能画像：extC vs 两个 C++ 参考

> 表在 `RESULTS-hash.tsv`（`run.sh`，池版/当前版/std::unordered_map 三臂）与
> `RESULTS-hash-flat.tsv`（`run-flat.sh`，extC/std::unordered_map/手写开放寻址表 三臂）。
> 判据：同一形状各臂输出逐字相同、交错多轮取最小值、RSS 取 `ru_maxrss`。

## 0 一句话

对 **libstdc++ 的 `unordered_map`**（链式节点表），extC 的 `hashMap` 快 2.5–7.0×；唯一的例外是
混合增删的 H3，慢 1.21×。对**手写同类开放寻址表**（同一算法、值内联在桶里、无稠密列），extC 慢
1.5–2.6×（H4 遍历持平）。callgrind 把差距定到**指令数**上：同一形状两侧的**末级缓存缺失相同**
（1.00×），而执行指令数差 3.5–3.9×。也就是说这张表的差距不是「多读了内存」，是「每做一件事要执行
更多的指令」——热路径上的边界检查、未内联的查找函数、以及稠密值列带来的逐次依赖读。

## 1 为什么要有两个 C++ 臂

拿 `unordered_map` 当「C++ 的上界」会把 extC 的优势说大：它是链式节点表，每插一个元素一次分配、
查找沿指针追，在开放寻址面前天然吃亏，而 extC 的 `hashMap` 正是开放寻址（2 的幂容量 + 线性探测 +
墓碑 + 0.5 装载率）。所以另写一个 `h_flat.cpp`：**同一类算法**、键与值内联在桶里、没有 extC 那两条
为「跨扩容稳定句柄」而存在的列。它回答的问题是：extC 的差距来自算法，还是来自列布局/代码生成？

## 2 形状（`h1_cap` … `h6_putonly`）

| 形状 | 做什么 | 考什么 |
|---|---|---|
| H1 | 4e6 条 i64 键：`withCap(N)` 容量一次给够，插入后全量命中查询 | 容量齐备时的稳态：探测、命中、稠密值列 |
| H2 | 同样的 4e6 条键，但从 `withCap(8)` 长起来 | 增长：重建要同时持有旧列与新列（峰值 RSS） |
| H3 | 8e6 次插入/查询/删除混在 1e6 个键上 | 墓碑与 swap-remove：删一次要搬值、修反查列 |
| H4 | 2e6 条之后两遍全表遍历（值列一遍、桶列一遍） | 遍历：稠密值列是连续的，桶列是稀疏的 |
| H5 | 4e6 条之后 8e6 次**不命中**查询 | 未命中路径：一直探测到 EMPTY |
| H6 | 只做 4e6 次插入 | 把 H1 拆成「插入侧」与「查询侧」两半 |

四臂的工作量逐字等价：同一份 `.extc` 源给 `old`/`new` 两臂，`cpp`/`flat` 是逐行对应的 C++ 写法，
随机源是同一个 xorshift64（`SEED0 = 0x2545F4914F6CDD1D`，键空间 `1000000007`）。每个形状打印一行
校验和，例如 H1 的 `n=3991987 hits=4000000 sum=5998249052996950`——四臂逐字相同才算数。

`h_flat.cpp` 的 `p1` 形状只做插入，正是 H6 的 C++ 对照。

## 3 表 1：存储基质换了什么（池 → `block`+`slots`）

这一半是 R4c 的问题：把 hashMap 从池板块搬到 `block<T>`/`slots<T>`，速度与内存各付了什么。

| 形状 | `old`（池） | `new`（`block`+`slots`） | `cpp`（`unordered_map`） | new/old | new 的 RSS / old 的 RSS |
|---|---|---|---|---|---|
| H1 | 439 ms / 201.7 MB | 438 ms / 239.6 MB | 1064 ms / 159.9 MB | 1.00× | 1.19× |
| H2 | 526 ms / 235.3 MB | 558 ms / 339.5 MB | 1874 ms / 175.2 MB | 1.06× | 1.44× |
| H3 | 574 ms / 35.7 MB | 580 ms / 64.5 MB | 483 ms / 30.2 MB | 1.01× | 1.81× |
| H4 | 118 ms / 101.7 MB | 82 ms / 120.8 MB | 563 ms / 83.0 MB | **0.70×** | 1.19× |
| H5 | 584 ms / 201.7 MB | 612 ms / 239.6 MB | 1402 ms / 159.8 MB | 1.05× | 1.19× |

读法：**换基质换掉的是结构，不是性能**。速度上互有胜负（H4 是 `new` 快 1.44×，因为稠密值列连续遍历；
H2 慢 6%），但 RSS 一律变高。原因在三张稠密列按**表容量**预留、按**元素数**触页：

- 桶侧四列（键 8 B / 标签 1 B / 稠密行号 4 B / 行号→桶 4 B）× cap=8,388,608 = 142.5 MB——这四条必须整容量可用；
- 稠密侧三列（值 8 B / 稠密→槽 4 B / 槽元数据 8 B）× n=3,991,987 = 80 MB——只有用到的那段被触页；
- 合计 222.5 MB + 竞技场量子对齐 ≈ **239.6 MB**（实测）；`h_flat` 是三条满容量列 × 17 B = 142.6 MB（实测 143.1 MB）。

所以差距是**每元素 20 B 换「跨扩容稳定的句柄 + O(1) 删除 + 稠密值列」**（H2 的 339 MB 是重建瞬间
旧列与新列同时在手：1.44× 而不是 1.19×）。这是设计的价钱，不是实现的疏漏；`RESULTS.tsv` 里
V1–V4/S1–S3 已经量过同一件事在 vector/string 上的版本（V4 生死循环 1.00×）。

## 4 表 2：extC vs 两个 C++ 参考

| 形状 | extC | `unordered_map` | 手写开放寻址 | extC / `unordered_map` | extC / 手写 |
|---|---|---|---|---|---|
| H1 | 440 ms / 239.6 MB | 1084 ms / 160.0 MB | 262 ms / 143.1 MB | **0.41×（快 2.46×）** | 1.68×（慢） |
| H2 | 556 ms / 339.5 MB | 1906 ms / 175.2 MB | 370 ms / 216.6 MB | **0.29×（快 3.43×）** | 1.50× |
| H3 | 612 ms / 64.5 MB | 505 ms / 30.1 MB | 239 ms / 56.2 MB | **1.21×（慢）** | 2.56× |
| H4 | 83 ms / 120.8 MB | 579 ms / 83.0 MB | 81 ms / 73.4 MB | **0.14×（快 6.98×）** | 1.02×（持平） |
| H5 | 577 ms / 239.6 MB | 1418 ms / 159.9 MB | 337 ms / 143.1 MB | **0.41×（快 2.46×）** | 1.71× |
| H6 | 172 ms / 239.6 MB | —（无此形状） | 156 ms / 143.1 MB | — | 1.10× |

三句话：

1. **对标准库是压倒性的**：开放寻址的算法优势 + 无节点分配，2.5–7.0×；H4（遍历）差 6.98× 主要因为
   `unordered_map` 遍历沿节点指针追，而 extC 的稠密值列是连续数组。
2. **H3 是唯一输给 `unordered_map` 的形状**：混合增删时 extC 每次删除都要 `swap-remove` 搬值、
   修反查列、写墓碑；链式表删除只是摘节点，且它的 1e6 键工作集（30 MB）全在缓存边上。
3. **对手写同类表慢 1.5–2.6×**：这是本轮真正要解释的数字。

## 5 分解：差距在查询侧，不在插入侧

H6（只插入）把插入侧单独量出来：extC 172 ms vs 手写 156 ms = **1.10×**，几乎持平。
于是 H1/H5 的差距落在查询侧：

| 形状 | 插入侧 extC / 手写 | 查询侧 extC / 手写 | 查询侧每次 |
|---|---|---|---|
| H1（4e6 次命中查询） | 172 / 156 ms（1.10×） | 268 / 106 ms（**2.53×**） | 67 ns vs 27 ns |
| H5（8e6 次不命中） | 172 / 156 ms（1.10×） | 405 / 181 ms（**2.24×**） | 51 ns vs 23 ns |

插入侧为什么能持平：一次插入要写七处（键、标签、稠密行号、行号→桶反查、值列三件套），工作集 100–240 MB，全部落在随机写缺失上，多出的
指令被缺失延迟盖住（同一份测量里插入侧的墙钟对指令数不敏感）。查询侧不同——命中查询在探测之后
还要两次**依赖读**（先读「行号→桶」反查列拿到稠密行号，再读值列），不命中查询要多走几次探测。
依赖读不能被乱序掩盖，所以指令与缺失都直接落在关键路径上。

## 6 callgrind：差距是指令数，不是缓存缺失

`run-cg.sh` 用 callgrind 的 cache 模拟在同一次运行里同时给出指令数与末级缺失（这台机器上
`perf` 不可用，故用 callgrind）：

| 形状 | 臂 | 指令数 | 指令/操作 | 数据引用/操作 | D1 缺失 | 末级缺失 | 末级缺失/操作 |
|---|---|---|---|---|---|---|---|
| H1 | extC | 1,522,224,048 | **190.3** | 95.3 | 27.68 M | 16,164,835 | 2.02 |
| H1 | 手写 | 392,871,698 | **49.1** | 6.4 | 26.74 M | 16,100,747 | 2.01 |
| H5 | extC | 2,094,544,323 | **174.5** | 88.5 | 27.80 M | 11,732,667 | 0.98 |
| H5 | 手写 | 593,389,260 | **49.4** | 6.0 | 27.32 M | 11,474,655 | 0.96 |

两件事：

- **末级缺失两侧相同**（1.00× / 1.02×）：extC 并没有「多读内存」，它读的是同样多的缓存行；
- **指令数差 3.9× / 3.5×**，数据引用差 15×（多出来的引用都命中在 L1，所以不影响末级缺失）。

换算成速率就把结论说死了：H1 的 440 ms / 1.522e9 指令 = **3.46 G 指令/秒**（这台机器上约一个周期
一条，即发射受限）；手写表 262 ms / 0.393e9 = **1.50 G 指令/秒**（它在等内存）。所以 extC 的墙钟由
指令数决定，手写表由缺失延迟决定——两边在不同的屋顶下，**extC 这一侧的可压缩空间是指令**。

## 7 结论、判据与下一步杠杆

结论（写进 `CONTAINER-OWNERSHIP.md` 与 changelog 的口径）：

1. 换基质（池 → `block`+`slots`）速度中性（H1 1.00×、H3 1.01×、H2 1.06×、H4 0.70×、H5 1.05×），
   RSS 结构性变高（+19%…+81%，重建瞬间 +44%）；它买到的是所有权、无纪元、可删池，不是性能。
2. hashMap 的算法选择是对的：对 `unordered_map` 快 2.5–7.0×，唯一的反面形状是混合增删（1.21× 慢）。
3. 对手写同类表慢 1.5–2.6×，归因**指令数**（3.5–3.9×）而不是内存流量（末级缺失 1.00×）。

下一步杠杆（按预期收益排序，都还在「不改语言、不加写屏障」的范围内）：

1. **热路径上的边界检查**：生成的 C 里每次 `block::idx` / `idxset` 都带「负 + 越界」两道比较和一条
   trap 分支（探针的每次迭代都能在反汇编里看到）；把行指针与容量提到循环外、探测循环内改用不带检查的
   内部写法，是纯 codegen 改动，不动语义（对外仍是 trap）。
2. **让 `find` 内联**：它现在是一个独立函数（`hashMap$hashMap_hashMap$i64Key_i64_find`，60 指令/次），
   每次调用重新加载表头（cap、三条列指针）、重算哈希；内联到 `get`/`put` 后这些都能消掉。
3. **`put` 的五条列写**：H6 持平说明插入侧被缺失掩盖，但 H2 的 339 MB 是列重建的两代同存；
   若把重建做成「分流式重排（一次只持有一条临时列）」，峰值能降到 1.19× 那一档。

不建议做：换回链式结构（H1/H4/H5 会退化 2.5–7×）、删掉稠密值列（H4 的 6.98× 优势与 O(1) 删除都靠它）。

## 8 复现

```
# 三臂（池版 / 当前版 / std::unordered_map）：需要旧编译器 worktree
bash bench/containers/run.sh --reps 7 --shapes h1,h2,h3,h4,h5 --tsv RESULTS-hash.tsv

# 三方（extC / std::unordered_map / 手写开放寻址表），含 H6 的插入侧分解
bash bench/containers/run-flat.sh --reps 7

# 指令数与末级缺失（callgrind；这台机器 perf 不可用）
bash bench/containers/run-cg.sh h1 h5
```

口径与注意：

- `taskset -c 6` 固定核；每臂每轮一次、**交错**，取 `REPS` 轮最小值（bash `time` 的 `%3R`，10 µs 分辨率）；
- RSS 用 `/usr/bin/time -f %M` 的 `ru_maxrss`（峰值，不是均值；单次运行即可，输出确定）；
- 编译时间不进窗口（只跑二进制）；旧臂必须 `EXTC_STD` 指向旧 worktree 的 `stdlib`；
- `h_flat` 只是「同一算法的 C++ 参考」，不是「C++ 能达到的上界」——它的值与键内联在桶里、
  没有稳定句柄与 O(1) 删除，是另一种设计取舍；
- callgrind 是模拟，指令数与缺失是模型值；墙钟结论来自前面的实测表，两者只用来解释方向。
