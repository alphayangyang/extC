# 并行（机制与待做）

这份文档说明语言层的并行长成什么样、一个并行循环允许写什么，以及为此要做的几件事。
它属于"有什么待做"那一类，和 [`TODO.md`](TODO.md) 同源：`TODO.md` 是清单，这里是它背后的机制。

## 模型总览

并发分成两类，边界很清楚：

- **I/O 并发**（等网络、磁盘、数据库）：由协程与调度器承担，见 [`usage/coroutine.md`](usage/coroutine.md)。这类并发放大的是等待，不是算力。
- **CPU 数据并行**（对一个数组做 map / reduce）：本页的范围。

用户模型只有一句话：**可变数据有唯一主人，能共享的只有只读**。引用不过线程。

并行的**单位是一个循环嵌套**，不是一个随意划定的代码块。原因有两条：

1. 检查器要判定的东西（写集、下标仿射、谁共享谁私有）在一个循环嵌套里是封闭的，跨循环就不封闭了；
2. 设备端（GPU 一类）接受的最小形状恰好也是一个循环嵌套。把限制集按"设备也能接受"取窄，
   将来换后端不用改用户代码。

所以并行性标在 `for` 上：`par` 是并行的唯一动词。

## 语法

一个并行循环：

<!-- fragment -->
```extc
par i in 0..n {
    out[i] = (a[i] * 2.0 + b[i]) * 0.5
}
```

二维就嵌套，内层折叠进同一个内核，不是内层再开一批线程：

<!-- fragment -->
```extc
par r in 0..rows {
    par c in 0..cols {
        out[r * cols + c] = (a[r * cols + c] + b[r * cols + c]) * 0.5
    }
}
```

`ext` 与 `par` 是语言里并发的两个动词：`ext` 抛出一个协程，`par` 把一个循环摊到多个 worker 上。
两者都不引入用户可见的线程、锁、原子。

## 一个并行循环允许什么

**捕获**

- 只读视图按引用共享，零复制——这是并行里唯一的"共享"；
- 内建标量（整数、`f32`/`f64`、`bool`）按值捕获：调用前求值一次，worker 拿到自己的副本；
  写副本不回传（结构体/引用这类值没有捕获故事，会报
  `` only read-only views and scalar values can be captured by a par loop ``）。

**写**

- 只能写本循环的**输出视图**里属于自己的那一格：一维是 `out[i]`，多维是 `out` 上以循环变量为
  仿射自变量的下标。谁写哪一格由下标决定，不重叠，所以不需要锁；
- 输出视图恰好一个。

**不允许**

- 写任何别的被捕获视图（那些是只读共享）；
- 在体内分配（`new` 一类）；
- 调用任何函数——设计只禁"带线程效果的调用"，**v1 取严**：体内的调用一律拒绝
  （纯函数调用要等效果摘要按调用图闭合后才放开）；
- `ext` / `yield` / `return` / `break` / `continue` 把控制流带出并行体；
- 输出视图与某个只读视图指向同一块存储（别名会让"谁写哪一格"的论证失效）。

**下标类型是 `i64`。** 窄下标在设备端会退化成逐元素转换，这正是数据并行最不想付的税。
两端只要都能无损进 `i64` 就够：`par i in 0..n` 合法（`0` 是精确常量）。

**二维折叠**：内层再写一个 `par` 是在同一个内核里再套一层循环，不另开线程。此时写目标的
下标必须**一一对应每个 `(r, c)`**，能证明的写法只有 `out[r * K + c]`：`K` 要能证明至少等于
内层循环的迭代次数（`par c in 0..cols` 时写 `out[r * cols + c]`）。证明的做法是把 `K` 读成
关于内层上下界的仿射形 `A*hi + B*lo + C`，`A >= 1 && A + B >= 0 && C >= 0` 时
`K >= hi - lo` 恒成立——所以带行填充的 `out[r * (cols + 1) + c]`、`out[r * (2 * cols) + c]`
都算得出证明；`K` 证不出来就拒绝（猜一个常数会让两个外层落进同一格，是静默错值）。
worker 拿到的是整份输出视图（一维时拿到的是 `[lo, hi)` 切段），所以写的槽位是绝对行号。
只写内层变量（`out[c]`）或常数（`out[0]`）都不一一对应，必须编译失败。

**v1 的收窄（实现比设计严）**：最多折叠两层；体内禁止一切调用；泛型函数体与协程体里不能写
`par`（实例化/状态机会把同一个块的降糖重复做）。

## 归约

归约是第二个形状：`sum` / `count` / `max` / `min`，吃一个 `slice<T>`，出一个值。

<!-- fragment -->
```extc
par i in 0..n {
    out[i] = a[i] * b[i]
}
let s = sum(out)
```

**语义与顺序**：`stdlib/stl/seq.extc` 已内置固定分块的并行归约 —— `sumBlocksI64`、
`maxBlocksF64`、`minBlocksF64`（`a` 均分成 `parts.len` 段，`par` 写每段局部结果，再按段序串行
合并；同一个 `parts.len` 下结果可复现）。只收"结合后与串行逐位相同"的归约：整数加法（模算术）、
`f64` 的 `max`/`min`（取极值）。**浮点 `sum` 不在列**——分块改变加法结合顺序，浮点加法不结合，
不能同时保证与"从左到右串行累加"逐位相同；浮点求和仍走串行 `sum`，或"先算进数组、再串行归约"。

先算进数组、再归约，仍是第一版唯一支持的组合。一趟完成的融合归约（循环体直接折叠成一个值）
需要"块的值"这一层语法，属于后面的事。

## 错误

限制集每一条都要有稳定的错误文案，例如：

```
error: this par loop may write only its own output slot
error: cannot write through a captured view inside a par loop
error: cannot allocate inside a par loop
error: cannot call a function with thread effects inside a par loop
error: cannot escape a par loop
error: the output view of a par loop aliases a read-only view
```

## 判据

"做完了"指这五条同时成立：

1. **等价**：每个并行程序，与"把 `par` 换成顺序 `for`"的版本相比，stdout 逐位相同；
2. **加速**：在基准里，多 worker 相对单 worker 有可测加速（具体数字以基准报告为准，不进本页）；
3. **拒绝**：限制集每一条都有反例，必须编译失败，且错误文案稳定；
4. **不退化**：顺序版本与并行版本的生成代码都不比同一份代码的纯顺序写法慢，
   向量化自报不减少；
5. **可解释**：基准报告 ns/cell 与有效带宽；带宽受限的负载要能看出它被带宽卡住。

## 状态

- **归约**：`stdlib/stl/seq.extc` 的 `sum` / `max` / `min` / `count` 串行版（与从左到右逐位
  相同的语义已钉）；固定分块的并行合并内置了 `sumBlocksI64` / `maxBlocksF64` / `minBlocksF64`
  （`tests/par/par_blocks.extc` 对拍且 1/4 线程同输出），浮点 `sum` 的并行合并按上面的理由不做；
  `tests/par/par_reduce.extc` 覆盖"先算进数组再 `sum`"这条路线。
- **`par` 语法与拖糖**：已实现（parser 造与区间 for 同形的块并打标记，检查器 `parLower` 把它
  降糖成合成 worker 上的一次调用——编译器自己的通道，不经过 `parallel::run` 的用户可见签名）。
- **限制集**：写集、捕获（视图/标量）、别名、控制流逃逸、效果五类判定已实现，错误文案稳定；
  二维折叠的下标形状判定与"最多两层"也在这条里。
- **反例测试集**：`tests/par/`（正例对拍 + 限制集每条一个反例），`tools/check.py` 已注册。
- **基准**：`bench/par/` 报告 ns/cell 与有效带宽。

`par` 的运行时复用 `parallel::run` 的 pthread 池化无关实现：每次调用起线程、原子计数器动态
领块（`n / (threads * 8)` 为块大小）、线程本地 arena；默认线程数来自 `_SC_NPROCESSORS_ONLN`，
可用 `EXTC_PAR_THREADS` 覆盖。

现有的 `parallel::run` 继续保留，作为逃生舱：它不保证将来下放到设备端，但今天能干粗活。

## 线程与回收（暂缓，规则已定）

多线程回收常被当成"全堆 GC 的并发版本"，那是另一道题。这套内存模型把它压成一句话：
**对象在哪块 arena 就由哪块 arena 回收**。由此得到的三条性质，决定了它不是一个研究题：

- **线程 = arena 树上的一个节点**。线程内的分配进自己的 arena；收集器因此永远是单线程的，
  没有跨线程屏障、没有 stop-the-world、没有原子根表。
- **引用不过线程**（既有模型，[`TODO.md`](TODO.md) 的并行条目）。一块 arena 里的对象只被
  它所属的线程引用 ⇒ 标记时的根集合就是本线程帧的根表，别的线程的栈不需要看。这是整套
  并发便宜的**全部**原因：省掉的是"扫描别人的栈"和"跨线程可见性"这两件最难的事。
- **跨线程只有两种值**：所有权**移动**（发送侧作废，所以值必须自包含 —— 深度检查已经在
  保证这一条）与**只读快照**（拷贝，或指向祖先 arena 的不可变值，`join` 屏障保证它还活着）。

剩下的工作，是工程和两个设计决定，不是算法：

1. **线程的语法与 arena 归属**：`spawn` 出的线程，它的 arena 挂在谁下面；`detached` 线程
   的父帧可能先退出，而现在的深度规则假设"子不会比父活得久" —— 第一版应当禁止 detached，
   或者把这种 arena 挂到根上、只由主线程回收。
2. **所有权转交的检查**：`send` 是移动、值必须自包含、`join` 时把结果提升到父 arena。
   `promoteInto2` 与 `promoteReceiverFields` 已经是这条机制的现成一半。
3. **池化的 arena 复用**：线程被复用时 arena 要"按任务重置"而不是"按线程销毁"，回收阈值
   与分片预算也跟着按任务重置 —— 这正是 arena 的强项（整块归还）。
4. **只读快照的发布单元**：读多写少时才给，单元由"多久写一次、写多大一坨"决定，不做透明
   的整对象复制。

一句话：**并发回收的难点被"引用不过线程"提前消掉了**，剩下的是线程语义与池化生命周期的
设计。它暂缓，不是因为难，是因为还没有需要它的程序（`par` 的 fork-join + 每线程 arena 已经
覆盖了今天所有的并行负载）。

## 非目标

- 用户可见的锁、原子、内存序、共享可变数据；
- 嵌套并行再开线程（内层折叠进同一内核）；
- 通道与只读快照（那是另一个形状，[`TODO.md`](TODO.md) 里单独列）；
- 设备后端本身。本页只保证限制集不封死它。
