# 模块系统：身份、导入、门面与所有权

这页写**现在的模块规则**：一句话能做什么、边界在哪、错了会看到什么。用法示例见
[`usage/modules-cabi.md`](usage/modules-cabi.md)，历史见 [`CHANGELOG.md`](CHANGELOG.md)。

## 1. 模块的身份：文件负责找，`module` 负责叫什么

一个**文件**一个模块。文件名默认就是模块名：`use a::b` 找的就是文件 `a/b.extc`。
文件第一行可以写 `module a::b` 改它的**身份**（诊断、限定名、生成 C 的前缀都跟着它走），
路径仍只负责找文件。

<!-- fragment -->
```extc
// lib/fancy.extc 第一行
module fancy::core

fn who() -> i64 { return 42 }
```

<!-- fragment -->
```extc
use std::io
use lib::fancy as api

fn main() -> i32 {
    // 文件路径是 `lib::fancy`；模块自己叫 `fancy::core`。导入用路径，句柄 `api` 照常用。
    io::println(f"who={api::who()}")
    return 0
}
```

边界（都在编译期报错）：入口文件不能声明模块名；两个文件不许声明同一个模块名。

## 2. 导入：句柄带来模块的全部公开名，值名要写出来

| 写法 | 带进什么 |
|---|---|
| `use a::b` | 句柄 `b`（于是 `b::name`），以及 `b` 导出的**类型名**（裸写 `box` 可用） |
| `use a::b as x` | 句柄 `x`，别名对路径整体生效：`x::name`、`x::box` 都能解析 |
| `use a::b::{f, g}` | 只带 `f`、`g` 两个**值名**进裸名空间（`f()` 直接调）；句柄 `b` 照旧在 |
| `use a::b::*` | 把一个模块的全部公开**值名**带进裸名空间；`@private` 的照样拿不到 |

两条规则合起来是一句话：**导入一个模块带来它的句柄与类型名；函数/全局量这类值名，
要 `::{…}` 或 `::*` 显式列出来**。

为什么类型名跟着导入走：类型在签名里无处不在，全要求 `use x::{Type}` 会把简洁度吃回去；
而反过来的选择（只拿句柄、什么都不带）会让每处签名都多一行导入。为什么值名不跟着走：
跟了之后"这个 `helper` 从哪来"就没人说得清，而且两个模块同名函数进裸名空间会变成
歧义诊断而不是一行多余的字。

裸名解析沿**所有者**走：`use api::{f}` 里的 `api` 只是发布名字的门面时，`f` 按其真正的
声明者查表；限定名 `api::f` 也一样。门面不会把名字"困"在自己身上。

## 3. 门面：`pub use` 让实现能拆、用户代码不动

模块可以把自己的名字**再导出**给别人：`pub use std::io::{padText, fmtI64Fast}`。
于是实现文件怎么拆都不影响调用方 —— `std::io` 就这样把流、格式化、诊断分成三个文件，
而 `use std::io` 的人一行不改。

只允许显式名字列表：`pub use x::*` 被拒绝，因为"再导出所有名字"会让公开面随实现文件漂移。

## 4. 所有权：一个类型只有一套方法，`@ext` 把提供者写下来

类型的方法集是它的一部分。给**别的模块**声明的类型加 `impl` 块时，块上要写 `@ext`：
读代码的人能在一行里看出这些方法由谁提供。块就住在类型自己的模块里时反过来不许写。

| 形状 | 结果 |
|---|---|
| 别的模块里写 `@ext impl far { … }` | 编得过，方法可调用 |
| 别的模块里写 `impl far { … }` | 拒绝：`` `impl far` extends a type of module `lib`: write `@ext` `` |
| 类型自己的模块里写 `@ext impl far` | 拒绝：`` `@ext` on an impl block of the type's own module `` |
| `impl i64 { fn hash … }`（内建标量） | 放行 —— 内建类型没有声明者，方法天然由写块的人提供 |
| trait impl | 走 orphan 规则（块必须在 trait 或类型的家），与 `@ext` 无关 |
| 两个模块各写一份同名方法 | 拒绝：`` struct `lib::far` has duplicate method `dup` ``，报在**第二份声明所在的文件**，note 指出第一份在哪 |

位置报在**块所在的那个文件**：模块体内的诊断与函数体一样，归它自己的文件。
标准库自己遵守这条规则；`stdlib/INDEX` 的 `method` 行里，模块列是**提供者**
（`impl` 块所在模块），不是类型的属主。

## 5. 语法糖自己登记它的模块

语言里的糖不要求用户为它 import 库：值 f-string（含格式说明符）与多下标糖在解析时
把需要的模块登进本文件的 `use` 列表。**糖碰到的库布局变了，改的是糖，不是用户代码**。

## 6. prelude：唯一隐式导入的模块

prelude 是编译器在每个编译单元前先过一遍的一段 extC 源码，它声明的名字不写 `use` 就能用
（`option`/`result`/`slice`/`varArray`、`println` 这类内建）。它**不**顺带把大模块
（`std::io`、`std::text::string`）整个拉进来：一次 `use` 两个模块的编译成本约 19ms，
每个程序都付就不划算了。默认面只放"所有程序都真的要用"的那几个名字。

## 7. 诊断质量

- 内部改名（`pair` → `pair$pair`）不许出现在诊断、输出与调试开关里。
- 模块体内的诊断指到**模块文件**，不是入口文件。
- 缺导入/写错限定名时，消息要给出该写的那一句（``write `lib::open` ``），而不是只说"未定义"。

## 9. 边界（今天不做）

- 没有相对导入（`use super::…`/`use self::…`）；模块名是全路径。
- 别名只作用于路径前缀，不是类型的另一个名字：`use a b as x` 之后写 `x` 当裸类型名不行，
  写 `x::box` 行。
- 没有条件导入、没有版本选择、没有重命名再导出以外的公开面控制。
- 导入带来类型名（见 §2 的成本取舍）；要更严格只能靠约定，不加开关。
