## ① 需要主人拍板

### ✅ 已拍板（2026-09-18）：引用语义 = **形状 3 + `mut ref`**

主人选定了 [`REFS.md`](../docs/topics/REFS.md) §3 的**形状 3**（值位置自动解引用），
并且**跟 `mut ref` 一起做**。

| 决定 | 内容 |
|---|---|
| **读** | `p`（`ref T`）在值位置**自动解引用** ⇒ 得到 `T` 的值 |
| **写** | `p = v` ⇒ 写进 `p` 指向的地方（这就是缺的那个操作） |
| **可见性** | 由**类型**承担：`ref T` 只读 / `mut ref T` 可变（不再靠标点标记） |
| **换指向** | **放弃**（`=` 被「写进去」占用了）。今天 0 处使用、有替代写法、以后能纯加法加回 |
| **引用字段的初始化** | **不是换指向** ⇒ 不受影响（`slice<T>` 的 `data: ref T` 靠它） |

**理由**：可见性由类型承担而不是标点（避免「`mut ref` 已说明能写，还在每处写 `.*`」的双重标记）；
零新语法；零迁移成本（换指向 0 处使用）；而且让编译器里 **30 处 `ttBase`** 从「地雷」变成「正确」。

### 待定：整数的算术语义（溢出 / 除零 / 移位）

**背景**：extC 编译到 C，而 **C 的整数算术有 UB** —— 这些 UB 会**被继承过来**，
跟「extC 不给 UB」的承诺直接冲突。奶昔实测了三处（见 `BOOTSTRAP.md` §6）：

| 情况 | 现在 | 选择 |
|---|---|---|
| 有符号溢出 | ✅ 已用 `-fwrapv` 变确定（**绕回**），但语义没正式定 | **绕回**（跟 C/Go/Rust release 一致，零成本） / **trap**（安全但要每次检查） |
| 除零 | 崩掉（SIGFPE），**没有 extC 位置** | **trap 带位置**（推荐：除法本来就要几十周期，一次比较可接受） |
| 移位 ≥ 位宽 | **静默算错**（UB），只有 gcc warning | **按位宽取模**（跟 x86 一致，零成本） / **trap** |

**奶昔建议**：绕回 + 除零 trap + 移位取模 —— 三条都是「零或极低成本」，
而且各自跟某个主流语言一致（C/Go、Rust debug、x86）。

### 待定：`let` 的「浅」要不要靠「可变性进类型」收口？

定案 28 让 `let` 挡住了直接写入，但**管不到数据层**：拷进 `var`、传进函数、
`self: ref T` 方法接收者，三条路都还能写同一块内存。

根因是 **`ref T` 一个东西兼了两种含义**（Rust 的 `&` 和 `&mut`）：

| 想要 | 但 `ref T` 表达不了 |
|---|---|
| 只读共享（大 struct 不想拷贝） | 跟「可变引用」长得一模一样 |
| 可变借用 | 只能靠「接收者是 `let` 还是 `var`」在调用点猜 |

**如果要收口，形状是这样**（Rust 味，但要加一个关键字）：

```extc
fn get(self: ref slice<T>, i: i64) -> T        // 只读引用 ⇒ let 也能调
fn place(self: mut ref board, x: i32, ...)     // 可变引用 ⇒ 接收者必须是 var
```

代价：**要改每个签名**（包括 prelude 的 6 个只读方法）、`ref` 语义要重定
（现在文档里写的是「`ref T` 是可变引用」，变成只读之后要全改），
而且要处理「`slice<T>` 到底是只读视图还是可变视图」——
Rust 用 `&[T]` / `&mut [T]` 两个类型，extC 得跟着定两个。
**顺带的好处**：能根治「写字符串字面量会崩」（只读视图的 `data` 是只读引用）。

**奶昔的建议**：先不动。理由 ——
① 现在缺的是**逃逸检查 / 借用检查**（week-4），那正是要把可变性放进类型的时候，
两件事一起做比现在拆开做省一次全量改签名；
② 定案 28 已经挡住了「忘了写 `var`」这个**真实痛点**（本地变量上的意外写入），
而剩下三个缺口都要**显式地**把值交出去（拷贝 / 传参 / 调方法），
不是「手滑」，是「有意为之但没意识到」——级别不同。

但要请主人拍：**够了就先这样，还是现在就把 `&` / `&mut` 那一层加上？**

### 决策 10 的一个待定细节：方法接收者要不要写 `ref`

示例代码**自己不一致**：

| 写法 | 示例 |
|---|---|
| 自由函数写了 `ref` | `evaluate(ref s.board, player)`、`alphabeta(ref s, ...)`、`candidates(ref real)` |
| 自由函数**没写** `ref` | `line_score(b, p, player)` —— 形参也是 `ref board` |
| 方法调用都不写 | `b.count_dir(...)`、`s.rollback(mark)`、`self.board.place(...)` |

**奶昔按这条规则实现（不对就骂奶昔）**：

> **`.` 本身就表示「在这个值上操作」，所以方法接收者自动取地址；自由函数的 `ref T` 实参必须在调用点显式写 `ref`。**

## ⑦ 泛型调用不写类型实参（2026-09-18 定）

> **类型实参只出现在类型位置。** 调用点不写。

```extc
fn makeBox<T>(v: T) -> box<T> { return { value: v } }

let b: box<i32> = makeBox(1)     // T 从实参推 —— 调用点不写 <i32>
let c = makeBox(2)               // 同上
let d: box<point> = newEmpty()   // 没有实参 → T 从**期望类型**推
```

**这不是新规则，是「类型可以省略」这条规则又一次应用**：
`var y = 4`（从初始化式推）、`let p: point = {}`（裸 `{}` 从上下文推）、
`makeBox(1)`（类型参数从实参推）—— 同一条「编译期推导」。

推不出来就报错、让你加标注，而标注**写在该在的地方**（类型位置）：
```extc
let x: box<i32> = newEmpty()
```

**为什么不做 Rust 的 `::<>` / Go 的 `[]`？**

- 那两个记号都是**推导不够用的补丁**，不是设计
- Rust 在**两个地方**写类型实参、而且**写法不同**（`Vec<i32>` / `Vec::<i32>`）——
  **那才是不统一**。extC 只有一种写法 ⇒ 零例外 ⇒ 统一
- Go 的方括号在 extC 里会跟**数组** `[15]i32` 撞（`[]` 同时表示数组和泛型实参），
  而且 `a[i]` 与 `box[point]` 的 `[` 需要区分「里面是表达式还是类型」——
  两者都是小写标识符，parser 分不出来，得回溯

**真需要记号的那一天再加**（比如加了重载、或方法链导致中间类型没有名字）——
那时是为**真实问题**加，不是为想象中的问题加。

## ⑧ 保留定义与命名强制（2026-09-18 主人定）

| # | 定案 | 实现 |
|---|---|---|
| 17 | **prelude 里的定义是「保留的」，用户不能重定义** | ✅ `reserved` 标记；重名时报 `` `slice` is a reserved definition and cannot be redefined `` |
| 18 | **不能给已有类型加方法** | ✅ **语法上不可达** —— 没有 impl 块，方法必须写在 struct 体内。不是运气，是「语法一致、不要有特例」的副产品 |
| 19 | **类型名首字母必须小写、泛型参数首字母必须大写** | ✅ 强制检查 ⇒ 两者**集合不相交**，语法上不可能同名 |
| 20 | **编译器认的「协议」要显式检查** | ✅ prelude 加载后校验 `slice` 的形状（`data: ref T` + `len`），不符合就报 internal error |

### ③ 的由来

主人问：「直接用 `T` 真的是好的吗，万一用户自定义结构体叫 `T` 呢」

**验证下来是真的能撞** —— `struct T` + `struct box<T>` 会编译通过，里面那个 `T`
**遮蔽**外面的。能编译但读者看不懂，就是坏设计。

奶昔之前只给了**约定**（「单个大写字母是通行写法」），没给**保证**。
改成强制检查之后就是保证了。

## ⑨ 第四批：数组与切片（2026-09-18 定）

| # | 定案 | 一句话理由 |
|---|---|---|
| 17 | **数组统一套 struct**，成员也一样 | 于是 `a[i]` **永远**编译成 `a.data[i]`，不需要「看上下文判是不是成员」——上下文相关的 codegen 是 bug 温床 |
| 18 | 数组字面量**严格计数**，末尾 `...` 补零 | 防 off-by-one；`...` 必须能从上下文拿到长度，拿不到就报错 |
| 19 | **数组是值**（赋值/传参/返回都拷贝），要省就写 `ref` | 沿用「默认值语义、引用显式」；900 字节的拷贝贵，但**不要让读者猜** |
| 20 | 切片越界：**能证明的在编译期报错，不能证明的运行时 trap** | P。字面量界越界（含负数、反着切）**跟另一个界无关，所以永远错** ⇒ 当场报 |
| 21 | 省略的界**由 check 补成字面量**（`a[2..]` → `a[2..15]`） | 让 codegen 只需判「两个界是不是字面量」，不用再判「有没有省略」 |
| 22 | 切固定数组的底必须是**「地方」**（变量/字段/索引链） | 切数组要取元素地址，`make()[1..3]` 会切到临时存储上。切 **slice** 不受限（只做指针算术）⇒ `"abcdef"[1..3]` 合法 |
| 23 | **视图元素是 lvalue**（索引原语返回指针，`s[i]` 解引用） | 否则 `fn ==(self: ref T, ...)` 收不了视图元素（`slice<struct>` 直接编不出来），且 `s[i] = x` 是 gcc 原始错误 |
| 24 | **视图可写**（不是「只读视图」） | `slice<T>` 的 `data` 本来就是 `ref T`，而 extC 的规矩是引用必须在类型里看得见（P′）。⚠️ 已知代价：写字符串字面量的字节会崩（没有 `const`） |
| 25 | **非字节视图按元素打印**（`[2, 3, 4]`） | 视图是「一片元素」；否则打印成 `slice { data: <ref>, len: 3 }`，给不出任何信息 |
| 26 | `b[2..5][3..8]` **不是二维切片**（它就是「行视图再切一刀」） | 不连续的东西没法用一个指针+长度表示。要拿「一个格子」就得两个下标分别取 |
| 27 | **`==` 右边的裸 `{}` 不做推断** | 主人定调：**显式是对的，不要那么多自动推导**。写全 `point { x: 1, y: 2 }` |
| 28 | **`let` 是只读的，而且管「根」** —— 字段 / 数组元素 / 视图元素 / 取 `ref` 一概不许 | 主人定调：**let 相当于 const，var 就不是**。之前只查裸标识符，于是 `let p; p.x = 1`、`let a; a[0] = 1`、`let v = a[..]; v[0] = 1` 全漏过去了 —— 而那正是「忘了写 var」最常犯的形态 |
| 28′ | ⚠️ **但这条规则是「浅」的：它管名字，不管数据** | 三个已知缺口：① 拷进 `var` 就能写；② 传进函数照样能写；③ `self: ref T` 的方法接收者不受限（`let p; p.moveBy(1)` 允许）。**收口要靠「可变性进类型」**（Rust 的 `&` / `&mut`），见下面的待定项 |

## ⑩ 第五批：`option` / `result` 与关联函数（2026-09-18 定）

| # | 定案 | 一句话理由 |
|---|---|---|
| 29 | **`::` 关联函数**：写在 `struct` 体内但**不带 `self`** 的函数，调用 `Type<Args>::name(x)` | 泛型自由函数压根不解析、方法又必须有 `self` ⇒ 没有它就**没法在 prelude 里写构造器**。顺带解锁 `array<T>::new()` |
| 30 | 调用点**写全类型**，不从参数或上下文倒推 | 定案 27 的延续：显式优于推导 |
| 31 | **`option<T>` / `result<T,E>` / `unit` 都写在 `stdlib/prelude.extc`**（不是编译器内建） | 「能写在 extC 里的就写在 extC 里」。零值就是 `none` / 失败侧 —— 定案 8 的直接结果 |
| 32 | **`unit` 用真实类型，不给 `result<void, E>` 开特例** | void 不能当字段类型，特例会破坏「语法一致无特例」。编译器给零字段 struct 补一个占位字节（C 不允许空 struct） |
| 33 | `result` 的构造器叫 **`success` / `failure`**（不叫 `ok` / `err`） | 标签字段已经叫 `ok`，而**字段和方法不许同名** —— 这条规则是编译器自己抓出来的 |
| 33′ | ⚠️ `option<T>` / `result<T,E>` 的 `T` **不能含 `ref`** | `None` 的那个 `value` 字段没有合法的值可填，而「`ref` 不可为空」是承诺。`option<slice<u8>>` 等 week-4 |
| 33″ | ⚠️ **故意不给 `option` / `result` 定义 `==`** | 泛型的 `==` 是「一实例化就检查」的，给了它就意味着任何 `option<point>` 都强迫 `point` 定义 `==`。等「只生成用到的方法」到位再说 |
| 34 | `?` 只在 **`f()?` / `let x = e?` / `x = e?` / `return e?`** 四处 | C 没有语句表达式，而 `?` 必须在语句级展开成「求值一次 + 判断 + return」。别的位置报清楚，而不是生成编不过的 C |
| 34′ | `?` **允许载荷类型不同、要求错误类型相同** | 里层 `result<i64, E>` 可以放进返回 `result<point, E>` 的函数（要构造新载荷的失败值）；但错误是**原样转发**，不编造转换 |
| 34″ | 编译器认识 option/result 的**标签与载荷字段名**（`has`/`value`、`ok`/`value`/`err`） | 跟视图协议 `data` + `len` 同一种分工：**语言认识协议，库提供结构**。`?` 是语言构造，它只知道这几个名字，别的全在 prelude |

## ⑪ 第六批：位运算与 `ref` 的两个洞（2026-09-18 定）

| # | 定案 | 一句话理由 |

## ③ 写代码时才发现的问题（真收获）

### 1. 裸 `{}` 逼出了一条规则，而且它必须是统一规则

`var p: point = {}` 能靠声明类型补全，那 `return { x: 0, y: 0 }` 呢？`f({})` 呢？

奶昔拍的是：**类型从上下文推导，只在「上下文能唯一确定类型」的三个地方允许** ——
`var x: T = {}`、`return {}`（函数返回 T）、`f({})`（形参类型 T），**推导不出来就报错，绝不猜**。

关键不是这三个位置，而是：**它必须是一条统一的规则，不能是一个特例**（§11.7）。如果只支持 `var` 那一处，它就是个特例，将来会变成坑。

### 2. arena 里的动态数组增长会留垃圾 ⚠️

`Vec`/`Buf` 增长时新块从 arena 拿，**旧块还不了**（arena 不单独回收）。编译器无所谓（跑一次就退出），但这是 **arena 模型的真实代价**，对长跑程序会有影响。

设计上要回答：`array<T>` 要不要提供 `reserve(n)`？arena 要不要支持"回收最后一个块"？—— **这条建议写进 DESIGN.md**。

### 3. 「不建 AST」在这里被实测判死

`typeOf` 必须在**表达式生成阶段**可用（`println` 要按静态类型选格式、字段访问要知道是 `->` 还是 `.`、`let` 检查要知道可变性）。这些信息只存在于符号表和类型里 —— 也就是**只存在于建了 AST 的世界里**。

v0 那句「不解析整个 C、只重写 token」里对的那一半（C 透传）保留着；错的那一半（不建 AST）在写第三行代码的时候就撞墙了。

### 4. 类型检查现在很浅（要说清楚）

week-0 只做这几项检查：
- 未定义名字 / 未知函数 / 未知字段 / 未知类型
- 给 `let` 赋值
- 参数个数
- 裸 `{}` 推导不出来

**没做真正的类型检查**：`let x: i32 = "abc"` 会漏过去，最后由 gcc 报错。真正的类型检查器是下一步。
另外**只报第一个错误**，没有错误恢复。

## ⑭ 修正：**定案 44 是错的** —— 调用结果深度 = `max(实参)`（2026-09-18）

| # | 原定案 | 修正 |
|---|---|---|
| 44 | 函数调用返回的引用，深度算 0 | ❌ **错的上界**。`identity(ref x)` 深度算 0 ⇒ `return identity(ref x)` 放行 ⇒ **实测打印 `0`（悬垂）** |
| 44′ | —— | ✅ **深度 = `max(所有实参的深度)`**（`EX_CALL` / `EX_METHOD` / `EX_ASSOC` 三处） |

**为什么 44 当时看起来对**：它的理由是「由被调用者自己的返回检查担保」。
**这个理由是半个对的** —— 被调用者担保的只是「**它**不返回自己的局部」，
担保不了「它返回的是**你给它的**那个深层局部」✓ 转发（identity）是最小的反例。

**为什么 `max(实参)` 不是保守估计，而是精确上界**：
被调函数**能返回的引用只有两种来源** ——
① 它自己的全局/静态（深度 0）；② **它的实参**（深度 ≤ `max(实参)`）。
（它返回自己的局部，那条规则单独就挡着。）所以这就是全部可能 ✓

**同一步的另外两条**（三个必须一起落地，因为误报在掩盖洞）：

| # | 定案 |
|---|---|
| 45 | **借来的值不能存进 `placeDepth == 0` 的地方**。判据 `exprBorrowed`：**参数派生** 和 **调用结果** 为真；**全局**和**字面量**为假（静态的，谁都存得下） |
| 46 | **整体赋值给视图 = 换绑那两个词**，不是「透过视图写元素」⇒ 目标本身是视图类型时，**跳过可写性检查** |

**为什么必须一起**：46 修之前，`s = a[..]` 报「cannot write through `s`」——
**误报让 45 和 44′ 的反例变得不可达**（写不出能触发洞的用例）。先修 46，洞就露出来了 ✓

> ⚠️ **流程定案**：**看到误报不要只想着绕过它，先问「它为什么会被触发」** —— 它可能在替真正的 bug 站岗。

## ⑰ `match`：**语句、穷尽、无兜底**（2026-09-18，BOOTSTRAP §8 第 3 步的第一刀）

起因是主人问：**「match 是不是可以落地了，因为我有个想法，就是 result 和 option 或许可以用 match 重写？」**
—— 对，而且那个想法比"更雅致"值钱得多：它撞上一个**硬限制**（见 ⑱）。

| # | 定案 |
|---|---|
| 50 | **`match` 是语句，不是表达式** —— 跟 `?` 同一个理由：C 没有语句表达式，所以它不"返回一个值"。想往外传就在分支里 `return` / 赋值 |
| 50′ | **穷尽检查**：枚举的**每一个**变体都必须列出，漏一个就是编译错误。这是这个特性的**全部价值** |
| 50″ | **暂时不做 `_ =>` 兜底** —— 穷尽列出才是价值所在；真要兜底，以后再说 |
| 50‴ | 分支体可以是块，也可以是单个语句；被 match 的表达式**只求值一次**（生成的 C 就是一个 `switch`）|

**为什么它比 `if` 链值钱**：今天写 `if e == gameError.outOfRange { } else { }` ——
① `else` 得**手写**；② 以后给枚举**加了第三个变体，编译器不会提醒你漏了**。
`match` 会 ✓

**这一刀只做「无载荷」**（`type gameError = | outOfRange | occupied`）：
穷尽检查跟载荷无关，而**无载荷不需要 tagged union** —— 生成的 C 就是一个干净 `switch`。
**风险最小，而且语法是下一刀的超集，不返工** ✓

**实现**（四处，都不大）：`lexer` 加 `match` 关键字和 `=>`；`parser` 的 `parseMatch`
（⚠️ 被 match 的表达式要**关掉结构体字面量**，否则 `match e { ... }` 里的 `{` 会被当成 `e { 字段: 值 }`）；
`check.c` 校验「变体存在 / 不重复 / 穷尽」；`codegen` 发一个 `switch`（**不需要 `default`** —— 漏了根本编不过）。

## ⑱ 带载荷枚举（tagged union）（2026-09-18，第 3 步第二刀）

| # | 定案 |
|---|---|
| 51 | **`type shape = \| circle(f64) \| rect(f64, f64) \| dot`** —— 变体括号里是**载荷**，**位置式**（不带字段名）⇒ `match` 的绑定也是位置的：`circle(r) => ...` |
| 51′ | **零值 = tag 0** ⇒ **变体顺序有意义**。`type option<T> = \| none \| some(T)`、`type result<T,E> = \| failure(E) \| success(T)` —— 这正好保住今天「零值就是没有 / 失败」两条语义 ✓ tag 0 的载荷含 `ref` ⇒ 按现有的「不能零初始化」规则报错（**不新增概念**）|
| 51″ | 构造：`shape.circle(2.0)`（认出来靠"`shape` 是类型名不是变量"）· 打印：只打**变体名** · **没有 `==`**（C 的 struct 不能比 ⇒ 用 match，或自己写方法）|
| 51‴ | C 表示：**无载荷还是 `enum`**（一个字节没变），**带载荷是 `struct { tag; union }`** |

**两个 C 层面的坑**（都真踩到了）：

1. **顺序**：带载荷枚举的定义要进**依赖排序**那一区 —— `| holding(slice<u8>)` 排在
   `slice_u8` 前面会报 `unknown type name`。这跟 struct 是同一个问题，所以走同一套机制
   （`SUnit` 多一个 `td` 字段）✓ **结构上排掉，不靠碰巧对了**。
2. **`typeContainsRef` 被拆成两个问题**：
   - **有没有零值** ⇒ 只看 **tag 0** 的载荷（`typeContainsRef` 里的枚举分支）
   - **能不能携带引用**（要不要跟踪 refDepth / 全局能不能存）⇒ 看**所有**变体
   ⚠️ 这里其实**还没拆干净**：今天 `typeContainsRef` 的枚举分支只看了 tag 0，
   所以 `type maybeName = | nothing | named(slice<u8>)` 这种类型在
   `exprRefDepth` 的早退判断里被当成"不含引用" ⇒ 绑定的载荷深度算成了字面量深度。
   **待修**（跟下面那条注一起做）。

## ⑲ 泛型枚举（`type option<T> = | none | some(T)`）（2026-09-18，第三刀的前置）

第三刀（把 `option` / `result` 重写成普通枚举）**需要它**，所以先补。

| # | 定案 |
|---|---|
| 52 | **`type 名字<T> = | ...`** —— 类型参数表跟 `struct` 同一套语法、同一条大小写规则 |
| 52′ | 构造：`maybe<i64>::just(42)`（**无载荷变体连括号都能省**：`maybe<i64>::nothing`）—— 认出来靠的是"这个类型是枚举而且这个名字是变体" ⇒ **原地改写成 `EX_ENUMVAL`**，跟非泛型那条路完全一样 ✓ |
| 52″ | 载荷类型**不预存到实例上**：`TypeDef` 上写的还是 `T`，用到时按 `edef->typeParams` + `t->targs` 现场替换（`ttSubstitute`）⇒ 一个 `TypeDef`、多个实例，跟泛型 struct 同构 ✓ |
| 52‴ | 实例单独一张表 **`tt->enumInstances`**（不混进 `tt->instances`）—— 它们的 owner 是 `edef` 而不是 `sdef`，混进去会让那些按 `sdef` 走的循环出岔子 |

**实心踩到的四处**（都值得记）：

| 坑 | 现象 |
|---|---|
| `substEnter` 假定有 `sdef` | 枚举实例没有 ⇒ 取 `edef->typeParams` |
| 载荷类型解析时要带 `td->typeParams` | 否则 `just(T)` 报 `unknown type T` |
| 实例名不在类型表里 | `ttFromName("maybe_i64")` 返回 NULL ⇒ 用 `assocOwner` 把**解析好的类型**带到 codegen |
| tag 常量要**按实例**出 | 基类型出 `maybe_nothing`，实例却用 `maybe_i64_nothing` ⇒ 名字对不上 |

**顺带解开一个限制**：`option<slice<u8>>` 那种「载荷含 ref」的枚举，现在**语言层面完全支持** ✓
（第三刀把它用起来。）

## ⑳ 视图的只读降级是**递归**的（2026-09-18）

主人问：「现在能不能写 `mut slice<mut slice<T>>` 的啊，或者设想中可以吗」

**实测**：能写，而且两级写穿、元素级换指向都工作 ✓ 但**只读降级只剥了一层** ⇒
`mut slice<mut slice<i32>>` 传不进 `slice<slice<i32>>` 参数 ✗

| # | 定案 |
|---|---|
| 53 | **`mut` 是权限，不是布局** ⇒ 视图之间的转换规则是「**只许去掉 `mut`，不许加**」，而且**递归到每一层**（`ttViewDowngradable`）|
| 53′ | ⚠️ `ttEquals` 判「是不是同一个类型」（`mut` 算身份），`ttViewDowngradable` 判「能不能当它用」（`mut` 只是权限）—— **两件事**。所以同一个 C 名字会有**两个实例** ⇒ codegen 必须**按 C 名字对实例去重**（struct / `_debug` / `_eq` / `writeText` 各生成一份）|

**为什么递归去掉是安全的**：C 里 `slice<mut slice<i32>>` 和 `slice<slice<i32>>`
是**同一个结构体** ⇒ 少一份权限不改变任何字节 ✓

**验收**：`examples/nested-views.extc`（两级写穿 + 递归降级）
· `tests/errors/view_add_mut.extc`（只读→可写必须报错）
· `tests/errors/view_write_readonly.extc`（透过只读视图写必须报错）✓

## ㉑ **「视图是窗口，不是快照」—— 别名安全是一个特性**（2026-09-18）

主人问：「同层别名是啥」→「这个可以当成语言特性吗」。**可以，而且应该** —— 因为它不是缺口，
是一条**能证明的承诺**。

| # | 定案 |
|---|---|
| 54 | **允许别名**（两个视图/引用指向同一块）—— 这是视图的基础语义，**不是缺陷**。写通过一个，另一个立刻看到（**没有缓存、没有隐藏副本**）|
| 54′ | **承诺：不存在"已经被归还的存储"。** 没有手动释放 ⇒ 存储只在词法出口归还；深度规则保证引用不活得比被指对象长 ⇒ 引用要么指向**活着的存储**，要么**根本不存在**。**「过期」= 内容变了，永远不是地址坏了** |
| 54″ | 推论：**过期视图读到的永远是初始化过的字节**（不崩、不是 UB）—— ⚠️ **前提是 arena 的分配要清零**；今天 `alloc<T>(n)` 是裸 bump ⇒ **补 `allocSlice<T>(n)` 时必须清零** |
| 54‴ | 仍然**抓不住**的是"这个借用还有效吗"（要生命周期标注）⇒ 归 §0.5 的边界，靠 API 形状 + 语法可见性 ✓ |

**跟 Rust 的对照**：Rust 用借用检查器**拒绝**这种代码；extC **允许但安全**（最坏是逻辑 bug，
不是内存不安全）。这是"不写生命周期"换来的**具体形状**：**松一档，但绝不崩。**

## ㉒ 算术的失败必须**响亮**：除零 / 移位超宽 ⇒ trap 带位置（2026-09-18）

`SPEC.md` §0.5 那张承诺表里，有两行本来是 ⚠️ **欠账** —— 现在补上了：

| 情况 | 以前 | 现在 |
|---|---|---|
| `a / 0`、`a % 0` | 崩（SIGFPE），**没有源码位置** | `main.extc:5: trap: division by zero` ✅ |
| `a / -1`（a 是最小值）| UB | `trap: integer overflow in division` ✅ |
| `a << 64`、`a >> 64`、负数移位 | **静默算错**（C 里是 UB）| `trap: shift count out of range` ✅ |

**实现**：`genBin` 里整数除法/取模/移位改走 helper（`extc_divI` / `extc_divU` /
`extc_modI` / `extc_modU` / `extc_shiftCount`）—— **每个操作数只求值一次** ✓
（所以没用 `(check(r), l op r)` 那种逗号表达式：它会把 `r` 求值两次 ✗）
除法按**有无符号**分流，避免把 `u64` 折进 `int64` 再除（那会算错）✓

**新增测试类别**：`tests/traps/*.extc` —— **必须编译通过、必须非零退出、必须带 `trap:` 消息** ✓
`tests/run.sh` 多了一段跑它。这是**运行时行为**的测试，跟"正例能跑"和"反例编不过"并列第三类 ✓
（越界 trap 也一起钉住了 —— 那是既有行为，之前没有测试压着。）

## ㉓ 可写视图是**影子**，按指针找不到它（2026-09-18 修）

主人问「造不出 buffer 什么意思」，实测时抓出来的真 bug：

```extc
struct reader { chunk: mut slice<u8>  pos: i64 }
// → error: field 'chunk' has incomplete type
```

**根因**：codegen 的**依赖排序**（`unitFind`）按**指针**在 `tt->instances` 里找类型，
而 `mut slice<u8>` 是**影子**（跟只读版**共用 C 名字、共用结构体**，但是**另一个 Type 对象**）
⇒ 找不到依赖 ⇒ `reader` 被排在 `slice_u8` 前面 ⇒ C 里字段类型还不完整 ✗

**修法**：泛型实例/数组改按 **C 名字**找（`strcmp(u->inst->name, t->name) == 0`）——
一次解决两件事：影子，以及"同一个名字有两个实例（可写/只读各一个）" ✓

> ⚠️ 这是「**影子 vs 基类型**」这个混淆**第三次**咬人：
> ① 只读降级只剥一层 ② 实例去重 ③ 依赖排序 ✓
> 共同点：**`mut` 是权限不是布局 ⇒ 凡是"按身份/指针"比较的地方都要重新想一遍。**

## ㉔ 内存安全攻击测试（2026-09-18，主人要求"试试各种 hack"）

十一个攻击，逐个实测。**没有一个能从 extC 源码拿到「悬垂 / UB」** ——
没拦住的几个都是"**失败得不够响亮**"（P′），不是"不安全"（P）✓

| # | 攻击 | 结果 |
|---|---|---|
| ① | 引用**换指向**一个更短命的局部 | ✅ 拦住：*borrowed from depth 2, but this can only hold up to depth 1* |
| ② | `alloc<[4]i32>(1)` 之后索引 | ⚠️ **编译器 bug**：extC 放行，生成的 C 编不过（gcc: *'p' is a pointer; did you mean to use '->'?*）|
| ③ | `alloc<holder>(1)` 读里面那个 ref | ⚠️ 这次 **trap 住了**（`index 0 out of range (length 0)`）—— 但**是运气**（新 malloc 的页恰好为零）⇒ **未初始化内存读**是潜在洞 |

| ⑦ | 返回局部**字段**的引用 | ✅ 拦住（depth 1 > 0）|
| ⑧ | 借来的视图塞进**参数的字段**（洗白）| ✅ 拦住：*cannot store a borrowed value into something that outlives this call* |
| ⑨ | 泛型混淆 `pair<i32,u8>` vs `pair<u8,i32>` | ✅ 拦住（类型分得清）|
| ⑩ | 无限递归 | ⚠️ **无声崩溃**（退出码 255，没有消息、没有位置）⇒ 欠账 9 |
| ⑪ | 别名 + 过期（改底层后再读旧视图）| ✅ **安全**：读到旧字节（打出 `cccc`），**不崩** —— `SPEC.md` §0.6 那条承诺**实测成立** ✓ |

**值得记的两点**：

1. **最强的是 ⑧ 和 ①** —— 那正是今天刚修的两条规则（借来的值 / 换指向），
   它们**真的在挡东西**，不是纸上的 ✓
2. **⑪ 实测打出 `cccc`**：视图过期后读到的是**旧字节**（99 = `'c'`），
   内存没坏、进程没崩 ⇒ **「视图是窗口，不是快照」是可验证的承诺**，不是说法 ✓

## ㉕ 攻击测试第二轮：**打出一个真 soundness 洞**（2026-09-18）

主人说「可以试试更狠的这些」—— 更狠的这批**真的打穿了**：

| # | 攻击 | 结果 |
|---|---|---|
| ⑫ | 三层函数**接力转发**引用 | ✅ 拦住（`max(实参)` 逐跳传递）|
| ⑬ | 参数引用**装进结构体**再返回 | ✅ 拦住 |
| ⑭ | 返回「**一半参数、一半局部**」的结构体 | ✅ 拦住 |
| ⑮ | 先建结构体、再往字段**塞本帧视图** | ✅ 拦住 |
| ⑯ | 返回 `alloc` 要到的东西 | ✅ 拦住 |
| **⑰** | **枚举载荷来自本帧** | 🚨 **没拦住 ⇒ 悬垂 / UB** |
| **⑱** | **泛型枚举载荷来自本帧** | 🚨 **同样没拦住** |
| ⑲ | 【正例】载荷来自**参数**（`maybe<slice<i32>>::just(g[0])`）| ✅ 合法，`第一行 = [1, 2, 3]` —— **新能力**（条件性地把借来的视图交出去，不拷贝）|
| ⑳ | 同一函数里两个 `match` 绑同名 | 🐛 **codegen bug**：`'s__2' undeclared` —— 绑定的**声明**用了原名字，而 body 里用的是 `cname` ✗ |

### 🚨 洞的根因（`DECISIONS.md` ⑱ 那条"还没拆干净"的注，现在被证明可利用）

`typeContainsRef` 的枚举分支**只看 tag 0**（那是给"零值"用的语义），于是
`exprRefDepth` 对 `type box = | empty | holding(slice<u8>)` 早退返回 0 ⇒ **载荷深度从没算过** ✗

**修法**：拆成两个问题（零值看 tag 0；能不能携带引用看**所有**变体），
并让 `exprRefDepth` / `exprBorrowed` / 全局检查用后者 ✓

### 两条附带发现
- **裸写构造器**只认 prelude 那四个名字（`nothing()` / `just(x)` 报"未定义"）⇒
  用户枚举要写全 `maybe<i32>::nothing`。**可以扩展**：返回类型是枚举时，任何变体名都认 ✓
- ⑳ 的 codegen bug：`match` 绑定的**声明**要用 `Sym.cname`，不能用原名 ✓

## ㉖ extC vs C 性能对比（2026-09-20，主人要求实测）

`bench/run.sh` 可复现。公平起见两边用**同一套旗子**（extC 的驱动用的是
`-std=c11 -O1 -fwrapv`），另加一组 `-O2` 看"差距有多少来自优化级别"。

| 程序 | extC(-O1) | C(-O1) | C(-O1)+手写检查 | extC 的 C 换个旗子(-O2) | C(-O2) |
|---|---|---|---|---|---|
| 欧拉筛 N=3e6（只数个数）| **13 ms** | 8 ms | 8 ms | 8 ms | 8 ms |
| 矩阵乘 200×200（平坦下标）| **10 ms** | 5 ms | 6 ms | 5 ms | 3 ms |
| fib(32) 递归（无数组、无检查）| **13 ms** | 8 ms | — | 5 ms | 4 ms |

### ⭐ 好消息：**安全检查几乎不花钱**

手写检查的 C（每次下标 `if (i < 0 || i > N) trap;`）**8 ms vs 不检查 9 ms** ——
噪声级 ✓ 矩阵乘也只差 1 ms（5 → 6）⇒
**「视图 = 16 字节 + 每次索引一次带文件行号的检查」这个设计的代价基本是免费的** ✓

### 差距来自哪儿（三条，都可优化）

1. **优化级别**：extC 生成的 C 换 `-O2` 就追平（13→8、10→5、13→5）⇒
   **一大半差距是 `-O1` 这个选择**，不是语言本身 ✓（`-O1` 是主人之前定的"最小干预"，
   `-fwrapv` 也让优化变保守 ⇒ 以后可以重新评估）
2. **每帧 arena 的开销**：`fib(32)` 有约 700 万次调用，**每次调用都 init/release 一只 arena** ⇒
   13 ms vs C 的 8 ms。**优化点：叶子函数/不分配的帧根本不需要 arena** ✓
3. **codegen 质量**：`slice_*_index` 这类小函数在 `-O1` 下没被内联 ⇒
   即使 `-O2` 也可能有残余（matmul 5 vs C 3）✓

**结论**：**没有数量级差距**，而且**安全的那部分基本免费** ——
剩下的是"优化级别"和"每帧 arena 的两个可优化点" ✓

### ㉖ 补测（放大之后）：唯一的常数级开销是**除法 helper**

第一轮工作量太小（十几毫秒，被启动开销淹了）。放大到计算为主、用全局数组让工作集真实
（10 MB 筛、1 MB 矩阵），并且挑"最吃常数优化"的循环（源码在 `bench/*_big.*` 和 `bench/mod.*`）：

| 程序 | extC:O1 | C:O1 | extC:O2 | C:O2 |
|---|---|---|---|---|
| 筛素数 N=1e7 | 42 | 29 | **29** | **29** |
| **整除/取模 3×10⁸** | **1270** | **277** | **268** | **266** |
| 矩阵乘 512×512 | 149 | 102 | **34** | **33** |

**三条结论**：

1. **同一份生成的 C 换 `-O2` 几乎完全追平**（29/29、268/266、34/33）⇒
   **语言本身不吃常数亏，`-O1` 这个选择才吃** ⚠️（当初定 `-O1 -fwrapv` 是"最小干预"，
   现在有数据了，值得重新评估）
2. **唯一的真问题：整除/取模 4.6×** —— gcc 把 `i % 7` 编成"乘法 + 移位"（**不用除法指令**），
   而 extC 发一次 `extc_modI` 调用（还带两条 trap 分支：除零、`INT64_MIN / -1`）。
   `-O2` 内联之后差距消失 ✓
3. ⭐ **真正该修的其实不是内联，是"除数是字面量/可证明非零时，检查根本不该存在"** ——
   「凡是编译期能证明的，运行时不留痕迹」直接适用，而且检查去掉之后 **gcc 又能把取模变成乘法** ✓

**另外**：矩阵乘在 `-O2` 下 34 vs C 的 33 ⇒ **带检查的视图在优化器看穿之后零代价** ✓
（跟第一轮"手写检查的 C 和不检查的 C 一样快"互相印证。）

### ㉖ 更正：真凶是**没内联**，不是优化级别（主人 2026-09-20 一句话点破）

我前面写「一大半差距是 `-O1` 这个选择」—— **不准确** ✗
主人说：「其实你的那些检查函数给成内联行不行呢，O2 主要就是内联了各种 trap 检查」⇒ **正是如此** ✓

**做法**：把运行时的原语（`extc_trap` / `extc_divI` / `extc_modI` / `extc_shiftCount` /
`extc_checkedIndex` / `extc_checkedRange` / `extc_arena_*`）和视图取值器 `%s_index`
全部改成 **`static inline`**（12 处）✓

| 程序（-O1）| 改之前 | **改之后** | C:O1 |
|---|---|---|---|
| 取模 3×10⁸ | 1267 ms | **275 ms** | 277 ms |
| 矩阵乘 512×512 | 152 ms | **105 ms** | 103 ms |
| 筛 N=1e7 | 43 ms | **29 ms** | 29 ms |
| fib(32) | 13 ms | **7 ms** | 8 ms ← **反超** ✓ |

**为什么这样就好了**：内联之后 gcc **能看见检查体** ⇒
① `i % 7` 重新变成乘法+移位（不用除法指令）② 越界检查被范围分析消掉/提出循环
③ 每帧的 `arena_init/release` 变成一两条指令（fib 反超 C 就是这个）✓

⚠️ **一条要给以后的人看的规矩**（已写进生成的 C 的注释里）：
**这些原语必须 `static inline`** —— 去掉 `inline` 会静默地慢 1.5～4.6 倍，而且**没有任何报错** ✓

**仍然值得做的**（但不再是性能必需）：除数是编译期常量时不生成检查 ——
那会让**未优化构建**也快，而且更符合「能证明的不留痕迹」✓

### ㉖ 多语言对比（2026-09-20，主人要求：C++ / Python+numpy / Node …）

本机有：**gcc / g++ / clang / node / python3.14 / perl**（没有 Go / Rust / Java）；

**按同一规模折算**（纯 Python）：取模 ≈ **15.7 s**（C 的 59×）、筛 ≈ **0.83 s**（29×）、

### 解读（四条）

1. ⭐ **extC 在 `-O1` 下跟 C/C++ 的 `-O2` 基本持平**：取模 +4%、筛**完全一样**（29 ms）、
   矩阵乘 3.2× 慢 —— **而那 3.2× 纯粹是 `-O1`**（同一份生成的 C 用 `-O2` 编 = 34 ms，已验证）✓
   也就是说：**"安全检查"没有留下可测量的代价** ✓✓
2. **矩阵乘对优化器极其敏感**：gcc `-O2` 33 / gcc `-O1` 105 / clang `-O2` 94 ⇒
   差别在**循环变换（交换/分块/向量化）**，不是语言 ✓
3. **Node（V8）很能打**：比 C 慢 1.5×（取模）、3.5×（筛）、7×（矩阵乘）⇒
   现代 JIT 已经吃掉大部分差距 ✓
4. ⚠️ **numpy 那两行不能直接比**：
   - 矩阵乘 0.4 ms 是 **BLAS**（多线程 + 分块 + SIMD）⇒ **不是同一个算法** ✗
   - 筛 19 ms **比 C 还快**，是因为它用向量化的 `comp[i*i::i] = True`（打满内存带宽、无分支）
     ⇒ 那是**算法层面的胜利**，不是"Python 快" ✓
   - 取模 236 ms @3×10⁷（折算 3×10⁸ ≈ 2.4 s，比 C 慢 9×）⇒ 逐元素取模要物化两个临时数组，
     **内存带宽受限** ✓

**一句话**：**extC 目前的性能位置是「跟 C 同级」**（-O1 下持平，只有矩阵乘因为优化级别差 3×）；
**跟 Node 相比快 1.5～7×**；**跟纯 Python 相比快 29～466×** ✓

## ㉘ ⭐ 主人提出：**arena 全自动管理**（2026-09-20）

主人原话：「**不需要显式传递 arena**，那会很麻烦。一种很 nb 的方法是全部自动管理……
由于每一个 `{}` 都有一个 arena，你完全可以直接把当前 arena 隐式地传递过去；
由于你能够访问的内容应该全部位于**一套 arena 链**上，所以情况会比较简单」

**这是对的，而且比我那张"显式 `arenaOf()` / `allocFrom()`"的表好** —— 但有一条必须解掉。

### 显式方案的问题（主人指出的）

`fn build(a: mut ref arena, …)` 要求**每个调用点**都传一只 arena ⇒ 用户到处写样板 ✗
而 arena 本质上是**实现细节**（用户只想知道"这块内存活多久"）⇒ 让他手写就是设计失败。

### 全自动的诱惑与陷阱

**陷阱**：如果"被调函数的分配一律进**调用者**的 arena"，那么
**被调者的垃圾会活到调用者返回** ⇒ 长循环里反复调用一个 helper ⇒ **内存一直涨** ✗
（今天每帧一只 arena 的最大好处正是"**被调者返回时它的垃圾就没了**"）

### 解法：**arena 链 + 一层提升**（既自动、又保住局域性）

1. **每帧一只自己的 arena，它的父 = 调用者当前那只** ⇒ 形成**链**（主人的直觉 ✓）
2. **分配默认进本帧** ⇒ 不逃逸的东西**照旧死在帧里** ✓ 局域性保住
3. **⭐ 如果这个值会逃逸**（流进返回值 / 出参 / 会逃逸的结构体字段），
   编译器把它**提升一级**到父 arena ⇒ **调用者拿得到、而且活得比本帧长** ✓
4. 提升是**逐帧递归**的：调用者再往外返回，就再提升一级 ⇒ 自动跟着**调用链**走 ✓

### 为什么深度规则几乎不用改

| 情况 | refDepth |
|---|---|
| 分配**不逃逸**（留在本帧）| **1** ⇒ 返回被挡住 ✓（现状）|
| 分配**逃逸**（提升到父 arena）| **0** ⇒ 返回**合法** ✓ |

⇒ **现有的返回检查原样成立**，`allocFrom` 也不再需要 ✓

### 两个必须记住的边界

- **逃逸分析要保守**：存进"会逃逸的结构体字段"也算逃逸（`varArray.home` 那类）
- ⚠️ **线程**：bump 分配器**不是线程安全的** ⇒ 线程的 arena **不能**父到派生出它的那个帧的链上
  （两个线程同时 bump 同一只 = 数据竞争）⇒ **每条线程一条自己的链**，
  跨线程只走**拷贝 / 移动** ✓（跟之前定的"引用不过线程"一致）

⇒ **显式 arena 退化成逃生舱**（`varArray.home`、跨多层长寿区、线程自己的）✓
**默认全自动** ✓ 成本是**一个局部逃逸分析**（不是全程序推断）+ 每帧一个 parent 指针（8 字节）✓

我上面写成「每帧一只自己的 arena，父 = 调用者那只」—— **错了一级** ✗

|---|---|
| 参数 = 0 | （调用者的作用域）|

**今天的状态 vs 目标**：

### ㉘ 附：**循环结构会生成什么 C**（2026-09-20 主人问）

```extc
fn sum(n: i64) -> i64 {
    var total: i64 = 0
    var i: i64 = 0
    while i < n {
        var t = alloc<node>(1)      // 每轮一个节点，不逃逸 ⇒ 住进**循环体那只** arena
        t.value = 1
        total = total + t.value
        i = i + 1
    }
    return total
}
```

```c
int64_t sum(int64_t n) {
    extc_arena __a1; extc_arena_init(&__a1);      /* 函数体（深度 1）*/
    extc_arena __a2; extc_arena_init(&__a2);      /* while 体（深度 2）—— **对象提到函数开头** */
    int64_t total = 0, i = 0;
    while (i < n) {
        extc_arena_reset(&__a2);                  /* ← 每轮回到起点：一个 store，**不 malloc / 不 free** */
        node *t = (node *)extc_arena_alloc(&__a2, sizeof(node));
        t->value = 1;
        total = total + t->value;
        i = i + 1;
    }
    extc_arena_release(&__a2);                    /* 循环结束：块还回去（不留到函数退出）*/
    extc_arena_release(&__a1);
    return total;
}
```

**四条要点**：

1. **arena 对象提到块外面**（这里是函数开头）—— 否则每轮 init/release 会变成
   malloc/free 抖动 ✗ 提到外面之后，**每轮只是一个 `top->used = 0`** ✓
2. **进块 reset，出块 release**：循环体每轮 reset（复用块）；整个循环结束时 release ✓
3. ⭐ **"提升"在生成的 C 里看得见**：如果 `t` 逃逸（比如被塞进返回值），
   那一行会变成 `extc_arena_alloc(&__a1, …)`（**父作用域那只**）✓ 一眼可查 ✓
4. **每个 `return` 按内→外释放所有活着的 arena** ✓（`?` 生成的 return、`trap` 也一样）；
   `break`/`continue` 处同理（`continue` 反正下一轮会 reset）✓

**一条省事的规则：只有"含分配"的块才生成 arena** ⇒ 绝大多数块**零开销** ✓
（只接收提升的块也不需要自己那只 —— 需要的是**发起分配**的块 ✓）

**成本**：每块一个栈槽（8 字节）+ 函数开头一次 init（一个 store）+ 每轮一次 reset（一个 store）
+ 出口的 release —— 内联后都是几条指令 ✓ 而它换来的是 **malloc/free 全消失** ✓

**主人的洞察**：「一个帧里面的循环深度必然是有限的，所以 arena 也是有限的」

⇒ 更精确的一条：**一个函数里的 arena 数 = 它"含分配"的块数** ✓

**主人的第二条**：「如果没有 alloc 就不生成 arena」——**已经是定的规则** ✓
补一句：**只有"发起分配"的块**才需要自己那只；

### ㉙ ⭐ arena 是**一等公民**，但**超脱于泛型体系**（主人 2026-09-20 纠正）

主人的原话：「arena 是某种**一等公民**，**超脱于整个泛型体系**」

我前面把它讲成了"作用域的实现细节"，**偏了** ✗ 准确的说法是两句：

| 是 | 不是 |
|---|---|
| **一个类型**（`arena`，单态、**不带参数**）| ❌ **不是** `arena<T>` |
| **一个值**：能命名、能传、能当字段、能放全局 | ❌ **不进泛型参数表**（`<T, A: Allocator>` 那种）|
| **寿命由词法作用域管**（不在类型里）| ❌ **不参与单态化**，没有每类型的运行时元数据 |

#### ⭐ 反面例子（必须避免的设计）

```extc
// ✗ Rust 的 `Vec<T, A: Allocator>` 那一路：每个容器、每个泛型函数都拖一个 A
struct varArray<T, A> { ... }
fn f<T, A>(x: T, a: A) -> ...

// ✓ extC：arena **不在类型参数里**
struct varArray<T> { buf: mut slice<T>  len: i64  home: ref arena }   // arena 是**字段** ✓
fn f<T>(x: T) -> ...                                                  // 泛型签名干干净净 ✓
```

⇒ **`varArray<T>` 恰好就是这个原则的实例**：它只需要 `<T>`，
arena 以 `ref arena` 的**字段**身份出现 ✓（`ARRAYS.md` 里记的形状正是这样 ✓）

#### 为什么必须这样（三条）

1. **arena 装的是杂七杂八的东西**（`i32` / `node` / `slice<u8>` 混在一只里）⇒
   它**不可能**被参数化 ✗ 参数化会把它切碎成一堆互不相通的池子
2. **"要多大"在调用点就是常量** ⇒ `new<T>(n)` 的 `T` 只用来算
   `sizeof(T)`，**编译期**就没了 ⇒ 不需要任何运行时类型信息（P ✓）
3. **寿命是词法深度的事，不是类型的事** ⇒ arena 跟"不写生命周期"那条定位
   **同一个立场**：**寿命不进类型** ✓

#### 于是默认两条路并存（不矛盾）

| 路 | 什么时候用 |
|---|---|
| **隐式**：`new<T>(n)` 自动进**当前作用域**那只（编译期决定，逃逸就提升）| **默认**，用户什么都不写 ✓ |
| **显式**：arena 是一等值 ⇒ 能命名、能传、能存字段 | 需要"活得更久/给别人"时：`varArray.home`、跨多层、全局区、线程自己的 ✓ |

⇒ **"全自动"和"一等公民"是同一件事的两面**：默认不用提，需要时提得到 ✓

### ㉙ 附：名字用 `arena`；**`*` = 当前作用域那只**（主人 2026-09-20）

1. **`region` ≈ `arena`，不用两个名字** ⇒ 就用 **`arena`** ✓（`region` 标成 `DESIGN.md` 里的历史写法）
2. **"绝大多数时候并不需要关心"** ✓ —— 这正是隐式那条路的意义：`new<T>(n)` 自动进当前那只，
   用户**什么都不写**；显式只是逃生舱 ✓
3. ⭐ **命名直接用 `let *`** —— 即 **`*` 是"当前作用域那只 arena"**（一个内建表达式）✓
   ```extc
   let here = *          // 给当前这只起名（类型 ref arena）
   {
       let inner = *     // ← 内层那只，跟 here 不是同一只 ✓
   }
   ```
   **为什么这个符号是空的**：extC **没有一元 `*`**（无指针、无解引用运算符）⇒
   `*` 只在二元位置出现（乘法）⇒ **前缀位置完全空着** ✓
   **而且"当前"是词法的**（不是动态的）⇒ 跟深度模型同一个立场 ✓
   ⇒ `arenaOf()` 那种函数名**不需要了** ✓

### ㉚ 分配**不能长得像泛型** ⇒ 做成"语言形式"（主人 2026-09-20）

主人：「`new<T>` 我反而觉得别扭，我感觉 arena 是一等的话，
**所有跟 arena 相关的操作都不能联想到泛型**」✓ 这条理由很硬：

`new<T>(n)` **长得就是一次泛型调用** ⇒ 又把 arena 拉回泛型体系 ✗
跟 ㉙ 刚定的"arena 超脱于泛型"**自相矛盾** ✗

**正确形状：分配是一个语言形式，操作数是*类型*（像 `sizeof`）**：

```extc
var t   = new node              // 一个 node（**零值就绪**）⇒ mut ref node
var buf = new i32[1000]         // 1000 个 i32 ⇒ mut slice<i32>
var arr = new [4]i32            // 一个 [4]i32 ⇒ mut ref [4]i32
var t2  = new node { value: 1 } // 顺带填字段
```

⇒ **一个 `<T>` 都不出现** ✓ 而且顺手解掉三个问题：

| 顺手解掉 | 怎么解的 |
|---|---|
| 不支持按参数个数重载（`new<T>()` vs `new<T>(n)`）| 一个形式全包 ✓ |
| `alloc` 不清零、`new` 该"零值就绪" | `new node` **就是清零的** ⇒ 正好兑现 `SPEC.md` §0.6 那条承诺 ✓ |
| 返回值类型不清楚 | `new node` → `mut ref node`；`new i32[1000]` → `mut slice<i32>` ✓ |

**"住哪只"也是非泛型形状**：隐式 = 当前作用域 ✓；显式 = 加个尾巴（`new node in home`）——
**具体名字不急**（主人：「名字而已，不重要」）✓

⇒ **整个 arena 的 API 里没有一个 `<>`** ✓✓ 这就是"不能联想到泛型"的落地 ✓
（`*` 那个是主人打错的，作废；`arenaOf()` 也不用 ✓）

### ㉛ ⭐ 有了 arena，**"虚表"可以做了 —— 而且很安全**（主人 2026-09-20）

主人：「现在有了 arena 之后，你会发现一个很变态的东西：**你居然可以做虚表了，而且会被回收，这很安全**」

**对，而且它要两个东西合起来才成立**：

| 缺哪一半 | 会怎样 |
|---|---|
| 只有**函数值**（身份编译期唯一）| 表能建，但**表本身往哪放**？没有 arena ⇒ 要么手动释放、要么泄漏 ✗ |

**为什么"调用"仍然是静态的**（P 不破）：
函数值的**身份编译期唯一** ⇒ 每个**构造点**都静态知道表里装的是哪些函数 ⇒
`t.area(x)` 在编译期就能解析成**直接调用**（或者退化成 `match`）⇒
**没有间接调用、没有运行时函数身份** ✓✓
（学界叫 **defunctionalization**；C++ 模板 / Rust 泛型做的是同一件事：静态派发 ✓）

| 变可能了 | 怎么 |
|---|---|
| **每个作用域一张登记表**（处理器集合）| 建在作用域里 ⇒ 出块自动回收，**不用手动拆除** ✓ |
| **闭包捕获 arena 数据** | 捕获的状态跟着 arena 死 ⇒ **不悬垂**（逃逸检查管 ✓）|
| **AST 每节点的表 / 解释器** | 递归的数据结构 + 每节点操作 ⇒ 自举要用 ✓ |
| **静态 visitor** | 表里装操作 ⇒ 组织方式跟 OO 一样，**性能是零间接调用** ✓ |

**仍然不行**（永久损失，跟以前定的一致）：**开放注册**（插件、运行期才知道调用谁）✗
—— 那需要**运行时函数身份 + 间接调用** ⇒ 违反 P ✓

⇒ 一句话：**你能有"表"，不能有"运行期才知道装什么"的表** ✓
而且表是**数据**（不是机制）：随作用域回收、不可能悬垂 ⇒ **这确实是新得到的能力** ✓
⚠️ 前置：**函数值（第 6 步 lambda）**；arena 是让它安全的那一半 ✓

### ㉟ ⭐ **函数自己的 arena 一定是最深的那只**（主人 2026-09-20 的推理）

**为什么成立**（不需要从参数推）：

函数自己那只 arena 的深度 = 调用者当前深度 **+1** ✓

⇒ **函数自己的 arena 严格比所有实参的 arena 深** ✓✓

| 方向 | 判定 | 需要知道两个参数的关系吗 |
|---|---|---|
| 把**函数里 `new` 的东西**存进**实参指向的对象** | **无条件错** ✗ | ❌ **不需要** ✓（函数自己的东西必然最短命 ✓）|

**想判它只有三条路**：① 把关系写进签名（约束 —— 偏离"不写生命周期"）✗
② 调用点单态化（代码爆炸）✗ ③ 运行期带深度标签 + 一次整数比较（**引用变胖** 16→24 ✗）

⚠️ 唯一反例是 Rust 的 `let`（默认可变）✗ —— 但 extC 跟 Swift 一样是"**只读的写 `let`、可变的写 `var`**" ✓

**更重要的结论**：主人之前说「根本的 bug 是名字」—— **回头看，根因是语义不是名字** ✓
**语义修完（㊶㊷㊳）之后 `let` 就不骗人了** ✓：
| 看见 | 承诺（真的成立 ✓）|
|---|---|
| **`let`** | 名字不能换绑 ✓ + **透过它拿到的东西是只读的** ✓ |
| **`var`** | 名字能换 ✓ + 透过它能不能写**看类型** ✓ |

⇒ **分工清晰、名字也对 ⇒ 不改** ✓（改名的活**取消** ✓）

## ㊺ ⭐ `ref? T`：**可空引用**（主人 2026-09-20 提出："不能有空引用太难受了，但怎么才安全呢"）

### 先纠正一个前提：**null 本身不是不安全的原因** ✗

C 的问题不是"有 null"，而是**类型不说它能不能为空** ✗：
`T*` **永远可能**为空 ⇒ 你**不知道该在哪查**、编译器也**帮不上忙** ✓

⇒ 所以安全的答案不是"禁止 null" ✗，而是 **"让可空进类型"** ✓✓

### 方案：**两个引用类型**（`?` 是类型位置的修饰符，跟后缀 `?` 运算符不冲突 ✓）

| 类型 | 能不能为空 | 解引用 |
|---|---|---|
| **`ref T` / `mut ref T`** | **绝不**（保证不变 ✓）| **零检查** ✓✓（跟今天一样快 ✓）|
| **`ref? T` / `mut ref? T`** | **可能**（零值就是它 ✓）| **一次比较 + trap 带位置** ✓ |

```extc
struct node { val: i32  next: ref? node }      // ← C 风格的空结尾链表 ✓

var p: ref? node = head
while p != null {
    println(p.val)          // ⭐ p 在这里被**窄化**成 `ref node` ⇒ **零检查** ✓✓
    p = p.next              // next 也是 `ref? node` ✓
}
```

### 为什么它**安全**（三条）

| # | 保证 |
|---|---|
| **1** | **非空引用仍然零检查** ✓（`ref T` 的保证一点没丢 ✓ ⇒ 热路径不变慢 ✓）|
| **2** | **可空解引用 = 一次比较 + trap 带位置** ✓（不是 UB ✗ 不是静默错 ✗）|
| **3** | ⭐ **空值检查之后编译器"窄化"** ⇒ `if p != null { … }` 里面**检查被消掉** ✓✓（跟"能证明的不留痕迹"一致 ✓）|

### ⭐ 它跟语言其它部分**完全一致**（同一个套路）

| 不能证明的 | extC 的处理 |
|---|---|
| 下标越界 | **trap 带位置** ✓（能证明的编译期报 ✓）|
| 除零 / 移位超宽 | **trap 带位置** ✓ |
| **引用可能为空** | **同一个套路** ✓✓ ← 这就是第 4 次应用 ✓ |

### ⭐ 白送的一大红利：**零值**

`ref? T` **有零值**（就是 null ✓）⇒ 于是：
```extc
struct node { val: i32  next: ref? node }
var n: node                 // ✓ **合法**（`next` 零初始化成 null ✓）
```
⇒ **C 风格链表的关键**（今天的 `var n: node` 会因为 `next: ref node` 含 ref 而**被拒** ✗✓）

### 代价（诚实）

| | |
|---|---|
| **4 个引用类型** | `ref` / `ref?` / `mut ref` / `mut ref?`（比 2 个多 ✗ 但每个都一句话说得清 ✓）|
| 每次可空解引用一个检查 | 可被窄化消掉 ✓；不可消的也就是一条 `cmp` + 分支预测 ✓ |
| 要定细节 | `null` 关键字 · 窄化规则（`if p != null` / `p == null` ⇒ return/break）· 能不能 `p != null && *p > 0` ✓ |

### 备选（不加语法）

把 prelude 的 `option` 重写成**枚举**（第三刀 ✓）+ `match`（或 `while let` ✓）⇒
也**完全安全** ✓ 但**没有 C 味** ✗（`match` 套循环比较啰嗦 ✓）

⇒ **建议**：**`ref? T` + 窄化** = 主人的"爽" + 语言的"安全" ✓✓

## ✅ 落地记录：`?T` / `?ref T` / `null` / 非空收窄（2026-09-20）

上面那张表是**设计**，这里是**真的跑起来之后的样子**（语言是实现出来的，不是写出来的）：

| 写了什么 | 在哪 | 语义 |
|---|---|---|
| `?ref T` / `mut ?ref T` | `parser.c` 的 `parseType` | 类型上打 `nullable` 标记（**可空性是类型的一部分**，解析/替换/比较都不能丢）|
| `?T`（T 不是 ref）| 同上 | 直接造一个 `option<T>` 走正常解析路径 ⇒ check 一行都不用改 ✓ |
| `null` | `EX_NULL` | **上下文关键字**：类型只能由 `adoptContextType` 寄放（跟裸 `{}` 数组字面量同一个套路）|
| 收窄 | `Checker.narrow` | 记「在当前这个位置上哪些绑定已被证明非空」，**跟着 `pushScope`/`popScope` 自动回退** |
| 证明的五个入口 | `ST_IF`（then / else / 护栏）· `ST_WHILE` · `&&` 右边 · `\|\|` 右边 | 见 MANUAL §7.6 |
| 证明的**失效** | 赋值（`p = null` / 换指向）| 收窄是栈式的，`unNarrow` 砍到它为止 |
| 生成 C | `EX_NULL` ⇒ `((void *)0)` | **一行运行时检查都没有** ✓ |

**两个坑（都真踩了，记下来）**

1. **作废/收紧的时机必须在"查完右边"之后。** 两处：`unNarrow`（`cur = cur.next` 里右边的 `cur`
   还要用循环条件证明过的信息）和 `sym->refDepth` 的更新（先更新就等于**拿新深度比新深度**，
   `p = ref <更深的局部>` 会整条漏过去 —— 攻击库 `h1_retarget` 当场打出来）✓
2. **收窄只认绑定名 ✗ 路径。** `p.next.value` 过不去（要 `var nxt = p.next` 再证明）。
   这是**故意**的：路径收窄得处理别名失效（任何一次赋值/带 `mut ref` 的调用都可能改掉 `p.next`），
   而"绑一个名字"是显式、零开销、且不用想别名的写法 ✓

**顺带修好的精度问题**（`PLAN.md` §0.4 #8 的一半）：**引用型绑定的「被指对象深度」单独跟踪**
（`Sym.refDepth`）：

```extc
fn find(head: ?ref node, want: i64) -> ?ref node {
    var cur: ?ref node = head
    while cur != null { if cur.value == want { return cur }  cur = cur.next }
    return null
}
```

`cur` 的**槽位**在本帧（深度 1），但它指的节点在参数那边（深度 0）。
以前一律拿槽位深度 ⇒ 上面这个最正常的写法被误报成"返回会死的局部" ✗。
现在：默认值仍是槽位深度（保守 = 老行为），只在**声明**和**换指向**时按初始值的真实深度收紧 ✓
（攻击形状 `var cur = ref local; return cur`、`cur = ref local; return cur` 仍然全部报错 ✓）

## ✅ 定案 52′：第三刀 —— `option` / `result` 就是**普通枚举**（2026-09-20）

```extc
type option<T>    = | none | some(T)
type result<T, E> = | failure(E) | success(T)
```

**为什么不继续用 struct + `has`/`ok` 字段**（原来那样）：

| 问题 | 旧（struct） | 新（枚举） |
|---|---|---|
| **载荷里有 `ref`** | ✗ **不行** —— `none` 的 `value: T` 没东西可填，而「ref 不可为空」是硬承诺 ⇒ `option<slice<u8>>` 报 `__extc_reference_has_no_zero_value__`（错还落在 prelude 上）| ✅ 行 —— tag 0 = `none`，**载荷根本不存在** ⇒ IO / 解析器的基本形状成立了 |
| **`?` 怎么读** | 靠**约定的字段名**（`.ok` / `.value` / `.err`）—— 语言偷偷认识一个库的字段布局 | 靠 **tag + 载荷**，跟用户自己写的枚举走**同一条** codegen ✓ |
| **`match`** | ✗ 不能 match（它是个 struct）| ✅ 穷尽检查 ✓ |
| 零值 | `has = false` / `ok = false` | tag 0（**变体顺序有意义**：`none` 必须在第一个）✓ |

**代价（诚实记下来）**：`option` 上的 `valueOr` / `has` 这类**方法写不出来了** ——
方法只住在 struct 体内（定案 29），而枚举不能带方法。今天的写法是
**`match`，或者自己包一个按类型的小函数**（`examples/` 里到处都是）。
⇒ 记成 `PLAN.md` #16（枚举方法 / 泛型自由函数），**修哪一头都行**。

**顺带修的两个真 bug**（都是这次撞出来的）：

1. `match` 分支绑定：声明用原名、分支体用 cname ⇒ 同一层两个 `match` 绑同名时报
   `'s__2' undeclared`。修法：check 时把 `cname` 写回 `MatchArm.binds`（PLAN #2 ✓）
2. **`match` 的 codegen 不再用 `switch`**：分支体里的 `break` / `continue` 是要跳出
   **外面那个循环**的，而在 `switch` 里只会跳出 switch ⇒ `while true` + `break` 的
   读行循环**当场死循环**（写 `examples/option-ref-payload.extc` 时真踩了）✗
   改成 if/else 链（穷尽性仍由类型检查担保，不需要 `else`）✓

**验收**：152 测试全绿；`?` 的四个位置 + `option<slice<u8>>` 的传递都有例子 ✓

## ✅ 定案 53：`?` 是一族记号 —— `?` / `??` / `!`（2026-09-20）

第三刀把 `option`/`result` 变成枚举之后，`.valueOr` / `.has` / `.ok` / `.value` / `.err` 全没了。
当时的判断是"要给枚举加方法、或者做泛型自由函数才能把 `valueOr` 写回来"（PLAN #16）。
**主人一句话把它推翻了**：「其实语法糖感觉就能解决这个问题了」—— 对的：

| 记号 | 含义 | 生成什么 |
|---|---|---|
| `e?` | **可能没有 ⇒ 顺着往上抛**（原来就有）| 求值一次 + 判 tag + return |
| **`e ?? d`** | **可能没有 ⇒ 用兜底** | C 三元：`(e.tag == t_some ? e.u.some._0 : d)` |
| **`e!`** | **我签字**（定案 1.3）：直接给我 | `e.u.some._0` / 对 `?ref` **一个字都不生成** |

三个都是**编译器**提供的（跟 `?` 一样按名字认识 `option`/`result`），
比"给枚举加方法"小得多，而且**对所有 `T` 通用** ⇒ PLAN #16 划掉 ✓

**规则与理由**（不是实现细节，是语义）：

- `??` 的左边必须是 `option` / `result` / `?ref T` —— 别的东西"永远有值"，
  写 `n ?? 1`（`n: i64`）是**写错了**，报错 ✓
- `??` 的左边必须**没有副作用**（判据是保守的语法检查：树里出现调用就不许）。
  第一版生成 C 三元，主体在 C 里出现两次 ⇒ `f() ?? -1` 会让 `f()` 跑两遍 ✗
  ⇒ 报错并教他 `let r = f()` 然后 `r ?? ...` ✓
  **这条规则同时是"不需要前缀机制"的担保** —— 宁可多一行，也不偷偷改变调用次数 ✓
- `??` **只算一边**（有值时兜底那侧不求值）—— 跟 `&&` / `||` 同一个道理 ✓
- `!` 只对 `option` / `result` / `?ref T` 有意义（别的报错）；对**非空** `ref` 签字也报错 ✓
- `!` 是"**错了算我的**"，**不是**"宽松版检查"：真没有值 ⇒ UB。
  会报错的那种（trap）是**另一件事**，故意的：prelude 不给 `unwrap`，
  要 trap 就让调用者自己写 `match` + 他想要的失败处理 ✓
- 深度/借用分析：`p!` 跟着主体的被指深度走（签字只是换个说法，**来源没变**）；
  `a ?? b` 取两边里**较深**的、并且**任一边借来的就算借来的** ✓

### ✅ 定案 53′：**语句前缀**机制（2026-09-20，PLAN #19 做完）

主体是**调用**时（`println(f() ?? -1)`）也能写了 —— 编译器在**所在语句之前**吐一句：

```c
option_i64 __extc_c0 = f();
... (__extc_c0.tag == option_i64_some ? __extc_c0.u.some._0 : ((int64_t)(-1))) ...
```

⇒ **f() 只跑一次** ✓（"不许悄悄改变调用次数"这条承诺保住了）

- 主体本来就是变量/字段/下标（纯的）⇒ **不生成任何临时变量**，还是纯三元 ✓
- 谁判定要不要临时变量：**检查器**（它已经算过 `repeatablePure`）打一个 `needTemp` 标记，
  codegen 只管照做 —— 判定只写一遍，不会两边跑偏 ✓
- **吐不出来的两个位置，由检查器报错**（不是静默降级）：
  - **`while` 的条件** —— 前缀会吐在循环**外面** ⇒ 变成"进循环前算一次"而不是每轮算
    ⇒ **语义就错了**，所以必须挡住 ✓
  - ~~全局初始化式~~ —— **不属于这条规则**：全局初始化式本来就有一条更根本的规则
    ——「必须是常量」（C 的静态初始化，全局就是 C 的静态对象）⇒ `get()` 在那里
    本来就写不了，跟 `??` 无关。**报错要说第一层原因**（否则用户以为删掉 `??` 就能写）
    ⚠️ 这里踩过一次：一开始给全局也设了"不许吐前缀"，结果报的是 `??` 那条，
    把"必须是常量"这条真正的原因盖住了 ✗ 已改 ✓
- ⚠️ **代价（诚实记）**：临时变量吐在语句最前面 ⇒ `g() + (h() ?? 0)` 里 `h()` **先于**
  `g()` 求值（源码顺序是反的）。extC 跟 C 一样**不承诺**语句内求值顺序，所以不算毁约，

## ✅ 定案 54：泛型体的检查 —— **按实例复查**（2026-09-20，修 PLAN #17/#18）

**问题**：泛型体是照**模板**查一次的，那时 `T` 不透明。而所有"含引用才查"的规矩都要先问
"这个类型里有引用吗"，对不透明的 `T` 只能回答 **false** ⇒ **整片早退跳过** ✗

三个实测能拿 UB / 坏不变量的形状（都在 `tests/errors/` 里）：

```extc
struct boxT<T> {
    v: T
    fn stash(self: mut ref boxT<T>, value: T) { self.v = value }      // ① 借用/深度
    fn mk(self: ref boxT<T>) -> T { var local: T  return local }       // ② 零值
    fn pick(self: ref boxT<T>) -> T { var local: T = self.v  return local }  // ③ 返回本帧
}
var b: boxT<slice<u8>> = { v: "abc" }        // ① 悬垂  ② 一个 null 引用  ③ 悬垂
```

**为什么不能用 2 行的保守修法**（`TY_PARAM` 一律当"可能带引用"）：洞是关掉了，
但 **`box<T>::set` 这种教科书写法会被一起拒掉** —— 而它对 `T = i64` 完全安全。
"安全"不等于"把正常代码也拒掉" ✓

**修法**（跟 `==` 的 `eqChecks` 同一个模式，推广成三类）：

| 步骤 | 做什么 |
|---|---|
| 1 · 模板期 | 走路函数对"类型里提到 `T`"的节点**不再早退**，按"`T` 可能带引用"算 |
| 2 · 模板期 | 把这条规矩**记进 `refChecks`**（连**深度/借用**一起记好 —— 那时作用域还在），当下不下结论 |
| 3 · 实例化 | `vt = tsub(类型)`；**`typeContainsRef(vt)` 为假 ⇒ 这条规矩不适用**（`T = i64` 全跳过 ✓）；为真 ⇒ 用记好的数字报错，消息**点名实例**（`boxT_slice_u8`）✓ |

**⚠️ 走过的弯路（记下来，下次别再踩）**：第一版把"算深度"也推到实例化再做 ——
那时**函数作用域已经没了**（`lookup` 找不到参数）⇒ 深度算成 0 ⇒ 检查**静默失灵** ✗
表现是攻击代码照样编过，而且**不报任何错**（最坑的那种失败）。
⇒ 教训：**推迟的只能是"结论"，不能是"上下文"** ✓

**验收**：三个攻击形状全部报错；`box<i64>::set` / `examples/generics.extc` 照旧通过；
`/tmp/hack` 27 个攻击文件通过集合与改动前**完全一致**（一条都没放松）✓

## ✅ 定案 55：arena **按块细化**（2026-09-20，PLAN A2）—— 主人：「这是地基吧」

**起因**：主人指出"先按块细化比先做 `new` 更对，这是地基"。实测支持他：

```extc
while n < 300 { var p = alloc<i32>(250000)  *p = n  n = n + 1 }   // 300 × 1MB
```
- `ulimit -v 150000` 下**现在就崩**：`extc: out of arena memory`（每帧 arena 会累积到返回）✗
- 按块细化之后同样代码同样上限 ⇒ 跑得完（上界 = 一次迭代）✓

**生成的东西**：

```c
extc_arena __extc_a[DEPTH] = {0};      // 栈上定长；层数 = 编译期算好的最大块深度
进块: extc_arena_release(&__extc_a[k]);
出块: extc_arena_release(&__extc_a[k]);
```
释放点 = 每个控制流出口：块出口 · `break`/`continue`（放到**循环体那一层**）·
`return` 与 `?` 的失败返回（放到第 1 层，函数体就是第 1 层）✓

## ⭐ 这件事里最值得记住的一条：**接缝**

> **检查器判引用用的"块深度"和生成的 C 选 `__extc_a[k]` 用的"块深度"，
> 必须是同一个数。**

所以 `alloc<T>(n)` 的引用深度从写死的 **1** 改成 **当前块深度**（`c->scopes.len`）。
不改的话：`while { p = alloc<i32>(1) }` 里 `p`（声明在循环外）会在下一轮指向
**已经释放**的内存 ⇒ **悬垂** ✗（"深度低估"被 arena 细化直接放大成 UB）

⇒ 这也回答了"为什么每作用域是对的"：**它不是新增一条安全义务，而是把检查器
已经证明的性质（引用深度 ≥ 存放处深度）兑现成回收行动** ✓ 深度模型和 arena
粒度天生就该是同一个数。

**验收**：`tests/arena/`（150MB 上限下循环里 300×1MB 跑完；含 break / continue /
嵌套块 / 循环里 early return 四种出口）+ 两个新反例（`alloc` 逃出块、返回刚分配的内存）
+ `/tmp/hack` 攻击库通过集合与改动前完全一致 ✓ **168 测试全绿**。

## ✅ 定案 56：`new` —— 分配进**当前块**、**永远是零**（2026-09-20，PLAN A1）

```extc
var n: mut ref node     = new node        // 一个 T 的地方
var a: mut ref [3]i32   = new [3]i32      // 定长数组的地方
var buf: mut slice<i32> = new i32[1000]   // n 个元素 ⇒ `mut slice<T>`（**buffer**）✓
```

**三件事一句话说清**（没有例外，没有开关）：

| | |
|---|---|
| **清零** | 运行时那条分配原语自己 `memset(p, 0, n)` ⇒ **"分配出来的一定是零"** —— extC 只有**一条**规则，没有 C 的 `malloc`/`calloc` 两条路的陷阱 ✓（跟定案 8 同源）|
| **活到当前块** | arena 按块细化（定案 55）⇒ 循环里 `new` 不涨内存 ✓ |
| **深度 = 当前块深度** | 跟"选哪只 arena"**是同一个数**（A2 那条接缝）⇒ 引用逃不出它所在的块 ✓ |

**为什么是原语而不是库函数**：arena 必须由编译器生成（库要用它分配自己 ⇒ 不能由库提供）✓

**暂不支持的**（记着）：
- `fn make() -> mut ref node { return new node }` ⇒ **编译错误**（活不过当前块）——
  那是 **A3 逃逸提升**的活 ✓ 今天跨函数就传 buffer/`mut ref`（`IO.md` 就是这么设计的）✓
- `new T`（模板里的类型参数）⇒ 大小不知道 ⇒ 报错 ✓（`varArray<T>` 会撞这条，见下）

⚠️ 顺手修的真 bug：`new` 后面原来写了个 `skipNl`，把**语句结尾的换行**吃掉了 ⇒
下一行整条被并进同一个表达式 ✗ extC 靠换行断语句 ⇒ 那里**不许 skipNl** ✓

## ✅ 定案 57：逃逸提升（A3 第一半）—— 分配**交给调用者**（2026-09-20）

**要解决的事**：`fn build() -> mut ref node { ... new node ... }` 以前是**编译错误**
（`new` 活到当前块结束 ⇒ 返回就悬垂）。可是"在函数里把东西建好、交给调用者"
正是链表/树/AST 的**基本形状** ✓

**规则**（一条，好记）：

> **函数体里有分配，且返回类型含引用/视图 ⇒ 这个函数多收一只隐藏参数
> `extc_arena *__extc_home`，它的 `new` 分配到调用者选的那只 arena。**

- 调用点自己选：**自己有家 ⇒ 传自己的家**（祖先那只，最稳）；
  **自己没有家 ⇒ 传当前块那只**（更紧 ✓）
- `needsHome` 要**传递闭包**（调用它的人得有东西可传）⇒ 到不动点为止 ✓
- `main` 的签名是 C 定死的 ⇒ 它自己定义 `extc_arena *__extc_home = &__extc_a[1];` ✓
- 检查器那边：有家的函数里 `new` 的深度按 **0** 算（= "活到调用者选的那个作用域"，
  正好是逃逸检查里"可以带出去"那一档）⇒ `var head = new node … return head` 成立 ✓

⭐ **必须保住的性质**：**返回 `i32` 的函数不要家** ⇒ 它循环里的 `new`/`alloc`
仍然分配到**块 arena** ⇒ **A2 的"循环不涨内存"一条不丢** ✓（`tests/arena/` 照旧通过）

⚠️ **还没做（A3 第二半）**：**出参** —— `fn fill(d: mut ref ?ref node) { *d = new node }`。
那要求把"家"从**函数级**细化到**按调用点/按 `mut ref` 实参**选 arena
（`ARENA.md` §1.2 那条"分配进最浅的 `mut ref` 实参的 arena"）。

**验收**：`examples/escape-promotion.extc`（函数里建链表并返回，两次调用各一条链）；
原来那个"必须报错"的反例 `new_return_escapes` **删掉** —— 它现在是正例 ✓ 172 测试全绿。

## ✅ 定案 58：规则 ④ + callee 放宽 —— **链表出参能写了**（2026-09-20，A3 第三半）

**要解决的事**：`fn push(l: mut ref list, v: i64) { … cell.next = l.head … }` 被
"借来的值不许存进活得更久的地方"挡住 ✗ 而按 `ARENA.md` §7，这个形状**本来就是安全的**：

> `cell` 进的家 arena = **拥有 `l` 的那只**（A3 第二半）；`l.head` 指向的东西
> 也只能在同一根链上（**链式只读**堵死了别的路），而且每次往 `l.head` 存东西
> 都按"目标深度 = 字段所在对象的深度"验过 ⇒ 它活得 ≥ 家 arena ⇒ 存进去安全 ✓

⇒ 那条老规则**比模型保守**。补法是把它的**前提**补上（两件事必须一起做）：

| # | 做什么 | 对应 ARENA.md |
|---|---|---|
| **① 规则 ④** | 调用点：传给 `ref`/`mut ref` 的实参，它指的东西必须**活得 ≥ 这一刀的家 arena**（`referentDepth ≤ h`）| §7 归纳的**前提**（"外面弄不进来东西"）|
| **② callee 放宽** | 有家函数里，"参数来的引用"可以存进深度 0 | §7 那句"分配的东西比所有可写目标都长寿 ⇒ 写进哪都安全"✓ |

报错样例：

```
error: argument 2 of `stash` points into a deeper scope (depth 2)
       than the arena this call may store it in (depth 1)
```

⚠️ **② 单独做是洞**（实测：`fn bind(s: mut ref slot, target: mut ref i32) { s.r = target }`
会被放行 ✗，而调用点可以传更深的局部进来）—— 这条洞被现有反例 `ref_launder_field`
当场抓住 ⇒ **①②必须一起** ✓

⚠️ **放宽只对"会分配的 callee"生效**（它才有家 arena）⇒ `ref_launder_field` 那种

## ✅ 定案 59：扩容因子 = **倍增**（2026-09-21，主人问「倍增是对的吗」）

**问题**：`varArray<T>` 满了 ×2 扩容 —— 这是最优的吗？

### 一、网上怎么说（注意：他们的模型都有 `free`）

| 出处 | 结论 | 前提 |
|---|---|---|
| CLRS §17.4 / 各校讲义 | 任意因子 `1+α > 1` 都是 **O(1) 摊还**；代价是空间：最坏浪费 `α/(1+α)` 的已分配内存，摊还拷贝 `O((1+α)/α)` ⇒ **不存在无条件的"最优"**，只有一条时间-空间权衡曲线 | 旧块**被释放** |
| Folly / `FBVector` 文档 | 因子 2 **"rigorously the worst possible"**：`1+2+4+…+2ⁿ = 2ⁿ⁺¹−1` ⇒ 新块永远比之前所有块之和还大 ⇒ **永远回不到已释放的地方**；1.5 在 4 次重分配后可复用，φ≈1.618 是那条界 | 分配器能**复用** |
| Tarjan & Zwick, *Optimal Resizable Arrays*（SOSA 2023 / SICOMP 2024）| 几何倍增**不是空间最优**：`N + O(N^{1/r})` 常驻 + `N + O(N^{1−1/r})` 临时峰值、摊还 `O(r)`；用 growth game 给出 `Ω(r)` 下界 ⇒ 那才是该方向的最优 | 依赖**释放 / 搬块** |

⇒ 理论上的"最优"是 Tarjan–Zwick 那套分块/分层方案，但它的记账**建立在能回收上**；
"倍增最差"是对**能复用内存的分配器**说的 ✓

### 二、我们的模型不一样：arena 没有 `free`

extC = 栈 + arena + 静态。扩容时旧 buffer **一直占着**（直到所在块退出）⇒
Folly 那条"能不能复用"的论证**方向反了**。正确的指标是：

> `R = max ( 累计分配的元素数 / 数组当前长度 )`

**结论（`examples/growth-factor.extc` 自己算的，不是抄的）**：

1. **几何因子** r 的最坏比值 = `r + r/(r−1) = r²/(r−1)` ⇒ 最小值在 **r = 2**，值为 **4**
   （1.5 ⇒ 4.5；1.25 ⇒ 6.25；1.618 ⇒ 4.236；3 ⇒ 4.5；4 ⇒ 5.33）
2. **精确 DP**（状态 = 容量 v 时的最小累计 S；对**所有**递增容量序列，不只几何序列）：
   `R < 4` 只能"撑到某个有限 N 就爆" —— 视野 N = 100 / 300 / 1000 / 3000 的最小 R
   分别是 **3.815 / 3.875 / 3.903 / 3.934** ⇒ **渐近下确界正好是 4**，
   而打到 4 的方式就是**倍增** ✓
3. 实测（n = 100000 个元素）：倍增累计 2.62n · ×1.5 是 3.03n · ×1.25 是 5.88n ✓
   （跟 Rust `Vec` 一致：`cap = max(cap*2, needed)`，最小 4/8）

⇒ **定案：`varArray<T>` 保持倍增** ✓（这条现在有据可查，不再是"大家都这么写"）

### 三、但同一个模型下，**分块（chunked）严格更好** —— 留给 v2

永不 realloc、每次只追加一块 `c` 个元素：
累计分配 = `⌈n/c⌉·c ≤ n + c`（chunk = 256 时 **1.001n**，chunk = 4096 时 1.024n），
零拷贝，而且顺手解决 MANUAL §7.9 那条**"扩容让元素引用失效"**（块永不搬）✓

代价：存取多一次间接寻址；**不再连续** ⇒ `slice<T>` 给不出来了。
⇒ 记在 **PLAN #29**，等 `varArray` v2（`insertAt`/`eraseAt`）时一起拍板 ✓

### 四、被排除的第三类：**运行时自适应**（记为 PLAN #30）

主人问的是"非运行时策略"，那么对立面就是"运行时策略"，这一侧也确实存在、而且理论上更省：

- **`realloc` 式**（libc `realloc` / Go `growslice`）：先问分配器能不能**原地扩**，
  不行才搬 —— 摊还拷贝量最坏仍是 O(n)，但常见情形（数组是最后分配的东西）**一次拷贝都不做** ✓
- **我们的 arena 恰好能给出更便宜的版本**：arena 是 **bump 分配器**
  （`codegen.c` 里 `extc_ablock { prev, cap, used, data }`，块 4096 起）⇒
  只要"这次分配是当前块的**最后一次分配**"，原地扩就是 `used` 往后推一格：
  **零拷贝、零查询**（一次指针比较）。要补的只有两件事：
  ① arena 记住"最后一次分配的指针 + 大小"；② 块留出 slack（现在 `cap = n` 时没有余量，
  小对象能蹭 4096 的残余）✓

⚠️ 但它跟我们现在的两条承诺有牵扯：原地扩**成功时**元素引用还稳，**失败搬走时**就失效 ⇒
"引用失效"从"必然"变成"看运气"（更难讲清楚）✗ 而且它是**运行时代码**（虽然语义不可见，
不违反 P，但按 P′ 的精神应该让用户知道）。
⇒ 所以**现在不选**：先保住"零运行时痕迹 + 讲得清楚"；chunked（上面 §三）能满足同样目标
而且**永远不失效**，优先级更高 ✓

## ✅ 定案 61：修 PLAN #31 用 **甲′**（"把事实写回容器深度"，而不是改家 arena）（2026-09-21）

**背景**：`varArray` 扩容后返回容器 / 往本地容器 push 造链表再返回 —— 两个形状都是
**静默 UB**（ASan 实锤 use-after-free）。主人先拍板"丙（owner depth）"，但追查发现
**丙的 E2（`v ∈ E ⇒ 传我的家`）不 sound**：家一旦变成"调用者的家"，被调者就能把
**接收者 / 本地实参的地址**存进活得比调用者帧还久的家内存 —— 而 `ARENA.md` §7 的证明
**正是靠"家 = 最浅可写目标的 arena"**才成立 ⇒ 那是换个洞 ✗（`ARENA.md` §9 有推导）

**定案 = 甲′**（保守拒绝，但**只针对"被调者往里塞过东西的容器"**）：

> 带 `mut ref` 实参、**且被调者会分配**的调用 ⇒ 把**实参那个绑定的有效深度**
> 抬到 ≥ 这一刀的**家深度**（`Sym.refDepth = max(refDepth, homeDepth)`）
> ⇒ 之后任何"让它逃出去"（`return l`、`return v.asSlice()`、塞进更浅的 struct）都被
> **现成的**逃逸检查挡住 ✓

**为什么它是这个语言的正确形状**（而不是"无奈的保守"）：

1. 它是 **P′**：证明不了安全的写法**响亮地报错**，而且报错**指路**
   （"在调用者作用域里建 + `mut ref` 传下去填"，或"用 `new` 直接建 = 逃逸提升"）✓

## 定案 63 · **块级逃逸提升**：`new` 存到更外层 ⇒ **提升 arena**，不拒绝（2026-09-22，主人拍板）

**背景（PLAN #38，真 UB）**：
```extc
var head: ?ref node = null
while cond {
    var n = new node
    n.next = head
    head = n          // ← n 住在循环体那块 arena，块尾就 release ⇒ 悬垂 ✗
}
```
实测 ASan **heap-use-after-free** ✗（不需要循环，普通嵌套块同样中招）。
根因："存进活得更久的地方"这条规则现在只对**借来的值**（参数派生 / 调用结果）生效，
而 `new` 既不是参数派生也不是调用结果 ⇒ 整条规则被跳过 ✗（PLAN #31 是同族的另一半）

**主人拍板**：
> 「感觉没啥问题，反正最终最多就一直退化成一个会自动清理的类似堆的东西，没必要拒绝」

⇒ **不要保守拒绝，一律走提升** ✓ 两条理由都成立：
1. 这个形状是**正常写法**（循环里建链表），拒绝等于把最常用的东西堵死 ✗
2. 最坏情况只是"这次 `new` 活到所在层块结束"—— 那**就是一个自动清理的堆**，
   安全性一点没丢（它本来就在 arena 里、出块一起放掉）✓

**做法**：`new` 用的 arena 从"当前块"改成 **"所有目的地里最浅的那层"**
```
arenaLevel(new) = min( 当前块深度, min over 所有目的地 place 的深度 )
```
- 只往更深处存 ⇒ 取当前块 ⇒ **行为完全不变**（零影响、零假阳性）✓
- 往更浅处存（`head` 在函数体那层）⇒ 提升到**函数体那只 arena**，它当然还活着 ✓
- **返回值**那道出口已经有 `needsHome`（家 arena）在做同一件事 ⇒ 这是把它**下沉一层** ✓
- 这正是 `ARENA-FORMAL` §7 那档「**把 region 拉长**」（而不是"把事实变细"）——
  所以它**不引入误拒** ✓

**落点（四步）**：
1. `Expr` 加 `arenaLevel`（只 `EX_NEW` 用）
2. checker 在 **赋值 / 结构体字面量字段 / `return` / 实参** 四条"值流向某处"的边上，
   把目的地的深度**回填**给值里所有 `EX_NEW`（取 **min**；同一棵树被多处用 ⇒ min 保守且正确）
3. codegen 的 `arenaRef`：`hasHome` 优先（不变），否则用 `e->arenaLevel` 而不是 `blkLevel`
4. 形状清单全覆盖 + 双向判据：ASan 干净 · 攻击库 BASELINE **一字不动** ·
   224 测试 · golden 差异只允许"arena 层级变了"这一类 ✓

### 63 · 落地记录（2026-09-22 完成 ✓）

**做出来的东西**（`src/` 六处）：`Expr.arenaLevel`（①）· `check_expr.c` 定初值 ·
`promoteInto`（`check_escape.c`，②③）· 三条边接上（`check_stmt.c` ×2 + `check_top.c` 规则④）·
`codegen.c` 的 `arenaRefAt` ✓ 判据：**227 测试全通 · 攻击库基线一字不动 ·
`tests/asan/` 5 个形状 ASan 干净 · golden 只多一个新例子（其余 81 个逐字节不变）** ✓

**① 提升顺着"值的来路"往回走**（`Sym.origin`）：绑定 / `!` / `??` / 结构体字面量 /
枚举载荷 / 数组字面量。**提不动的照旧报错** ⇒ 这个函数只可能把"本来就该放行"的东西
放过去（该不该放行由原来那条深度检查兜着）⇒ 方向天然安全 ✓

**② 三个必须记住的坑**（每个都有实证）：

| 坑 | 现象 | 结论 |
|---|---|---|
| **`placeDepth` 答错了问题** | `head = n` 的目的地深度算出来是 **0**（`head` 是引用型、初值 `null` ⇒ 它报的是"**指着的地方**在哪"）⇒ 提升永远够不着 ✗ | "**往哪一层存**"是另一个问题 ⇒ 新增 **`storeLayer`**（定案 ㊲ 那张表欠了两轮的那一半）✓ |

| **来路链会断** | 双层循环里 `var cell = new node … mid = cell`，然后**外面的** `head = mid`：查到时 `cell` 早已出作用域 ⇒ `lookup` 找不到 ⇒ 链断 ✗ | 记来路时**压平成根**（`noteOrigin`）+ 跳数上限（绑定之间可能成环：`a = b  b = a`）✓ |

**③ `storeLayer` 顺手补齐了定案 ㊲ 的另一半**：

| 目标 | 存储住在哪 | 深度 |
|---|---|---|

| **参数本身的槽位**（`a = b`：参数是**副本**，写它调用者的指针一个字不动）| 本帧 | **1** ✓（㊲ 的表）|
| **全局** | 静态 | 0 ✓ |
| **透过引用/参数投影**（`b.r` / `a[i]` / `*p`）| **调用者的对象里** | 0 ✓（那条攻击照旧被挡）|

**④ 提升的代价**（主人已认可）：被提升的分配**不再每轮回收**，
最坏 = 一个**函数级、自动清理的堆**。⚠️ 它**不等于**"循环里不涨内存"那条保证丢了：
**没被存出去的东西照样按块回收** —— `tests/arena/promote.extc` 同时验这两件事

照旧被挡）——它是原语，行为先保持原样 ✓；`return` 那条边不用新代码

## 定案 65 · **`@overwrite`**：复用一块存储（把"上一轮那个我不要了"写进源码）（2026-09-22，主人拍板）

### 一、起因：一个**本质是泄漏**的形状（主人提的）

```extc
fn stash(dest: mut ref slot_t, v: i64) { var n = new node  n.value = v  dest.v = n }
var slot: slot_t = { v: null }
while i < N { stash(ref slot, i)  i = i + 1 }     // ✗ 每轮的节点都攒着
```
实测（N = 1e7）：**RSS 159.7MB**（= 1e7 × 16B，一份没回收）✗ 而"C 里 `malloc` 忘了 `free`"是 314MB、
"复用同一个节点"是 **1.7MB** ✓ ⇒ 对用户来说这就是**内存泄漏** ✓

**根因不是分析不够精**（这点很重要）：槽位声明在函数体那层 ⇒ **它的存储活到函数结束** ⇒
"引用"的含义就要求被指对象也活那么久 ✓。要做到"每轮回收"，必须能判断**旧对象已经不可达** —— 
那是 GC（`PLAN §5 永远不做`）或 `free`（P″ 明确不做）✗ ⇒ **任何 sound 的静态分析都推不出更小的区域** ✗
（别名分析也不行：这里没有歧义；区域推断也不行：约束就是"活得 ≥ 槽位"）

⇒ 唯一的路：**让用户把意图写出来**，编译器照办 ✓ —— 显式是对的，但要**好写** ✓

### 二、决定：一个修饰符 `@overwrite`（主人提的形状）

```extc
while i < N {
    @overwrite var n = new node      /* ← 跟原来的写法**只差一个修饰符** ✓ */
    n.value = i
    slot.v = n
    i = i + 1
}
```
**语义一句话**：「**存储只有一块：在本函数帧那层分配一次、每次执行到这句就清零复用**」✓
对照着记：**`new T` = 拿一块 + 清零；`@overwrite new T` = 拿一块（第一次）**，之后每次**只清零** ✓

**为什么用它**（三点，都踩过）：
1. **就地可读**：读 `new` 那一行就知道"这块是复用的"，不用往上翻找循环外的声明 ✓
2. **教学成本为零**：用户从 GC 语言搬过来的写法**形状不变** ⇒ 编译器那条警告可以**直接指路**
   （"想复用就写 `@overwrite`"）✓ 而"自己把声明搬到循环外"是要用户先懂区域模型 ✗
3. **顺手铺路**：`@main` / `@recursive` 早就定案但没实现（`@` 在词法里都还没有 ✗）⇒ 这套注解机制反正要写 ✓

**命名理由**：它命名的不是机制，而是**用户保证的那件事** —— "上一轮那个我不要了" ✓
（这是最容易踩错的一点：留着旧指针的人会看到"历史里每一项都指向同一块"✗ ⇒ 名字得提醒他 ✓）

### 三、展开规则（编译器做的事，零新运行时）

```extc
@overwrite var n = new node
```
⇒ 展开成（人也可以自己这么写 ✓）：
```extc
/* 函数序言：每站点一个格子（**递归各激活一份** —— 是普通局部，不是 static ✓）*/
node *__extc_ow0 = null
while … {
    if __extc_ow0 == null { __extc_ow0 = new node }   /* ⭐ **懒分配**：循环 0 次就不分配 ✓ */
    else                  { *__extc_ow0 = node 的零值 }  /* 清零复用 ✓ */
    var n: mut ref node = __extc_ow0
    …
}
```
生成 C 就是 `extc_arena_alloc` + `memset` 几行内联代码 ⇒ **零新运行时、零元数据** ✓

### 四、三档（**存储一律走 arena，不进栈**）

| 语法 | 存储 | 分配次数 | 内存上界 |
|---|---|---|---|
| `@overwrite var n = new T` | 一块 | **1** | 常量 ✓ |
| `@overwrite var b = new [N]T`（编译期定长）| 一块 | **1** | 常量 ✓（**缓冲多大都不占栈** ✓）|
| `@overwrite var b = new T[k]`（运行时长度）| `{ptr, cap}` | 只在"比见过的都大"时**翻倍**重来 | **≤ 2 × 见过的最大长度** ✓（**与迭代数无关** ✓）|

⚠️ **为什么定长也不上栈**（主人 2026-09-22 提醒）：默认栈只有 8MB（实测 `ulimit -s` = 8192 ✓，
语料里 12MB 局部数组就 segfault 过 ✗）· 递归会**乘上深度** ✗ · 阈值是魔法数字 ✗ ——
而 arena 那条路**语义一模一样**（寿命都是函数帧）成本只差一块内存 ✓ ⇒ **一条规则更省心** ✓
（将来若要"小定长上栈"，**先测量再决定** ✓）

⚠️ **为什么翻倍**：长度逐轮变大时"每次按 k 精确分配"是 `Σk ≈ O(N²)` ✗；翻倍是几何和 ✓
——跟 `varArray` 扩容的**定案 59 同源** ✓

### 五、只能解决什么（诚实划界，别含糊）

| ✗ 不解决 | 为什么 |
|---|---|
| **要保留历史**（链表 / `varArray` / 环形缓冲第 N 个）| 那些对象**本来就该活着** ✓ 不是浪费（要上限就 slab + 索引 ✓）|
| **"每轮一个全新对象、旧的别人还指着"** | 真需求 ⇒ 就该有 N 份 ✓ |
| **只有 GC 能救的**（"随便丢掉任意不可达对象"）| 明确不做 ✗ |
| **每轮长度任意 + 要"还回去"** | arena 没 `free`，但**不需要**：`k ≤ cap` 就直接用前 k 个 ✓ |
| ⭐ **"每轮新分配 + 只留最后一个"**（`let n = new node  p = n` 那种）⇒ 内存线性涨 ✗ | **不加警告、不修** —— 主人 2026-09-22 拍板：「这么写代码的这辈子有了」✓ 判据其实**存在**（那个槽位被反复覆盖、而旧值在覆盖前**从没被读过** ⇒ 必是纯垃圾 ✓ 能跟正当的建链形状区分开），但**收益不抵复杂度**：它只是"内存多花了"，不是 UB、不是悬垂，而且用户有 `@overwrite` 这把正路了 ✓ ⇒ 按"**只解决常见情况**"的原则，这个不解决 ✓（真要加，位置就在这条）|

### 五′ · 为什么是"语法 + 响亮报错"而不是"更聪明的分析"（2026-09-22 主人提的 Rice 定理）

主人：「根据莱斯定理你无法在编译期证明全部东西」⇒ 这正是 extC 的取舍：

- **Rice 定理**：任意非平凡语义性质在一般程序上**不可判定** ⇒ 不存在"又 sound 又完备"的分析；
  编译器只能选**漏报**（unsound ✗ 危险）或**误报**（sound 但更保守 ✗ 烦人）✓
- extC 的选择：**sound + 不完备 + 便宜 + 局部**（深度模型就是这样的抽象：能判定的那一小块 ✓），
  判不了的地方**不猜** —— 而是要求**写在源码里**（`@overwrite` / `ref` / `mut ref` / `!`）+ **响亮报错** ✓
- 换句话说：`@overwrite` 不是"编译器猜出了复用"，而是**用户把意图写出来、编译器照办** ✓
  —— 这条比任何分析都稳（Rice 管不着"用户已经说了"的情况 ✓）

### 六、报错清单（P′：该响亮就响亮）

| 写法 | 结果 |
|---|---|
| `@overwrite var x = 5` / `= f()` / `= 某局部` | ❌ **编译错误** —— **`@overwrite` 修饰的是"分配"**，右边必须是 `new`（主人的要求 ✓）|
| `@overwrite let x = new T` | ❌ 错误：复用存储必须写 `var`（每次执行都要重新绑定 + 通常还要往里写）|

## 定案 68 · **层号的唯一权威：检查器算完，codegen 只翻译**（2026-09-22，主人拍板）

**为什么要统一（原来的病）**：同一件事**两个地方各算一遍** ✗

### ✅ 2026-09-23 落地：per-module 名字 mangle（`pair` → `liba$pair`）

> 上一条记的是我**第一次尝试失败**的过程。判据写对了（"别比名字，比 `Type*`"）——
> 这次就是顺着它查出来的：根因根本不是"两份 `Type` 节点"，而是
> **`tt->aliases` 这个 `Vec` 的 `elemSize` 写成了 `sizeof(void*)`**（`Alias` 是 16 字节）
> ⇒ 两个条目在缓冲里**交错** ⇒ 别名表打出 `pair=>make` ⇒ 裸名查不到 ✗
> **教训**：症状（`unknown type pair`）跟根因（vec 元素宽度写错）之间没有任何线索，
> 唯一有效的办法是**在"写表处"和"读表处"各打一次**，一眼就能看断在哪一段 ✓

**形状**：每条顶层声明改写成模块内唯一的内部名，`$` 在 C 里合法、在 extC 标识符里
**不合法** ⇒ 天然不撞用户名字，也不需要在 parser 里加保留字 ✓

| 位置 | 改什么 |
|---|---|
| 声明 | `struct pair` → `liba$pair`、`fn make` → `liba$make`、顶层 `let`/`type` 同理 ✓ |
| 跨模块引用 | 装载器把 `liba::pair` / `liba::make(…)` 解析成那个内部名 ✓ |
| 模块**内部**的裸名 | 也必须改（`fn make() -> pair`、`fn a(){ b() }`、`color.green`）✗ |
| `extern!` | **一律不改** —— 那是 ABI（见下）✓ |
| 报错回显 | 打印**源码里写的那个名字**（`Expr.u.ident.srcName` 存着 ✓）|

**六条必须记住的不变式**（每条都是踩出来的，细节见 DEVLOG 同日条目）：

1. **`extern!` 的名字就是链接器要找的符号** ⇒ 加前缀只会得到
   `undefined reference to sys$read`，而报错来自 `ld`，跟"模块改名"八竿子打不着 ✗
2. **表达式自己的名字要改，不能只走子节点** ✗ —— `EX_STRUCTLIT` 的 `inits` 走了、
   它自己的类型名没走 ⇒ 检查器按裸名 `ttFromName` ⇒ **静默绑成先注册的那个模块的类型**
   （两个类型同名时**编得过、类型是错的** —— 比报错坏得多 ✗）
3. **只认"本模块自己声明的名字"**，不认"任何模块导出过的名字"：
   认了的话，同一个名字在别的模块里也有时，本模块的裸写会被**悄悄改写过去** ✗
4. **parser 里加限定名语法必须"先看不动"**：`pcg32::withStream(…)` 是绝大多数情况，
   把它的记号吃掉再指望后面的兜底，会直接把它拆烂 ✗（prelude 当场编不过）
5. **裸名有歧义时必须报错，绝不能挑一个** ✗ —— 两个模块都导出 `pair` 时，
   `var p: pair = …` 若"挑第一个匹配"，就会**静默绑成先注册的那个模块的类型**
   （编得过、类型是错的，违反 P′「不能证明的，语法上必须看得见」✗✗）
   ⇒ 别名表**不去重**（同名同名两条都登记），`ttResolve` 数出 ≥2 个匹配就报
   `ambiguous type \`pair\` -- 2 modules export it, write \`module::pair\`` ✓
   （代价：一个模块被 `use` 两次会登记两条一模一样的别名 —— 已按 `(from,to)` 对去重 ✓）
6. **内部名与显示名必须分家** ✗ —— `name` 是 `io$reader`（C 里要唯一），
   `srcName` 是 `io::reader`（用户写的那个词）。诊断、`typeStr`、调试开关
   一律走 `DN(x)` / `FN(f)`，codegen 一律走 `name`。
   把 `alpha$pair` 印给用户，等于把编译器的内部编码漏出去 —— 用户从没写过那个词 ✗
   （踩过：`struct \`alpha$pair\` has no field \`zzz\``）
   **唯一的例外是 `EXTC_DBG_M`** —— 它的用途就是展示"谁被改名成了什么" ✓

**验收（全绿 ✓）**：`tests/modules/run.sh` 里有一条**自动判据** ——

## 定案 74 · **`reader`：隐式 64KB 块缓冲 + 切片解析函数族 + 三条路分得开**（2026-09-23）

> 主人：「**修IO然后把1-4都先做了，反正现在能读了之后会好办很多**」
> 这是 `IO.md` §8 那三档里的 **IO-0 主体**（`reader` + `nextInt` 一族）✓

### 1. 为什么有 `reader`（"一定要快"那一条）

原 `readLine` 是**逐字节**读的（每读一个字节进一次内核）。实测（12MB / 100 万行，`-O2`，都读满）：

| 读法 | 时间 | syscall |
|---|---|---|
| 逐字节 | **1.444 s** | 1200 万 |
| 一次 64KB | **0.032 s** | ~183 |

⇒ **45×**，而且差距**全在 `sys` 时间**（1.060s → 0.008s）✓
（主人早先测的是 19MB/50 万行 2.30s vs 0.012s = **190×** —— 同一件事，规模不同 ✓）

⇒ 所以 `reader` 是"一次 `read(2)` 拿回一整块、然后在内存里切" ✓
**块大小 64KB**：实测 64B/469MB/s · 4KB/5820 · **16KB 与 64KB 都 7275MB/s** · 1MB 反而 0.05s
⇒ 16KB 以上就平了，取 64KB ✓（`IO.md` §9 原来写的 4KB 改成 64KB ✓）

### 2. 块缓冲**隐式给**，行缓冲**调用者给**（这条曾经自相矛盾 ✗）

`IO.md` 里 §4.3 写"调用者给块缓冲"、§9 写"`readerOf` 不用给" ⇒ **打架** ✗
现在统一成 **§9 那条**：

| 缓冲 | 谁给 | 为什么 |
|---|---|---|
| **块**（64KB） | **`readerOf` 自己给**（`new u8[BLK]`） | 它是**实现细节**（一次读多大），不是用户该操心的 ✓ |
| **行**（`out`） | **调用者给** | 那是**数据归属** —— 拷进你的 buffer ⇒ 你手上的 `line` 一直是你的 ✓ |

⚠️ "隐式给块"**能成立**靠的是 arena：那 64KB 是 `new` 出来的，落进**调用点**的 arena
（"有家被调者"那条路）⇒ 跟 `reader` 自己**同寿** ✓
⇒ 代价：`reader` 不能比创建它的块活得久 —— 而这条**由逃逸检查管着**
（越界是**编译错误**，不是悬垂 ✓。当天刚修的 `#52` 正是这条规则的实例 ✓）

### 3. 三条路必须分得开（P′）

| 情况 | 返回 |
|---|---|
| 读到 **EOF** | `success(0)` —— **这不是错误** ✓ |
| 行比 `out` **长** | `failure(lineTooLong(n))` —— 数据没读全 ✗ |
| `read(2)` **出错** | `failure(readFailed(fd))` —— 上次读的可能已经坏了 ✗ |

⚠️ 原 `readLine` 把后两条**都当成 EOF**（`if got <= 0 { return n }`）：
读错误看起来就是"文件结束了"，而**超长行会被静默切成两"行"** ✗✗
那种"看不出来的数据损坏"正是 P′ 要挡的东西 ✓
⇒ 现在两条都有常设反例（`tests/io/line-too-long.extc` / `read-failed.extc`）✓

### 4. `nextInt` 的两个坑（都踩过，记下来）

| 坑 | 症状 | 修法 |
|---|---|---|
| **数字后的空白"吃掉"而不结束** | `5 7` 读成 **57**（两个数并成一个）✗ | 空白**结束**当前数（推回）；**只有换行吃掉**（这样 `nextInt` 之后接 `nextLine` 不会先读到空行 ✓）|
| **还没读到数字时的分隔符推回** | `12,34` ⇒ 第二次调用停在同一个 `,` 上 ⇒ **永远返回 0、卡死** ✗ | 还没读到数字 ⇒ **吃掉**分隔符继续找 ✓ |

⚠️ 第一个坑我**绕了好几轮**：连手写的 C 对照都证明"吃掉空白"是错的，
而我一直在怀疑逃逸检查 / arena / `isSpaceByte` ✗
**教训**：算术推理错了的时候，**手写一份等价的 C 跑一遍**是最快的判据 ——
那份 C 一跑出 57 就该立刻明白"是我的算法错，不是编译器错" ✓

### 5. 落地的东西

```extc
// stdlib/std/io.extc（普通库，自己不碰 extern ✓）
type ioError = | readFailed(i32) | lineTooLong(i64)
let BLK: i64 = 65536

struct reader {
    fd: i32  chunk: mut slice<u8>  len: i64  pos: i64
    fn avail / buffered / fill / nextByte / eof
    fn nextLine(out) / nextToken(out) / nextInt / skipSpace
}
fn readerOf(fd: i32) -> reader        // 隐式 64KB ✓
```

**验收**（`tests/io/`，7 条，全绿 ✓）：
正例（两种风格混用）· **EOF** · **行太长** · **读错误** · 分层（sys/io）· **分块读性能**
（10 万行 < 400ms；实测 158ms ⇒ 退回逐字节会当场红 ✓）

## 定案 75 · **`writer` + `writeBytes` 里那个 `flush()`**（2026-09-23）

> 起因：主人点了"**统一 I/O 的形状**"这一步（`reader`/`writer` 只认 fd，
> 文件/标准输入/网络**不该分开**）。做到一半发现一个**真缺陷**，先修它 ✓

### 1. 真缺陷：`println` 与 `writeBytes` 混用**顺序会乱** ✗

`println` 走 C 的 `printf`（**有缓冲**），`writeBytes` 走 `write(2)`（**直写**）⇒
两支队各走各的，谁先到 stdout 不由调用顺序决定 ✗✗

**实测**（去掉修法之后）：

```
B（writeBytes）      ← 本该在 A 后面
文件写完了 ✓
A（println）
C（println）
```

⇒ 原来靠调用者自己记得 `flushOut()` —— "看不见的错"，P′ 正是不许这个 ✓
**修法一行**：`writeBytes` 里先 `flush()`（刷的就是 stdio 那一支） ✓

⚠️ **为什么这条要常设验收**：删掉那行，程序**照样"能跑"**，只是顺序变成 B/A/C ✗
而大多数测试只查"某段文字在不在" ⇒ **抓不到**。
⇒ `tests/io/order.extc` 断言的是**整段连续文本**（`A\nB\nC`），不是分段包含 ✓
⇒ 另有一条**静态**判据：`awk '/^fn writeBytes/,/^}/' … | grep -q flush()` ✓
（两条都验过：删掉 `flush()` 立刻红 ✓）

### 2. `writer`：有缓冲的写，跟 `reader` 对称

```extc
struct writer {
    fd:  i32
    buf: mut slice<u8>      // ← **可见**（`IO.md` 反复讲的"不要 cin 那个黑盒"✓）
    len: i64
    fn cap(self: ref writer) -> i64
    fn flush(self: mut ref writer) -> result<i64, ioError>
    fn write(self: mut ref writer, data: slice<u8>) -> result<i64, ioError>
}
fn writerOf(fd: i32) -> writer      // 隐式 64KB，跟 readerOf 对称 ✓
```

* **只认 fd** ⇒ 同一个 writer 能写文件、stdout、**以后的 socket** ✓
* 装不下就**先 flush**（不丢弃、不扩容）✓
* 写 stdout/stderr 时，**每次 flush 之前先刷 `println` 那一支** ⇒ 顺序天然对 ✓
* 缓冲是**字段**：`w.len` 随时能看、能自己决定什么时候吐 ✓

### 3. 文件 I/O **不需要新机制**（顺带验证）

`std::sys::io` 加了四个原语就够，**一行编译器代码都没动**：

那是 IO-1，需要 `extc_files` 那套 ✓）

`std::io` 和 `std::sys::io` 的短名**都叫 `io`** ⇒ 同一个文件里不能同时 `use` ✗

我上一轮写重构时说"这恰好是对的"（写库的人和用库的人在不同文件里）——

|---|---|---|---|
| 读 | `fs::openRead(p)` | `inputFile` | 不动 ✓ |
| 写（截断） | `fs::openWrite(p)` | `outputFile` | **清掉** ⚠️ |
| 写（追加） | `fs::openAppend(p)` | `outputFile` | **保留** ✓ |

**⭐ 读型 / 写型是两个 struct**（这条是判据，不是口味）：
读方法只挂 `inputFile`、写方法只挂 `outputFile` ⇒ **误用是编译期错误** ✓
```
argument expects `inputFile`, found `outputFile`
no method `put` on `inputFile`
```
⇒ 价值在于"打开错了**编不过**"，而不是运行到一半才发现 ✓

### 明确不选

* `open(p, fileMode.write)`（一个函数 + 枚举实参）：**能编译**（实测过），但
  ① 模式仍藏在实参里 —— 正是主人嫌的那一点 ② 返回类型统一 ⇒ 丢掉编译期判据 ✗
* 把 `O_*` 暴露给用户：平台细节外泄 + 还得自己 `|` ⇒ 老问题原样保留 ✗

### 与既有命名的关系

`xxxOf` = **从已有材料造**（`readerOf`/`writerOf`）· `openXxx` = **打开外部资源**
（后半段是**模式**，所以 `openAppend` 与 `openRead` 成兄弟 —— **故意的** ✓）·
`withXxx` = 构造器带可选参数（`withCap`/`withStream`）✓ 完整规范见 `SYNTAX.md` §3′ ✓
