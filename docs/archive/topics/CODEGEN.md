## 4. 零回退的两个手法（本方案的精髓）

1. **旧机制当预言机**：W1–W3 期间**保留**删除 pass，只把删除条数打印出来。按需发射真做对了 ⇒

2. **双路径并存 + 单开关**：W1/W2 保留旧路径，任一步指纹不符就单开关回退 ✓

### 4.1 W1 已落（2026-10-05）：登记 API + 兜底

* **块变成表**：运行时原语块原来是 4 个字符串字面量；现在是 `src/back/codegen.c` 里的
  `PRIM_BLOCK[]`——**61 行**（**34 个定义** + 27 段脚手架：注释、空行、`#if/#else/#endif` 骨架）。
  逐字节与原块相同（生成器 round-trip 校验 9,675 B ✓，全语料指纹为证）。
* **登记**：`primEmit` 一边发一边登记 `PrimEnt{name, kind, off, span}`（`primEnts`）。
  宏行的名字从它自己的 `#define` 行读出（表里不写裸 `EXTC_*` 字面量：`tools/check_switches.py`
  把任何这种字面量当编译器开关）。
* **删除端**：`dropPrimReg` 用登记的 span 做与旧扫描**同一个判据**（全篇提及数 == span 内提及数；
  宏另按 `#ifdef` guard 不计入、`#define` 行算自身）。旧扫描 `dropRuntimeDefs` **降级为兜底**，
  仍然运行；`EXTC_DBG_PRIMSCAN=1` 跳过登记路径 ⇒ **单开关回退** ✓（已在 `--help` 里点名）。
* **读数**：**414/414 指纹逐字节不变** ✓ · `EXTC_DBG_DCE` **13,923 条不变** ✓ ·
  `./check.sh quick` **72/0** ✓ · `tools/golden.sh` 414 份全是合法 C ✓。
* **`__extc_dying`**：原来是块内一行 + 手工 `DeadDef` 登记（它有括号，行形扫描看不见它）。
  现在它是块里的一个普通 `PRIM_VAR` 实体；`quiet=1` 使它不计入 `[dce] prim`，好让读数与 8,332 基线**可比**。

### 4.2 W1 挖出来的坑（**W2 必须先处理**）

**旧扫描的窗口会越过块尾**：`dropRuntimeDefs` 的 `rl` 每次外层重启都重置为 `rl0 = strlen(primText)`，
而块在被裁剪后变短 ⇒ 窗口 `[rp, rp+rl0)` **伸进块后面的文本**。实测后果：它顺手删掉了
pool 运行期头部的 `extc_pool_capacity`（全语料 **2 份**产物：`tests/stl/clone_warn.extc`、
`tests/pool/rt_stale_alias.extc`）——**这是巧合，不是设计**（伸进去多少取决于块被裁掉多少）。

登记式删除把范围**限定在块内**（这才是这个 pass 一直以来的本意），于是那 2 份会多留一个死函数。
为了 W1 指纹不变，**旧扫描作为兜底保留**并由它继续负责那 2 份 ✓。

⇒ **W2 的入口条件**：要让 `prim → 0`，必须先把 **pool 运行期**（`poolsEmitRuntime`，`src/back/pools.c`，
14 个大字面量）也纳入登记/闭包，否则这 2 份产物要么带死代码、要么指纹变（二选一）。
W2 的验收必须**逐条解释**这 2 份的变化。

### 4.3 W2a 已落（2026-10-05）：原语块按需发射 —— 块内删除 → **0**

**做法**（这是方案 §0 那句话的落点：「在发射之前决定谁存在」）：

* 块在 `primEmit` 里组装到**自己的缓冲区**（`g.prim`），**不写进 `out`** ⇒ 它还不是产物的一部分。
* 8 轮 `dropUnreferenced` 收敛后，`primSplice` 做**需求闭包**：在「还没有这个块」的成品文本 +
  块的脚手架 + 还活着的定义之间迭代到不动点。判据与旧 pass **同一个**（名字的提及全在自己这段里 ⇒ 删；
  宏另按 `#ifdef` guard 不算使用、`#define` 行算自身），但它是**问登记表**，不是猜行形。
* 脚手架（注释、空行、`#if/#else/#endif`）**永远发** ⇒ 丢弃一个定义后留下的字节与旧 pass 完全一样。
* 然后把块**拼进 `primA`**（协程运行期也拼在这个偏移，所以块落在它前面 —— 原来的顺序）。
* 旧的行形 pass 随后跑**一次**：**预言机**（块内必须删 0 条）+ **兜底**（§4.2 的越界）。

**W2a 顺手修掉的真 bug（闸门抓到的）**：`dropRuntimeDefs` 的窗口是 `strlen(primText)`

删除与窗口同步收缩，越界不深；W2 把「裁短」交给了 `primSplice`，越界一下大了几千字节 ⇒
`memchr` 里 SIGSEGV（复现：把 gate 用例的**绝对路径**喂进去，`build/gate/diff/f_neg_zero/t.extc`）。
修法：窗口按 `text + len` 夹一次（越界处本来也没有可删的东西，`span` 检查早就拦着）。
这是审计 §7 闸门③（差分 fuzz）抓到的，不是判据覆盖率问题 —— 是**真崩**。

### 4.4 W2b-1 已落（2026-10-05）：BG-1 修好 —— `rtPrint` 独立按需

`extc_print`（`rtPrint`）」。`needPrint` 只在**两个**调用点置位（`genPrint` 的结构化分支、

### 4.7 下一步：W3（函数/实例/描述符）—— 难点已探明（2026-10-05 读码结论）

**先写结论，免得下一轮重新推**：W3 **不是** W2a/W4 那种"旁置 + 拼接"能完成的一步。

1. **调用边在生成函数体时才发现**（发射 `foo(...)` 文本）⇒ "在发射之前决定谁存在"要求**工作集式生成**：
   从根（`main`/`@export`/`dyn` 表点名/`inTraitTable`）出发逐个发射可达函数，边发边收集被点名的
   callee，迭代到不动点。
2. **今天已有一层剪枝**：`planUsed`（检查器在调用点打标）在选 `g.funcs` 时就丢掉了没人调的函数；
   但它是**语法层**的 —— 只被死代码调用的库函数照样被标 `used` ⇒ 剩给 `[dce] func` 的 5,466 条正是
   **"只被死代码调用"的链**（一条链要在文本上多轮才 unravel）。
3. **偏移活不下来（这条路是堵的）**：函数体生成之后，`dropUnusedLocals` 会在**函数体内部**删文本，
   `bodyOff` 与各函数体的位置随之失真 ⇒ 今天的 pass 只能用文本搜索重新定位
   （`strstr(df->proto)` + `funcDefStart` 的签名行兜底）。要做 by-construction，得先把局部删除也搬到
   缓冲区上，而 `dropUnusedLocals` 是**明确不动**的（335 行，另立项）。
4. **指纹一定会变**：工作集发射顺序 ≠ `m->funcs` 顺序；判据也不等价 —— 文本计数把**注释里提一次**
   当"有人用"、把**自递归的死函数**留住，需求闭包会删掉它们。⇒ W3 的验收**不能**沿用"指纹不变"，
   必须像 W2b-1 那样**逐条解释**并重取基线。

**量化结论（第三轮，2026-10-05）**：造了一把"差集尺"——解析最终产物的函数定义、按**代码里的
名字提及**建图（根 = `main` / 外部链接的定义 / 非函数顶层文本里的提及；**原型不算提及**），
把 9,389 个 `DeadFunc` 候选（**5,466 删 / 3,923 留**）与"从根出发的需求闭包"求差：
**语料上需求闭包并不比文本判定多删任何东西**（第一版报"6 个自递归"是尺子自己的 bug：生成名里
带 `$`（`map$map_pt_i32_kn`）而正则漏了 ⇒ 边丢失；修正后剩 5 个，逐个查证也不成立 ——
`pt_lt` 实测被调用 4 次）。⇒ **W3 的"判定换机制"在语料上可观测变化 ≈ 0**，它的价值落在机制本身，
而"从不发射"那个理想仍堵在 `dropUnusedLocals`（第 3 条）。

**下一轮建议的开工顺序**：
① 先造一把**差集尺**：把 `[dce] func` 的 5,466 条与"工作集闭包"逐产物求差，按类别计数
（注释提及 / 自递归 / 死链 / `vtDefs`·`coroDefs` 这类**后拼接**文本的提及 —— 它们不在 pass 眼里，
是已知的保守来源）。差集 = 指纹变化面；**先量再改**。
② 再改发射：多趟遍历 `g.funcs`（尽量**保持顺序**：只在被点名的那一趟发射），与 `planUsed` 并存，
旧 func 段降级为预言机（`[dce] func` → 0 是这一步的读数），任一步指纹不符就单开关回退。

### 4.8 W2b-2（其余 `need*` 旗子）—— 结论：多半**不该**动

除 `rtPrint`（BG-1 已修）之外的 `need*` 旗子，触发点是**声明**（`extern!`），不是调用 ——
因为那些运行期的入点是**接口**：手写 C / 链接进来的代码可以按名字调它们，而"生成的 C 里没人提到"
不等于"没人用"（§4.6 的 `extc_dyn_put` 就是活证据）。把接口块的旗子换成"调用点需求"会**漏发接口**
✗。⇒ 这一格的正解是**保持粗旗子**；BG-1 之所以能拆，是因为 `extc_print` 是**生成器内部**函数
（只有 codegen 自己调它），不是接口。

### 4.9 第三轮已落：自递归函数不再被自己的调用留住（唯一被证实的洞）

`== 2` 判据把"函数自己调自己"**算成一次使用** ⇒ 一个只被死代码调用的自递归函数会留在产物里
（gcc 照样为它花钱）。改成问"**声明 + 定义之外**还有没有提及"（与两个 piece 的 inside 计数比较，
判据方向不变：**互相递归、没有入口的对仍然保留**）。

* 合成复现（**语料今天不命中**）：自递归 `helper` 只被没人调用的 `deadA` 调 ⇒ 修复前在产物里，修复后消失。
* 读数：**414/414 指纹不变** · `[dce] func` 5,466 **不变**（语料 0 命中）· 编译器耗时 4.49s（同量级）·
  `./check.sh quick` **72/0** · `gate_checkc --scope full` **0** · `gate_asan_corpus --scope full` **0**。

## 9. 记账（已知的坑与教训，别重踩）

1. **判据的覆盖率不可知** ⇒ 判据只能当安全网，**质量看代码是否好维护**（用户 2026-10-05 的纠正）；

5. **`static inline` 不是"未使用"的通用解**：GCC 认，Clang 报 `-Wunneeded-internal-declaration` ✗；

6. **审计 §0.2/§0.3 已经写下本方案的等价物**（手术 B「发射需求闭包」/ C「命名单一来源」；

# 第 2 部分 · 契约与现状 · 三层目标架构 · 质疑 Q1–Q7 · E1 实测（原 `CODEGEN-ARCH.md`）

## CodeGen 是怎么工作的 / 按它的逻辑重构（2026-10-05）

> 目的：**先看清它自身的逻辑**，再谈重构（不是面向 bug 修）。
> 配套：`docs/reviews/CODEGEN-2026-10-05.md`（BG-1 与维护性四条）、
> `docs/reviews/COMPILER-AUDIT-2026-09-30.md` §0.2/§0.3（共性根因与四台手术）。

## 一、它的对外契约（这句话是全部设计的钥匙）

`src/back/codegen.h`：

> **"it infers no types of its own -- every decision it needs has already been written
> onto the tree by the checker."**

⇒ 代码生成**本该是一个投影**（把已决定的事实印成 C），**不该自己重新决定任何事**。
下面会看到，现在它恰恰在重新决定"什么该存在" ✗ —— 这就是要重构的那条缝。

## 二、入口与缓冲区（现状）

**入口只有一个**：`bool generateC(Ctx*, Arena*, TypeTable*, Module*, bool lineMap, Buf *out)`
（`codegen.c:6907`），**一个约 900 行的函数**（到 8815）把整份 C 源拼出来。
它之上是 ~5000 行的 `gen*` 助手（表达式/语句/声明/描述符）。

**它手里的缓冲区**（发射的"内存"）：

| 缓冲区 | 装什么 |
|---|---|
| `out` | 最终 C 文本（`body` 会被拼进来）|
| `body` | 函数体（单独写，之后再定位/删改）|
| `rt` | 通用运行时块 |
| `rtPrint` | 打印运行时（`extc_print` + 描述符表）|
| `rtCout` / `rtCoutF64` | 控制台快路径 |
| `primText` | 运行时**原语**（**保留为文本**，供 `dropRuntimeDefs` 扫描）|
| 另有 pool / http / dns 的运行时发射器 | 各自独立模块 |

**发射顺序**（`generateC` 内部）：函数类型 typedef → 描述符表骨架 → 函数体池 →
各运行时块（**按 15 个 `need*` 旗子逐个决定发不发**，8660–8670）→ 删除 pass。

## 三、真正决定"什么留下"的，是收尾那批 pass（≈600–700 行）

| pass | 位置 | 行数 | 它靠什么判断 |
|---|---|---|---|
| `dropUnreferenced` | 6519 | ~180 | 顶层定义：按**名字**在**整篇文本**里的提及数 |
| `dropUnusedLocals` | 6172 | **335** | 函数体内局部：按块级 span 计数 |
| `dropRuntimeDefs` | 5904 | **266** | 运行时原语：**行形识别**（行尾 `{`/`}`/`,` + 含 `(`，首字符不是空格 `/` `#` `*`）+ 大括号配对量 span + 宏的 guard/define 覆盖 |
| `dropUnreferenced`（函数段） | ~6556 | — | `countGet(name) != 2`（"原型 + 定义，别无提及"）|
| 共用工具 | 5820–6520 | ~90+ | `NameCount` 哈希表、`countMentions` / `countMentionsIn` / `countSpan` |

**关键事实：活跃性是"文本里这个名字出现几次"** —— 定义边界靠**行形状**，块归属靠
**写进了哪个缓冲区 + 哪个旗子**。于是：

* 注释里写一个名字 = 一次"使用" ✗（BG-1 的加重细节，已修）；
* 发射端与删除端**各自知道"一个定义长什么样"** ✗（改一边不报错）；
* 一个旗子管两个需求不同的块 ✗（BG-1 的根因）；
* 每砍一次就**重扫整篇**（两处 `for(;;)` + `!cut ⇒ break`）✗（曾烧 15 分钟无诊断）。

## 四、按它自己的逻辑，重构应该长成三层

契约说"代码生成不做决定" ⇒ 那么：

### L1 决定（发射之前）：**需求闭包（needs set）**

从入口（`main`、`@export`、模块 init）出发做一次可达性，产出一个**需求集合**：
哪些函数、哪些泛型实例、哪些描述符、哪些运行时**原语**、以及哪些运行时**块**。

* 15 个 `need*` 旗子**全部退休** —— 块的需求 = "这个块里有片段在需求集合里"；
* 函数/描述符的存活也在这里决定 ⇒ 那批**计数 pass 全部不需要**；
* 事实来源：`plan`/AST（`NodeResults.used` 之类的既有事实 ✓），**不是文本**。

### L2 发射（纯投影）：**每个实体就地登记**

发射时把 `{name, kind, block, 起始偏移}` 记进一张**输出符号表**：

* 删除端**不再从行形猜**（行形规则、brace 配对、anchor 技巧全删）✗✗；
* "发射端 vs 删除端"的双份知识**收成一份**（审计 §0.2-3 / R2 ✓）。

### L3 装配：块按固定顺序拼接；删除 pass 退成**断言**（或删除）

到这一步，"该发什么"已经在 L1 定了，L3 只做拼接与自检 ✓。

## 五、迁移路线（每步都可用 414 份产物指纹度量）

| 步 | 内容 | 预期产物变化 | 消掉 |
|---|---|---|---|
| **S1** | 引入**登记 API**（`rtPiece(name, kind, span)`），让 `dropRuntimeDefs` **用登记信息**而不是行形；块级门控改为"本块有无被引用的片段" | **应当为零**（纯重构 ⇒ 指纹一致 ✓）| 双份知识、参数化门控 |
| **S2** | 引入 **needs set** 取代 15 个旗子 | 只在旗子**判错**的产物上变化（BG-1 那类 ✓）| 粗旗子 |
| **S3** | 函数/描述符/局部 的存活也进 needs set ⇒ **删掉计数机制** | 应当极小（只修掉历史误判）| ①②③④全部 |

**度量方式**：每步前后对 `tools/golden.sha256` 的 414 份产物逐个编译+哈希
（`/tmp/leadchk/fp-before.sha256` 是今天的基准 ✓）⇒ **"这一步到底改了什么"是数据** ✓。
判据/闸门只当**安全网**，不作为质量依据 ✓。

## 六、边界（明确不做）

* 不动 **C 发射层**（表达式/语句/描述符的印法）—— 它是好的（可读、确定性、双编译器 `-Werror` 干净 ✓）；
* 不动 `needRuntime` 这类旗子的**语义**去"精确化"（注释写明漏发=生成物坏掉 ✗）—— 是**替换机制**，不是调参；
* BG-1 的那个 `__attribute__((unused))` 在 **S2 完成后**删掉（它存在的唯一理由就是那面粗旗子）。

# 附：质疑这套逻辑本身（2026-10-05，用户要求"可以质疑"）

上面的 L1/L2/L3 仍然**接受了现状的前提**（先全发、再决定谁留）。这里逐条质疑前提。

## Q1（最深）"先全发再删"——为什么会有"死代码"这个问题？

编译器后端**本来是走着程序发射的**：谁被引用就发谁。只有在"发射到一半才发现需要某样东西"
（泛型实例、描述符、运行时原语、库函数）时，才需要"补发"。于是设计上只有两条路：

* **按需发射（pull/worklist）**：从入口出发，遇到引用就补发 ⇒ **死代码根本不会产生** ✓✓
* **先全发再删（push + GC）**：现在这条 ✗ —— 它把"补发"的懒惰性换成了"事后判定谁没用"的负担，
  而判定的依据只能是**输出文本**（因为没有别的 IR）✗

**结论**：那 ~600–700 行删除逻辑，是"先全发"这个选择的**账单** ✓ 不是必需品。

## Q2 为什么必须是"一个 TU、全是 static"？

这个选择**逼我们自己重写链接器** ✗ —— 而工具链里那个是免费的、精确的：

```sh
gcc -ffunction-sections -fdata-sections -Wl,--gc-sections ...
```

一个 TU 里 `-ffunction-sections` 同样给**每个函数**一个 section ⇒ 未被引用的 static 函数/数据
会被**链接器**丢掉 ✓ 正确性由 binutils 保证，不需要"数标识符 + 行形识别 + 大括号配对" ✗。
**（这可以直接测：见下面的实验 E1。）**

## Q3 运行时为什么是**字符串字面量**？

`rt`/`rtPrint`/`rtCout`/`primText` 是嵌在 `codegen.c` 里的 C 源码文本 ✗ ⇒ 三重代价：
① 只有某个程序用到它时才发现语法/警告 ✗；② "一个定义长什么样"的知识**被迫复制**一份给删除端 ✗；
③ 无法单独编译测试 ✗。若它们是真 C 文件（或 `#include` 的 support TU）⇒ ①②③ 同时消失 ✓，
`need*` 旗子也失去存在理由 ✓。

## Q4 codegen 凭什么"决定"？（它自己的契约说它不做决定）

`needRuntime` / `needCout` / `needPool` / `needDns` / `eqNeed` **是程序的事实**，属于**分析（plan）** ✓
而它们在**发射过程中被顺带置位** ✗ ⇒ 结果**依赖发射顺序**，而且契约（"every decision ... has already
been written onto the tree"）**被自己违反** ✗。两条都行，**现在这条（边发射边决定 + 事后猜）最差**：
(a) 把决定上移到 plan ✓ 或 (b) 承认 codegen 是决策点、做成**正经的按需引擎** ✓。

## Q5 粒度错了

"这个程序要不要 http / dns / pool / 打印运行时"是**模块级**事实 ✓，却用**符号级文本计数**去救 ✗。
模块级可达性（模块依赖图）便宜、精确、且**在 plan 里就能算** ✓ —— 这正是审计 §0.3 里 R13
"**粒度建模错**"的同一种形状 ✓。

## Q6 为什么没有显式 IR？

因为**半成品 C 文本就是 IR** ✗ ⇒ 于是到处都是 `span` / `offset` / `anchor`（缓冲区的第一行）/
`bodyOff` ✗。标准形状是一张小表：`CEntity { kind, name, deps, text }` + 若干 pass ✓ 可单测、可重排 ✓。

## Q7 一个 900 行的编排函数

`generateC` 里 typedef → 描述符骨架 → 函数体池 → 块 → 删除 pass 全在一个函数 ✗ ⇒
没有相位边界、不能单独测 ✓（而且它是"顺序敏感 bug"的温床 ✗）。

## 保留的前提（也要说清）

**单文件输出**（一个 `.c`，无构建系统、无运行库版本错配）对"2 核小机器上部署"是**真价值** ✓ ——
如果它是硬要求，那么 Q2 的工具链 DCE 只能省**二进制**、省不了**源文本** ✓ ⇒ 这时正解是
**Q1 的按需发射**（源文本里根本没有死代码）✓✓。

## 实验 E1（今天就能做，纯测量）

对 414 份产物各做两件事，比较**二进制大小**与**源文本大小**：

| 量 | 做法 |
|---|---|
| A：今天的样子（文本已删）| `extc x.extc -o a.c && gcc -O2 a.c` → 记 `size a.out`、`wc -c a.c` |
| B：不删，交给工具链 | 关掉文本删除（或拿"未删版本"）⇒ `gcc -O2 -ffunction-sections -fdata-sections -Wl,--gc-sections` → 同两个量 |

若 `size(B) ≈ size(A)` ⇒ **文本删除对二进制毫无贡献**（只影响源文本外观 ✓）⇒ Q1/Q2 直接成立，
那 ~600–700 行可以整体退场 ✓。这一步是**数据**，不是判据 ✓。

# 第 3 部分 · 完整方案与子步细节 · 已答问题（原 `CODEGEN-WORKLIST.md`）

## 按需发射（worklist）实施方案（2026-10-05）

> 第 1 步的施工方案。目标：**在发射之前决定"谁存在"**，让生成的 C 里不可能有死代码。
> 前提与验收数据见 `第二部分（本文）`（附录二 + E1 实测）。**动手前先回答文末"必须先回答的问题"。**

## 一、为什么这一步是纯重构（这就是"零回退"的底气）

死代码**今天已经被删掉了**（M1：6917 个 static 函数，0 个没人调用 ✓）。
所以按需发射**不改变可观测输出** ⇒ **414 份产物指纹应当逐字节不变** ✓✓
⇒ 每一步都能用一个 `diff` 判生死，不需要"跑跑看" ✗。

**收益在别处**：文本扫描层退场（成本不再随产物规模增长）、`need*` 旗子退休、发射顺序不再决定事实。

## 二、发射的现状：三类东西，三种"谁存在"的判定

| 类别 | 今天怎么决定 | 目标 |
|---|---|---|
| **函数/泛型实例/原型** | **先全发**，之后由 `dropUnreferenced` 的函数段按 `countGet(name) != 2` 删 | 需求闭包 |
| **描述符行** | 已经是半按需的（`descRef` 发号；`SCALAR_DESC` 行"发了再删"）✓ | 收进闭包 |
| **运行时块/原语** | 15 个 `need*` 旗子（**发射途中顺带置位** ⇒ 顺序敏感 ✗） | 收进闭包 |
| **函数体内的局部/载荷绑定** | `dropUnusedLocals`（**在活函数内部**，按需发射帮不上 ✗） | **本轮不动**（另立项）|

## 三、worklist 的形状

```
起点集合 S0 = { main, @export 的函数, 模块 init 入口, 被驱动的入口 }
worklist W = S0
while W 非空:
    e = W.pop()
    if e 已发射: continue
    发射 e（原型 + 定义 / 描述符行 / 运行时片段）
    在这次发射**过程中**记录它引用的实体 ⇒ 全部推入 W
```

**关键性质**：发射某个实体**只依赖名字**，不依赖别的实体的文本 ⇒ 可以按任意顺序发射 ✓
（这正是现在做不到的地方：现在的删除判定依赖"整篇文本"✗）。

**闭包要覆盖的引用边**（每一条都要在发射时登记）：
函数/方法调用 · 泛型实例引用 · 描述符（含**嵌套字段类型**的描述符 ✓ 递归）· 运行时原语 ·
运行时**块**（块 ⇐ 它的任一原语/片段被引用 ✓ 这正是替换旗子的地方）· 模块级全局与其 init。

## 四、子步（每步都有判生死的数据）

| 步 | 做什么 | 期望指纹 | 期望 M1 | 可回退性 |

| **W1** | **登记 API**：发射实体时就地登记 `{name, kind, block, span}`；删除端**优先用登记信息**，行形识别降级为兜底 | **不变** ✓ | 0 | 小（双路径并存 ⇒ 可对照）|
