什么是 dyn Trait？

以及 extC 为什么把它做成现在这样

一句话：让「用同一段代码处理不同种类的对象」这件事，
在编译期不知道具体类型的时候也能成立。

1先看问题

你有三种形状，都想算面积。类型不一样，但你要用同一个名字。

Circler: f64
Rectw, h: f64
Tria, b, c: f64
// 一张"方法清单"：谁想被当成 Shape，就得交出 area
trait Shape {
    fn area(self: ref Self) -> f64
}

// 各自"签字交作业"
impl Shape for Circle { fn area(self: ref Self) -> f64 { return 3.14 * self.r * self.r } }
impl Shape for Rect   { fn area(self: ref Self) -> f64 { return self.w * self.h } }

// 现在：写一段"能把它们一起算掉"的代码
fn total(shapes: slice<dyn Shape>) -> f64 {
    var sum: f64 = 0.0
    for s in shapes { sum = sum + s.area() }   // ← 这里 s 到底是 Circle 还是 Rect？编译期不知道
    return sum
}

那行 s.area() 调谁？ 这就是 dyn Trait 要解决的问题。

2两条路：编译期定死 vs 运行期去查

静态分发（编译期就知道）

fn total<T: Shape>(xs: slice<T>) -> f64 {
    // 编译期知道 T 是 Circle
    // ⇒ 直接调用 circle_area
}

快：零查表、能内联。
窄：你必须写代码时就知道类型。

动态分发（dyn）

fn total(xs: slice<dyn Shape>) -> f64 {
    // 编译期只知道"是某种 Shape"
    // ⇒ 运行期查表找 circle_area
}

宽：能处理写代码时还不存在的类型（插件、动态注册）。
慢一点：查一次表 + 一次间接调用。

写 dyn 就是明说：「我知道这是运行期的，我接受那点开销。」

3所以一个 dyn 值里装了什么？

两样东西：东西在哪儿 + 它的方法表在哪儿。

dyn 值
「对象在哪儿」+「方法表在哪儿」
→
东西（Circle 的数据）
Circle 的方法表
area → circle_area 的地址
 ← 这张表俗称 vtable

为什么不用"两个指针"？

C 里就是 {数据指针, vtable 指针}。裸指针 ⇒ 悬垂了没人知道，是 UB。

extC 用什么？

extC 的世界里没有裸指针，只有「池 + 下标」。所以：
dyn 值 = 3 个整数：哪只池、第几个、第几代。

4extC 的 dyn 值 = 一个句柄

pool哪只池
idx第几个
gen第几代

三个整数，纯数据。没有指针、没有别名。

复制它

就是复制 3 个整数，随便传、随便存。

方法表也在池里

不放在静态数据段，而是和对象一样住在池里。

用之前对一下 gen

对不上 ⇒ trap，带 .extc 行号。
不是读到垃圾，不是 UB。

5一次 s.area() 到底发生什么

dyn 值{pool, idx, gen}
→
去池里取方法表顺手检查 gen
→
跳到 circle_area把对象地址交给它

gen 对得上

正常调用。开销 = 取一次表 + 一次间接调用。

gen 对不上

池没了、插件被卸载了……
当场 trap：foo.extc:42: this vtable belonged to the unloaded library X

这就是 extC 相对 C++/Rust 的核心不同：失败是稳定的、带位置的，不是 UB。

6但句柄住在池里，就带来一条规则

extC 每个值都住在两块地之一。能不能被"借"（引用），只看一件事：它什么时候结束，编译期知不知道。

地方 / arena

  • 局部变量、new 出来的东西
  • 整块释放：地方结束 → 全没了
  • 何时结束？编译期知道 ✓

⇒ 可以借出去（ref T / slice<T>）

池 / pool

  • 容器自己的存储（vector、map）
  • 随容器释放；容器一增长就换块
  • 何时释放？运行期的事 ✗

⇒ 不要借出去，要用就传句柄

所以只有一句大白话：借进来可以，借出去不行。

7其实还有第三块地

每块内存的「寿命信息」在哪里，决定了用什么机制保证安全 —— 这就是 extC 内存模型的全部。

编译期就知道

地方 / arena

  • 栈、块、new 出来的东西
  • 机制：静态检查（逃逸 / 深度）
  • 视图 ref T / slice<T> 零成本
  • 出错：编译错误

运行期才知道

池 / pool

  • 容器、dyn 里的对象
  • 机制：句柄 + 代际
  • {pool, idx, gen}：取用前对一下编号
  • 出错：trap，带行号

谁都不知道

外面的世界（C）

  • 别人给的缓冲区、fd、mmap
  • 机制：你签字（extern!）
  • effects Addr=0 Cont=0
  • 出错：签了字就认账

一个能记住的比喻

地方 = 场次
到点整场清空，谁到期了编译器知道

池 = 货架
位置 + 编号；货架什么时候拆，日历说了算

C = 外面的世界
递地址 / 收地址，你签字

不是"三选一"：这是同一件事的三档答案。
少了谁都不好：没有日历 → 货架什么时候拆没人知道；没有货架 → 换大货架要整场重来；没有外面 → 孤岛。

8C 互操作丢了吗？没有

互操作靠的是「视图就是裸指针」，跟 arena 还是 pool 无关。

// tests/extern/libc.extc —— 真在跑的写法
extern!("libc") fn write(fd: i32, buf: ref u8, n: i64) -> i64
    effects Addr=0 Cont=0          // "我不存你的指针" —— 这就是签字

var s: slice<u8> = msg[..]
let n = libc::write(1, s.data, 5)   // s.data 就是地址，直接递给 C

内存是真的

arena 的块、池的块都是 malloc 来的 ⇒ 随时能给出真实地址。

视图零转换

slice<T> / ref T 在 C 层面就是 T*（+ 长度）。

布局天然兼容

extC 的 struct 生成的就是普通 C struct ⇒ 不用序列化、不用 marshal。

arena / pool 管「什么时候安全」；C 那一层管「外面信不信」。
你担心的"实际存储能力"从来没丢 —— 丢的只会是"保证"，而保证本来就不该由外面给。

9那池里的方法里创建变量呢？

照常写，不用管。编译器按「这东西会活多久」自动决定它落在哪一层。

impl Shape for Circle {
    fn scaled(self: ref Self, k: f64) -> Circle {
        var tmp: Circle = { r: self.r * k }              // 局部变量 → 落在"当前这个地方"
        var buf: vector<f64> = vector<f64>::new()    // 临时容器 → 拿自己的一只池
        return tmp                                     // 按值返回 → 拷出去，没事
    }
}

如果它要活得比调用点更久？

编译器偷偷给这个函数多传一个「生在哪层」的参数，由调用者决定：

调用者我知道它该活多久
→
池里的方法隐藏参数：生在哪层

这套今天就在跑。dyn 完全不用管它。

10池里的对象要访问 arena 的变量

借进来 ✓

池里的对象可以存一个 arena 的引用（字段，或当参数传进来）：

struct Circle {
    r:   f64
    ctx: ref RenderCtx   // arena 的引用
}

编译器检查：arena 活得比这只池久吗？（和 vector<slice<u8>> 同一条规则）

借出去 ✗

不要拿 ref 指着池里的对象：

ref 指着池里
→
池增长换块
→
悬垂

换块是运行期的事，编译器看不见 ⇒ 用句柄传。

11dyn 唯一多出来的麻烦

类型一擦除，对象里有没有借来的东西，编译器就看不见了。

普通 struct：看得见

编译器知道 Circle 里有个 ref，能算它活多久 ⇒ 照常检查 ✓

dyn：看不见

只知道「某种 Shape」，payload 里装了什么不知道 ⇒ 没法保证安全。

v1 最省事的答案

dyn 里的数据不许含借来的东西（ref / slice）。
在转成 dyn 的那一行检查 —— 那里具体类型是知道的 ✓

以后想放开：让 trait 声明 payload 的引用深度上界，每个 impl 注册时核对。

12只剩两个问题要你拍板

问题 1

dyn 里的数据能不能含借来的东西？（ref / slice）

建议 v1：不能。
数据要么放池里，要么当参数传。最省事、最好解释。

问题 2

池对象的方法要不要环境参数？

fn draw(self: ref Self,
        ctx: mut ref RenderCtx)

建议要。显式传，编译器什么都能查，接口也自洽。

就这两个。其余都是实现者的事，你不用背。

13回头看那三句话

1. dyn 值 = 一个句柄（3 个整数，复制无害）
2. 方法表放在池里，用之前对代际 ⇒ 陈旧是 trap，不是 UB
3. 它不引入新的内存规则 —— 只有一条：借进来可以，借出去不行
