# 数组与视图（数组对象的语义契约）

这份文档回答"数组对象该怎么设计"。它属于"有什么待做"那一类，和
[`PARALLEL.md`](PARALLEL.md)、[`FUSION.md`](FUSION.md)、[`TODO.md`](TODO.md) 同源：
清单在 `TODO.md`，这里是机制与判据。

结论先写在这里：数组只保留**两个角色**——拥有者（`array`/`array2`）与视图（`view1`/`view2`），
多维视图内建；整数组表达式由编译器降低成融合循环，**不分配临时数组、不引入运行时**。
这两个决定的去向是 NumPy 的手感 + C 的可预测性，而不是 NumPy 的实现方式。

## 为什么值得做（证据）

`bench/stream`（[`bench/stream`](../bench/stream)）量到：同一条逐元素管线，物化中间数组比融合慢
36%，不落数组比融合再快 44%（n=4M，出 L3）。`bench/par` 量到 `par` 在 1M 元素上的加速比约 4.1×。
也就是说：**手感的代价主要是内存流量，而内存流量正是编译器能自动省掉的部分**——这正好是造编译器的
意义，所以这里不该让人手写 `i * n + j`。

## 类型模型

| 角色 | 类型 | 说明 |
|---|---|---|
| 拥有、1 维 | `array<T>` | 运行期长度，唯一主人，arena 分配，索引 `a[i]` |
| 拥有、2 维 | `array2<T>` | 运行期 rows/cols，行主序，索引 `a[r][c]` |
| 借用、1 维 | `view1<T>`（`slice<T>` 是它的同义词） | `{data, len}`，零拷贝传递 |
| 借用、2 维 | `view2<T>` | `{data, rows, cols, rs, cs}`，行主序或任意步长 |
| 内联、定长 | `[N]T`、`[N][M]T` | 长度进类型，值语义，只用于小数据与 C 互操作 |

视图按值传递（几个字的结构体），拥有者按移动语义传递。`mut` 前缀表示可写：`mut view2<T>`。
数组与视图之间只有两条转换：拥有者 → 视图（隐式、零拷贝）、视图 → 拥有者（显式 `.copy()`）。

三维及以上暂不提供。理由：`par`、融合、以及现有的 C 互操作都只需要到 2 维，rank 特化到 2 维
能把下标与边界检查都编译成常数级；三维以「`view2<view2<T>>` 是错的、按需再议」处理。

<!-- fragment -->
```extc
// 现在的形状（一串 flat 下标）
var a: mut slice<f64> = new f64[rows * cols]
b[r * cols + c] = a[(r - i64(1)) * cols + c]

// 目标形状（视图 + 多维下标）
var a: view2<f64> = array2<f64>::zeros(rows, cols)
b[r][c] = a[r][c] + a[r + i64(1)][c]
```

## 索引与切片

- `a[i]`：1 维视图；对 2 维视图则取第 `i` 行（零拷贝行视图，`view1<T>`）。
- `a[r][c]`：元素。每个维度各一次边界检查；按 `data + r * rs + c * cs` 取址。
- `a[r0..r1, c0..c1]`：子视图，零拷贝；省略下标的写法不给（v1 不猜形状）。
- 越界：与今天一致，trap 报文件与行号。循环里的仿射下标允许在循环入口做一次范围检查，
  体内走裸访问（[`FUSION.md`](FUSION.md) 里"逐元素成本"那节）。
- 负下标、步长切片：不支持，写了就报错。

## 整数组表达式

这是 NumPy 手感的核心，做法是**语法糖 + 降低**，不是运行时对象：

- 允许 `+ - * / %`、比较、一元 `-` 作用在同形视图之间或视图与标量之间；标量广播只到
  "每个元素都拿这个标量"。形状不同、类型不同一律编译错。
- 赋值目标是视图时，右侧整数组表达式按目标形状展开成循环嵌套；**不产生临时数组**。
- 表达式的用处限定在赋值右值与 `par` 体内的输入；它不能作为返回值或字段初值
  （那需要"持有"一个形状，而形状只在视图里）。需要保存就显式写进一个视图。
- 求值顺序：逐元素运算与顺序无关（每个元素独立）；归约按行主序、从左到右固定顺序，
  与串行参考实现逐位相同。
- 别名：目标与读视图重叠时，按"每个元素先读后写自己"的语义处理；含归约的表达式不允许
  与目标重叠（编译错）。这条让融合不需要做别名证明，只要不做跨元素重排。

<!-- fragment -->
```extc
// 一个 Jacobi 步：降成一个 (rows-2) × (cols-2) 的循环嵌套
b[1..rows - 1, 1..cols - 1] =
    (a[0..rows - 2, 1..cols - 1] + a[2..rows, 1..cols - 1] +
     a[1..rows - 1, 0..cols - 2] + a[1..rows - 1, 2..cols]) * 0.25
```

## 降低契约（编译器必须保证）

1. 任何整数组表达式**不分配堆内存**。降低结果只有循环、临时标量、以及原有视图的地址计算。
2. 每个循环入口至多一次范围检查；子视图构造是 O(1) 的加法。
3. 连续赋值之间的中间视图若无其他读者，融合阶段消掉（`FUSION.md` 的 S1/S3），
   `--no-fuse` 关闭后代码逐位一致。
4. `par` 体内的整数组表达式按当前 worker 的输出槽形状展开，不跨线程重排。
5. 生成的 C 只多出 `double` 循环，不引入新的运行期符号。

## 所有权与并行

- 拥有者唯一主人；跨线程传所有权是移动，传视图是零拷贝共享；写视图只能有一个主人。
- `par` 的输出可以是 `mut view2<T>`：每维下标必须恰是该维的循环变量，于是"不同迭代写同一格"
  在结构上不可能——这取代 2 维循环折叠里那套 flat 下标唯一性检查，也让 `[r][c]` 的写法
  自然通过检查。
- 归约是第二形状：先写进视图，再 `seq::sum` 这类固定顺序的归约；融合把"写进数组再归约"
  收成一遍（S3）。

## 分阶段落地

每一阶段独立可用、独立验收；后面的不阻塞前面的。

1. **止血（库层）**：`varArray` 支持 `v[i]`（等价于先 `asSlice()` 再下标）、定长数组隐式转
   `view1` 传参、`tensor2` 补 `[]` / `[]=`，让现有代码少写转换。
2. **`view2<T>` 内建**：类型、下标、切片、`array2` 分配、`par` 写支持；`tensor2` 变成薄包装；
   2 维折叠的写判据改成"每维下标恰是该维循环变量"。
3. **整数组表达式**：语法与类型检查、降低成融合循环、逐位对拍闸门；`bench/stream` 加表达式臂，
   `bench/par` 加 `view2` 臂。
4. **三维/rank 泛化**：等到有真实需求再说。整数泛型与它同属一块地基，暂不进这页的范围。

## 判据

- 语义：每个阶段的语义测试都有"串行朴素循环"参考实现，stdout 逐字节相同。
- 逐位：`--no-fuse` 开/关、`par` 线程数 1 与 N 的输出一致。
- 边界：越界 trap 的时机与文案；空视图；形状不匹配的编译错文案稳定。
- 性能：`bench/stream` 表达式臂不劣于手写融合臂；`bench/par` 的 `view2` 臂相对 `seq` 有可测加速；
  不使用新特性的既有 bench ±3% 内。
- 文档：本页 + [`usage/language.md`](usage/language.md) 的新章节 + 示例闸门。

## 未决问题

- `a[r][c]` 与 `a[r, c]` 二选一：倾向前者（与 `[N][M]T` 一致，`a[r]` 又能当行视图）。
- `tensor2` 的去向：薄包装还是删除（步长能力搬进 `view2`）。
- 可变性放在类型里（`mut view2<T>`）还是靠借用推断；前者简单，后者接口少一半。
- 整数组表达式的归约写法：函数调用（`sum(a)`）还是方法（`a.sum()`）；`par` 禁调用，
  需要为归约算子开特例。

## 库原型（第一步的落地设计）

第一步只在 `stdlib/stl/` 里做：不改编译器、不进 `prelude`。目标是先拿到 API 的手感与
"少拷贝"的收益数字，让第二步的取舍有据可依。

### 模块与类型

- `stl::nd`：`array2<T>`（拥有、行主序，`data/rows/cols`）、`view2<T>`（借用，
  `data/off/rows/cols/rs/cs`）；一维沿用 `slice<T>` 与 `mut slice<T>`。
- 构造走关联函数（与 `tensor2::fromFlat` 同形）：`array2<T>::zeros(rows, cols)`、
  `array2<T>::fromFlat(s, rows, cols)`、`view2<T>::of(s, rows, cols, rs, cs)`；
  失败返回 `?`，不 trap。
- 访问：`rows` / `cols` / `rowStride` / `colStride`；`get(r, c) -> ?T`、`set(r, c, v) -> bool`；
  `row(r) -> ?slice<T>`、`col(c) -> ?slice<T>`（零拷贝）；`sub(r0, r1, c0, c1) -> ?view2<T>`
  （零拷贝）。`[]` 与 `[]=` 运算符方法第一步就给（`tensor2` 已有先例），`m[1][2]` 与行视图
  `m[1]` 都走它。

### 逐元素运算：按目标写入，不产生临时数组

第一步没有融合，所以每个运算都写到调用者给的视图：

- `addInto(dst, a, b)`、`subInto`、`mulInto`、`divInto`
- `scaleInto(dst, a, k)`、`axpyInto(dst, a, b, k)`（`dst = a + k * b`）、
  `mulAddInto(dst, a, b, c)`（`dst = a * b + c`）
- 一元：`negInto`、`absInto`
- 形状不匹配、空视图 → 返回 `false`，不 trap；同形时允许原地（`addInto(a, a, b)`），
  逐元素先读后写。

### 归约：流式，不落数组

`sum` / `max` / `min` / `count` 直接遍历视图（复用 `seq` 的语义：空视图给 `none`，
行主序固定顺序）；分块并行版本沿用 `parts: mut slice<T>` 的 `sumBlocks` / `maxBlocks` /
`minBlocks` 形状。**泛型约束**：extC 的泛型函数不能调用另一个泛型函数，所以每个归约
自带一个小循环，不转调 `stl::seq`——这也是第二步把归约下沉到"整数组表达式 + 降低成
流式循环"的理由之一。

### 卷积（第二步再展开）

第一步只留两个形状：`stencil5Into(dst, src, c: slice<T>)`（五点模板，逐元素、不落中间平面）
与 `conv1dInto(dst, src, kernel)`（可分离卷积的前半）。它们只验证"零拷贝 + 一遍流"的写法，
不做性能承诺。

### 零拷贝的来源（八条）

1. 视图按值传（几个字），子视图构造是加法；2. 运算写进调用者给的 `dst`；3. 行/列视图零拷贝；
4. 归约流式；5. 允许原地；6. 只有 `copyInto` 真正搬元素；7. 卷积不建中间平面；
8. 库内部不持有元素数组。

### 判据（第一阶段的验收）

- 语义：每个运算与"朴素循环"参考实现逐字节相同（`f64` 同序 ⇒ 可按位比较）。
- 零临时数组：大尺寸（≥ L3）下库 pipeline 的峰值 RSS 与单 `dst` 方案一致；`bench/stream`
  加一条"库 pipeline"臂，与手写融合臂对比。
- 泛型覆盖面：`f64` 与 `i64` 两套测试都过。
- 错误模型：形状不匹配、越界、空视图一律 `false` / `none`，不 trap。
- 闸门：doxygen / walkers / ast-freeze / 公开面清单照跑。

### 第二步：把什么放进 prelude / 编译器

- `view2<T>` 变内建类型（与 `slice<T>` 同族）：`a[r][c]`、`a[r0..r1, c0..c1]` 走语法；
  `par` 输出 `mut view2<T>`，每维下标即该维循环变量——二维折叠的地址唯一性由此成为结构性质，
  顺带修掉现行 `parIndexOverLoops` 的竞争。
- 整数组表达式（`dst = a * 0.25 + b`）由编译器降低成融合循环；第一步的 `*Into` 函数退成薄壳。
- 保留在 `stl` 的：需要具体算法的（卷积、可分离滤波、矩阵乘），避免 `prelude` 变成大库。

### 落地顺序

1. `view2<T>` / `array2<T>` + 构造、访问、子视图 + 测试。
2. 逐元素 into 运算 + 原地 + 别名测试。
3. 流式归约（含分块并行）+ 逐位测试。
4. `stencil5Into` / `conv1dInto` + `bench` 一条臂量化"少拷贝"。
5. `docs/usage/stdlib.md` 一节 + 公开面清单 + 闸门。

每一步独立提交；prelude 化在第一步的 API 稳定后再谈。
