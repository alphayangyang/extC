## 1. 为什么需要它（先看数字，别听我说）

四个形状，`/usr/bin/time -f "%M"` 量的**峰值 RSS**：

| 形状 | 峰值 RSS | 活跃数据 | 结论 |
|---|---|---|---|
| **A** 翻倍长到 1e5，但每轮在**会退出的块**里做（12 轮）| **2,640 KB** | — | **平** ✓ 块退出就还 |
| **B** **一个**数组从 1 翻倍长到 1e6（4 MB）| **9,900 KB** | 4,096 KB | **≈2.4×** ✗ 历代旧副本全留着 |
| **C** 每轮新建/重建，分配点落在**长命层**（12 轮）| **14,184 KB** | — | **随轮数线性涨** ✗✗ |
| **D** 一次要够（`new i32[1048576]`）| **5,676 KB** | 4,096 KB | ✓ 只差进程基线 |

**规则**（比"增长了几次"重要）：
1. arena 只在**分配点那一层的块退出**时回收 ⇒ 长命层里**任何**分配都是永久的
2. **同一个容器对象复用** ⇒ 增长只到峰值一次 ⇒ 浪费 ≈ 1× 活跃量（B）—— 有界但真实
3. **每轮新建对象**、分配点又在长命层 ⇒ **无界**（C）✗✗

⇒ 服务型程序（跨请求状态、缓存、会话表）**必然**撞在 2、3 上：它的层永远不退出 ✓

## 2. region 是什么：把"层"从词法变成**动态但显式**

今天 extC 只有一种回收单位：**词法块**。region 是第二种：**程序自己命名的 epoch**。

- **运行时那套已经有了**：`extc_arena` 是值类型，`extc_arena_release`（**留一块复用**）与
  `extc_arena_destroy`（全还）都在 ✓ ⇒ region 的 API 与它们 1:1，**不需要新的分配器** ✓
- **逃逸检查那套也在按层推理**了 ✓ ⇒ "引用不能活过它所属的 region" 与 "引用不能活过它的块"
  是**同一条规则**，只是层的来源变了 ✓
- ⭐ 它一次解决三件事：**服务型内存**（按 epoch 还）· **容器 churn 回收**（`reset`）·
  **线程间块转移**（无锁的"把一块内存交出去"）✓

## 3. 语义设计：五个岔路（请逐条批）

### 3.1 【R1】region 能活多久？（**这条决定其余全部**）

| 选项 | 含义 | 收益 | 代价 |
|---|---|---|---|
| **R1-a 块内局部**（阶段 1）| region 是**块里的局部值**，最晚随块退出销毁 | 容器 churn 回收 · 每请求/每阶段的批量回收 ✓ | **跨迭代的缓存救不了**（服务型的核心痛点 ✗）|
| **R1-b 词法作用域内**（阶段 2）| region 可以是外层 `var`，活到它自己的作用域结束；引用带"这个 region 的 epoch" | **跨迭代按 epoch 回收** ✓✓ 服务型从根上不炸 ✓ | 层的比较要扩展 · `drop` 需要 affine 检查（谁还持有它的引用）✗ 大 |
| **R1-c 可传参/返回/进字段**（阶段 3）| region 变成普通值，能跨函数传 | 库可以造"带自己 arena 的容器" ✓ | region 演算全套 + 能力传递 ✗ 最大 |

> **我的倾向**：**R1-a 现在做，R1-b 作为目标，R1-c 先不定** ✓
> 理由：R1-a **完全不碰逃逸 pass**（region 的层 = 创建它的块那一层 ⇒ 没有新比较 ✗ 而那个 pass
> 很娇气：7 个 canary，前几轮有一次补丁差点把它们变成洞）✓ 它已经能解决"容器内部 churn"
> 和"每请求/每阶段"这两种最痛的形状 ✓

### 3.2 【R2】分配怎么指定 region？

| 选项 | 样子 | 代价 |
|---|---|---|
| **R2-a** | `new (r) T[n]` | 语法小扩（`new` 后面加一对括号）· 与现有 `new T[n]` 读起来同族 ✓ |
| **R2-b** | `r.alloc<T>(n)` | 方法 + 显式类型实参 —— 这条路今天不确定走不走得通 ✗ 要验 |
| **R2-c** | `alloc<T>(n) in r` | 新关键字 `in` ✗ |
| **R2-d** | 隐式"当前 region" | **不做** ✗ 隐藏状态正是 extC 明确不要的（`MODULES` 的语义导入、定案 79 的程序拥有，都是同一条口味）|

> **我的倾向**：**R2-a**（显式、可见、跟 `new` 同族）✓ 备选 R2-b，但要先验方法能不能带类型实参 ✓

### 3.3 【R3】指向 region 的引用，层是什么？

- **R3-a**：region 的层 = **创建它的块**那一层（阶段 1）⇒ 现有规则**原样够用** ✓
- **R3-b**：region 是一个**新的层种类**（动态层）⇒ 层比较从"整数比大小"变成"含 region 句柄的偏序"
  ⇒ 编码要扩（今天 `arenaLevel` 是 int，`ARENA_HOME = -1`）✗ 且直接动逃逸 pass ✗

> **我的倾向**：R1-a ⇒ R3-a（什么都不用扩）✓；R1-b 才需要 R3-b，那时**先出定案再动代码** ✓

### 3.4 【R4】`drop` / `reset` 怎么保证不悬垂？

| 选项 | 机制 | 取舍 |
|---|---|---|
| **R4-a affine** | `drop(r)` **消费掉** region 这个能力 ⇒ 之后任何经它派生的引用都编不过；`reset(r)` 不消费（region 还在，只是内容清空）⇒ 引用全部作废 ⇒ 也要检查 ✗ | 简单、可靠，跟 `close(f)` 消费句柄同一套 ✓✓ |
| **R4-b 全程序活跃引用分析** | 证明"此刻没有活引用" ⇒ 允许 drop | 精确但贵且脆 ✗ |
| **R4-c 不检查（靠纪律）** | 像 C++ 那样 | **会带 UB 回来** ✗ 直接违反 extC 的立身之本 ✓ |

> **我的倾向**：**R4-a** ✓ 并且 region 值**本身不可复制**（它是能力，不是数据 —— 跟文件句柄同一个道理）✓
> 未决：`reset` 要不要也走 affine（我倾向"要"：reset 之后旧引用一律作废，编译器必须拦）✓

### 3.5 【R5】何时归还？

- **R5-a**：`drop(r)` = `destroy`（块全还）· `reset(r)` = `release`（留一块复用）—— **映射到现有两个运行时函数** ✓✓
- **R5-b**：块退出时**自动** drop（若没被显式消费）✓
- **R5-c**：只有显式（不自动）✗ 写起来啰嗦，且忘了就漏 ✗

> **我的倾向**：**R5-a + R5-b 一起**（能早还就早还，没还的随块走）✓ 显式 drop 之后再 drop = 编译错误（跟消费语义一致）✓

## 4. 服务型程序会怎么写（两个 epoch + 长命对象）

```extc
while true {
    let req = accept()?                  // 连接在循环体的块里
    { ... 处理请求，随便分配 ... }         // ← 请求结束，整块还回去 ✓ 今天就能写（A 的量测）
    if hourChanged {
        cache.reset()                    // ← 跨请求的缓存按 epoch 清空并复用块（R1-b/R5-a）
    }
}
```
- **每请求**内存：块 ✓（今天就行）
- **跨请求**状态：region `reset`（要 R1-b）✓
- **长命对象**（连接、缓存条目、后台任务）：`uniq`（第二根轴）⇒ 谁持有谁 `drop` ✓

## 5. 它**不**解决的（别指望）

1. **epoch 内部的碎片**：一个 region 里反复 erase/insert ⇒ 仍然要 free-list / slot map /
   分块增长那套工程 ✓ region 只把"整批还"变成可能，不是 wc
2. **完全动态、说不出来的生命周期** ⇒ 出口只有 C 互操作（交给带 malloc/free 的库）✗
   或一个真 GC（会推翻"隐藏语义为零"与"过期字节确定"两根柱子 ⇒ 不建议）✓
3. **`new (r) T[n]` 的原地扩展**（把 B 的 2.4× 打到 D 的水平）是**补充**，不是替代 ✓
   它只在"那块还是块里最后一块"时有效 —— 所以它救不了服务型 ✓
