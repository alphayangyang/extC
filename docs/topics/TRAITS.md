# trait / dyn：设计定稿与第一期实施清单

> **状态：第一期已定案待实现**（2026-09-26 与作者逐条确认）。
> 第二、三期只在本文末尾记录范围，不在此实现。

## 一、已定的七条决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | 拼写 **`impl Codec for circle { … }`** | 与既有 `impl circle { … }`（固有方法）只差一个 `for` 子句；作者口径「rust 是对的」 |
| 2 | **`Self` = trait 的隐式类型参数** | 顺着"首字母大写 = 类型参数"的既有规则，复用泛型实例化与实例期检查；不引入新关键字 |
| 3 | trait **可声明关联函数**（无 `self`），但它们**永不动态分发** | object safety 的第一条，提前写死 |
| 4 | 第一期**禁止跨 trait 撞名**（两个 trait 在同一类型上声明同名方法 ⇒ 报错并指名两者） | 一个类型一份方法集（既有规则）；将来若做"精确匹配重载"可单向放宽 |
| 5 | trait 方法可见性 = **声明 trait 的模块被引入** | 沿用 `impl` 的既有规则（本会话落地：没 `use` 就没有这些方法） |
| 6 | 孤儿规则：**trait 与类型至少一个来自本程序** | 比 Rust 宽、比无规则稳；程序级方法集下冲突会编译报错 |
| 7 | 第一期**不允许**同一 `(trait, 类型)` 多次实现 | 规则一句话；将来放宽只影响查找规则 |

## 二、第一期的范围

**语法**：`trait Name { fn … }`（只有签名）· `impl Name for Type { … }` · 直接调用（静态分发）。
**六条检查**：实现齐全（缺哪几个列出来）· 签名逐项相符 · `(trait, 类型)` 唯一 · 与**固有方法**撞名 ·
跨 trait 撞名 · `Self` 越界使用（trait/impl 块之外出现即报错）。
**生成**：为每个 `(trait, 类型)` 发一张 **C 静态方法表**（槽位顺序 = **trait 声明顺序**，键 = mangled `trait$type`），
但**没有任何代码使用它** ⇒ 生成物里不应出现函数指针调用，性能与今天完全一致。
**明确不做**：`T: Trait` 上界 · `dyn Trait` 值 · 关联类型/常量 · trait 默认方法（会让 trait 体里第一次出现函数体）·
动态分发 · 运行期注册。

## 四之一、第一期剩余两项的实施锚点（2026-09-26 勘察结果）

### A. codegen 静态方法表 —— **已落地（2026-09-26，第五次尝试）**

**发在哪**：全部函数定义之后、`main` 之前（与其它静态数据同一区）。参照现成的原型发出点
`src/codegen.c:6131`：它已经解决了三件难事 —— 返回类型用 `cType(&g, f->ret)`、参数列表必须用
**同一个 `cgParamList`**（注释里写着：漏掉隐藏的 home 参数曾造成真实的 C 类型不匹配）、名字走同一个
mangling 助手。方法表只是把这三样再用于"字段类型 + 函数名"。

**发什么**（形状，`__attribute__((unused))` 是必需的，否则零告警守不住）：

```c
/* static method table: `Codec` for `circle` -- slot order = the trait's declaration order */
static const struct { int64_t(*tag)(circle *); } __attribute__((unused))
    extc_vt$Codec$circle = { circle$tag };
```

**槽位顺序**：严格按 `TraitDef.methods` 的顺序（声明顺序）。**不许**用哈希/字母序/插入序 ——
将来的动态链接会把这个顺序当 ABI，重排 trait 声明会静默改变它。

**键**：`trait$type`（trait 名不 mangle；类型名用既有的 mangled 名，例如 `stl$string`）。
本期**没有任何代码引用这些表**。

**两版都错在"位置"，但第二次才查到真根因（2026-09-26 第二次尝试后）**：

- 第一版写在"最终装配"之前，通过 `cgLine` 落到 `g.out` —— 那一刻它指向**会被按字节偏移拼接的旁路缓冲**，
  于是表文本落进了头部注释区；
- 第二版改为 `bufPuts(&g.body, …)`（追加到函数体缓冲的**末尾**，不改动任何已有 span）—— **仍然损坏**，
  且损坏形态与第一版**逐字节相同**。用"不含 trait 的最小程序"对照后确认：头部文本完好、二进制是新的
  ⇒ 损坏确实由表引起。真正机制是：**"未引用定义"趟（`dropUnreferenced`）按偏移与名字定位 span 并重写**，
  而表里**重复出现了方法名**（`box_zeta` 等）⇒ 它找到了错误的出现位置，把头部注释削掉。

**第三次尝试（2026-09-26）：顺序那一半成功，登记那一半还差一步**

已按下面的 1+2 实现并实测：
-  **表发在全部 `dropUnreferenced` 轮次之后**（`markUnusedParams` 之后、`return` 之前，直接 `bufPuts(out, …)`）
  ⇒ **头部注释完好**（前两次的"未闭合注释"消失），这是根因判断正确的直接证据；
-  但表里引用的方法**根本没被发出**（`box_zeta` 在生成物里只出现于表本身）⇒ 生成物 `-std=c11` 编不过
（`'box_zeta' undeclared`）。

**真因（第三种机制，逐层剥出来的）**：`g.funcs` 不是"模块的全部函数"，而是**可达性播种**的结果
（`src/codegen.c:5291`/`5320` 两处入列）。第一期的表**没有任何调用者**，所以那些方法既不入列、也就不会
被发出 —— 与死代码消除无关，是"从没被收录"。

**第四次尝试（2026-09-26）**：按上一条把"表引用的方法"加进**自由函数**那处播种过滤
（`if(!f->used && !cgIsMain(f) && !inTraitTable(m, f)) continue;`）—— 头部仍然完好，但方法**依旧**没被发出。
⇒ **播种过滤有两个点，我只改了一个**：`src/codegen.c` 里方法（`sd->methods`）与自由函数（`m->funcs`）
各自有一处 `!f->used` 过滤（前者的入列语句是 `*(FuncDef **)vecPush(&g.funcs) = md;`，约在 5291 行）。
**下一轮只需把同一条件加到方法那一处**（复用 `inTraitTable`，不要写第二份规则）。

**原来记的那一步（保留）**：在播种处把"**被某个(trait, 类型) 表引用的方法**"当作**根**
无条件入列（与"排除死代码候补"用同一个谓词 `inTraitTable`，仍然是一处规则）；
随后表自然指向已发出的函数，生成物即可编过。

**此前记的做法（保留，第 1、2 条已实现）**：
1. **不要**让 trait 实现的方法进入"未引用定义"候补：在原型发出点登记 `DeadFunc` 时跳过
   "属于某个 `(trait, 类型)` 表"的方法（表会引用它们，它们从来不是死代码）；
2. 表在**全部 `dropUnreferenced` 轮次之后**、直接 `bufPuts(out, …)` 追加到单元末尾（此时没有任何
   按偏移重写的趟会再跑），既不会干扰头部，也不会引用到已被删掉的函数；
3. 顺序仍严格按 `TraitDef.methods`。

**原先记的"这一版错在哪"（保留）**：表文本写得对（`__typeof__` + `unused` + 声明顺序），但**发出点**放在了
"最终装配"之前 —— 而 `g.out = out;` 是那段装配的**第一句**，在它之前往缓冲区写，内容会落进头部文本区，
生成物于是出现**未闭合注释**（`/* Every path that ends thh is`）并直接编不过。
**正确插入点：`g.out = out;` 之后**（装配完成再追加），或把表文本存起来在函数收尾处一次写出。

**这次的收获是判据**：下面那条"生成物必须在文档化合同下编译"的判据**当场抓到了它** —— 这正是它存在的理由。
回退后树是绿的；下一轮按上面的插入点重做即可。

**已确立的两处决定**：① 字段类型用 **`__typeof__(实现函数)`**，于是本代码不必对接收者、隐藏的
home 参数、任何 extC 类型的 C 拼写有意见（那些问题由原型发出点回答）；② 必须是**保留拼写**
`__typeof__` 而非 `typeof` —— 生成物的合同是 `-std=c11`，而 `typeof` 在严格模式下属 GNU 扩展被关掉，
本会话实测生成物直接编不过。

**判据（已实现）**：
1. `生成物里没有间接调用`：断言 vtable 符号在生成物里**只出现一次**（定义处），且生成物中不存在
   通过它调用的形式；再加一条"没有 `(*` 形式的调用语法"作为兜底；
2. `槽位顺序 = 声明顺序`：把 `trait` 的声明顺序倒过来再编译，生成物的字段顺序必须跟着倒过来
（这条判据能挡住"按字母序发"这类实现）。

### B. 撞名的专门诊断

今天两条撞名（trait 与**固有方法**同名、两个 trait 同名）都由既有的"一个类型一份方法集"重复检查
兜住，消息是 `` struct `box` has duplicate method `tag` ``，**不指名来源**。

实现锚点：在 `impl` 挂载趟里，方法入集**之前**先看 `sd->methods` 里有没有同名者；若有，再从
`m->impls` 里反查它是哪个 trait 声明的（或判定为固有方法），据此给出"两个 trait 都声明了 `tag`，
请改名或（将来）用 `Codec::tag(c)`"这类消息。

 **必须同时翻面**判据 `tests/impl/trait_collide_inherent.extc` 与 `trait_collide_cross.extc`
（它们现在断言的是通用消息）—— 这是本项目一贯的纪律：判据把行为焊死，改行为就要改判据。

## 五、两条相关但独立的记录

- **函数重载**：定位 = "把运算符那套**形状键**从右操作数推广到全部参数，**只认精确匹配**"。
  性质 = **单调**（新增重载只会让原本非法的调用变合法，不会改变已有绑定）⇒ **随时可加、无迁移成本**；
  代价 = 库命名可能留后缀（`hashI64` 是活证据）。**第一期不需要它**；若将来有了它，决策 4 可单向放宽为
  "签名不同即重载，签名相同才是重复定义"。
- **object safety**：第一期就要写下"哪些方法将来不能被动态分发"（泛型方法、返回 `Self` 的方法、无 `self` 的
  关联函数），否则第二期会遇到"这个 trait 用不了 dyn"的意外。
