# PLUGINS.md —— 插件/扩展：四档隔离与结论

> **状态：讨论归档（2026-09-27），暂缓实施。** 这份记录"运行期新增实现"这条路的设计空间、实测
> 数字与危险清单，结论是**先不做**。唯一已经落地的部分是第 1 档 —— 进程内选表，也就是
> `varArray<dyn Trait>` 注册表（见 [`DYN.md`](DYN.md) 与 [`DECISIONS.md`](../DECISIONS.md) ㉛ 的
> 2026-09-27 补记）。
>
> 触发条件写在 §7：出现"**不重新编译就要换实现**"的真实需求时再回来。

## 0. 一句话

**`dlopen` 不是"插件"，是延迟链接。** 加载完那一刻，那段代码就是你程序的一部分：你的保证覆盖它，
它的错误也覆盖你。所以分界是二元的 —— **要么它是你（编进去，或运行期链进来），要么它在另一个
进程里**。中间没有"只读不能写""信任一半"这种档（想在 in-process 拿到这种保证，现实里只有 WASM
那类线性内存沙箱，而那就不是 C ABI 了）。

## 1. 四档

| 档 | 能否运行期**新增**实现 | 隔离强度 | 代价 | 适用 |
|---|---|---|---|---|
| **① 进程内选表**（`varArray<dyn Trait>`）| ✗ 只能选编译期已知的 | **绝对**（没有外来代码）| 无 | 默认 |
| **② 同进程 + 宿主池 + 只走拷贝 + 沙箱分配** | ✓ | **纪律级**：内存全记账、可整体回收、接口内 sound；**不防恶意、不防崩** | 一个编译档（插件以宿主分配器运行）+ 一块邮箱 | 自己人写的，且省 IPC 有实际收益 |
| **③ 同进程裸 `dlopen`** | ✓ | **无**（就是延迟链接）| 运行期块 + `@export` | 不建议；`@export` 也已降级为"只服务这一档" |
| **④ 独立进程 + 行协议** | ✓ | 崩溃/内存隔离（**不是**权限隔离：插件仍拿你的 uid 跑）| 每次往返几微秒~几十微秒 | 不可信实现；也是唯一对"任意插件"成立的一档 |

因为 ③ 的收益全被 ② 覆盖、风险却大得多，**③ 事实上可以不做**；`@export`（让 extC 编出的 `.so`
有可被外部看到的符号）只服务 ③，因此也跟着推迟。**注意 ④ 不需要 `@export`** —— 插件是一个独立
可执行文件，用 `main(args)` 读协议，这在 extC 里今天就能写。

## 2. 术语

第 ② 档在文档里叫 **extension（扩展）**，不叫 plugin（插件）—— 名字一致了，就没人会误以为它有
隔离。第 ④ 档才配叫 plugin。

## 3. 实测数字（2026-09-27，本机；best of 5）

| 方式 | 往返耗时 |
|---|---|
| `socketpair`(AF_UNIX, STREAM) 64 B | 21.8 µs |
| `socketpair` 4 KB | 23.1 µs |
| 共享内存 + eventfd 通知 | 23.3 µs |
| 进程内直接调用 | 1.48 ns |
| 进程内间接调用（函数指针，≈ `dyn` 派发）| 1.62 ns |
| pipe 单向吞吐 | 1.36 GB/s |

两个反直觉但重要的观察：

1. **共享内存并不比 socketpair 快** ⇒ 这笔钱几乎全是**两次唤醒/上下文切换**，不是拷贝。
   想省掉它只能改成自旋轮询，那就开始烧核。
2. **载荷大小几乎不影响单次往返**（64 B 与 4 KB 差 1 µs）⇒ 固定底价。反过来**批量几乎线性摊薄**：
   一次往返塞 1000 个请求 ⇒ 摊到 **22 ns/个**（≈ `dyn` 派发的 14 倍）。

分界线：**≈ 4.5k 往返/秒 = 10% 一个核**（按上表的 22 µs）。

| 负载 | 每秒往返 | 占一个核 |
|---|---|---|
| 棋类/工具类"每次决策一次往返" | 10 | 0.02% ⇒ 免费 |
| 编译器前端问插件 | 1k | 2.2% |
| 每请求一次往返的服务 | 10k | 22% ⇒ 疼 |
| 同上 | 100k | 220% ⇒ 不可行 |

（裸机上往返通常 3–6 µs，分界线会宽几倍，但量级与结论不变。）

## 4. 第 ② 档的设计（若将来做）

1. **池由宿主拥有**：`extc_plugin_pool_create(limit)` → `poolId`；插件里所有分配（`new`、运行时内部
   的 `malloc`）都改成调用**宿主提供的符号**。卸载 = `pool reset` + drop ⇒ 一次全收、零泄漏。
2. **ABI 只走一个邮箱**：宿主把请求拷进双方约定的共享缓冲，告诉插件"输入是 `[0, n)`"；插件把结果
   写回同一块并返回长度 ⇒ **全程零指针**（就是 ④ 的行协议，只是换到共享内存上）。
3. **返回值一律夹紧**：长度/偏移对着邮箱大小检查（进程运行期里已经这么做）。
4. **世代句柄**：插件残留的任何句柄在卸载后立刻失效（池那套现成的）。
5. **trap 不许跨边界**：extC 的 trap 是 `fputs + exit(70)`（硬退整个进程）⇒ 插件必须编一个"边界
   模式"，把 trap 收敛成返回码，否则一次 trap 打死宿主。

抄自工业界的三条纪律：**谁分配谁释放** · **panic/trap 不许跨边界** · **不卸载**（`dlclose` 会让
悬垂的 vtable/函数指针留在宿主里）。

## 4.5 与 `DYN.md` 第三期 / §10 的关系

**机制那一半早就在 [`DYN.md`](DYN.md) 里设计好了**，本页补的是另一半：

- **DYN.md 负责"接缝"**：第三期 = **可注册的表 + 键→表注册表** · 接口文件 + ABI 版本握手 · 卸载墓碑。
  §10「为卸载/重载预留的接口（不做，但留门）」已经把三条不变量立住 —— ① 表指针只许出现在**槽**里
  （不进句柄/载荷/任何 ABI 可见布局）② 键是**稳定的 mangled 名**（`extc_vt$Trait$Type`，不依赖插入
  序）③ 有效性**只看槽/池世代**、不看"哪个模块装的" ⇒ 将来卸载只需两件事：**让某个模块的表整体
  作废**、**允许同一个键重新注册**，两者都**不动布局**。
- **现在就要守的约束**（DYN.md §9.5）：统一 struct 的**字段顺序 = 声明顺序** ⇒ 给 trait 加方法会改
  布局 ⇒ 开放注册必须"**追加式 + 版本号**"（与市面 ABI 同一条规矩，见 §6 的 `abi_stable`）。
- **作者口径**（DYN.md §10 引，2026-09-26）：「卸载其实可以做因为我感觉很 nb，但是依旧是不急，
  留出一些接口即可。」⇒ 本页的"暂缓"与这个"留门不出手"是**同一个决定**。
- **本页回答 DYN.md 没回答的问题**：运行期新增的表**从哪来**、每种来源**隔离强度如何** ⇒ §1 的四档
  （编译进来 / 同进程宿主池扩展 / 裸 dlopen / 独立进程）。一句话：**DYN.md 定义接缝，本页给插头与安全账。**

## 5. 为什么难（危险清单）

- **地址空间共享** ⇒ 插件能算地址、调 `mmap`/`sbrk`、直接写任意地址。`malloc` 拦截只约束**配合
  的代码**：这是纪律，不是保证。
- **`malloc` 符号插入是"全有或全无"**：宿主可以导出 `malloc` 接住插件的显式调用，但 **libc 内部**
  （`strdup`、stdio 缓冲、`dlopen` 自己）有自己的 `malloc` ⇒ 插件 `strdup` 的块被宿主 `free` ⇒ 崩。
  工业界的解法是"所有人都同意用同一个分配器"（UE 的 `FMemory`、CLAP 的 host `malloc/free`、
  Vulkan 的 `VkAllocationCallbacks`）。
- **崩溃无解**：段错误照样杀整个进程 ⇒ 只有 ④ 或 WASM 能挡。
- **两个运行期副本**：插件自带一份 extC 运行期（池表、zone）⇒ 跨界的"共享状态"必须重新定义；
  插件要自包含就得 `-fvisibility=hidden` + `-Wl,-Bsymbolic` 藏住自己的符号。
- **平台差异**：ELF 的 `visibility`/`--wrap` 与 Windows 的 `__declspec(dllexport)`/调用约定完全不同。

## 6. 业界怎么做（先例）

| 系统 | 做法 | 对本页的含义 |
|---|---|---|
| **CLAP** | host 结构体里带 `host->malloc/free`，跨界内存一律用宿主的 | 第 ② 档"宿主提供分配器"是标准做法 |
| **Vulkan** | `VkAllocationCallbacks` 由宿主提供 | 同上 |
| **UE / Unity** | 插件全走引擎自己的分配器（`FMemory`）| "全有或全无"的正面样板 |
| **`abi_stable`（Rust）** | `StableAbi` + `RBox`/`RVec`/`RString`：**值自带分配器 vtable** + 布局/版本检查 | 与本页第 ② 档同一个想法，人家做成了库 |
| **`cxx`（Rust↔C++）** | 生成 C 垫片 | = 我们"指针留在 C 的运行时块"那条 |
| **`libloading`** | `dlopen` 的薄封装；文档警告不要随便 `dlclose` | 印证"不卸载" |
| **WASM（wasmtime 等）** | 线性内存 ⇒ 插件命名不到宿主内存 | in-process 唯一的真沙箱；代价是放弃 C ABI |
| **`rustc` 的 proc macro** | **同进程 dlopen 的 dylib** | 反面教材：一个烂 proc macro 能带走 rustc |
| **GIMP / Chrome / VS Code / GStreamer** | 插件/扩展/站点/扫描器都独立进程 | 不可信代码的答案 |

Rust 在这件事上没有魔法：它**没有稳定 ABI**（`repr(Rust)` 布局不保证、`dyn Trait` 的 vtable 也不
稳定）⇒ 跨界只能用 `#[repr(C)]` + 不透明句柄 + 同编译器版本，生态只好自己造稳定 ABI。
**这一点上 extC 位置更好**：`dyn` 的 vtable 是编译期生成的静态表、留在宿主侧，插件只暴露扁平 C
函数 ⇒ 不需要 `abi_stable` 那套运行时布局校验。

## 7. 什么时候回来做

- 出现"**不重新编译就要换实现**"的真实需求（发布一个二进制宿主、让用户丢新实现进来）；
- 且该扩展在**热路径**上，④ 的往返成本超过 10% 一个核（≈4.5k 次/秒）；
- 且实现**由自己人写**（或者接受了"插件能改我内存"这个事实）。

三条同时成立才做 ②/③；否则 ①（自己人）与 ④（外部）已经覆盖全部场景。

## 8. 已经落地的部分

- **第 ① 档可用**：注册表就是一张 `varArray<dyn Trait>`；"谁坐哪个位子"是一张普通的数据表，
  换表 = 改那张表，实现与调用点一行不动。`dyn` 句柄是池底的 `{pool, slot, gen}`，取用前过世代
  校验，payload 在构造时**拷进池** ⇒ 注册表不依赖原对象的寿命。
- 已知边界（`dyn` 既有的）：trait 不能有泛型方法、不能返回 `Self` ⇒ 注册表当不了工厂，实现必须
  在调用点构造。
