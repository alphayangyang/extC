# IO-BENCH.md —— **IO 速度大横评**（2026-09-24）

> 主人要求：extC 流 · C++ `cin`/`cout`（C++14 与 latest）· Rust · Go · Java · C，**输入/输出、文件/控制台分开**量 ✓
> 一键复跑：`bash bench/io/run.sh`（数据生成用 `bench/io/gen.py`，**它不参与计时** ✓）

## 2.5 这一格是怎么从垫底变并列第一的（`PLAN #68` 的修法）

| | 优化前 | 优化后 |
|---|---|---|
| **③ stdout 输出** | 3407 ms（垫底 ✗） | **203 ms（与 Go 并列第一 ✓）** |
| **④ 文件输出** | 404 ms | **303 ms（与 C/Go 并列第一 ✓）** |
| **① stdin 输入** | 303 ms | **203 ms** |

**三处改动**（都在库/codegen，语言规则一条没动 ✓）：

1. **不再借内建 `print`**（那是"一条操作数一次 `printf`" ✗）：格式化搬进库，输出走
   **运行期持有的 256 KB 缓冲**（`extc_cout_put` / `extc_cout_flush` 由生成器提供 ✓
   定案 90），满了自己写出去，**尾巴由 `main` 返回前的一次 flush 收掉** ✓
   （`println` 已弃置 ⇒ 不再有"与 stdio 抢顺序"的问题，只剩"退出前别丢"一条 ✓）
2. **热点里不许出现视图下标** ✗：生成的 C 里 `slice_u8_index(...)` 是**一次函数调用**
   （还带文件名/行号），而一行输出 4 个操作数、每个数字十几次下标 ⇒ **上亿次调用** ✗
   ⇒ 热路径改写成**全程只碰定长数组**（`FMT: [24]u8` + 两位表 `PAIRS: [200]u8` ✓
   定长数组的下标是内联的小检查 ✓）
3. **两位一查表**（`"00"…"99"` 拼成的常量 ✓ 每次除 100 出两位 ✓）⇒ 除法次数减半 ✓
   并且**从后往前填**（不能"低位在前追加 + 最后整体反转"：那样**对内的顺序也会被翻**，
   `40` 会印成 `04` ✗ 这个 bug 真发生了 ✓）

## 2. 结论（按"该不该改"排）

1. ⭐ **extC 的输入流是能打的**：**303 ms**，与 Rust 并列第二梯队 ✓ 比 Go（403）快 1.3×，
   比 Java（603）快 2×，比**默认 C++ `cin`（1504）快 5×** ✓ 而内存只要 **7 MB**
   （Rust 那条路 114 MB、Java 247 MB ⇒ 流式在这两项上都赢 ✓）
   · **控制台与文件同速**（都是 303 ✓）⇒ 程序级流（`cin` / `fs::fin`）**没有**额外代价 ✓
2. ⭐ **extC 的文件输出是能打的**：**404 ms**，与 Rust（403）并排，比 C++（503）快 ✓
3. ✅ **`cout` 已修**（`PLAN #68` 当天修完）：**3407 → 203 ms，与 Go 并列第一** ✓
   修法与量到的证据见 §2.5 ✓ 而这条路也正是 `print` 退役那条线的实测理由
   （内建 `print` 每条操作数一次 `printf` ✗ 慢 16.8×）✓
4. **C++ 的结论正好回答主人的问法**：**C++14 与 C++ latest 一模一样**（1504 vs 1505、403 vs 403 ✓）
   ⇒ "版本"不是变量，**两个开关**才是：
   - `ios::sync_with_stdio(false)`：**1504 → 403（3.7×）** ✓
   - `"\n"` 换掉 `endl`：**1204 → 403（3×）** ✓（`endl` 每次都 flush ✗）
   两条加起来 = **11×**（1504 → 135 的理论上限，实测同场景 1204 → 403 ✓）
   ⚠️ 还有一条：`ifstream` 的 403 **不受 sync 开关影响**（那是 `cin` 与 stdio 的同步问题 ✓）
5. **Go 的输出最快**（202 ms，`strconv.AppendInt` 避免了 `fmt` 的反射 ✓）；
   **Java 在"启动之后"其实很快**（输入 ~500、输出 ~200 ✓），代价是 **+103 ms 启动**与**大内存** ✗
6. **Rust 的 `read_to_string` 是拿内存换速度**：303 ms / **114 MB**（整份文件进内存 ✓）
   —— 与 extC 的 303 ms / 7 MB 一比，就知道流式缓冲的价值 ✓
