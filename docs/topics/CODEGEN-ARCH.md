# CodeGen 是怎么工作的 / 按它的逻辑重构（2026-10-05）

> 目的：**先看清它自身的逻辑**，再谈重构（不是面向 bug 修）。
> 配套：`docs/reviews/CODEGEN-2026-10-05.md`（BG-1 与维护性四条）、
> `docs/reviews/COMPILER-AUDIT-2026-09-30.md` §0.2/§0.3（共性根因与四台手术）。

## 一、它的对外契约（这句话是全部设计的钥匙）

`src/back/codegen.h`：

> **"it infers no types of its own -- every decision it needs has already been written
> onto the tree by the checker."**

⇒ 代码生成**本该是一个投影**（把已决定的事实印成 C），**不该自己重新决定任何事**。
下面会看到，现在它恰恰在重新决定"什么该存在" ✗ —— 这就是要重构的那条缝。

## 二、入口与缓冲区（现状）

**入口只有一个**：`bool generateC(Ctx*, Arena*, TypeTable*, Module*, bool lineMap, Buf *out)`
（`codegen.c:6907`），**一个约 900 行的函数**（到 8815）把整份 C 源拼出来。
它之上是 ~5000 行的 `gen*` 助手（表达式/语句/声明/描述符）。

**它手里的缓冲区**（发射的"内存"）：

| 缓冲区 | 装什么 |
|---|---|
| `out` | 最终 C 文本（`body` 会被拼进来）|
| `body` | 函数体（单独写，之后再定位/删改）|
| `rt` | 通用运行时块 |
| `rtPrint` | 打印运行时（`extc_print` + 描述符表）|
| `rtCout` / `rtCoutF64` | 控制台快路径 |
| `primText` | 运行时**原语**（**保留为文本**，供 `dropRuntimeDefs` 扫描）|
| 另有 pool / http / dns 的运行时发射器 | 各自独立模块 |

**发射顺序**（`generateC` 内部）：函数类型 typedef → 描述符表骨架 → 函数体池 →
各运行时块（**按 15 个 `need*` 旗子逐个决定发不发**，8660–8670）→ 删除 pass。

## 三、真正决定"什么留下"的，是收尾那批 pass（≈600–700 行）

| pass | 位置 | 行数 | 它靠什么判断 |
|---|---|---|---|
| `dropUnreferenced` | 6519 | ~180 | 顶层定义：按**名字**在**整篇文本**里的提及数 |
| `dropUnusedLocals` | 6172 | **335** | 函数体内局部：按块级 span 计数 |
| `dropRuntimeDefs` | 5904 | **266** | 运行时原语：**行形识别**（行尾 `{`/`}`/`,` + 含 `(`，首字符不是空格 `/` `#` `*`）+ 大括号配对量 span + 宏的 guard/define 覆盖 |
| `dropUnreferenced`（函数段） | ~6556 | — | `countGet(name) != 2`（"原型 + 定义，别无提及"）|
| 共用工具 | 5820–6520 | ~90+ | `NameCount` 哈希表、`countMentions` / `countMentionsIn` / `countSpan` |

**关键事实：活跃性是"文本里这个名字出现几次"** —— 定义边界靠**行形状**，块归属靠
**写进了哪个缓冲区 + 哪个旗子**。于是：

* 注释里写一个名字 = 一次"使用" ✗（BG-1 的加重细节，已修）；
* 发射端与删除端**各自知道"一个定义长什么样"** ✗（改一边不报错）；
* 一个旗子管两个需求不同的块 ✗（BG-1 的根因）；
* 每砍一次就**重扫整篇**（两处 `for(;;)` + `!cut ⇒ break`）✗（曾烧 15 分钟无诊断）。

## 四、按它自己的逻辑，重构应该长成三层

契约说"代码生成不做决定" ⇒ 那么：

### L1 决定（发射之前）：**需求闭包（needs set）**

从入口（`main`、`@export`、模块 init）出发做一次可达性，产出一个**需求集合**：
哪些函数、哪些泛型实例、哪些描述符、哪些运行时**原语**、以及哪些运行时**块**。

* 15 个 `need*` 旗子**全部退休** —— 块的需求 = "这个块里有片段在需求集合里"；
* 函数/描述符的存活也在这里决定 ⇒ 那批**计数 pass 全部不需要**；
* 事实来源：`plan`/AST（`NodeResults.used` 之类的既有事实 ✓），**不是文本**。

### L2 发射（纯投影）：**每个实体就地登记**

发射时把 `{name, kind, block, 起始偏移}` 记进一张**输出符号表**：

* 删除端**不再从行形猜**（行形规则、brace 配对、anchor 技巧全删）✗✗；
* "发射端 vs 删除端"的双份知识**收成一份**（审计 §0.2-3 / R2 ✓）。

### L3 装配：块按固定顺序拼接；删除 pass 退成**断言**（或删除）

到这一步，"该发什么"已经在 L1 定了，L3 只做拼接与自检 ✓。

## 五、迁移路线（每步都可用 414 份产物指纹度量）

| 步 | 内容 | 预期产物变化 | 消掉 |
|---|---|---|---|
| **S1** | 引入**登记 API**（`rtPiece(name, kind, span)`），让 `dropRuntimeDefs` **用登记信息**而不是行形；块级门控改为"本块有无被引用的片段" | **应当为零**（纯重构 ⇒ 指纹一致 ✓）| 双份知识、参数化门控 |
| **S2** | 引入 **needs set** 取代 15 个旗子 | 只在旗子**判错**的产物上变化（BG-1 那类 ✓）| 粗旗子 |
| **S3** | 函数/描述符/局部 的存活也进 needs set ⇒ **删掉计数机制** | 应当极小（只修掉历史误判）| ①②③④全部 |

**度量方式**：每步前后对 `tools/golden.sha256` 的 414 份产物逐个编译+哈希
（`/tmp/leadchk/fp-before.sha256` 是今天的基准 ✓）⇒ **"这一步到底改了什么"是数据** ✓。
判据/闸门只当**安全网**，不作为质量依据 ✓。

## 六、边界（明确不做）

* 不动 **C 发射层**（表达式/语句/描述符的印法）—— 它是好的（可读、确定性、双编译器 `-Werror` 干净 ✓）；
* 不动 `needRuntime` 这类旗子的**语义**去"精确化"（注释写明漏发=生成物坏掉 ✗）—— 是**替换机制**，不是调参；
* BG-1 的那个 `__attribute__((unused))` 在 **S2 完成后**删掉（它存在的唯一理由就是那面粗旗子）。

# 附：质疑这套逻辑本身（2026-10-05，用户要求"可以质疑"）

上面的 L1/L2/L3 仍然**接受了现状的前提**（先全发、再决定谁留）。这里逐条质疑前提。

## Q1（最深）"先全发再删"——为什么会有"死代码"这个问题？

编译器后端**本来是走着程序发射的**：谁被引用就发谁。只有在"发射到一半才发现需要某样东西"
（泛型实例、描述符、运行时原语、库函数）时，才需要"补发"。于是设计上只有两条路：

* **按需发射（pull/worklist）**：从入口出发，遇到引用就补发 ⇒ **死代码根本不会产生** ✓✓
* **先全发再删（push + GC）**：现在这条 ✗ —— 它把"补发"的懒惰性换成了"事后判定谁没用"的负担，
  而判定的依据只能是**输出文本**（因为没有别的 IR）✗

**结论**：那 ~600–700 行删除逻辑，是"先全发"这个选择的**账单** ✓ 不是必需品。

## Q2 为什么必须是"一个 TU、全是 static"？

这个选择**逼我们自己重写链接器** ✗ —— 而工具链里那个是免费的、精确的：

```sh
gcc -ffunction-sections -fdata-sections -Wl,--gc-sections ...
```

一个 TU 里 `-ffunction-sections` 同样给**每个函数**一个 section ⇒ 未被引用的 static 函数/数据
会被**链接器**丢掉 ✓ 正确性由 binutils 保证，不需要"数标识符 + 行形识别 + 大括号配对" ✗。
**（这可以直接测：见下面的实验 E1。）**

## Q3 运行时为什么是**字符串字面量**？

`rt`/`rtPrint`/`rtCout`/`primText` 是嵌在 `codegen.c` 里的 C 源码文本 ✗ ⇒ 三重代价：
① 只有某个程序用到它时才发现语法/警告 ✗；② "一个定义长什么样"的知识**被迫复制**一份给删除端 ✗；
③ 无法单独编译测试 ✗。若它们是真 C 文件（或 `#include` 的 support TU）⇒ ①②③ 同时消失 ✓，
`need*` 旗子也失去存在理由 ✓。

## Q4 codegen 凭什么"决定"？（它自己的契约说它不做决定）

`needRuntime` / `needCout` / `needPool` / `needDns` / `eqNeed` **是程序的事实**，属于**分析（plan）** ✓
而它们在**发射过程中被顺带置位** ✗ ⇒ 结果**依赖发射顺序**，而且契约（"every decision ... has already
been written onto the tree"）**被自己违反** ✗。两条都行，**现在这条（边发射边决定 + 事后猜）最差**：
(a) 把决定上移到 plan ✓ 或 (b) 承认 codegen 是决策点、做成**正经的按需引擎** ✓。

## Q5 粒度错了

"这个程序要不要 http / dns / pool / 打印运行时"是**模块级**事实 ✓，却用**符号级文本计数**去救 ✗。
模块级可达性（模块依赖图）便宜、精确、且**在 plan 里就能算** ✓ —— 这正是审计 §0.3 里 R13
"**粒度建模错**"的同一种形状 ✓。

## Q6 为什么没有显式 IR？

因为**半成品 C 文本就是 IR** ✗ ⇒ 于是到处都是 `span` / `offset` / `anchor`（缓冲区的第一行）/
`bodyOff` ✗。标准形状是一张小表：`CEntity { kind, name, deps, text }` + 若干 pass ✓ 可单测、可重排 ✓。

## Q7 一个 900 行的编排函数

`generateC` 里 typedef → 描述符骨架 → 函数体池 → 块 → 删除 pass 全在一个函数 ✗ ⇒
没有相位边界、不能单独测 ✓（而且它是"顺序敏感 bug"的温床 ✗）。

## 保留的前提（也要说清）

**单文件输出**（一个 `.c`，无构建系统、无运行库版本错配）对"2 核小机器上部署"是**真价值** ✓ ——
如果它是硬要求，那么 Q2 的工具链 DCE 只能省**二进制**、省不了**源文本** ✓ ⇒ 这时正解是
**Q1 的按需发射**（源文本里根本没有死代码）✓✓。

## 实验 E1（今天就能做，纯测量）

对 414 份产物各做两件事，比较**二进制大小**与**源文本大小**：

| 量 | 做法 |
|---|---|
| A：今天的样子（文本已删）| `extc x.extc -o a.c && gcc -O2 a.c` → 记 `size a.out`、`wc -c a.c` |
| B：不删，交给工具链 | 关掉文本删除（或拿"未删版本"）⇒ `gcc -O2 -ffunction-sections -fdata-sections -Wl,--gc-sections` → 同两个量 |

若 `size(B) ≈ size(A)` ⇒ **文本删除对二进制毫无贡献**（只影响源文本外观 ✓）⇒ Q1/Q2 直接成立，
那 ~600–700 行可以整体退场 ✓。这一步是**数据**，不是判据 ✓。

# 附二：重构的**三条前提与验收标准**（2026-10-05，用户拍板）

1. **编译到 C：保留** ✓（不动这个方向）；
2. **多文件输出：可以接受，而且期待** ✓ ⇒ "一个 TU、全 static"**不是**硬要求；
3. **生成的 C 里不能有死代码** ✓ —— 理由是**编译期压力**：`-ffunction-sections` +
   `--gc-sections` 只省**链接期**，**gcc 在 -O2 下照样把每个死函数解析/优化/发射一遍** ✗
   ⇒ 工具链 DCE **不够**，必须在**发射之前**决定谁存在 ✓✓。

## 由此确定的目标架构（不再讨论"要不要"，只讨论"怎么切"）

| 要素 | 现状 | 目标 |
|---|---|---|
| 谁存在 | 先全发 + 事后按文本删（≈600–700 行）✗ | **按需发射（worklist）**：从入口出发，引用谁发谁 ⇒ **死代码不可能产生** ✓ |
| 文件数 | 一个 TU ✗（逼我们重写链接器）| **多文件** ✓：模块/区域分 TU ⇒ 2 核可并行编译 ✓ |
| 运行时 | 字符串字面量，**每份产物重编一遍** ✗ | **独立 C 文件/TU**（可预编译复用 ✓）⇒ 旗子失去理由 ✓ |
| 决定时机 | 发射过程中顺带置位 ✗（顺序敏感，违反自己的契约）| 决定在 **plan**（或发射前的需求闭包）✓ |
| 中间表示 | 半成品 C 文本 ✗（span/offset/anchor 满地）| `CEntity{kind,name,deps,text}` 小表 + pass ✓ |
