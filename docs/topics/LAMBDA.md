# lambda 方案（v2）

> **一句话**：lambda 是**一个唯一的编译期身份**（生成的捕获结构体）+ **直接调用**；
> 传参走**单态化**；**可写的捕获必须显式写出来**；而"运行期注册"这条路**不靠 lambda 也不被它挡** ——
> 它已经由 **`pool<dyn Trait>`** 提供了（实测可用）。

## 0. 本次修订相对 v1 的两处变化

| | v1（已作废）| **v2（本方案）** |
|---|---|---|
| 语法 | A/B 待拍板 | **B 锁定**：`fn(x: i64) -> i64 { … }`（复用 `fn`，零新符号）|
| 运行期注册 | 当作"永久不做"的前提 ⇒ 设计被限制成"不能异构存储" | **前提作废** ✗：SPEC 那句已过时 —— 有 Pool 之后**运行期注册已经有了**（见 §5，实测 `pool<dyn Tag>` 可 insert/get/派发）|
| 捕获 | 推荐"按值 + 要写就捕 `mut ref`" | **决策落地**：读 ⇒ 按值捕获（不写）；**写 ⇒ 必须在捕获列表里显式写出**（§4）|

## 1. 为什么这样设计（三条，都来自决策）

1. **身份编译期唯一**：每个 lambda 一个**生成的唯一类型**（捕获结构体 + 一个 `call` 方法）
   ⇒ 调用是**直接调用**，可内联，没有间接调用表；
2. **单态化传参**：把闭包传给函数走**泛型参数**（`fn each<T, F>(v: []T, f: F)`）⇒ 每个闭包类型
   实例化一份 ⇒ 依然是直接调用；
3. **可写捕获显式**：这条把"谁能被改写"摆在源码上（和 extC"转换要写出来""引用不是值"同一口味）。

## 2. 语法（B）

```extc
/* 无捕获 */
var twice = fn(x: i64) -> i64 { return x * i64(2) }

/* 读外层变量：按值捕获，不写任何东西（捕获是拷贝 ⇒ 与"值位置自动解引用拿到拷贝"一致） */
var base: i64 = 100
var addBase = fn(x: i64) -> i64 { return x + base }

/* 要**写**外层变量：必须在捕获列表里显式写 `mut ref` */
var hits: i64 = 0
var count = fn(x: i64) [mut ref hits] -> i64 {
    hits = hits + 1
    return x
}

/* 返回类型可省（与具名函数同一套推导）；无参写 fn() */
var zero = fn() -> i64 { return 0 }
```

> **待确认的一件小事**：捕获列表用方括号 `[mut ref hits]`（本方案默认）。
> 备选是 `mut(ref hits)` 或 `capture(mut ref hits)`；符号不影响任何机制，只影响观感。

## 3. 类型与变换：零新运行时

```
fn(x: i64) -> i64 { return x + base }        /* 在函数 f 里，base 是 f 的局部 */
  ⇒  struct $lam$f$3 { base: i64 }                                   /* 捕获环境 = 结构体 */
     impl $lam$f$3 { fn call(self: ref $lam$f$3, x: i64) -> i64 { return x + self.base } }
     表达式处 ⇒ $lam$f$3 { base: base }
```

* `let f = fn(…)` ⇒ `f` 的类型就是这个结构体（**用户不用写**，诊断里显示成 `fn(i64) -> i64`）；
* `f(1)` ⇒ `f.call(1)` ⇒ 直接调用；
* **v1 不引入可写的函数类型**（`fn(T)->R` 不作类型写）：一旦可写，就要回答"两个不同闭包怎么统一"
  ⇒ 那正是 §5 的场景，交给 `pool<dyn Trait>`，不要用函数类型。
  （实测：`var f: fn(i64) -> i64 = …` 今天报 `expected a type, found 'fn'` ⇒ 与决策一致，保持不引入。）

## 4. 捕获规则（决策落地）

| 情形 | 规则 | 生成物 |
|---|---|---|
| body **只读**外层变量 | **按值捕获**（拷贝进结构体），源码里**不写任何东西** | 字段 `base: i64` |
| body **写**外层变量 | **必须显式**：`[mut ref hits]` | 字段 `hits: mut ref i64` |
| 捕获 `ref T` 的值（只读） | 按值捕获那个引用（= 拷贝引用，仍受逃逸规则约束）| 字段 `r: ref T` |
| 未提及的外层变量 | **不捕获** | 无字段 |

**生命周期不新增任何概念** ✓：捕获结构体就是一个普通值 —— 里面装了 `ref`/`mut ref`，就照旧受
现有**逃逸/arena 检查**约束（`ARENA-FORMAL.md`）。于是：

* `return` 一个捕了本函数局部的闭包 ⇒ **现有规则直接拒**（不用新代码）；
* 捕了跨块的 arena 值 ⇒ 层号/提权规则照旧。

**这就是"可写捕获必须显式"的第二个好处**：**可写别名在源码上永远可见** —— 逃逸分析、提权
（§2.7′ 的 `__extc_home`）与"谁在改写这个变量"三件事都能直接读源码确认。

## 5. 运行期注册：**已经有了，用 Pool**（不是 lambda 的活）

SPEC 里"开集/运行期注册 ⛔ 永久不做（需要间接调用）"这句**已经过时** ✗：有了 `Pool`
（稳定句柄 `(slot, gen)` + 世代校验），**异构表是安全的**，而且今天就能用。实测：

```extc
use stl::pool
trait Tag { fn tag(self: ref Self) -> i64 }
struct a { v: i64 }   impl Tag for a { fn tag(self: ref a) -> i64 { return self.v } }

var p = pool<dyn Tag>::withCap(4)
let h = p.insert(dyn Tag(a { v: 9 }))
io::cout << (p.get(h) ?? dyn Tag(a { v: 0 })).tag() << "\n"     /* 实测输出 9 ✓ */
```

⇒ **两条路分工清楚**，谁也不挡谁：

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 编译期已知的"函数值"（`map`/`filter`/`each` 的实参）| **lambda + 单态化** | 直接调用、可内联、零运行期 |
| **运行期注册**的处理器 / 回调表 / 插件式扩展 | **`pool<dyn Trait>`** | 稳定句柄 + 世代校验 ⇒ 删了/换了旧句柄必失效；这正是 Pool 的分内事 |
| 闭集分派（事件/状态/命令/AST）| `match` + 枚举 | 穷尽检查，且无间接调用 |

**一条实测限制**（方案要如实写）：trait **今天不能带类型参数**（`trait Fn1<A, R>` 报
`expected '{', found '<'`）⇒ 回调表要为**每种签名**定义一个具体 trait
（如 `trait CallI64I64 { fn call(self: ref Self, a: i64) -> i64 }`），
或在 prelude 里提供一小族常用签名的 trait。**这与 lambda 无关**，是独立的一格。

## 6. 实现步骤（每步都以 **414 个生成 C 逐字节不变**为闸门）

lambda 是**纯增量**：现有语料一个 lambda 都没有 ⇒ 正确的实现不该改变任何现有输出。

| # | 做什么 | 判据 | 状态 |
|---|---|---|---|
| 1 | **解析**：表达式位置接受 `fn`（形参 + 可选返回 + 语句体 + 可选捕获列表）⇒ `EX_LAMBDA` | 新语法能过解析；现有文件输出不变 | **已落地** `3cf970e` |
| 2 | **检查**：按用收集捕获；生成唯一类型（结构体 + `call` 方法）；`[mut ref x]` 校验"确实被写、且可写" | 静态错误集合写进 `tests/lambda/` | **已落地** `838ee83` |
| 3 | **逃逸**：把捕获结构体当普通值送进**现有** pass（不新增规则）| 返回捕本帧局部的闭包 ⇒ **被拒** | **不需要新代码**：闭包的**类型不可命名** ⇒ 值只能活在写它的作用域里，既不能声明也不能返回 ⇒ 捕获的引用逃逸整类问题写不出来（见 §7）|
| 4 | **代码生成**：发射结构体 + `call` 方法 + 环境构造表达式；`f(x)` ⇒ `f.call(x)` | 生成物 `-Wall -Wextra -Werror` 零告警 | **已落地**（随第 2 步）|
| 5 | **套件** `tests/lambda/` | 挂进 `check.sh` | **已落地**：10 正例 + 8 反例 |

**实现顺序就是设计**（第 2 步的注释里也写着，这里给结论）：

1. 体**在原地检查**，作用域里放着闭包的形参 ⇒ 体内的名字走常规解析，**遮蔽自然正确**（只按名字做的
   预扫描会把 `var base` 遮蔽外层 `base` 判错）；
2. 体引用到的**外层绑定**就是捕获集：从**已经解析好的 `Sym`** 上读，不猜文本；
3. 每个捕获是合成结构体的一个字段：按值（拷贝 ⇒ 闭包看到建立它时的值），`mut ref x` 的是指到外层
   变量本身的引用；字段名用 `c0/c1…`（下标命名，因为两个捕获可能同名）；
4. 体成为该结构体的 `call` 方法，捕获名发射成 `self.c<i>`（可写的是 `(*self.c<i>)`，同时是读和写的
   左值）——这一步不需要改 AST，codegen 用 `cname` 打印标识符，改写就是给 `cname` 赋值；
5. `f(x)`（`f` 持有闭包）在调用点**就地**改写成 `f.call(x)`，与 EX_CALL 里"构造枚举变体"那一支同构。

路上踩到并修掉的两处（都是实测逼出来的，值得记）：

* 合成方法必须走 **`resolveSignature`**，否则形参类型还是解析器的原始节点 ⇒ 连 `i64 + i64` 都报
  "cannot apply `+` to `i64` and `i64`"；
* `call` 方法被 `checkFunc` 跳过（体已经检查过），于是"声明了返回类型却没有 `return`"这条检查也得
  在这里补，否则生成的 C 从非 void 函数的末尾掉出去。

**走查器的语义（给后来人）**：闭包的体归 `call` 方法自己的按函数分析，**不归外层函数**；外层函数
透过闭包节点只该看到**环境字段值那几次读**。所以每个表达式走查器对 `EX_LAMBDA` 的处理就是"当作一串
字段值来走"，与它处理 `EX_STRUCTLIT` 一样——把体也算进外层函数是错的（"只是建了个闭包"的函数不该被
认为会打印、会分配）。

## 7. v1 明确不做

* **可写的函数类型** `fn(T)->R`（§3）· 函数指针 · `dyn` 闭包（异构走 §5 的 Pool）；
* 显式捕获列表之外的其它捕获语法（`move`、按引用只读捕获等）；
* 闭包与 `@overwrite` / 跨模块身份的交互（今天没有用例）；
* 参数化 trait（§5 末的独立一格，不属于 lambda 方案）。

**落地时明确划出的边界**（每一条都报清楚的话，不静默）：

| 边界 | 为什么 | 症状 |
|---|---|---|
| **闭包套闭包** | 内层的环境要嵌进外层环境里，布局与提升规则都还没定 | 编译期拒：`a lambda inside a lambda is not supported yet` |
| **体内 `new`** | 闭包在哪儿被调用还没定 ⇒ 那次分配属于哪只 arena 不明 | 编译期拒：`a lambda body may not allocate yet` |
| **把闭包传给泛型函数** | 模板检查期实参类型还是类型参数 ⇒ `f(x)` 解析不到 `call` 方法（实例化时才会定） | 报 `call to undefined function` —— 要支持得先给"参数必须带 call 方法"一个写法（trait 约束那一格）|
| **返回闭包 / 声明闭包变量** | 类型是生成的、**源码里写不出来** | 类型错误；顺带把"捕获的引用逃逸"整类问题挡在门外（第 3 步因此不需要新代码）|

## 8. 与协程的关系（顺带收益）

`CONCURRENCY.md` §4 第 3 步就是它；而 §4 第 4 步（`coroutine<A,B>`）的形状也能借此说清：
**协程的请求类型 ≈ "往协程里送值"**，而实测 `send` 方法**已经存在**（方法集 `next value send`），
缺的只是**带类型的请求参数** —— 这件事与 lambda 共用同一套"环境显式化成结构体"的变换。

> **状态（2026-09-28 核实）：`coroutine<A,B>` 还没做。** 具体卡在哪，查源码就能说清：
> prelude 里是 `struct coroutine<T> { unit: bool }`（**一个**类型参数），而 `check_top.c` 合成
> 协议方法时 `next`/`value`/`send` **都用那唯一的 `T`** —— 于是今天的 `send` 送进去的类型和
> `yield` 出来的类型是同一个。要做的是：prelude 改成两个参数，`send` 取请求类型、`value` 取应答
> 类型，帧里放得下挂起时的那个请求。**这不是 lambda 的前置条件**（lambda 已经落地），但它是
> "worker 当协程 + `send`/父线程 resume"那条线的前置条件。

另外顺带纠正 `CONCURRENCY.md` §4.4 的一处过时示例：**`for x in c` 今天不行** ✗
（检查器要 `iter` 方法），实际驱动是 `while c.next() { … c.value() … }`。
