# lambda —— 设计稿

> **一句话**：lambda = **一个唯一的编译期身份** + 一个**捕获环境结构体** + 一个**直接调用**。
> 它与状态机变换（`coroutine<T>`）、与闭包变换是**同一个变换**（`CONCURRENCY.md` §4 第 3 步原话），
> 所以先做它，第 4 步 `coroutine<A,B>` 的形状会顺很多。

## 1. 为什么只能是这个样子（原则先行）

`SPEC.md` §7 把口子收死了：

> | **开集**：运行期注册插件 / 热替换 / 用户自定义回调 | ⛔ **永久不做**（需要间接调用）|
> 换来的是「**每个调用在哪都能静态找到**」。

所以 lambda 的设计空间**不是自由的**，三条推论：

1. **每个 lambda 有唯一的编译期身份** ✓（`SPEC.md:701` 的原话："传 / `let` 存 / 捕获，身份编译期唯一"）
   ⇒ 它的类型是**编译器生成的唯一具体类型**，不是函数指针、不是 `void*` + 转换；
2. **调用是直接调用** ✓（`f(1)` ⇒ `f.call(1)`，单态化后就是普通方法调用）⇒ 不引入间接调用，
   P 不破；
3. **异构存放不做** ✗：`var fs: [3]fn(i64)->i64 = [f, g, h]`、回调注册表、运行期插插件
   —— 全部落进上面那格"永久不做"。想做闭集分派就用 `match` + 枚举（项目已有，且**更好**：
   穷尽检查 + 无间接调用）。

**这不是"少了什么"，而是换来的东西**：没有函数指针 ⇒ 没有"这个调用到底去了哪"的未知，
逃逸/arena 那套分析才能对**每一个调用点**都成立。

## 2. 语法：两个候选，推荐 (B)

| | 形态 | 好处 | 代价 |
|---|---|---|---|
| **(A)** | `var f = \|x: i64\| x + 1` | 熟悉（Rust / Swift）；紧凑 | 新语义的 `\|`：`\|` 在本语言里**已经有两种身份** —— 枚举声明（`type c = \| red \| green`）与按位或（`a \| b`）；空参写成 `\|\|` 还要再和逻辑或区分；**闭包的 `\|` 必须是"表达式起始位置的 `\|`"**，规则能写清但要额外解释 |
| **(B) 推荐** | `var f = fn(x: i64) -> i64 { return x + n }` | **零新符号**：复用已有 `fn` 的形参/返回/函数体语法，闭包体长得和具名函数**逐字一样**；与 `type c = \| red`、`a \| b` 都不冲突；符合本项目"少两个概念"的口味（`CONCURRENCY.md` §4.4 拒绝 `spawn`/`resume` 关键字就是同一口味） | 关键字 `fn` 在表达式位置出现，解析器要多一条入口（局部、可控） |

**推荐 (B)**，理由就是上表最后两列：**不新增符号**，且闭包体与具名函数同形
⇒ 读代码的人不需要学第二套函数语法。今天实测 `fn(x: i64) -> i64 { … }` 在表达式位置报
`expected an expression, found 'fn'`，正是"解析器还没这条入口"，不是设计上的冲突。

**返回类型可省**：`fn(x: i64) { return x + 1 }` ⇒ 由 `return` 推出（与具名函数同一套推导）。
**无参**：`fn() { … }`。

## 3. 类型：唯一具体类型（用户不可命名）

一个 lambda 的类型是编译器生成的结构体，**名字不出现在语言里**（诊断里显示成 `fn(i64) -> i64`）：

```
fn(x: i64) -> i64 { return x + n }        // 在函数 f 里，n 是 f 的局部
   ⇒  struct $lam$f$3 { n: i64 }                              // 捕获环境 = 显式结构体
      impl $lam$f$3 { fn call(self: ref $lam$f$3, x: i64) -> i64 { return x + self.n } }
      表达式求值 ⇒ $lam$f$3 { n: n }
```

* `let f = fn(…)` ⇒ `f` 的类型就是这个结构体（**编译器知道，用户不用写**）；
* `f(1)` ⇒ `f.call(1)` ⇒ **直接调用**，可内联，零间接；
* 诊断里打印成 `fn(i64) -> i64`，不暴露 `$lam$…`（它是实现细节）。

**因此 v1 不引入"函数类型"**（`fn(T)->R` 不作类型写）✗：一旦它成为可写类型，就要回答
"两个不同的闭包怎么统一" ⇒ 只能靠间接调用 ⇒ 与 §1 冲突。

## 4. 怎么"传"：泛型实参（单态化）

```extc
fn each<T>(v: []T, f: $$closure) -> i64 { … }        // ← 这里需要一个"任意闭包"的写法
```

v1 的答案是**泛型参数**：

```extc
fn each<T, F>(v: []T, f: F) -> i64 { … f(v[0]) … }   // F 被每个闭包类型各实例化一次
each(xs, fn(x: i64) -> i64 { return x + 1 })         // 单态化 ⇒ 直接调用
```

* 这正是 `SPEC.md` 说的"**身份编译期唯一**"：每个调用点实例化一份 ⇒ 无间接、可内联；
* 代价：**代码体积**（每个闭包类型一份 `each`）——与泛型其它用法同一代价，项目已经接受；
* **不做**：`dyn` 闭包、`fn` 类型参数以外的"存进异构容器"。

## 5. 捕获：按用捕获，生命周期交给**已有**的逃逸/arena 规则

* **按用捕获**（body 里提到谁就捕谁，最小集），不要求写捕获列表 —— 少一个概念；
* **默认按值进捕获结构体**（`struct $lam { n: i64 }`）⇒ 与"值拷贝"语义一致；
* **body 需要写它** ⇒ 捕 `mut ref`（`struct $lam { n: mut ref i64 }`）；
* **arena / 逃逸不新增规则** ✓：捕获结构体就是一个普通值，**值里带了 `mut ref`/低层 `ref`
  就照旧受 §4 的逃逸检查约束** ⇒
  * `let f = fn(…) { … }` 后 `return f` 而 `f` 捕了本函数的局部 ⇒ **现有逃逸检查直接拒**（无需新代码）；
  * 捕了跨块的 arena 值 ⇒ 层号规则照旧 ⇒ 该拒的拒。
  这是这个设计最省事的地方：**lambda 不引入新的生命周期概念，只是把捕获显式化成结构体**。

## 6. 和其它机制的关系

| 机制 | 关系 |
|---|---|
| `coroutine<T>`（已落地） | 同一个变换（环境显式化成结构体）⇒ lambda 做完，`coroutine<A,B>` 第 4 步好定 |
| `for x in c` / 迭代器协议 | 闭包作为泛型实参传给迭代器族函数，v1 的"传"路径就通了 |
| `@poolObject` / `@sharesStorage` | 捕获结构体里含池对象 ⇒ 拷贝语义照旧（警告照旧），不搞特殊 |
| `match` / 枚举 | **闭集分派继续用 `match`**（本项目立场），lambda 不抢它的活 |
| `dyn` | v1 **不**给闭包做 `dyn`；需要异构时说明设计想错了（回到 §1）|

## 7. 实现步骤（每一步都以"413 个生成 C 逐字节不变"为闸门）

lambda 是**纯增量**：现有语料一个 lambda 都没有 ⇒ 正确的实现**不应该改变任何一个现有输出**
（这正是最好的验收：`/tmp/refC/MANIFEST.txt` 413 文件全等）。

1. **解析**：表达式位置接受 `fn` ⇒ 新增 `EX_LAMBDA`（形参表 + 可选返回类型 + 语句体）；
2. **检查**：
   * 收集捕获（按用）⇒ 每个 lambda 生成唯一类型（结构体 + `call` 方法）；
   * 泛型实参位置把闭包类型当普通类型参与单态化；
   * **逃逸/arena 复用现有 pass**（把捕获结构体当普通值送进去）；
3. **代码生成**：发射结构体 + `impl` + 构造表达式 + `f(x)` ⇒ `f.call(x)`；
4. **验收**：新套件 `tests/lambda/` —— 无捕获 · 按值捕获 · `mut` 捕获（写回可见）· 作为泛型实参 ·
   **返回闭包捕获局部 ⇒ 必须被拒**（逃生反例）· 与 `for` 组合 · 与协程组合；
   `check.sh` 新起一节；全程 `-Wall -Wextra -Werror` 零告警。

## 8. v1 明确不做

* `fn(T) -> R` 作为**可写类型**（§3）；函数指针；`dyn` 闭包；
* 异构闭包容器 / 运行期回调注册 / 插件（= `SPEC.md` §7 那格"永久不做"）；
* 捕获列表语法（`[move n]` 之类）——按用捕获已经够；将来真需要再说；
* 闭包与 `@overwrite` / 跨模块身份的交互：**留到需要时单独定**（今天没有用例）。

## 9. 待作者拍板的三件事

1. **语法**：(A) `|x|` 还是 **(B) `fn(x) { }`**（本文推荐 B）；
2. **"传"的口径**：确认走**泛型参数单态化**（本文推荐），还是要求 v1 就能写 `fn(T)->R` 类型
   （后者会重新打开"间接调用"的口子，与 §1 冲突，不推荐）；
3. **捕获默认**：确认**按值**进结构体、"要写就捕 `mut ref`"（本文推荐），
   以及**是否需要**显式捕获列表（本文认为不需要）。
