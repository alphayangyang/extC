# ARENA.md —— arena = 词法作用域（主人的模型，2026-09-20）

> 由主人 2026-09-20 的笔记整理。**这一份取代** `DECISIONS.md` ㉔（"逃逸提升"）和 ㉙（"一等公民"）里的对应部分 ✓

---

## 0. 一句话

> **Arena = 词法作用域。每个 `{}` 一个 arena。**
> 编译器**隐式**把它传给被调函数；**返回值进调用者的 arena**；父子 arena **物理平行**（各自块链）。
> **用户 90% 场景完全无感。**

---

## 1. 形式化

### 1.1 作用域树

程序从**单一入口**开始 ⇒ 以入口为根建一棵**作用域树**；
入口之外声明的东西深度为 **0**，挂在**虚根**上 ✓
**每只 arena 的层级关系 = 这棵树** ✓

### 1.2 函数的 arena 怎么定（核心规则）

对调用 `f(arg₁, …, argₙ)`：

1. 只看**可访问的东西**（否则根本调用不了）⇒ 这些 `argᵢ` 所在的 arena
   **必然在一条链上**（单入口 + 作用域树 ⇒ 任意两个可达位置有祖先关系 ✓）
2. ⭐ **取链中「最浅」的那只（活得最久的那只）作为函数体用的 arena**

**为什么"最浅"而不是"最深"**：函数里 `new` 出来的东西会被**写进实参指向的对象**，
而"写进去"要求它**活得不比那个对象短** ⇒ 取最浅（最长寿）那只 ⇒
它**比任何一个实参的存储都长寿** ⇒ **写进哪个都安全** ✓✓

### 1.3 证明（安全性）

设实参的 arena 从浅到深为 A₁ ⊂ A₂ ⊂ … ⊂ A_m（一条链），函数分配进 **A₁**。
则函数 `new` 的任何对象寿命 ⊇ A₁ ⊇ A_m ⊇ … ⊇ 每个实参的存储 ✓

| 动作 | 安全？ | 理由 |
|---|---|---|
| 把 `new` 的东西**写进某个实参指向的对象** | ✅ 安全 | A₁ 比那些对象长寿 ✓ |
| 把 `new` 的东西**返回给调用者** | ✅ 安全 | A₁ 是调用者作用域链上的祖先 ✓ |
| 把**实参的引用**存进 `new` 的对象 | ✅ 安全 | 对象的寿命 ≤ A₁ ≤ 实参的东西 ✓ |
| **函数据以分配的 arena** | 不需要额外信息 ✓ | A₁ 由链唯一确定 ✓ |

**前提（两条，要写清楚）**：
① **单链** ⇒ **多线程**时每个线程一条自己的链 ⇒ 跨线程只能**拷贝/移动**（跟"引用不过线程"一致 ✓）
② **全局/静态**在虚根（深度 0）⇒ 它们比谁都长寿 ⇒ 谁都能存下 ✓

## 2. 物理布局：父子**平行**

> 主人：「父 arena 和子 arena 在空间上应该是**平行的**，否则我子 arena 扩容会冲击父亲」

| | |
|---|---|
| **每只 arena 一条自己的块链** | 父的块里**只有父自己 `new` 的东西**，不含子块的 ✓ |
| **各自 bump，O(1) 扩容** | 子扩容不会挪动父的指针 ⇒ 不会退化成 O(n) ✓✓ |
| 释放 | 出作用域 ⇒ 把**自己这条链**还掉（父不受影响 ✓）|

## 3. 用户看得见什么

| 场景 | 用户写什么 |
|---|---|
| 日常 `new` | **什么都不写** ✓（编译器按 §1.2 选 arena ✓）|
| 返回值 | 什么都不写 ✓（进调用者的 arena ⇒ 调用者的规则照旧 ✓）|
| **显式指定**父 arena | **允许**（逃生舱）：「你可以显式地指定调用的时候函数被放在哪一个父级 arena 中处理」✓ |

⚠️ **arena 不是数据类型，是作用域**（主人原话）⇒
**匿名**（对用户）、不进泛型参数（㉙ ✓）、**不需要也不该被处处命名** ✓
（`arenaOf()` / `allocFrom` / `varArray.home: ref arena` 那套**作废** ✓）

## 4. 代价（诚实）

| 代价 | 说明 |
|---|---|
| ⭐ **保留期变长** | 分配进**最浅**那只 ⇒ 只要那只还活着，函数里 `new` 的垃圾就**不会回收** ✗<br>例：`fn step(buf: mut ref T) -> i64 { var t = new node … }` 在循环里被调用 100 万次，
而 `buf` 来自**外层**作用域 ⇒ **100 万个节点留到外层结束** ✗✗ |
| 对策 | ① **显式指定**更浅/更深的那只（逃生舱 ✓）② 把 `buf` 放进**更内层**的作用域 ✓ ③ 以后可加"**按需提升**"（逃逸分析）作为优化 ✓ |

> **这是本设计唯一真正的取舍**：**§1.2 换取"零分析、零标注"** ✓
> 备选方案（分配进函数**自己**的作用域 + 逃逸时提升一级）保留期更短，
> 但需要**逃逸分析**（编译器复杂度换内存占用）✓
> ⇒ **主人选了前者**（简单优先），并留了显式指定当出口 ✓

## 7. 证明的最后一环：**"可写目标的集合由实参决定"**（主人 2026-09-20 追问）

主人：「当然我显然无法阻止你 `mut ref` 之间赋值来赋值去（）」

**对，拦不住 —— 但也不需要拦** ✓ 因为**传来传去不会造出新的可写目标** ✓

### 不变量

> **函数体里任何可写目标，其 arena 只能是两种之一：**
> **(a) 某个 `mut ref` 实参指向的 arena；(b) 本函数自己的作用域。**
> 没有第三种 ✓ ⇒ 而 (a)(b) 全都 **⊇ A₁**（A₁ = `mut ref` 实参里**最浅**的那只）✓

⇒ 函数分配在 A₁ 的东西 **活得比所有可写目标都长** ⇒ **写进任何一个都安全** ✓✓
⇒ `mut ref` 在局部之间赋值、传参、拷贝 —— **都只是换了个句柄，目标没变** ✓
⇒ ⭐ **A₁ 的公式只用"实参"，所以"赋值来赋值去"根本影响不到它** ✓✓

### 为什么这个集合只有两种：（逐个排除）

| 想造出第三种可写目标 | 结果 |
|---|---|
| `var x: i32` 本帧局部 ⇒ `ref x` | (b) ✓ 更深，无害 |
| 参数的引用（`ref *p` / `*p`）| 就是 (a) ✓ 同一个目标 |
| **`ref` 参数指向的东西** | ❌ **写不进去** —— 靠**链式只读** ✓（㊱）|
| **全局 / 静态** | ❌ 全局**不能含 ref**（连声明都拒 ✓）⇒ 伸不进 arena ✓ |
| 函数返回的引用 | 深度 = A₁ 的深度 ⇒ 调用者 ≥ 它 ✓ 递归成立 ✓ |

### ⭐ 所以**链式只读是承重墙，不是讲究**

反例（如果 `ref` 参数能写）：
```extc
fn f(ro: ref big, rw: mut ref small) {    // A₁ = rw 的 arena（更深）
    var t = new node                       // 分配在 A₁
    *ro.field = t                          // ✗ 写进**更浅**的 arena ⇒ t 先死 ⇒ **悬垂** ✗✗
}
```
⇒ **没有链式只读，这个 `*ro.field = t` 就是合法的悬垂** ✓✓
⇒ 链式只读把它堵死 ⇒ **A₁ 的公式才成立** ✓

### 一句话

> **可写目标 ⊆ {`mut ref` 实参} ∪ {本帧}；A₁ = 前者里最浅的 ⇒ 分配永不悬垂。**
> **`mut ref` 怎么传都不影响这个集合 —— 所以"拦不住"没关系** ✓

## 8. ⭐ 用法速查（`new` 还没实现，这是**设计**✓）

### 8.1 一句话

> **不写 `new` 的东西在栈上**（定长、随函数走 ✓）；
> **写了 `new` 的东西在 arena 里**（运行时大小 / 要跨作用域 ✓）；
> **住哪只 arena、什么时候回收，用户都不用管** ✓

### 8.2 `new` 的四个形状（操作数是**类型** ⇒ 没有 `<>` ✓）

```extc
var n  = new node             // 一个 node（**清零**）⇒ mut ref node ✓
var b  = new i32[1000]        // 1000 个 i32 ⇒ mut slice<i32> ✓
var a  = new [4]i32           // 一个 [4]i32 ⇒ mut ref [4]i32 ✓
var p  = new point { x: 1, y: 2 }   // 顺带填字段（字段可省略 ⇒ 补零）✓
```
| 想要 | 写 |
|---|---|
| 一个对象 | `new T` ✓ |
| **一片**（长度运行时才知道）| `new T[n]` ✓ |
| 一个定长数组 | `new [N]T` ✓ |
| 建好就填 | `new T { … }` ✓ |

### 8.3 谁能跨函数（**这是 arena 存在的理由**）

```extc
// 节点活得比造它的函数长 ⇒ 用 new ✓（以前做不到 ✗）
fn make(v: i32, tail: mut ref node) -> mut ref node {
    var n = new node
    n.val = v
    n.next = tail
    return n                  // ✓ 合法：它住在本函数**实参**那层的 arena 里 ✓
}
```
**规则（ARENA.md §1.2）**：函数分配进 → **`mut ref` 实参里最浅的那只** arena ✓
（没有 `mut ref` 实参 ⇒ 用**调用点自己那层** ✓）

### 8.4 什么时候回收

| 东西 | 什么时候消失 |
|---|---|
| 栈上的（`var a: [100]i32`）| 出作用域 ✓ |
| **`new` 的** | **它所在的那只 arena 出作用域时** ✓（循环体那只每轮 `reset` ⇒ 零 malloc 抖动 ✓）|

⚠️ **唯一的坑**（ARENA.md §4）：分配进"最浅的那只" ⇒ 如果那只在外层，
**垃圾要等到外层结束**才回收 ✗ ⇒ 对策：
```extc
// 想让临时东西早点死 ⇒ 把参数放在**更内层**，或者显式指定更内层的 arena ✓
```

### 8.5 不需要的东西（都作废了 ✓）

| 作废 | 为什么 |
|---|---|
| `arenaOf()` / `allocFrom(a, n)` | arena **隐式**、**匿名**（是作用域，不是数据类型 ✓）|
| `withTarget` 那种"构建并返回"来绕 | 有了 §1.2 的规则 ⇒ **直接写进实参对象就行** ✓ |
| `varArray.home: ref arena` | 增长时的 buffer ⇒ 走同一条隐式规则 ✓ |
| 手动 `free` | **永远没有** ✓ |

### 8.6 今天（`new` 还没做）能凑合到什么程度

```extc
let buf = alloc<[4]i32>(1)     // 一个 [4]i32 的地方
(*buf)[0] = 65                 // ← 靠今天做的 `*p` 才写得出来 ✓（实测能跑 ✓）
```
⇒ **能跑，但丑** ✗（`(*buf)`、要手写长度、没有清零保证）⇒ 这就是 **A1** 要解决的 ✓

## 9. ⭐ owner depth：**容器的内容活多久**（2026-09-21 设计，实现中 —— 修 PLAN #31）

### 9.1 触发它的问题（`PLAN.md` §0.6，ASan 实锤 use-after-free）

```extc
fn mk() -> varArray<i32> {
    var v: varArray<i32> = varArray<i32>::withCap(0)
    v.push(42)   v.push(43)
    return v                       // ⚠️ 编过，但 buffer 死在 mk 的块 arena 里
}
```
实测打印 `[1002, 0]`（正确 `[42, 43]`）✗ —— 建容器走 `EX_ASSOC`（家 = `__extc_home` ✓），
扩容走 `EX_METHOD` 而实参是本地的 `v`（家 = `&__extc_a[1]` ✗）⇒ **同一个容器的 buffer 落在两只 arena**。

### 9.2 为什么 §7 的证明没挡住它（证明的边界在哪）

§7 的不变式说的是 **"函数体内的可写目标 ⊆ (a) `mut ref` 实参指向的 arena ∪ (b) 自己的作用域"**，
于是"分配在 A₁ 的东西活得比所有可写目标都长 ⇒ 写进哪儿都安全" ✓ ——
**这句话只管到"函数活着的时候"** ✗

`push` 把新 buffer（A₁ = 调用者的块 arena）写进 `self` ✓ **在函数内完全正确**；
出问题的是**之后**：调用者把容器**搬出这个块**（`return v` 会拷贝结构体），
而 buffer 留在块 arena 里、块一退就没了 ⇒ **容器活着，它里面的东西死了** ✗

⇒ 缺的不是"写进去安不安全"，而是「**容器的内容 ≥ 容器能去的任何地方**」这一条寿命约束。

### 9.3 新概念：owner depth（每个绑定记一个数）

> **`owner(v)` = `v` **拥有的内容**分配在哪只 arena。**
> 数字**越小活得越久**（0 = 参数/家一级；k = 第 k 层块）。
> **默认 = 槽位自己的深度**（"内容和槽位同命"）⇒ 不额外信息时最保守 ✓

配合已有的 `refDepth`（**里面指着的**东西有多深），一个值的"逃逸危险度"是
**`max(owner, refDepth)`** —— 谁更深（更短命）谁说了算 ✓（两个是不同的问题：
`refDepth` 管"指向别人"，`owner` 管"自己带的存储"）

### 9.4 新分析：**E = 这个局部会不会被搬出本函数**

拿 AST 走一遍就行（跟现成的 `stmtHasNew` / `stmtStoresThroughDeref` 同一风格），
不动点规则（**保守方向 = 宁可在 E 里**）：

| 形状 | 结论 |
|---|---|
| `return e` | `e` 里**出现的每个**局部名都进 E（不管是不是真被拷出去）|
| `p = e`，`p` 的根是**参数 / 全局** | `e` 里的局部进 E |
| `x = e`，`x ∈ E` | `e` 里的局部进 E（传递）|
| 拿不准（按值传给调用、塞进枚举载荷…）| **进 E** |

⚠️ E **只用来决定"家 arena 选哪只"**，不改变任何"能不能写"的判断 ✓

### 9.5 三条规则（实现清单）

| # | 规则 | 效果 |
|---|---|---|
| **E1 创建** | `var v = f(…)`，`f` 会分配且返回带引用的类型：v ∈ E ⇒ 家 = **我的家**（`-1`）；否则 = **本块** | `mk` 里 `withCap` 走 `__extc_home` ✓（今天**碰巧**就是这样：`EX_ASSOC` 默认分支）|
| **E2 扩容** | 调用带 `mut ref` 实参、根是局部 `v`：v ∈ E ⇒ 家 = **我的家**；否则 = **`v` 的块** | **这条就是 #31 的修法** —— `push` 也传 `__extc_home` ⇒ buffer 活得 ≥ 调用者 ✓ 与 E1 一致 ✓ |
| **E3 逃逸检查** | 绑定的有效深度 = `max(owner, refDepth)` | `mk` 里 `owner(v) = 0` ⇒ `return v` **合法** ✓（今天它靠"`refDepth` 算错成 0"才勉强合法 ✗）|

### 9.6 为什么不自相矛盾（两条约束碰不上的证明）

- v ∈ E ⇒ 创建与扩容都用**我的家** ⇒ `owner(v) = 0` ⇒ `return v` 要求 `≤ 0` ✓ **合法**
- v ∉ E ⇒ 本地就不 `return` 它 ⇒ 没有"搬出去"这回事 ⇒ 内容留在本块 ✓ **且省内存**（PLAN #24 的紧致性不丢）

⇒ **E 分析和 owner 深度正好互补：不会有假阳性，也不会漏 UB** ✓

### 9.7 与"乙"（把家一律换成我的家）的区别（为什么乙不行）

乙 = 不看 E、一律传我的家 ⇒ 与 **规则 ④** 打架：家的深度变成 0 ⇒ 接收者自己（深度 1）就被拒 ✗；
把接收者豁免掉的话，被调者就能把**接收者的地址**存进"活得比调用者帧还久"的家 arena 内存 ⇒ 换一个洞 ✗
（§7 的证明正是靠"家 = 最浅可写目标的 arena"才成立）✓

### 9.8 遗留（记在 PLAN，不在这次做）

- `new` 在**有家函数**里一律进家（`arenaRef` 看 `hasHome`）⇒ 循环里会累积到函数结束 ✗
  **同一份 E 分析**可以把它精确化（`cell ∉ E` ⇒ 进当前块）—— 独立的一小步，别跟本次混 ✓
