# 函数指针与 C ABI

> **一句话**：extC 本来就生成 C，所以 C 的 ABI 是**资产**而不是负担；函数指针是拿到这份资产的钥匙。
> 它不新增安全面 —— 它只把"这段代码还在吗"这个问题，交给我们已经有答案的那套（世代句柄 + 卸载协议）。

## 0. 为什么现在要它

`HEAP.md` §2 那张 `extc_heap_api` 表**整张都是函数指针**，而语言里没有这个类型。于是那条线卡在一格上：
不改语言，就写不出那页文档。这是唯一一处"文档跑在语言前面"的地方。

同时要看清：这条线**不是**为了把函数指针当日常工具用（那不是 C 的用法，也不是 extC 的用法），
而是为了**边界**——`dlopen` 进来的模块、以及我们自己链接的 C 库。日常的分发继续用枚举 + `match`（§1 第三条）。

## 1. 三条线（这一页的全部结论，其余都是推论）

1. **跨界只有裸函数指针**：`fn(A) -> R` 是**代码指针**，**没有环境**。需要状态就显式传 `ctx`
   （`HEAP.md` 的表里那只 `ctx` 就是这个用法）。
2. **方向定死**：**模块 → 宿主免费**（宿主代码与内存比模块活得久，`HEAP.md` §4 那条不对称规则）；
   **宿主 → 模块只经世代句柄**（宿主永不持有模块的裸代码指针）。
3. **闭集分发仍用枚举 + `match`**：`fn` 只为"被调方编译期未知"的场合存在。

在这三条内，函数指针**不新增安全面**：

* 它是一个**值**，和 `ref T` 没有种类差别；危险从来是**寿命**与**权限**两件事，
* 而"代码还在吗"＝世代句柄 + 卸载协议（`HEAP.md` §4，已写），
* "它能碰什么"＝它的**参数** + **它自己模块的全局**（§6），与 `HEAP.md` §1.5 那条链同一个答案。

## 2. 类型：`fn(A, B) -> R`

* **是什么**：一个代码指针。`fn(i64) -> i64` 在 C 里就是 `int64_t (*)(int64_t)`，一一对应，没有包装。
* **能出现在哪**：参数、返回值、**结构体字段**、泛型实参、数组元素、`slice<T>` 的元素 `T`。
  它是普通值，所以出现在这些地方都不需要新规则。
* **不能是什么**：
  * **没有空值**。要可空就用 `option<fn(A) -> R>`（与语言其它地方一致），不引入 `null` 函数。
  * **不带环境**。带捕获的闭包**不能**变成 `fn` —— 那需要 `{code, env}` 两个词，属于"闭包当值"那条线，
    这一页不开（§7）。
  * **捕获为零的闭包可以**：`fn(x: i64) { return x * 2 }` 本身就是个静态函数，转成 `fn(i64) -> i64` 是零成本的。
    检查器已经在算捕获（`EX_LAMBDA.captures`），所以这条规则**可判定**，不需要新分析。
* **不承诺**：可调用性的副作用信息照旧由 `effects` 那套表述（`Addr=` / `Cont=` / `Thread=`），
  函数指针的**目标**若来自外来模块，其效果只能按"最保守"记 —— 这一点与 `extern!` 同规。

## 3. ABI 承诺：不比平台 C ABI 多一个字

`fn(A) -> R` 的 ABI 就是**平台 C 的函数指针 ABI**。我们不发明调用约定：

* 参数按平台 C ABI 传（含结构体按值、`f32/f64`、小整数提升 —— 都由平台定）；
* 返回值按平台 C ABI（含结构体返回值的那几种传递方式）；
* 产物本来就以 `-std=c11 -fwrapv` 编译（`HEAP.md` 与 `LIB` 那条线同规），所以"另一侧"只要也是
  同一个平台的 C 编译器，就对得上。

**这条是有意的**：任何自定义约定都会把 C ABI 生态换掉，而那正是我们要拿的东西。
代价是：**跨界的结构体布局必须与 C 一致** —— 那是下一格（§9 第 2 步），不是这一格。

## 4. 进入外来的两条路：表是主路

| 路 | 用途 | 谁提供 |
|---|---|---|
| **版本化的表**（`HEAP.md` §2，头字段是 `size` + `ctx`）| `dlopen` 进来的模块 | **宿主** |
| `extern!("…")` 声明 | 我们自己链接的 C 库（`memfind`、`time`、…）| 链接期符号 |

**不做符号 interposition**（`HEAP.md` §7）：模块不靠解析宿主符号，宿主也不接管模块的符号。
两条路都只传**值**：表是数据，`extern!` 是符号，函数指针在两条路上都只是"表里的一个字段 / 一个实参"。

## 5. 回调（这题最尖的地方）

三个方向必须分开看，混起来就会得出"回调很危险"的错结论：

| 方向 | 判定 | 凭什么是 |
|---|---|---|
| 宿主 → 模块 | 安全 | 指针是宿主自己从**已加载**的模块拿到的，模块还开着 |
| **模块 → 宿主** | **免费安全** | 宿主代码/内存**比模块活得久**（`HEAP.md` §4 不对称规则）|
| **模块注册回调给宿主** | 需要机制 | 宿主将持有**模块**的指针 ⇒ **禁止裸指针，只给 `{slot, gen}` 世代句柄** |

第三行不用新东西：`HEAP.md` §4 已经定了——**注册一律给世代句柄**，`dlclose` 之前先把该模块的槽
世代加一，之后旧句柄来用就是当场 trap（那套保护的是**代码**，不只是数据）；卸载四步协议
（停发新活 → `deinit` → 作废世代 → `dlclose`）+ "在模块里跑着的调用计数"照旧。

**回调不需要是闭包**：要状态就显式 `ctx`（表里那只，或每个注册项自己的 `ctx`）。
于是 §1 第一条能一直成立，而"闭包当值"那条线可以继续关着。

## 6. 寿命与权限，按代码指针重述一遍

* **寿命**：一个 `fn` 值**不得比"保证这段代码存在"的东西活得久**。
  * 程序内的函数：静态存在 ⇒ 没有寿命问题；
  * 外来模块的函数：由 §4/§5 的**世代句柄 + 卸载协议**保证；
  * 结论：不需要为 `fn` 新增任何生命周期规则 —— 需要的那条已经有了。
* **权限**：调用它能碰到的，是**它的参数** + **它自己模块的全局**。
  它拿不到宿主的隐式状态（不 interposition、没有"按名字要全局"、表是显式递过去的），
  这与 `HEAP.md` §1.5 是同一个能力论证。

## 7. 明确不做（这一页不开的门）

* **不做**带环境的函数指针跨界（要状态就 `ctx`）；
* **不做**"闭包当一等值"（那是另一条线，见 `LAMBDA.md` 的状态）；
* **不做**自定义调用约定 / 自造 ABI；
* **不做**符号 interposition / 全局钩子；
* **不做**多进程沙箱（`HEAP.md` §7 已定）；
* **不做**函数指针的"可空"（用 `option`）；
* **不做**函数指针的相等/哈希语义承诺（代码地址可能被合并，`==` 只在同一模块内可比 —— 待作者拍，§8）。

## 8. 要作者拍的（我按实现侧给建议，但决定权是作者的）

1. **`fn` 是类型关键字还是别的写法**？（建议：与现有 lambda 的签名写法**同一个拼法** `fn(A) -> R`，
   只是这次它出现在**类型位置**——`var f: fn(i64) -> i64 = …`。语法上零新增。）
2. **捕获为零的 lambda 允许自动转成 `fn` 吗**？（建议允许，理由在 §2；检查器已有捕获信息。）
3. **`fn` 允许做泛型参数吗**（`vector<fn(i64) -> i64>`）？（建议允许：它是普通值；但这是本页语义上最大的一步，
   如果作者想先收着，就限制"`fn` 只能在签名与结构体字段里"。）
4. **`fn` 能放进 `@private`/跨模块边界自由传递吗**？（建议：能。它是值，没有资源。）
5. **`extern!` 是否降级为"只给我们自己链接的库"**（表成为唯一的外来入口）？（建议是，与 §4 一致。）
6. **可空**：`option<fn(A) -> R>` 就够，还是想要 `?fn` 这种更短的写法？（建议前者。）

## 9. 实施顺序（每步都能单独过闸门）

1. **类型 + 解析 + 检查 + 下降**：`fn(A) -> R` 作为类型；下降就是 C 的函数指针类型。**不动 prelude**
   （在 prelude 里加声明会改所有产物；类型不是声明，天然零位移）。判据：产物逐字节不变（语料里没有
   这个类型 ⇒ golden 414/414 应不动）。
2. **跨界的结构体布局**：`extc_heap_api` 那种表要按 C 布局。这一格与 `HEAP.md` §2 一起做。
3. **`std::dl`**：`dlopen/dlsym/dlclose` 的 `extern!` 声明 + 表的分发；第一个用户是 `prototype-heap/`
   那套（纯 C 原型已经在跑，见其 README）。
4. **Heap 板进运行期**：`mmap` 保留 + 按需 commit + 那道门（区间检查）+ `close` 即 `munmap`。
   到这里 `HEAP.md` 才有实现可指。

## 9.5 第 1 步的实施笔记（2026-09-29 摸地形后写，动手前先看这段）

**会牵动哪些文件**：`ast.h`（新增 `TY_FN` + 两个字段：参数类型表与返回类型）、`parser.c`（**类型位置**接受
`fn(A, B) -> R`）、`types.c`（intern 键、等价判断、`typeName` —— 那里有 21 处 `case TY_`）、`codegen.c`
（`cType` 的 11 处分派）。语法零新增：`fn(...)` 的拼法与 lambda 一致，只是这次在类型位置。

**必须先解决的坑（否则会在每个使用点炸）**：`cType` 在本项目里是**"类型文本"**，调用点普遍按
`"%s %s"`（类型 + 名字）拼接。而 C 的函数指针声明符**要把名字包进中间**：

```c
int64_t (*)(int64_t)          /* 类型文本能是它 */
int64_t (*f)(int64_t)         /* 但"类型文本 + 名字"拼出来是坏的 */
```

⇒ **函数类型一律走 typedef**：按需在产物前言里发一条
`typedef int64_t (*extc_fn_i64_i64)(int64_t);`，类型文本就用那个名字。这与本仓库"按需发射运行期"的
老套路一致（`needMemFind` / `needTime` / `needDomain` 都是这个形状），而且**typedef 的名字进 mangle**
⇒ 同一个函数类型只会发一条。**不要**去改所有 `%s %s` 调用点（那是把一个小改动摊成一次大手术）。

**三个要在这一步就定的小问题**（都在 §8 的建议之内）：

1. **怎么造出一个 `fn` 值**：最省的第一步是"**函数名当值**"（`var f: fn(i64) -> i64 = double_it` ⇒ 下降成
   `&double_it`），它比"捕获为零的 lambda 自动转"更小 —— 后者留给下一步。
2. **不初始化怎么办**：语言的规矩是"没有初始化器 ⇒ 零初始化"，而零值的函数指针是 **NULL**，
   与 §2"没有空值"直接冲突。第 1 步先让"声明一个 `fn` 而不初始化"**编译期报错**（要空就用
   `option<fn …>`），别在运行期留一个能跳进去的空指针。
3. **相等/哈希**：这一步**不承诺**（§7 最后一条）。要比较就等作者拍。

**判据（第 1 步）**：make 0 诊断；语料里没有程序用这个类型 ⇒ **golden 414/414 逐字节不动**；
带超时的单遍扫描 0 变化；探针写进 `tests/ops/`（一个函数名赋给 `fn` 变量、当参数传、当返回值返回、
放进结构体字段各一次）。

## 9.6 第 1 步落地实录（2026-09-29，全部判据已过）

**做出来的东西**：`fn(A, B) -> R` 是一个**普通值类型**。函数名当值（`&f`）、经指针调用（`f(x)`，
字段里的 `o.f(x)` 也是）、参数/返回值/结构体字段/泛型实参都能放。`TY_FN` 的 C 文本是**typedef 名**
（`extc_fn_i64__i64`；分隔用 `__` 而不是一个 `_`，因为 mangle 自己就用单个 `_` 连接部件 ——
`pair_i32_u8`，一个 `_` 会被读成名字的一部分），typedef 按需发射在**枚举之后、结构体 forward typedef
之后、结构体定义之前** ——
那个位置是唯一的：签名要能命名枚举与结构体，而结构体**字段**要能命名签名。
"哪些函数类型要发"这件事**没有专门的扫描**：`tt->fnTypes` 就是需求集（每个被写出来的 `fn` 都过
`ttFn`）。语料里没有 `fn` ⇒ 表是空的 ⇒ 一个字节都不动 ✓（**golden 414/414 逐字节不变**，实测）。

**四个当场发现、当场修的坑**（都会产生"合法但错"的产物，或者指向错东西的诊断）：

1. **共享走查器故意不看 call 的 callee**（`ast.c`：callee 是**名字**不是表达式）。而经值调用的 callee
   恰恰是一次**读取**。不修的症状：`fn apply(f: fn(i64) -> i64, …)` 报 "parameter `f` is never used" ——
   函数体里唯一的语句就在调它。现在只在 `callViaFn` 时把 callee 当子节点。
2. **`o.f(x)` 是 parser 眼里的方法调用**（`EX_METHOD`），不是 `EX_CALL` ⇒ 字段里的函数会得到
   "no method `f` on `op`" —— 一句说错对象的话。修法：在方法解析**之前**用 `peekFieldType` 偷看一眼
   字段类型（**不检查表达式**，否则普通方法调用的接收者会被检查两遍），是 `fn` 就原地改写成经值调用。
3. **零值**：`typeLacksZeroValue(TY_FN) = true`，于是"声明 `fn` 不初始化"由**已有那条**零值规则挡住，
   而且诊断按 `typeContainsFn` 分成两句（`ref` 那句会让人去找一个不存在的引用）。`codegen` 的
   `zeroValue` 里补了一条防御：`fn` 的零值发射成一个**不存在的标识符**（让 gcc 点名），而不是 `0`
   —— `0` 是一个**空代码指针**。
4. **隐藏参数**：编译器给"收 home arena / zone"的函数偷偷加参数，那些标志是**可传递闭包**，只有在
   所有函数体查完之后才定。所以"这个函数的地址能不能当 `fn` 值"在检查期**答不了**，由 codegen 在
   标志已终局处拒绝（报错，不是发一个类型不匹配的指针让 gcc 去吼）。

**顺带收掉的一处重复**：`extern!` 的"什么能过 C 边界"原本在 `check_top.c` 里**手抄了两遍**，而且
两处都带一个**永远走不到的分支**（对一个已经被 `ttBase` 剥光引用的类型问 `kind == TY_REF`）。
现在只有一处 `ttCrossesC(t, isReturn)`，`fn` 的签名检查与 `extern!` 共用它 —— 这正是"`fn` 不该比
`extern!` 松"那条规则能被机器保证的原因。**`fn` 自己可以过界**（一个代码指针就是一个指针，C 一直
在传这种东西 —— `qsort` 的比较函数就是这个形状）。

**这一步没有关上的门（都记在这里，别当洞）**：

* **`fn` 的类型**签名只放行"标量 / 单指针（指向标量的）/ `fn`"。**指向声明类型的指针**（`ref point`）
  和 **`ref void`（C 的 `void *`）**今天过不去 —— 这不是新收窄，是 `extern!` 一直就有的窄；§9 第 2 步
  （跨界的结构体布局）才有资格放开它，因为那时"指向的那个东西长什么样"才有答案。`HEAP.md` §2 那张表
  里的 `ctx: ref void` 就是被这一格挡着的（**文档跑在代码前面的第二处**，第一处就是 `fn` 本身）。
* **`fn` 值没有地方签 `effects`**：签字是**声明**的属性（`collectEffects` 只对 `extern!` 读那条子句），
  裸代码指针没有声明 ⇒ 经 `fn` 调用的效果摘要只能是**最保守**（"它可能留住一切"）。后果：把帧内的
  `s.data` 经 `fn` 传出去会被拒（与"没签字的 `extern!`"同一档，安全但不好用）。给**类型**带签名的
  路（表字段上写 `effects`，或者签名别名）是 §9 第 3 步的事。
* **相等/哈希**：不承诺（§7）。`fn` 放不进 `==`，也不该放。
* **泛型体里的 `fn(T) -> T`**：模板检查时 `T` 未定，那条"能不能过 C 界"的检查**跳过**；实例化成
  不可过界的签名时今天**没有再查一遍**（没有程序能构造出这种实例：唯一的来源就是模板自己）。
  第 2 步改谓词时一起收。

**验收（实测，长在这里免得下次重新推）**：`make -j24` **0 诊断**；`tools/golden.sh` **414 个产物
逐字节不符 0 · 非法 C 0**；`./check.sh quick` **45/0**；`tests/ops` 新增正例 `fnptr.extc`
（值 / 参数 / 返回值 / 结构体字段 / **嵌套签名** `fn(fn(i64) -> i64, i64) -> i64` / **`extern!` 符号当值**
各一次）+ 四条反例（零值 · slice 签名 · 泛型裸名 · 结构体字段漏给）全过；手册加了
[3. 类型 § 函数指针](../manual/04-types.md) 一节，示例进 `check_manual_examples` 闸门（示例编不过就红）。

## 9.7 第 2 步：指针放开（2026-09-29 作者拍板"应该放开，不放开啥都写不了"）

**改了什么**：`ttCrossesC` 原来的规则是"**剥掉引用之后是个标量**"（于是 `ref u8` 能过、
`ref point` 与 `ref void` 都不能）。现在是：

> **一个机器字就能过**：标量 · 指向**任何东西**的指针（`ref T` / `mut ref T` / `?ref T`，含 `ref void`）
> · 函数指针 `fn(A) -> R`。**不是**一个机器字的一律不过：`slice<T>`（C 那边是两个参数）、
> 结构体/带载荷枚举**按值**（布局没冻结）、`void` 按值（它只是返回类型）。

配套的两件事：

1. **`ref void` 看不进去**：`*p` 在 `EX_DEREF` 处编译期报错（"`void` has no size"），`p[i]` 由已有的
   索引检查挡住。C 也会拒绝 `*(void*)p`，但它拒绝在**生成物**里 —— 错误指向一行作者没写过的代码。
   `ref void` 能做的只有：**传回给 C**、放进 `?ref void` 判空、当参数转手。
2. **结构体按值这一格不开**（与第 2 步分开）：见下。

### 它动不动安全？——不动类型安全，动的是"借出去的内存"这件事的边界

这是作者问的原话（"这会破坏我的类型安全吗"），答案按四条给，每条都能指到代码：

1. **指针没有布局问题**。一个对象指针就是一个机器字，指向什么不影响 ABI。**这一格与"结构体按值
   过界"是两种东西**：按值要两边布局逐字节一致，不一致是**静默错**（C 按错的偏移读写，不 trap 也
   不报错）⇒ 那一格需要"冻结布局 / `@reprC`"，本步**没开**，反例钉在
   `tests/extern/errors/struct_by_value.extc`。
2. **extC 能对新类型做的操作，一件都没新增**。`*p`、`p.f`、`p.m()`、`p[i]` 全部走现成规则
   （`mut` 权限、`?ref` 非空收窄、逃逸深度、`@private` 字段）。放宽只改了"**哪些类型的指针被允许
   出现在签名里**"，没有新增任何一条操作。
3. **寿命与权限一个字没改，而且正是它们在管这件事**。`checkCallRefArgs` 的判据是"**这个实参是
   `ref` 吗 + 它指向多深 + 被调方签名说没说它会存**"，与指向类型无关 —— 所以 `ref point` 和
   `ref u8` 走**同一条**规则：没签字的 `extern!` 拿帧内地址就报错
   （`errors/ptr_unsigned.extc` 钉着），签 `effects Addr=0 Cont=0` 才放行。
4. **真正变大的是"义务"，不是"漏洞"**：以前只能借出**没有内部指针**的内存（`ref u8`），
   现在能借出 `ref node`（`node` 里有 `?ref node`）⇒ C 可以**从我们内存里读出一个指针并留着**，
   那是 **`Cont`** 那一半的签名在管；反过来，C 也可以**往我们内存里写一个指针**（见下）。
   两件事都不是类型规则变松，而是"你把可写内存借给了外来代码"的固有含义。

**必须点名的一条后果**（写进手册 18-modules §12.3）：把 `mut ref T` 借给 C 之后，C 可以往 `T` 的
`?ref` 字段里写一个**它自己的指针**，之后 extC 会当真去解引用。挡它的办法只有三条，都是**声明处**
的选择，不是编译器的推断：(a) **只读借出**（声明写 `ref T` 而不是 `mut ref T`）；(b) 大块输入用
**只读映射**那种硬保证（`HEAP.md` 里那条 `mprotect` 的贷款，实测 ≈0.7 MiB 处盈亏平衡）；
(c) 在签字里写明 C 不写回指针 —— 今天那三个掩码（`Addr`/`Cont`/`Other`）描述的是"**从我这里往 C 流**"
的方向，**写回**方向还没有一个掩码；要不要加第四个（比如 `Wr`），等真有库需要它的时候再拍，
不先发明。

**这一步顺带核掉的一个隐患**：生成物里**没有 `restrict`**（`grep restrict src/*.c` 只命中
`base.c` 的 C 关键字表，那是给标识符重命名用的）。若有，C 存下指针再写就会与 extC 的读构成 UB ——
现在没有，写在这里是因为"指针放宽"之后这个前提值得被记住。

**验收（实测）**：`tests/extern` 新增正例 `capi.extc` + `capi-main.extc`（**真调 libc**：
`gettimeofday(ref tv, null)` 让 C 写进 extC 的结构体再读字段 · `mmap`/`munmap` 把 `void *` 进出一趟 ·
经 `fn(mut ref point) -> void` 的间接调用），三条反例（不签字的声明拿帧内指针 · `*p` on `ref void` ·
结构体按值）全过；`golden 414/414 逐字节不变`（放开只是**多接受**程序，语料里没有这种声明 ⇒
产物一字不动）；`check.sh quick 45/0`。

## 9.8 第 2.5 步：`@frozen` —— 布局的签字（2026-09-29 作者拍板"可以先加……就叫 @frozen"）

**为什么不是"编译器自己判"**：`ref T` 放开之后，唯一还挡着"按值传结构体"的就是**布局**。而
extC 的布局**今天就是 C 的布局**（产物本来就是 C：字段按声明顺序一条条印，没有隐藏字段）——
问题是**没人承诺过**，于是将来一次"按大小重排字段"（Rust 默认就这么干）或者一个"往结构体里塞个
判别位"的功能，都会让跨界调用**静默读错**：不 trap，不报错，只是值不对。

按作者的口径（"你不能阻止用户犯傻"），这一格**不**去做字段白名单，而是一个**签字**：

> **`@frozen`**：这个类型的字节布局 = C 为这份字段表排出来的布局 —— 字段按声明顺序、按 C 的
> 对齐与填充、里面**没有别的东西**。

**作者那一半**：往里放什么由作者定（`slice<T>`、枚举、泛型参数都行）。代价是 C 那边得照抄我们发射的
形状；对不上是作者的账 —— 与 `effects` 完全同类。**切片仍然不因为 `@frozen` 就变成一个参数**：
视图在 C 那边是两个，想传就写 `s.data` / `s.len`。

**编译器那一半（硬的，两条）**：

1. **永不重排字段、永不加隐藏字段。** 将来任何想要"把 tag / 世代号塞进结构体"的功能，只能放到别处。
2. **在产物里把它钉住**，每个 `@frozen` 类型两条**平台无关**的 `_Static_assert`：

```c
_Static_assert(offsetof(mixed, a) < offsetof(mixed, b),
               "extC @frozen: the fields stay in declaration order");
_Static_assert(sizeof(mixed) <= offsetof(mixed, arr) + sizeof(((mixed *)0)->arr) + _Alignof(mixed),
               "extC @frozen: nothing may be added to a frozen struct");
```

数字全部由 C 自己算（`offsetof` / `sizeof` / `_Alignof`），**不写死**：写死 `== 8` 会在对齐规则不同的
平台上把一次合法构建搞坏，那正是"冻结布局"的反面。两条断言各管一半：顺序（永不重排）· 尺寸
（`sizeof` 最多是"最后一个字段的末尾 + 本类型的对齐"，也就是 C 允许的尾部填充 ⇒ 多一个字段会露出来；
若新增的字段正好塞进已有的填充里，那 `sizeof` 没变、布局也没变，没什么可抓）。

**门票的粒度**：`ttCrossesC` 里一行 —— 按值过界只认 `sdef->frozen`（`TY_STRUCT` 与泛型实例都算）。
没标记的照旧拒，而且诊断现在**点名**该写什么。

### 这一格怎么验（`tests/frozen/`，四正四反 + 两条有牙）

* **真调 libc 的按值返回**：`imaxdiv` 返回 `{intmax_t quot; intmax_t rem;}`（两个 i64，System V 从
  RAX:RDX 回来）。`<inttypes.h>` 没被前言 include ⇒ 我们自己的声明不与它冲突 —— 与 `memcmp` 那条
  "库的签名里有 `size_t`/`void *`，所以只能走 shim" 是同一个道理的另一面。
* **字段形状凑齐**：i8 / i64 / f64 / bool / 可写指针 / `[4]u8` / 嵌套 `@frozen`（中间填充与尾部填充
  都被踩到）。
* **C 侧镜像**（这是"布局对得上"唯一能真验的办法）：`mirror-pre.h` 把产物的 `main` 改个名字，
  然后把**产物 + 一份手写等价 C 结构体**拼进同一个翻译单元，编译期断言 `sizeof` 相等、**每一个字段**的
  `offsetof` 相等，运行期再打印一行（`layout ok: mixed=64 inner=16 mixed2=16 (b@8 p@32 inr@48)`）。
  编译器看不见 C 那边的结构体；**镜像就是"那边"的一份抄本**，抄错了就红。
* **两条牙**（判据不能是摆设）：把产物里 `struct inner` 的两个字段调换 ⇒ 顺序断言必须响；
  把镜像里同样的两个字段调换 ⇒ `offsetof` 断言必须响。两条都实测会被抓。
* **五条反例**：没标记的按值 · `@frozen` 标在函数 / 枚举 / `impl` 上 · 写两遍。

**顺带核到的一件事**：把**带指针字段**的 `mixed` 经 `fn` 值传出去会被（正确地）拒 —— 未签字的代码指针
按"它可能留住一切"算，而 `mixed` 里有一个 `mut ref`。与 §9.7 那条"义务变大"是同一件事，验收里留着它
当活例（`tests/frozen/frozen.extc` 的注释）。

**判据**：`make -j24` 0 诊断；`tools/golden.sh` **414 个产物逐字节不变**（语料里没有 `@frozen` ⇒
一条断言都不发）；带超时扫描 414/0；`check.sh quick` 全绿（新增 `tests/frozen` 一项）。

## 9.9 第 3 步：让这张表在 extC 里写得出来（2026-09-29 开工）

§9.6 的 `fn` 让"代码指针"成为类型，§9.7 让指针过界，§9.8 让**按值**的结构体有门票。剩下的
是 §9 第 3 步那条线：**`std::dl` + `HEAP.md` §2 的表**。它拆成四块，每块单独过闸门、单独提交。

### ① `@export`：把符号交出去（已完成）

`extern!` 是"我调 C"，`@export` 是另一面："C 调我"。产物里它是**外部链接**的 C 符号，名字就是
源码里写的那个（模块前缀 `plugin$` 在符号上去掉 —— `$` 不是合法 extC 标识符，所以它只可能来自
加载器的改名）。C 那边直接链接或 `dlsym` 都行。

四条配套的硬规矩（每条都在它自己的位置报错，因为那里的答案才是终局）：

| 规矩 | 在哪报 | 为什么 |
|---|---|---|
| 签名每个参数/返回值是"C 能写的一个机器字或 `@frozen`" | 检查器（紧挨着 `extern!` 那条，**同一个 `ttCrossesC`**）| 边界的两半用一把尺子，才不会漂 |
| 不能有隐藏参数（home arena / zone）| codegen | 那是**可传递闭包**，只有查完所有函数体才知道 |
| 名字不能需要 C 改名（C 关键字）、不能与另一个导出重名 | codegen | 符号是契约，改名之后 C 猜不到 |
| 泛型 / 方法 / 协程 / `extern!` 不能导出 | 语法层（各有各的话）| 它们没有"那一个 C 符号" |

顺带一处必须做对的：**导出不能被可达性剪枝剪掉**。剪枝的判据是"这个名字在产物里只出现两次
（自己的原型 + 定义）"，而 C 侧调用的符号在 extC 侧**没人提** ⇒ 与 `main` 同一档，不登记进
`deadFuncs`。

**验收（`tests/cabi/`，实测）**：三个导出（标量 · 指向 `@frozen` 的指针 · **按值**返回 `@frozen`）
编出的产物既**链接**进一份手写 C 宿主（`triple=42 mid=7 pair=(3,4)`），又单独编成 `.so` 用
`nm -D` 查到 `T triple / T mid / T makePair` —— 后者正是 `dlsym` 的前提。加十条反例（泛型 · 方法 ·
`extern!` · C 关键字名 · `slice` 参数 · 隐藏 arena · 写两遍 · 标在 struct / 全局上 · 两个模块重名）。

### ② `fn` 字段的 `effects` 签字（已完成）

表槽是函数指针，而签字从前只挂在**声明**上（`collectEffects` 只对 `extern!` 读那条子句）——
表的被调方不是声明（宿主运行期才填地址），所以那句话没有别的地方可写。现在写在**槽**上：

```extc
struct extc_heap_api {
    size:  u64
    ctx:   ?ref void
    alloc: fn(i64, ?ref void) -> ref u8 effects Addr=0 Cont=0
    free:  fn(ref u8, ?ref void) -> i32 effects Addr=0 Cont=0
}
```

三件事值得记下来：

1. **同一把尺子**：调用点把掩码交给 `checkCallRefArgs` 的 **extern 那条路**（合成一份声明），
   所以"签字的槽"与"签字的 `extern!`"不可能漂 —— 这正是 §9.5 那条"一处理一处"。
2. **顺带补掉一个真洞**：从前经 `fn` 值调用走的是 `callee == NULL` 的**非 extern** 保守路径，
   而那条路的界是"被调方拿到的那只 arena 活多久"—— 经指针调用的被调方**根本没拿到 arena**，
   于是帧内指针能被交出去（实测：没签字的槽放行了 `ref x`）。现在没签字的槽拿到的正是
   `extern!` 的最坏情况（掩码全 1），拒绝帧内指针 ✓。
3. **签名在槽上、不在类型上**：`fn(A) -> R` 这个**类型**没有地方写 effects（它不是声明），
   所以从槽里直接调带着签名，**拷贝到局部就丢了**（按最保守算）。这是刻意的边界，反例
   `errors/slot_copied_out.extc` 钉着。

`Thread=` 在字段上暂时**报错**（"还没有用"）：读它的那条检查（worker 里允许调谁）是冲着
**已解析**的调用去的，运行期填的槽不是；记下来却没人读，比拒绝更坏。

### ④ 端到端：表 + C 模块 + 一次区间检查（已完成）

`tests/cabi/`：**真编一个 `.so`**（`heapmod.c`），extC 宿主拿 `std::dl` 打开它、`dlsym` 到 `init`、
把地址经显式转换写成 `fn(mut ref heapapi) -> ref u8`、调它；模块只经**表**拿内存、回调宿主、
把板内指针还回来；宿主用**一次区间检查**验证后解引用。跑出来：

```
plate=ok byte=42 logged=2 outside=rejected
```

`outside=rejected` 是**判据的牙**：模块另有一个 `badPtr` 返回它自己一个静态变量的地址 ——
那个地址谁也看不出不该信，只有那一比较知道。

这一格又把四件事逼了出来（每一件都是"不做就写不出来"，不是顺手加的）：

1. **函数地址是常量**（`isConstInit` 里新的 `EX_IDENT`）：表**不能**零初始化（`fn` 没有零值 ——
   那正是 §9.5 定的），所以必须在声明处初始化；而表又必须放在顶层（模块可能长期持有它）
   ⇒ 全局初始化器里出现函数名必须是合法的。它本来就是 C 的静态初始化器能折叠的东西
   （`&f`）。顺带补了 `null`（C 的 `(void*)0`）与**常量的转换**（`i64(3)`）—— 表里那两行恰好这么写。
2. **全局的初始化器要能看见函数声明**：产物顺序是 结构体 → **全局** → 原型 → 函数体，
   于是 `static heapapi api = { .alloc = &hostAlloc };` 报 "`hostAlloc` undeclared here"。
   修法是给"初始化器里点名的函数"在全局之前补一份原型（后面的原型池会再写一遍，C 允许重复声明）。
3. **板内的地址怎么取**：`ref plate[i]` **不行**（只有变量与字段能取引用），要写 `plate[i..].data`
   （视图的 `data`）；而且这个视图**不能先存进局部** —— 那样逃逸分析看到的是"返回指向本帧局部的
   指针"（它只知道局部的深度，不知道视图指向全局），直接写 `plate[off..].data` 才对，临时视图的
   深度是板（全局，0）。
4. **指针 → 整数，一个方向**（`u64(p)` / `i64(p)`）：区间检查要它，而语言里本来连两个指针都
   不能比较（"引用不是值"）。这一条故意只开一个方向：数字变不回引用 ⇒ **指针能被验证、不能被
   伪造**，而且能对那个数字做的只有整数运算（比较、相减、当下标）。`u32(p)` 这种窄目标仍被拒
   （截断），错误消息就是"引用不是值"那一句。

**还没做的（写在这里免得下次重推）**：`HEAP.md` §2 的草稿写的是 `plate.holds(p)` 与
`p as ref i64` —— 前者要"板对象 + 一个能实现它的东西"（extC 侧实现不了：`holds` 里要比较两个
指针，而这一格只给了指针→整数，够写 `base <= u64(p) && u64(p) < base + n` ✓ 其实够了），
后者（**整数 → 引用**）**故意不开**：那是"把数字当指针用"，是另一个决定。所以今天复现 `holds`
要写成宿主里的一个函数（本测试就是这么做的），把它做成**板对象的方法**是下一步的事。

### ⑤ 还没做（第 5 步）
* **③ `std::dl`**：`open` / `close` / `sym`。两个缺口：extC 的 `str` **不是 NUL 结尾**的（库侧
  适配函数解决），以及从 `dlsym` 拿回来的 `ref void` 要变成 `fn(…)` —— 用**显式转换** `T(x)`
  （走"收窄必须写出来"那条既有的路，不新增 builtin）。
* **④ 端到端**：`gcc -shared` 编一个 C 模块导出 `init(table)` 填表，extC 宿主用 `std::dl` 打开、
  经签字的表槽调用、再经表里的函数指针调用，拿回一个指针用**一次区间检查**验证 —— 也就是把
  `prototype-heap/` 那套搬进语言。


（`tests/heap/`：保留 4 GiB 只让 RSS 涨 **4 KB**；commit 按 CHUNK = 1 MiB 走；板外指针 `holds`
为假、`copyIn` 的目标不在板内返回 -1；第二笔分配之后第一笔的视图仍可写（不搬家）。另有一条
`afterclose`：`close` 之后写板内指针 ⇒ **SIGSEGV**，测试检查退出码 139 且崩溃前的标记可见。）

四件"不做就写不出来"的事：

1. **指针的抹除方向**（§9.10 上一节 ①）：`mprotect` / `munmap` 的参数在 C 里就是 `void *`，
   而板手里是 `ref u8` 视图的 `data`。擦掉 pointee 类型不丢权限（`ref void` 什么都解引用不了）。
2. **视图造不出来** —— 这是第 ② 块。`slice<u8> { … }` 写不出（泛型实例没有结构体字面量，实测
   被当成"类型出现在表达式位置"拒绝），而 `ref void` → `ref T` 又故意不开。所以
   `extc_viewOf(p, n)` 由**编译器**给三行 C（`src/plate.c`，`@builtin` + `needPlateView` 触发）。
   它是"指针 + 长度 ⇒ 视图"的唯一入口，**不做任何检查**：谁调用谁负责（板用 `holds`，C 边界用
   声明处的签字）。
3. **`memcpy` 也需要一道门**：它的签名里有 `const void *` 与 `size_t`，而手写声明会与
   `<string.h>` 撞（`src/memfind.c` 的文件头记过同一件事）。`extc_memCopy` 与 `extc_viewOf`
   同一块发射，**按声明触发**（一个声明一个标志）—— 这一条是被闸门逼出来的：最初把它加进
   `extern!("extc-mem")` 那一块，`std::string` 的用户全都声明它 ⇒ **21 个产物逐字节变化**，
   golden 当场抓住。
4. **`mmap` 家族按 C 的原型声明，但返回类型写 `?ref u8`**：`<sys/mman.h>` 没被 include，所以
   声明是我们的；指针的指向类型在**声明处**定，这正是把保留区当视图用的前提。
   `MAP_FAILED` 是 `(void *)-1` 而不是 null ⇒ 用最高一页的地址比较来判失败。

两个副产物（都记了理由，不是顺手加的）：

* `isConstInit` 接受**无损**转换（`i64(3)`）—— 表与板的常量就这么写。带运行时检查的转换
  （`u64(4096)`，产物里是 `extc_narrowU(...)` 调用）**不算**常量：gcc 会报 "initializer element
  is not constant"。这是实测出来的（`let PAGE: u64 = u64(4096)` 编不过），所以库里的常量写字面量：
  `let CHUNK: u64 = 1048576`（`1024 * 1024` 是 i32 算术 ✗）。
* 崩溃可见的输出要**两道 flush**：`io::flushCout()`（cout 缓冲 → stdio）+ `flush()`（stdio → fd）。
  只做第一道时，`afterclose` 的标记在 SIGSEGV 后看不见（`atexit` 不跑，stdio 那 4 KB 缓冲整个丢掉）。

**还没做的**：Arena 兜底（`HEAP.md` §3：忘了 `close` 就由 open 它的那只 Arena 收）今天只是漏到
进程结束；只读借出（`mprotect` 成 `PROT_READ`，原型量过 ≈0.7 MiB 盈亏平衡）与"板的表"（§9.9 ④
那张 `extc_heap_api`）把它们接起来，是第 5 步。

## 9.11 第 5 步 ③：用**真的**第三方库画一张画（cairo 1.18.4）

前四步的 dl 测试用的都是我们自己编的 `.so`：签名我们写的、布局我们定的、行为我们知道。
这一节换成 `libcairo.so.2` —— 一个我们没参与过的库，没有它的头文件，也**不链接**它。

```
cairo=1.18.4 surface=ok png=ok green=30771 white=9532 edges=1111 drawn=1 center=ok
```

`tests/real-lib/cairo-logo.extc`：`dlopen` → 20 个 `dlsym` → 填一张带签名的表 → `plate` 里拿画布
内存 → 二十来个真 API 调用 → `cairo_surface_write_to_png` 落盘 512×512 的 PNG。

"画对了"不靠眼睛：绿色（边框 + 大括号 + 基线）30771 像素、白色（三个字母）9532 像素、四条边各有
绿色、中间横带有白色；同一组数字用 Python 解 PNG **独立复核过一遍**（30771 / 9532 / 1111 / mid=1）。
没有 cairo 的机器上这套测试**显式跳过**。

它逼出来的四件事（前两件是语言层的，值得记）：

1. **`extern!("libcairo")` 会去链接，不会去 dlopen**：声明写下去，链接器就找那些符号
   （实测 `undefined reference to cairo_select_font_face`）。dl 那条路上函数只是**地址**，所以
   这里一个 `extern!` 都没有 —— 全是 `dlsym`。
2. **地址必须有签名，而签名在槽上**：转换出来的 `fn` 值**没有签名** ⇒ 按最保守算（"它可能留住
   每一个实参"）⇒ 连一个 `var c: ref void = cr` 这样的本帧局部都会被拒（实测报
   "may be kept by C forever, but it points into this frame (depth 1)"）。于是把地址填进
   `struct cairoApi` 的**字段**，每个字段带 `effects`，调用点走槽的签名。**表要传下去，不能把
   函数指针拷出来** —— 拷出来签名就丢了。
3. **"可能留住"要求实参活得比这一帧久 ⇒ 指针要内联从板里取**：`cairo_image_surface_create_for_data`
   的槽签 `Addr=1`（surface 持有那块内存），而 `var px = pl.alloc(...)` 之后再传 `px.data` 会被拒
   （存进局部的视图在逃逸分析眼里只有本帧寿命）⇒ 写 `pl.view(off, n)!.data` 内联在调用点 ✓
   为此给板加了 `view(off, n)`（同一道门的另一个出口）。
4. **包一层 helper 会让签名失效**：把槽调用包进一个 extC 函数（`fn rgb(api, cr, ...)`）之后，
   那个 helper 的 effect 总结是 **incomplete**（实测 `EXTC_DBG_REFARGS=1`：`complete=0`，因为
   经函数指针的调用在收集阶段被记成 `effUnknown`），于是**它的调用者**不能再传本帧的指针
   （实测报 "points into a deeper scope (depth 1) than the arena this call may store it in"）。
   这条**已经修了**（§9.14）：经签字的槽调用现在并进所在函数的总结，不再把它记成 incomplete。

顺带两件小的：C 字符串反方向（`dl::cstrLen` / `dl::viewCStr`，`cairo_version_string` 那种），
以及库层的 `plate::view(off, n)`。

## 9.12 第 5 步 ①：板 + 表 + C 模块（HEAP.md §2 那张表，两边都签字）

```
init=16 holds=true byte=42 outside=rejected logged=16 closed=0
```

`tests/cabi/platetable.{extc,c}`：宿主开一块**真板**（`std::heap`：4 GiB 保留、按需 commit、
`close` 即 munmap），给模块一张 `@frozen` 的表，槽就是板的门（`alloc` / `copyOut`，两个槽都签
`Addr=0 Cont=0`）；模块（C，编成 `.so`）经表申请板内内存、写进去、回调宿主的门验一次，再把
**板内**与**板外**两种指针还回来 —— 后者被 `holds` 挡住（`outside=rejected` 是判据的牙）。

三条"不做就写不出来"的：

1. **两个方向都要签字**。宿主 → 模块的 `init` 也必须走**带签名的槽**：经"裸转换出来的 `fn` 值"
   调用按最保守算 ⇒ 连一个本帧的表都传不进去（§9.11 ② 那条）。所以这里有两张表：`plugin_api`
   （宿主 → 模块）与 `plate_api`（模块 → 宿主）。
2. **`ctx` 的真类型写在声明处**。C 那边是 `void *`，extC 这边写 `mut ref plate` —— 指针的指向类型
   在**声明处**定（§9.6/§9.7 的口径），于是门函数直接就能用那块板（`pl.allocPtr` / `pl.holdsRange`），
   **不需要全局、也不需要把类型从 `ref void` 里抠出来**（那条回路故意不存在）。模板也照样成立：
   `@frozen` 是对 C 的布局承诺，`tests/frozen` 的镜像测试担保它。
3. **"拿回一个指针，用一次区间检查验证"**：模块还回来的 `ref u8` 先过 `pl.holds`（一次比较），
   再用第 4 步的 `extc_viewOf` 变成视图才解引用（`byte=42`）。

两个被这件事逼出来的库 API（都记着理由）：

* `plate::allocPtr(n) -> ?ref u8`：门要的是**裸指针**，而"先 `alloc` 拿视图、再取 `.data`"会被逃逸
  分析挡住 —— 存进局部的视图在它眼里只有本帧寿命，`Addr=1` 那种签名要求活得更久（§9.11 ③）。
  板内部把视图做成**临时**的（`self.mem[a..b].data`），深度跟着 `self`（参数，0）⇒ 合法。
* `plate::holdsRange(p, n)`：门拿到的是"指针 + 长度"，而"先 `extc_viewOf` 变成视图再 `holdsView`"
  会让**那个门函数带上隐藏的 arena 参数**，于是它的地址不是 `fn` 值、放不进表槽（实测的报错很直白：
  "takes a hidden arena parameter, so its address is not a `fn` value"）。门要的本来也就是这一件事。

## 9.13 第 5 步 ②：只读借出（`mprotect PROT_READ`）

板的两个方法：`loanRO(off, n)` / `loanRW(off, n)`（`off` 必须页对齐；长度向上取整到页；
区间必须在**已 commit** 的板内）。

```
alloc=ok write=ok ro=true read=after-ro rw=true write2=ok closed=0      （tests/heap/loan.extc）
loaned ⇒ 写 ⇒ SIGSEGV（rc=139，崩溃前标记可见）                          （tests/heap/loanwrite.extc）
```

为什么要有它：大输入进来时"拷贝进板"是 1830 MB/s，而只读借出是**零拷贝**（`prototype-heap/`
4b 量过 21.6 GB/s，两次 `mprotect` 各 ≈370 µs ⇒ 盈亏平衡 ≈0.7 MiB）。代价是那段内存借出期间
**谁都不能写** —— 内核保证，写就是硬缺页，而这一条有专门的测试盯着。

## 9.14 第 5 步 ④：把槽的签名接进 effect 总结（包一层不再丢签名）

上一节 ④ 那条留下的口子。修之前，把槽调用包进一个 extC 函数之后：

```
$ ./build/extc tests/cabi/slotsummary.extc
error: argument 1 of `inner` points into a deeper scope (depth 1) than the arena this call
       may store it in (depth 0)
```

槽明明签着 `Addr=0 Cont=0`（"我不留你的指针"），却因为**总结不完整**按最坏情况办 —— 而一旦那个
调用点有一个"活到帧外"的目的地（深度 0，比如从 C 回来的指针、指向全局的指针），实参里的本帧局部
就被拒。cairo 那次就是这么被逼着把画图的调用一行行摊在 `main` 里的。

**修法**（`src/check_top.c` 的 `collectEffectsExpr`）：经 `fn` 值调用时，如果那个值来自**带
`effects` 的槽**，就把槽的掩码并进本函数的总结，并**保持 complete** —— 它与 `extern!` 上的子句
是同一件事（同一个解析器、同一套键，调用点的签名本来就是从它建出来的）：

* `Addr` 第 j 位 ⇒ 那个实参的"地址"被留下 ⇒ 能追到本函数的某个参数就把那位点上（`addrMask`），
  追不上就记 `otherMask`（"不可归属"，调用点读作最严）；
* 槽**没签**（或值只是局部拷贝、参数传来）⇒ 仍然 `effUnknown`（总结不完整，保守）—— 这一条没变。

修完 `wrapped=41 twice=41`（包两层、传本帧局部都编得过），而**没有放松别处**：

* `make` 0 诊断 · `tools/golden.sh` **414/414 逐字节不变**（effects 只影响检查，不影响产物）·
  `./check.sh quick` **49/0**（含逃逸/借用那几套判据：`ref_arg_too_deep`、`borrowed_into_param_place`）。

**还没修的（同一片区域，记在这里免得下次重推）**：槽签 `Addr=1`（"我留下你的指针"）时，
**直接**在调用点经槽调用会被正确处理（报 "may be kept by C forever, but it points into this frame"），
但**包一层**之后那层要求会退化成"活得比我的某个 ref 实参久"—— 因为总结的词汇表里没有"存到 C 自己的
内存里（永久）"这一档：`addrMask`/`contMask`/`homeAddrMask` 说的都是"存进调用方给的某处"。
要补就得给总结加一档（例如 `foreignMask`：这些位置的实参必须深度 0），那是独立的一步。

## 9.15 第 5 步 ⑤：`effects Ret=0` —— 库签一次，用户零签字

用户的目标是"**随心所欲 dlopen 任何库、一个字都不签**"，而签字又不能因此消失（那是安全性）。
分开这两件事的办法：**让"需要签的那一条事实"落在能证明它的那一层**（库里签一次），用户只在
"把帧内地址就地交给 C"时才需要自己签 —— 而这正是 `std::fs` 早已在做的事
（`sys::io` 里 `read`/`write` 各一句 `Addr=0 Cont=0`，用户写 `f.readAll(buf[..])?` 时什么都不写）。

新的事实：**`effects Ret=0` = "我返回的引用/视图不指向调用方的任何帧"**（`Addr` 的返回侧）。

* `std::heap` 的四个出口（`alloc` / `allocPtr` / `view` / `store`）各签一句 —— 板是 `mmap` 来的、
  活到 `close`，所以它是**真的**；
* 检查器把它记到绑定上（`Sym.outOfFrame`），于是**视图**绑定的深度不再取"槽所在的块"，而取
  "它指向的存储" ⇒ 用户可以把板内视图**存进局部**再交给任何**没签字**的 C 函数（从前报
  "points into this frame (depth 1)"）；
* 同一个判定也认**根在全局**的视图（静态存储，天然不在帧里）—— 不需要谁签；
* **帧内的东西一律不认**：栈数组、`new`、arena 的视图仍然被拒 ✓（这是 `effects` 唯一必须存在的
  理由：把帧内地址**就地**交给 C，需要那句"我不留"）；
* **赋值即收回**：签过字的绑定一旦被再赋值（`v = buf[..]`），信任立刻撤销 —— 否则
  `if c { v = mem[..] } else { v = buf[..] }` 会留着一条分支的信任去放另一条分支的帧内视图。

实测（`tests/cabi/outframe.extc` + 三条反例）：

| 形状（调用点是一个**没签字**的 dl 函数，最坏情况） | 结果 |
|---|---|
| `var v = pl.alloc(n)!` → `f(v.data)`（板内视图存局部） | **过 ✓** |
| `var v = pl.view(off, n)!` → `f(v.data)` | **过 ✓** |
| `var g = mem[..]`（全局）→ `f(g.data)` | **过 ✓** |
| `var p = pl.allocPtr(n)!` → `f(p)` | **过 ✓**（本就是 `ref`，一直可以） |
| 栈数组视图 / `new` 视图 / 赋值之后的视图 | **拒 ✓** |

语言侧的改动很小：`effects` 多一个键（`Ret=0|1`，与 `Addr`/`Cont` 同一个解析器）；带身体的 extC 函数
也可以写它（**只准 `Ret`/`Thread`** —— `Addr`/`Cont` 由身体算，写了会报错而不是静默失效，这一条是
为了不让"签字"变成装饰）。

判据：`make` 0 诊断 · `tools/golden.sh` **414/414 逐字节不变**（这次没有产物变化：事实只来自
作者写的 `Ret=0` 与全局根，不像上一版那样去读"还没算出来"的 0 哨兵）· `./check.sh quick` **49/0**。

## 9.16 第 5 步 ⑥：绑定生成器（`tools/cbindgen.py`）

用户在 9.15 之后的目标是"随心所欲 dlopen 任何库、一个字都不签"。剩下的是**工具问题**，不是语言
问题，所以做成了一个构建期工具（在 extc 仓库里，但**不为每个库建 stdlib 模块** —— 产出写到用户
自己的项目路径）。

```
$ python3 tools/cbindgen.py @tools/cbindgen-cairo.args --include cairo.h -I <cairo 头>
生成 tests/real-lib/cairoapi.extc：19 个函数，3 组枚举
$ CAIRO_INC=<cairo 头> ./tests/real-lib/run.sh
ok   cbindgen  ->  ok  tests/real-lib/cairoapi.extc 与头文件一致（19 个函数）
ok   cairo      ->  cairo=1.18.4 surface=ok png=ok green=30771 white=9532 edges=1111 drawn=1 center=ok
```

那个夹具现在**用生成出来的绑定**画同一张画，判据不变（同一组像素数 = 类型映射没错）。

三条刻意的"不做"：

1. **不生成 `effects`**。槽不签 = 最坏情况 = 安全的那一侧；只有"帧内地址就地交给 C"要人签一句。
   （`cairo_text_extents` 就是那一个：`te` 在栈上 ⇒ 夹具里手写的 `textApi` 只有这一个槽，签了
   `Addr=0 Cont=0`。19 个自动，1 个人写 —— 这就是 9.15 那条规则的实际形状。）
2. **不假装布局**。不认识的指针一律 `?ref void`；要读字段就人写 `@frozen` 镜像（§9.8）。
3. **不猜**。按值传的结构体/变参等直接列出来并非 0 退出；枚举常量由 clang **求值**（JSON AST 对
   隐式值是空的 —— 试过数组初始值也不折叠，所以最后是"编个小程序打印出来再读回"）；求不出来就
   **跳过并报告**，绝不给一个猜测值。

**实测的一条使用细节**：生成的槽没签字 ⇒ 包一层 extC helper 时，那个 helper 的总结是 incomplete
⇒ 它的调用者不能再把**本帧**的表地址（`ref c`）传进去 ✗。两种解法都写进夹具注释了：
把表**按值**传（callee 拿自己的副本，什么都不悬 ✓），或者给那几个槽签 `Addr=0 Cont=0` ✓。

| 同上，缓冲区在**板**里且宿主已 `close()` | **rc=139** 硬缺页 | 设计 ✓ |
| `munmap` 掉宿主的板 + **同址重映射**自己的页 | `hijacked=65`：区间没变 ⇒ 检查照样通过 | 攻击 ✗ |
| 改宿主**表里的槽**（`mut ref` 交出去，且槽签了字） | `slot-hijacked=1042`：之后宿主经它调用跑到模块的代码上 | 攻击 ✗ |
| 同上，但槽**没签字** | **编译期就挡住**："may be kept by C forever, but it points into this frame" | 设计 ✓ |

**一句话**：这套东西**防错不防敌**（HEAP.md 早就这么写：能力模型，不是沙箱）。一个 dlopen 进来的
模块跟主程序同一个进程、同样的权限 —— 它要真想干坏事，`munmap`/改表/越界写都能干成；但它**干错事
的时候**（bug、越界、忘了约定）大部分会变成编译错误、一次区间检查拒绝、或者一次响亮的硬缺页，
而不是悄悄读到别人的数据。C 里这两种情况没有区别：全靠人小心。

这次攻击测试**抓到了两处真问题**（都已修）：
1. **生成器原来假设 `!` 会 trap** —— 实测 `null!` 拿到 0（纯编译期签字）。所以缺符号会得到一张
   全是空指针的表、第一次调用跳 null。现在 `open` 逐个人工判空并把缺的符号名说出来。
2. **`use std::io` 之后本模块里的 `fn open` 报 "duplicate function `open`"** —— 导入一个模块会把
   它（连同**传递导入**的）顶层名字占住，哪怕调用要写限定名。生成的取符号/填充因此改成挂在类型上的
   关联函数（`api::needSym` / `api::open`，与 `ifstream::new` 同一风格），天然不占通用名。

## 9.19 分析精度：两处"复用已有框架"的修复（定案 97）

写 §9.18 那份 93 行的 C ABI 全貌时，8 次编译尝试里有 3 次撞在**分析本身**上（不是设计）。摊开看，
两处的根因是同一句话：**框架早就有这个答案，是某条路没有去问它**。

**① `match` 的 payload 拷贝没做"收窄"。** `declare()` 的注释把契约写得很清楚：

> "A reference-typed binding starts with the depth of its slot as the pointee depth, the conservative
> answer. **Whoever knows the initializer narrows this to the real depth afterwards**"

`var` 那条路做了（`exprRefDepth` + home-arena 修正 + `outOfFrame`），`match` 那条路**只调了 `declare`
就完事** ✗。于是这份**指针的拷贝**被当成"借了 arm 块里的局部变量"：

```extc
match dl::sym(h, n) {
    some(p) => { return p }      // ✗ this return value would hold a reference to a local
    none    => { trap("没有") }   //    variable that dies first (borrowed from depth 2)
}
```

**后果比"多写几个字"严重得多**：检查过的那条路不可写 ⇒ 只剩 `!`（不检查的签字）⇒ "不方便"和
"不安全"是同一个 bug 的两面。修法是复用：payload 的引用指向哪儿 = scrutinee 的引用指向哪儿，
而 scrutinee 的**绑定上**已经有这个答案（`exprRefDepth` 对标识符正是去读绑定，见 `check_escape.c`
里那段"binding's depth is authoritative on the binding, not on the expression node"）。

**② 目的地深度的代理把 `ref u8` 也算进去了。** 调用点用"引用型实参里最浅的那个"当作"callee 可能
存进去的 arena 深度"。但只有**能装引用的东西**才可能是目的地（容器、板、带 ref 字段的记录）；
`ref u8` 不是。算进去的后果：一个 depth 0 的实参（全局内存的视图）把目的地压成"活到永远"⇒ 连
callee **自己的表**（局部）都被判"活得不够久" ✗（实测 `pl.viewAt(全局视图.data, 4)`）。修法同样是
复用：用框架自己的 `typeContainsRef` 当过滤条件。

**判据**：`tests/cabi/checked_path.extc`（`match` 取指针再还回去 ✓、取标量 ✓、depth 0 实参不再
压垮目的地且**运行时照样被区间检查拒** ✓）· golden **414/414 逐字节不变**（两处都是精度修复：
只把"误拒"变成"接受"，没有一个已有生成物改变 ⇒ 这也正是它们安全的原因）· `./check.sh quick`
**51/0** · 带超时扫描 414/0/42s。

**留一条规矩**（定案 97）：新增"声明一个绑定"的路径时，必须复用 `declare` 的收窄契约 —— 谁引入
新的绑定点（`match`、`yield`、将来的 `if let`……），谁就要问一句"我知道初始化器吗"。
