# 函数指针与 C ABI

> **一句话**：extC 本来就生成 C，所以 C 的 ABI 是**资产**而不是负担；函数指针是拿到这份资产的钥匙。
> 它不新增安全面 —— 它只把"这段代码还在吗"这个问题，交给我们已经有答案的那套（世代句柄 + 卸载协议）。

## 0. 为什么现在要它

`HEAP.md` §2 那张 `extc_heap_api` 表**整张都是函数指针**，而语言里没有这个类型。于是那条线卡在一格上：
不改语言，就写不出那页文档。这是唯一一处"文档跑在语言前面"的地方。

同时要看清：这条线**不是**为了把函数指针当日常工具用（那不是 C 的用法，也不是 extC 的用法），
而是为了**边界**——`dlopen` 进来的模块、以及我们自己链接的 C 库。日常的分发继续用枚举 + `match`（§1 第三条）。

## 1. 三条线（这一页的全部结论，其余都是推论）

1. **跨界只有裸函数指针**：`fn(A) -> R` 是**代码指针**，**没有环境**。需要状态就显式传 `ctx`
   （`HEAP.md` 的表里那只 `ctx` 就是这个用法）。
2. **方向定死**：**模块 → 宿主免费**（宿主代码与内存比模块活得久，`HEAP.md` §4 那条不对称规则）；
   **宿主 → 模块只经世代句柄**（宿主永不持有模块的裸代码指针）。
3. **闭集分发仍用枚举 + `match`**：`fn` 只为"被调方编译期未知"的场合存在。

在这三条内，函数指针**不新增安全面**：

* 它是一个**值**，和 `ref T` 没有种类差别；危险从来是**寿命**与**权限**两件事，
* 而"代码还在吗"＝世代句柄 + 卸载协议（`HEAP.md` §4，已写），
* "它能碰什么"＝它的**参数** + **它自己模块的全局**（§6），与 `HEAP.md` §1.5 那条链同一个答案。

## 2. 类型：`fn(A, B) -> R`

* **是什么**：一个代码指针。`fn(i64) -> i64` 在 C 里就是 `int64_t (*)(int64_t)`，一一对应，没有包装。
* **能出现在哪**：参数、返回值、**结构体字段**、泛型实参、数组元素、`slice<T>` 的元素 `T`。
  它是普通值，所以出现在这些地方都不需要新规则。
* **不能是什么**：
  * **没有空值**。要可空就用 `option<fn(A) -> R>`（与语言其它地方一致），不引入 `null` 函数。
  * **不带环境**。带捕获的闭包**不能**变成 `fn` —— 那需要 `{code, env}` 两个词，属于"闭包当值"那条线，
    这一页不开（§7）。
  * **捕获为零的闭包可以**：`fn(x: i64) { return x * 2 }` 本身就是个静态函数，转成 `fn(i64) -> i64` 是零成本的。
    检查器已经在算捕获（`EX_LAMBDA.captures`），所以这条规则**可判定**，不需要新分析。
* **不承诺**：可调用性的副作用信息照旧由 `effects` 那套表述（`Addr=` / `Cont=` / `Thread=`），
  函数指针的**目标**若来自外来模块，其效果只能按"最保守"记 —— 这一点与 `extern!` 同规。

## 3. ABI 承诺：不比平台 C ABI 多一个字

`fn(A) -> R` 的 ABI 就是**平台 C 的函数指针 ABI**。我们不发明调用约定：

* 参数按平台 C ABI 传（含结构体按值、`f32/f64`、小整数提升 —— 都由平台定）；
* 返回值按平台 C ABI（含结构体返回值的那几种传递方式）；
* 产物本来就以 `-std=c11 -fwrapv` 编译（`HEAP.md` 与 `LIB` 那条线同规），所以"另一侧"只要也是
  同一个平台的 C 编译器，就对得上。

**这条是有意的**：任何自定义约定都会把 C ABI 生态换掉，而那正是我们要拿的东西。
代价是：**跨界的结构体布局必须与 C 一致** —— 那是下一格（§9 第 2 步），不是这一格。

## 4. 进入外来的两条路：表是主路

| 路 | 用途 | 谁提供 |
|---|---|---|
| **版本化的表**（`HEAP.md` §2，头字段是 `size` + `ctx`）| `dlopen` 进来的模块 | **宿主** |
| `extern!("…")` 声明 | 我们自己链接的 C 库（`memfind`、`time`、…）| 链接期符号 |

**不做符号 interposition**（`HEAP.md` §7）：模块不靠解析宿主符号，宿主也不接管模块的符号。
两条路都只传**值**：表是数据，`extern!` 是符号，函数指针在两条路上都只是"表里的一个字段 / 一个实参"。

## 5. 回调（这题最尖的地方）

三个方向必须分开看，混起来就会得出"回调很危险"的错结论：

| 方向 | 判定 | 凭什么是 |
|---|---|---|
| 宿主 → 模块 | 安全 | 指针是宿主自己从**已加载**的模块拿到的，模块还开着 |
| **模块 → 宿主** | **免费安全** | 宿主代码/内存**比模块活得久**（`HEAP.md` §4 不对称规则）|
| **模块注册回调给宿主** | 需要机制 | 宿主将持有**模块**的指针 ⇒ **禁止裸指针，只给 `{slot, gen}` 世代句柄** |

第三行不用新东西：`HEAP.md` §4 已经定了——**注册一律给世代句柄**，`dlclose` 之前先把该模块的槽
世代加一，之后旧句柄来用就是当场 trap（那套保护的是**代码**，不只是数据）；卸载四步协议
（停发新活 → `deinit` → 作废世代 → `dlclose`）+ "在模块里跑着的调用计数"照旧。

**回调不需要是闭包**：要状态就显式 `ctx`（表里那只，或每个注册项自己的 `ctx`）。
于是 §1 第一条能一直成立，而"闭包当值"那条线可以继续关着。

## 6. 寿命与权限，按代码指针重述一遍

* **寿命**：一个 `fn` 值**不得比"保证这段代码存在"的东西活得久**。
  * 程序内的函数：静态存在 ⇒ 没有寿命问题；
  * 外来模块的函数：由 §4/§5 的**世代句柄 + 卸载协议**保证；
  * 结论：不需要为 `fn` 新增任何生命周期规则 —— 需要的那条已经有了。
* **权限**：调用它能碰到的，是**它的参数** + **它自己模块的全局**。
  它拿不到宿主的隐式状态（不 interposition、没有"按名字要全局"、表是显式递过去的），
  这与 `HEAP.md` §1.5 是同一个能力论证。

## 7. 明确不做（这一页不开的门）

* **不做**带环境的函数指针跨界（要状态就 `ctx`）；
* **不做**"闭包当一等值"（那是另一条线，见 `LAMBDA.md` 的状态）；
* **不做**自定义调用约定 / 自造 ABI；
* **不做**符号 interposition / 全局钩子；
* **不做**多进程沙箱（`HEAP.md` §7 已定）；
* **不做**函数指针的"可空"（用 `option`）；
* **不做**函数指针的相等/哈希语义承诺（代码地址可能被合并，`==` 只在同一模块内可比 —— 待作者拍，§8）。

## 8. 要作者拍的（我按实现侧给建议，但决定权是作者的）

1. **`fn` 是类型关键字还是别的写法**？（建议：与现有 lambda 的签名写法**同一个拼法** `fn(A) -> R`，
   只是这次它出现在**类型位置**——`var f: fn(i64) -> i64 = …`。语法上零新增。）
2. **捕获为零的 lambda 允许自动转成 `fn` 吗**？（建议允许，理由在 §2；检查器已有捕获信息。）
3. **`fn` 允许做泛型参数吗**（`vector<fn(i64) -> i64>`）？（建议允许：它是普通值；但这是本页语义上最大的一步，
   如果作者想先收着，就限制"`fn` 只能在签名与结构体字段里"。）
4. **`fn` 能放进 `@private`/跨模块边界自由传递吗**？（建议：能。它是值，没有资源。）
5. **`extern!` 是否降级为"只给我们自己链接的库"**（表成为唯一的外来入口）？（建议是，与 §4 一致。）
6. **可空**：`option<fn(A) -> R>` 就够，还是想要 `?fn` 这种更短的写法？（建议前者。）

## 9. 实施顺序（每步都能单独过闸门）

1. **类型 + 解析 + 检查 + 下降**：`fn(A) -> R` 作为类型；下降就是 C 的函数指针类型。**不动 prelude**
   （在 prelude 里加声明会改所有产物；类型不是声明，天然零位移）。判据：产物逐字节不变（语料里没有
   这个类型 ⇒ golden 414/414 应不动）。
2. **跨界的结构体布局**：`extc_heap_api` 那种表要按 C 布局。这一格与 `HEAP.md` §2 一起做。
3. **`std::dl`**：`dlopen/dlsym/dlclose` 的 `extern!` 声明 + 表的分发；第一个用户是 `prototype-heap/`
   那套（纯 C 原型已经在跑，见其 README）。
4. **Heap 板进运行期**：`mmap` 保留 + 按需 commit + 那道门（区间检查）+ `close` 即 `munmap`。
   到这里 `HEAP.md` 才有实现可指。

## 9.5 第 1 步的实施笔记（2026-09-29 摸地形后写，动手前先看这段）

**会牵动哪些文件**：`ast.h`（新增 `TY_FN` + 两个字段：参数类型表与返回类型）、`parser.c`（**类型位置**接受
`fn(A, B) -> R`）、`types.c`（intern 键、等价判断、`typeName` —— 那里有 21 处 `case TY_`）、`codegen.c`
（`cType` 的 11 处分派）。语法零新增：`fn(...)` 的拼法与 lambda 一致，只是这次在类型位置。

**必须先解决的坑（否则会在每个使用点炸）**：`cType` 在本项目里是**"类型文本"**，调用点普遍按
`"%s %s"`（类型 + 名字）拼接。而 C 的函数指针声明符**要把名字包进中间**：

```c
int64_t (*)(int64_t)          /* 类型文本能是它 */
int64_t (*f)(int64_t)         /* 但"类型文本 + 名字"拼出来是坏的 */
```

⇒ **函数类型一律走 typedef**：按需在产物前言里发一条
`typedef int64_t (*extc_fn_i64_i64)(int64_t);`，类型文本就用那个名字。这与本仓库"按需发射运行期"的
老套路一致（`needMemFind` / `needTime` / `needDomain` 都是这个形状），而且**typedef 的名字进 mangle**
⇒ 同一个函数类型只会发一条。**不要**去改所有 `%s %s` 调用点（那是把一个小改动摊成一次大手术）。

**三个要在这一步就定的小问题**（都在 §8 的建议之内）：

1. **怎么造出一个 `fn` 值**：最省的第一步是"**函数名当值**"（`var f: fn(i64) -> i64 = double_it` ⇒ 下降成
   `&double_it`），它比"捕获为零的 lambda 自动转"更小 —— 后者留给下一步。
2. **不初始化怎么办**：语言的规矩是"没有初始化器 ⇒ 零初始化"，而零值的函数指针是 **NULL**，
   与 §2"没有空值"直接冲突。第 1 步先让"声明一个 `fn` 而不初始化"**编译期报错**（要空就用
   `option<fn …>`），别在运行期留一个能跳进去的空指针。
3. **相等/哈希**：这一步**不承诺**（§7 最后一条）。要比较就等作者拍。

**判据（第 1 步）**：make 0 诊断；语料里没有程序用这个类型 ⇒ **golden 414/414 逐字节不动**；
带超时的单遍扫描 0 变化；探针写进 `tests/ops/`（一个函数名赋给 `fn` 变量、当参数传、当返回值返回、
放进结构体字段各一次）。

## 9.6 第 1 步落地实录（2026-09-29，全部判据已过）

**做出来的东西**：`fn(A, B) -> R` 是一个**普通值类型**。函数名当值（`&f`）、经指针调用（`f(x)`，
字段里的 `o.f(x)` 也是）、参数/返回值/结构体字段/泛型实参都能放。`TY_FN` 的 C 文本是**typedef 名**
（`extc_fn_i64__i64`；分隔用 `__` 而不是一个 `_`，因为 mangle 自己就用单个 `_` 连接部件 ——
`pair_i32_u8`，一个 `_` 会被读成名字的一部分），typedef 按需发射在**枚举之后、结构体 forward typedef
之后、结构体定义之前** ——
那个位置是唯一的：签名要能命名枚举与结构体，而结构体**字段**要能命名签名。
"哪些函数类型要发"这件事**没有专门的扫描**：`tt->fnTypes` 就是需求集（每个被写出来的 `fn` 都过
`ttFn`）。语料里没有 `fn` ⇒ 表是空的 ⇒ 一个字节都不动 ✓（**golden 414/414 逐字节不变**，实测）。

**四个当场发现、当场修的坑**（都会产生"合法但错"的产物，或者指向错东西的诊断）：

1. **共享走查器故意不看 call 的 callee**（`ast.c`：callee 是**名字**不是表达式）。而经值调用的 callee
   恰恰是一次**读取**。不修的症状：`fn apply(f: fn(i64) -> i64, …)` 报 "parameter `f` is never used" ——
   函数体里唯一的语句就在调它。现在只在 `callViaFn` 时把 callee 当子节点。
2. **`o.f(x)` 是 parser 眼里的方法调用**（`EX_METHOD`），不是 `EX_CALL` ⇒ 字段里的函数会得到
   "no method `f` on `op`" —— 一句说错对象的话。修法：在方法解析**之前**用 `peekFieldType` 偷看一眼
   字段类型（**不检查表达式**，否则普通方法调用的接收者会被检查两遍），是 `fn` 就原地改写成经值调用。
3. **零值**：`typeLacksZeroValue(TY_FN) = true`，于是"声明 `fn` 不初始化"由**已有那条**零值规则挡住，
   而且诊断按 `typeContainsFn` 分成两句（`ref` 那句会让人去找一个不存在的引用）。`codegen` 的
   `zeroValue` 里补了一条防御：`fn` 的零值发射成一个**不存在的标识符**（让 gcc 点名），而不是 `0`
   —— `0` 是一个**空代码指针**。
4. **隐藏参数**：编译器给"收 home arena / zone"的函数偷偷加参数，那些标志是**可传递闭包**，只有在
   所有函数体查完之后才定。所以"这个函数的地址能不能当 `fn` 值"在检查期**答不了**，由 codegen 在
   标志已终局处拒绝（报错，不是发一个类型不匹配的指针让 gcc 去吼）。

**顺带收掉的一处重复**：`extern!` 的"什么能过 C 边界"原本在 `check_top.c` 里**手抄了两遍**，而且
两处都带一个**永远走不到的分支**（对一个已经被 `ttBase` 剥光引用的类型问 `kind == TY_REF`）。
现在只有一处 `ttCrossesC(t, isReturn)`，`fn` 的签名检查与 `extern!` 共用它 —— 这正是"`fn` 不该比
`extern!` 松"那条规则能被机器保证的原因。**`fn` 自己可以过界**（一个代码指针就是一个指针，C 一直
在传这种东西 —— `qsort` 的比较函数就是这个形状）。

**这一步没有关上的门（都记在这里，别当洞）**：

* **`fn` 的类型**签名只放行"标量 / 单指针（指向标量的）/ `fn`"。**指向声明类型的指针**（`ref point`）
  和 **`ref void`（C 的 `void *`）**今天过不去 —— 这不是新收窄，是 `extern!` 一直就有的窄；§9 第 2 步
  （跨界的结构体布局）才有资格放开它，因为那时"指向的那个东西长什么样"才有答案。`HEAP.md` §2 那张表
  里的 `ctx: ref void` 就是被这一格挡着的（**文档跑在代码前面的第二处**，第一处就是 `fn` 本身）。
* **`fn` 值没有地方签 `effects`**：签字是**声明**的属性（`collectEffects` 只对 `extern!` 读那条子句），
  裸代码指针没有声明 ⇒ 经 `fn` 调用的效果摘要只能是**最保守**（"它可能留住一切"）。后果：把帧内的
  `s.data` 经 `fn` 传出去会被拒（与"没签字的 `extern!`"同一档，安全但不好用）。给**类型**带签名的
  路（表字段上写 `effects`，或者签名别名）是 §9 第 3 步的事。
* **相等/哈希**：不承诺（§7）。`fn` 放不进 `==`，也不该放。
* **泛型体里的 `fn(T) -> T`**：模板检查时 `T` 未定，那条"能不能过 C 界"的检查**跳过**；实例化成
  不可过界的签名时今天**没有再查一遍**（没有程序能构造出这种实例：唯一的来源就是模板自己）。
  第 2 步改谓词时一起收。

**验收（实测，长在这里免得下次重新推）**：`make -j24` **0 诊断**；`tools/golden.sh` **414 个产物
逐字节不符 0 · 非法 C 0**；`./check.sh quick` **45/0**；`tests/ops` 新增正例 `fnptr.extc`
（值 / 参数 / 返回值 / 结构体字段 / **嵌套签名** `fn(fn(i64) -> i64, i64) -> i64` / **`extern!` 符号当值**
各一次）+ 四条反例（零值 · slice 签名 · 泛型裸名 · 结构体字段漏给）全过；手册加了
[3. 类型 § 函数指针](../manual/04-types.md) 一节，示例进 `check_manual_examples` 闸门（示例编不过就红）。

## 9.7 第 2 步：指针放开（2026-09-29 作者拍板"应该放开，不放开啥都写不了"）

**改了什么**：`ttCrossesC` 原来的规则是"**剥掉引用之后是个标量**"（于是 `ref u8` 能过、
`ref point` 与 `ref void` 都不能）。现在是：

> **一个机器字就能过**：标量 · 指向**任何东西**的指针（`ref T` / `mut ref T` / `?ref T`，含 `ref void`）
> · 函数指针 `fn(A) -> R`。**不是**一个机器字的一律不过：`slice<T>`（C 那边是两个参数）、
> 结构体/带载荷枚举**按值**（布局没冻结）、`void` 按值（它只是返回类型）。

配套的两件事：

1. **`ref void` 看不进去**：`*p` 在 `EX_DEREF` 处编译期报错（"`void` has no size"），`p[i]` 由已有的
   索引检查挡住。C 也会拒绝 `*(void*)p`，但它拒绝在**生成物**里 —— 错误指向一行作者没写过的代码。
   `ref void` 能做的只有：**传回给 C**、放进 `?ref void` 判空、当参数转手。
2. **结构体按值这一格不开**（与第 2 步分开）：见下。

### 它动不动安全？——不动类型安全，动的是"借出去的内存"这件事的边界

这是作者问的原话（"这会破坏我的类型安全吗"），答案按四条给，每条都能指到代码：

1. **指针没有布局问题**。一个对象指针就是一个机器字，指向什么不影响 ABI。**这一格与"结构体按值
   过界"是两种东西**：按值要两边布局逐字节一致，不一致是**静默错**（C 按错的偏移读写，不 trap 也
   不报错）⇒ 那一格需要"冻结布局 / `@reprC`"，本步**没开**，反例钉在
   `tests/extern/errors/struct_by_value.extc`。
2. **extC 能对新类型做的操作，一件都没新增**。`*p`、`p.f`、`p.m()`、`p[i]` 全部走现成规则
   （`mut` 权限、`?ref` 非空收窄、逃逸深度、`@private` 字段）。放宽只改了"**哪些类型的指针被允许
   出现在签名里**"，没有新增任何一条操作。
3. **寿命与权限一个字没改，而且正是它们在管这件事**。`checkCallRefArgs` 的判据是"**这个实参是
   `ref` 吗 + 它指向多深 + 被调方签名说没说它会存**"，与指向类型无关 —— 所以 `ref point` 和
   `ref u8` 走**同一条**规则：没签字的 `extern!` 拿帧内地址就报错
   （`errors/ptr_unsigned.extc` 钉着），签 `effects Addr=0 Cont=0` 才放行。
4. **真正变大的是"义务"，不是"漏洞"**：以前只能借出**没有内部指针**的内存（`ref u8`），
   现在能借出 `ref node`（`node` 里有 `?ref node`）⇒ C 可以**从我们内存里读出一个指针并留着**，
   那是 **`Cont`** 那一半的签名在管；反过来，C 也可以**往我们内存里写一个指针**（见下）。
   两件事都不是类型规则变松，而是"你把可写内存借给了外来代码"的固有含义。

**必须点名的一条后果**（写进手册 18-modules §12.3）：把 `mut ref T` 借给 C 之后，C 可以往 `T` 的
`?ref` 字段里写一个**它自己的指针**，之后 extC 会当真去解引用。挡它的办法只有三条，都是**声明处**
的选择，不是编译器的推断：(a) **只读借出**（声明写 `ref T` 而不是 `mut ref T`）；(b) 大块输入用
**只读映射**那种硬保证（`HEAP.md` 里那条 `mprotect` 的贷款，实测 ≈0.7 MiB 处盈亏平衡）；
(c) 在签字里写明 C 不写回指针 —— 今天那三个掩码（`Addr`/`Cont`/`Other`）描述的是"**从我这里往 C 流**"
的方向，**写回**方向还没有一个掩码；要不要加第四个（比如 `Wr`），等真有库需要它的时候再拍，
不先发明。

**这一步顺带核掉的一个隐患**：生成物里**没有 `restrict`**（`grep restrict src/*.c` 只命中
`base.c` 的 C 关键字表，那是给标识符重命名用的）。若有，C 存下指针再写就会与 extC 的读构成 UB ——
现在没有，写在这里是因为"指针放宽"之后这个前提值得被记住。

**验收（实测）**：`tests/extern` 新增正例 `capi.extc` + `capi-main.extc`（**真调 libc**：
`gettimeofday(ref tv, null)` 让 C 写进 extC 的结构体再读字段 · `mmap`/`munmap` 把 `void *` 进出一趟 ·
经 `fn(mut ref point) -> void` 的间接调用），三条反例（不签字的声明拿帧内指针 · `*p` on `ref void` ·
结构体按值）全过；`golden 414/414 逐字节不变`（放开只是**多接受**程序，语料里没有这种声明 ⇒
产物一字不动）；`check.sh quick 45/0`。

## 9.8 第 2.5 步：`@frozen` —— 布局的签字（2026-09-29 作者拍板"可以先加……就叫 @frozen"）

**为什么不是"编译器自己判"**：`ref T` 放开之后，唯一还挡着"按值传结构体"的就是**布局**。而
extC 的布局**今天就是 C 的布局**（产物本来就是 C：字段按声明顺序一条条印，没有隐藏字段）——
问题是**没人承诺过**，于是将来一次"按大小重排字段"（Rust 默认就这么干）或者一个"往结构体里塞个
判别位"的功能，都会让跨界调用**静默读错**：不 trap，不报错，只是值不对。

按作者的口径（"你不能阻止用户犯傻"），这一格**不**去做字段白名单，而是一个**签字**：

> **`@frozen`**：这个类型的字节布局 = C 为这份字段表排出来的布局 —— 字段按声明顺序、按 C 的
> 对齐与填充、里面**没有别的东西**。

**作者那一半**：往里放什么由作者定（`slice<T>`、枚举、泛型参数都行）。代价是 C 那边得照抄我们发射的
形状；对不上是作者的账 —— 与 `effects` 完全同类。**切片仍然不因为 `@frozen` 就变成一个参数**：
视图在 C 那边是两个，想传就写 `s.data` / `s.len`。

**编译器那一半（硬的，两条）**：

1. **永不重排字段、永不加隐藏字段。** 将来任何想要"把 tag / 世代号塞进结构体"的功能，只能放到别处。
2. **在产物里把它钉住**，每个 `@frozen` 类型两条**平台无关**的 `_Static_assert`：

```c
_Static_assert(offsetof(mixed, a) < offsetof(mixed, b),
               "extC @frozen: the fields stay in declaration order");
_Static_assert(sizeof(mixed) <= offsetof(mixed, arr) + sizeof(((mixed *)0)->arr) + _Alignof(mixed),
               "extC @frozen: nothing may be added to a frozen struct");
```

数字全部由 C 自己算（`offsetof` / `sizeof` / `_Alignof`），**不写死**：写死 `== 8` 会在对齐规则不同的
平台上把一次合法构建搞坏，那正是"冻结布局"的反面。两条断言各管一半：顺序（永不重排）· 尺寸
（`sizeof` 最多是"最后一个字段的末尾 + 本类型的对齐"，也就是 C 允许的尾部填充 ⇒ 多一个字段会露出来；
若新增的字段正好塞进已有的填充里，那 `sizeof` 没变、布局也没变，没什么可抓）。

**门票的粒度**：`ttCrossesC` 里一行 —— 按值过界只认 `sdef->frozen`（`TY_STRUCT` 与泛型实例都算）。
没标记的照旧拒，而且诊断现在**点名**该写什么。

### 这一格怎么验（`tests/frozen/`，四正四反 + 两条有牙）

* **真调 libc 的按值返回**：`imaxdiv` 返回 `{intmax_t quot; intmax_t rem;}`（两个 i64，System V 从
  RAX:RDX 回来）。`<inttypes.h>` 没被前言 include ⇒ 我们自己的声明不与它冲突 —— 与 `memcmp` 那条
  "库的签名里有 `size_t`/`void *`，所以只能走 shim" 是同一个道理的另一面。
* **字段形状凑齐**：i8 / i64 / f64 / bool / 可写指针 / `[4]u8` / 嵌套 `@frozen`（中间填充与尾部填充
  都被踩到）。
* **C 侧镜像**（这是"布局对得上"唯一能真验的办法）：`mirror-pre.h` 把产物的 `main` 改个名字，
  然后把**产物 + 一份手写等价 C 结构体**拼进同一个翻译单元，编译期断言 `sizeof` 相等、**每一个字段**的
  `offsetof` 相等，运行期再打印一行（`layout ok: mixed=64 inner=16 mixed2=16 (b@8 p@32 inr@48)`）。
  编译器看不见 C 那边的结构体；**镜像就是"那边"的一份抄本**，抄错了就红。
* **两条牙**（判据不能是摆设）：把产物里 `struct inner` 的两个字段调换 ⇒ 顺序断言必须响；
  把镜像里同样的两个字段调换 ⇒ `offsetof` 断言必须响。两条都实测会被抓。
* **五条反例**：没标记的按值 · `@frozen` 标在函数 / 枚举 / `impl` 上 · 写两遍。

**顺带核到的一件事**：把**带指针字段**的 `mixed` 经 `fn` 值传出去会被（正确地）拒 —— 未签字的代码指针
按"它可能留住一切"算，而 `mixed` 里有一个 `mut ref`。与 §9.7 那条"义务变大"是同一件事，验收里留着它
当活例（`tests/frozen/frozen.extc` 的注释）。

**判据**：`make -j24` 0 诊断；`tools/golden.sh` **414 个产物逐字节不变**（语料里没有 `@frozen` ⇒
一条断言都不发）；带超时扫描 414/0；`check.sh quick` 全绿（新增 `tests/frozen` 一项）。

## 9.9 第 3 步：让这张表在 extC 里写得出来（2026-09-29 开工）

§9.6 的 `fn` 让"代码指针"成为类型，§9.7 让指针过界，§9.8 让**按值**的结构体有门票。剩下的
是 §9 第 3 步那条线：**`std::dl` + `HEAP.md` §2 的表**。它拆成四块，每块单独过闸门、单独提交。

### ① `@export`：把符号交出去（已完成）

`extern!` 是"我调 C"，`@export` 是另一面："C 调我"。产物里它是**外部链接**的 C 符号，名字就是
源码里写的那个（模块前缀 `plugin$` 在符号上去掉 —— `$` 不是合法 extC 标识符，所以它只可能来自
加载器的改名）。C 那边直接链接或 `dlsym` 都行。

四条配套的硬规矩（每条都在它自己的位置报错，因为那里的答案才是终局）：

| 规矩 | 在哪报 | 为什么 |
|---|---|---|
| 签名每个参数/返回值是"C 能写的一个机器字或 `@frozen`" | 检查器（紧挨着 `extern!` 那条，**同一个 `ttCrossesC`**）| 边界的两半用一把尺子，才不会漂 |
| 不能有隐藏参数（home arena / zone）| codegen | 那是**可传递闭包**，只有查完所有函数体才知道 |
| 名字不能需要 C 改名（C 关键字）、不能与另一个导出重名 | codegen | 符号是契约，改名之后 C 猜不到 |
| 泛型 / 方法 / 协程 / `extern!` 不能导出 | 语法层（各有各的话）| 它们没有"那一个 C 符号" |

顺带一处必须做对的：**导出不能被可达性剪枝剪掉**。剪枝的判据是"这个名字在产物里只出现两次
（自己的原型 + 定义）"，而 C 侧调用的符号在 extC 侧**没人提** ⇒ 与 `main` 同一档，不登记进
`deadFuncs`。

**验收（`tests/cabi/`，实测）**：三个导出（标量 · 指向 `@frozen` 的指针 · **按值**返回 `@frozen`）
编出的产物既**链接**进一份手写 C 宿主（`triple=42 mid=7 pair=(3,4)`），又单独编成 `.so` 用
`nm -D` 查到 `T triple / T mid / T makePair` —— 后者正是 `dlsym` 的前提。加十条反例（泛型 · 方法 ·
`extern!` · C 关键字名 · `slice` 参数 · 隐藏 arena · 写两遍 · 标在 struct / 全局上 · 两个模块重名）。

### ②③④ 还没做

* **② `fn` 字段的 `effects` 签字**：表槽是函数指针，而签字今天只挂在**声明**上（`collectEffects`
  只对 `extern!` 读那条子句）。没有它，经表槽的调用只能按"它可能留住一切"算 —— 与"没签字的
  `extern!`"同一档：安全，但表不好用。做法：把子句写在**字段**上（`alloc: fn(…) -> ref u8 effects
  Addr=0 Cont=0`），调用时把掩码喂给 `checkCallRefArgs` 的 extern 那条路（**不写第二份规则**）。
* **③ `std::dl`**：`open` / `close` / `sym`。两个缺口：extC 的 `str` **不是 NUL 结尾**的（库侧
  适配函数解决），以及从 `dlsym` 拿回来的 `ref void` 要变成 `fn(…)` —— 用**显式转换** `T(x)`
  （走"收窄必须写出来"那条既有的路，不新增 builtin）。
* **④ 端到端**：`gcc -shared` 编一个 C 模块导出 `init(table)` 填表，extC 宿主用 `std::dl` 打开、
  经签字的表槽调用、再经表里的函数指针调用，拿回一个指针用**一次区间检查**验证 —— 也就是把
  `prototype-heap/` 那套搬进语言。
