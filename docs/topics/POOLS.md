## 0. 命名

三层名字，互不打架，各自准确：

| 名字 | 是什么 | 释放点 |
|---|---|---|
| **arena** | 栈式的分配区；不可逐对象 free，只能整块还 | 拥有它的块退出时 |
| **pool** | 池式：等大元素、槽位复用、世代 handle、可手动释放 | 显式 `release`，或它所在的地方退出时 |
| **zone** | 一个「地方」里的一组 pool；本身也是栈式 | 该地方退出时 |

**为什么机制叫 pool，不叫 region**：内存管理领域里 *region-based memory management* 的
region 就是本文的 arena（按作用域整块释放的分配区）；拿它命名「等大元素 + 槽位复用 + 手动
释放」的东西，读者会先入为主地理解反。作者描述它时用的就是「池」。

**arena 这个名字是准的**：整体思路确实是 region-based，但这里的 arena 语义与工业界一致
（Zig 的 `ArenaAllocator`、Rust 的 `bumpalo`/`typed-arena`、C++ 的 arena allocator）：
指针一路 bump，不能逐个 free，只在作用域边界整块还。

**接口用词**（作者 2026-09-26）：

- 容器释放叫 **`release`**，不叫 `close`：作用域一结束这棵树本来就会被自动清空，
  `close` 会被读成「你负责关」
- 面向用户的两个操作：**`clear`**（清空，但索引还在）· **`shrink`**（缩容，把不用的空间让出去；
  比 compact 更贴切：真正有用的是把高水位降下来）
- **扩容像 vector**：容量不够就翻倍搬一次（dense 数组保持连续，`denseView`/SIMD 因此一直成立）；
  旧的块留给 arena，到地方退出时一起收

## 1. 它要解决什么

作者原话：

> region 是一种基于 ECS/Handle 的内存管理模式，旨在高效利用内存、保证内存安全和 SIMD 优化，
> 同时能够允许用户手动介入 GC，是为了弥补 arena 在管理删增动态度很大的数据结构时的劣势。

三个具体问题：

1. 用户无法手动回收容器里的垃圾（erase 掉的槽位、旧代缓冲永远留在 arena 里）
2. 无法复用（同一块内存不能重新利用，反复 add/erase 就线性涨）
3. 指针跳转导致 SIMD 难以优化（链式/树式结构，每次访问都是一次 cache miss）

主要应用面是 STL：`varArray` · `string` · `pool` · `map` · `set`，后续 `graph`。

动机是量出来的（`/usr/bin/time -f "%M"` 峰值 RSS）：

| 形状 | 峰值 RSS | 结论 |
|---|---|---|
| 翻倍长到 1e5，每轮在会退出的块里做（12 轮） | 2,640 KB | 平（块退出即还） |
| 一个数组从 1 翻倍长到 1e6（4 MB 活跃） | 9,900 KB | 约 2.4 倍，历代旧副本全留着 |
| 每轮新建/重建，分配点落在长命层（12 轮） | 14,184 KB | 随轮数线性涨 |
| 一次要够 | 5,676 KB | 只差进程基线 |

规则：arena 只在分配点那一层的块退出时回收，所以长命层里的分配是永久的，每轮新建则无界。
服务型程序（跨请求状态、缓存、会话表）必然撞在这上面。

## 2. 模型

整个模型不怎么讲堆和帧（作者 2026-09-26）：最后数据大多落在堆上，只是在堆上实现了不同的
内存管理方案。所以：

- 没有「帧」这个东西：组织单位是「一个地方」（作用域），不是函数帧。
- arena 是**寿命**的来源，它不只是栈：它是块链，管「哪块内存属于哪个地方、什么时候没」。
  **它不是唯一的内存来源** —— pool 有自己独立的一块（见下一条），两者的关系是**寿命**，不是包含。
- pool **持有自己的内存**：数据、free list、嵌套池各占自己的一块块空间，池把这些板块连成旁链/树，
  索引层本身不含数据。**生命周期与 arena 一起管**（地方退出时整块回收），但板块内部怎么分配、怎么伸缩、
  能不能还回去，是 pool 自己的事 —— 所以 `shrink` 能做真收缩、`release` 能立刻还内存，
  而 arena 里的 `new T[n]` 只能等地方结束。作者原话：

  > pool 的内存是独立的一个板块，只是生命周期给 arena 一起管理。

  这条口径**不是新加的**：从第一天起 pool 就是独立板块（图里画的就是这个），阶段表里那句「池不管内存」
  只该读成「池不管 arena 的块」，一度被误读成「池不拥有内存」，本文已按作者口径改正。
- zone 是虚概念：实现上不嵌在 arena 的栈里，而是一条独立的旁链。作者原话：

  > 这样子你才能够枚举 zone 自己啊，否则你块一回退不就全爆了。

- 一个地方可以有多个 pool（多个 STL 容器）。作者原话：

  > 如果一个地方里面有多个 region（就是多个 STL 容器的话），你需要多一层：就是
  > region 区 -> region 树 -> region 三层结构。

于是三层是：

```
zone（一个地方的索引头，独立旁链）
  └── pool 树（容器套容器：逻辑父子）
        └── pool（单个容器的那一份：数据 + 簿记）
```

zone 自己是链式还是数组随实现，反正都是指针指向实际的 pool 空间，它只是一个索引。

### 2.1 分层：pool 是**基础容器**，STL 容器是**逻辑**（作者 2026-09-26 口径）

作者原话：

> Pool 应该是一种基础容器，只负责存储、查询、压缩、重建等等，然后 STL 通过特定逻辑和 Pool 交互就可以
> 形成数据结构。有点像你写 OI 题的时候开一个静态大数组然后通过某种方式说这是链表 / 这是平衡树，
> 但是现在 Pool 是动态的。

于是分工是：

- **pool = 基础容器**：存储 · 句柄 · 查询 · **压缩** · **重建**。它不知道 map / set 是什么，也不含任何数据结构
  逻辑。槽面就是这一组，不需要新概念：`withCap` / `insert` / `get` / `set` / `contains` / `remove` /
  `len` / `capacity` / `grow` / `shrink`（压缩）/ `clear` / `release` / `atDense` / `denseView` /
  `handleAtDense` / `gather` / `toSlice`。**块面（`poolSlice<T>` / 归还旧块）是这一轮要补的第二副面**，
  见本节末「池有两副面」。
- **容器 = 纯逻辑**：把 pool 的**句柄**当数组下标用，自己决定怎么解释它 —— 哈希怎么探测、树怎么分裂、链表
  怎么串。和 OI 里「开一个大数组，然后用 `nxt[i]` 说这是链表」是同一件事，**区别只有一条：这块数组是
  动态的**（扩容、压缩、重建都由 pool 负责，逻辑只管解释）。

现状对照（哪里已经对了，哪里偏了）：

| 容器 | 现状 | 按分层看 |
|---|---|---|
| `hashMap<K, V>` | 桶表（`keys` / `tag` / `slot` / `bucketOfDense`）是逻辑，元素值住 `pool<V>` | 对，正是「逻辑 + pool 存储」 |
| `vector<T>` / `string` | 连续数组 + 一条运行期池记录，缓冲区来自 `new T[n]`（arena） | **偏**：连续序列不需要句柄（下标即位置），但**存储照样必须是池的** —— 缓冲区从自己的池板块拿，扩容时旧块立刻还回去；否则历代旧副本全留在 arena 里（见下） |
| `map<K, V>`（B+ 树） | 节点 / 键 / 值全在 arena 切片里，还自己手写了空闲链、翻倍扩容、`shrink` 压实 | **偏**：它在手搓一个 pool（这些活正是 pool 的），却没有句柄、没有染色、没有真板块 |
| `linMap<K, V>` / `linSet<T>` | 稠密数组 + 线性扫描 | **偏（但轻）**：那个稠密数组就是 pool 的稠密面（插入序、swap-remove 都在 pool 里），缺的只是「用 pool」 |

由此修正后续计划：

1. `map` 不再谈「把它的存储搬进它自己的池板块」，而是**直接用一个 `pool<bnode>`**：节点是池元素、孩子是
   **句柄**，分裂 / 借位 / 合并是纯逻辑；空闲链、扩容、压实交给 pool。
2. `linMap` / `linSet` 同理：**就是 pool + 线性扫描**（`atDense` / `denseView` 就是它的遍历面）。
3. 于是「pool 要有自己的板块」（`extc_pool_alloc` / `resize` / `free` + 「运行时内存 → `mut slice<T>`」那一步
   语言能力）从「优化」升级成**基础容器能不能成立的前提** —— pool 一旦是基础容器，它的存储就必须真是它
   自己的、能压缩能重建，而不是借 arena 的切片。

**裁决一（作者 2026-09-26）：`vector` / `string` 也走 pool，没有例外。** 作者原话：

> vector/string 你如果不在 pool 里就肯定在 arena 里面，那 arena 又没法扩容之后删掉旧数据，那不就完蛋了。

这条推翻本节初稿里「连续序列不需要 pool」的推断。理由是 §1 那张动机表的读数：一个数组从 1 翻倍长到 1e6
（活跃只有 4 MB）峰值 9,900 KB —— 历代旧副本全在 arena 里，因为 arena 只能在分配点那一层的块退出时整块回收。
所以池底化的判据不是「有没有句柄」，而是**扩容之后旧块能不能立刻还回去**：`grow` 拿到新块、拷完、把旧块还给池，
峰值应当从 2.4 倍降到接近活跃量。这条同时把「pool 有自己的板块」从优化变成**前提**。

**裁决二（作者 2026-09-26）：类型名与同名模块的消歧要在语言层做，但排在 STL 与 pool 之后**（见 §6 待决）。

**裁决三（作者 2026-09-26）：`varArray` 弃置，底座不替换。** 原话：

> varArray 已经死了，依旧弃置，这玩意儿比 vector 拉。

它是 prelude 里的旧底座（arena 底，`grow` 是 `new T[ncap]` + 拷贝），已被显式 import 的
`stl::vector` 取代 ⇒ 那 35 文件 / 66 处**不做迁移**，新代码一律用 `vector`。
（这一条先前的写法是「先不动，等 pool 与 STL 定了再谈」——现在两件都定了，结论是弃置。）

**池元素形态：探针已做（2026-09-26）**，两半分开答：

- **定长数组字段本身可行。** 探针：`struct node { n: i32, keys: [16]i32, kids: [17]i32 }`，写读元素、
  `new node[n]` 承载，全部通过（`n=3 k3=77 k15=9 kid16=5`）。也就是说 OI 那种「一个池元素里内联一张小表」
  在 extC 里写得出来，只是**全仓此前没有先例**，所以这条一直是未知数。
- **元素类型是泛型参数则不行。** `struct gnode<K> { keys: [4]K }` 被直接拒绝：
  `cannot make a fixed array of the type parameter 'K'` /「定长数组的元素类型必须是具体的（尺寸是类型的一部分）」。
  ⇒ 泛型 `pool<bnode<K, V>>` 的节点**不能**内联 `keys: [16]K`。

于是泛型有序 map 的节点只有两条路，待裁决：

1. **实例化时定尺寸**（倾向）：`[N]K` 在实例化期把 `K` 落实之后再定尺寸，与 #79 / #80 那套「推迟到实例期」
   同一机制 —— `gnode<i32>` 的尺寸在实例化时是已知的，今天拒得过早。
2. **节点继续用视图**：节点里放 `keys: mut slice<K>`（今天的 `bnode` 就是这样），三块扁平存储由**同一个池的
   块面**供给（增长/收缩都走池），节点本身仍是池元素。代价是多一层间接，收益是不动语言。

**池有两副面，一副记录。** 上面两条裁决把这件事说清楚了：`pool<T>` 既能发**槽位与句柄**（map / linMap /
`pool<T>` 自己用），也能发**整块连续内存**（vector / string 的缓冲区、以及节点视图指向的扁平存储）。
两面共用同一条池记录、同一条寿命、同一次 `release` —— 槽面给稳定身份，块面给可增长可归还的连续内存。
「一个非嵌套容器一个池」这句话对两副面都成立。

### 2.2 边界：什么能进池，什么不能（作者 2026-09-26）

作者原话：

> 你不能把块也生成 Handle 放到 Pool 里面，否则块反复 Bump 会导致 Pool 反复扩容，
> 那块的 Bump O(1) 的优势又没了。

三条规则，从这一句推出来：

1. **进池的必须是「等大 + 需要身份/复用」的元素**：值、节点、槽。句柄、世代、空洞链、
   `slots[]` 反查这些东西是为"元素会被随便删、删了要复用、复用后旧句柄要失效"付的钱。
2. **块不进池**：块是变长的、没有身份、不需要随机访问，只需要 LIFO 的 push/pop ⇒ 走**链**
   （指针、O(1)、无句柄无世代）。给块发句柄是纯开销：每个块一次 `insert`，还可能触发池自己
   三块数组的 resize + 拷贝 —— 那就是把 bump 的 O(1) 换成"摊销 O(1) 加元数据"。
3. **两层只共享寿命所有者，不共享数据结构**：合的是"一个地方一条记录"（块链 + 池树 + 字节账），
   不是分配器、也不是数据结构。

顺带一条**结构上根本接不通**的事实，记下来免得再试：块分配器活在生成器发的 C 运行期里
（`extc_ablock` + `malloc`/`free` + `char data[1]`），池库活在 extC 层 —— 后者拿不到 `void*`、
没有指针转换，也不能把裸块当值。要把块当池元素，等于把运行期分配器搬进库，又会撞回
「库要指针」那道墙（#85 绕开它的办法是只让**类型化视图**过内建）。

**由此否掉的两个提案**（都量过或推过，别再走）：

- **「arena 全部改成 pool」**：同一形状（2e7 个 16 字节小对象）arena 0.01s / 1,452 KB，
  池 0.52s / 939 MB ⇒ 每次分配 0.5ns 对 26ns（约 50 倍），占用 2.9 倍（块头 + malloc 头 + 对齐）。
  而且语言层没有 `free`，用户根本调不了那个买来的能力。
- **「块进池登记」**：本节的规则 2。

**arena 的释放今天是什么**（免得"直接 reset 指针"被误读成现状）：`extc_arena_release` 走整条链、
**保留一块**（`cap ≤ EXTC_ARENA_SPARE_MAX`，1 MB）当 spare、其余 `free`。这条规则是量出来的
（注释里记着：32e6 次 malloc+free 让 churn 慢约 50 倍）。字面上的"reset 块指针"（mark/restore：
进入时存 `{top, used}`、退出恢复）要配**预算**才成立 —— `tests/arena` 把虚拟内存卡在 150 MB
跑"300 轮 × 1 MB"，要求不许涨，无条件保留会直接撞红。

## 3. 生命周期与回收

随容器创建。作者原话：

> region 随着 STL 容器（或者未来用户自定义）一起创建，你不能单独创建一个空的不知道放啥的
> region（至少目前是这样，当然未来可以）。

元素等大：

> 因为 STL 容器大部分时候每一个元素大小都是确定的，所以这会使得 free slots 的复用成功率
> 极高，基本不可能留下碎片。

嵌套只是逻辑的：

> STL 很可能有嵌套的情况（比如 `vector<vector<int>>`），这种情况下 region 也会逻辑嵌套；
> 但嵌套的 region 应该仅构成逻辑父子关系，实际全部统一在同一个 arena 下，生命周期和 arena
> 中的其他对象一样。

数据与簿记的分工：

> arena 里的其他对象真的把数据段存进去了，而 region 在 arena 里面只会维持某种树状结构的
> 指针存储，在清空时遍历树清空（这是可接受的，因为清空的情况不多，region 一般长时间存在，
> 而且树的结点不可能多）。

维护位置与清空时机：

> 你的 region 可能会特别地在 arena 旁边单独维护，arena 回收的时候清空 region（因为 region
> 里面的东西得手动 `reset` 否则就内存泄露了）。
>
> 旁边专门有一个树形结构维护 arena（这个树因为大小确定，里面怎么实现随你）。

回退很快：

> 区本质也是栈之类的，反正怎么快怎么来，因为反正你回退都得一个一个遍历，
> 你 release 掉一个 region 的速度应该还是可以很快的。

两套管理都要「自动」：

> region 和 arena 很像，我认为都应该是能够自动管理的，只是方式不一样：
> arena 是某种栈结构，region 是某种池结构。

## 4. 接口

用户面（写代码的人只看见这些）：

```extc
use std::pool
var p = pool<i32>::withCap(1024)
let h = p.own(42)?          // 稳定 handle（索引 + 世代），是普通值，可自由复制
if p.contains(h) { p.free(h) }
p.clear()                   // 清空，索引还在
p.compact()                 // 压缩空间
p.release()                 // 释放这一层（作用域结束本来也会自动清空）
```

机制面不对外：`extc_pool_*` 是生成器提供的运行期原语，只有标准库用；普通程序里连 pool 这个
词都不该出现。

失效是值，不是崩溃（与既有口径一致：程序 bug 用 trap，正常条件用值）：世代对不上就
`failure(staleHandle)` 带位置；越界、用已释放的池走 trap 带位置。

## 5. 边界

1. epoch 内部的碎片仍要靠容器自己的 free list / dense-swap 那套工程；pool 只让「整批还」
   成为可能，不是万能。
2. `slice` 对 pool 容器不适用（作者已确认）：用 `copyInto` / `forEach` 那一套。
3. 长命容器必须显式 `release` / `clear`：这套方案保证「不漏」，不保证「自动收缩长命数据」。
4. 引用不许出池：对外只给 handle（普通值），池内寻址只在容器方法内部瞬时使用。
   **2026-09-26 作者补全了这条的两半，方向不同、判据也不同：**

   - **允许：对整个容器值的引用** —— `ref vector<i32>` / `mut ref vector<i32>` 都可以。
     容器值本身是 arena 上的普通值（它只是 `{pid, pidGen, 视图…}`），所以按普通引用的规则走：
     深度格管它、逃逸分析管它 —— 容器方法的 `self: mut ref vector<T>` 就是这个形状，一直在用。
   - **禁止（出）：把指向板块内部的视图交给外面** —— `asSlice` / `denseView` 这一族必须是
     **拷出来**（拷到目的地所在的那个地方），不能是"池里的视图"。
     作者原话：「否则就变成引用 Pool 里的东西了，而 **Pool 里的东西永远不能被外面引用**」（PLAN #89）。
   - **禁止（入）：元素类型携带引用** —— `vector<ref T>` 一律不许（PLAN #88）。
     元素住在**池的板块**里，而板块的寿命是**池出生的那个地方**；元素里的引用要活到那为止，
     这件事保证不了（引用指向的对象有自己的所有者）。用法上这也把人推向正确的那条路：
     交叉引用用**句柄**（`Vec<NodeId>`），环就是普通数据环、删节点只是句柄失配（可检测）。

   一句话记法：**可以把容器整个借出去，不可以把池里的东西借出去，也不可以让池里的东西拿着外面的引用。**
5. **世代/句柄空间的防御阶梯（作者口径，2026-09-26）**：重建是**最后一招**，不是机制本身。
   按代价从便宜到贵排：
   1. **不重用那个槽**（毒化，O(1)）：free list 推入时发现计数器要满，该槽在本纪元内不再发放
   2. **换一茬戳**（纪元 +1，O(1)，数据不动、活跃 handle 继续有效）
   3. **响亮地拒绝**：空间真耗尽时拒绝分配，让人显式处理；禁止静默复用旧值
   4. **rebuild / `compact`（最后一招，O(n)）**：搬 dense 前段 + 一趟重编号，会让已发出的视图失效
   ⇒ 回绕的处置走前三级；`compact` 只在真要回收高水位、或拒绝之后人工恢复时用。
   **重建 = 干净启动，这就是 ABA 的解法**（作者口径）：重建把整池回到纪元 0 / 世代 0，
   空间从零开始重新滚动 ⇒ 不存在「被旧数据淹没」。清空世代之所以安全，是因为
   **唯一长期持有下标/手柄的地方就是池自己**（池内不许存引用，只存池内下标；外部只能临时
   拷贝出手柄来读写）⇒ 重建把这批下标一次性、一致地改写，重建之后不存在能对上的旧手柄。
   因此**不需要纪元参与校验**（手柄可以更小）。
   **时机**：单线程随时可做；多线程按 redis 架构 —— 发现该重建就**挡住后续操作**，
   等在飞的做完（这期间撞上 ABA 的**就地毒化**，反正马上重建），再重建。代价是 STW 停顿，
   触发频率极低，因此安全。
   **频率的量化口径**：一茬能撑多久 = 计数器位宽 ÷ **该槽的复用速率**。32 位 + 每秒 1e8 次
   复用同一槽 ⇒ 约每 43 秒停一次（太频繁）；**计数器放 48 位** ⇒ 同速率约 32 天一次，实际上见不到。
   重建仍是最后一招：之前几档（毒化 / 直接拒绝）负责把窗口堵住。
   并发落地前要满足的两条前置不变：数组作为**不可变包一次原子发布** · **先写载荷再发布状态**。
   数组作为**不可变包一次原子发布** · **先写载荷再发布状态**。
   数据共享」，因此没有 handle 跨线程转移，池不需要锁与原子；注册表的进程级 `static`

## 7. 染色：zone 级批量失效（作者 2026-09-26 定口径）

作者的原始说法：

> 我在一个 while 里面创建了一堆 pool，然后我给 zone 一个 color，每个元素也记一个 color，每次访问的时候
> 检查 pool 里元素的 color 和 zone 的 color 是否匹配，如果不匹配那么说明全部都死了，那你就全是 freeslots，
> 很爽。…… zone 本身是固定的并不会被移动，也不需要扩容。

这条成立，而且是这一层里回报最高的优化：它把「zone 退出」从**逐个池走查 + 逐个槽位重写**降成**翻一位**，
并把「池重新可用」变成零成本刷新。落地时有三处要按下面的口径钉死。

### 7.1 两层失效，各管一段

- **池级（新增）：`pool.epoch` 对 `zones[pool.zone].color`。** 池创建时把自己的出生色抄下来；zone 退出时
  把该 zone 的色翻一位（或加一取模，见 7.4）。这一层管「整个 place 死了」，代价是一次固定地址读
  加一次比较，**零走查、零重写**。
- **槽级（保留）：`handle.gen` 对 `slot.gen`。** 管 epoch **内部**的槽位复用 —— `remove` 之后 `insert` 复用
  同一个槽时，若只比色，旧句柄的色会重新对上（同一个 epoch 内色没变）⇒ 静默读到新元素。这一层今天就在
  `ent` 的高 32 位里，不能拿掉。

结论：**「每个元素记一个 color」单独不够**（同 epoch 内复用会漏），**「每个元素记一个 gen」也不够**
（跨 epoch 会漏）。两层各管一段；句柄本身只要 `(slot, gen)`，池级那层比的是池对象自己的 epoch，
不必往句柄里再加字段。

### 7.2 色从哪来（不需要数据流分析）

`extc_pool_new` 里已经有 `r->zone = extc_zoneTop` —— 池创建时就把 zone 下标记在自己身上，所以池随时能回到
自己那一格 zone。这里要纠正作者说法里的一处**实现细节**：zone 数组**不是**固定数组，而是按需翻倍扩容的
堆数组（`static ExtcZone *extc_zones`、`extc_zoneCap`、`realloc`），所以「不会移动、也不需要扩容」这句在今天的
实现上不成立。但结论不变，因为**下标是稳定的**：zone 按下标寻址、按栈式重用，`realloc` 换基址不影响下标，
池记的也是下标，读色就是 `extc_zones[pool.zone].color` 一次下标读。附带一条纪律：**不许缓存指向 zone 的
指针**，只能缓下标 —— 否则 `realloc` 之后就成悬垂指针。
「这个对象属于哪个 zone」在运行时是已知的，染色这一层用不到数据流分析；DFA 的用途在别处（把「该放哪个
arena」从运行时决定变成编译期决定），与本方案无关。
zone 槽的下标就是**栈深度**（`extc_pool_zoneEnter` 里 `id = extc_zoneTop + 1`），所以循环体每轮复用同一个
下标 —— 这正是色能起作用的前提。`zoneEnter` 今天的动作是 `firstPool = -1`，染色后改成翻色（加一取模）即可；
`zoneLeaveTo` 今天逐个 `extc_pool_drop` 走 `zoneNext` 链，染色后那一段可以整个省掉。

### 7.3 零成本刷新与「全是 freeslot」

僵尸池（epoch 与 zone 当前色不符）不需要逐槽处理：`n = 0`、`free = 0`、空洞链头 `-1`，再抄一次当前色即可，
cap 个槽位**一个字节都不用写**。之后的插入走两条路：稠密游标从 0 递增取槽，`remove` 产生的洞挂到显式空洞链
上优先复用。这就是「全是 freeslots」的字面实现。

### 7.4 两处代价与一个前提

1. **注册表记录也要按 zone 分片。** zone 退出若仍逐个 `extc_pool_drop` 走链表，就是 O(池数)，染色省下的又被
   吃回去。做法：每个 zone 在注册表里占**一段连续槽位 + 一个 bump 游标**，zone 死 = 游标归零。于是「zone 死」
   整条路径是「翻一位 + 游标归零」，全程 O(1)。
2. **零初始化写的前提是「这段内存上一轮是我们写过的」。** 全新页或第一遍的垃圾值可能偶然命中色（1 位的命中
   概率是 1/2），空槽被当成活槽就读出垃圾值。所以第一遍仍要付一次初始化，或者保证槽数组来自上一轮写过的
   arena 区域。这也是色标取 **3 位**（命中 1/8）而不取 1 位的理由之一 —— 位宽是检测强度，而位宽不花钱
   （同一个字里的计数器）。

### 7.4.1 实测结账（2026-09-26 第八段）：色落地了，但它的防护价值被 `generation` 覆盖

机制已在运行期落地并验证 sound：`ExtcZone.color`（3 位，`EXTC_ZONE_COLOR_BITS`）在 `zoneEnter`
里翻一位、0 跳回 1；`extc_pool_new_at` 把当下的色抄进 `ExtcPool.color`；`extc_pool_birthColor`
与 `extc_pool_rowColor` 两个读数都可用（`tests/pool/rt_color.extc`：同一个下标每轮 `c1=1 c2=2 c3=3`）。

但**库侧一个调用点都没有**，原因是两层判据已经覆盖了同一件事：

1. `zoneLeaveTo` 会沿 zone 链把该地方的池**逐个 `drop`**，所以池不可能活过它出生那一代地方
   ⇒ 「出生色 ≠ 当前色」在正常执行路径里**构造不出来**（唯一例外是"提权到更外层、而外层还没退出"，
   而那时色本来就相等）。
2. 真正能构造出来的跨代失效（容器值记着某个下标，而那个下标已被新池占用）已被**槽级 `generation`**
   挡住：池记录释放后同一个槽被新池拿走时 `generation` 必然 +1，池值自己的 `pidGen` 守卫先响。
   色是"位置级别的群体判据"，它看得见的东西 `generation` 都看得见。

**所以本节的性能账要按实测重排**：第 1 条（分片）不划算（10 ns/池里只占 2~3 ns）、
真收缩今天已成立（800 KB × 2000 轮峰值 2.3 MB 平）、跨代复用要重审（见下）。
色本身**留着**——它是 sound 的，也是"整个地方死了"这层语义的显式表达；但它不是性能杠杆。

**真正的杠杆是"哪些东西可以不清零"。** 池自己的簿记表（`vals`/`slots`/`ent`）不必清零
（`pFree` 把 `low == 0` 认作空闲，也没有用户能读到未写过的槽），走 `poolSliceRaw` 之后
「每轮建一个 `cap=10 万` 的池」2000 轮：**1.09 s → 0.012 s（约 90 倍）**。
这条比染色里任何一条都大，并且它改写了 `bench/zoneexit/RESULTS.md` 里 ④ 那条的论证：
原文说"复用省不掉清零所以不划算"，而**省不掉清零正是把清零从路径上拿掉的理由**。

### 7.4.2 保留池（阶段 b，2026-09-26 第九段）：板块归还时不立刻还给 malloc

> **⚠️ 已回滚（2026-09-26 第十段）。** 结论：收益（62 KB 块 3.5 倍）配不上它引入的机制量
> —— 分档、预算、单块上限、退出结账入口，以及"块头来源标记必须每条路径都写对"这个新坑
> （漏写 ⇒ `munmap` 走错路 ⇒ 真泄漏）。下面记的是当时的量测与设计，留作参考，机制不在树里。
> 同时被否掉的还有 `mmap` 拿零页（真口径下比 `memset` 慢 4~46 倍，且要引进平台依赖）——
> 见 `bench/zero/RESULTS.md` §7。

**它解决的问题**：`poolSliceRaw` 之后，池簿记表的成本只剩"每次 drop 把板块还给 malloc、
下一轮再要回来"。保留池 = 归还时**先留一段**，给下一次同尺寸、且**逻辑上不需要清零**的分配复用。

**三条实测决定它的形状**：

1. **丢页不是清零的替代品。** `madvise(MADV_DONTNEED)` 在 64 B..16 MB 的**每一个**尺寸上
   都比 `memset` 慢（64 B：2.24 µs 对 0.003 µs；16 MB：7,778 µs 对 984 µs）。
2. **收益来自"不再触碰那些页"，不是"省掉 malloc 的调用"。** A/B/C 三对照（每块只写 4 KB）：
   4 MB 的块，现状 88.5 µs · 保留池+清零 73.6 µs · **保留池不清零 0.03 µs**。
   所以"复用前先清零"几乎吃掉全部收益 ⇒ 保留池**只服务 `take_raw`**（池自己的簿记表：
   没有用户能读到未写过的槽，拿到的块立刻被整片重写）。
3. **预算与单块上限是判据的一部分。** 第一版"8 MB、不留单块上限"把
   `zt_shrink_rss`（800 KB × 2000 轮）的峰值 RSS 从 2.4 MB 顶到 **10.2 MB** ——
   那块被留住，glibc 的 mmap 阈值随之抬高，后面每轮都从堆里要 800 KB。
   收紧到**总预算 1 MB、单块 ≤ 256 KB** 之后峰值回到 2,340 KB。

**字节账的口径**：保留池里的块**不在任何池名下**，所以不进 `extc_pool_bytesLive()`
（那个数仍然必须能归零），单独用 `extc_pool_keep_bytes()` 读。

**常设判据**：`tests/pool/keep_pool.extc`（挂进 `tests/pool/run.sh`）——
复用真的发生 · 超过上限的块不被留下 · 复用来的簿记表照旧正确。

### 7.4.3 共享存储的拷贝：`clone()` + 编译期警告（2026-09-26 第十一段）

`var b = a` **不是深拷贝** —— 它是结构体逐成员拷贝，容器值里的切片指针被抄了一份，两份
**共用同一块板块**。而别的值（`[3]i32`、普通 struct）复制都是各一份 ⇒ **只有容器例外**，
这与直觉相反，后果还是静默的：

    var b = a            // 两个名字，一块板块
    b.push(i32(9))       // ← 改到了 a 的内容
    a.release()          // ← b 变成悬垂（守卫能 trap，但那已经是事故了）

两条出路，都摆明面上：

| 你想要 | 写什么 | 代价 |
|---|---|---|
| 一份**独立**的副本 | `var b = a.clone()` | 显式 O(n)：一次拷贝 + 一块新板块 |
| **有意**共享（借） | `f(ref a)` / `mut ref a` | 零拷贝，但不能越过借用期 |

编译器在两处**警告**（不是错误 —— 有些共享是正当的，作者口径「万一用户就是神人」）：
`var b = a` / `let b = a`（无标注绑定）与 `return a`（返回**已有**的值）。
「已有」的判据是 `Sym.line > c->curFunc->line`：函数体里刚绑的 ⇒ 移交，不报；
参数/外层值 ⇒ 拷贝，报。库自己写的代码不报（按**拷贝发生的位置**判断）。

实测影响面：全量扫 559 个 `.extc` 只命中 **2 处**（其中一处就是别名陷阱判据）⇒ 不制造噪音。
常设判据：`tests/stl/clone.extc` · `clone_warn.extc`（该报的）· `clone_ok.extc`（不该报的）。

### 7.5 三个动词在新形态下的落点

| 动词 | 语义 | 代价 |
|---|---|---|
| `clear` | 零成本刷新（见 7.3） | O(1)，不碰槽数组 |
| `shrink` | 降高水位（工作集），重建活槽与空洞链 | O(cap) |
| `release` | 真还池记录（分片游标回退） | O(1) |

### 7.6 可靠性（soundness）条件：色只用来「否决」，不用来「确认」

染色本身是可靠的，但它**只在下面四条同时成立时**可靠。四条缺一条就会退化成静默读到错数据。

1. **对象记的是自己出生时的色。** 池（以及容器对象）在创建时抄下当时的 zone 色；校验是
   「我记的色 对 当前 zone 的色」。若改成「槽的色 对 zone 的色」，就漏掉了**同一个 epoch 内部**的
   复用：`remove` 之后 `insert` 复用同一个槽，槽的色重新等于当前色，旧句柄又被判活。见 7.1。
2. **epoch 内部的保护必须留着。** 槽级的 `gen`（管 `remove`/`insert` 复用同一个槽）与池级的
   `generation`（管注册表槽位回收后又被新建的池占用）都不能拿掉。一个 k 位的色无法区分两个
   「都是当前 epoch」的状态，这两件事本来就不归它管。**染色是加法，不是替换。**
3. **色只在每一条退出路径上翻。** 这一点已经由「退出表达成回到进入时的 mark」结构保证
   （`zoneLeaveTo(mark)` 覆盖 `return`/`break`/`continue`，见 PLAN #75 的教训），不需要每个出口各写一遍。
4. **色只做否决，确认仍归权威字段。** 活的池必然满足「出生色 = 当前色」（出生时写、复用时刻刷新），
   所以**不相等 ⇒ 一定死**，据此拒绝是可靠的；反过来「相等 ⇒ 活」不可靠 —— 垃圾值可能偶然命中色，
   老对象的色也可能在 2^k 次翻转之后绕回来。因此判定活性的权威永远是 `n`、自由链、`gen` 这些字段，
   色只多加一道否决。**这一条是整节关键的纪律**：一旦让色去「确认」活性，垃圾内存与位宽绕回都会变成
   假活，那就是不 sound 的。

在这个口径下：k 取几位只影响**检测强度**（漏判的概率是 2^-k），不影响正确性 —— 对合规程序（句柄与容器
都不跨自己那个 place 的生命周期，见第 5 节）任何 k 都是 sound 的；对不合规程序，k 越大越容易「响亮失败」
而不是静默用错。取 3 位的理由见 7.4 第 2 条。


### 7.7 池树：寿命挂在地方，父子只讲逻辑（作者 2026-09-26 口径）

作者原话：

> 池是一种空间管理方式……一个非嵌套容器对应一个池，一个容器对应一个池构成的逻辑树，
> 然后把池树串成 zone 是因为 arena 要管理其生命周期。

**两条链，各挂各的。** 一个池既要能"按地方整批回收"，又要能"按容器整棵丢掉"，所以它得同时挂在两处：

- **寿命链（zone 根链）**：每个池都进**它自己那个 zone** 的根链（运行时 `zoneNext` / `ExtcZone.firstPool`）
  ⇒ 地方退出时按 zone 枚举、整批回收。这一层是 arena 管池寿命的地方。
- **逻辑链（父池的子链）**：有父的池同时进**父池的子链**（运行时 `nextSibling` / `firstChild`）
  ⇒ `drop(父池)` 递归带走整棵子树，容器套容器作为"一个容器"被整体处理。

**修之前的实现是二选一**：`extc_pool_new` 里

    if (parent >= 0) { 挂进父池的子链 } else { 挂进 zone 的根链 }

⇒ 有父的池**不在** zone 根链上。后果不是崩，而是**寿命被拉长**：一个池若在**更深的地方**创建、却挂在外面
某个容器的名下（例如外层容器的方法里造出的内层池），它自己的地方退出时 `zoneLeaveTo` 走的是 zone 的
根链、根本看不到它 ⇒ 它要等**外层**地方退出、由父池的递归才被回收。
**已修（2026-09-26，`62737da`）**：`extc_pool_new` 现在**两条链都挂**（`zoneNext` 进 zone 根链、
`nextSibling` 进父池子链），`extc_pool_drop` 无论有没有父都从 zone 链上摘掉；
常设判据 `tests/pool/rt_tree.extc`。

**与染色的关系（作者点明的那条）**：同一个地方里的池树整棵共享一个 zone ⇒ **一次翻色作废整棵树**，
不需要逐池走查（§7.3、§7.4）；反过来，第二步的"真收缩"要在地方退出时把每块池板块还回去，也得沿这棵树
枚举 ⇒ **池树是染色与真收缩的共同前提**。

**容器的义务**：容器为**自己内部**造出来的池要传父。
**已落地（2026-09-26，`0e22af3`）**：`stl/pool.extc` 加了 `pool<T>::withParent(parent, n)`（`withCap(n)` 委托给它）；
`hashMap<K, V>` 先建**自己的一只池**（`pid` / `pidGen` 两个字段），再让 `vals: pool<V>::withParent(rp, c)`
以它为父；`hashMapI64` / `hashSetI64` 转发 `release`。常设判据 `tests/pool/rt_container_tree.extc`：
`live=2 len=2 v=22 after=0` —— `live=2` 就是"两个记录"的证据（接线之前只有值池那一个 ⇒ 1）。
而用户在容器外先建好、再放进去的容器（`vector<vector<T>>` 的内层）今天**没有语言层上下文**
可传 ⇒ 它保持为独立根池，寿命按自己的地方走；这一档如实记在这里，不要假装树是全的。
`map<K, V>`（B+ 树）的节点还在 arena 切片里（PLAN #84），所以它那棵树暂时只有一个根池，等 `pool<bnode>` 落地再补。


### 7.8 外部方案的逐条核对（2026-09-26）

有人提出过一版"O(1) clear"的方案，结论与本文 §7.3 / §7.5 一致，但有三处必须补上才 sound，
另有两处措辞会把实现带偏。记在这里，因为这一族错误会重复出现。

**对的部分**：`clear` 改成"代际 +1、高水位归零"两条写、一个槽都不写；"空闲不是一个状态位，是一个
比较结果"；分配走高水位游标，不再扫描。这与 `pool<T>::clear()` 今天的实现**逐字相同**
（`epoch + 1` · `n = 0` · `cursor = 0` · `holeHead = -1`，四行、代价与 `cap` 无关）。

**三处硬伤**：

1. **槽级世代不能是"池代际的副本"。** 那样同一个 epoch 里 `remove` 之后 `insert` 复用同一槽时，
   新占用者的 `(slot, gen)` 与旧句柄**逐位相同** ⇒ 旧句柄静默读到新元素。正确做法是世代在**每次释放**
   时 +1（`remove` 里 `pPack(pGen(e) + 1, …)`），池代际只负责"整个地方死了"这一段。判据
   `tests/pool/rt_epoch.extc` 的 `reuse=0` 就是钉这条的：按"抄池代际"改，它立刻变 1。
2. **"相等 ⇒ 活" 不成立。** 代际/色只能**否决**（不等 ⇒ 一定死），确认活性的权威永远是 `n`、
   空洞链与槽世代（§7.6 规则四）。把 `slot_gen == pool_gen` 当存活判据，垃圾内存与位宽绕回都会变成假活。
3. **空洞链头必须一起归零**，不能只靠"旧条目作废"。"作废"是**判定**上对，**链头**上不对：旧链的链接
   指向的槽在新纪元里可能已经落进 `[0, cursor)` 变成活的，顺着旧链发槽就会把同一个槽发两次
   （`slots` 与 `ent` 立刻不一致）。归零只写一个头，仍然是 O(1)；丢掉的旧洞无所谓 —— 整张表都空了。

**两处措辞**：

- **"`swap_remove` 不留空洞、所以不需要 free list"** 只在池自己成立。句柄不能是稠密下标：`swap_remove`
  会把最后一个元素搬进洞，被搬走的那个元素的稠密位置变了。本实现把句柄定成**槽号**，另用
  `slots[]`（稠密下标 → 槽）与 `ent` 低半区（槽 → 稠密下标）两列反查来兜这件事；容器侧还要再兜一层 ——
  `hashMap` 的 `bucketOfDense` 就是为 `pool.remove` 的 swap-remove 准备的（§8）。
- **"位宽不够就 rebuild"** 跳过了前三级。处置顺序照 §5 的阶梯：毒化槽（O(1)）→ 换茬戳（纪元 +1，O(1)）
  → 响亮拒绝 → `rebuild`（最后一招，O(n)）。位宽只影响**检测强度**（漏判 2^-k），不影响正确性。

**一条与 zone 的关系**：那版方案讲的是**池级 clear**，不是 zone 染色。zone 那一层是同一个技巧往上抬一层
（池出生时抄下出生色，zone 退出翻一位 ⇒ 整棵树一次作废）。两点照旧：zone 表是按需翻倍的堆数组，
**只能缓下标、不许缓指针**（§7.2）；而且**染色只有在"翻色 + 注册表游标归零"时才是 O(1)** ——
zone 退出若仍逐个 `extc_pool_drop` 走链，代价是 O(池数)，染色省下的又被吃回去（§7.4 第 1 条）。
这两件**今天都还没落**：`zoneEnter` 仍只做 `firstPool = -1`，`zoneLeaveTo` 仍是逐个 drop 走链。


## 8. 下一步：`stl/hashMap` 池底化（设计已定，待落；有序 `map` 是另一件，见 §10）

现状（`stdlib/stl/map.extc`，156 行）：`mapI64<V>` 是开放寻址表 —— `keys: mut slice<i64>` ·
`vals: mut slice<V>` · `tag: mut slice<u8>`（EMPTY / LIVE / TOMB）· `n` · `dead` · `cap`（2 的幂）；
面是 `withCap` / `len` / `find` / `contains` / `get` / `put` / `remove` / `rebuild` / `clear` /
`keyAt` / `valAt` / `liveAt` / `capOf`。要做的三件事：

1. **值搬进池**：`vals` 从表里挪进池，表里只留 `keys` / `tag` 和一列 `slot: mut slice<i32>`
   （桶到池句柄，空桶 -1）。于是活着的元素在池里是**稠密**的，遍历从「扫整张表」变成「扫稠密区间」。
2. **`rebuild` 只重排桶，不搬值**：今天它要把 `keys` / `vals` / `tag` 三块一起搬；值进池之后重排只搬
   `keys` / `tag` / `slot` 三列（i64 / u8 / i32），元素的地址与句柄**跨 rehash 稳定** —— 这正是池底化
   要换来的东西。
3. **`remove` 的交换不必给池加新接口**：池的 `remove` 是 swap-remove（把最后一个稠密元素填进洞）。
   map 侧要同步自己那列「稠密到桶」的反查，做法是在调用 `pool.remove(h)` **之前**读
   `hMoved = pool.handleAtDense(pool.len() - 1)`，调用之后把 `hMoved` 那条稠密记录从末尾挪到被删位置。
   这依赖 `handleAtDense` / `atDense` / `len`，现有接口已够用，不必动 `stl/pool`。

**对现有调用点的影响**：公开面（`withCap` / `len` / `contains` / `get` / `put` / `remove` / `clear` / `capOf`）
语义不变；`keyAt` / `valAt` / `liveAt` 是「按表位置扫」的旧面，池底化后**新增**稠密迭代面
（`keyAtDense(i)` / `valAtDense(i)`），旧的先留着不动，避免又一次全语料改动。句柄由池发放、map 只是存下来，
所以第 7 节的 epoch 改动（句柄多一个字段）不要求 map 跟着改。


## 9. `stl/hashSet`：无值哈希表（设计，已落地）

`set` 就是 `map` 把值去掉之后剩下的那一半，所以**不另起一套桶**：`struct setI64 { m: mapI64<u8> }`，
元素即键，`u8` 当占位值。面是 `withCap` / `len` / `contains` / `put`（新插入返回 true）/ `remove` /
`clear` 加遍历三件（`keyAt` / `liveAt` / `capOf`）；池底化之后再加稠密遍历面。

这样哈希、线性探测、墓碑、`rebuild` 阈值这些最容易写错的东西**只有一份实现**，set 与 map 的行为不可能
各漂各的。代价照实写：多存一列 `u8` 占位值，池底化之后这列对 map 是值、对 set 是空，即每元素一字节。

验收照 `tests/map` 那四条判据搬（碰撞链、挖中间一个后仍能找到、墓碑 churn 的峰值 RSS 不随轮数涨、
只插不删必须涨的 canary），再加 ASan 干净。

## 10. 命名定案：`hashMap` 是哈希，`map` 是有序平衡树（作者 2026-09-26）

作者口径：「map 不应该这样，map 应该是 hashMap<K, V>，然后是哈希；map<K, V> 是有序的平衡树实现」。

据此改名（本轮已落）：`stdlib/stl/hashMap.extc`（`hashMapI64<V>`，开放寻址 + 墓碑 + 三态桶）、
`stdlib/stl/hashSet.extc`（`hashSetI64`，建在哈希 map 上）、套件目录 `tests/hashmap/`。
**`map` / `set` 这两个名字从此留给有序实现**（平衡树），它们不再是哈希的别名。

两个名字各自的门槛，都还没跨过去（同属「库作者撞墙」那一族，PLAN #57）：

- `hashMap<K, V>`：K 要能 `hash()` 与 `==`。今天 K 固定 i64（`hashMapI64<V>`），因为**泛型体里调不了
  类型参数上的协议方法**；名字先摆正，`K` 泛化要等 #57 那条「实例化时检查」的方向落地。
- `map<K, V>`（有序）：K 要有**序**，也就是某种 `cmp` / `less` 协议 —— extC 没有运算符重载，所以这层
  同样只能走「按形状认协议 + 实例化时检查」。另外两件事没定：树的选型（红黑 / AVL / 其他），以及
  「节点住哪」（池里还是 arena 里）。这两条定了才动笔。

`linmap` / `linset`（线性扫描、泛型键）保持原名 —— 它们既不是哈希也不是有序树，是第三条路（只要 `==`）。

## 11. 有序 `map` / `set` 的裁决与 `[]` 重载的现状（作者 2026-09-26）

作者口径：「B 树是对的啊我说」·「现在重载是不是还不能重载 `[]` 的，把 map/set 写了之后看看吧」。

**裁决：有序 `map<K, V>` 用 B 树。** 理由（作者要"最好的算法"，不是"最好写的"）：内存里的瓶颈是 cache miss，
fanout 16 的 B 树在 n = 10^6 时约 5 层，二叉平衡树约 20 层；叶子是连续数组 ⇒ 顺序遍历就是扫内存。小表时
B 树的根本身就是一个排序数组，自动等于最快的 flat map，不需要两套实现切换。落地形态：节点容量 16、节点内
二分、**叶子存「键 + 池句柄」**、节点自己住池（下标当指针），于是分裂/合并搬的是十几字节、值一个都不动，
元素身份稳定且能 `shrink`。整数极致性能另开 `mapI64`（ART / radix）是以后的事，与通用 `map<K, V>` 的
`cmp` 协议冲突，不能合并成一个。

**`[]` 重载的现状：今天不支持。** 证据：全仓没有任何类型写过 `fn []`；编译器源码里没有 `"[]"` / `"[]="`；
编译器认识的运算符方法名只有 `== != < <= > >= + - * / %`（外加 `<<` 这种作为方法名用的），而 `EX_INDEX` 只
对数组 / `slice` / 视图找元素类型（`viewElemOf`），根本不会去问用户类型有没有 `[]`。要加得三处一起动
（`<<` 当年踩过：**解析器白名单与 mangle 表必须同时改**）：解析器收 `[]` / `[]=` 作方法名 · codegen 的 mangle
表给它们起合法 C 名 · 检查器在 `EX_INDEX` 里**先问用户类型**再退回内建（泛型接收者要按 #57 那套推迟到实例期）。
顺带一条设计问题要在动手前定：`[]` 返回**值**还是 `ref` —— 返回 `ref` 才能写 `m[k] = v` / `m[k].f = ...`，但那
与"`ref` 不许逃出生命周期"的规则纠缠；建议第一版只做**读**（`?V`），写入仍走 `put`，`[]=` 先不做。

## 12. 自定义池底容器（用户面）—— 作者 2026-09-26 定

**为什么要写这一节**：池是"基础容器"，STL 只是在它上面的一层逻辑。作者说过"一个非嵌套容器对应一个池"，
所以库里那七个容器不是特权：**你自己写的结构体也应当能拥有一个池**，走完全一样的路。
不写下来没人会自己建 —— 这一节就是那条路。

### 12.1 先问一句：你要的是哪一层

| 你要的东西 | 走哪条 | 代价 |
|---|---|---|
| 能存等大元素、要稳定身份、删了要能复用（链表 / 平衡树 / 图 / 对象表） | **用现成的 `pool<T>`**，逻辑写在**句柄**上（句柄当数组下标用） | 只写你的逻辑；存储/句柄/压缩/重建都是池的活 |
| 一个**自己的**存储块（连续数组、自己的布局、成块簿记），要能长、能还 | 自己声明 `@poolObject`（12.2） | 一个结构体 + 四个方法 + 一对守卫 |

第一条是常态（OI 那个写法：开一个大数组，用 `nxt[i]` 说这是链表）。`stl/pool.extc` 的公开面够用：
`withCap` / `withParent` / `insert` / `get` / `set` / `contains` / `remove` / `len` / `capacity` /
`shrink` / `clear` / `release` / `atDense` / `handleAtDense` / `gather` / `toSlice`，外加 `handle` 与 `same(a, b)`。

### 12.2 自己拥有板块：`@poolObject` + 一份模板

**声明。** 结构体前面写 `@poolObject`，它说的是一句事实：**这个类型拥有一个池**（存储住在池自己的
板块上，寿命随它所在的地方）。修饰符由**你**写、编译器照办 —— 它不猜（早先试过"看有没有 `pid` 字段"
与"看方法建不建池"：前者是魔数式约定，后者要等所有函数体检查完才算得出来）。

**模板。** 下面这份是**跑通过的**（`tests/stl/custom_pool.extc`，判据
`n=10 cap=13 v9=81 live=1 bytes=104`），照它改：

```extc
use std::sys::pool as syspool      /* 特权层：运行期池记录（库作者面，普通程序不 import）*/

@poolObject                        /* 这个类型拥有一个池 */
struct mybuf<T> {
    pid:    i64                    /* 运行期池记录的下标 */
    pidGen: u64                    /* 建池那一刻的世代（陈旧拷贝靠它认出来）*/
    vals:   mut slice<T>           /* 存储 = **这个池自己的板块** */
    n:      i64
    cap:    i64

    fn withCap(c: i64) -> mybuf<T> {
        let rp  = syspool::extc_pool_new(i64(-1))          /* 随容器登记一条池记录（父 = -1）*/
        let rpg = syspool::extc_pool_generation(rp)        /* 抄下出生世代 */
        var cc: i64 = c
        if cc < i64(4) { cc = i64(4) }
        var b: mybuf<T> = {
            pid: rp, pidGen: rpg,
            vals: poolSlice<T>(rp, cc),                    /* 从自己的板块拿一块 */
            n: i64(0), cap: cc,
        }
        return b
    }

    fn push(self: mut ref mybuf<T>, v: T) {
        if self.n >= self.cap {
            let ncap = self.cap + self.cap / i64(2)
            self.vals = poolResize<T>(self.pid, self.vals, ncap)   /* 原块加长（内容保住）*/
            self.cap  = ncap
        }
        self.vals[self.n] = v
        self.n = self.n + i64(1)
    }

    fn release(self: mut ref mybuf<T>) {
        if self.pid < i64(0) { return }
        self.vals = poolResize<T>(self.pid, self.vals, i64(0))     /* 1) 视图先收成 0 长 */
        self.cap  = i64(0)                                         /* 2) 容量归零 */
        syspool::extc_pool_reset(self.pid)                         /* 3) 重置记录 */
        syspool::extc_pool_drop(self.pid)                          /* 4) 回收记录 ⇒ 板块整块还 */
        self.pid = i64(-1)
    }
}
```

三个原语是**生成器内建**（不是 `extern!`：它不许返回 `slice<T>`，extC 也没有指针转换）：

| 内建 | 干什么 | 什么时候用 |
|---|---|---|
| `poolSlice<T>(rid, n)` | 拿一块新的 `n` 个 `T`（清零） | 构造、要换块时 |
| `poolResize<T>(rid, s, n)` | 把**这一块**改成 `n` 个（内容保住，只清零新增那一段） | 增长/缩容（首选，一个字节都不搬） |
| `poolGive<T>(rid, s)` | 把一块还回去 | 换块：新的先拿、旧的最后还（不留悬垂窗口） |

### 12.3 编译器替你做的三件（所以你不必做）

1. **提权**：`@poolObject` 类型的构造调用是**逃逸站点**，与 `new` 同一条规则 ⇒
   `fn build() -> mybuf<i64>` 里建好、返回给调用方**合法**，池会生到**调用者选的那个地方**去。
2. **隐藏的「家 zone」参数**：建池的函数（可传递）自动多收一个 `int64_t __extc_home_zone`，
   调用点自动传对。你写 `syspool::extc_pool_new(i64(-1))`，生成的是
   `extc_pool_new_at(parent, __extc_home_zone)`。
3. **释放之后是响亮失败**：见 12.4 的守卫。

**一处已经修掉的坑（记在这里，免得重踩）**：库函数"对地方透明"（构造器自己不压 zone），
而**用户写在入口文件里的构造器原先被当成一个地方** —— 池会生进它自己的帧、返回时被回收、板块悬垂
（实测是段错误）。修法：让运行期那一句 `extc_pool_new` 本身也算池站点，于是它跟着容器一起提权。
`tests/stl/custom_pool.extc` 就是这条的常设判据。

### 12.4 你必须自己写的两件

**守卫（一对）。** 别名是结构体浅拷贝：两个名字共用一个板块，一份 `release` 之后另一份就悬垂，
而且**它不会报错**（除非加这一对）。库里五个容器都有，形状照抄：

```extc
    fn pStale(self: ref mybuf<T>) -> bool {          /* 出生世代对不上现在这一格 ⇒ 陈旧 */
        if self.pid < i64(0) { return false }
        return syspool::extc_pool_generation(self.pid) != self.pidGen
    }
    fn pPoison(self: mut ref mybuf<T>) {             /* 陈旧 ⇒ 把这一份收成空容器（别碰板块）*/
        self.vals = poolSlice<T>(i64(-1), i64(0))
        self.n    = i64(0)
        self.cap  = i64(0)
        self.pid  = i64(-1)
    }
```

然后在**写入路径入口**各查一次（`push` / `set` / `put` / `insert` 的第一句）：
`if self.pStale() { self.pPoison() }`。代价实测在噪声内（1e7 次 push：0.048~0.050s 对 0.047~0.049s）。

**`release` 的四步顺序**（模板里有）：**先收视图、容量归零，再放记录**。反过来写就是一个悬垂窗口：
视图还在、板块已经还给 malloc。

### 12.5 三条纪律（不是建议，是模型的结果）

1. **池里的东西不许出容器**：要"拿出来"就拷贝（`toSlice()` 那一族，落在**目的地**所在的地方）。
   作者原话：「`asSlice` 应该是某种拷贝……否则就变成引用 Pool 里的东西了，而 **Pool 里的东西永远
   不能被外面引用**」。视图本身也守不住 —— `push` 一次（可能搬家）、`clear`（翻纪元）、`shrink`、
   `release` 任何一个动作都能让它失效。
2. **池元素不许带引用**：元素住在板块里，板块会压实/复用/翻纪元 ⇒ 元素里的引用活不到那为止。
   交叉引用用**句柄**（`Vec<NodeId>`）：陈旧可检测、节点可复用、环也是普通数据环。
   **例外**：`varArray<T>`（arena 底，元素地址永不移动/复用）**可以**装引用 —— 见 §13。
3. **整个容器值可以借出去**：`ref mybuf<T>` / `mut ref mybuf<T>` 都允许。容器值是 arena 上的普通值，
   按普通引用规则走（容器方法的 `self` 就是这个形状）。

## 13. 唯一能装引用的容器：`varArray<T>`（作者 2026-09-26）

作者口径：

> `varArray` 是你唯一能够写 `varArray<ref T>` 而不会报错的方式，因为都是 arena 里的对象，
> 不会出现循环，所以还是得留着。

**为什么只有它能。** 这是两种存储的**语义差**，不是配置差：

| | 元素地址 | 能装 `ref T` 吗 |
|---|---|---|
| `varArray<T>`（arena 底） | **永不移动、永不复用**（没有逐对象 free、没有压实、没有纪元翻色） | **能** —— "引用在它的地方活着期间一直有效"是真的；两个节点互相 `push` 的环也只是普通数据结构 |
| 池底容器（§12） | 会压实 / 复用 / 翻纪元（`shrink` / `clear` / `release`） | **不能** —— 池里的引用是雷 |

**三条实测**（`tools/memsafe/qa/r11` 与 `tests/stl/vararray_ref.extc`）：

1. `varArray<ref i32>` + `push(ref x)`（同地方）⇒ 编过；
2. `struct node { refs: varArray<ref node> }`，两个节点互相 `push` ⇒ **编过**（这是"大的要来了"那个图的形状）；
3. 内层块里局部变量的引用塞进外层 `varArray` ⇒ **仍然被拒**（`argument 2 of push carries a reference
   into a deeper scope`）—— 借用检查按**寿命**管，这一档它管得住。

**性能账（诚实记）**：`bench/vararray/RESULTS.md` —— 四个**偏向它**的形状里它一个都没赢
（时间打平或更慢、内存输 20~90 倍：循环里反复新建时 arena 的 home 机制把分配提到帧那一层，
33 MB 对池底的 1.5 MB）。所以**留它的理由不是性能，是这条语义能力**；拿它当"快的数组"用没有优势。

**与"池元素不许带引用"（§12.5）不冲突**：那条纪律说的是池底容器。判据也从来不靠命名约定 ——
**要不要装引用，取决于存储会不会动**，这一节就是那条界线。
