## 1. 要解决的三个问题（主人原话）

1. **用户无法手动回收容器里的垃圾**（erase 掉的槽位/旧代缓冲永远留在 arena 里）
2. **无法复用**（同一块内存不能重新利用 ⇒ 反复 add/erase 就线性涨）
3. **指针跳转导致 SIMD 难以优化**（链式/树式结构，每次访问都是一次 cache miss）

主要应用面是 **STL**：`varArray` · `string` · `set`，后续 `graph` 这一类封装
而 pool 要支持泛型 ⇒ 泛型套泛型 ⇒ **pool 套 pool**（逻辑嵌套）

## 2. 为什么今天不行（量测，2026-09-24 当场跑的）

`/usr/bin/time -f "%M"` 峰值 RSS：

| 形状 | 峰值 RSS | 活跃数据 | 结论 |
|---|---|---|---|
| **A** 翻倍长到 1e5，但每轮在**会退出的块**里做（12 轮）| **2,640 KB** | — | **平** 块退出即还 |
| **B** **一个**数组从 1 翻倍长到 1e6（4 MB）| **9,900 KB** | 4,096 KB | **≈2.4×** 历代旧副本全留着 |
| **C** 每轮新建/重建，分配点落在**长命层**（12 轮）| **14,184 KB** | — | **随轮数线性涨**|
| **D** 一次要够 | **5,676 KB** | 4,096 KB | 只差进程基线 |

**两条规则**：arena 只在**分配点那一层的块退出**时回收 ⇒（i）长命层里任何分配都是永久的 ·
（ii）同一个容器对象复用则浪费有界（B ≈1× 活跃量），**每轮新建则无界**（C）
⇒ 服务型程序（跨请求状态、缓存、会话表）**必然**撞在（i）（ii）上

## 3. 设计：ECS 版

### 3.1 pool = **注册表里的一个槽**，`new` 出来的是 handle

- `pool`（对用户而言）是一个 **handle = 索引 + generation** ⇒ 是**普通值，可以自由复制**
- **作者口径（2026-09-26 主人原话，权威）**：*"region 是一种基于 ECS/Handle 的内存管理模式，
  旨在高效利用内存、保证内存安全和 SIMD 优化，同时能够允许用户手动介入 GC，是为了弥补 arena
  在管理删增动态度很大的数据结构时的劣势"* · *"region 随着 STL 容器（或者未来用户自定义）
  一起创建，你不能单独创建一个空的不知道放啥的 region"* · *"因为 STL 容器大部分时候每一个元素
  大小都是确定的，所以这会使得 free slots 的复用成功率极高，基本不可能留下碎片"* ·
  *"嵌套的 region 应该仅构成逻辑父子关系，实际全部统一在同一个 arena 下"* ·
  *"arena 里的其他对象真的把数据段存进去了，而 region 在 arena 里面只会维持某种树状结构的指针
  存储，在清空时遍历树清空"*
- **三层结构（作者 2026-09-26 追加口径）**：*"你的 region 可能会特别地在 arena 旁边单独维护，
  arena 回收的时候清空 region（因为 region 里面的东西得手动 reset，否则就内存泄露了）"* ·
  *"旁边专门有一个树形结构维护 arena"* · *"如果一个地方里面有多个 region（就是多个 STL
  容器的话）你需要多一层：region 区 -> region 树 -> region 三层结构"*
  - **region 区（zone）**：一个作用域里的 region 归一个区；同一处有多个容器就靠这一层分开
  - **region 树**：区内的逻辑父子关系（容器套容器）
  - **region**：单个容器的那一份（数据结构的簿记与数据）
  ⇒ 区与树都是"维护在 arena 旁边的独立结构"（不占 arena 自己的数据段）；**arena 回收时连
  整区一起清空**——必须如此，否则 region 里手动 reset 才释放的东西会漏掉
  ⇒ 树的实现随实现者（大小确定、节点不多）
- 落到结构上：**arena 是寿命的来源，它不是栈**；带 pool 的容器在那只 arena 里放一个
  **指针**，指针指向它的 pool，pool 里装着这个容器的数据结构（动态数组 / map / set 平衡树 /
  树 / 图）。pool 自己的簿记（槽位表、free list、generation、父子链）**也在同一只 arena** 里，
  是一棵指针树；清空 = 遍历这棵树把槽位标成可复用，内存本身随 arena 的块一起走（因此 pool 的
  寿命就是它所在 arena 的寿命）。嵌套的 pool 逻辑上父子、实际共用同一只 arena，所以一起走
- 实现上，槽位记录**它属于哪只 arena、哪一层**（`ExtcRegion.arena`）：分配走那只 arena 的
  分配器，于是提升规则、逃逸分析、层号编号对 pool 内存原样适用
- 注意：层号必须**就是创建它时所在的那一层**，而这个数**不该由调用方手写**——
  `tests/pool/alloc.extc` 第一版把 main 体里的 pool 写成第 2 层，循环体第一次退出就把它回收了，
  之后分配返回 NULL。这正是"层号该由生成器给"的实证（期 2 的入口由生成器发射层号）
- ⇒ **"拷贝容器 ⇒ 双主"不存在**（持有者不是所有者，所有者是注册表/父节点）
  ⇒ 也因此**不需要 `@nocopy`**（旧版那条撤回）

### 3.2 容器的**可变簿记也放进 pool**，用户手上只有 handle

不是"struct 里塞一个指向 pool 的指针"，而是：**struct 里只有 handle**
（`{ r: pool, d: handle }`，`d` 指向**住在 pool 里**的 descriptor）
⇒ "两个 header 共享一块内存 ⇒ free list 成环死循环"这个隐患**从根上消失**
⇒ 代价：每次操作多一次查表（可批量校验）

### 3.3 失效 = **generation 校验 ⇒ trap**（主人 2026-09-24 定：「ECS 里的东西 trap 即可」）

`pool::drop(rid)` · `pool::reset(rid)` · **创建它的块退出** ⇒ **generation 加一** ⇒ 任何旧
handle 的访问 ⇒ **trap（带位置）**

**为什么这是对的**（它其实正好合 extC 的既有口径：**bug ⇒ trap；条件 ⇒ 值**）：

| 情形 | 类别 | 怎么办 | 语言里的先例 |
|---|---|---|---|
| stale handle（drop/reset 之后再用）· 槽位越界 · 用已释放的 pool | **程序 bug** | **trap**（带位置）| `a[i]` 越界就是 trap |
| "这个键/槽位没有东西" · 想先问一下 | **正常条件** | **值**：`option` / `?T` / `contains` / `valid` | `slice` 的 `hasAt` / `get` |
| 分配失败（pool/arena 要不到内存）| 系统条件 | 运行时已 trap（带位置）| `extc_arena_alloc` 现有行为 |

**但有一条铁律会撞上**：trap 必须带**正确位置** 而**库里的 trap 会指到库自己的源码行**
（`@inline` 也一样：`#line` 指向库源）⇒ 两条路：
- **(a) 查询式 API**（`valid(h)` / `tryGet(h)` / `contains(k)`）让调用者**先问** ⇒
  服务型不会因为一个陈旧 handle 就整个进程死掉 **零编译器改动**
- **(b) `@trackCaller`**（小特性）：被标的方法额外收一对**隐藏参数**（调用点的 file + line），
  于是 trap 指到**用户那一行** —— 机制与隐藏 `__extc_home` 参数**同源** 小

这也是一处**有意偏离**：`prelude.extc` 顶上写着"会 trap 的库不符合 extC 的性格"
⇒ 这里的口径是：**那条规矩管"条件"，不管"bug"** 容器内部的陈旧索引是 bug ⇒ 该响就响
（服务型想要"别死"，就用 (a) 的查询式 API）

另一处**有意的降级**：容器不追求"编译期挡悬垂"，改用**校验过的索引**
理由：`reset` 的时机本质上是运行时的（epoch 什么时候结束只有程序知道）⇒ 静态规则管不到
（extC 别处仍是"能证明就编不过" 这条降级**只限容器内部寻址**，不外溢）

### 3.4 块与 pool 是**同一棵树**上的两种节点

- 嵌套是**逻辑**的：pool 的父 = 另一个 pool，**或者创建它的那个块（层）**
- **释放粒度 = 子树**：`reset`/`drop` 递归到子 pool；**块退出 ⇒ 挂在它下面的 pool 子树一起释放**
  （主人原话：「pool 给一个指针给 arena 指向，回收的时候顺手把 pool 回收了」）
- **不做 O(1) 逐对象释放/复用** —— 这条是共识：**这不可能** 摊销的批量释放是唯一的诚实答案
- **独立块**（已定）：每个子 pool 至少一块 malloc ⇒ 换来**子容器能独立 `reset`**
  （`cache.reset()` 才成立；叶子容器以后可以优化成共享父块）

### 3.5 注册表：**每帧一个**（选 a），挂在块 arena 的子链上

⇒ 用户**不用传**注册表 · "块退出 ⇒ pool 子树一起没"自然成立
⇒ **pool 的寿命 = 创建它的那个块**（没有隐藏语义：释放点仍然写在程序里 —— `reset`/`drop`/块退出）
**由此一个好处**：工厂函数不靠"提升"就能安全 —— 想要跨作用域活着的容器，**由调用者建 pool
再把 handle 传进去**（「跨 pool 也是传 pool handle」）⇒ **完全不用碰逃逸/提升那个娇气的 pass**

## 4. 连续性怎么保住：`buf<T>` + 原地扩展

`varArray` / `string` 要的不是"分配"，是**"一块能长大、而且始终连续"**的内存 ⇒ pool 提供
**唯一一个**高级原语：

```extc
var b = r.buf<T>(cap)      // pool 里的一块连续内存
b[i] · b.len
b.grow(n)?                 // 几乎总是**原地延长**（见下）
```
**为什么几乎总是原地**：pool 是**私有的、安静的**（里面只有这个容器自己的几块东西）⇒ 那块内存
**通常是 pool 里最后一块** ⇒ bump 指针一推就长大 **零拷贝、零旧副本**；万一不是最后一块，
就在同一 pool 里再要一块并拷（有界，且不产生永久垃圾 —— pool 的寿命是统一的）
⇒ 于是 **`varArray`/`string` 放进 pool 依然永远连续**（**不 chunk 化**；只有 churn 敏感的
容器才走"列 + handle"）

## 5. 契约分工：谁给 `slice`、谁给 `copyInto`/`forEach`

| | **平数组家**（单块 · 无洞 · 不跨块）| **pool 容器**（dense/sparse · 列 · 有洞）|
|---|---|---|
| 零拷贝取视图 | `asSlice()` 保留 | **不给**（原理上给不出：分块/有洞/会被 `reset` 挪走）|
| 拷出去 | 同上 | `count()` + **`copyInto(dest)`** 调用者给 buffer（不够 ⇒ `failure(destFull)`）|
| 遍历 | 现有吃 `slice` 的算法 | **`forEach`** 零拷贝、按列遍历、可向量化（配 `@inline`）|
| 改 | 自己改 | `set(h, v)` / `forEachMut`（明说：遍历期间只许改值，不许增删）|

- **两种契约用两个类型分开**（跟"读型/写型两个 struct"同一个道理），**不要**给 pool 容器一个
  "看运气"的 `asSlice() -> ?slice<T>`（那种 API 一定会被误用，而且误用时看起来是对的）
- **`string` 不跟着 chunked 化**：下游全吃 `slice<u8>`（print · IO · 哈希 · `extern!` 边界）⇒
  原则一句话：**「数据面用列 + handle，序列化面保持连续」**
- **dense 要保住**：删除用 **swap-remove**（把末尾搬进空位）⇒ 前段永远连续 ⇒ 遍历可向量化
  `graph` 用 **CSR**（每节点一段连续边）这正是兑现"消灭指针跳转"的那个封装

## 5.5 用户会怎么用（默认路径应该是"零心智负担"的）

```extc
use std::set
var s = set<i32>::new()          /* pool 在容器内部 —— 用户看不见，也不用管 */
s.insert(1)  s.insert(2)  s.insert(3)
s.erase(2)
if s.contains(2) { println("还有") }

/* 遍历：今天最自然的形状（迭代器结构体；`for`/lambda 落地后再加语法糖）*/
var it = s.iter()
while it.next() { println(it.value()) }

/* 想要 `slice`：一行拷出来，生命周期 = 当前块，用完随块回收 */
let view = s.toSlice()
println(view)

s.reset()                        /* 想手动回收时才有这一句（长命容器用）*/
```

**默认路径与今天的 `varArray` 一样自然**：pool 是容器的实现细节，用户只在
"想手动回收"（`reset`/`close`）或"写自己的 pool 容器"（§6）时才见到它

**三处手感与 C++ 不同（要提前说清，避免"用起来别扭"的落差）**：

| # | 差异 | 对策 |
|---|---|---|
| 1 | **迭代**：今天没有 `for` / lambda（`forEach` 收不了函数值）| 容器提供 **`iter()`**（`while it.next()`）与 **`atDense(i)`**（dense 下标循环）；`for`/lambda 落地后加糖 |
| 2 | **不能长期持有元素引用**（`ref T` 会挡住 erase 的自由）| 用 `at(h)` **瞬时**读、`set(h, v)` 写 换来的是"**erase 永远不会让你的引用悬垂**"（C++ 那边正是 UB 之源）|
| 3 | **拿不到 `slice`** | 容器直接给 **`toSlice()`**（内部拷到**当前块**的 arena ⇒ 生命周期 = 当前块、用完自动回收）· 或 `copyInto(dest)` 由调用者给 buffer |

## 6. 用户怎么写自己的 pool 容器（骨架）

```extc
/* 一个"对象池"：pool 由调用者给（跨作用域靠传 handle），descriptor 住在 pool 里 */
struct pool<T> {
    r: pool                 /* 注册表槽的 handle（值，可复制）*/
    d: handle                 /* pool 里 descriptor 的 handle */

    fn withCap(r: pool, n: i64) -> pool<T>    /* 建 descriptor + slots（r.buf<T>(n)）*/
    fn own(self: mut ref pool<T>, x: T) -> ?handle
    fn at(self: ref pool<T>, h: handle) -> ?ref T
    fn free(self: mut ref pool<T>, h: handle)   /* swap-remove + 槽位还给 free list */
    fn reset(self: mut ref pool<T>)             /* pool::reset(self.r) ⇒ 子树级清空，块复用 */
    fn close(self: mut ref pool<T>)             /* pool::drop(self.r)  ⇒ 连块一起还 */
}

/* 用法 */
var r = pool::new()                            /* 建在**当前块**下 ⇒ 块退出即回收 */
var p = pool<i32>::withCap(r, 1024)
let h = p.own(42)?
...
p.reset()                                        /* 清空但复用块（churn 不涨）*/
```

## 7. 不解决的 / 明确的边界

1. **epoch 内部的碎片**：pool 里反复 erase/insert 仍要靠 **free list / dense-swap** 那套工程
   pool 只把"整批还"变成可能，不是万能
2. **完全动态、说不出来的生命周期** ⇒ 出口只有 C 互操作（交给带 malloc/free 的库）
   或一个真 GC（会推翻"隐藏语义为零""过期字节确定"两根柱子 ⇒ 不建议）
3. **"顺手回收"只在块退出时发生** ⇒ 服务级长命容器（活在永不退出的块里）**永远不会被顺手销毁**
   ⇒ 那类容器**必须显式 `reset()`/`close()`**
   ⇒ 一句话：**这套方案保证"不漏"，不保证"自动收缩长命数据"**
4. **`slice` 对 pool 容器不再适用**（主人已确认）⇒ 用 §5 的 `copyInto`/`forEach` 兜
5. **原地扩展只是优化**：它救不了服务级长命容器（那要靠 `reset`）
6. **`pool` 的设计不允许外部引用**（对外只给 handle）—— 这是**硬规则**，不是纪律：
   用户**拿不到**指向 pool 内存的引用 ⇒ 用户可见的表面上不存在「引用悬垂」
   唯一会出现这种引用的地方是**容器方法内部**（「查表拿到 descriptor」那一下），瞬时用完即弃
   **而且现有规则本来就算得对，不需要新检查**（2026-09-24 核对 `src/check_escape.c`）：
   「调用结果的深度 = 实参与接收者的最大深度」—— `EX_METHOD` 取 `max(receiver, args)`，
   `EX_CALL` 取 `max(args)`
   ⇒ 库方法 `fn at(self: ref pool<T>, h) -> ?ref T` 返回的引用，深度 = **容器自己所在的层**
   = **pool 所在的层** ⇒ 想把它存到更长命的地方，**照样编不过**也就是说：
   **走"容器方法"这条路取引用是安全的，一个字的编译器改动都不需要**
   唯一的窄口子：**自由函数**（没有任何携带容器的实参，例如只在内部包一层
   `extc_region_alloc(rid, …)`）返回这种指针 ⇒ 深度会算成 **depth 0**（"哪儿都能存"）
   ⇒ 这才是「库纪律 / 可选小检查」真正的适用面，而且它很窄
   （结论：把纪律变成硬约束是可选的锦上添花，不是必需）

### 10.1 时间开销（主人问「会不会明显提升开销」——量出来的答案）

`-O2`，3–4 次取最好，用户时间（`/tmp/perf.extc` 模式的临时基准）：

| 场景 | 裸 `slice`（varArray）| `pool`（句柄容器）| 倍率 |
|---|---|---|---|
| **遍历**（2e8 次读取）| 0.124s（0.62 ns/元素）| `atDense` 0.151s · `denseView` **0.143s** | **1.15–1.22×** |
| **随机访问 · 按下标**（1e7，`denseView` 后 `v[x]`）| 0.065s | **0.071s** | **1.09×** |
| **随机访问 · 按下标**（`atDense(x)` 方法版）| 0.065s | 0.079s | **1.22×** |
| **随机访问 · 经句柄**（`get(hs[x])`）| 0.065s | 0.586s | **9.5×**|
| **随机访问 · 先 `gather` 再按下标**（`idx[x]` → `v[d]`）| 0.062s | **0.199s** | **3.2×**（比句柄路径好 **2.9×**）|
| **churn**（2e8，O(1) 内存）| 0.317s（只是栈式 pop）| 0.899s（任意槽 remove + 复用 + 失效检测）| **2.8×** |

**两次更正（都是我的基准/口径写错，记下来免得再犯）**：
1. "遍历 2.5×" ⇒ 真实是 **1.15–1.22×**：建表阶段的 insert 成本没摊掉，被算进了遍历
2. "随机访问 12–19×" ⇒ **把两件不同的事混成一件了**：
   - **按下标随机访问**（现实里绝大多数"随机访问"：邻居表、置换、跳着读）⇒
     `denseView()` 之后就是 `v[x]`，**1.09×** **根本不用优化**（pool 的值本来就在一段连续内存里）
   - **经句柄访问**（`get(h)`）才是 9.1× —— 但那不是"随机访问容器的代价"，而是
     **"拿句柄当下标用"的代价**：句柄是**稳定标识**（对象池/实体表/撤销栈），不是数组下标
     它贵在**三条互不相干的随机访存流**（句柄数组 → 元数据 → 值）

### 10.2 两条优化做完了（2026-09-24），实测如下

| 做法 | 结果 |
|---|---|
| **元数据打包**（`sparse`+`gens` 合成一张 `ent` i64：存活 `(gen<<32)\｜(dense+1)`、空闲 `(gen<<32)\｜(next+cap+2)`）| **内存 12 → 8 字节/槽** 但**时间几乎没变**（0.594 → 0.586s）—— 我原来预期 1.4–1.6×，**猜错了** 原因：随机访存的**流数**没变（句柄数组 + 元数据 + 值 三条），少一张表并不减少 miss |
| **`gather`**（一批句柄一次性解析成 dense 下标）| **9.5× → 3.2×**（比句柄路径好 **2.9×**）—— 代价是**多一趟 O(k)**：只访问一次的句柄不值得 gather，反复访问同一批才划算 |

残留的 3.2× 来自 `idx[x]` 自己也是一条随机流（逃不掉，除非索引本身顺序产生 ——
那正是 **CSR / 局部下标** 的形状：**关系型访问（邻居、边、孩子）应当顺序产生下标**）

**结论（按访问模式选工具）**：
| 模式 | 用什么 | 实测 |
|---|---|---|
| 顺序遍历 | `denseView()` / 列 / CSR | 1.15× |
| **按下标随机** | `denseView()` + `v[x]` | **1.09–1.23×** |
| 句柄密集且反复 | 先 `gather` 再一次解析 | **3.2×** |
| 句柄偶尔用 | 直接 `get(h)` | 9.5×（但只有几次，无所谓）|
| key → value 随机 | **已落地** `std::map`（`stdlib/std/map.extc`：开放寻址 + 墓碑 + i64 键 / 泛型值；`tests/map/` 挂成 `check.sh` 第 19 节）| 1 次 miss |

**内存**：每槽元数据 12 字节（`slots`+`sparse`+`gens` 各 4）⇒ 元素是 `i32` 时**总内存 4×**；
元素 ≥12 字节时可忽略 ⇒ 小元素别用句柄容器（或把 `sparse`+`gen` 合成一个 i64 ⇒ 8 字节）

**三条把开销压回去的路**（都已实测或明确可做）：
1. **热点循环不要走容器，遍历"列"**：`denseView()` 零拷贝给出 dense 前段（见 `pool.extc` 的注释）
   ⇒ 遍历回到 1.15× 这也正是 ECS 的形状（系统遍历列，不是遍历容器）
2. **句柄随机访问贵在 cache miss**（三张表 + 校验）⇒ 元数据瘦身 · 批量校验（先验一批再一次跑）
3. **`@inline` 挑着加**：实测 `get`/`contains` 内联**对随机访问有利、对 churn 有害** ⇒ 不内联

**换来的是什么**（跟 2.8× 不是一个量级）：churn 的内存是**平**的（否则**无界**涨）·
任意槽 `remove` 是 O(1)（`varArray` 只能栈式）· 旧句柄**可检出**（C++ 那边是 UB）
