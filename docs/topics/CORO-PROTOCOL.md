## 二、协议层：现状拼图

挂起请求是**协程 `yield` 出去的一个 i64**，含义靠猜负数：

| 值 | 含义 | 谁产生 |
|---|---|---|
| `>= 0` | 等这个 fd **可读** | 用户直接 `yield fd` |
| `-1` | 不等，立刻重新推进 | 用户/库 |
| `-3`（`WAIT_UNTIL`） | 等 `loop.pendingUntil` 那个 deadline | `scheduler` |
| `-4`（`WAIT_FD_W`） | 等 `loop.pendingFd` **可写** | TLS 需要 |

代码位置：`stdlib/std/coro/scheduler.extc` 的 `resumeRow`（解读请求）、`pump`（事件分发）、
`finish`（收尾）；文档 `docs/topics/CONCURRENCY.md` §4.4。

## 三、被咬到的三个实例（都是真事）

1. **返回码撞车（静默）**：`tls` 包用 `WANT_READ = 1`，而会话层的约定是"`>0` 就是字节数"
   ⇒ 会话层把"等可读"当成"读到 1 字节"逐次累加：缓冲全 0 而计数涨到 4096 ✗。
   是两个包**各自的判据都绿**、只有**组合**才暴露的那种 bug。修法：全栈统一"成功 = 正字节数、
   等待/关闭/错误 = 负数"。
2. **同一个 fd 两个等待者（静默）**：epoll 的 `user-data` 一个 fd 只能存一个 tag，而我们把 tag
   当成**行号** ⇒ 第二个等待者一注册就覆盖第一个 ⇒ **一个被唤醒，另一个永远挂着**。
   判据里表现成 `STUCK live=1 rounds=500`（我最初还以为是自己 fixture 写错了）。
3. **helper 不能 `yield`（语言级）**：`yield` 只在协程体里合法 ⇒ 每处阻塞要写 4 行
   "让出 → 就绪 → 重试"。量过：一条网关会话约 6 处阻塞 ⇒ **约 24 行样板 / 整个模块 ~300 行 = 8%**。

## 四、三条修法（同一个问题的三种深度）

### A. tag 存 fd 本身 + 任务侧等待表 + **全员唤醒**（最小）

- `yield fd` 时 `extc_epoll_arm(ep, fd, 1, /*tag=*/fd)`，并把 `(fd, row)` 记进一张等待表；
- 事件到达时按 fd 扫表，把这批行**全部**唤醒（先快照再唤醒：唤醒的行可能立刻又挂起，
  边扫边唤醒会自己喂自己、原地空转）；
- 正确性依据：**level-triggered ⇒ 重复唤醒安全**（协程醒来重试，没就绪就再挂起）。
  这条不变式我们本来就在用（"先写后注册不丢唤醒"判据就是它）。
- 量：`scheduler.extc` 约 **40–60 行**；等待表是定长数组（`tasks` 用字面量组装，
  省略字段零值 ⇒ 现有调用点一个不用改）；表满要**响亮 trap**（静默丢等待者 = 任务永远挂着）。
- 已知的丑：`tasks<T>` 里塞裸数组（因为换 `vector` 会让每个调用点都要改）；容量 256 是拍的数，
  真修法是 `docs/topics/BOUNDED-TABLE.md` 里那套"定长热路径 + 溢出容器"。

### B. 每个等待者一个 eventfd/管道

- 每个等待者有自己的 epoll 句柄，fd 就绪由"拥有者"转发。代价：每个等待者多 2 个 fd +
  转发逻辑。**看不出比 A 好在哪**，只在"等待者要跨进程"时才有意义。

### C. **带类型的请求** + `wait(ticket)` 原语 + fd 就绪归一个 demux（最彻底）

```extc
type request = | read(fd: i64) | write(fd: i64) | sleep(until: i64) | wait(ticket: i64) | yieldNow
```

- 请求是**一个类型**而不是"猜哪个负数" ⇒ 撞车（第三节第 1 条）从构造上不可能；
- `wait(ticket)` 让"唤醒"与"fd 就绪"**解耦**：谁都可以唤醒一个 ticket（不绑 fd），
  于是一条连接上的多路复用由**一个 demux 协程**拥有 socket、把事件转成 ticket 唤醒 ✓
  （这正是 Go/idio 的分层，也正好是 QQ 网关层的形状：一条会话协程独占 TLS socket）；
- `read/write/sleep` 仍是 fd/deadline 的语法糖，由调度器翻译成 epoll 注册 + ticket；
- 量：`scheduler.extc` 一次重写 **300–500 行**（**不动语言**——请求类型就是普通枚举，
  `yield` 出去的仍是 i64 tag+载荷，或者用暂存槽）。

## 五、我的意见（与事实分开）

1. **A 该做**：它把"静默"变成"正确"，成本小，而且顺手把那个静默失败变成响亮 trap。
2. **C 是它该长的样子**，但**现在不该做**：它改变的是内部接口，而 QQBot 主线还没跑起来；
   等 `qq::gateway` 真写出"多路复用一条连接"的需求，C 的收益才有判据可依。
3. **B 不用考虑**。
4. **"一坨屎"的准确位置**是：协议层是"一串猜出来的负数 + 一张覆盖式的 tag"，
   而不是"一个类型 + 一张等待表 + 响亮失败"。**语言层（状态机、arena、效应）不背这个锅。**
5. 语言级那条（helper 不能 `yield`）是**另一件事**（Kotlin 模型的"可挂起函数"），
   前面已记账；它与协议层无关。
