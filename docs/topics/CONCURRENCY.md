## 0. 一句话

> **不加并发运行时，只加一个编译期变换 + 四个 syscall 包装。**
> 协程 = 把「控制流状态」从**隐式**（机器栈）变成**显式**（一块 arena 内存）；
> 调度器 = 一段**普通 extC 代码**，你能读、能改、能换掉。

| 层 | 谁写 | 内容 |
|---|---|---|
| **1 · 编译器** | 状态机变换 + 一个类型 | `coroutine<Req, Resp>` · `yield` · `spawn` / `resume` |
| **2 · `std::sys::*`** | 4 个原语（`extern!` 签字） | `sys::io` 的 `epoll_*` · **`sys::thread`** 的 `thread_*`/`mutex_*`/`channel_*` |
| **3 · stdlib** | **extC 写** | 调度器（`while` + `epoll_wait`）· `parallel` |
| **4 · 用户** | 主人 | 协议循环、服务器、GUI、Actor |

**没有第 5 层。** 没有绿色线程，没有 executor 抽象，没有隐藏的运行时线程。

## 1. 前提：**无栈**（这一节不成立则本文全部作废）

协程暂停时，"执行到哪儿了 + 局部变量"这一堆东西放哪？两条路：

| | 状态是什么 | 「控制流状态 = 数据」成立吗 |
|---|---|---|
| **无栈**（C++20 / Rust `async` 式） | 编译器生成的 **frame 结构体 + PC 整数** | **字面成立** —— 它就是一块内存 |
| **有栈**（`ucontext` / `setjmp` / boost.context 式） | **一整条 C 机器栈** | **恰恰不成立** |

### 为什么有栈会让主人的核心命题失效

有栈路线下，状态是**一整条连续的机器栈**。而栈**不是一等值**：

- 不能放进 arena、不能按块回收、不能检查里面有什么
- 需要**自己的**栈分配器 + 栈池 + guard page + 固定大小的栈（深递归会爆）

⇒ 那等于**偷偷引入第二种内存模型**，而它恰好是 extC 最不想要的那种：
**藏起来的、编译器管不了的**（违反 P：能证明的不留痕迹；违反 P′：不能证明的必须看得见）

### 无栈的代价（诚实清单，别当白拿）

| 代价 | 说明 |
|---|---|
| **`yield` 不能跨函数** | 只能在协程体**自己这一层**。`fn a(){ yield }` 被 `b()` 调用时，`b` 里 yield 不上去。这是 C++20 / Rust 同样有的限制 |
| 生成的 C 啰嗦 | 函数体变成一个大 `switch`，状态数 = `yield` 点数 + 1 |
| 局部变量要逐个提升 | 跨 `yield` 活着的局部必须搬进 frame；编译器要算活跃性（**这一步最容易出 bug，见 §4 第 1 步**）|

**为什么还是选无栈**（三条，按分量）：

1. 无栈是"控制流状态 = 数据"的**唯一**成立形式 ⇒ 本文其他所有结论都靠它
2. 主人的用例**没有一个是真需要有栈的**（见 §7 逐个核过）
3. 无栈**只是编译期变换** ⇒ **今天就能手写它验证**（§4 第 1 步，不动编译器）

## 2. 帧 + arena：为什么结合得好

### 2.1 三条实测事实（2026-09-23 核过）

| 事实 | 出处 |
|---|---|
| arena 的**块是 4096 字节起**：`cap = n > 4096 ? n : 4096` | `src/codegen.c:2687` |
| arena **目前没有块大小字段**：`struct extc_arena { extc_ablock *top; }` | `src/codegen.c:2662` |
| 一个函数调用里 **arena 是入口建一次、所有分配点共用**；`__extc_a[]` 的下标 = **词法层号** | `src/codegen.c` 生成的代码 |

第三条尤其重要。它长的样子是：

```c
static int32_t fill(int64_t n) {
    extc_arena __extc_a[3] = {0};          // ← 入口建一次
    ...
    extc_arena_alloc(&__extc_a[1], ...)    // ← 所有 new / alloc 都用它
    ...
    extc_arena_release(&__extc_a[2]);      // ← 块退出时释放那一格
}
```

⇒ **协程帧就是"某一层的一次分配"** —— 它跟具体某个块同寿，跟 arena 天生对齐

### 2.2 帧的寿命："往上追溯"（主人 2026-09-23 的答案）

> 主人的话：「**协程 arena 给创建协程的 arena 里面的那个玩意儿 release，总之往上追溯**」

**这就是全部，而且不需要任何新机制。** 展开：

`spawn` 返回的句柄深度是 N，句柄的**所有用法**都被"深度 ≤ N"这条规则罩住
⇒ `promoteInto` 会自己**往上爬**，一直爬到"那只 arena 的寿命盖得住所有用法"为止。
爬到哪里，帧就落在哪只 arena 里，release 也归那只 —— **跟普通值完全一样**

| 协程寿命 | 帧落在哪 | 谁 release |
|---|---|---|
| 和某个块一样 | 那块 | 块退自动 |
| 比块长（连接级） | **更外层的块** | 那个块退 |

**本文第一稿在这里写错过一次**：我当时说"连接级长寿命协程需要一点点新东西
（`close()` 或者绑在连接对象上）"—— **不需要**。上面的 `serve()` 那种写法里
**一个额外的块都没有 ⇒ 什么都不会被提前回收**，寿命自动就是"连接级"
（记录在案：这是当天第二个"我以为要加东西、其实不用"的例子）

### 2.3 唯一要守的规则（现成的，一行）

> **句柄的寿命 ≤ 帧的 arena 的寿命**

反过来说：**"协程比创建它的块活得久"在 extC 里是编译错误**

而这条**已经有机器在管**：逃逸检查的深度规则。`PLAN #52`（2026-09-23 修）刚补的那个
机制 —— "目的地更浅 ⇒ 把调用点的 arena 一起拉浅" —— 跟 `spawn` 是**同一个形状**：

```
#52：  while i<3 { let t = make()   b = t }     ← t 的存储比 b 深 ⇒ 挡 / 或拉浅
spawn： while … { let c = spawn(f) reg.add(c) } ← c 的 arena 比 reg 浅才行 ⇒ 同一条规则
```

⇒ `spawn` 不是一个"新种类的东西"，它就是又一个**有家被调者**（`needsHome`）
⇒ 用户撞到它时看到的是一条**编译错误**，指着那行 `spawn` —— 比 Go 里
"goroutine 捕获了循环变量"那种运行时惊喜好得多

### 2.4 推导：`coroutine<Req, Resp>` 是**普通 enum**，所以调度器是用户代码

**这是本文最重要的设计选择。** 定义全部能写在 stdlib 里（`stdlib/std/sched.extc`）：

```extc
// 协程对外的"一步" —— 普通的带载荷枚举，**没有隐藏语义**
type step<Req, Resp> = | produced(Resp) | want(fd: i32, events: i32) | finished

fn resumeStep<Req, Resp>(c: mut ref coroutine<Req, Resp>, req: Req) -> step<Req, Resp>
```

于是**整个调度器就是一段普通 extC**：

```extc
fn run<Req, Resp>(cs: mut ref varArray<coroutine<Req, Resp>>) {
    var evs: [64]epoll_event
    while cs.len > 0 {
        let n = sys::epoll_wait(ep, evs[..], -1)      // ← 唯一的"等待原语"
        var i: i64 = 0
        while i < i64(n) {
            let c = cs[evs[i].data]
            match resumeStep(ref *c, reqOf(evs[i])) {
                produced(r)  => flush(r)
                want(fd, ev) => epoll_ctlAdd(ep, fd, ev)
                finished     => removeSwap(cs, i)
            }
            i = i + 1
        }
    }
}
```

**好处不是"写得更少"，而是**：

- 调度策略**看得见、可替换、可调试**（想让某类 fd 优先？改那个 `while`）
- 等待队列是 `varArray`、事件循环是 `while`、句柄是索引、取消是 `removeSwap`
- ⇒ **不需要并发运行时**。它不是"藏在库里的调度器"，就是几十行你自己写的代码

**代价**：调度器**必须与它驱动的协程同帧**（否则 §2.3 那条规则挡你）。
这是好事（结构化并发免费拿到），但要写清楚：**`run` 不返回之前，帧不会退**

### 2.5 一个必须指定的实现细节（否则静默错）

> **`resume` 必须把「帧自己那只 arena」当 home 传下去，而不是"恢复者的当前块"。**

不然：调度器在一个每轮退出的块里 `resume`，协程内部 `new` 出来的状态就落在那个块里
⇒ 下一轮悬垂

⇒ 顺带得到一条**使用规矩**（要写进手册）：

> **协程里 `new` 的东西活到协程结束，不是活到这次 resume。**
> 想要"这一次用完就扔"的临时数据，就在调度器那一侧分配

## 3. 已知代价与限制（别让文档说谎）

### 3.1 `blkSize`：块大小要能显式指定（主人 2026-09-23 提出）

**问题**：arena 块 4096 字节起，而一个协程帧通常**只有几十字节** ⇒ 几十倍浪费 + 每帧一次
`malloc`。

**主人的方案**：让 `blkSize` 成为 arena 的字段（**缺省 4096**），协程 arena 用帧大小当块大小。

**成立，但有一个坑要说清**：

> **要的是"帧单独一块、精确大小"，不是"把整只 arena 的块大小压到帧那么小"。**

因为块大小**恰好等于**帧大小时，协程体里第一个 `new` 就装不下 ⇒ 立刻又 `malloc` 一块
⇒ 正确形状是：**帧自己一块（精确适配）** + **它内部 `new` 的走正常 4096 块**

```c
typedef struct extc_arena { extc_ablock *top; int64_t blkSize; } extc_arena;
// blkSize == 0 ⇒ 用缺省 4096
```

**副产品**：既然 `sizeof(frame)` **编译期就知道**，就能按**大小分级（size class）的块池**分配
⇒ 分配退化成 O(1) 取链表头（**比 malloc 快**），按大小分桶则**内部碎片为零**

**这一条推翻了一个我先前写下的推论**（诚实记账）：

| | 只有 4KB 地板 | 有了 `blkSize` |
|---|---|---|
| 长寿命协程（连接级，上千次 resume） | 摊到零 | 摊到零 |
| 一次性协程（一请求一协程） | 4KB/个 | **≈帧大小/个** |

⇒ 我先前说"4KB 粒度会把你**顶向**长寿命协程"—— **那个结论作废**
"一请求一协程"在有了 `blkSize` 之后**重新变得可行**

### 3.2 剩下的真问题：**累积**（不是寿命）

"往上追溯"解决**寿命**，解决不了**累积**：

> 一只长寿命 arena 里反复 `new` ⇒ 内存**只增不减**，因为 arena 的回收粒度是**块**
> （没有对象级释放）。`@overwrite` 能复用固定几块，但装不下的部分还是会堆。

⇒ **长寿命服务器里，"每连接一只 arena"迟早要面对"这只 arena 什么时候 reset"** ——
而答案只能来自**语义边界**（连接关了 / 每 N 个请求）。

这是 arena 语义的直接推论，**不是协程引入的债**；但它是一条**运维上必须写清楚**的东西，
否则跑一个月之后 RSS 曲线会很难看

有了 §3.1 之后这个痛**小多了**（帧按精确大小分块 ⇒ 一连接几十字节而不是 4KB）

### 3.3 两个"永远诚实"的边界

| 边界 | 说明 |
|---|---|
| **协程不能比 `main` 活得久** | 这是必须的（进程结束一切皆无），但意味着"守护协程"这种形状要靠 `main` 里的循环 |
| **`yield` 不能跨函数** | 见 §1。递归下降解析器想"在递归深处 yield"写不出来 —— 出路是显式栈（自己维护 `varArray` 当栈）|

## 4. 落地顺序（这一节最重要 —— 它决定会不会翻车）

| 步 | 内容 | 为什么是这个顺序 |
|---|---|---|
| **1** | **手写一个状态机**（**不动编译器**）| 拿 `reader` 的行迭代器当例子，照 §1 那个 `struct + switch` 的形状手写。**这一步免费验证全部假设**：帧放 arena 顺不顺、哪个变量要提升、`yield` 出来的引用深度该是几。**一行编译器代码都还没写就能发现设计问题** |
| **2** | `for` + 迭代器协议 | 已在 `PLAN.md` §1 主线上。**迭代器 = 最弱的协程**，先把它做顺 |
| **3** | lambda / 闭包 | **闭包转换 = 把捕获环境显式化成结构体**，跟状态机转换是**同一个变换**（主人那张表里就是这么对的）⇒ 先做它 = 把变换写第一遍 |

### 4.0 第 1 步结果（2026-09-26 实测 —— 已做，结论：**可行，但撞出一个真洞**）

**做了什么**：`tests/coro/statemachine.extc` —— 一个 RESP 风格协议（`PING` / `SET k n` + 长度前缀值体 / `GET k`）
的**手工状态机**：`struct frame { pc, need, lineBuf[128], keyBuf[32], valBuf[256], … }` +
`fn step(f, st, in, out)`，字节一个个喂。**一行编译器代码都没写。**
判据 `tests/coro/run.sh`（已接进 `check.sh`）：① 响应逐行正确（含 CRLF）；② **切分 1..16 字节与一次喂完逐字节相同**；
③ 生成物过 `-std=c11 -Wall -Werror`。

**三个待答问题的答案**

| 问题 | 答案 | 依据 |
|---|---|---|
| ① 帧放 arena 顺不顺 | **顺 —— 但今天最省的帧根本不需要 arena** | 帧若含 `string`（⇒ 含 `ref`），`var f: frame` **编不过**（"cannot zero-initialize … it contains a reference"），必须用结构体字面量或构造函数初始化；**无引用的帧**（`pc` + 定长缓冲 + 长度）直接 `var f: frame` ✓ |
| ② 哪些局部变量必须搬进帧 | `pc`（走到哪）· **半截的行缓冲** · 待读长度 `need` · 键/值累积缓冲 | 实测：少了任一个，切分不变性立刻不成立 |
| ③ 引用能不能跨暂停活着 | **在"帧内自有存储"的设计下，这个问题根本不会出现** | 帧里只放字节缓冲 + 偏移 ⇒ **没有任何引用跨越暂停** ⇒ §9 第 4 条（跨 yield 的引用深度）无需新规则 ✓ 顺带：帧可自由移动/复制（调度器挪帧、池化帧都要这个性质） |

**顺带得到的两条可用结论**
- **含引用的结构体数组今天声明不了**（`var a: [2]p` 报同一个零值错误，且没有数组字面量语法）⇒ 帧里不能放"表"，应用状态要么放帧外、要么做成无引用；
- **模型在推着你把帧和状态都做成"无引用聚合"**：整个会话 = 一块普通内存，零分配、可整体搬运 ✓ 对协程是**好消息**（帧便宜、可池化）。

**⚠️ 撞出的洞（不是协程的问题，是既有 arena 机制的缺口）**：[`tests/arena-soundness/H2_home_zone_depth2.extc`](../../tests/arena-soundness/H2_home_zone_depth2.extc)
> **home zone 的传递闭包只做了一层。** `main → put → newString`（3 层）正确；
> `main → wrap → put → newString`（**4 层**）就坏：`wrap` 把**自己的** zone 传给 `put`，并把自己的
> `__extc_home_zone` 标成 `EXTC_UNUSED` ⇒ `newString` 的缓冲分配在 `wrap` 的 place 里，返回即被释放 ⇒
> 缓冲被下一次分配复用 ⇒ **静默改坏**（`keys[0]` 从 `"k"` 变成 `"a"`）。
> **ASan 判定 `heap-use-after-free`**（反例库按自己的语义记为 `ACCEPT+UAF` = 洞成立）。
> 文档对照：[`ARENA-FORMAL.md`](ARENA-FORMAL.md):678 写的就是"**needsHome 的传递闭包**" ⇒ **实现比文档少一层**。
>
> **对协程的含义**：任何"多层辅助函数 + 往容器里塞新建的值"的写法都会中招，而**协程调度器正是这种写法**
> （调度器 → 处理函数 → 辅助函数 → 往容器里放结果）。⇒ **修它应当排在协程第 2 步之前**。

**第 1 步要挑"最像会咬人"的例子，不是最简单的**
挑最简单的会给你**假信心**。建议挑一个真的请求-响应协议（比如 HTTP 解析的一小段），
看无栈写起来有多别扭 —— 如果别扭到不能忍，§1 那个前提就要重新审

### 4.1 第 2 步进展（2026-09-26）：迭代器协议**原型已跑通**，特性待落地

**做了什么**：`tests/coro/iterator_protocol.extc`（判据已进 `tests/coro/run.sh`，`check.sh` 里跑）——
一个**用户类型**加三个方法，用**显式 `while`** 驱动：

```extc
fn iter(self: ref counter)  -> counter   // 迭代状态是**值**，活在调用者帧里
fn next(self: mut ref counter) -> bool   // 还有一个吗？
fn value(self: ref counter) -> i64       // 当前这个
```

实测：`sum=15 shown=5` · `empty=0` · `steps=4`（第三个断言是**两个迭代器互不干扰** —— 状态是值、
不共享 ⇒ 这是无引用聚合模型的直接好处 ✓）

**为什么是这三个方法，而不是 `option<T> next()`**：`option` 要 `?T` 解包，而"先问有没有、再取值"
两步在无引用聚合的模型里更省：状态就是一个普通 struct，零分配、零引用 ✓（与第 1 步的状态机同款）

**`for x in c` 今天为什么驱动不了它**（这就是特性的"before"）：

```
error: cannot slice a value of type `counter`
  note: Only a fixed array or a view can be sliced.
```

⇒ 今天的脱糖是**基于切片**的（`for d in c` → `var __extc_s = c[..]`）✓ 用户类型没有 `[..]` ✓

## 5. 并行：三种原语，一个模型

### 5.1 Redis 式 chunk（主人的模型）

```
主线程（拥有 arena）
  ├── worker A：生产 chunk A（chunk 自己的 arena）
  ├── worker B：生产 chunk B
  └── worker C：生产 chunk C
       ↓ channel（所有权转移，不是共享）
主线程：按顺序 flush，回收 chunk arena
```

只加三个 `std::sys::thread` 原语：**`thread_spawn` · `mutex` · `channel`（有界）**，
然后 stdlib 提供一个函数：

```extc
fn parallel<A, B>(input: slice<A>, f: fn(A) -> B) -> varArray<B>
// 语义：split → 每个 worker 一条线程 + 自己的 arena → 产出经 channel 转移回来 → 主线程合并
```

### 5.2 两处要把规则写严

**(1) "worker 不碰共享数据" → 改成「worker 只碰 _不可变_ 共享数据」**

分（split）本身就要求每个 worker 看得见**同一份输入**。那是共享的 —— 只是**不可变**，所以安全。
差别很大，必须说清：

> **不可变可共享（`ref slice<A>`）· 可变必转移（移动）**

⇒ 无数据竞争是**结构保证**，不是靠纪律：唯一能共享的是 `ref`（编译器不让你通过它写），
唯一能传出去的是**移动**

**(2) arena 池是唯一会真堵的地方 —— 要**有界** + 背压**

主人原文写的"低频加锁"，但真实负载下最容易出事的就是它：

> 生产者比消费者快 ⇒ 块在 channel 里排队 ⇒ 池里的 arena 全被占住 ⇒ **内存涨**

⇒ **有界池 + 背压**，不能只靠"低频"

**诚实的共享清单**（一共三处，不是一处）：**channel · arena 池 · 每线程的分配器**
（跨线程给块，C 里需要显式的内存序或一把锁 —— 那是第三处）

### 5.3 "这是通用并行，不是受限并行"

> 主人：所有并行计算都能表达成 `分 → 并行处理 → 合并`；唯一真正的限制是"不能原地修改共享数据结构"。

**同意**，但把那条限制说得更准一点：不是"不能原地修改"，而是
**"原地修改必须发生在同一个 worker 自己的 arena 里"**。跨 worker 的合并一律走 `分-合`
（这跟 MapReduce / fork-join 的结构一致）

## 6. `enum` 协议 vs `trait` / `interface`（主人那张表的一处更正）

| 语言 | 协议怎么固定 | 分发方式 | 编译器检查 |
|---|---|---|---|
| C | 函数指针签名 | **间接调用** | |
| Python | 文档 + 约定 | 动态查找 | |
| Go | interface | **间接调用**（itable）| 但是运行期查表 |
| Rust | trait | 单态化 / **间接调用**（`dyn`）| |
| **extC** | **`enum` + 协程类型** | **`switch` 直接跳** | |

**更正/加强**：extC 这一格不只是"零开销的 vtable"，而是**根本没有间接调用** ——
`enum` 分发是 `switch`，没有函数指针、没有表
⇒ 这比"零开销抽象"更强，值得写明白

**代价必须并排写着（否则读者以为白拿）**：

> **协议是封闭的。** 加一种请求类型要**重编译所有处理者**。

这正是主人说的"**开放实例，不开放类型**"
⇒ 而它在**插件系统**里其实是**优点**：协议 ABI 必须冻结，否则 `dlopen` 回来的东西对不上

## 8. 明确**不做**的（每条都有理由）

| 不做 | 理由 |
|---|---|
| **有栈协程** | 状态变成不透明的机器栈 ⇒ arena 管不了 ⇒ 偷偷引入第二种内存模型（§1）|
| **`async`/`await` 的函数着色** | 染色的根源是"普通函数不能碰协程状态"。无栈确实有这条限制，但**没必要把它传染到类型系统上** —— `yield` 是控制流，不是函数类型的一部分 |
| **运行时拥有的调度器** | 藏起来的调度器就是 `cin` 那个黑盒（§2.4）⇒ 违反 P′ |
| **共享可变状态 + 隐式同步** | 主人的原则。改成"不可变可共享 · 可变必转移"（§5.2）|
| **绿色线程 / 抢占** | 那是另一门语言 |
| **协程池 / executor 抽象** | 帧很便宜（一个 struct），要池子自己写 `varArray` |
| **第一版做跨线程协程迁移** | 协程绑在线程上，简单得多，**够覆盖 Redis 式模型** |
| **结构化并发的语法** | `run { … }` 那个块本身就是结构化的 |

## 11. 最后：为什么这条路是从 arena 长出来的（主人原文）

> **1. 控制流是数据 → 数据能被 arena 管理 → 协程不需要新内存模型**

## 12. 并发对 arena/pool 的 soundness 要求（2026-09-26 定稿）

起因：作者指出「协程/线程对 arena/pool 程序 soundness 要求很高」。下面把这句话**变成可执行的规则**。

现在这套分析靠三个假设撑着，协程与线程各破坏其中不同的部分：

| 假设 | 单线程单栈下 | 协程（可挂起） | 线程（真并行） |
|---|---|---|---|
| **一条调用链**决定"此刻在哪个地方" | ✓ | ✗ 挂起后从**另一条链**恢复 ⇒ 同一帧前后两次分配落在不同地方 | 各自有栈，共享堆 |
| **词法深度 ≈ 生命周期** | ✓ | ✗ 帧活得比创建它的词法块久 ⇒ 深度不再是上界 | 同左，且跨线程可见 |
| **单线程 ⇒ 元数据无竞争** | ✓ | ✓ 协作式仍单线程 | ✗ 共享可变状态 |

### 12.1 四条规则（每条都必须有判据）

| # | 规则 | 为什么 | 判据 | 状态 |
|---|---|---|---|---|
| **1** | **任务/线程是"地方根"**：place 在**创建时钉死**、随帧存下来；恢复点**禁止重新推导** | 否则同一帧前后两次分配落在不同地方 | **前身判据已就位**：`tools/check_concurrency_guards.py` 的 J1 —— 生成物里每个 zone 实参只许是**转发** `__extc_home_zone` / **本帧记号** `__extc_zm<k>` / **整数字面量**；`spawn` 落地时再加"实参必须来自帧字段"（生成物断言 + 一个 `tests/coro` 用例） | 判据已就位（见下"现成实例"） |
| **2** | **跨任务/跨挂起点只传值或池句柄**；引用必须提到 home/任务层，**指不动的东西（C 栈局部）直接拒绝** | 帧/computed 值活得比创建它的词法块久 ⇒ 深度不再是上界 | 反例库 `E1_dyn_payload_carries_ref`；修好后毕业进 `tests/errors/` | ✗ **洞已实测确认** |

### 12.2 已实测的证据（2026-09-26）

### 12.3 为什么"先立判据"不是形式主义

并发把失败模式改了：单线程下判错 ⇒ 一个线程里悬垂，**ASan 能抓、可复现**；
并发下判错 ⇒ **只在某种交错下出现**，不可复现、ASan 也未必抓到 ✗
⇒ 唯一靠得住的是**静态保守性**，而全项目还有 **37 个带 `default:` 的手写遍历器**（加 AST 种类时
编译器**不会**提醒）⇒ 它们是"静态判断静默出错"的入口 ✓（见 `docs/topics/AST-WALKERS.md`）

落地顺序：**先修规则 2（E1）→ 把规则 1/3/4 的判据写在特性之前 → 再动 `coroutine`/`spawn`/`resume`** ✓
