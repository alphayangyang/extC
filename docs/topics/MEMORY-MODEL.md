# extC 的内存管理模型：Arena 与 Pool

> **一句话**：这里没有 GC，也没有裸 `malloc/free`。用户看到的是两种**作用域化的内存** ——
> **arena 管寿命**（块链，LIFO，零 free），**pool 管复用**（句柄 + 世代，可删可回收）。
> 编译器负责证明"每个解引用都落在活着的区域里"，运行期只做一次比较。

---

## 0. 一页总览

```
                        一个地方（作用域 / 块）—— zone（索引头，独立旁链）
                                     │
              ┌──────────────────────┴───────────────────────┐
              │                                              │
        arena（寿命的骨架）                            pool 树（复用与身份）
        ┌────────────────────┐                     ┌──────────────────────┐
        │ 块 → 块 → 块 …     │  生命周期一起管      │ pool（容器套容器=逻辑父子）│
        │ bump 分配，无 free │ ─────────────────▶ │ 数据 + free list + 世代  │
        │ 层号 = 词法层      │                     │ 句柄 = (slot, gen)       │
        └────────────────────┘                     └──────────────────────┘
              │                                              │
      「什么时候没」                                   「能不能重新用」
```

| | **arena** | **pool / region** |
|---|---|---|
| 治什么病 | 寿命：谁的内存、活到什么时候 | 复用：删掉/重建的容器垃圾、无法复用、指针跳转 |
| 结构 | 块链，bump 指针，LIFO | 槽位 + free list + 世代 + 父链 |
| 分配代价 | ~0.5 ns/次（实测） | ~26 ns/次（实测，买到的是身份与复用）|
| 释放 | 块退出时整块回收（不做逐个 free）| `remove`/`clear`/`release`，可**真收缩** |
| 身份 | 无（地址即可） | **稳定句柄**：`(slot, gen)`，旧句柄必失效 |
| 适合 | 连续增长的数据、临时量、AST/帧 | 删增动态大的容器（`pool`/`map`/`set`/`graph`）|

> 「**按访问模式选工具**」是这套模型的使用心法：连续追加 → arena/`vector`；频繁增删 → pool；
> 随机 key→value → 哈希表（`stl/map.extc` 的开放寻址 + 墓碑）。三者都在同一套寿命规则下。

## 1. 为什么需要两套（动机是量出来的）

作者原话（`docs/topics/POOLS.md` §1）：

> region 是一种基于 ECS/Handle 的内存管理模式，旨在高效利用内存、保证内存安全和 SIMD 优化，
> 同时能够允许用户手动介入 GC，是为了弥补 arena 在管理**删增动态度很大**的数据结构时的劣势。

三个具体问题：① 用户无法手动回收容器里的垃圾（erase 掉的槽、旧代缓冲留在 arena 里）；
② 无法复用（反复 add/erase 线性涨）；③ 链式/树式结构的指针跳转让 SIMD 难以优化。

**峰值 RSS 实测**（`/usr/bin/time -f "%M"`，`POOLS.md` §1）：

| 形状 | 峰值 RSS | 结论 |
|---|---|---|
| 翻倍长到 1e5，每轮在**会退出的块**里做（12 轮）| 2,640 KB | 平（块退出即还）|
| 一个数组从 1 翻倍长到 1e6（4 MB 活跃）| 9,900 KB | 约 2.4×：历代旧副本全留着 |
| 每轮新建/重建，分配点落在**长命层**（12 轮）| 14,184 KB | 随轮数**线性涨** |
| 一次要够 | 5,676 KB | 只差进程基线 |

⇒ 服务型程序（跨请求状态、缓存、会话表）**必然**撞在"长命层里分配不回收"这条上 ——
这就是 pool 存在的理由。

**反向也量过**（`POOLS.md` §2.2，别再走）：把 arena 全改成 pool，同一形状（2e7 个 16 字节小对象）
**arena 0.01 s / 1,452 KB** vs **pool 0.52 s / 939 MB** ⇒ 每次分配 **0.5 ns 对 26 ns**（约 50 倍）、
占用 2.9 倍（块头 + malloc 头 + 对齐），而且语言层没有 `free`，用户调不了那个买来的能力。

## 2. Arena：寿命的骨架

### 2.1 形状与实现事实（`CONCURRENCY.md` §2.1，2026-09-23 核过）

| 事实 | 出处 |
|---|---|
| 块 **4096 字节起**：`cap = n > 4096 ? n : 4096` | `src/codegen.c:2687` |
| arena 目前**没有块大小字段**：`struct extc_arena { extc_ablock *top; }` | `src/codegen.c:2662` |
| 一个函数调用里 arena **入口建一次**、所有分配点共用；`__extc_a[]` 的**下标 = 词法层号** | `src/codegen.c` |

生成物长这样：

```c
static int32_t fill(int64_t n) {
    extc_arena __extc_a[3] = {0};          /* ← 入口建一次 */
    ...
    extc_arena_alloc(&__extc_a[1], ...)    /* ← 所有 new / alloc 都用它 */
    ...
    extc_arena_release(&__extc_a[2]);      /* ← 块退出时释放那一格 */
}
```

⇒ 分配点的**层号是编译期算出来的**（词法作用域），运行期没有查找、没有链表遍历。

### 2.2 回收语义（别把它想成"直接 reset 指针"）

`extc_arena_release` 走整条链、**保留一块**（`cap ≤ EXTC_ARENA_SPARE_MAX`，1 MB）当 spare，其余 `free`。
这条 spare 规则本身是量出来的：**32e6 次 malloc+free 让 churn 慢约 50 倍**（注释记着）。

字面意义的 mark/restore（进入时存 `{top, used}`、退出恢复）**要配预算才成立**：
`tests/arena` 把虚拟内存卡在 **150 MB** 跑「**300 轮 × 1 MB**」并要求不许涨 —— 无条件保留会直接撞红。

### 2.3 区域（region）≠ 一块内存：这是 #31 的根源

`ARENA-FORMAL.md` §1.4 的关键一句：

> 容器 `v` 的**槽位**在区域 `R_v` 里，但它**里面的指针**指向区域 `ρ` 的对象。
> **拷贝 `v`**（返回、赋值、塞进别的 struct）只搬**槽位**（指针值），**不搬 `ρ` 的对象**
> ⇒ 只要 `v` 或它的副本活到某个时刻，`ρ` 就必须**也**活着。

⇒ 于是 `mk()` 里分配的 buffer、被 `return` 出去之后就是**悬垂**：槽位活着，buffer 的区域死了。

### 2.4 zone 是**旁链**，不是栈里的一格（作者原话）

> 实现上不嵌在 arena 的栈里，而是一条独立的旁链 —— 这样子你才能够**枚举 zone** 啊，
> 否则你块一回退不就全爆了。

三层结构（`POOLS.md` §2）：

```
zone（一个地方的索引头，独立旁链）
  └── pool 树（容器套容器：逻辑父子）
        └── pool（单个容器的那一份：数据 + 簿记）
```

### 2.5 home zone：跨调用的"这只值该落在谁家"

分配点不总在本函数里：如果值最终要被**外层**的容器接住，它就必须分配在**外层**的 zone。
编译器为此算一个 `needsHome` 的**传递闭包**（`ARENA-FORMAL.md:678`）。

**这里出过一个真洞**（`H2`，由协程原型挖出）：闭包**只做了一层** ⇒
`main → wrap → put → newString`（4 层）时，字符串被分到**中间层** `wrap` 的 place 里，
`wrap` 一返回就被复用 ⇒ `keys[0]` 从 `"k"` **静默变成 `"a"`**（不 trap、ASan 也不报，因为块是逻辑复用）。
**已修**（`f3b0c13`：调用点的 zone 层级改在 `makesPool` 闭包**之后**结算）；反例改名保留为
`tests/arena-soundness/H2_home_zone_two_hops.extc`。

## 3. 安全：靠**规则**，不是靠运行期兜底

### 3.1 要证的东西只有一条

`ARENA-FORMAL.md` §1.3：配置 `⟨σ, λ⟩`，`σ : Addr ⇀ Value`（`reg(a)` 是地址的属性），
`λ : Reg → {live, dead}`；安全 = **一条 trace 里每次 `deref` 都命中活区域**；程序 sound ⟺ 所有 trace 安全。
所有分配点的区域 ρ 是**唯一要推导的东西** —— 由编译器静态算出来，运行期只比较层号。

### 3.2 检查器实际用的抽象：`refDepth` + 两条判据

`ARENA-SOUNDNESS.md` §1.2/§1.3 给出检查器真正在算的数（`Sym.refDepth` 等），
§4 列出三类"**记小了**"的失效形态（整值读取被强更新压小 · 只看一个数不看字段表 ·
把深度当成"表达式自己多深"而不是"它指着的东西多深"），§5 给出 **7 个反例**。

**两类流**的区分是这套分析的核心（`ARENA-FORMAL.md` §2.1）：
**地址流**（指针值被搬去哪）与**内容流**（指针指向的对象被搬去哪）；
把两者**合并**成一个数，就必然产生 #31，而补丁（甲′）只能把后果记下来。

### 3.3 已经修掉/正在跟踪的洞（诚实清单）

## 4. Pool / Region：可回收、可复用、SIMD 友好

### 4.1 身份：两层失效，各管一段（作者口径，`POOLS.md` §7）

作者原始说法：

> 我在一个 while 里面创建了一堆 pool，然后我给 zone 一个 color，每个元素也记一个 color，
> 每次检查 pool 里元素的 color 和 zone 的 color 是否匹配，如果不匹配说明全部都死了，
> 那你**全刷**，很爽。zone 本身是固定的并不会被移动，也不需要扩容。

落地时被钉成**两层**（一层不够，两种漏法都实测过）：

* **池级**：`pool.epoch` 对 `zones[pool.zone].color` —— 管「**整个 place 死了**」，
  代价是**一次固定加一次比较**，零走查、零重写；
* **槽级**：`handle.gen` 对 `slot.gen` —— 管 **epoch 内部**的槽位复用。
  只比色会漏（同一个 epoch 内色没变，旧句柄会"重新对上" ⇒ 静默读到新元素）；只比 gen 也会漏
  （跨 epoch）。⇒ 两层各管一段；句柄本身只要 `(slot, gen)`。

### 4.2 什么能进池、什么不能（三条从一句原话推出来）

> 你不能把块也生成 Handle 放到 Pool 里面，否则块反复 Bump 会导致 Pool 反复扩容，
> 那块的 Bump O(1) 的优势又没了。

1. **进池的必须是「等大 + 需要身份/复用」的元素**（值、节点、槽）；
2. **块不进池**（变长、无身份、只需 LIFO ⇒ 走链）；
3. **两层只共享寿命所有者，不共享数据结构**。

另有一条**结构上根本接不通**的事实：块分配器活在生成器发的 C 运行期里（`extc_ablock` + `malloc/free`
+ `char data[1]`），池库活在 extC 层 —— 后者拿不到 `void*`、没有指针转换、也不能把裸块当值。

### 4.3 回收与资源利用（实测）

| 判据 | 数字 | 含义 |
|---|---|---|
| `pool` churn | 1e5 → **1e6** 轮：1,660 KB → **1,724 KB** | 平的（元素等大 ⇒ free slot 复用率极高、几乎无碎片）|
| 不留槽位的对照（canary）| 9,916 → **67,324 KB** | 判据有牙：不回收就会涨 |
| pool 期 1 注册表 churn | 20 万次后 `live=0 cap=64 gen=0`（`tests/pool/run.sh` 的 `rt_churn`）| **容量停在高水位**，内存平的机械判据 |
| 哈希表墓碑 churn | 1e5 → 1e6：**1,660 → 1,660 KB** | 墓碑复用有效 |
| `map` 墓碑 canary | 8,380 → 55,036 KB | 同上，判据有牙 |

**"容量停在高水位"不是缺陷**：池有**独立板块**（不是借 arena 的切片），所以 `shrink` 能做**真收缩**、
`release` 能**立刻还内存**；arena 里的 `new T[n]` 只能等地方结束。
作者口径：**「pool 的内存是独立的一个板块，只是生命周期给 arena 一起管理。」**

## 5. 性能：两套机制各自的账

| | arena | pool |
|---|---|---|
| 单次分配 | **~0.5 ns**（bump）| **~26 ns**（含身份/世代/簿记）|
| 释放 | 块退出整块回收（O(1) 摊销）| `remove`/`clear`/`release`（可复用、可真收缩）|
| 内存放大 | 块内 padding + spare 一块（≤1 MB）| 块头 + malloc 头 + 对齐 ⇒ 实测 2.9×（小对象）|
| 身份 | 无 | **稳定句柄**，旧句柄必失效（gen）|
| 遍历 | 连续 ⇒ SIMD 友好 | 槽位连续（dense 前段）+ 索引层 ⇒ 也可 SIMD |

**选型口诀**（`POOLS.md` §10.2 那张表的结论）：连续追加走 arena / `vector`；
频繁增删走 pool；随机 key→value 走哈希表；跨请求的长命状态走**显式**的 pool（而非长命层里的裸 arena 分配）。

## 6. 协程怎么长在这上面

### 6.1 前提：**无栈**（`CONCURRENCY.md` §1）

> 这一节不成立则本文全部作废。

**帧是一个普通的 extC 值**：`yield` = 存 pc 后 `return`，`resume` 从 pc 继续。
于是「协程的状态」不需要单独的栈、不需要复制栈、也不引入第二套生命周期概念。

### 6.2 三件事天生对齐（`CONCURRENCY.md` §2.1）

* arena 的分配点是**词法层**、一个调用入口建一次；
* ⇒ **协程帧就是"某一层的一次分配"** —— 它跟具体某个块同寿，与 arena **天生对齐**；
* 帧的寿命按「**往上追溯**」定（作者 2026-09-23 的答案），调度器不用猜。

### 6.3 唯一要守的规则（否则静默错！）

> **`resume` 必须把「帧自己那只 arena」当 home 传下去，而不是"恢复者的当前块"。**

不然：调度器在一个**每轮退出**的块里 `resume`，协程内部 `new` 出来的状态就落在那个块里
⇒ **下一轮悬垂**。由此得到一条要写进手册的**使用规矩**：

> **协程里 `new` 的东西活到协程结束，不是活到这次 resume。**
> 想要"这一次用完就扔"的临时数据，就在**调度器那一侧**分配。

### 6.4 驱动方式：复用已有协议，零额外机制

```extc
fn counter(n: i64) -> coroutine<i64> {      /* 返回类型写 coroutine<T> ⇒ 体内允许 yield */
    var i: i64 = 0                           /* 普通局部：跨挂起点活着 ⇒ 按值进帧 */
    while i < n {
        yield i                              /* `yield e` 是**语句**（v1 不是表达式） */
        i = i + 1
    }
}

let c: coroutine<i64> = counter(i64(3))      /* spawn = **就是调用**：帧生在这个调用点 */
for x in c { … }                             /* ① 复用迭代器协议（推荐） */
while c.next() { … c.value() … }             /* ② 显式：与用户迭代器同一套名字 */
```

**不做 `spawn`/`resume` 关键字**（少两个概念）；组合用 `for x in inner { yield x }`（= `yield from`）。
⇒ 协程**没有为内存模型新增任何机制**，它只是"某一层的一次分配 + 一个普通的迭代器协议"。

### 6.5 实测与欠账

* `tests/coro` **27/27**（含调度器、`epoll`、echo server、帧布局、协程池、句柄、状态机、迭代器协议）；
* 欠账（都写进 `PLAN.md`/`CONCURRENCY.md`，此处不美化）：**`coroutine<A,B>`（请求类型 / send-in）
  还没有** —— 落地的是 `coroutine<T>` 单向生成器（实测：`` `coroutine` expects 1 type argument(s), got 2 ``）；
  `parallel` + channel 未做（文档口径"**并行是最后一件事，不是第一件**"）；`blkSize` 需要能显式指定
  （§3.1）；`POOLS.md` 期 2/3（池板块化 + 整个 STL 上池）未做。

## 7. dyn Trait 怎么配合

### 7.1 值形状：dyn 是**值**，不是引用（`DYN.md` §2）

```extc
trait Tag { fn tag(self: ref Self) -> i64 }

struct box { v: i64 }
impl Tag for box { fn tag(self: ref box) -> i64 { return self.v } }

dyn Tag(b).tag()          /* 阶段 1：构造 + 立即调用（不碰池） */
```

* **`dyn Tag` 是一个值类型**，载荷是**一份拷贝**（放进 dyn 池的槽里）
  ⇒ **不存在"dyn 值指向栈上临时量"的寿命问题**，与语言既有的"引用不能活过它的帧"完全同构；
* 构造写成 **`dyn Tag(x)`**（与既有的 `T(x)` 转换同形）；
* **object safety**：泛型方法、返回 `Self` 的方法、无 `self` 的关联函数**不能进表**，
  且在 `dyn Tag(...)` 的**使用点**报错（而不是等派发时炸）。

### 7.2 五条必须做对的事（`DYN.md` §4）

| # | 事 | 今天的机制 |
|---|---|---|
| 1 | dyn 用的池**只追加** | `extc_pool_new_table` + `extc_pool_kind`；`give`/`resize`/`_raw` 三处守卫 |
| 2 | 删除 = **墓碑**（对象在、标记已删）| 槽表里 `0` 表示空闲 ⇒ 天然墓碑 |
| 3 | 派发前**校验 `gen`** | **已落地**：`extc_dyn_slot` 的五段校验链 |
| 4 | 整池作废只需一次比较 | `extc_pool_reset` 的 `generation++` |
| 5 | 深度上界/效应声明只写在**被动态跨越的边界**上 | 静态部分照旧，动态部分由此收敛 |

⇒ 也就是说：**`dyn` 的安全性建立在 pool 的生成（gen/epoch）之上**，而不是另起一套运行期。
`tests/dyn/`（含 `dyn_promoted_two_hops.extc`：**跨两跳返回的 dyn 值同样被提升**）与
`tests/arena-promoted/` 是常设判据；`DYN.md` §10 记着"卸载/重载**不做但留门**"及其不变量
（**表指针只在槽里**）。
