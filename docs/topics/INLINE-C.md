# 内联 C（`inline C!`）：归档的设想

> **状态：设想，未定案。**
> 作者 2026-09-26：「不急，这个我还没想清楚所以先不做，先归档吧。」
> 因此本文**不是计划、不是承诺**，只是把已经想到的部分与**尚未想清的部分**放在一处，
> 以免它散在对话里被误当成已定案的功能。实现与排期都不在本文范围内。

## 一句话

允许在 extC 里直接写一段 C，**由写它的人签字**（`!`），从而使"编译器看不见的代码"这条路
从"只能声明外部函数"扩展到"可以就地写"。

## 为什么它天然属于签字族

语言里"编译器看不见的东西"已有三条出口，各自的义务写在 `SOUNDNESS.md` 的 O7：

| 出口 | 签字的是什么 |
|---|---|
| `!` | "这里确实有值/非空" |
| `extern!` + `effects` | "这个外部函数对地址与继续执行的影响如此" |
| `subView` | "这个零拷贝视图在我使用期间不会失效" |
| **`inline C!`** | "**这段 C 的后果见下面的申报**" |

四者是同一族：**把不可证的东西交回给写它的人**，而语言负责把这些声明显式化、可检索、可评审。

## 两层，不要混在一起设计

| 层 | 回答的问题 | 归属 |
|---|---|---|
| **签字** | 谁负责 | 本文 |
| **沙箱** | 就算写错了，坏到什么程度 | [`BOOTSTRAP.md` §4.4](BOOTSTRAP.md)（已有分析，不在此重复） |

`BOOTSTRAP.md` §4.4 的结论是：**不加沙箱**时，块里的 UB 会伤到 extC 的不变量（语言承诺作废）；
**加沙箱**后，它只伤到自己，垃圾落回 `result<T,E>` 的值域（可检查、可丢弃、可重试）。
两层的分工因此是：**签字保证诚实，沙箱保证后果可控**。

## 签字要申报的四类后果

编译器对块内代码一无所知，因此下列四件事必须由作者申报，其中两件可沿用 `extern!` 的既有词汇：

| # | 后果 | 词汇 |
|---|---|---|
| 1 | 收到的**引用**是否会被存到活得更久的地方 | `effects Addr=` |
| 2 | 是否可能**不返回**（长跳转、`exit`） | `effects Cont=` |
| 3 | 是否**分配**、分配之物归谁（影响 home 机制与物化位置） | 需新词汇 |
| 4 | 是否会让**池里的东西失效**（`give` / `resize` / 换代）—— 即跨过此块之后，手里的池句柄是否仍可信 | **新义务** |

第 4 条是它与池 / dyn 那条线的交汇点：若沙箱禁止块触碰 extC 管理的存储，则第 4 条**按构造恒为否**，
签字退化为"只申报进出数据的形状"，设计复杂度大幅下降。

## 待定的问题（作者尚未想清的部分）

1. **拼写与位置**：`inline C! { … }` 只在语句位，还是也允许出现在表达式位（需要类型信息）；
2. **块内如何称呼 extC 的变量**：文档化的 C 名映射 / 显式捕获列 / 结构化占位符；
3. **能否触碰编译器的运行期全局**（`extc_pools` 一类）：默认应当不能，否则 TCB 一次性扩到整个运行期；
4. **`#include` 的处理**：块内是否允许（涉及生成物头部的可预测性）；
5. **`#line` 的保持**：块内编译错误必须指回 extC 源文件的对应行；
6. **沙箱的档位与首版形态**：见 `BOOTSTRAP.md` §4.4 的三档比较；
7. **首版是否只做签字**：不做沙箱时爆炸半径是**整个程序**，这一点必须在文档里写明而不是含糊。

## 与既有工作线的关系

- **与 dyn 第一期无依赖**：`trait` 声明 + 静态方法表那条线不等待本文任何结论；
- **与"运行期文本"的关系**：长期看，"运行期自身用 prelude 的 extC + `inline C!` 块写"是一条可能的路，
  可逐步摆脱"一大段字符串"的形态；这是远期方向，不构成近期的理由（近期仍以独立重构处理）。
- **不在本文范围**：C 兼容模式的完整设计（那是 §4.4 的主题）、C 生态库的引入策略。
