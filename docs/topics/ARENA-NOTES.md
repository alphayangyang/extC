## 1 没做成、但方向已经清楚的两件事

### 1.1 路径敏感的 arena 选择（「下沉」）

**问题**：同一个 `new` 站点，走不同分支时"这一次真正需要活到哪一层"可能不同；
现在按**最坏那条路径**定案 ⇒ 别的路径陪着多占内存。

**实测靶子**：200 万轮下，只读不外存 **1.6 MB** vs 多一条外存分支 **33.2 MB**。

**落地形态**（原型里跑通过）：检查期维护一条**分支条件栈**，存储时把"这次存储的目的地层"
与"夹在分配点与存储点之间的那个条件"记到分配点上；codegen 吐
`(*(cond ? &__extc_a[shallow] : &__extc_a[deep]))` ⇒ 走别的分支时对象住得更深、回收更早 ✓

**三条必须的护栏**（每条都是被实测逼出来的）：
1. 备用层必须落在合法区间里，越界**一律退回单层**（越界写比不优化危险得多）；
2. 条件必须**可重复求值**（三元在 C 里会求值两次）；
3. 条件所在的作用域必须**严格比分配点更外** —— 同层"声明在使用之后"也查得到，
   否则生成的 C 会 `undeclared` ✗。

**为什么没落地**：机制通、判据错了 5 次 ⇒ 停手。方向铁律：新机制**只许把层放深，绝不许放浅**
（放浅需要整个新的证明）✓

### 1.2 两层尝试：把"层号"从"边查边拍板"改成"按照约束解算"

**已经落地的部分**（这一版是好的）：分配站点的层号由**一张事实表**重放到不动点而定，
而不是"见到 `new` 就先定一个层"。实测：长运行形状 **98 MB → 50.8 MB**（= 容器自己内联写
那条目标线，一分不差）✓

**还没做成的部分**：把"容器里某一格装的东西活到哪一层"也纳入解算 ——
聚合类型的字段表**参与了记数**，但**没有参与传播**：
`var h: box = { p: null, q: null }` 之后 `h.q = x` 的来路只在字段表里，
而顺着 `out = h` 想给 `x` 降层号时，沿 `Sym.origin`（只记声明时的初始化式）**追不到它** ✗

**教训（值得记住的形状）**：`promoteInto` 有**两个身份** ——
"提升"和"记事实"。它的每一处**提前返回**都只对前者成立 ⇒
凡是"往外存必须经过的地方"都不许提前返回，要么记完再退，要么退之前先递归 ✓

## 1.3 字段表的深度是"检查期冻结"的 —— 最后一个已知缺口（2026-09-24）

**症状**：`tests/arena-promoted/C3_if_join_wholevalue.extc`（以及 `C2` 的兄弟/cousin 共 4 条）
编译通过，但返回的结构体里那个指针指向**块层 arena** ⇒ 函数一返回就悬垂（ASan 实锤）。

**逐环量出来的链路**（gdb，不是推理）：

```
var x = alloc<i32>(1)   => 站点 lexicalLevel=2，而 refDepth=0
                           （EX_GENCALL 分支在函数有家时写 ARENA_HOME，映射回深度 0）
var g: box = { q: x }   => exprRefDepth(x) 读 sy->refDepth=0
                           => 字段表记 g.q = 0（真相是 2）
out = h                 => 提升走路看到 g.q 的深度 0 <= 目的地 1 ⇒ **跳过**
return out              => 站点没被提升 ⇒ 留在块层 ⇒ 悬垂
```

**根因（一句话）**：**字段表的深度在检查期就冻结了，而它引用的是"解算之后才定案"的站点。**
所以"某个值现在有多深"这件事，在字段这一侧永远慢一拍。

**两条走过的错路（都实测、都回退，别重走）**：

1. 在 `EX_NEW` 分支加对齐 —— **加错了分支**：`alloc` 走 `EX_GENCALL`（约第 1040 行）。
   症状：转正库 18 → 15，而目标字段仍是 0（那行根本没被执行）。
   ⚠️ 教训：**先确认改的那一行真的会执行** —— gdb 断点没打印就是没执行，别继续往下推。
2. 改到正确的 `EX_GENCALL` 分支 —— 字段表**修对了**（`g.q` 从 0 变 2），但转正库 18 → **15**：
   - C3 仍失败，只是换了地方：`out = h` 报 "borrowed from depth 2, but … up to 1"
     ⇒ **提升走路本该把 `out`/`h` 的深度降下来，而它在报错之后才跑**（顺序问题）；
   - 三条本来绿的变红（`A_field_root_lowered` · `alloc_return_local` · `arena_root_depth_lowered`）
     ⇒ "抬高站点深度"是个**全局钝器**：它同时抬高了**不需要**那么深的站点。

**⇒ 下一步的两个候选（都要求先想清"谁在什么时候读这个数"，不许再加钝器）**：

- **A（惰性）**：字段项存"来源表达式"，深度在**首次读取时**按站点的最终层号算；
- **B（顺序）**：让**提升走路在逃逸判据之前**拿到正确的字段深度（或让逃逸判据用"走路之后"的数）。

### 1.4 字段表已经修好了，剩下的坑在别处（2026-09-24 下半场）

**先说这一轮做成的两件事**（都已提交）：

1. **提升走路不再把"间接"当成"值的来路"**。`*e` 是 `e` 指向的东西、`&e` 是 `e` 的地址、
   `e[a:b]` 是视图 —— 三者都**不是 `e` 存的那个值**，所以它们**终止**走路而不是继续。
   实测副作用：`examples/alloc-in-block` 里 `return total` 曾顺着 `total = *q` 走进 `q`，
   再走进嵌套块里的 `alloc`，把那个站点判成"必须活过本帧"；函数没有家 arena 可给，
   生成的 C 里就出现了 `__extc_home`，**编不过** ✗
2. **"某个绑定现在装的是什么"不再靠表达式缓存**。缓存每人只有一个答案，
   而 `if` 汇合有两个 —— 数据流本来就算好了（`h` 与 `out` 的 `.q` 都是 **2**，实测），
   让走路去读那个数，而不是让缓存记住**一支**。

**字段表现在是对的**：数据流的不动点算完之后回写，
`g.q` / `h.q` / `out.q` 都已经是 **2**（`EXTC_DBG_DFA=1` 与 gdb 双证）✓
两个 `CX_if_join_*` 用例**不是**卡在字段表上。

**卡在哪（这一轮新的、确定的结论）**：`minAt` 从头到尾**没有被降到 0**，
而"必须活过本帧"这件事**只有 `0` 能表达**：

- `D`（深度）是**上界**，把它调小是**收紧**而不是放宽 ——
  所以"把目的地的最终深度当成要传播的需求"这条路**在语言层面就不成立**：
  C3 要的是"活过本帧"，而目的地 `out` 的最终深度是 **2**（"活到第 2 层"），
  两者不是同一个陈述，**深度域里没有那个数**。
- 唯一表达了那个需求的地方是**发布记录**：`return out` 记的是 `at=0`。
  要把它接到 `x` 上，必须沿**记录之间的边**传播
  （`at=0` 的发布 → 它的目的地绑定 `out` → 所有写进 `out` 的发布 → 再往下的值），
  而这条边**不在**"值→来路"的走路里，所以怎么走都走不到。

**⇒ 下一步的形状（三条都要求"谁在什么时候读这个数"先说清）**：

- **A（给"必须活过本帧"一个名字）**：在层号域里引入显式的
  "此需求比本帧更长"，不再借道深度域 —— 传播就走**记录之间的边**，不套现成的深度数；
- **B（目的地需求表）**：`StoreSite` 记下目的地绑定；
  先算每个绑定的**最小层号**（写它的所有发布与返回取 min），再沿值链下推；
- **C（值绑定的来路）**：让普通赋值也更新 `Sym.origin`。
  已实测**不够**：`out` 的来路会变成 `h` 的**汇合节点**，
  而 `h` 的两支里有一支是空盒子 ⇒ 走到空盒子就断 ✔（这一条可以排除）

**排除掉的路（别重走）**：把"目的地最终深度"当作需求传播（上面已证伪）；
把检查期的 `at` 与目的地深度取 `min`（两个都是 2，什么也没发生）。

**现成的判据（第一步的产出）**：`EXTC_DBG_RHO=1` 会把"带缓存版"与"只依赖词法层号+来路"的
参照实现对拍，报出每一处不一致并标方向 —— 全语料当前 **2,396 处 UNDER**（缓存偏低 = 漏的方向），
其中 90% 集中在 prelude 的 4 行（`withCap` 的 `new`、`grow` 的 `new` 与重复绑定）。
任何修法都应当让这个数**塌下来**，而不是只让 C3 一条转绿 ✓

## 2 仍然有效的判据（别删，删了就会重犯）

1. **层号与深度必须同数**：`refDepth` 与 `arenaLevel` 是同一个事实的两种说法
   （`ARENA_HOME ⇒ 0`）。只在某个条件分支里更新其中一个，另一个就会漂 ——
   这一条已经做成自检：`EXTC_SELFCHECK=1 ./build/extc <file>` ✓
2. **"两把尺子一起看"**：改这一层时，每次都要同时跑 `tests/run.sh`（期望 255/0）
   **和** `tests/arena-promoted/run.sh`（期望 22/22 + ASan 干净）。
   出现过"转正库 18→20 而主套件 255→253"的**假进步** ✗
3. **哨兵不许动**：`tests/errors/generic_return_local.extc` 必须**仍然被拒**，
   反例库 `H1_strongupdate_missed` 必须**仍然 REJECT** ——
   它们是"什么都放宽"的守卫，历史上都抓到过"绿的但是假的" ✓
4. **只改注释的改动也要有判据**：`tools/comment_neutral.py`（剥掉注释逐字节比代码）✓

## 3 环境与流程坑（当时浪费了好几轮，记下来）

- **宿主路径**：WSL 的 UNC 路径（`\\wsl.localhost\…`）+ 目录会让工具把 `.git` 当文件
  realpath ⇒ `EISDIR` ⇒ 会话重置。绕法：用一个不含 `.git` 的镜像目录，或修工具 ✓
- **`/tmp` 是 tmpfs**：会话一崩就清空 ⇒ 试错用的程序放**仓库内**（`build/tmp/`）✓
- **`make clean` 会 `rm -rf build/`** ⇒ 放在 `build/tmp/` 下的 git worktree 会被一起删掉 ⚠️
- **别用大段 heredoc 重写整个文件**：这个仓库被批量替换弄坏过 4 次 ✗
  改源码用小步替换（`edit`，或 Python 里 `assert old in s` 之后替换）✓
- **`.o` 逐字节相同不能当"只改了注释"的判据**：注释行数一变，调试行号表就变 ⇒
  要看**剥掉注释之后的代码文本**（`tools/comment_neutral.py`）✓
- **gdb 优先于 print**：`build/extc` 自带 `-g`，断点要按符号名/行号**过滤**（否则 prelude
  的几百次调用淹掉输出）、`%d` 要配 `(int)` 强转（否则 gdb **静默失效**）、
  断点行要选**变量已赋值的那一行**；`watch -l e->refDepth` 能一次答出"谁改的" ✓
- **一次只改一处、改完立刻跑两把尺子**：把"改源 + make + 跑测试"塞进同一次调用时，
  崩了分不清是哪一步 ✗
