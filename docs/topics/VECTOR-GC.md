# 容器的半自动回收（设想）

> **状态：设想，未定案。** 2026-10-04 提出。**实现 `BOUNDED-TABLE.md` 之前要先解决本文** ——
> 容器进了热路径以后，"什么时候能把这块内存还回去"就成了必须先回答的问题。
> 本文不是计划、不是承诺。

## 一句话

`vector` 现在只有 `clear`（保留容量）/ `shrink`（显式缩）/ `release`（交还）；缺的是
**"什么时候可以缩"这件事本身**。要把它从"调用方的纪律"变成"语言能看见的事实"。

## 已有的判断

* **arena/zone 已经回答了"什么时候一定可以回收"**：作用域结束、或提权到更外层的 zone。
  容器的问题在于**它的内存在表达式的生命周期之外**（`vector` 的底层缓冲不属于任何一帧），
  所以逃逸/深度那套规则看不见它。
* 因此这不是"加个 GC"，而是**给容器一个可证明的回收点**：最自然的候选是
  **"最后一次被可达引用指向的地方"**（`@noCopy`/`owned` 已经有一半的语言支撑）。
* **别做追踪式 GC**：这门语言的全部卖点是"不拒绝、可证明、`grep` 得到"；一个后台收集器会把
  这些一次性抹掉（也会把 2C2G 的内存曲线变成不可预测）。

## 尚未想清

1. **回收点的最小语言面**是什么？候选：`owned` 返回值 + 显式 `drop`（已有？）；
   或者把 `shrink` 挂到"作用域结束"上（`defer` 一类）；或者按引用计数（那要把 `@noCopy` 语义改掉）。
2. **抖动**：`shrink` 之后马上又 push ⇒ malloc/munmap 反复。要不要滞后/水位线？
3. **跨协程**：任务挂起时它持有的容器属于哪个 zone？恢复后还在吗？（与 `BOUNDED-TABLE.md` 第 4 条同一个问题。）
4. **判据怎么写**：`tests/stl` 的 `churn` 已经会量 RSS ⇒ "跑完一批后回落到基线"是可判据的；
   但"什么时候**必须**回落"（而不是"可以回落"）需要语言给出承诺，否则判据只能测实现。
