# 融合（视图管网的编译期去物化）

这份文档说明"数组/张量当一等公民之后，值不值得引入计算图"这个问题的答案：**不引入运行时图，
把用户写的顺序程序当成图，让编译器去掉中间物化**。它属于"有什么待做"那一类，和
[`PARALLEL.md`](PARALLEL.md)、[`TODO.md`](TODO.md) 同源：清单在 `TODO.md`，这里是机制。

## 模型总览

- **没有运行时计算图，没有惰性求值**。用户写的顺序程序就是图：视图是节点，逐元素循环是边。
- 编译期只做一件事：把"写进临时视图、下一段再整块读"的形状**合并/去掉**，让一次遍历干完。
- 与并发的关系：`par` 仍然是唯一的并行动词；融合是**单线程语义保持**的改写，发生在并行降糖
  之前对普通循环生效（v1 不跨 `par` 融合，也不进 `par` 体里融合）。
- 与张量的关系：`stl/tensor` 的 `tensor2<T>` 只是"形状 + 步长"，对融合没有特殊待遇 —— 融合看到
  的仍然是仿射下标表达式，多维视图只是它的一个写法。

为什么不做图：图的真正价值是 autodiff、惰性放置、多设备执行；代价是执行时机、错误时机、内存
归属全都变得不可见 —— 这与语言一直守着的三条（无隐藏运行时、结构化并发、可变数据有唯一主人）
直接冲突。真的需要图的那天，它可以作为**库里的显式值**存在，而不是编译语义。

## 为什么在这里划算（证据）

`bench/stream`（n=4M，三块数组 96 MiB，`-O2`，extC 发射的 C）量到的同一条管线：

| 形状 | 遍数 | best ms | 相对物化 |
|---|---|---|---|
| 物化中间数组 | 5 | 77.4 | 1.00× |
| 融合成一个循环 | 3 | 49.4 | 0.64× |
| 不落数组、边算边归约 | 1 | 27.6 | **0.36×** |

同一份手写 C 上，指令级调整里只有非临时写赢（0.79×），`restrict`/对齐/`ivdep`/软件预取都不赢。
也就是说：**在这里能拿的收益几乎全在"少一遍内存流量"上**，而这正是融合能自动化的部分。
越出 L3（36 MiB）收益越大：L2 档 0.75×/0.61×，出 L3 后 0.64×/0.36×。

## 三个形状（v1 支持）

设 `tmp` 是块内临时视图，A 是"写 `tmp`"的循环、B 是"读 `tmp`"的循环。

**S1 元素链**：A、B 迭代空间相同，A 的体是 `tmp[i] = <纯表达式>`，B 里 `tmp[i]` 只以同一个下标
表达式出现 ⇒ 合并成一个循环，`tmp` 消失：

<!-- fragment -->
```extc
// 改前：两遍
for i in 0..n { tmp[i] = in[i] * 1.5 + 0.25 }
for i in 0..n { out[i] = tmp[i] * tmp[i] + 1.0 }

// 改后：一遍，tmp 不再存在
for i in 0..n {
    let y = in[i] * 1.5 + 0.25
    out[i] = y * y + 1.0
}
```

**S2 归约融合**：A 写 `tmp`，B 是升序归约 `for v in tmp { acc = acc + v }`（或等价的索引升序
`while`）⇒ 归约累加进 A 的循环体。**累加顺序不变**，所以浮点结果逐位相同。

**S3 组合**：S1 + S2 ⇒ 流式归约（`bench/stream` 的 `stream` 形状）。

## 资格判据（全部满足才融合，否则原样保留）

1. **相邻**：两条循环在同一个块里相邻（中间只允许编译器自己插入的东西：边界检查、作用域进入）。
2. **形状可识别**：都是脱糖后的区间循环形状 `[var i = lo, var __extc_hi = hi, while i < __extc_hi { B; i += 1 }]`
   （沿用"循环入口一次范围检查"那个 pass 的识别方式，`planForStep`）。
3. **迭代空间一致**：`lo`/`hi` 的操作数相同（结构相等即可；S1 还要求 `tmp` 的写下标与读下标逐字相同）。
4. **体是纯的**：与 `par` v1 的限制集同一套 —— 无调用、无 `new`/切片/构建值、无控制流逃逸；
   只允许算术/比较/字段/下标/局部 `var`。理由：融合会**复制**表达式，有副作用或求值次数敏感的
   东西不能复制。
5. **单赋值且死掉**：`tmp` 是同一块里的 `var`，A 是唯一写它的地方，此后只被 B（可能多条）读；
   `tmp` 与别的视图没有同名关系（v1 只按名字判别名）。
6. **有序归约**：S2 只收升序、单累加器的归约；累加位置与原循环一致。
7. **trap 语义不变**：融合前，A 的视图访问由"循环入口一次范围检查"保护；融合后必须把 A、B 需要的
   检查**按 A 再 B 的顺序**发在融合循环入口。不得出现"原来 A 先 trap、现在 B 先 trap"的元素。
8. **不放大表达式**：融合后每元素表达式节点数 ≤ 原 A + B 之和（复制一次，不许指数展开）。

## 逐位一致（硬约束）

- 融合只删"存储—再读"，不动 f64 运算顺序：`tmp[i]` 的值在 A 里算一次，融合后仍在同一位置算一次；
  S2 的累加顺序仍是 i 升序。
- 明令禁止：重排乘法、把 `a + b + c` 变成 `a + (b + c)`、把 `a*b + c` 换成 FMA。这些都会改 bit。
- 判据：同一份 extC 源，开/关融合各编一次，stdout 必须逐字节相同（用开关做红绿对拍，见下）。

## 放哪一层（实现位置）

- 现在没有 IR，codegen 直接吃 AST。采取与 `par` 降糖同一招：**checker 阶段做 AST→AST 改写**
  （新文件 `src/fuse.c`，入口 `fuseBlock(Checker*, Stmt*)`，在 `checkBlockBody` 逐条语句检查之后
  按块调一次），新节点用 plan API 手工登记（`planSetCName`；不分配 ⇒ arena 层是家层，不需要
  `planSetArenaLevel`）。
- 使用计数：`Checker` 已经记 `nameUses`；再加一条"这个局部视图的整块读都在本块内某条循环里"的
  判定即可（v1 可以更窄：只认紧邻的下一条循环）。
- **开关**：`--no-fuse`（测试专用；默认开）。测试里同源两份二进制对拍，红的半边必须先红。
- 保守退回：任何一条判据不满足就原样保留，不做部分融合、不做猜测。

## 不做的

- 运行时计算图、惰性求值、autodiff、设备放置、多设备、调度器 —— 都不做（理由见上）。
- 跨函数融合（`seq::sum(tmp)` 是调用，v1 不穿过；后续给归约原语加可识别标记再说）。
- 跨 `par` 融合、`par` 体内的进一步融合（并行结构不在这层动）。
- 通用循环变换（多面体/分块/tiling）；cache 分块是另一个话题。
- 指令级调整（非临时写、对齐提示、`restrict`）：`bench/stream` 里只有非临时写赢 0.79×，且需要
  "写完不再读"的逃逸分析；留到融合落地之后的单独一步。

## 判据

- **语义**：`tests/run.sh`、`smoke`、`nobench`、`docs` 全绿；新增 `tests/fuse/`：S1/S2/S3 正例
  （融合后与手写融合版逐字节一致、生成 C 里只剩一个循环）、反例（不满足判据的写法不融合、结果
  不变）、trap 用例（融合前后报的越界下标相同）。
- **逐位**：`bench/fortran`、`bench/par`、`bench/stream` 的 `cs` 与改前一致。
- **性能**：新增 `bench/fusion/`（未融合的 extC 写法 vs 编译器融合后 vs 手写融合）：4M 下 S3
  ≥ 2× 相对未融合，S1 ≥ 1.3×；不满足判据的对照臂不许变慢（±3%）。
- **可解释**：生成 C 的注释里标出融合了哪几条（或至少 `EXTC_FUSE_DEBUG=1` 能打印），否则下次
  没人知道数字为什么变了。
