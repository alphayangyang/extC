# 可增长数组：预留地址 + 按需 commit 取代拷贝增长（原型实测）

> 口径：本轮无运行期改动。探针 `tools/probe/reserveproto.c`、`tools/probe/reservehuge.c`；
> 机器 Intel Core Ultra 9 275HX / WSL2 / `taskset -c 6` / `cc -O2 -std=c11 -D_POSIX_C_SOURCE=200809L`。
> 形状：push 8M 个 i64（活集 64 MiB），容量按 1.1× 增长，与 `grow11` / `t13_growth_copy` 同族。

## 1. 要回答的问题

`S1` 之后容量归还已经收敛成一个水位，但**拷贝增长本身**没有动：`grow11` 到达 64 MiB 活集时要累计分配 767 MB、墙钟 287–379 ms、峰值 3.0× 活集。三条可选路线：

1. **拷贝增长**（现状）：容量几何增长，每代 memcpy；
2. **chunk 链**：增长 = 追加一段，代价是两级索引（散读 +28~33%，顺序扫丢向量化）；
3. **预留虚拟地址 + 按需 commit**：地址连续、基址不变、增长 = bump 长度。

本轮的结论是第 3 条在**每一个维度**上都不劣于现状（增长 16–48×、峰值 1.94×、顺序扫不变或更快），
而第 2 条被它支配。

## 2. 四条臂

| 臂 | 机制 | 增长动作 |
|---|---|---|
| `copy` | 每代 `mmap` + `memcpy` + `munmap` | 2 次系统调用 + 全量拷贝 |
| `arena` | 帧 arena：bump 分配 + `memcpy` | 0 次系统调用（旧代留在 arena 里） |
| `plate` | `mmap(PROT_NONE)` 预留 + `mprotect` 按 1 MiB commit | 每 MiB 一次 `mprotect` |
| `lazy` | `mmap(PROT_READ|WRITE, MAP_NORESERVE)` 预留 + bump | **0 次系统调用** |
| `lazy+huge` | `lazy` + 2 MiB 对齐 + `MADV_HUGEPAGE` | **0 次系统调用** |

## 3. 增长到 64 MiB（7 次，中位；括号为区间）

| 臂 | 增长 ms | 峰值 kB | seq ms | rand ms | 次缺页 | 增长期系统调用 |
|---|---|---|---|---|---|---|
| `copy` | **353.5**（350.1–357.9） | 131,020 | 6.68（5.87–8.20） | 18.30（17.63–18.66） | **194,424** | 159 mmap + 158 munmap |
| `arena` | 337（332–450，3 次） | **778,692** | 4.7–5.5 | 17.0–19.3 | 194,331 | 1 mmap，之后 0 |
| `plate` | 22.7（5 次） | 67,228 | 8.45 | 19.66 | 16,466 | 31 mprotect × 1.651 µs = 51 µs |
| `lazy` | **21.4**（20.8–22.1） | 67,420 | 5.95（5.18–7.58） | 17.77（17.41–18.08） | **16,465** | 1 mmap，**增长期 0** |
| `lazy+huge` | **7.26**（6.3–17.6） | 67,352 | **3.62**（2.95–5.19） | **16.64**（16.39–16.82） | **113** | 1 mmap + 1 madvise，**增长期 0** |

读法：

- **增长**：`copy` 353 ms → `lazy` 21.4 ms（16.5×）→ `lazy+huge` 7.3 ms（48×）。`arena` 的 778 MB 峰值来自「bump 出去的旧代在帧退出前不能回收」，等于 767 MB 的累计分配全部驻留。
- **峰值**：`copy` 131 MB = 旧代 + 新代同时驻留；预留路线 67.4 MB ≈ 活集 64 MiB（容量 slack 只吃虚拟地址，不吃 RSS）。
- **访存**：`lazy` 的 seq / rand 与 `copy` 同价（5.95 / 17.77 vs 6.68 / 18.30，区间重叠）；`lazy+huge` 反而更快 —— 64 MiB 用 2 MiB 页是 32 个 TLB 条目，4 KiB 页要 16,384 个（L2 TLB 装不下）。
- `plate` 与 `lazy` 的差就是 31 次 `mprotect`（每次 1.651 µs，共 51 µs）—— commit 系统调用本身可忽略，所以「零系统调用」是**去掉一道不必要机制**，不是省时间。

## 3.1 为什么快：把成本拆成缺页次数

`grow_ms` 不是玄学，它是三个可数的量：**首触的页数 × 每次缺页的成本**，加上**真正写进去的字节**。`/usr/bin/time -f %R` 的次缺页计数把第一项直接量了出来（同一台机器、`taskset -c 6`、3 次一致）：

- `copy` **194,424 次** ≈ 767 MB ÷ 4 KiB —— 每一代新分配的容量都要重新首触一次；
- `arena` 194,331 次，同样的页数，只是旧代留在 arena 里没有还（所以增长 337 ms、峰值 778 MB）；
- `lazy` **16,465 次** ≈ 64 MiB ÷ 4 KiB —— 每个字节在整个生命周期里只首触一次，增长多少次都一样；
- `lazy+huge` **113 次** ≈ 64 MiB ÷ 2 MiB 加尾部小页 —— 一次缺页换 2 MiB。

按每次缺页 ≈ 1.2 µs（WSL2 上 `mmap` 匿名页的零填 + 缺页处理）算：`lazy` 的 16,465 次 ≈ 20 ms，正好是它的增长速度；`copy` 的 194,424 次 ≈ 233 ms，是它 376 ms 里的主体。THP 之后 113 次缺页 ≈ 0.14 ms，剩下的 7.6 ms 是零填与数据写入本身（64 MiB，≈8.8 GB/s）—— 也就是**理论上限**。

一句话：预留路线并没有让「分配」变快，它只是**删掉了 12 倍的重复首触**；THP 再删掉「每 4 KiB 一次缺页」这件事。两者都是删工作，不是加机制。

## 4. 增长因子不再影响内存

| 因子 | `copy` 增长 ms / 峰值 kB | `lazy` 增长 ms / 峰值 kB |
|---|---|---|
| 1.1 | 378.9 / 131,020 | 21.7 / 67,420 |
| 1.5 | 154.6 / 126,028 | 23.3 / 67,356 |
| 2.0 | 96.0 / 67,360 | 22.6 / 67,356 |

`copy` 的时空二选一是结构性的：1.1× 省容量但拷贝 12× live，2.0× 只拷贝 1× live 但容量浪费一倍（这里峰值没涨是因为旧代在下一次 `mmap` 前已 `munmap`）。
`lazy` 三档都是 67.4 MB / ≈22 ms —— **预留之后容量 slack 只消耗虚拟地址**，增长因子退化成 VA 策略，不再是内存参数。

## 5. 256 MiB 与 THP 的稳定性

| 形状 | 臂 | 增长 ms（5 次区间） | seq ms | rand ms | AnonHugePages |
|---|---|---|---|---|---|
| 64 MiB | plain | 21.2（20.5–22.2） | 7.13（5.88–7.67） | 17.6–18.8 | 0 |
| 64 MiB | huge | 8.20（7.16–20.35，一次回退） | **5.08**（4.39–5.39） | 16.75–19.33 | 65,536 kB |
| 256 MiB | plain | 85.4（84.5–88.8） | 27.2（25.4–29.2） | 20.3–21.0 | 0 |
| 256 MiB | huge | 33.3（29.5–70.7，一次回退） | **17.6**（15.2–21.7） | 17.9–19.3 | 262,144 kB |

`MADV_HUGEPAGE` 在 `[madvise]` 模式下生效（`AnonHugePages` 等于整个范围），但也**偶发回退到 4 KiB 页**（64 MiB 那次 20.35 ms、256 MiB 那次 70.72 ms），所以合同要写成「THP 在时更快，不在时也有 16.5×」。

## 6. 小数组：不要把每个数组都变成一次 mmap

100,000 个容器，每个 512 个 i64（4 KiB），容量因子 2：

| 方式 | 墙钟 ms | 峰值 kB | 系统调用 |
|---|---|---|---|
| 每代 `mmap` + `memcpy` | 2,863.8 | 401,824 | 1,000,000 mmap + 900,000 munmap |
| arena bump + `memcpy` | 409.9 | 801,820 | 1 mmap |
| 每数组一次 `mmap`（预留 32 KiB，不增长） | 60k：112.9（30k：55.9） | 241,820（60k） | 60k mmap；VMA 27 |

每数组一次 `mmap` 约 1.9 µs，对 4 KiB 的数组是 470 ns/KB（大数组只要 128 ns/KB），所以**小数组应该留在帧 arena 里拷贝增长**：
阈值以下拷贝便宜（≤256 KiB ≈ 40 µs），越线时晋升一次、之后永不拷贝。VMA 计数 27 说明相邻匿名映射会被内核合并，但这不是可依赖的性质。

## 7. 归还

64 MiB 的 `MADV_DONTNEED`：**864.7 µs = 13.5 ns/KB**，RSS 67,168 → 1,824 kB，一次系统调用。
这与 `S1` 标定的 `c_cap = (13 + 233·p) ns/KB` 的归还项一致（13 ns/KB），所以预留路线的归还代价与现在同一个价目表，可以在 `extc_rc_returnStep` 里按 256 KiB 预算批量做（≈3.5 µs/步）。

## 8. 机制结论

```
每个 region 预留一段虚拟地址（默认 1 GiB，MAP_PRIVATE|MAP_ANONYMOUS|MAP_NORESERVE，2 MiB 对齐）
  └─ MADV_HUGEPAGE 覆盖整段（一次 madvise）
     └─ 数组 = bump 指针切出的 2 MiB 对齐区间，容量 = bump 长度，增长 = 只改长度（0 次系统调用）
        └─ 归还 = MADV_DONTNEED（13.5 ns/KB，进 return pass 批量）
```

- 地址连续、基址不变 ⇒ 已经发出的 view/slice **永远有效**，这是它相对 chunk 链的最大优势（chunk 需要 chunk-major 句柄，会把间接层传染给所有下游代码）。
- 增长不需要 `mremap`（后者改地址，实测 64→96 MiB 要 12.7–25.1 µs 且指针失效）。
- 不需要增长因子参与内存决策；容量 slack 只消耗 VA，所以 `M ≤ live + 2 MiB/数组 + 槽` 这一条比现在的 `M ≤ 2L + 16 MiB + …` 更紧。
- 首触成本是唯一的下界：128 ns/KB（THP）/ 320 ns/KB（4 KiB），即「第一次写这页」的零填 + 缺页；拷贝路线的成本是它的 12×（1.1× 因子），因为每一代都要重新首触。

## 9. 边界（未验证 / 未实现）

1. **VA 预算**：每 region 预留 1 GiB 时，10,000 个并发 region 就是 10 TiB 虚拟地址（47 位用户空间约 128 TiB），需要一层「共享大预留 + 2 MiB 对齐切分」的 arena，并把预留耗尽写成回退路径（回退到拷贝增长，或返回 Err）。
2. **THP 回退**：`[madvise]` 模式下偶发 4 KiB 页（本文第 5 节两次），合同只能承诺 4 KiB 页的数字。
3. **平台**：Windows/MinGW 没有 `madvise(MADV_HUGEPAGE)`，走 4 KiB 路径（21 ms/64 MiB），语义一致。
4. **账本**：预留区今天是「回收器看不见的外来内存」⇒ 进 pin 表（与 arena/pool 同病）。要把它接进 region 账本，需要在 `extc_rc` 侧给「预留段」一个 O(1) 的容量登记，而不是靠 pin。
5. **失败路径**：`mmap` 失败、`MADV_HUGEPAGE` 失败、预留耗尽三种情况的行为都还没有写。
6. **多线程**：`par` 每 worker 一个 region 的既有约定不变 —— 预留段要跟着 worker 走，不能共享 bump 指针。

## 10. 与语言层的关系（两个决策，不是实现细节）

1. **增长后已发出的 view 是否仍然有效**：预留路线的答案是「有效」（基址不变），chunk 路线的答案是「要么变句柄、要么失效」。选预留就等于选「view 稳定」。
2. **晋升阈值**：≤256 KiB 留在帧 arena（拷贝 ≤40 µs），越线晋升一次。这是**一个常数**，要记进「≤12 个旋钮」的预算。

## 11. 复现

```
cc -O2 -std=c11 -D_POSIX_C_SOURCE=200809L -o /tmp/rp/reserveproto tools/probe/reserveproto.c
cc -O2 -std=c11 -D_POSIX_C_SOURCE=200809L -o /tmp/rp/reservehuge tools/probe/reservehuge.c
taskset -c 6 /tmp/rp/reserveproto copy 1.1      # 350–358 ms, 131,020 kB
taskset -c 6 /tmp/rp/reserveproto lazy 1.1      # 20.8–22.1 ms, 67,420 kB
taskset -c 6 /tmp/rp/reservehuge huge 8         # 6.3–17.6 ms, 67,352 kB, seq 3.62 ms
taskset -c 6 /tmp/rp/reserveproto trim          # 864.7 us for 64 MiB
taskset -c 6 /tmp/rp/reserveproto small 100000 0   # 2,863.8 ms
taskset -c 6 /tmp/rp/reserveproto small 100000 1   # 409.9 ms, 801,820 kB
taskset -c 6 /tmp/rp/reserveproto small 60000 2    # 112.9 ms, 241,820 kB
```
