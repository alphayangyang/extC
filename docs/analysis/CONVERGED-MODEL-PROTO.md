# 收敛模型原型：chunk 记账 + 水位归还，对同一形状的 A/B 实测

本文件是一次**树外原型**的结论记录：把「一个单位（chunk）、一个所有者（region）、三个策略（T0/T1/T2）、一条契约（每 region 的 M_max 与 P_max，一步的工作量按 chunk 计数）」这套收敛模型，按仓库发射代码的形状重写一遍，与现行模型在**同一个 workload** 上对拍。原型不进门禁，也不改变任何产品代码。

口径：v31 源码（`src/back/reclaim.c` `29a6372eb0fac935f215847df35ccf41` / 4,780 行、`src/back/codegen.c` `ec12011cc5bbff7100072bb465d8f234` / 16,346 行、`build/extc` `f82ee508c6fe7233f228fc0decc00b9c`）。原型文件 `tools/probe/converged-model.c`（单文件、约 600 行）。

## 1 为什么要原型

收敛方案的每一条都能在纸上论证，但有三件事只有在同一份代码里对拍才知道：(a) 增长不再拷贝，到底换回多少墙钟；(b) 归还只看字节水位（不看 grace、不看比例闸门）会不会把容量又钉住；(c) 停顿契约在以 chunk 为步长时是否还成立。

所以原型的原则是：**同一个 workload、同一份标记代码、同一份跨区记账代码、同一个触发律、同一个步预算与同一个时钟**，只在「分配单位 / 增长方式 / 归还判据」三处不同。这样差出来的数字只归因于这三处。

## 2 两个模型

| 项 | cur（复刻现行模型） | new（收敛模型） |
| --- | --- | --- |
| 分配单位 | 512 KiB slab（16,368 个 32 B 槽，占位位图 256 词） | 64 KiB chunk（2,032 个槽，位图 32 词） |
| 大对象 | 512 KiB 对齐的独立映射 | 连续的 chunk run（每 64 KiB 一个块头） |
| 增长 | 新块 + `memcpy` 旧内容，旧块变垃圾 | 追加 chunk，元素永不搬 |
| 归还判据 | `cap − bytes ≥ 8 MiB` **且** `cap ≤ 3×bytes`（两把尺子串联） | 纯水位 `cap − bytes > 1 MiB` |
| 掩码 | 每 64 B 组一位，随「写过的组」置位 | 同左，但按 chunk 固定 8 字节 |
| sweep 步 | 一个 slab | 一个 chunk |
| mark 步 | 512 pop | 512 pop（同一段代码） |
| reclaim 步 | 4 单元，大死块先 512 KiB `madvise` 再 `munmap` | 同左 |
| 触发律 | `bytes > thr`，`thr = 3×max(liveAfter, 1 MiB)` | 同左 |
| 步计时 | `min(wall, CLOCK_THREAD_CPUTIME_ID)` | 同左 |

两个模型的对象头相同（`Block` 头 512 B，位图放块头，payload 从 `base+512` 起），所以 8 MiB 的对象在 cur 里是「512 KiB 对齐 + 一个槽」，在 new 里是「128 个连续 chunk」。

## 3 形状（一个形状覆盖五件事）

1. region A：50,000 个持久 32 B 链节点（`root[0]` 指向头）—— 长寿命活集，标记的主战场；
2. region A：每轮 10,000 个成环垃圾（`a->next = b; b->next = a`），只有 sweep 能收；
3. region B：每轮 200,000 个 churn 节点，每个持有一条**指向 A** 的跨区引用，分配后立即丢根 —— 垃圾要 sweep，且出边要 unlink；
4. 可增长数组：每轮从 1M 长到 4M 个 `i64`（8 → 32 MiB），按 1.1× 收缩增量增长，然后求和 —— cur 拷贝增长、new 追加 chunk；
5. 每轮 20 个 512 KiB 的稀疏大块（65,536 个引用槽，只写 512 个组，且跨区），分配→写→丢根 —— 位图掩码与巨块归还。

这个形状同时压到：标记（活链 + 环）、清扫（环 + churn）、跨区引用（churn + 稀疏块）、拷贝增长（数组）、容量归还（数组 + 大块）。3 轮、3 rep、`taskset -c 6`、`-O2`。

## 4 正确性对照（先证明两个模型算的是同一件事）

- 求和结果逐字相同：1 轮 `8796090925056`，3 轮 `26388272775168`；
- 跨区记账逐字相同：`rs_inc = 630,720`、`rs_dec = 690,720`（两模型的 `rs_dec` 相同 ⇒ 没有漏 unlink，也没有多减）；
- ASan 版全绿（只有退出时的进程级泄漏，属原型可接受）。

## 6 四条读法

**① 增长策略是主因，不是回收器。** cur@1.1 拷贝了 254.2 MB（≈ 累计分配量），wall 156–162 ms；new 一次不拷，wall 49.5–54.1 ms ⇒ **2.9–3.1×**。即便把 cur 的增长因子放宽到 2.0×（拷贝降到 24.0 MB，峰值也降到 66.7 MB），wall 仍是 52.7–57.6 ms，**依然慢于 new** 3–7%：拷贝增长只能在「时间」与「空间」之间二选一，收敛模型的 chunk 追加两个都不选。

**② 峰值与归还同时拿到。** new 峰值 62 MB vs cur@1.1 的 112 MB（1.8×），peak/live 1.80 vs 3.12。cur@2.0 靠浪费容量把峰值压到 66.7 MB，但峰值过后容量钉在 `rss_now = 46.9 MB`；new 回落到 **39.5 MB**（-16%）—— 因为它只有一条水位判据，没有 grace、也没有 `cap ≤ 3×bytes` 这道会与水位串联的闸门。

**③ 停顿的性质没变，变的是别处。** 三个臂的最坏步都是 ~1.4 ms 且**都落在 mark 步**，p99 在 114–146 µs，p99.9 ≈1.36–1.45 ms：两模型共用同一份 512-pop 标记代码与同一条 50k 链，所以收敛不改变停顿画像。GC 绝对时间从 14.4–14.9 ms 降到 9.4–10.2 ms（-32%，因为要扫的容量少一半），但它占的墙钟份额反而升到 18–19% —— **分母变小了**。

**④ 简化模型的边界。** 三个臂的 mark 步最大值都在 1.4 ms 量级，这是原型里标记步没有做「按活集分档 / 按段续扫」的结果，不是模型差异；产品代码里这条已经由 `EXTC_RC_MARK_STEP_POP_MAX`、`EXTC_RC_SCAN_CHUNK` 与冷档批量路径封住。读数时应看 p99 与 GC 绝对时间，不要拿原型的 max 与产品的 max 相比。

## 7 边界（不承诺的事）

- 简化：单线程、单一小对象形状（32 B）、无 size class、无 compaction、无写屏障、无分代；
- cur 的大块按 512 KiB 对齐，每个大块最多浪费 512 KiB（这一点对 cur 略不利，但只影响第 5 项的占用，量级 <1 MB）；
- new 的数组求和走 **chunk-major** 视图（布局感知的写法）；朴素 `v[i]` 降低还要再慢 25–30%（见 `tools/probe/chunkproto.c` 的 seq vs seqMaj），即便如此 new 仍领先；
- 触发律、标记、sweep 都是抄产品形状的最小实现，没有实现 T1 计数档与 idle 证明；
- 数字来自本机（WSL2、core 6、`-O2`），只做模型间对拍，不作为产品性能承诺。

## 8 复现

```
cc -O2 -std=c11 -D_POSIX_C_SOURCE=200809L -o /tmp/cm tools/probe/converged-model.c
taskset -c 6 /tmp/cm cur 3 1.1    # 现行模型，复刻 grow11 的 1.1x 拷贝增长
taskset -c 6 /tmp/cm cur 3 2.0    # 拷贝增长的最省时间档
taskset -c 6 /tmp/cm new 3        # 收敛模型（chunk 追加 + 水位归还）
```

每行输出一行汇总：wall、gc 与份额、collects、steps、步分位、peak、live、peak/live、rss_now、copied、`rs_inc/rs_dec`、三个 kind 的最大步时。

## 9 对 S1–S4 的推论

- **S1（记账收敛，只改运行期）** 能单独拿到第 ② 条：把 `slabShrink` + `pageTrim` + `grace` + `SHRINK_CAP_LIVE` 四道旋钮换成一个 chunk 水位，峰值与归还同时改善，且不碰 codegen、不碰布局。这是最便宜的一步。
- **S2（大对象 chunk run）** 是第 ① 条的前提：没有 chunk run，就没有「追加而不拷贝」；同时它可以删掉巨块载荷单独 `mmap` 的那条路径与 `wmark` 的尺寸门槛（掩码固定 8 B/chunk），unlink 的成本从 `O(字节/8)` 变成 `O(字节/chunk)`。
- **S3（池收敛）/ S4（词汇与旋钮收敛）** 本原型没有覆盖：容器 API（代数、借用冻结）与池块共存的问题需要在产品树上再做一次对照，而不是用原型判。
- 原型给出的**上限**是：这三处收敛在「会增长的大数组 + churn + 跨区引用」混合形状上值 2.9–3.1× 墙钟与 1.8× 峰值；实际产品收益会被「不增长的形状」摊薄（chase/promote 这类静态尺寸形状在本轮改动里应保持零成本）。
