# arena 手写容器 vs pool 容器：v31 后的五条对照

**问题。** 用户问「把所有容器 arena 化划算吗」（m22998）：原先引入 pool 是因为完全没有 GC 运行时；现在有了 rc（清扫档）与 criterion (d)（v30，见 [`MEMORY-MODEL-CURRENT.md`](MEMORY-MODEL-CURRENT.md) §19.14），旧代能不能交给回收器，从而把 pool 整层删掉？

**v31 修正（先读这段）。** 本文件第一版按 v30 写的，结论里有一句「(d) 修的是**无界**，不是**代价**」——**后半句对，前半句当时不成立**：v30 的 (d) 只挡住「整段不发射运行期」这一类，**巨块载荷（一个 slab 一个槽、载荷自己 mmap）在整个运行期一次都不释放**，所以同一语义下「重复增长的函数级变量」仍然无界（v30 峰值 749,980 kB = 11.7× live，且随轮数增长）。v31 把这一条补上（见 §2 的第 5 行与 §3），峰值降到 240,716 kB 且与轮数无关。教训写在这里：**「复测不优」先问「是不是没修完」**。

**口径。** v31 编译器（`build/extc` = `f82ee508c6fe7233f228fc0decc00b9c`，`src/back/reclaim.c` = `29a6372eb0fac935f215847df35ccf41` 4,780 行、`src/back/codegen.c` = `ec12011cc5bbff7100072bb465d8f234` 16,346 行）。`-O2 -std=c11 -fwrapv -D_POSIX_C_SOURCE=200809L`、`taskset -c 6`、每臂 5（wall）或 3（轮数扫描）次取最小、峰值用 `/usr/bin/time -f %M`。
对照臂：v30 = `/tmp/d6/wt/build/extc`（`f5ed0d06…`）、v29 = HEAD `853e46d0` 树内构建；v31 前的基线 = `git worktree add -f /tmp/s4/basewt HEAD` 的 `/tmp/s4/basewt/build-b/extc`（`a70616b3…`，运行需 `EXTC_STD=/tmp/s4/basewt/stdlib`）。探针在 `/tmp/s4/`（`ab.sh` 四条对照、`rounds.sh` 轮数扫描、`g11mr` 重复增长）。

## 2. v31 修掉的那一条：巨块载荷从来不归还

第 5 行是 arena 手写容器最自然的增长写法：函数级 `var`，循环里 `b = new i64[nc]`，`nc = cap + cap/10`。它的旧代没有释放点（块作用域不结束），尺寸每轮都变，所以：

- **v30**：`(d)` 让它进 T2、`extc_rc_alloc` 真的被发射了（收集 34 轮），但巨块载荷的释放路径是空的 —— `extc_rc_freeSlot` 只清 occ 位并 `classPush`，`extc_rc_bigPayloadRelease` 只有三个调用点（free 队列排空 / region 析构 / 进程退出），而 `extc_rc_slabShrink` 与 `extc_rc_pageTrimStep` 都 `if (s->big) continue`。⇒ **空巨块永远出不了链**，容量 = 各代之和，峰值 749,980 kB（11.7× live），并随轮数线性。
- **v31**：①空巨块与普通块同权离链（`slabShrink` 去掉 `s->big` 跳过）；②离链前要过复用宽限（`deadA`/`deadN`，`EXTC_RC_SHRINK_GRACE=1`）与容量闸门（`C ≤ EXTC_RC_SHRINK_CAP_LIVE · live`，默认 3）；③丢弃速率绑到分配速率 —— 每次巨块分配在申请新载荷**之前**按本次请求字节丢死载荷（`extc_rc_bigTrimStep(slotSize)`，记入 `[chan] bigdrop`）。⇒ 峰值 240,716 kB（3.8× live），与轮数无关。

机制、实测、契约与旋钮见 [`MEMORY-MODEL-CURRENT.md`](MEMORY-MODEL-CURRENT.md) §19.15 与 [`GC-ROOFLINE.md`](GC-ROOFLINE.md) §6.20；行号口径见 [`REFS-V31.md`](REFS-V31.md)。

`[chan] bigdrop` 在本轮 `grow11` 上的实测：n=40、max_us=1,389.7、total_us=15,694.1、work_max=47,136,768（47 MB 一口丢弃 ≈ 29.5 µs/MB = 0.0295 ns/B，约为同一请求首次触页成本的 11%）。**这是「暂停 ∝ 请求」而不是常数上界**，契约里要写成 `P_step ≤ … + c_drop·N_req`。

## 3. 怎么读这五条

**① pool 的优势只出现在「增长」与「归还」两个动作上。** 第 2、3 行是平的：预分配之后每元素成本不可区分，每容器创建-丢弃的成本也不可测量（200,000 次 churn 的 RSS 差 4 kB、墙钟都 <5 ms）。所以「pool 有额外开销」这个假设不成立；它贵的地方是它**提供的两个动作**：`poolResizeRaw` 原地加长（不拷贝），和 `release()` 把块还给池。

**② arena 手写的增长要自己拷贝。** 1.5× 增长到 10.2M 元素，总拷贝量约 2.5n；旧代的归宿只有两种：交给回收器（v31，峰值 = live + 两代 ≈ 3.8× live），或干脆没有释放点（v29 第 4 行，随轮数线性）。两条路都比 pool 的 1.00× 差。第 5 行进一步说明：**即使回收器把容量界住了，峰值仍是 3.8× 闭包活集**，因为「拷贝瞬态 + 一轮垃圾」就是这个形状的下界，回收器只能保证它不随历史增长。

**③ 把增长容器路由进 rc 是要付标记钱的。** 第 1 行 v29（不发射运行期、纯 arena）0.090 s / 223,996 kB vs v31（T2）0.100 s / 242,224 kB ⇒ **+11% 墙钟**。原因不是 (d) 判错：10.2M 个槽的活数组每轮标记都要被扫一遍（每槽一次访问），这是「让回收器看得见」的固定成本，不是被回收的垃圾。

**④ 第 4 行是 (d) 真正修好的形状**：不是「容器」而是「容器被反复重建」——函数级变量在循环里被替换，旧代没有释放点。v29 判 idle（没有 ref ⇒ 三条引用判据空洞成立），峰值 20 轮 639 MB、80 轮 2.55 GB；v30/v31 判非 idle、进 T2，峰值钉在 37 MB。但**即使修好，arena 也不是最省的写法**：同一件事用 pool（每轮一个新 vector）是 9,740 kB / 0.010 s，比 arena 手写小 3.8×、快 9×。

**⑤ 第 5 行说明「有界」有两种。** v31 之后它是有界的（3.8× 闭包活集，与轮数无关），但这个界**不是 1× live**：arena 的语义就是「块内不归还」，回收器能把「各代之和」压到「live + 两代」，压不到 pool 的 1.00×。把容器 arena 化省掉的是一层抽象，付出的是这条常数。

## 4. 结论

**不划算。** 四条可比对照里 pool 全部赢或平（1.00× vs 3.78×、1.00× vs 1.00×、0.00 s vs 0.00 s、1.22× vs 4.66×）。v31 修正的是「无界」：第 5 行从 11.7× live（v30）降到 3.8× live（v31），但它仍然是 pool 的 3.8× 内存与 9× 墙钟。**回收器让 arena 有界，不让 arena 划算。**

可行的 arena 用法（实测支持的两条）：

1. **固定大小/预分配**（第 2 行）：与 pool 完全平手，且少一层生命周期管理。
2. **每轮/每请求寿命**（块作用域里 `var a = new T[n]`）：块末 `extc_arena_release` 整片归还，0 处 rc 调用、峰值平（`/tmp/av/loop1.extc`：20 × 64 MiB、峰值 61,556 kB）。这是 arena 最合适的位置 —— 它本来就是作用域分配器。

不可行的用法：**长寿命 + 增长**（第 1 行）、**在循环里替换函数级变量**（第 4 行，现在不再是内存漏洞但比 pool 差 3.8× 内存 / 9× 墙钟）、**循环里按不同尺寸反复增长函数级变量**（第 5 行，v31 起有界但 3.8× live）。

## 6. 边界

- 只在 core 6 上跑、每臂 5 rep：0.000 s 的两行（第 3 行）只能说明「差异小于 5 ms 的计时分辨率」，不能当成精确比值。
- 第 1 行的 pool 用 `poolResizeRaw` 的 1.5× 策略；把 arena 手写的增长因子改成 2× 会少拷贝一些，但改变不了「峰值 = 所有代之和」被回收器压到「live + 两代」这一项。
- 第 4、5 行的 pool 版本是「每轮新建 vector / 预留容量」；若容器本身跨轮复用（`clear()` 保留容量），peak 就是容量高水位（§6.10/§6.11 的容量项），但那是另一种语义。
- 本轮不涉及引用容器：pool 块是 foreign memory，含引用的容器走 `extc_rc_storeRefUnknown` ⇒ pin，arena 化对它们的回收没有收益。
