7.7 分配：new（new T / new [N]T / new T[n]）

var n: mut ref node     = new node        // 一个 T 的**地方**（清零）
var a: mut ref [3]i32   = new [3]i32      // 定长数组的地方
var buf: mut slice<i32> = new i32[1000]   // **n 个元素** —— 造 buffer 就是它

三条规矩（都是一句话）：

规矩为什么
分配出来的一定是零跟定案 8（默认零初始化）同源 ⇒ 没有 C 那种 malloc/calloc 两条路的陷阱（新 node 的 next 天生是 null、新 buffer 全是 0）
活到当前块结束arena 按块细化（每只 {} 一只）⇒ 循环里 new 不会涨内存
引用深度 = 当前块深度跟"哪只 arena"是同一个数 ⇒ 引用逃不出它所在的块

第三条有个放宽（放松方向 = 安全方向）：存进更外层的地方就提升那一层 —— 见下

块级逃逸提升（定案 63）：把块里 new 出来的东西存到外面的变量里是 正常写法（循环里建链表就是它）⇒ 编译器不拒绝，而是把那只 arena 提升上去：

var head: ?ref node = null
while cond {
    var n = new node
    n.next = head
    head = n          // ← `head` 在函数体那层 ⇒ 这些节点活到**函数结束**
}

规则一句话：new 的层 = min(当前块深度, 所有目的地的层)（层越小 = 活得越久） - 只往更深处存（同块内用一下就走）⇒ 一个数都不变 ⇒ 循环里照样不涨内存 - 往更外层存 ⇒ 提升；代价是这些节点活到那一层结束（最坏 = 一个自动清理的堆） - 提不动的照样报错（比如把借来的引用存出去）⇒ 不会静默放行

复用一块存储：@overwrite（定案 65）

从"有 GC 的语言"搬过来的写法，在 extC 里本质是泄漏：

while i < N { var n = new node   slot.v = n   i = i + 1 }   // 每轮一块，攒到函数结束

（实测 1e7 轮 = 159.7MB，而复用是 1.7MB）

根因不是"分析不够精细"：引用的含义即"持有者的生存期不短于该引用的生存期" —— 槽位活到函数结束 ⇒ 它的内容也必须活那么久 想更小就得知道"谁已经不可达" = GC（不做）

⇒ 唯一可行的做法是把意图写出：@overwrite 声明「复用该存储，上一轮的内容不再需要」 写法只多一个修饰符：

while i < N {
    @overwrite var n = new node      /* 存储只有一块：第一次分配、之后每次清零复用 */
    n.value = i
    slot.v = n
    i = i + 1
}
写法存储分配次数内存上界
@overwrite var n = new T一块1常量
@overwrite var b = new [N]T（定长缓冲）一块1常量（不占栈）
@overwrite var b = new T[k]（运行时长度）{ptr, cap}只在"比见过的都大"时翻倍≤ 2 × 见过的最大长度（与迭代数无关）

规矩： - 右边必须是 new（它修饰的是分配；值/局部/调用结果都报错） - 必须 var（每次执行都要重新绑到那块存储上，而且通常还要往里写） - 懒分配（循环一次都不跑 ⇒ 一块都不分配）；清零契约跟 new 一样 - 存储住在本帧（递归各激活一块）；return / 出参照旧走逃生规则 - 它是一句承诺：留着旧指针的人会发现"历史里每一项都指向同一块" ⇒ 想留历史就别用

"这段循环占多少内存"怎么估（三行，记住就够）：

while … { var n = new node }                  // ≈ 16B × 迭代数   （每轮一块，出块回收？不 —— 见下）
while … { @overwrite var n = new node }       // ≈ 16B            （复用）
while … { setIn(n, …) }                       // 0                （一个都不分配，最快）
第一行只有在"分配的东西没被存到更外层"时才是每轮回收 存进循环外的槽位（slot.v = n）⇒ 那层 arena 到循环结束才释放 ⇒ 就是上面的 159.7MB

这跟 A3「逃逸提升」是两件事：A3 管"分配的东西要返回给调用者"（跨函数，靠隐藏参数 __extc_home，见 examples/escape-promotion.extc）；这里管"存进本函数更外层的某个地方" （examples/store-promotion.extc）

跨函数怎么传（逃逸提升 / A3，2026-09-20 三半全齐）：

想干的事写法谁决定它活多久
函数里建好东西返回fn build() -> mut ref node { … return head }调用者：自己有家传家、没有传当前块
往调用者给的容器里塞（出参）fn push(l: mut ref list, v: i64) { … l.head = cell }拥有 l 的那只 arena（= ARENA.md §1.2：最浅的 mut ref 实参）
纯草稿（不外传）函数里 new 但不写进参数、也不返回本函数当前块 ⇒ 循环里不涨

规则 ④：传给 ref/mut ref 的实参，它指的东西必须活得 ≥ 这一刀的家 arena —— 因为被调函数可能把它存进那只 arena。传更深的局部会被当场拦下：

error: argument 2 of `stash` points into a deeper scope (depth 2)
       than the arena this call may store it in (depth 1)

2026-09-22 起：这条规矩改成「在调用点判」（定案 67）—— 因为被调者一次编译， 它根本不知道调用者传来的是长寿还是短命 ⇒ 以前它只能一律拒 ⇒ 一整族正常写法被误拒：

var t: varArray<slice<u8>> = varArray<slice<u8>>::withCap(4)   // 字符串表
t.push("abc")                                                  //   （以前：编译错误）
var g: varArray<varArray<i32>> = varArray<varArray<i32>>::withCap(4)   // 动态邻接表
fn stash(dest: mut ref T, v: T) { *dest = v }                  // 通用"存起来"

现在：被调者只声明"会把什么存到哪里"，由调用点代入实际实参求解 ⇒ 判据变成调用点上这个实参活得够不够久：

写法结果
stash(ref outer, local[..]) —— local 与 outer 同一个块合法（同层 ⇒ 安全 tests/asan/borrowed-stash-sameframe.extc）
stash(ref outer, local[..]) —— local 在更深的块里编译错误（tests/errors/stash_view_from_deeper.extc）
stash(ref slot, i) —— 值不是引用合法（没有引用可悬垂）

拿不准的时候（递归 / 互相调用 / 有解析不出来的东西 ⇒ 效果摘要算不完整）⇒ 调用点保守拒， 消息会说清是"分析不出来"而不是"一定错" —— 这是故意的：宁可误拒，不可漏 UB 处方：把那个助手函数的体写简单些（让摘要算得出来），或让值活到调用点那一层

（旧限制已解：A3 逃逸提升 2026-09-20 落地）new 出来的东西可以用上面三种方式交出去，例如 fn make() -> mut ref node { return new node } 是编译错误（它活不过当前块）。跨函数接线要等 A3 逃逸提升 （今天要在函数间传递，就让调用者提供 buffer/mut ref —— 这也是 IO.md 的设计）

new T 的 T 必须是具体类型（模板里的 T 大小不知道 ⇒ 报错）

new T[n] 里的 n 只求值一次（不纯时编译器自己引临时变量）。
