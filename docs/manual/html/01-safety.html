0.5 内存安全：承诺 × 现状

这一章回答一个问题：extC 到底承诺了什么，今天实现了多少。 每条都标了「实测状态」，不是设计愿望。

三条前提（一开始就定的）

#前提现在
G1内存自动回收 —— 用户永不写 malloc / free / close语言里连 malloc 都没有（生成的 C 里出现 0 次）
G2第一个真实用户是五子棋（不是自举）棋盘/五连判定/result 都能写
G3能自举🔸 修正：主人 2026-09-18 说「不一定完全自举」⇒ 降级成可选的验证手段

一条原则

P：凡是编译期能证明的，运行时不留痕迹。

它禁的是隐藏的机制（GC / 异常 / 运行时元数据 / 隐藏分配 / 运行时类型标签）， 不是数据拷贝（值语义的拷贝是写在类型上的、看得见的）。

P′（同一句话的另一面）：不能证明的，语法上必须看得见。

内存安全的九条承诺

#承诺状态说明
1无 GC、无引用计数从来就没有（运行时零分配）
2无异常、无栈展开失败归 result，? 展开成三句语句
3未初始化 UB 消失默认零初始化：var b: board 自动清零
4ref 不可为空没有 null；ref 也没有零值
5越界 = trap 带 extC 位置a[i] 越界 → trap: index 7 out of range (length 3) + 文件行号。一处显式例外：函数标了 @unchecked 时，该函数体的元素下标不生成检查，越界 = UB（§12.5，写的人签字）
6切片越界能证明的编译期报错，不能证明的运行时 trap 带位置
7只读 / 可写看得见ref T / mut ref T、slice<T> / mut slice<T>（见 §3）
8算术无 UB是溢出用 -fwrapv 兜成确定行为；除零与移位超宽都 trap，且带 extC 位置（tests/traps/div_zero.extc、shift_too_big.extc）
9引用不能活得比被指对象长（逃逸检查）词法深度 depth(r) ≥ depth(v)；参数 = 0、函数体 = 1、每层块 +1。比两个整数，不写生命周期

trap(msg)：无法处理的事情（2026-09-29）

编译器自己插的那些 trap（越界 / 除零 / 移位 / 收窄，见上表第 5、6、8 行）现在有了用户版本：

fn sym(h: ?ref void, name: slice<u8>) -> ref void {
    var p: ?ref void = dl::symOrNull(h, name)
    if p == null { trap("库里没有符号") }     /* 这里没有"怎么办"：程序不该再往下走 */
    return p
}
  • 同一条路：文件:行号: trap: 消息 印到 stderr，退出码 1，经 extc_die ⇒ 临终钩子照跑， 所以已经缓冲的 io::cout 输出不会丢（实测：before-trap 那行先出来 ✓）。
  • 消息必须是文本：字面量 / slice<u8> / ref u8。给一个数字是编译错误 —— 把数字当消息印 出来，正是 trap 要避免的那种安静的错。消息里带 % 也安全（它是参数，不是格式串）。
  • 它不是异常：没有处理器、没有栈展开、不会返回。只用于无法处理的事情（不变量破了、硬编码 的绑定缺一个符号）；可预期的失败（文件不存在、库打不开、解析失败）是 result / option 的 值，用 ? 往上交。这条界线就是"无异常"那一条承诺的具体形状（上表第 2 行）。

判据：tests/traps/trap_literal.extc（字面量）、trap_slice.extc（运行时切片）、trap_cstr.extc （C 字符串）、反例 tests/errors/trap_bad_message.extc（非文本消息必须编译期挡掉）。

逃逸检查：唯一引用规则

若引用 r 指向值 v，则 depth(r) ≥ depth(v)。 人话：引用不能活得比被指对象长。
fn bad() -> slice<i32> {
    var a: [8]i32 = [1, 2, 3, 4, 5, 6, 7, 8]
    return a[..]        // error: this return value would hold a reference to a
}                       //   local variable that dies first (depth 1 > depth 0)

合法的三种写法（视图/引用照样好用）：

写法为什么可以
fn rowView(b: ref board, y: i32) -> slice<i32> { return b.cell[y][0..4] }借的是参数（深度 0）⇒ 活得比函数长
fn copyRow(...) -> [4]i32按值返回 ⇒ 拷贝，不带引用
局部视图只在函数内用同深度 ⇒ 一起生一起死

深度会递归地看进 struct/数组：return holder { s: a[..] } 同样被拦住。

以前故意不查的那条，现在查了：把引用传进函数、函数把它存起来。 这条曾经是欠账（「需要引用的传染性分析，比深度模型贵得多」）—— 现在做成了两条便宜规则，都不需要传染性分析：

#规则拦住什么
A函数调用的引用深度 = max(所有实参的深度)return identity(ref x) —— 转发把信息丢了 ⇒ 放行 ⇒ 实测打印 0（悬垂）
B借来的值不能存进 slotDepth == 0 的地方fn stash(s: slice<u8>) { G = s } —— 参数把「借来的」洗成了「自己的」

A 的一句话证明：被调函数能返回的引用只有两种来源 —— 它自己的全局/静态（深度 0），或者它的实参（深度 ≤ max(实参)）。 它返回不了自己的局部（那条规则单独就挡着）⇒ max(实参) 是精确上界

B 的判据：exprBorrowed —— 参数派生和调用结果是「借来的」； 全局和字面量不是（静态的，谁都存得下）

fn identity(r: ref i32) -> ref i32 { return r }        // 转发本身合法
fn bad() -> ref i32 {
    var x: i32 = 5
    return identity(ref x)   // borrowed from depth 1, but this can only hold up to depth 0
}
var G: slice<u8> = "x"
fn stash(s: slice<u8>) { G = s }   // cannot store a borrowed value into something that outlives this call

还有一条：s = a[1..3]（整体赋值给视图）= 换绑那两个词，

let 是给"已有的别名"降级的，不是"造一个不可变对象" let x = new T 会拿到一条只读引用，而只读引用提权不回来（ref *x / 传进 mut ref 参数 / x.f = v 全被挡）⇒ 这块存储谁也写不进去、永远是零 ⇒ 编译器给警告（不拦）： 想写就用 var；想要"只读视图"就 var w = new T + let r = w

不是「透过只读视图写元素」⇒ 合法。它和上面两条必须一起修 —— 这条以前误报，而误报让上面两条的反例写不出来（谁来触发洞的代码自己都编不过）

深度模型不是为今天设计的，是为内存模型设计的： 加上 arena（深度 0 的存储）之后，g.s = a[..] 这类照样被同一条规则挡住

算术 UB：三处都已带位置 trap

情况现状
有符号溢出-fwrapv 兜成确定的绕回
除零trap：trap: division by zero，带 .extc:行号
移位 ≥ 位宽trap：trap: shift count out of range，带位置

这三条是从 C 继承来的（编译到 C 就意味着要负责把 C 的 UB 一处一处堵上）。生成物里对应的是 extc_divI / extc_shiftCount 这类检查过的帮助函数，常设判据在 tests/traps/。

UB 的全部出口（可审计清单，2026-09-29）

上面那九条里，五到八是"编译器插检查"换来的。检查是可以被关掉的，所以安全承诺的完整说法不是 "没有 UB"，而是"UB 只有这几个出口，每一个都写在源码里、且有判据盯着"：

出口纯 extC 代码碰得到吗换来的 UB门
@unchecked（§12.5）碰得到（自己写）那个函数体的元素下标不生成检查 ⇒ 越界 = UB一处函数、写在源码里
@builtin 声明碰不到（只有标准库能声明，定案 96）给运行期原语起名字 ⇒ 任意 (指针,长度) 变视图加载器按文件位置拒（tests/errors/builtin_outside_std.extc）
use std::sys::heap（特权层）碰不到（定案 96）同上，外加载任意区间 mmap/munmap加载器按模块名拒（tests/errors/privileged_import.extc）；要指针就用 plate::viewAt(p, n)，它先做区间检查
!（签字）碰得到null! / none! 拿到零值 ⇒ 调用或解引用 = 段错误（实测 rc=139）它是"这里担保非空"，语言故意不检查；要检查用 ? 或 trap
fn 转换（签名）需要先拿到地址（dl::sym、C 给的指针、@export 的另一面）签名与真实函数不符 = UB转换只能写一次、且过类型检查；地址来自 C 那边
effects Addr / Cont / Ret碰得到谎报"这个库不留"或"返回的不指向帧" ⇒ 悬垂引用只在过 C 边界时参与判定（纯 extC 里没有 C 会替谁留指针）
@frozen碰得到布局与 C 那边不一致 ⇒ 数据静默错（实测：{i64} 对 C 的 {i32,i32} 编过、跑过、读到 5007/0）只在跨 C 边界时咬人；extC 内部的布局自洽有 _Static_assert 盯着
extern! 声明任意 C 符号碰得到比如自己声明并调用 munmap这就是 C 边界本身：extern! 是一句签字
dlopen 任意 .so碰得到同进程同权限，没有沙箱（十种攻击的实测见 C-ABI.md §9.17）威胁模型写在 C-ABI.md

结论：把 C 关在门外（不写 @unchecked、不用 ! 硬闯）时，语言里没有第二条通往 UB 的路 —— 这一条在定案 96 之前不成立：use std::sys::heap 加一句 extc_viewOf(任意指针, 任意长度) 就能造出越界视图（实测：8 字节的全局配 1,000,000 的长度，读第 999,999 个字节，rc=139）。现在那条路 关掉了：原语只有标准库能声明，特权层只有标准库能导入，程序要的是板的有检查的门 ✓。
