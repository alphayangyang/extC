**结构。** `src/back/reclaim.c` 与 `src/back/codegen.c`：①**H1 描述符扇出无上界** — codegen 的 `rcEmitTypeDesc` 描述符上限 4096 → **32**（`if (offs.len > 32) return "((const ExtcRcType *)-1)"`，超过即退回保守扫描，零运行期成本），单个 pop 最多 push 32 个 child；②**H2 内联保守扫描无额度** — markStep 新增 `size_t _scanLeft = EXTC_RC_SCAN_CHUNK`（8192 词），保守分支条件从 `words > SCAN_CHUNK` 改成 `words > _scanLeft` 并 `_scanLeft -= words`，一步内联扫描词数 ≤ 8192 与形状无关；③**H3 标记栈无软上限** — 新增 `EXTC_RC_MARK_STACK_SOFT 8192`，续扫条件改成 `if (r->scanObj && r->msp <= STACK_SOFT)`，栈深超限的步改为 drain 而不是续扫（此前 1M-child 对象把栈推到 1,048,576 条 = 8 MB，并付一次翻倍 realloc 拷贝）；④**H4 free 队列的 1 ms 硬帽** — `EXTC_RC_FREE_DEADLINE_US` 100 → **40**、`EXTC_RC_FREE_HARD_DEADLINE_US` 1000 → **50**（drain pass 本身是停顿，且 sweep 收尾会调它），上限变成「一次 pass ≤ 50 µs + 一块 slab」；⑤**H5 巨块 munmap 不可分** — 新增 `[rt:hugefree]` 发射块（84 行）：巨块载荷改页对齐 `aligned_alloc`，释放时登记进 `ExtcRcBigDrop` 链，每步用 `madvise(MADV_DONTNEED)` 丢 **≤ 512 KiB**（实测 6.7 µs/512 KiB），最后一 chunk 才 `free`（实测 2 µs —— 页表已空，只剩 munmap）；⑥新增 `EXTC_RC_MARK_STEP_POP_MAX 512` 硬钳制每步 pop（压力档 1024 也会被压到 512）；⑦冷档 `EXTC_RC_MARK_COLD_BATCH` 128 → **32**（冷 pop 实测 ~1 µs，32 个落在 50 µs 内）；⑧push 记账改成**每批一次**（`if (r->msp > _sp) pushes += ...`，约 200 pop 才 2 Ir）+ `EXTC_RC_MARK_PUSH_STEP 2048` 截断 ⇒ 一步 push ≤ 2048 + 200×32。量具：`[wbudget]` 增加 `pop_max`/`push_max`/`pops_tot`，`[work]` 增加 `cons_max`（无钟高水位）。为什么不做 per-pop/每字段记账：Ir 消融（A/B/C/E/F/K）证明那样每 pop 约 7 Ir、总量 +1.42M，Ir 门禁不可支付；`scanDesc` 双游标（0 = 保守词索引、1 = 描述符字段索引）让 `markResume` 两种扫描都能续扫。

## 2026-12-01 · 块级归还接到 mutator 路径：空块在轮末就还，不再等 settle

**症状。** 11-30 的页级归还只把「块内的空页」还给 OS；块本身（512 KiB 的 slab）仍只在 `extc_rc_settle` 里被摘掉，而 `extc_rc_settle` 只有 `extc_rc_collect` 走。真实程序的分配触发路径是 `extc_rc_alloc` → `extc_rc_maybeCollect` → `extc_rc_sweepStep`，从不经过 settle ⇒ 一个从不显式 collect 的程序会把峰值时的整块容量钉在堆上，页归还只能把每块缩到「含活对象的页」。自动路径探针 `/tmp/pg/pages6.c`（64 MB 峰值、零 root、之后 140 万次分配、只调 `extc_rc_maybeCollect`）在改动前：slabs 64 → 64、`slabRel=0`、RSS 43,788 kB 不降。

**结构。** `src/back/reclaim.c`：①删除 `ExtcRcRegion.shrinkDue` 字段与三处使用（`sweepBegin` 清零、`sweepStep` 置位、`settle` 消费）——「轮末就是归还点」之后这个标志没有语义；②`extc_rc_sweepStep` 收尾分支把置位换成调用：`extc_rc_slabShrink(r)`（3915）+ `extc_rc_fqDrainAuto()`（3916）+ 原有的 `extc_rc_pageTrimStep(...)`（3917），三者都在同一个被计时的步内 ⇒ 归还成本进 `[step]`/`[histo]` 的停顿分布；③新宏 `EXTC_RC_SHRINK_MIN_SLACK (8 << 20)` 与 `extc_rc_slabShrink` 体首早退 `if (r->capBytes - (int64_t)r->bytes < (int64_t)EXTC_RC_SHRINK_MIN_SLACK) return 0;   /* skip:shrink-slack */`（1900）；④`capBytes` 的累加/递减从 `#if EXTC_RC_PAGE_TRIM` 移出改无条件（885 / 1929）——`PAGE_TRIM=0` 时它恒为 0，slack 闸门会把块归还永久拦住。

为什么只能在轮末：清扫游标可能停在链上任意一块，摘块的前提是游标已清空，所以摘链固定在收尾分支；`settle` 不再摘块。为什么要有 slack 闸门：容量只比占用多一点时，摘块换来的是「munmap 512 KiB → 之后重新 carve」，抖动会赢；8 MiB 是容量界上抬的常数。全在冷路径，**不引入写屏障**。
