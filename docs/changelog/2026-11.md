## 2026-11-01 · 区间循环的下标检查前移从未生效：`i64(v[i])` 被当成副作用

**症状** `bench/realsvc` 的 `parmix` 臂（顺序建每条记录的偏移表，再 `par` 解析 + 混合）比 C++ 慢，
且单线程每记录 **1,705 条指令**（C++ 1,445、Rust 1,340）。看生成 C 才发现原因不是"没优化好"而是
"优化从没发生"：`grep -c '__extc_rk' bench/realsvc/build/main.c` 是 **0** —— 下标检查前移
（`loopHoistRangeFor`）在这个程序里一次也没触发，每个字节都是 `(*slice_u8_index(buf, i, …))`。

**结构** 定位到 `src/back/codegen.c` 的 `hoistForbiddenExpr`：它判断"循环体里的下标能否安全提到
循环入口"，原则是只允许纯表达式；但 switch 里**没有 `EX_CONV` 分支**，于是 `i64(v[i])` 落进
`default: return true` 被判成副作用 —— 而这正是几乎所有字节循环的写法（`u8` 下标要转 `i64` 才能
参与算术）。补 `case EX_CONV: return hoistForbiddenExpr(e->u.conv.operand);`（转换不调用、不 trap、
不会被跳过，是纯的，可以穿越）。同时 `hoistSitesStmt` 只收集 `ST_VAR`/`ST_ASSIGN`/`ST_EXPR`，
`if` 的**条件**每轮必求值却漏了 ⇒ 补 `case ST_IF: hoistSitesExpr(s->u.ifs.cond, sites); return;`
（两个分支仍不穿越：那里的下标只在分支被走到的轮次执行，提前判会改变 trap 时机）。

**判据** `tests/ops/hoist_forms.extc` + `tests/ops/run.sh` 的「下标检查前移」一节钉住**形态**：
三种最容易被漏掉的写法（`s + i64(v[i])`、`if v[i] == u8(9)`、`s + i64(v[i]) * 2`）编译后
`__extc_rk` 出现 3 次，且三个函数体里**没有**按元素的 `slice_u8_index`。牙齿验证：把 `EX_CONV`
分支去掉重编 ⇒ 该节红、`slice_u8_index` 回来；加回去 ⇒ 绿。语义判据仍由
`tests/io/hoist-order.extc` 守：trap 报文报**第一个越界元素**而不是区间极值（`index 2` 而非 `3`）。
效果：`parmix` 单线程每记录 **1,705 → 1,351 条指令**（低于 C++ 的 1,445），`t=1` 344 → 306 ms、
`t=4` 141 → 108 ms、`t=24` 67 → 62 ms（同机 C++ 320/112/57）；`bench/realsvc` 的 worker 内层变成
`uint8_t c = (*((buf).data + (int64_t)((base + j))));`，每条记录入口一次性判 `starts[i]`/`lens[i]`。

## 2026-11-01 · 协程服务的性能：每请求一次 `send` 的代价

**症状** `bench/realsvc` 的 `serve` 轴（64 连接 × 8 深度、20 万请求）里 extC 只有 430k req/s，
同机 C++ 595k、Go 578k、Rust 565k —— 比 C++ 慢 39%，远超同一份 `RESULTS.md` 里其它三轴的差距。
但协程本身不像瓶颈：`callgrind` 用"两个请求数（5k 与 25k）的整轮指令数差分"算出每个请求
**1,059 条指令**，同一方法对 C++ 是 2,099 条 —— 用户态工作量 extC 只有 C++ 的一半。差别在系统调用：
`strace -c` 数 20,000 个请求，extC 发了 **20,000 次 `sendto`**（一条应答一次），C++ 只发 **2,560 次
`write`**（一次读到的请求攒起来一起回）。也就是每个请求多付一次 `send` 系统调用，20k 请求多 1.7 万次。

**结构** `bench/realsvc/extc/main.extc` 的 `conn` 协程改成"按读到的这一批回"：连接私有的 4 KB
应答缓冲 `rep`，`rn` 记已攒长度，每写一条应答前若剩余不足 40 字节就先冲一次，内层请求循环结束后
（即 `yield` 之前）把 `rn` 冲干净再等下一批输入。这样"单独到达的一条请求"仍然立刻应答 —— 冲在
等待之前，不在定时器上，语义与延迟不变；批量到达的应答只花一次 `send`。`SPEC.md` §5 补了一条口径：
写策略由各臂自己定，但必须保序、且单独到达的请求不必等下一批。`run.sh` 的 `serve` 改成**按臂交错**
重复（每轮四臂各跑一次），让机器漂移不偏向某一臂的均值。

**判据** 四臂 checksum 与 `bad=0` 全部不变；`strace -c` 20k 请求的系统调用从 **1.16 次/请求**
降到 **0.30 次/请求**（`sendto` 20,000 → 2,536，`recvfrom` 2,597，`epoll_wait` 706）；7 次交错重复
的中位吞吐 extC **430k → 559k req/s**（11 次按臂交错测量：C++ 558k、Go 558k、Rust 568k —— extC
与 C++ 落在同一个数上，从 `0.72×` 到 1.00×），`RESULTS.md` 的并发表与 `README.md` 的首轮摘要同步更新。
方法备注：`callgrind_control -z` 清零后归因会塌缩成 `__libc_start_main` 一条，不能用；perf 的硬件
计数器在 WSL2 不可用（`<not supported>`），`cpu-clock` 软件事件只到用户态符号，所以"指令数差分 +
系统调用计数"才是这台机器上可靠的两把尺子。

## 2026-11-01 · `io::flushCout()` 不冲刷：stdout 变成文件/管道时输出卡到进程退出

**症状** 一个先打印、显式 `io::flushCout()`、再继续干活的程序，在被重定向到文件时**看不到任何输出**，
直到进程退出；在终端上一切正常。协程服务因此暴露得更明显：`bench/realsvc` 的服务臂启动后在监听前

**判据** `tests/io/run.sh` 新增 `flush-mid`：`tests/io/flush_mid.extc` 打印 `mid-run`、`flushCout()`、

两条防线，避免端口占用时整轮测量挂住。

`stdlib/std/sys/file.extc` 增加两条 `extern!("extc-runtime")` 声明与两个公开包装
`openAt(path, len, flags, mode)` / `open(path, flags, mode)`；`stdlib/std/sys/io.extc` 删掉 `open` 的
libc 声明（`O_*` 常量留着）；`stdlib/std/fs.extc` 的 5 处 `sysio::open` 改 `sysfile::openAt`；
`bench/app/stamped/extc/*.extc` 同步改用 `sysfile::open`。`std::sys::io` 从此不再声明任何与系统头
同名的函数。
