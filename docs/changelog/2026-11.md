## 2026-11-01 · bench/realsvc：一个真实场景的四轴横评（extC / C++ / Go / Rust）

**症状** 既有的性能卡具都是单点的：`bench/fortran` 只看数值内核，`bench/memstudy` 只看回收机制，
`bench/par` 只看并行分块，`bench/httpd` 只看协程。它们各自说明一件事，却回答不了"整台服务用这门语言
写会怎样"。要回答这个，需要**一个数据、四种活**：同一份请求日志被解析聚合（常规）、每条记录物化成对象
再丢弃（回收）、按站点预聚合后并发应答（协程）、同一批记录做多核重计算（并行），四个语言各写一遍，
且四份输出的 checksum 必须逐字节相同 —— 否则比的不是同一件工作。

**结构** `bench/realsvc/`：`SPEC.md` 定数据集（7 列 TSV，2,000,000 行 / 71,582,794 字节，uid 重尾分布
90% 落在 `[0,19999]`、TTL 300 秒 ⇒ 约四分之一会话存活、其余成为垃圾）与四个 workload 的输出行；
`gen/gen.c` 用 xorshift64* 固定抽取顺序生成；`client/client.c` 是四臂共用的 TCP 客户端，自己从数据集
算出期望值并逐条校验；`cpp/main.cpp` 是参考实现，`extc/main.extc`、`go/main.go`、`rust/main.rs` 各自
按语言惯例实现同一形状（C++ `new`/`delete` + `unordered_map`；Rust `Box` + `HashMap`；Go `&Event{}` +
`map`；extC arena 块回收 + 扁平数组 + 存活标志）。`run.sh` 负责建、绑核、重复取中位并写 `RESULTS.tsv`，
`report.py` 生成 `RESULTS.md`。

**判据** 四臂的四个 checksum 逐字节相同：`etl` `11191182498282499399`、`sessions`
`16199615779603620825`、`parmix` `10280782628320053244`（`sum=2919411389961607233`，任意线程数相同）、
`serve` 服务端 `620352923810747373` 且客户端 `bad=0`。首轮实测（中位，比值对 C++）：`etl` extC 65.0ms
（0.96×）/ Go 90.7（1.33×）/ Rust 73.5（1.08×）；`sessions` extC 62.2ms（0.58×）/ Go 138.4（1.29×）/
Rust 168.8（1.57×），峰值 RSS extC 76MB 对其余 85–86MB；`parmix` extC 337.9 / 91.5 / 70.9ms（1/8/24
线程，自加速 4.8×），与 C++ 各档相差 10–13%；`serve` extC 430k req/s、C++ 595k、Go 578k、Rust 565k，
四臂全部 `bad=0`。

## 2026-11-01 · 长表达式链让编译器爆栈：表达式深度预算

**症状** `let x: i64 = 1 + 1 + …`（5000 个操作数写在一行）让编译器自己崩：release 构建 `rc=139`
（SIGSEGV），sanitizer 构建 `AddressSanitizer: stack-overflow`，栈帧在
`checkExprInner`（`src/check/check_expr.c`）→ `checkValue`（`src/check/check_escape.c`）→
`checkExpr` 之间循环。这是合法输入：源码里没有任何嵌套，`a + b + c` 是左结合链，语法深度只有一层；
解析期的 `PARSE_DEPTH_LIMIT`（64）管的是**括号嵌套**，所以这类程序到不了任何现有闸门。而检查、
逃逸分析、层号求解与代码生成都沿 AST 逐层递归 ⇒ 8 MB 栈在 release 约 4000 个操作数处耗尽
（实测 20000 通过、40000 崩；sanitizer 构建约 4000 崩）。

**结构** 检查器加一条深度预算：`Checker.exprDepth` 记录当前表达式走行的深度，上限
`EXPR_DEPTH_LIMIT`（2048），`checkExpr` 每次进入 +1、返回 -1，超限报
`expression too deep to check (the compiler's limit is 2048 levels)` 并返回错误类型。判据取
"合法但不崩"的边界：2048 个操作数的链照旧编译并运行（`tests/sugar/sugar_long_chain.extc`，1500 项求和），
2049 起拒绝（`tests/errors/expr_chain_too_deep.extc`）。上限取值与 `PARSE_DEPTH_LIMIT` 同类，理由写在
`src/check/check_expr.c` 的常量注释里：sanitizer 构建在 2048 层仍留约一倍栈余量（实测 3500 通过、
4000 崩）。用户可见的口径补进 `docs/usage/language.md` §12 的"现在写不出来的写法"表。

**判据** `tests/run.sh` 376/0（新增反例进全局拒绝语料）；`tests/sugar/run.sh` 29/0（新增正例与反例各一条）；
sanitizer 构建对 5000 项链给出一行诊断而不再 `DEADLYSIGNAL`；`&`、`|`、`*`、`&&`、移位、调用与下标
混合的 5000 项链同样只出诊断（不再有哪一类运算符走别的递归路径）。

**判据** `python3 tools/inject.py --check-anchors` → ok（32 条注入、41 处原文各命中一次，且 `old != new`）；

## 2026-11-02 · 静态分析扫出的契约空洞：断言、注释与一次复核

**症状** `cppcheck --enable=warning,performance,portability` 与 `clang-tidy`（`bugprone-*`、
`clang-analyzer-*`，28 个翻译单元）对编译器自身扫出六条真问题与若干噪声。真问题里没有一条是
"运行时会崩"的可复现缺陷，而是**契约只写在人脑里**：`src/check/check.c` 的
`checkAssignable(Checker *c, Type *want, Type *got, …)` 在 `ttIsError` 之后直接 `want->kind`，而
`ttIsError` 把 NULL 当"不是错误"，缺类型会被解引用而不是被报告（18 个调用点核对后没有能传 NULL 的
路径，但函数本身没写这条前提）；`src/back/codegen.c` 的 `parallel::run` 分支
`size_t nCaps = wf->params.len - 4` 默认参数表至少有四个（少一个就无符号下溢、循环走飞）；
`src/front/parser.c:1401` 在 `parseType` 已报错返回之后还写 `if (!ft || ft->kind != TY_FN)`，`!ft`
恒假；`src/check/check_top.c:2954` 把 `int anFreshCount(...)` 传给 `%u`。

**结构** 补齐契约而不改语义：`checkAssignable` 开头加 `EXTC_DBG_ASSERT(want != NULL && got != NULL)`
（`EXTC_DBG=1` 才生效，由 `src/base/dbg.h` 的运行期开关控制），并写明"缺类型是调用方的 bug"；
`codegen.c` 的 worker 分支加 `EXTC_DBG_ASSERT(wf->params.len >= 4)` 并把不变量写进注释；两处加
`#include "dbg.h"`。纯清理：`parser.c` 删掉恒假的 `!ft`；`check_top.c` 的 `%u` 实参加 `(unsigned)` 转换；
`codegen.c` 的 scratch 窗口补"指针只在函数内有效"的注释、`ST_DOMAIN` 分支补
`EXTC_DBG_ASSERT(body != NULL && body->kind == ST_BLOCK)`。文档侧：`fieldDepthEntry` 注明返回的槽指针
在下次 `symFieldsGrow` 后失效；`depthComesFromAlloc2` 的 `EX_GENCALL` 分支注明这是**有意过近似**
（泛型实例可能返回自己分配的内存，走错方向只是放宽深度上界，不产生崩溃）。

**判据** `make -j8` 无告警；`./tests/run.sh` 376/0；`check.sh smoke` 16/0；`check.sh docs` 13/0；
`EXTC_DBG=1` 下现有语料不触发新断言。clang-tidy 剩余告警逐条看过：239 条
`DeprecatedOrUnsafeBufferHandling` 是 `memcpy`/`vsnprintf`/`fprintf` 的 C11 附录建议，`strcpy` 一处
（`src/check/check_lookup.c` 的 `checkFnDisplay`）前面已有长度上界判断，`PRIVILEGED_MODULES` 与
`atNames` 两处数组越界告警都是分析器看不见哨兵/`items.len >= 2` 分支造成的假阳性。

## 2026-11-01 · 编译器注释整仓英文化：src 49 个文件、22 万汉字、零代码改动

**症状** `src/` 的 62,000 行里有约 25,000 行中文注释、22.5 万个汉字。注释本身是资产（大量"为什么

**结构** 分六批（`src/base`、`src/front`+`main.c`、`ast`+`typelayer`+`plan`+`check.c`、

每个文件的中文注释改写成简洁英文：文件头 `@file` + `@brief`，public 声明按声明顺序写
