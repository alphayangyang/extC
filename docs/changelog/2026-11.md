## 2026-11-73 · 检查器：运算符结果按**目的地**定池层级

`for i in 0..n { s = s + t }` 编不过，报 `this assignment would hold a reference to a local variable
that dies first (borrowed from depth 4, but this can only hold up to depth 1)`；而同样语义的
`s = s.concat(t)` 一直是对的。

**根因**：运算符重载在检查器里是"调用的另一种拼写"——`s + t` 解析到 `string` 的
`fn +(self: ref string, other: slice<u8>)`，它的体里调 `concat` 建池，生成的 C 与方法写法调用同一个
函数。但两条链在检查器里走的是不同分支：

- 调用站点（`EX_CALL`/`EX_METHOD`/`EX_ASSOC`）参与**按目的地降层级**的求解（`promoteInto2`）：
  结果存进哪一层，池就记在哪一层，所以 `s.concat(t)` 的池落在 `s` 所在的函数体层；
- 运算符站点（`EX_BIN`/`EX_UN`）**不在那张表里**：它的 zone 参数被记成"表达式所在块"（循环体，
  第 4 层），于是"池比目的地短命"被如实报出来。

**修法**（两处，都不改语义、都不放宽规则）：

- `src/check/check_top.c` 的 `markCallHomeIfEscaping`：把"解析出了 callee 的运算符"当调用站点看待
  （`opCall`）。内建运算符没有 callee，仍走原路。
- `src/check/check_escape.c` 的 `promoteInto2`：新增 `EX_BIN`/`EX_UN` 分支，**只**做"池建层可降"
  那一件事（callee 建池时把 zone 降到目的地层；不建池就 `return false`，让调用方照原样报错）。
  这里刻意复用调用分支的判据而不是把节点改写成方法调用——改 Kind 会让延迟实例化重放把它当普通
  方法调用**重新解析重载**，`+ (i64)` 会被解析成 `+ (slice<u8>)`，13 个套件红。

**判据**：`tests/ops/op_result_depth.extc`（`len=10 same=true n=42 tail=3`）——循环里 `+` 与
`concat` 得到同一个池层级、结果相同；内建 `i64 + i64` 不受影响；函数返回位置上的 `+` 仍工作。
`tests/run.sh` 379/0、`tests/ops` 全过。

**已知边界（既有，与方法写法同受一条限制）**：在循环里建出来的字符串**再 return 出去**仍被拒
（`return s` 报 depth 4 → 0）；`s.concat(t)` 同样。这条属于"池站点跟着重绑走、返回要再提一层"，
另案。

## 2026-11-69 · 验收：ASan 那支的随机红不是被测程序的错（gcc 12 的 libasan × 高熵 ASLR）

上一笔之后，干净 Debian 12 里整轮还剩 1 条红，而且**每次红的用例都不一样**（`promote-nested-block`、
`overwrite-dyn`、`promote-loop`、`nonfinite-float`、`reclaim` 的 ASan 单元……），报错形式是
`AddressSanitizer:DEADLYSIGNAL` 刷屏后挂住，或者干脆"运行超过 60s"。查下来是三层，逐层定案：

**① LSan 对这套内存模型没有意义。** `-fsanitize=address` 在 Linux 上默认带 LeakSanitizer：进程
退出时停所有线程、从寄存器/栈/TLS/全局段做保守扫描，报"分配了再也到不了"的块。而本项目 arena
的块**到进程结束才释放**、各级登记表（槽表、根表、板块链表）本身就是常驻结构 ⇒ 泄漏判据不适用，
它还会在最小发行版里偶尔卡在退出扫描上。15 个跑 ASan 的套件统一 `ASAN_OPTIONS=detect_leaks=0`
（`tests/reclaim/run.sh` 早就这么做了）。真正管"界不随轮数涨"的是 `tests/reclaim-*` 的峰值棘轮。

**② 剩下的随机挂住是 libasan 与内核的 ASLR 熵不兼容。** 用一条 `int main(void){return 0;}`
做对照，在 chroot 里 32 路并发跑：**9/32 次**在启动阶段自己 SEGV（stderr 只有 DEADLYSIGNAL），
`setarch -R`（关地址随机化）之后 **0/32**；同一台机器宿主上的 gcc 15 libasan 一次都不犯。
根因是 `vm.mmap_rnd_bits` 被新内核提到 32，而 gcc≤12 的 libasan 按固定偏移映射影子内存时不
处理这种熵（gcc 13 / clang 17 起才修）。**这不是被测程序的错**，测下去只会得到随机红。

**③ 于是给 ASan 两支各加一层"别误伤"机制。**
- `tests/asan-probe.sh`（新）：先用一个 trivial 程序把 ASan 跑 8 遍（`EXTC_ASAN_PROBE_RUNS` 可调），
  任何一次非零退出或出现 `AddressSanitizer` 字样 ⇒ 判定这台机器上 ASan 运行时不可靠，
  `skip` 并**打印原因与三条出路**（换 gcc>=13 / `sysctl -w vm.mmap_rnd_bits=28` / `setarch -R`）。
- 15 个跑 ASan 的套件在开头自降随机化后重新 exec 自己（`exec setarch $(uname -m) -R bash "$0"`，
  `EXTC_ASAN_NO_SETARCH=1` 可关）；`tests/asan/run.sh` 另外改用探针决定整支跑不跑。

**判据** 干净 Debian 12 chroot 里 `./tests/run.sh` **378/0、rc=0**（连续三次跑 `tests/asan/run.sh`
也是 0 FAIL，之前是每次挂一两个不同用例）；本机 `tests/run.sh` 378/0、`tests/asan` 全绿、
`check.sh docs` 13/0、`bash -n` 全部通过。

### 2026-11-21 · 库：`buf<T>` —— 会交还板块的可增长缓冲区

**结构**：`std::data::buf<T>` 标 `@noCopy`，所以值位置出现时**转移**而不是拷贝 ——

## 2026-11-20 · `@drop`：单所有者的类型离开作用域时交还状态

`@noCopy` 的类型持有的是地方管不着的东西（fd、socket、锁），过去每条提前返回的路径都要用户
自己写 `close()`。现在给方法标 `@drop`，它就在**块退出**、**中途 `return`**、**覆盖赋值**三处
自动跑，顺序是逆序、内层先：

```extc
@noCopy
struct res { id: i64
    @drop
    fn gone(self: mut ref res) { println("drop ", self.id) }
}
{
    var a: res = { id: 1 }
    { var b: res = { id: 2 } }
}                    // 打印 drop 2 然后 drop 1
```

标签是 `@drop`（不是魔法方法名），只能挂在 `@noCopy` 结构体的
`self: mut ref T` 方法上，一个类型恰一个；泛型实例有自己的实体，钩子按标签找、不按类型名找。
`break` / `continue` 跳出块时也交还状态（先跑钩子、再放它们身后的 arena 层）。程序退出、trap
路径、以及字段自动析构都还没做——它们目前是**漏释放**（可恢复的一侧），不是双重释放。

字段跟着父值走：自己有钩子就先跑钩子、再按声明顺序跑字段的钩子（`outer` 没有钩子时只跑字段），
可达性也跟着递归标，否则泛型实例只剩隐式声明。

资源警告也跟着走了：有 `@drop` 的类型不再被报"打开了没关"——钩子就是编译器自己发的释放点
（同样的程序去掉 `@drop` 会照报，判据里就是这么钉的）。

判据：`tests/drop/` 10 项（逆序、覆盖、中途 `return`、`break`/`continue`、字段、无钩子、泛型、
资源警告不再误报、两条拒绝）。

### 2026-11-19 · 检查器：`@noCopy` 的值现在会**移动**，不再一律拒绝

`var b: counter = a` 过去报"`@noCopy` 不许按值拷贝"，可这个形状的意图恰恰是**把状态交给新名字**：
两个名字共享一个身份才是注解要防的，转移只留一个名字。检查器现在把绑定与结构体字面量字段上的
`var b = a` / `var b: box = { c: a }` 记成**移动**：

```extc
@noCopy
struct counter { pos: i64 }
var a: counter = { pos: 1 }
var b: counter = a        // 移动：值去了 b，a 的名字作废
a = { pos: 7 }            // 赋新值 ⇒ a 重新拥有一个值
```

- 移动之后**读**源名字是编译错误（``error: `a` was moved into `b` and cannot be read here``），
  note 给两条出路：赋一个新值，或者一开始就用 `ref` 让两个名字看同一个状态；
- 只搬**普通名字**。字段、数组元素、实参、返回值仍按原样拒绝拷贝（把字段取出来会让聚合体半卖身），
  所以 `arg_copy` / `assign_copy` 两个反例照旧成立；
- 语义按**标签**走，不看类型名：任何标了 `@noCopy` 的类型都适用，`string`/`vector` 之类没有标签的照旧拷贝。

判据：`tests/nocopy` 6/0（新增 `move_bind`、`move_into_field` 两个正例与
`use_after_move`、`use_after_move_field` 两个反例 —— 移动后读源名字必须被拒）；

### 2026-11-18 · 绑定里的 `T **` 出参：生成器补一个 C shim

`sqlite3_open(path, &db)` 这种"出参一个句柄"的 C 函数，在 extC 里表达不出来 —— `ref` 只作用于值，
`ref` 一个引用是非法的（`?ref ?ref void` 在调用点造不出来）。生成器现在为这种形状补两个东西：

- 同目录的 `<out>.shim.c`：`void *extc_shim_x(...)` 调原函数、把句柄返回、状态码写进 `int64_t *rc`；
- 绑定里的一层包装：`fn x_out(参数…) -> ?ref void`（状态码 0 给句柄、非 0 给 `null`），
  字符串形参在包装器这一层直接收 `slice<u8>`（内部用 `cstr`，调用点不用写 `.data`）。

shim 的 `.c` 由生成器写进 `.link`（`ccflag <abs shim.c>`，**排在库前面** —— cc 从左到右扫，
静态库要先看到引用它的目标文件），`-I` 目录也一并写进去。shim 的形参用**绑定里**的 C 类型、
调用处再按头文件里的写法显式转回去（`uint8_t *` 与 `const char *` 在 C 里是不同的类型）。

只自动处理"恰好一个 `T **` 出参 + 整数状态返回"这一格；其余形状（多个出参、返回别的类型）

`tests/extpkg-system` 4/0、`tests/cbindgen` 全过。

### 2026-11-18 · 绑定里的 C 字符串：别提 `.data`、别自己补 NUL

`extpkg add zlib --all` 生成的绑定现在多两个便利函数（只在绑定里真的出现 `ref u8` 形参时才发）：

```extc
use zlib::*
let g: ?ref void = gzopen(cstr(path), cstrAt(1, "wb"))   // path 是运行时的 slice<u8>
```

`cstr(s)` 把一段 `slice<u8>` 拷进模块自己的 4×1024 字节拷贝区、补 NUL，返回首字节的引用；
一次调用里有几个字符串就按序用 `cstrAt(0, …)`、`cstrAt(1, …)`（最多 4 个、每个 ≤1023 字节，
越界是带位置的 `trap`）。**指针只在下一次 `cstr`/`cstrAt` 之前有效** —— 这正是绑定里
`effects Addr=0 Cont=0` 签的那句话；库要是把指针存起来，签字就是假的，包的判据该红。

为什么需要它：C 的 `char *` 在绑定里是 `ref u8`，调用点写 `f(name.data)` 只对**字面量**
成立（字面量本来就 NUL 结尾）；运行时拼出来的字符串没有 NUL，也没有稳定的首字节引用。

判据：`tests/extbind` 6/0（新增 `cstr-helper`：运行时拼的字符串经 `cstr` 交给 C，
`sum=42 len=12`）、`tests/extpkg-system` 4/0（`gzopen(cstr(path), cstrAt(1, "wb"))` 真的写出
一个 31 字节的 gzip 文件）。

### 2026-11-17 · `extpkg add <库>`：`add` 完就能直接 `use`

"用别人的库"最后一层仪式也拿掉了。机器上装了开发包的库（有 `.pc` 或标准路径的头文件）：

```bash
extpkg add zlib --all          # 一条命令
```

它做三件事：① 问 `pkg-config` 要版本与头文件目录；② 用 `cbindgen.py --extern` 生成
`vendor/zlib/zlib.extc`（`extern!("extc-zlib") fn …` + 每条一条 `effects` 签字）与
`vendor/zlib/zlib.link`（`pkgconfig zlib`）；③ 往 `packages.toml` 记一条 `system = true`，
往 `vendor/zlib/extpkg.toml` 写"签字待证伪"的台账（`state = "unverifiable"`，`verify` 照实报
"没验"，不谎称验过）。

然后**直接写** —— 没有 `extern!`、没有 `effects`、没有链接参数：

```extc
use zlib::*
let rc = compress(dst.data, ref dlen, src.data, u64(64))
```

`extpkg build` 会给每个 vendored 包加 `-I vendor/<name>`，`.link` 由编译器读到时自动带上
（`pkgconfig zlib` ⇒ `-lz`）。判据 `tests/extpkg-system/`：`add zlib --all` → `use zlib` 的程序
`extpkg build` 后真跑 zlib 往返（`in=64 out=19 back=64 same=yes`）；不存在的包被明确拒绝；
没有 `pkg-config`/zlib 开发包的机器上整条跳过。

顺带修两处生成器的毛病：① `--all` 以前会把头文件 `#include` 进来的系统函数也卷进来
（`readlinkat`/`select`/`syscall`，于是"生成失败：`char *restrict` 映射不了"）—— 现在按 clang
AST 里的出现顺序跟"当前文件"，**只收请求的头文件里声明的函数**；② `--all` 时没法生成的形状
（变参、宏、按值结构体）不再让整次生成失败，而是写进产物头部注释的"没绑的形状"清单；
`--only` 仍然严格（点名要的绑不出来就失败）。

### 2026-11-17 · 用别人的 C 库：一条命令从头文件生成绑定（声明式 + 一条签字 + 链接要求）

以前"用别人的 C 库"要手写一堆 `extern!`，还要给每个函数补 `effects Addr=0 Cont=0`（否则调用方
连本帧的 `ref` 都递不过去）。现在 `tools/cbindgen.py` 多了一个 `--extern` 模式：

```bash
tools/cbindgen.py --include sqlite3.h -I vendor/sqlite \
    --only sqlite3_open,sqlite3_exec,... \
    -o proj/sqliteapi.extc --extern extc-sqlite --effects trusted \
    --link lib:sqlite3
```

产出三样东西，**调用方一行都不用写**：

| 产物 | 内容 |
|---|---|
| `sqliteapi.extc` | `extern!("extc-sqlite") fn …` 声明（`?ref void` 句柄、`?ref u8` 字符串、`i64`/`u64`…）|
| 同一文件的 `effects` | `--effects trusted` 时每条一条签字：`Addr=0 Cont=0`，返回指针的再加 `Ret=0` |
| `sqliteapi.link` | `--link` 给的链接要求（`ccflag:` / `lib:` / `pkgconfig:`），`use` 它的程序自动带上 |

`trusted` 是**声明不是证明**：签的是"我不留你给的地址、不读走指针"，包的 claims 台账里应该有一条
判据去证伪它（`extpkg verify` 已经能跑这种判据）。不写 `--effects` 时一条都不生成 —— 不签 = 最坏
情况 = 安全的那一侧（这是 `cbindgen` 一贯的口径）。

顺带修掉一个真 bug：`effects` 的续读只认 `Addr` / `Cont` / `Thread`，**`Ret=` 写在末尾时 clause
提前结束**，后面的 `Ret` 被当成新的顶层声明报 `expected `fn`, `struct`, `type` or `let`/`var`,
found `Ret`` —— 生成器产的正是 `Addr=0 Cont=0 Ret=0` 这个顺序，于是一生成就编不过。现在四个名字
任意顺序、任意位置都行；判据 `tests/cabi/effects_order.extc`（`Thread=0 Addr=0 Cont=0 Ret=0`）。

变参（`...`）**不出绑定**：extC 的调用是静态的、参数个数编译期固定，生成器把它列出来并非零退出，
不猜、不静默丢 `...`。

**调用开销实测**（这条决定 C ABI 的取舍）：`extern!` 生成的是**直接的 C 调用** —— 生成的 C 里
就是 `acc = cadd(acc, i);`，没有表、没有 thunk、没有 `dlopen`。20M 次循环（`taskset -c 2`）：
同 TU 内联的 extC 函数被优化到 0，`extern!` 调外部 TU 的 C 函数 **+0.34 ns/次**（就是一条
`call`+`ret`）；跨 TU 想连这条 `call` 也消掉需要 `-flto` 且库也带 LTO 信息（带 LTO 加 `-flto`
编译这套微基准测到 0.27 ns/次，仍未内联 —— 静态库本身没有 LTO 信息）。

所以 C ABI 的口径是 **快 + 方便**，安全做到"防错不防敌"（`C-ABI.md` §9.17）：
`plate` 的守卫页/末端对齐（让越界当场 `SIGSEGV`）**不做** —— 它挡的是"正常库写越界"，而每缓冲
一页虚拟地址的代价与"高效"直接冲突；真要跑不可信库，只有独立进程隔离这一条路。

判据：`tests/extbind/run.sh` 5/0（形状 · `--check` 幂等 · 真编一个 `libdemo.a` 并调通
`sum=42 count=1` · `.link` 由生成器写出 · 变参被拒）；`tests/cabi` 全绿（含新的 effects 顺序）。

### 2026-11-14 · `impl` 挂在泛型实例上：视图的方法与运算符也能找到

`impl slice<u8> { fn firstByte(self: ref slice<u8>) -> u8 { … } }` 以前**能通过检查、但调用点找不到**：
`arr[..].firstByte()` 报 `no method \`firstByte\` on \`slice<u8>\``。原因不是方法没挂上，而是视图类型
有**两个表示**：`new u8[n]` 造出来的是只读实例的**可写影子**（`ttViewMut` 建的 `slice<mut T>`，
与 `slice<T>` 共享 C 名字和布局、不在实例表里），而方法集挂在只读实例的 holder 上。影子查不到。

修法是让"影子"按定义共享方法集：`src/types/typelayer.c` 新增 `static StructDef *methodHolder(Type *st)`
（先看 `st->mholder`；`st->mut && st->inner` 时退回 `st->inner->mholder`），`findMethod` 与 `findOperator`
都走它。运算符还得放开两处"接收者/返回值必须就是声明类型"的判据（`src/types/typelayer.c` 的右操作数
匹配、`src/check/check_escape.c` 的返回类型与左操作数）：`impl slice<u8>` 的 holder 不是 `slice` 的
结构体体，且 `mut` 是权限不是身份，因此比较前两侧都用 `ttViewReadonly` 规范化。

顺带：`impl [8]u8` 的报错从 `expected a type name after \`impl\`, found \`[\``改成规则说明 ——
`` `impl` cannot extend a fixed array `[N]T` ``（定点数组是形状，没有方法集可挂）。

判据：`tests/impl/view_methods.extc`（`a=7 b=3 eq=true sum=6 fill=65`：只读视图与 `new` 出来的

### 2026-11-13 · 默认参数：省略的尾部实参在调用点补齐

`fn scale(n: i64, by: i64 = i64(2), plus: i64 = i64(0))` 现在可以写 `scale(15)` 或
`scale(3, 1)`；方法、关联函数、泛型函数同样支持。**没有动调用约定**：省略的实参在检查器里
被补成一棵克隆的常量表达式，代码生成照旧把实参传满 —— 生成的 C 与"用户自己写全"一致。

为什么是"检查器补齐"而不是"被调方默认值"：extC 的函数调用一直是静态的、参数个数编译期
固定；在调用点补齐保持了这条性质，也让默认值不必进函数体、不必成为 ABI 的一部分。

三条声明期规则：① 默认值必须是编译期常量（字面量，或它的一次转换/取负）——它会被复制进
每个省略它的调用点，读不到被调方的局部变量；② 默认值必须形成后缀（`fn f(a: i64 = i64(1),
b: i64)` 报 `parameter `b` comes after a parameter with a default value, so it needs one
too`）；③ `self` 与 `extern!`/`@builtin` 声明不能有默认值。

判据：新套件 `tests/defaults/`（12 项：省略 0 个/部分/全部实参、方法、泛型、关联函数、

    二分 0.78–3.6 ns；
  - 代码体积：8 类型 × 6 字段，每类型手写打印 13.9 KB → 描述符表 + 一份 walker 1.2 KB + 1.7 KB 表。

语言侧实测（同一套代码、`taskset -c 0`）：内联装箱+拆箱 ≤8 字节 **0.59 ns**；16 字节结构体装箱
**5.4 ns**（大头是分配与缺页，一千万次 = 160 MB 留在 region）；动态派发 ≤8 候选 **0.9 ns**
（热循环常被内联成直接调用）、12/40 候选 **2.0/4.0 ns**；静态调用 ≈0。

**没做的那一项**：描述符里的 `id` 与"动态方法表"——派发最终用"候选描述符地址排序表 + 二分"，
同样拿到 log 复杂度且不必在描述符里存函数指针或名字；只有候选 >100 时换成真 id 跳表（0.36 ns）
才划算。装箱分配复用也没做：`any` 的拷贝是**共享同一个箱子**（16 字节值拷贝），改一个不会改另一个，
但也就没法安全复用旧箱子——那需要引用计数给出"最后一个拥有者"。

### 2026-11-11 · `std::reflect`：把描述符当数据读（JSON / 类型名）

`any` 里装的类型只有运行期知道，所以"读它"必须走描述符。新增 `stdlib/std/reflect.extc`：
`reflect::json(ref v, out)` 按字段/变体表递归编码成 JSON 写进调用方缓冲（返回**需要**的字节数，
可以先问长度再写），`reflect::typeName(ref v, out)` 拷出类型名。两者都是运行期 extern 的薄包装
（`extc_any_json` / `extc_any_type_name`，带 `effects Addr=0 Cont=0`），实现在 `any` 运行期块里，
复用打印器那张表：不分配、不在用户代码里递归，深度上限 32 层。

编码细节：`ref`/`?ref` 字段编成 `null`（不跟进去，安全性归深度检查）；枚举编成变体名；`slice<u8>`
当文本转义（`\"`、`\\`、`\n`、`\t`，其余控制字符用 `\u00XX`）；定长数组与其它视图编成数组。

顺带修的路障：`extern!("extc-runtime")` 的声明必须与运行期定义**链接属性一致**（`static` 定义对不上
extern 原型），且 `ref any` 实参在 extern 处会被当成"C 可能永久保存"而拒绝 —— 这两个都是写运行期
extern 时的一般性注意点，前者报 `static declaration follows non-static declaration`，后者报
"may be kept by C forever"。

判据：`tests/any/reflect_json.extc`（嵌套结构体 + 文本 + bool ⇒ 逐字节 JSON、`type=rec`、标量 `7`）；
`tests/any` 10/0。

### 2026-11-11 · `any`（第四批）：候选多了就二分，不再线性扫

候选 ≤8 个时派发器是一串 `if (__t == &T_desc)`；超过 8 个改成**排好序的查找表 + 二分查找 + 按命中
下标跳转**。排序在第一次调用时做一次（描述符地址链接期才定，编译期排不出序），之后每次只比地址。

成本实测（20M 次、两条运行期才能决定的类型交替、`taskset -c 0`）：4 个候选 0.69 ns/次、8 个 0.11 ns/次
（被内联成直接调用）、12 个 2.02 ns/次、40 个 4.03 ns/次。C 原型里对照的线性链是 16 个 2.7 ns、
64 个 9.2 ns、256 个 25.3 ns ⇒ 候选一多，二分把成本从 O(n) 拉回 O(log n)。

**顺带修的两个真问题：**
  - 派发器里引用的描述符没人登记。`descRef` 是"登记待发射"的副作用，而派发器在描述符区**之后**
    才发（它要调 `extc_any_box`，得等 any 运行期先出现）⇒ 候选类型的描述符从来没被发出来
    （`s1_desc undeclared`）。新增 `collectDynCallDescs`，在 `emitDescRegion` 之前把所有派发站点的
    候选类型与返回类型登记一遍。这个问题只在"某类型除了被动态派发之外没有任何其他用途"时才露头，
    所以前一批的 2 类型测试没抓到。
  - `ExtcAny` 的载荷原本是个 union（`small[8]` / `box`），整值拷贝后再按具体结构体读，GCC 的
    `-Wmaybe-uninitialized` 在 `-Werror` 下直接拒编。改成单个 `uint64_t u`（装箱时存指针位、内联时
    存字节），派发分支里把 payload `memcpy` 进一个具体类型的局部再传地址 —— 不再做指针强转，
    代价是每次派发多一次几字节拷贝。

判据：`tests/any/dyn_wide.extc`（12 个类型各自 `area()`，`acc=156`）、
`tests/any/dyn_wide_missing.extc`（11 个类型有 `area`、`plain` 没有 ⇒ 编得过、运行期
`trap: no `area` for a `plain``）；`tests/any` 9/0。

### 2026-11-11 · `any`（第三批）：装箱即拥有（视图深拷贝）

`var v: any = buf[..]` 之后改 `buf`，箱内还是旧字节 —— 装箱把**视图指向的字节**也复制了一份。这是
"`any` 拥有它装的值"的实现：值 ≤8 字节且不含视图时直接存在 `any` 里（零分配）；超了就复制到 arena；
含视图时把被指向的字节也复制过去。装进去之后再改来源，箱内不变（`tests/any/own_payload.extc` 的
`snapshot=ABCD live=ZBCD` 钉住这一点）。

**必须编译期知道要不要深挖。** 深拷贝的判定从**静态类型**算出来（`typeNeedsAnyDup`：视图、数组、
含视图的结构体、枚举 —— 保守取真），作为常量参数传给 `extc_any_box`。于是"memcpy 就够"的程序保持
原来的快路径（纯标量 ≤8 字节装箱 ≈ 0.6 ns），只有可能含视图的类型才走 `extc_any_fixup` 的逐字段
改写。这条判定要是放到运行期按描述符猜，所有装箱都会变慢。

`extc_any_fixup` 按描述符递归：结构体走字段表、定长数组走元素、视图（两个机器字的
`{data,len}`）分配新缓冲区并改写指针、`ref` 保持浅拷贝（它是否安全由既有的深度检查负责 ——
带引用的结构体从函数里返回会被拒，实测报 "would hold a reference to a local variable that dies
first"）。深度上限 32 层，超了原样保留（环不会被无限展开）。

代价：装含视图的值每箱两次分配。实测 16 字节结构体 + 16 字节视图 ≈ 25 ns/箱（大头是分配与缺页），
所以文档 §3.9 写明"热循环里别反复装箱"。

判据：`tests/any/own_payload.extc`（快照语义）；既有 6 项 `tests/any` 与 377 项 `tests/run.sh` 全绿。

### 2026-11-10 · `any`（第二批）：按类型的动态方法调用

`v.area()` 里哪个 `area` 跑，由 `v` 运行期持有的类型决定。编译期不为它解析 `FuncDef`：调用点被标记成
动态调用，代码生成在**每个调用点**发一个派发器 —— 按描述符比较的一串 `if`，命中就取出 payload、
直接调那个类型的真方法、把返回值装箱；一个都不命中就 trap 并说出类型（`trap: no `area` for a `line``）。
没有函数指针表，所以不会调到"从没生成过"的函数。

**为什么编译期只查名字存在。** 名字要在程序里存在，否则没有任何派发器可能命中；但**签名与歧义推迟到
运行期**。按签名在编译期判歧义看起来更严格，实际会让"加一个同名重载"把已经编过的程序变成编不过 ——
单调性（加类型不破坏已有程序）是这条特性的硬约束，所以不这么做。

**路上修的两处。** ① 候选方法必须**全部** `planSetUsed`：可达性剪枝会删掉"没人按名调过"的方法，而动态
调用点不是静态调用点；只标第一个候选会让派发器调到未生成的函数（`implicit declaration of
`circle_area``）。② 派发器比较的是**接收者**的描述符（`descRef(g, sd->type)`），不是方法自己的名字。

**判据。** `tests/any/dyn_method.extc`（同一槽先后装 `box`/`circle`，各自的方法各跑一次，`a=12/a=12/k=2`）、
`dyn_method_missing.extc`（程序编得过、运行期 trap 说没有这个方法）。

**v1 限制。** 动态调用不能带实参；候选只覆盖普通结构体（泛型实例的方法暂不参与）；返回值类型是 `any`，
由调用方按需拆箱。

### 2026-11-10 · `any`：类型只在运行期知道的值（第一批：装箱、拆箱、打印、相等、容器）

`docs/usage/language.md` §3.7 记录了规则。为什么现在做：`docs/archive/DESIGN.md` 的决定表把
「无 `any` / `interface` / 反射」留在 **"v0 没写，补上"** 那一栏 —— 是欠的账，不是否决。

**结构。** `any` 16 字节（与 `slice` 同宽）：描述符指针 + 内容。8 字节以内且无引用的值直接内联，
其余在创建它的 arena 里拷一份。描述符是编译器早就在发的 `ExtcDesc`（调试打印与结构化 `==` 用它），
所以 `any` 不需要新的运行期机制：打印是 `extc_print(payload, type)`，比较是 `extc_eq`，`any` 只是把
"类型"从编译期挪到了值里。inline/boxed 这个二选一藏在描述符指针的最低位（描述符对象对齐，位是空的），
于是值仍是 16 字节而不是 24。

**隐式转换。** 装箱（具体类型 → `any`）无损，走既有"只隐式加宽"的口径；拆箱（`any` → 具体类型）是
extC 里**唯一一条可能运行期失败的隐式转换**：上下文要 `T`、值里不是 `T`，就在**那一行** trap，报文
说明两个类型（`this `any` holds a `i64`, not a `string$string``）。不静默重解释字节、也不做"尽力转换"。

**判据。** `tests/any/`：装箱与拆箱、换类型（`i64` → 字符串，走 arena 拷贝）、函数返回 `any` 再拆成
结构体、`any == any`、`varArray<any>`、空槽与类型不符的 trap（程序编得过、运行期停在本行）。

**路上修的两处。** ① 装箱要一个能跨帧的 arena ⇒ 装箱点按 `new` 的同一机制登记进 `curArenaSites`
（`planSetArenaLevel(ARENA_HOME)`），`REACH_USES_HOME` 闭包给函数加 `__extc_home` 形参；否则
`fn f() -> any { var s = "abc"  return s }` 的拷贝随帧死掉。② `desc->size` 不是值的字节数（byte view
的描述符 size 是元素大小 1）⇒ inline/boxed 由发射点传的 `sizeof(<T>)` 决定。

**还没做。** 按类型的动态方法调用（`v.area()`）、`reflect::*`、JSON 编码、拥有引用字段时的深拷贝。

## 2026-11-10 · 生成的 C 在 `-Wall -Wextra -Werror` 下不再报两处警告

症状。拿严格警告编产物，两个形状稳定报警：① **每个**区间循环都带一个没被用到的标签
`__extc_forstep_<id>`（`-Wunused-label`）—— 标签是给 `continue` 跳的，给"一步走到尾"的循环发
等于白写；② `par` 语句的调用被包成 `((int32_t)extc_par_run(...));`，一个值表达式当语句用
（`-Wunused-value`）。这两条对语言本身无害，但用户如果拿 `-Werror` 编产物就得自己关警告，
而"extc 生成的 C 编不过"这种报告最难查。

结构。① 循环表新增 `loopStepUsed`（与 `loopStep` 同长、随函数分配）：发 `continue` 的 `goto`
时置位，发标签时查它 —— 没有 `continue` 跳过去的循环一个标签都不发（有 `continue` 的照旧，
`continue` 仍要跨过步进这一点不变）。② `par` 的调用不再套 `(int32_t)` 转型，直接把
`extc_par_run(...)` 当表达式发 —— 语句位置是普通调用（不算未用值），值位置（`parallel::run`
当 `i32` 用）靠隐式转换。同时 `parallel::run(...)` 作为值出现在表达式里这一点也补了判据。

判据。新增套件 `tests/cgen/`：`for_no_continue` 产物里 `__extc_forstep_` 出现 **0** 次；`for_continue`
（嵌套 + 外层各一个 `continue`）输出 `42 3135` 且标签照发；`par_forms` 两种写法输出 `992 140 0`；

`通过 2，失败 2`（标签与 `par` 各一条）。`tests/lambda` 的 `withrc` 判据也顺带在同一个严格
警告档下编了闭包产物。

## 2026-11-10 · 闭包与回收运行期同框的判据

症状。闭包那几套形状（`[mut ref]` 捕获、按值捕获引用、泛型体里按实例布局的环境、`dyn` 载荷）
此前只在**不带回收运行期**的程序里被测过：`tests/lambda` 全语料产物里 `extc_rc_` 出现 0 次，
也就是说"闭包和回收同时存在"这件事没有任何判据。它并非显然：环境是一个结构体，被捕获的引用
住在它的字段里，泛型体里那份环境还是按实例布局的克隆 —— 克隆出来的字段要不要进根表、模板那份
不发射之后根表还认不认得它，都不是"能编过"能证明的。

结构。新增 `tests/lambda/rc_closures.extc` 与 `rc_env_refs.extc`：前半段是让回收运行期必须
出场的形状（堆槽里装引用、每轮覆盖，`cyclic` 类），后半段叠上三种闭包；`rc_env_refs` 更进一步，
被捕获的值结构体里就装着引用。`tests/lambda/run.sh` 新增 `withrc` 判据 —— 产物里 `extc_rc_` 必须
非零（否则这条测的是空壳）、默认档与 `EXTC_RECLAIM=0` 的输出必须逐字相同、再比期望串。

判据。`rc_closures` 输出 `1225 2 7 13`（rc=785 处调用），`rc_env_refs` 输出 `1225 507 507`
（rc=791 处）；两者在 `EXTC_RECLAIM=0` 下逐字相同，ASan+UBSan 干净。顺带确认 `tests/lambda`
的既有语料仍然一个 `extc_rc_` 都不发射 —— 本特性没有把回收运行期拖进"本来不需要它"的程序。

## 2026-11-09 · 泛型体里的 lambda 按实例布局环境

症状。泛型函数体里的 lambda 只要捕获了"类型依赖类型参数"的值，产物就编不过：环境结构体只在
模板上布局一次，字段类型停在 `T`，代码生成把它渲染成 `int`，到实例里初始化式却是 `key` ——
`cc` 报 `incompatible types when initializing type 'int' using type 'key'`。检查期当时直接把这种
形状拒掉了，于是"泛型代码里用闭包"要么绕开捕获，要么先把值折成具体类型。

结构。lambda 的环境结构体与它的 `call` 方法现在可以**按实例各有一份**：检查器不再拒绝这种捕获，
只记下环境属于哪个函数模板；四个延迟检查的回放循环（运算、方法、延迟使用、引用）在遇到"记录时
所在的函数是某个 lambda 的 `call`"时，用那个 `call` 所属模板的实例去回放，于是 lambda 体里的
方法调用按实例检查。代码生成新增 `LamVar`：一个 `(环境, 实例)` 一份布局，名字带实例后缀，
结构体定义随其它类型单元一起发，`call` 方法与按需的 thunk 单独发；模板那份环境与 `call` 不再
发射。只有"字段或方法签名依赖类型参数"的环境才走这条路，普通闭包仍然一份布局。

顺带修掉一个既有缺陷：`markUnusedParams` 把 `EXTC_UNUSED` 插到"发现顺序"的偏移上，而插入点
的发现顺序不是它在文本里的顺序（先发的原型可以对应后发的函数体），插入会让后面的偏移整体错位
—— 表现是属性落到**另一个参数**上：真正被用到的参数被标成未使用、真正未使用的没被标。现在
插入点先按文本顺序的倒序排好再插。这条在 `-Wextra -Werror` 下才会暴露，正是本例的
`__extc_home_zone` 用的位置。

判据。`tests/lambda` 35 项全过：新增 `generic_capture`（`17 8 46`：两个实例各自调用自己类型的
`hash`，同一个泛型函数里两个不同的 lambda）、`generic_capture_missing`（负例：实例缺方法时报
`` `calc_plain` needs `plain` to define `hash` ``，不再静默成 0）、`generic_capture_dyn`（负例：
捕获类型参数相关值的闭包仍不能进 `dyn`，理由是"一份载荷对多份布局"）。泛型结构体方法里的同形
写法也验证过（`box<key>::run` 与 `box<item>::run` 各自正确）。`tests/run.sh` 377/0，
`smoke` 16/0，`docs` 13/0。

## 2026-11-06 · 可调用的值（一）：捕获不到的 lambda 就是裸函数指针

症状。`fn(i64) -> i64` 类型的参数只能接到"从 `ref void` 转出来的代码指针"，任何 lambda 字面量
放进去都报 `initializer expects `fn(i64) -> i64`, found `fn(i64) -> i64`` —— 两个类型名一模一样，
读者无从判断差在哪。闭包能就地调用、也能交给泛型参数再 `call`，唯独不能直接放在函数类型的位置
上，于是"把行为当参数传"这件事只剩一条绕路。

结构。lambda 的值是编译器合成的环境结构体（捕获字段 + `call` 方法），`fn(...)` 是裸代码指针；
两者在**捕获集为空**时指的是同一件事。检查器在赋值、实参、返回值这些位置认这个形状：环境没有
字段、签名逐参相同，就给字面量打一个"这里是函数指针"的计划位，代码生成据此发一个 **thunk** ——
和 lambda 自身签名相同的静态函数，把自己那份静态空环境交给合成的 `call`。空环境用静态哑变量而
不是空指针（它从不被读，但也不必传空指针），`cc -O2` 会把 thunk 内联，剩下的只有任何函数指针
调用本来就有的间接跳转。捕获集的形状单独报一句："捕获的状态要跟代码一起走"，并给出两条改法。

顺带修掉同一条路径上的一个静默缺陷：类型参数上的方法调用（`f.call(v)`，`f: F`）在模板期只记录
待实例化，**参数表达式没有被检查**，于是参数在生成的 C 里没有名字 —— 未使用参数的检查因此误报
"parameter `v` is never used"。现在模板期也检查这些实参。

判据。`tests/lambda` 22 项全过：新增 `fn_ptr_basic`（`42 7 9 8`：实参位置、两层嵌套调用、
`fn` 变量、`fn` 变量之间的赋值）、`fn_ptr_no_param`（`11`：零参）、`fn_ptr_capture`（负例，报
"but this lambda captures"）。`tests/run.sh` 377 项、`smoke` 16 项、`docs` 13 项全过；

## 2026-11-05 · 元素引用第一步：定长数组的元素是位置

## 2026-11-04 · `new T[n]` 进回收体系：视图的数据字是一条根

**症状** 循环外声明的变量接住 `new T[n]`，每轮一块，回收器看不见：生成 C 里一处

**结构** 视图不是引用槽，计数到不了它的数据指针，所以 `new T[n]` 的块一直留在帧里。改成三件

## 2026-11-04 · 循环里的 `??`／option／字面量包装：存储跟着目的地走

**症状** 循环里 `var a: buf = mkopt(one) ?? mk(0)` 每轮新增 1 MiB，内存随轮数线性涨；同一个
调用拆成两句（`var o: ?buf = mkopt(one)` 再 `var a: buf = o ?? mk(0)`）就不涨。`some(mk(...))`、
结构体字面量字段里写调用同样攒。文档里的 `ndarray<f64>::zeros2(r, c) ?? ndarray<f64>::empty()`
按五十轮 8 MiB 跑出 **411 MB** —— 这不是"帧是栈、只能从顶上退"的必然结果，`new T[n]` 的存储
本来就会跟着**存放它的那个块**归还。

**结构** 问题在调用点的 arena 参数：`??` 的左操作数是一个调用，`markCallHomeIfEscaping` 只认
`EX_CALL`/`EX_METHOD`，遇到 `EX_COALESCE` 直接返回，站点保持"待结算"；最后一轮结算一律塞
`ARENA_HOME`（函数体那一级），于是每轮的缓冲都活到函数退出。修法是三件事一起：目的地深度要
**穿过值流包装**传到调用（`??` 两侧、`try`、显式转换、`some(...)`/枚举负载、结构体字面量字段、
数组字面量元素）；记录下来的深度**只接受块内（≥ 2 层）**，并且站点留在待结算集合里，等一次
更晚的"逃逸"把它提回 home；结算时按记录的深度与 `usesHome` 一起决定，而不是无条件 home。
关联函数（`varArray::withCap`、`ndarray::zeros2`）**不进**早期 `needsHome` 判断：那是整程序
答案，检查函数体时可能已经读成"是"，而它的存储会被后面的 `return` 交出去 —— 提前判成"块级"
会让被调者的块随块退出释放、返回值悬垂（`wordcount` 一度输出 `words=7`，UAF 就在
`string::split` 里那次 `withCap`）。

**判据** `q1` 形状 **103.8 MB → 2.4 MB**（常数）；`ndarray` 惯用法 **411 MB → 9.6 MB**（约等于
一个 8 MiB 数组加开销）；拆两句的对照形状与 `wordcount` 输出不变（`words=12 lines=4 longest=7
first=the avg=4.00`）。新增 `tests/arena/coalesce-buffer.extc`：1024 轮、每轮三种包装各一个
1 MiB（合计 3 GiB），在 `run.sh` 的 150 MB 虚拟内存上限下**修前 `out of arena memory`、修后
`keep=3221225472`**。

## 2026-11-04 · 元素引用的设计页：三条设计、一张失效规则表

**症状** 语言里"看内容"有两套说法：帧存储借出视图（零拷贝），拥有身份的存储走句柄（`dyn`、
值池槽）。容器夹在中间：想让调用方直接读容器内容，唯一的路是拷一份出来 —— 循环里拷了只读一遍
就是"每次拷贝活到函数退出"（二十万轮约 52 MB）；读-改-写一条记录要两次探测加一次整值拷贝，
横评里唯一落后的那项差的正是这个。

**结构** 设计页把问题拆成三条按成本排序的路线：**稳定存储上的元素引用**（定长数组、帧内切片与
它们的视图，只放宽"对哪些位置可以取引用"，深度仍由存储所有者决定，不需要新概念）；**借用区间**
（可增长容器用显式作用域把"这段时间不换存储"说出来，区间内名字只能只读使用，名字级语法约束，
不需要别名分析）；**世代校验的元素引用**（引用自带存储世代，扩容即失效，失配响亮 trap，给
"确实要存下引用"的地方兜底）。明确不做 Rust 式借用检查 —— 别名照旧允许，并发仍由 `par` 的
"只写自己那一格"管。

**判据** 三条各自的落地判据写在页面末尾（能取读写引用的形状、必须拒绝的形状、区间内 `push`
必须被拒、扩容后解引用必须 trap）。本轮只交付设计与入口登记，实现按页面顺序开工。

## 2026-11-04 · `dyn` 的 payload：界是"这个位置里造过多少"，不是"同时活着多少"

**症状** 交接材料把"`dyn` 的对象表只回收槽、不回收字节"记成待修的高水位。实测下来它不是一个

## 2026-11-04 · 自己写板块底的容器：能力本来就在，缺的是样板

**症状** 内存模型那页纸把"自己写容器"写成待做：说板块能力只对内置容器开放、自己搓一个

## 2026-11-04 · 循环里换缓冲：编译器把保留陷阱指出来

**症状** 在帧里自己搓可增长数组时，有一个"行为正确、只是内存"的坑：缓冲声明在循环外、循环里

**结构** 检查器在赋值处看三件事：语句在循环体里（进入 `while` 体时记下该块的词法深度）；右边

## 2026-11-03 · `hashMap` 的值访问改走 dense 前缀：手柄留给逃逸的身份

**症状** 上一条把 `sessions` 的 1.52x 归到"两次探测 + 32 字节拷贝"，并据此加了 `entry`/`at`/`setAt`。
实测发现这个 API 方向本身就是反的：`at`/`setAt` 要先 `handleAtDense`（读 `slots` 数组 +
打包）再 `vals.get/set`（读 `ent` + 换代号 + 纪的三重检查），每次访问比"再探测一次桶"更贵 ——
`pool` 自己的文档就写着"热循环不要穿过容器，走 `atDense`"，而 `hashMap` 的值访问恰恰穿了过去。

**结构**

- `pool<T>` 加 `setAtDense(i, v) -> bool`：写 dense 前缀的第 `i` 个值，只做边界检查（`0 <= i < n`）。
  dense 下标命名的是**存储**，不是手柄，所以这里没有换代检查 —— 调用方若通过 `slot[b]` 或
  `gather` 拿到它，活性早已由那次探测确认。
- `hashMap<K,V>::get`：`find` 命中后直接 `vals.atDense(i64(slot[b]))`，不再 `handleAtDense` →
  `vals.get`（那是把同一个 dense 下标重新推导一次，再检查一个这次调用不可能错过的换代号）。
- `hashMap<K,V>::put` 的覆盖路径：`vals.setAtDense(i64(slot[had]), v)`。
- `remove`、`slotOf`/`at`/`setAt` 保持手柄路径：它们的入参或返回值是**逃出去了的身份**，
  换代检查正是要在那儿做。

**判据** `bench/realsvc` 的 `sessions` 轴（2,000,000 条，`taskset -c 0`，交错五次中位）：
`get`+`put` 走 dense **141.9 ms** 对 `entry`+`at`+`setAt` **176.3 ms** 对修复前手柄路径
**185 ms**；checksum 不变（`cs=16199615779603620825 retained=47881 liveoff=1856229`）。
`./tests/run.sh` 376/0、`tests/hashmap/run.sh` 与 `tests/stl/run.sh` 失败 0，
`bench/realsvc` 全量五轮后 `sessions` extC 140.0 ms 对 C++ 134.9（1.04x，此前 1.52x）。

**教训** 手柄是给"身份要离开循环"的地方用的；循环内部该用手柄已经解析好的那个下标。把一个
API 暴露成"更少探测"并不等于更快 —— 少一次哈希探测，可能换来两三次随机 load 和一次拷贝。

## 2026-11-02 · `hashMap` 把槽（handle）暴露成一等 API：读-改-写只要一次探测

**症状** `bench/realsvc` 的 `sessions` 轴里 extC 是 C++ 的 1.52x（202.2 ms 对 132.7）。变体隔离与
相位拆分把它归到"每记录两次哈希探测"：extC 的 map API 返回值，`get` 再 `put` 就是两次探测 +
两次结构体拷贝；C++ 的 `operator[]` 返回引用，一次探测、零拷贝。这不是实现质量差距，是 API 形状。

**结构** `hashMap<K,V>` 与 `hashMapI64<V>` 门面各加四个方法：

- `slotOf(k) -> ?handle`：一次 `find` 拿到值槽（`vals.handleAtDense(slot[b])`）；
- `at(h) -> ?V` / `setAt(h, v) -> bool`：按槽读写，不再探测；
- `entry(k, dflt) -> handle`：命中直接回槽、缺失先 `put` 再回槽 —— "取出来改一下写回去"的循环
  因此每记录一次探测。

handle 是池的**值**（槽号 + 换代号 + 纪），不是指针：值池扩容搬数据不会让它悬垂；键被
`remove`（swap-remove，搬最后一个元素）或池清掉之后 `at` 还 `none`，而不是读到别人的值 —— 这件事
由池的换代检查兜住，不需要调用方记账。

**判据** 新增 `tests/hashmap/handle.extc`（`entry` 缺失插入 / 命中不覆盖 / `at`+`setAt` 累加 /
插 200 个别的键后老槽仍有效 / 键被删后 `at` 还 none / `contains` 在带 `slice` 形参的函数里可用，
`// expect: sum=14 n=2 same=true stale=true keep=true sixth=true`）：修复前编不过（effects 摘要不完整，
见上一条），修好后全绿。`tools/manual_surface.py` 重生成（公开面 823 → 831：新增 8 个方法）；
`docs/usage/stdlib.md` 的 map 表补两行并加一段槽的说明。`tests/hashmap/run.sh` 失败 0、
`./tests/run.sh` 376/0、`smoke` 16/0、`docs` 13/0。

**实测：探测次数不是 `sessions` 的瓶颈（把上一条的推测否掉）** 把 `bench/realsvc` 的 extC 臂改成
`entry` + `at` + `setAt` 之后，2,000,000 条记录的交错对比是旧写法（`get` + `put`）
`191.4 / 190.3 / 194.0 / 184.5 / 219.7 ms` 对新写法 `185.1 / 187.5 / 193.5 / 184.7 / 192.9 ms`
—— 差异在噪声内；callgrind 200k 子集上新的反而多 `10.6M` 条指令（`193.4M` → `204.0M`，`entry` 在
未命中时要"插入后再探一次"，而 `at`/`setAt` 各自带池的换代号检查）。分相位隔离给出真正的账
（2M 条，三次中位）：只解析 **~55 ms**、加 `entry` + `at` **~142 ms**、再加 `setAt` **~180 ms**
⇒ 探测与读 ~87 ms、写回 ~38 ms。也就是说 handle 化省下的第二次探测，被 32 字节 `session`
的"进/出拷贝 + 池间接"吃掉了 —— C++ 那边 `operator[]` 交出来的是引用，字段就地写。

结论：`handle` 作为货币是对的（值池扩容会搬数据，`mut ref V` 表达不了"到下次修改前有效"；
槽带换代检查，过期读还 `none` 而不是脏值），但它**不会**自动把值语义的拷贝省掉。要在热路径上
真正靠拢 C++，需要"就地改"的入口（借出 `mut ref V` 的块，且块内不许再碰这张表）或结构体数组
（map 存 dense 下标 + 平行的 `slice` 字段）。两条都还没做，记在这里。

**症状** 任何"接收视图参数、又调用 `hashMapI64::remove`（或 `contains`）"的函数都编不过：


   显式类型实参、`fn` 值类型）提到类型参数时**不下这个结论**，交给实例轮；模板自身的保守性由
   `mentionsParam` 那一族规则提供（`T` 可能带引用），`tests/errors/generic_borrowed_store.extc`

3. **过期闭包要作废**。`hashMapI64::remove` 与 `hashMap::find` 属于**不同**类型实例，实例表按创建序

1. **淘汰是"压缩"而不是原地擦除**：`hashMapI64::remove` 今天不能在"同时接收视图参数"的函数里调用。

## 2026-11-01 · 协程服务的性能：每请求一次 `send` 的代价

**症状** `bench/realsvc` 的 `serve` 轴（64 连接 × 8 深度、20 万请求）里 extC 只有 430k req/s，
同机 C++ 595k、Go 578k、Rust 565k —— 比 C++ 慢 39%，远超同一份 `RESULTS.md` 里其它三轴的差距。
但协程本身不像瓶颈：`callgrind` 用"两个请求数（5k 与 25k）的整轮指令数差分"算出每个请求
**1,059 条指令**，同一方法对 C++ 是 2,099 条 —— 用户态工作量 extC 只有 C++ 的一半。差别在系统调用：
`strace -c` 数 20,000 个请求，extC 发了 **20,000 次 `sendto`**（一条应答一次），C++ 只发 **2,560 次
`write`**（一次读到的请求攒起来一起回）。也就是每个请求多付一次 `send` 系统调用，20k 请求多 1.7 万次。

**结构** `bench/realsvc/extc/main.extc` 的 `conn` 协程改成"按读到的这一批回"：连接私有的 4 KB
应答缓冲 `rep`，`rn` 记已攒长度，每写一条应答前若剩余不足 40 字节就先冲一次，内层请求循环结束后
（即 `yield` 之前）把 `rn` 冲干净再等下一批输入。这样"单独到达的一条请求"仍然立刻应答 —— 冲在
等待之前，不在定时器上，语义与延迟不变；批量到达的应答只花一次 `send`。`SPEC.md` §5 补了一条口径：
写策略由各臂自己定，但必须保序、且单独到达的请求不必等下一批。`run.sh` 的 `serve` 改成**按臂交错**
重复（每轮四臂各跑一次），让机器漂移不偏向某一臂的均值。

**判据** 四臂 checksum 与 `bad=0` 全部不变；`strace -c` 20k 请求的系统调用从 **1.16 次/请求**
降到 **0.30 次/请求**（`sendto` 20,000 → 2,536，`recvfrom` 2,597，`epoll_wait` 706）；7 次交错重复
的中位吞吐 extC **430k → 559k req/s**（11 次按臂交错测量：C++ 558k、Go 558k、Rust 568k —— extC
与 C++ 落在同一个数上，从 `0.72×` 到 1.00×），`RESULTS.md` 的并发表与 `README.md` 的首轮摘要同步更新。
方法备注：`callgrind_control -z` 清零后归因会塌缩成 `__libc_start_main` 一条，不能用；perf 的硬件
计数器在 WSL2 不可用（`<not supported>`），`cpu-clock` 软件事件只到用户态符号，所以"指令数差分 +

## 2026-11-01 · `io::flushCout()` 不冲刷：stdout 变成文件/管道时输出卡到进程退出

## 2026-11-07 · 可调用的值（二）：闭包放进 `dyn`，`impl` 由编译器补

**问题**：`fn(...)` 指针只能携带代码，闭包携带代码 + 环境，二者是不同的值。要"一个容器装不同的闭包"，需要一个 erased 的可调用值 —— 而 `trait` + `impl` + `dyn` 本来就能表达这件事，问题是闭包的环境类型由编译器合成，用户**写不出** `impl SomeTrait for $lam$…`，于是闭包永远进不了 `dyn`。

## 2026-11-07 · `dyn` 载荷的安全边界：含引用的值也不能当闭包的捕获

**问题**：上一节让"捕获按值拷贝的标量/结构体"的闭包可以进 `dyn`。但"按值拷贝"不等于"自足"：一个结构体里可以含 `slice<T>` / `ref T`，拷贝结构体只拷了指针，载荷一旦离开该帧，派发读的就是悬垂内存 —— 而 `dyn` 值是 `{pool, slot, generation}` 句柄，生命周期分析看不到载荷内部的指针。

## 2026-11-08 · 修复：把 lambda 字面量直接当泛型实参时类型参数推不出来

**问题**：`apply(fn(x: i64) -> i64 { return x + k }, 0)` 报 `argument expects `fn(i64) -> i64`, found `fn(i64) -> i64`` —— 两个类型名看起来一模一样，因为诊断把 lambda 的环境结构体也渲染成用户写的签名。实际上 `F` 被绑到了**另一个** `$lam$` 环境类型：调用点的实参表在检查时把 lambda 检查了一次（生成 `$lam$main$0`），等被调函数的签名（可能带替换）再套到实参上时又检查了一次，于是生成了结构相同但**不是同一个类型**的 `$lam$main$1`，实参与从它推断出来的形参自然不相等。

## 2026-11-08 · 修复：泛型体里的 lambda 捕获“类型依赖类型参数”的值会生成编不过的 C

## 2026-11-16 · 检查器：视图还在用的时候容器不许改变存储

**问题**：`var s = v.view()` 之后再 `v.push(...)`，`push` 可能重新分配存储，`s` 就指向旧缓冲区。今天编译器一声不吭，`-fsanitize=address` 会报 `heap-use-after-free`（`extc_pool_resize_raw` 释放掉了它）。`varArray` 的注释里写着 "a lent-out view must not be used after growth"，但那只是规范，不是检查。

**结构**：`src/check/check_stmt.c` 新增"同块内的视图借贷表" —— 一个块里记下每个 `var x = container.view()` / `var x = container[lo..hi]` 绑定的视图，以及它借自哪个容器（`LiveView`/`LiveViews`，上限 16 个）。遇到 `push`/`append`/`grow`/`reserve`/`insert`/`shrink`/`release` 这类可能搬走或归还存储的调用时，若该视图**在这条语句之后仍被使用**，报

```
error: `v` changes the storage that `s` views
note:  a view is only good until the container moves its storage: copy what you need
       (`snapshot()`) or finish with the view before growing
```

视图在增长之前就用完、或视图活在内层块里，都放行（前者没读到旧字节，后者出块即失效）。检查器不认识具体库类型：判据只看方法名与接收者的名字，用的是语言层面的 `view`/`viewMut` 约定。

这是 `docs/design/TYPE-MODEL.md` §六那条"存储身份变了就失效"的静态那一半：把可静态判定的形状变成编译错误，剩下的动态形状等冻结位（`buf<T>` 带来的所有权计数）在运行期 trap。

**判据**：

- `tests/pin/view_grow_vector.extc`（反例：`v.push` 之后还读 `s`）；
- `tests/pin/view_grow_string.extc`（反例：视图在 f-string 里被读）；
- `tests/pin/view_ok_before.extc`（正例：增长前用完）；
- `tests/pin/view_ok_inner_block.extc`（正例：视图活在内层块里）；
- `tests/pin/run.sh` 4/0，接进 `tools/check.py` 的 `pin` 一项；`tests/run.sh` 377/0、`check.sh smoke` 16/0。

## 2026-11-22 · `drop x`：显式交还，之后这个名字就不再是值

**症状。** `@drop` 只有在块退出、覆盖、`return`、`break`/`continue` 时才跑。想在中间某一
行释放（读完文件、答完一个连接）只能手动调钩子，然后把块尾的那次交给"再调一次会不会
double free"的运气。

**结构。** `drop` 是一条**语句**，不是方法调用：它当场跑钩子，并把那个 place 标成死的，块
尾不再跑第二次。四种形状各有各的句子：不是名字（`` `drop` takes a variable name ``）、
类型没有钩子（``` `p` has no `@drop` method ```）、已经被 move 或已经 drop 过、以及容器还被
活着的视图借着（`` `b` is dropped while `v` still views it ``）。对被 drop 的名字赋新值会让它
重新可用。

**判据。** `tests/drop/` 17 项：`explicit_drop`（`before|drop 1|after|b=2|drop 3|drop 4|end|drop 2`
—— 显式的那三次在当场，块尾只剩没被显式 drop 的那一个）、`revive_after_drop`
（`drop 1|drop 2`，覆盖时不再对已经交还的旧值跑钩子）、反例 `drop_then_use`/`drop_twice`/
`drop_no_hook`/`drop_borrowed`。`tests/run.sh` 377/0、`check.sh smoke` 16/0、`docs` 13/0。

**顺带。** 视图闸门原来只认 `@poolObject`（编译器管的板块），`buf<T>` 这类库自己管板块的类型
漏在门外 —— 现在"有 `@drop` 钩子"同样算作 place，所以 `buf` 的"借出后增长/借出后 drop"都
在编译期拒绝。

## 2026-11-23 · `fn +=`：累加不再每轮造一个新值

**症状。** 字符串的 `s += t` 只是 `s = s + t` 的糖：`+` 必须返回一个**新**字符串，于是每轮都
分配一份、把旧内容拷过去，上一份存储留在原地成为垃圾。累加到 n 字节总代价是 O(n²) 时间加
O(n²) 垃圾 —— 200k 次追加（最终 12.6 MB）跑不完；同一形状用 `s = s + t` 写的探针在超时前
被 SIGTERM 杀掉。

**结构。** 复合赋值允许类型自己接管：`fn +=(self: mut ref string, other: slice<u8>)` 让
`x += y` 成为**语句级的就地写入**（不返回新值、不经过临时量）。钩子与 `+` 的重载集按右操作
数类型一一对应；没有定义钩子的类型仍按 `x = x + y` 脱糖，所以对既有代码零影响。检查器只把
"解析出的运算符名字恰好是 `+=`"当作钩子，其余仍是原来的算术检查。

**判据。** `tests/ops/compound_hook`（`total=6 buf=ab|cd|ef calls=3 n=5`：用户类型走钩子、
字符串走钩子、有 `+` 无 `+=` 的类型仍脱糖、内建整数仍是 C 的 `+=`）；同一探针 `s += t`
12.6 MB 追加 **3 ms / 13.9 MB RSS**，`s = s + t` 版本不收敛。`tests/run.sh` 377/0、
`smoke` 16/0、`tests/ops` 全过。

## 2026-11-24 · 冻结位的库级形式：`buf::borrow()`

**症状。** 编译器的视图借贷表只管同一个函数体：把视图交给别的函数、或者把容器借出去之后在
被调用的函数里 `push`，增长会把旧板块还给分配器，而手里的视图一声不吭地指向那块内存（ASan
在 `vector` 上抓到的 heap-use-after-free）。

**结构。** `buf<T>` 加一个 `pins` 计数，`borrow()` 返回一个 `@noCopy` 守卫：它持 `ref buf<T>`

`trap: this buffer is frozen by a live borrow`。守卫不拥有存储、不决定寿命，只让"改变存储身份"
这件事在运行期从静默错误变成确定性失败 —— 与越界、陈旧 `dyn` 句柄同一种失败方式。整个机制
在库里，编译器没有为它加一行。

**判据。** `tests/pin`：`borrow_freezes`（守卫活着、跨函数 `push` ⇒ trap）、`borrow_release`
（守卫离开作用域后增长恢复正常）。`tests/run.sh` 377/0、`tests/pin` 6/0、`tests/stl` 全过。
顺带修掉一个真 bug：`typeNeedsDrop` 把 `mut ref T` 字段当成拥有者，守卫结构体一出现就让产物
编不过（`box_release` 收到 `box**`）。

## 2026-11-29 · 池特权是承重的：实验记录与文档

**做了什么。** 试着删掉 `calleeMakesPool` 里"`@place` 类型的方法都算池站点"这条捷径（它让标签同时

## 2026-11-30 · 全局对象的 `@drop` 在进程退出时跑

## 2026-11-35 · 检查器：不带 `effects` 的 `extern!` 只把能携带引用的参数记成"可能被存"

## 2026-11-56 · `hashMap`：删除不再留墓碑，探测链当场把后面的条目挪回来

**症状**：删除频繁、活跃集稳定的表（会话表就是这样）会累积墓碑，而 `put` 的触发线只看"放得下放不下"，

每次删除都要走完整条簇 ⇒ 二次复杂度（20 秒未完成），所以 `hashI64` 的混合是有意的，不是保守。

## 2026-11-57 · 字符串：`appendI64` 不再造临时对象，短模式查找改走 `memchr`

**症状**：① 循环里 `s.appendI64(i)` 拼 100 万个数字要 94 ms，而写数字本身不过几毫秒；② `string::find`
扫 9 MB 找一个 11 字节的模式，200 次要 82–98 ms，C++ 的 `std::string::find` 只要 36 ms。

**结构**：① `appendI64` 原来先 `fromI64(v)` 造一个临时 `string` 再 `append` 它的视图 —— 每个数字一次
对象构造 + 长度计算 + 借用视图。改成把十进制位直接写进栈上 `[21]u8`，正序搬一次，再 `append` 一次。
② `extc_memFind` 原来一律走 `memmem`（两路 Crochemore-Perrin），它的主循环是标量的；短模式
（≤ 32 字节）改用 `memchr` + `memcmp` 循环 —— `memchr` 是向量化的，实测 29–37 ms 对 65–68 ms。
长模式仍走 `memmem`，那里跳表才挣得回来。

**判据**：`tests/run.sh` 377/0、`tests/stl` 全过、`smoke` 16/0、`docs` 13/0。实测（`taskset -c 6`，
min of 2）：`appendI64` 100 万次 94 → **7 ms**（C++ `to_chars` 11 ms）；`find` 200 次 9 MB 扫描
82–98 → **34–36 ms**（C++ 34–36 ms）；单字节 push 1000 万次 11 ms（C++ `push_back` 15 ms）。

**发现但未改**：`f"…{i}…"` 造 100 万行要 118 ms，同样内容用 `appendI64` 手工拼只要 **34 ms** ——
f-string 的值形式每次都会造中间 `string` 再拼接，多出来的 84 ns/行全在那些临时对象上。

## 2026-11-58 · `string`：补上 replace / erase / insert / rfind / count / 大小写

**症状**：`string` 只有 `find`/`contains`/`startsWith`/`endsWith`/`split`/`trim*`/`removeFront`，
"改一个已经有内容的串"基本没路可走 —— 想替换子串要么 `concat` 出一串临时值，要么自己拼
`subView` + `erase` 都没有。

**新增**（全在原地改 `self`，不造中间串）：`erase(lo, hi)`（删区间，返回删掉的字节数，越界夹边界）、
`insert(at, s)`（内联态就地挪、池态先 `grow`）、`replace(needle, with)`（等长时原地逐字节改写、

**判据**：`tests/stl/stringEdit.extc`（新增，单行输出逐字段对齐：替换次数 2/2/2、`erase` 5、插入两端、

## 2026-11-59 · 编辑器：语言服务器（诊断 · 大纲 · 悬停 · 跳转 · 补全）

**症状**：没有人愿意在纯文本里写 extC。编译器能在一瞬间把整个程序检查完、也能把错误
定位到行列，但那些诊断只以"给人看"的形式写在 stderr 上；编辑器既不知道错在哪，也不知道
这个文件里有哪些函数。于是每个语法细节都要靠编译一次来验证。

**结构**：编译器多四个查询开关，语言服务器只做 JSON-RPC 的搬运，不含任何语言规则 ——
所以编辑器里出现的错误和 `extc` 命令行给出的**是同一句话**：

- `--diagnostics-json`：每条诊断一行 JSON（`severity` / `file` / `line` / `col` /
  `message` / `note`），位置与人类可读形式一致（1-based、字节列）；
- `--symbols-json`：打印该文件的声明表（`fn`、方法、`struct`、`type`、全局、`trait`），
  只列这个文件自己的声明，不含预置模块与导入模块；
- `--check-only`：查到类型检查为止，不生成 C；
- `--source-stdin`：源码从 stdin 读，但**保留命令行给的路径作为文件身份** —— 这是
  "编译一个没保存的缓冲区"的关键：模块名与 `use` 解析都来自路径，写临时文件会改掉它们。

`tools/extc-lsp.py` 在这些开关上做 `initialize` / `didOpen` / `didChange` / `didClose`、
`publishDiagnostics`、`documentSymbol`、`hover`、`definition`、`completion`（击键去抖
250 ms；一次全程序检查 20–60 ms，够快）。`tools/vscode-extc/` 是 VS Code 客户端与语法
高亮：Windows 上的 VS Code 通过 `wsl.exe` 起服务器，并把 `file:///c%3A/…`、UNC
`\\wsl$\<distro>\…`、`vscode-remote://wsl+<distro>/…` 三种拼写翻成 WSL 路径（`paths.js`，
纯函数、可 `node` 直接测）。

**判据**：`tests/lsp/run.sh` 跑一次真实的 JSON-RPC 会话（`tests/lsp/drive.py` 起服务器）：
干净缓冲区 → 无诊断；把 `p.y` 改成 `p.zz` → 一条诊断，行号与 `no field` 报文对得上、
`note` 被拼进消息；`documentSymbol` 恰好给出本文件的 `fn area` / `fn main` / `struct point`
且不含预置模块的 `println`；`hover` 在**调用点**命中 `fn area`；`definition` 跳回声明行；
补全包含本文件符号与关键字；`didClose` 之后诊断清空；`node tests/lsp/paths.test.js` 覆盖
三种路径拼写。共 11 项。已注册进 `tools/check.py` 的 `nobench` 套件。

**已知短板**（写进 `docs/topics/LSP.md`，不假装）：编译器一次只报**第一个**错误；悬停与

## 2026-11-60 · 语法与库：让"每天都写的那几种写法"直接能写

**症状** 一批写法要绕：`"  x  ".trim()` 报 `no method 'trim' on 'slice<u8>'`（字面量是字节视图，
文本函数全是自由函数）；`struct P { x: i64, y: i64 }` 报 `expected a field name, found ','`
（字段用换行分隔，可结构体字面量又必须用逗号）；`io::println(42)` 报
`argument expects 'slice<u8>', found 'i32'`（内建 `println(42)` 却可以）；`(0 - 7).abs()`、
`assert(x > 0)`、`max(1, 2)` 都没有；`fn shrink(s: mut slice<u8>) { s.len = 1 }` 竟然编得过。

**结构**
1. **文本方法挂到字节视图上**（`stdlib/std/text/string.extc` 的 `impl slice<u8>`）：
   `trim/trimStart/trimEnd/split/find/contains/startsWith/endsWith/toI64/toF64/len/isEmpty`，
   全部转发给原有的自由函数（同一份实现、零拷贝）。`string` 上补同名 `trim/trimStart/trimEnd/split`。
   顺带修一个真 bug：`v[lo..hi]` 的基址是 `ref slice<T>` 时，codegen 把**指针**当结构体传给
   切片助手（`extc_sliceTo_slice_u8(v, …)`，`v` 是 `slice_u8 *`）⇒ 生成的 C 编不过。修在
   `src/back/codegen.c` 的 `genSlice`：视图基址是 `ref` 时补一次解引用。
2. **视图坐标只读**（`src/check/check_escape.c` 的 `requireMutable`）：`EX_FIELD` 的基址类型是视图
   就拒绝写入，报文给出替换写法（`v[lo..hi]` / `v.sub(...)`）。`mut slice` 管元素，不管坐标。
3. **结构体字段可用逗号**（`src/front/parser.c` 的 `parseStruct`）：字段与方法后面都接受一个可选
   `,`，与结构体字面量的规则对齐；换行分隔仍然有效。
4. **`assert` / `assertMsg` / `unreachable`**（`stdlib/prelude.extc`）：库里写，`@inline`，失败即
   `trap`（报文带文件与行号，判据见 `tests/ergonomics/neg_assert.extc`）。
5. **数字方法**（`stdlib/prelude.extc` 的 `impl i64/i32/u64/f64`）：`abs/min/max/clamp`、
   `i64::toF64`/`i64::toI32`/`i32::toI64`。
6. **`io::print` / `io::println` 就是内建打印器**（`src/check/check_expr.c` 的
   `isPrintBuiltinName` + `src/back/codegen.c` 的 `builtinNameIs`）：带模块名的调用直接走内建分支，
   于是 `io::println(42)`、`io::println(true)`、`io::println(f"n = {n}")` 与裸 `println` 行为一致。

**判据** `tests/ergonomics/`（8 项，已注册进 `tools/check.py` 的 `tests` 组）：字面量文本方法、
`string` 同名方法、字段逗号、数值方法、`assert` 通过、`io::println` 五种实参、`mut slice` 写 `len`
被拒、断言失败 trap 的报文。另：`tests/run.sh` 367/0 + 377/0，`smoke` 16/0，`docs` 13/0。

**顺带修的第二个真 bug** `impl slice<u8> { … }` 一旦存在，实例的**方法持有者**就盖住了
`slice<T>` 声明体里的方法 —— `cmd == "PING"` 立刻报 `` `slice` does not define `==` ``
（`tests/coro/statemachine.extc` 先红）。修法（`src/types/typelayer.c`）：`findMethod` /
`findOperator` 先查实例持有者、**未命中再查声明体**（拆出 `methodNamed` / `findOperatorIn`
两个小函数），于是 `impl` 是"加方法"而不是"换一套方法集"；判据
`tests/ergonomics/impl_adds.extc`（`eq=true len=3 trimmed=[ab]`）。

**代价** `io::println` 的实参不再要求是字节视图（内建打印器按静态类型分派，`string` 走 `.view()`，
其余走描述符打印器）；两次名字比较（`::` 与 `$` 后缀）是编译期的，产物不变。

## 2026-11-61 · 驱动器：`extc run` / `extc build`，项目不用再背参数

**症状** 单文件 `extc --run x.extc` 一直是零仪式的，但要一起编一个多模块项目，就得自己拼
`--build -o app -I vendor/a -I vendor/b --ccflag vendor/a/shim.c src/main.extc`：参数是
"构建描述"，却由人每次背一遍。单文件能用、项目用不动，是这套工具链最不现代的一处。

**结构** `--run` / `--build` 同一套机器前面加两个子命令拼写，并让"项目"变成约定：

- `extc run [<file> | <dir>]`、`extc build [<file> | <dir>]`；不给文件就等于"在当前目录找项目"，
  给目录就等于进那个目录找。纯 `extc`（没有模式、没有输入）行为不变：打印用法、退出 2。
- 入口发现顺序写死在 `findProjectEntry`：`src/main.extc` → `main.extc` → `src/main.extc` →
  `main.extc` → `packages.toml` 的 `[build] entry`。清单只认这一种形状（`[build]` 表里一行
  `entry = "<路径>"`），更复杂的需求属于 `tools/extpkg.py`，不是驱动器的职责。
- 找不到入口时**列出试过的每一条路径**，而不是只说"没有入口"。
- 裸 `--` 之后的一切原样交给被运行的程序（`extc run -- -m demo x`），这是让 `@module` 的
  运行时子命令能被直接驱动的关键；`--run` 以前根本无法传参数（多给的位置参数会报
  `only one input file is supported`）。
- `runArgv` 由 `binPath` 加透传参数组成，程序看到的 `argv[0]` 仍是自己的路径（`args.len` 里算一个）。

**判据** 新套件 `tests/cli/`（12 项，全部在临时目录里跑，不依赖仓库布局）：约定入口两种拼写、
`packages.toml [build] entry`（含非 `.extc` 的文件名，驱动器不猜扩展名）、目录参数、无入口时报错
列出路径、`--` 后实参含空格的透传、没写 `--` 时不传参、`build` 只出二进制且产物能跑出同样结果、
无参数仍是用法退出 2、旧 `--run` 拼写不变。已注册进 `tools/check.py`（`cli`，`tests` 组）。

**顺带统一扩展名。** 仓库里 24 个判据文件曾用 `.extx` 拼写（2026-11-04 起，无文档、编译器也不看
扩展名），而其余 940 个是 `.extc`；清单、文档、编辑器关联里还被抄成了"包内部源文件的拼法"。
现在统一为 `.extc`，入口约定也只认它：别的名字由 `[build] entry` 写明。

## 2026-11-75 · 池层级写成一条规则，并划出边界

上一笔把"这是不是调用"统一成了一个谓词；这一笔把**池层级本身**写成一条规则，并说明它的边界，
新增 `docs/design/POOL-LEVELS.md`：

- **规则 S（存储）**：把值存进层级为 `p` 的 place 要求 `level(v) ≥ p`。更深的值有两种前途 ——
  S1：它的站点可移动（字面量 / `new` / 体里建池的调用或运算符）⇒ 站点被降到 `p`，生成的 C 在
  `p` 里分配；S2：站点不可移动（从容器里读出来的值、局部视图）⇒ 拒绝。
- **规则 R（读回）**：按值读一个元素得到的值，层级是**容器的层级**，不是它当初那个绑定的帧深度。
- **三条义务 O1/O2/O3**：只有一个规则回答"能不能降"（`promoteInto2` / `lowerPoolSite`）；
  存储后记录的是**移动后**的层级；除了 `promoteInto2` 没有人能降层级（读出来的值永远不降）。
- **边界**：两条 open gap 各带复现器 —— G1（P1，**不漏**的反面）：循环内局部池里读出的值存进
  外层池被接受，读回是 heap-use-after-free（ASan 验证，`tests/zone/neg_pool_read_escape.extx`）；
  G2（假阳性）：`var s = …; k.insert(s)` 之后 `k.atDense(0)` 被拒（`tests/zone/pool_readback.extx`，
  `run.sh` 钉住"今天仍被拒"）。承诺写成一方向：**被接受的程序不会读已释放的池存储**，代价是拒绝
  一些安全的程序；G1 是唯一方向错反的形状，列为 P1。
- 判据 `tests/zone/`：`pool_forms`（五种调用形状一致）、`pool_readback`（G2 现状）、三条反例
  （循环内 `new` 视图、循环内定长数组视图、G1 复现器）。

## 2026-11-76 · 协程：被放弃的驱动结束它的任务

栈帧形式的协程（`for v in f(n) { … }`、`var c = f(n)` 不带标注）把帧放在调用者的栈上，
任务 id 由 `extc_task_begin()` 取得。结束任务只有一个门：驱动器的完成分支
（`if (!__r) extc_task_end(f->task);`）。于是**半途离开**的驱动 —— `break`、`for` 里提前
退出、帧被丢弃 —— 永远不结束任务，任务的 arena 与它的 place 就一直活着：

- 实测（`taskset -c 6`，`/usr/bin/time -f %M`）：协程体里建 1 KB 池时 N=2000 常驻 4152 KB、
  N=20000 27576 KB；把 pad 改 16 KB、N=20000 则 **327864 KB** —— 线性、无上界。
  协程体只含 8 字节标量时 N=2000 与 N=20000 都是 1864 KB ⇒ 帧本身不泄露，
  **漏的是任务的 place 与它名下的池块链**。
- 修法：块被离开时结束"这个块里的栈帧驱动"对应的任务。列表按块层级记（`CG.coroTaskAt`，
  与 `zoneMark` 同构），释放点在 `genBlockBody` 的探针分支与 `cgReleaseLevel` 两处发出
  `extc_task_end(__extc_czid<sq>);`。`extc_task_end` 幂等（`!extc_taskLive[id]` 直接返回），
  所以跑完的任务不受影响；一个块只发一次。
- 修后（同机同负载）：4852→1864 KB（N=2000）、27576→**2424 KB**（N=20000，1 KB 池）、
  327864→**2424 KB**（16 KB 池）。判据 `tests/coro/abandon_loop.extc`：50 个被 `break`
  放弃的任务跑完，`extc_pool_live()` 从 `before=0` 回到 `after=0`（修前是 `after=50`，
  先红后绿验证过）。
- 没覆盖的形状（记进 `docs/plans/TODO.md`）：**包装句柄**（`var h: coroutine<T> = f(…)`）
  的任务由 `extc_coro` 持有，句柄可以移动进更长寿的变量 ⇒ 任务该由**最后一个所有者**结束，
  不能由块决定。审计（`/tmp/poolleak/REPORT.md`）确认这是唯一仍泄露的形状（L1/L2），
  它的方向是"按整池粒度进回收"：以 `ExtcPool` 记录 + 它的整条块链为单位，用既有的
  `extc_rc_framePush` 根链标记可达的根 zone，未标记的 `extc_pool_zoneNewRoot` zone
  整体释放；那是一片独立工作，不在这一笔里。

## 2026-11-77 · 一个只观察的 place 层级分析（`EXTC_DBG_LVL`）

池层级的规则已经写成一条（2026-11-75），但"同一问题在别的写法上答案是否一致"没有独立
的第二个实现来对照。这一笔加一个**只观察**的分析：`src/check/check_lvl.c`，对每个"把值
存进 place"的调用点算出它认为的答案（`accept` / `reject`），与检查器当场的判定逐条对比，
只在 `EXTC_DBG_LVL=1` 时打印差异；不改任何诊断，不改一个字节的生成 C。

- **格**：`LVL_UNKNOWN`（⊤，参数与外部调用的结果）/ `LVL_NONE`（⊥，i64、字面量这类不
  占 place 的字节）/ 已知层级 0..64（0 = 帧之外，1 = 函数体，与 `c->scopes.len` 同号，
  越深越大）。值的 join 取 **max**（验收判据是 `argLvl <= placeLvl`，`if` 两支要按活得
  短的那支判）；**目的地**的 join 取 min（`h` 本来就这么算）。每个值另带 `movable`
  = "由新鲜站点产生，站点可以降到目的地"（规则 S1）。
- **实现照 `check_dataflow.c`**：256 个绑定 × 4 个字段、64 轮迭代、溢出位；28 个
  `ExprKind` 全覆盖并带 `/*@@all-kinds*/`（walker 棘轮仍是 23）。
- **语料对照**（`tests/` + `examples/` 1501 个文件，`EXTC_DBG_LVL=2` 会连"一致"的也打）：
