# 2027-01

## 2027-01-04 · buf 底盘的第二个制度（密排槽 16 B…64 KiB）+ 关掉「@noCopy 值从字段/元素里被静默拷出」

**症状。** 把小 `string` 迁到 `buf<T>` 的第一天就撞墙：`vector<buf<u8>>` 里放 20 万个 32 字节的 buf，
峰值 RSS 442,348 kB，运行期还 `trap: buf: cannot give the reservation back`；同样 20 万个 32 字节的 `string`
（池底，密排 slab）只要 18,372 kB。根因在底盘：buddy 的单位是 2 MiB 量子（`EXTC_BUF_QSHIFT 21`），`carve` 的
块大小是 `2^ord << QSHIFT` ⇒ **最小块就是 2 MiB**，小值也得占一个量子。

同一批探针还挖出第二个洞：无注解的 `let d = s[0]`（元素）与 `let d = box.b`（字段）会把一个 `@noCopy` 值
**按字节拷出来**，两份共享同一片存储、两个析构器各还一次 ⇒ 运行期 trap。带注解的
`let d: buf<u8> = s[0]` 一直会报错，缺的是无注解这条路。

**结构。**

- 运行期新增「密排槽」制度：每个 2 MiB 量子首 64 字节放 `ExtcBufSml {cls, live, free, next}`，槽地址 =
  `quantum + 64 + idx * cls`，类 `lg` 的槽 = `16 << lg` 字节（13 类，16 B…64 KiB）。同类量子挂在
  `smlHead[lg]` 链上，空闲链穿在槽首 4 字节；整量子空了才 `smlRetire`（先从类链摘掉再 `give`，buddy 的合并
  照常发生）。`extc_buf_release` 用 `extc_buf_smlClsAt` 分派两个制度；`extc_buf_discard` 对槽是空操作
  （槽与邻居共页，`MADV_DONTNEED` 会抹掉活槽）。
- 修掉 `extc_buf_slotReserve` 在 `extc_buf_nArena == 0`（一次都没切过块）时恒返回 NULL 的缺陷：取锁后先建一个
  arena，类链才有地方挂。
- 编译器：`check_escape.c` 导出 `ckRejectNoCopyCopy`，`check_stmt.c` 的无注解绑定在「不是名字」时调它 ——
  名字仍是转移（不误报），字段/元素是拷贝（报错）。
- 文档：`BUF-INVARIANT.md` 新增 §13（两个制度、量子的头、派发、`discard` 的例外）与 §14（取出来是拷贝，
  不是移动；就地读合法；`for d in v.view()` 是已知边界）；`TYPE-MODEL.md` §七补「只有名字能转移」。

**判据。**

1. `tests/bufrt/`（新目录，走仓库真实的发射口 `bufRtEmitRuntime`）：27 条判据 × `EXTC_BUF_MT` 0/1 两档全绿 ——
   20 万个 32 B 槽的地址空间 ≤ 16 MiB、`span` == 32、内容互不覆盖、全部归还后账回零；同类槽步长 32；
   单槽退还不牵连同量子其他槽；量子空了退回 buddy；槽上 `discard` 返回 0 且字节不丢；槽与 4 MiB 预留共存时
   账 = 6 MiB；131072 拒绝、65536 命中最后一类、预留起点不许当槽还；10 万次 40 B 周转账回原值。
2. C 级探针：20 万个 32 B 槽只占 8 MiB 地址空间（4 个量子），全部归还后 `live` 回 0。
3. 新反例 `tests/nocopy/errors/bind_field_copy.extc` 与 `bind_elem_copy.extc` 报
   `` `@noCopy`: it may not be copied by value ``。
4. 新正例 `tests/stl/buf_elem.extc`：`n=1 len0=3 live=4194304` —— 就地只读方法调用不产生第二份所有权。
5. `./check.sh nobench` 154 通过 / 2 跳过 / 0 失败；`tests/stl`、`tests/pool`、`tests/copy`、`tests/nocopy` 全绿。

> 未做：容器还没切到这个制度上（`buf.extc` 的 `withCap` 一律走预留，改双 regime 会让 `cap`/`moves` 的既有判据
> 全部变化，必须单独一轮配 `tests/stl` 全量验证）；`for d in v.view()` 需要"借出视图元素"的语义，属语言面。
## 2027-01-03 · G22：长串周转的峰值位移判据（XFAIL 棘轮，string 迁 buf 之后转硬判据）

**症状。** `string` 还在池上，值拷贝是「别名 + 世代号」：长串周转时池只还世代号、不还板块，于是峰值
随**构造过的总量**涨而不是随活集。这条性质没有量具守着 —— 上一轮只有 `bench/containers/` 的手工读数
（S2 的 5.8 / 9.9 / 18.2 / 34.5 / 67.3 MB 斜率表），迁完 `string` 之后没有东西会红。

**结构。**

- 新形状 `tests/gc-p0/src/leak_string_grow.extc`：连续构造 k 条 1 MiB 长串（每条 64 字节块 append 16384 次），
  每条用完即弃 ⇒ 活集恒为一条；`argv[1]` 是 k，stdout 是 `G22 k=… sum=…` 校验和。
- `tests/gc-p0/run.sh` 新增 `g22` 子命令（并进 `all`）：`timemax g22 4` / `timemax g22 16` 出峰值，
  `run_plain` 两档出 stdout/exit，`summarize.py` 新段判 `maxRSS(16) ≤ 1.5 × maxRSS(4)`。
- 判据现在是 **XFAIL 棘轮**：迁移前必须红（现有 3.154×），迁移后必须转 PASS；转绿时把它提成硬判据
  （与 G15 → 硬判据的提法相同）。

**判据。**

- 实测 `k=4 maxRSS = 5704 kB`、`k=16 maxRSS = 17992 kB`，比值 **3.154×**，两档 stdout 逐字等于
  `G22 k=4 sum=4194304` / `G22 k=16 sum=16777216`、exit 0 ⇒ 量具自身有牙（形状真的走到了长串增长路径）。
- `bash -n tests/gc-p0/run.sh` 与 `python3 tests/gc-p0/summarize.py --selftest` 均绿。

> 未做：`string` 本体还没迁（下一步）；G22 转 PASS 之后才提硬判据。
## 2027-01-02 · 容器所有权规则成文：拥有预留的值只能移动、拷贝显式 clone，并钉住 string 迁移前的 bench 基线

**症状。** `vector` 已经搬上 `buf<T>` 预留，但 `string` / `hashMap` / `map` 还在池板块上，它们的值拷贝是
「别名 + 世代号」：`var b = a` 是 O(1) 共享，代价记在内存上。`bench/containers/` 的 S2 形状量出这笔账 ——
16 条 4 MiB 长串顺序构造、活集恒为一条，峰值 RSS 却是 5.8 / 9.9 / 18.2 / 34.5 / 67.3 MB 随串数线性增长
（C++ 同一形状 11.7 MB），因为池只还世代号、不还板块。缺一条能照着做的规则：容器拥有预留之后，
「值拷贝」到底该是什么。

**结构。**

- 新 `docs/design/CONTAINER-OWNERSHIP.md` 把规则定成四条不变量：R1 拥有存储的值不可拷贝只能移动；
  R2 元素进容器是移动、容器逐元素跑 `@drop`；R3 没有预留的值（`i64`、`@value` 小结构体、SSO 区内的
  `string`）按值语义照旧；R4 容器要留存外来值时自己 clone，所有权不共享。文档同时否掉「四种容器都做成
  `@value` 深拷贝」这条备选路（静默 O(n) 与内存有界冲突、解决不了嵌套、与已提交的 `buf`/`vector` 规则不一致），
  并给出迁移顺序（`string` → `hashMap` → `map` → `place` → 删池）与每步判据。
- `bench/containers/` 增加三格 `string` 形状：S1 1000 万次 15 字节短串周转（SSO，不分配）、S2 16 条 4 MiB
  长串各 65536 次 64 字节 append、S3 8 MiB 串 clone 20 次（深拷贝）；各配一份逐行对应的 C++ 臂。
- `run.sh` 加 `--tsv` 选项（一次跑一种形状组不再覆盖 `RESULTS.tsv`），`--shapes` 支持 `s1,s2,s3`。

**判据。**

- S 三格三臂输出逐字一致；`--reps 5` 的 min-of-5：S1 35/36/32 ms（old/new/C++）、S2 22/23/40 ms、
  S3 19/19/23 ms —— `string` 还在池上，old 与 new 逐字相同，这三行是迁移后的验收基线。
- S2 的峰值 RSS 与串数 k 的表写进 `bench/containers/SPEC.md`：迁移后必须不再随 k 增长（目标 ≈ 2 × 单条活集）。
- 规则与判据都是文档与 bench，不动运行期，所以门禁只需 `check.sh docs`、`check_tree`、`check_changelog`。

> 未做：`string` 本体还没迁（下一步）；`hashMap` / `map` / `place` 的池引用仍在；`pStale` / `pPoison` 的用例
> 要等 `string` 迁移时按新语义重写。

## 2027-01-01 · 容器元素所有权：视图元素写入是移动，容器的 clear/shrink/release 逐元素跑 @drop

**症状。** 把容器存储换成 `buf<T>` 之后，容器的元素只能是"不拥有存储"的类型：`vector<vector<i64>>`、
`buf<buf<i64>>` 一实例化就被拒（`a view element cannot hold ...`），理由是元素存储是视图背后的平面数组，
写入只搬字节、不为那份拷贝跑 `@drop`，源名字再跑一次钩子就还两次。反过来，如果放行而不改钩子，
`pop` 出来的容器永远没人还（`?T` 的 `some` 载荷一条 drop 都不跑）。两条路都通向"容器不能装自己拥有
存储的值"，而 `string`/`hashMap`/`map` 迁 `buf` 全都卡在这一条上。

**结构。**

- 视图元素写入成为第五个移动点：源是普通名字时标死（与 `movedInto = "the callee"` 同族），临时量由容器
  接管；源是字段或另一个视图的元素仍然编译错误。检查器**不**在写入处标死名字（同一个名字可能在两条
  分支里各写一次，`linMap::put` 就是这样），标死由生成器按名字登记、块尾/形参收尾跳过 `@drop`。
- 两个库内部原语 `elemDrop<T>(view, from, to)` / `elemTake<T>(view, i)`（`isBufPrimitiveName` 第五、
  六个名字）：前者在语句前缀里逐槽跑钩子再 `memset` 清零，后者取值、清零、返回；元素类型没有钩子时
  发 `(void)0`，`buf<u8>::clear` 仍是 O(1)。
- `buf` 的 `clear`/`shrink`/`release` 逐元素 `@drop`，`pop` 改成"降 `n` → 撤引用边 → `elemTake`"；
  `clone` 改成逐槽视图赋值，于是元素拥有预留时它在实例化阶段被拒（不再拷出共享所有权的值）。
- `typeNeedsDrop` 与 `genDropValue` 认枚举载荷（`switch (v.tag)` + `case <类型>_<变体>:` + `v.u.<变体>._<k>`），
  `pop` 返回的 `?T` 不再漏。
- 按值实参成为移动：`take(a)` 把所有权交给被调函数，`a` 之后是死的（`errors/arg_twice.extc` 判第二次读）。
- 修掉两个真缺陷：方法实参的形参类型没有实例化（`pm->type` 还是 `T` ⇒ 移动没登记 ⇒ 同一块预留还两次）；
  无钩子元素类型的 `elemDrop` 早退返回 `0` 生成 `0;` 被 `-Wunused-value` 判错。

**判据。**

- `tests/stl/buf_own.extc`：`len=3 popped=1 n=2 poplive=6291456 clearlive=2097152 live=0`（移动进入只有
  一份预留、`pop` 移出后 `clear` 不多还、逐元素 drop 后账本归零）。
- `tests/stl/buf_own_clone.extc` 被拒（`a view element cannot hold`）。
- `tests/pool/rt_nest_promote.extc` 从反例改成运行期正例：`after=0 innerlen=2 v=20 bytes=0`。
- `tests/nocopy`：`move_arg` 正例 `taken = 0|after = 1`，`arg_twice` 反例报「was moved into `the callee`」。
- `tests/stl` 0 失败（含 ASan 全部干净）、`tests/copy` 5/0、`tests/drop` 19/0、`tests/pool` 0 失败。

> 未做：`string` 仍是池底 `@sharesStorage`，还没迁到 `buf`；`hashMap`/`map` 的元素所有权要等 `string` 之后；
> 视图元素写入的"移动后使用"不由前端拦（见 TYPE-MODEL §七 的边界段）。
