# 2027-01

## 2027-01-01 · 容器元素所有权：视图元素写入是移动，容器的 clear/shrink/release 逐元素跑 @drop

**症状。** 把容器存储换成 `buf<T>` 之后，容器的元素只能是"不拥有存储"的类型：`vector<vector<i64>>`、
`buf<buf<i64>>` 一实例化就被拒（`a view element cannot hold ...`），理由是元素存储是视图背后的平面数组，
写入只搬字节、不为那份拷贝跑 `@drop`，源名字再跑一次钩子就还两次。反过来，如果放行而不改钩子，
`pop` 出来的容器永远没人还（`?T` 的 `some` 载荷一条 drop 都不跑）。两条路都通向"容器不能装自己拥有
存储的值"，而 `string`/`hashMap`/`map` 迁 `buf` 全都卡在这一条上。

**结构。**

- 视图元素写入成为第五个移动点：源是普通名字时标死（与 `movedInto = "the callee"` 同族），临时量由容器
  接管；源是字段或另一个视图的元素仍然编译错误。检查器**不**在写入处标死名字（同一个名字可能在两条
  分支里各写一次，`linMap::put` 就是这样），标死由生成器按名字登记、块尾/形参收尾跳过 `@drop`。
- 两个库内部原语 `elemDrop<T>(view, from, to)` / `elemTake<T>(view, i)`（`isBufPrimitiveName` 第五、
  六个名字）：前者在语句前缀里逐槽跑钩子再 `memset` 清零，后者取值、清零、返回；元素类型没有钩子时
  发 `(void)0`，`buf<u8>::clear` 仍是 O(1)。
- `buf` 的 `clear`/`shrink`/`release` 逐元素 `@drop`，`pop` 改成"降 `n` → 撤引用边 → `elemTake`"；
  `clone` 改成逐槽视图赋值，于是元素拥有预留时它在实例化阶段被拒（不再拷出共享所有权的值）。
- `typeNeedsDrop` 与 `genDropValue` 认枚举载荷（`switch (v.tag)` + `case <类型>_<变体>:` + `v.u.<变体>._<k>`），
  `pop` 返回的 `?T` 不再漏。
- 按值实参成为移动：`take(a)` 把所有权交给被调函数，`a` 之后是死的（`errors/arg_twice.extc` 判第二次读）。
- 修掉两个真缺陷：方法实参的形参类型没有实例化（`pm->type` 还是 `T` ⇒ 移动没登记 ⇒ 同一块预留还两次）；
  无钩子元素类型的 `elemDrop` 早退返回 `0` 生成 `0;` 被 `-Wunused-value` 判错。

**判据。**

- `tests/stl/buf_own.extc`：`len=3 popped=1 n=2 poplive=6291456 clearlive=2097152 live=0`（移动进入只有
  一份预留、`pop` 移出后 `clear` 不多还、逐元素 drop 后账本归零）。
- `tests/stl/buf_own_clone.extc` 被拒（`a view element cannot hold`）。
- `tests/pool/rt_nest_promote.extc` 从反例改成运行期正例：`after=0 innerlen=2 v=20 bytes=0`。
- `tests/nocopy`：`move_arg` 正例 `taken = 0|after = 1`，`arg_twice` 反例报「was moved into `the callee`」。
- `tests/stl` 0 失败（含 ASan 全部干净）、`tests/copy` 5/0、`tests/drop` 19/0、`tests/pool` 0 失败。

> 未做：`string` 仍是池底 `@sharesStorage`，还没迁到 `buf`；`hashMap`/`map` 的元素所有权要等 `string` 之后；
> 视图元素写入的"移动后使用"不由前端拦（见 TYPE-MODEL §七 的边界段）。
