# 内存模型：寿命由"住哪儿"决定

> 状态：**当前口径** —— 这篇写的是现在的事实，改语义先改它。

> **基质变更注记（v38–v39）。** 池容器、池原语（`poolSlice*` / `poolResize*` / `poolGive`）与 `@poolObject` / `@place` 的容器用法已经从语言里退场：容器自己拥有的存储今天只有两种形状 —— `buf<T>` 的**地址预留**（`vector`、`string`）与 `block<T>` 的**平坦块**（`hashMap` / `map` / `set` / `linMap` / `linSet`）。下文出现的「板块」一律指「容器自己拥有的那段存储」，按这两种形状读；`dyn` 值住的是 place 的载荷区（`src/back/places.c`），不是池。

extC 没有 `free`，也没有垃圾回收器。`new` 出来的东西只可能住在三种地方，**住哪儿决定了它能活多久、也决定了用起来贵不贵**。选错地方不会编译报错，只会让内存数字看不懂 —— 这一页就是那张对照表。

回收机制本身（四层、什么时候才真正跑回收器）在[回收机制与待做](RECLAMATION.md)；日常说法在[内存回收：怎么回事](../usage/reclamation.md)。

## 一、三种地方

| 地方 | 形状 | 什么时候归还 | 适合 | 不适合 |
|---|---|---|---|---|
| **帧**（块自带的内存） | 一块一块往上摞的栈，分配只是挪指针 | 离开块时整片归还，保留一块备用 | 大小已知、只在块内活的临时数据 | 长度会变的东西 |
| **预留**（缓冲区基质：`buf<T>`、`string`） | 小载荷拿 16 B…64 KiB 的密排槽，大载荷拿一片 2 MiB 对齐的地址空间；`buf<T>` 的元素地址恒为 `base + i*sizeof(T)`，没写过的页不驻留 | `shrink(k)` 把 `[k, cap)` 的页还给操作系统（地址不变），`release()`（也在 `@drop`）把整片还给基质 | 会变长、而且增长后还要拿视图的大数组；要能把容量还回去的东西 | 想让元素随块退出自动收走的东西（容器只在显式动作 `clear`/`shrink`/`release`/`pop` 里逐元素跑钩子）；对拥有元素的容器按值迭代元素仍是编译错误，见 [`BUF-INVARIANT.md`](BUF-INVARIANT.md) §14 |
| **对象表**（按句柄寻址的槽表） | 槽数组 + 世代；句柄是"槽号 + 世代" | 槽可回收；回收后旧句柄读到的是"没有"，不是悬垂 | 需要身份、要活过出生位置的值（`dyn` 值） | 热循环里的逐次读写（每次都要过世代检查） |

三者的关系是**分工**，不是三套竞争方案：

- 帧是地基。绝大多数分配落在这里，代价接近零：不记账、不扫描、退出不遍历。
- 板块是"会变长的东西"的存储。它属于某个容器，容器换掉旧缓冲时旧缓冲**当场**就还了。
- 对象表只在"值必须有身份、且身份要离开创建它的地方"时才值得用；它买的是"读不到"而不是"读坏"。
- 预留是"会变长"的另一种答案：长度在预留里推，**不拷贝**；只有撞到预留上限才搬一次家。它买的是"增长不付拷贝"和"容量能还给操作系统"，代价是地址空间与一次 `madvise`。

## 二、一条判据

| 你要的是 | 用什么 |
|---|---|
| 块里用一下就算完的临时量 | `new T[n]`、定长数组、局部变量 |
| 长度会变，或者在函数之间传递一段存储 | `vector`、`string`、`hashMap` —— 它们自带板块 |
| 长度会变、可能很大，而且增长时不想付拷贝 | `buf<T>` —— 它自带一片预留（增长零拷贝，容量能还） |
| 值要活过创建它的位置，而且要被别处记住 | `dyn` 值（或装箱的 `any`） |
| 只是"看看"别处的数据 | `slice<T>` 视图：零拷贝、不拥有、不负责归还 |
| 要在大块数据上原地算，不复制 | `slice<T>` 视图 + 接收视图形参的函数 |

一句话：**先问"它活多久"，再问"长度会不会变"，这两个答案合起来只对应一种存储。**

## 三、为什么可增长的容器必须拥有板块

增长是**乱序死亡**：新缓冲在旧缓冲之上分配，被替换的那一块死在它下面。而帧是栈 —— 只能从顶上往下退，退不了下面的。所以被替换的缓冲会一直占着，直到它所在的块退出。

两个实测（同一台机器，2,000,000 条记录尺度上的同族负载）：

| 写法 | 峰值内存 | 墙钟 |
|---|---|---|
| 在帧里自己搓可增长数组（每次增长换一块新缓冲） | 增长到八百万个 `i64` 时 **132.8 MB**（历代旧缓冲之和，约 2 倍） | 70 ms |
| `vector<i64>`（拥有板块，原地长 1.5 倍） | **64 MB** | 28 ms |

反复建了又丢的负载差别小一些，但方向一样：一百次"分配 1 MiB 再丢弃"，用板块的容器稳态只要 **2.5 MB**；同形状在帧里换缓冲，回收器能收掉那些被替换的块（见下一节），峰值由**收集底盘**决定 —— 实测 **11.8 MB**，接近五倍。

这就是规则：**容器拥有存储，存储才可能在容器替换它的那一刻被还掉。** 帧只适合"和块同寿命"的东西。

板块之上还有一步：`buf<T>` 把"容器拥有存储"做成"容器拥有**一片地址预留**"，于是增长连"换一块"都不必发生 ——
长度在预留里往前推，搬家的次数由 `relocations()` 数得出来（`bench/buf` 里 8e6 次 `push` 是 0 次搬家，
`std::vector` 是 24 次）。容量还原地还：`shrink(k)` 只丢页、不改地址。细节见
[`BUF-INVARIANT.md`](BUF-INVARIANT.md)。

## 四、四个会咬人的写法

**① 在帧里手搓可增长容器。** 见上表：内存是"历代之和"，翻倍增长约 2 倍，按固定步长增长是二次增长。正确做法是换成 `vector`/`string`，或者自己写容器时也让它拥有板块。

**② 循环里分配、循环外的变量接住。**

```
var b: mut slice<u8> = new u8[1024]
for ... {
    b = new u8[1024 * 1024]     // 每轮新块：上一块要等收集器
    ...
}
```

一百轮之后峰值 **11.8 MB** —— 被替换的块是垃圾，回收器会收，但**界是收集底盘**，不是存活量：同时活着的只有一个 1 MiB 缓冲，峰值却十倍于它。把同一行写进循环体（每轮一个新变量），峰值 **2.6 MB** —— 每轮结束时整块被归还，连收集都不必等。这条判据很好记：**变量的块比循环长，旧缓冲就只能等回收器。** 关掉回收时它回到线性增长（一百轮 **103.8 MB**）。

**②的例外：值经包装存放时，存储跟着目的地走。** 从函数调用拿到的存储，如果中间过了 `??`
的兜底、`some(...)`、结构体字面量的字段，它落在**存放这个值的那个块**里 —— 写在循环体里就随
循环体释放。所以"`var b: buf = make() ?? dflt` 在循环里"不会攒；攒的是 ② 那种把 `new`
直接写进循环外变量的写法，编译器对它单独给一条警告（见[语言手册](../usage/language.md)）。

**③ 把拷贝来的视图丢掉。** `snapshot()` 是拷贝：拷贝本身是回收区里的一个块，也会被收掉（二十万轮实测 **2.6 MB**），但每一轮都真的付一次复制的工作量。热循环里不要制造要逃逸的拷贝；需要看内容就直接读容器的 dense 前缀。

**④ 长命位置里的 `dyn` 垃圾。** `dyn` 的 payload 由它所在位置的对象表持有，槽可以回收，**payload 的字节随位置一起还**。所以界是"这个位置里造过多少"，不是"同时活着多少"：

| 形状 | 峰值 |
|---|---|
| 被调函数里造、用完返回（每次都是新位置） | 两百万次构造后 **1.8 MB**（常数） |
| 长命位置里造、每次覆盖同一个变量 | 一百万次后 **82 MB**（历史高水位） |

**`dyn` 的池诞生在"写下这个值的地方"。** 所以把 `dyn T(x)` 直接写在循环体或内层块里、又交给外面记住，池会随那一层的块退出被归还，句柄随后陈旧 —— **检查期就拒绝**（`dyn` 的值是某个 place 里槽位的句柄，和引用一样算"携带存储"；容器活得更久就不接受）。正确写法是先赋给一个**在这层之外声明**的 `dyn` 变量 —— 赋值会把池提升到变量的层级 —— 再把变量交出去；异构容器请用 `any`（装箱即拷贝，自己拥有载荷）：

```extc,no-check
var slot: dyn Tag = dyn Tag(box { v: 0 })   /* 声明在当前帧 */
while … {
    slot = dyn Tag(b)                      /* 赋值：池被提升到这一帧 */
    xs.push(slot)                          /* 交出去的是已经提升过的句柄 */
}
```

每个 `dyn` 值还在对象表里占一个槽（几十字节），槽同样随位置退出才回收。所以 `dyn` 适合"数量有界、有身份"的用途，不适合在长命位置里当"每轮丢一个"的槽位 —— 后者要么把批处理放进一个内层块（每批一个新位置），要么别用 `dyn`。

## 五、碎片

没有经典意义上的碎片，因为**没有共享大堆**：帧是栈（天然没有洞），板块是每个容器自己的独立分配（换掉就还，归还交给系统分配器），对象表的槽按类型/尺寸分组复用。三者都不需要"合并相邻空洞"，也就不需要搬动（compaction）。

剩下的只是三种**内部余量**，都是有界的：

- 帧的块尾余量：一块之内用不完的那点，量级是"每块几十字节到一块"；
- 容器容量余量：`vector` 按 1.5 倍长，最坏 50%；`hashMap` 还有墓碑，按装载比例重建；
- 对象表的槽余量：回收的槽留在表里复用，表不会立刻缩。

稳态实测（同一个进程里反复建、反复丢）：一百个 1 MiB 容器 = **2.5 MB**；两千轮、每轮三个不同尺寸的容器同时活 = **1.5 MB**；两百次 4 MiB 的帧内分配 = **5.6 MB**。都不随轮数增长。

## 六、和"有垃圾回收的语言"差在哪

会做回收的语言（比如 Go）解决的是**任意时刻、任意顺序的死亡**：`append` 越界时新开一块、拷过去，旧的那块变成不可达，下一次标记清扫把它收回空闲链复用。所以"分配完就丢"的形状它也能稳态在几个 MB。

我们解决的是**词法边界 + 静态证明**：不问"还有没有引用"，只问"是不是退出了这个块"。好处是分配免费、没有写屏障、没有停顿；代价是"乱序死亡"没人管 —— 而这恰好是可增长容器天生制造的形状。

所以对比要分两件事看：

- **丢弃即回收**：有回收器的语言赢（一百次 1 MiB 的 churn，它们几 MB，帧里换缓冲的写法 103.8 MB）；
- **增长的峰值**：两边一样（都是拷贝瞬间两份都活，约 2 倍）。有回收器的语言不会让增长更省，只是不用你操心旧的那份。

结论：**帧不是"更差的堆"，它是另一种形状。** 长度会变的存储必须交给拥有自己存储的容器；把这件事做对，稳态内存和速度都能追上有回收器的语言。

## 七、想自己写容器

想自己写容器，今天有两条路，都是给结构体一块**自己拥有**的存储，再对它做四个动作：**留**（`buf::reserve` 按最大容量留地址；`block` 在创建时定容量）、**长**（`buf::grow` 在预留内原地长，超出预留才搬家并让旧视图失效）、**还**（`buf::shrink` 把页还给系统、`buf::release` 整片归还；`block` 创建时定容量）、**取视图**（`buf::view` / `viewMut`，元素地址恒为 `base + i*sizeof(T)`）。`vector`、`string` 是第一条路的完整样板，`hashMap`、`map` 是第二条路的样板，两者的实现都在 `stdlib/std/data/`。

不做这几件事会怎样：没有预留就地每次拷贝增长（峰值 = 历代之和，手写的 800 万个 `i64` 容器实测峰值 64 MB 是预留的形状，逐轮新分配会翻倍）；在视图活着的时候增长，旧视图指向的地址会被放弃 —— 同一块里的这种写法现在是编译错误，跨函数由 `buf::borrow()` 的守卫在运行期 trap。语义细节见 [`BUF-INVARIANT.md`](BUF-INVARIANT.md)。

## 八、要记的三句话

1. **先看寿命，再看长度**：块内 → 帧；会变长 → 预留（`buf<T>`）或平坦块（`block<T>`）；要身份 → 对象表。
2. **谁的块退，谁的内存还**：变量的作用域比循环长，旧缓冲就会攒。
3. **拷贝要记账**：`snapshot()` 的存储活在调用者的位置，热循环里它就是你写的每一次分配。
