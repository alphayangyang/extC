# hashMap 的形态（v2，已实现）

> 状态：实现清单见 §11 —— 存储、API、迭代都按本稿落地；判据见 §8：J1 / J2 / J3 / J5 同轮全过（J2 从逐字节时代的 2.17× 降到 1.14×，解法与代价在 §9）。

## 0 一句话

一个哈希表本体只需要三样东西：一块桶数组、线性探测、重哈希。其余上千行都在回答同一个问题 —— **元素能不能被取引用**。这个问题应该在语言层一次答完，容器里不重答：不承诺元素地址，跨修改持引用用 `std::weak`。

## 1 目标与非目标

目标：

- 每元素元数据从 20 B 降到 **0**（没有槽元数据、没有反向列、没有世代号）；
- 访问**零拷贝**：桶里就是键与值的字节，`get` 按值取出（值类型自己决定拷贝多贵）；
- **零编译器特例**：本稿不需要任何新的语言原语，pool 那一族特例整族消失；
- **不依赖 GC**：存储是 `dense::block<T>`（显式 `release`）；
- 有硬判据（§8），其中 h1 峰值与 `datalog_lite` 的 RSS 红线是必须过的。

非目标：

- **不承诺元素地址稳定**（C++ 的 `unordered_map` 承诺它，代价是每元素一个节点、多 32~48 B）；
- **不提供借用守卫 / 冻结位**：不承诺地址就不需要「借出期间禁止改结构」这套机制；
- **不做增长期的有界停顿**（理由见 §6，选择与 C++ 同一档的全量重哈希）；
- 不做并发/跨任务共享（今天的约束不变）。

## 2 结构

```
@noCopy struct hashMap<K, V> {
    @private keys: block<K>     /* 活桶的键 */
    @private vals: block<V>     /* 活桶的值，与键同下标 */
    @private tag:  block<u64>   /* 每字节一个桶：0 = 空桶；否则 h2 的最高位置 1 */
    @private n:    i64          /* 活元素个数 */
    @private cap:  i64          /* 桶数（不是 2 的幂） */
}
```

三列同长（`keys` / `vals` 长 `cap`，`tag` 是 `(cap + 7) / 8` 个 `u64`）；一个桶 `1 + sizeof(K) + sizeof(V)` 字节（`K = V = i64` 时是 17 B/桶）。标签单独一列是为了不给键值对齐付 padding：内联成 `struct { tag: u8, k: K, v: V }` 会变成 24 B/桶（+41%）；按字打包又让 tag 列只占原来的 1/8 字节（它只是控制字节，不参与键值寻址）。

`tag` 是**控制字节**列：每字节一个桶，0 只留给「没有元素」，非零是该键哈希的 7 位片段（h2）加 128（最高位恒为 1）。探测按机器字一次读 8 个桶：空桶用「字里有没有零字节」定位，候选桶用「字里有没有等于控制字节的字节」定位，各只需一次减法加掩码，命中才碰键列 —— 键可能是 `string`，比较比一个字节贵得多。

存储复用 `stdlib/std/data/dense.extc` 的 `block<T>`：`[]`（读）、`[]=`（`elemPut`，写**没有元素**的槽）、`take`（`elemTake`）、`dropAt`（`elemDrop`）、`growTo`/`shrinkTo`/`release`。本稿不新增原语。

## 3 不变量

- **I1** `keys` / `vals` 同长 = `cap`；`tag` 是 `(cap + 7) / 8` 个 `u64`，第 i 个字节对应桶 i；`n` 是活元素数，`n <= cap * 17/20`。
- **I2** `tag` 的第 i 个字节为 0 ⟺ 桶 `i` 里没有元素。写有元素的槽必须先 `take` 出来（这就是 `elemPut` 与普通赋值的区别）。
- **I3** 装载超过 `17/20` 就重哈希到 `max(8, (n+1) * 20 / 17)`；增长用**全量重哈希**（§6）。
- **I4** 没有冻结位、没有守卫计数：结构修改在元素被搬走时让旧的下标失效，**这是契约不是缺陷**。
- **I5** 桶位会随重哈希变，值不会：要一份独立的表用 `clone()`。

## 4 API

```
withCap(c)              /* 预置容量，避开重哈希 */
len() / capOf() / bytesOf()
contains(k) -> bool
get(k) -> ?V            /* 按值取 */
put(k, v) -> bool       /* true = 键本来就在；值被移动进桶 */
remove(k) -> bool       /* 回移，不留墓碑 */
take(k) -> ?V           /* 搬出去，不是拷 */
clear()                 /* 容量留着 */
compact()               /* 按活元素重排到刚好够的容量 */
release()               /* 三列整批还回去 */
keyAt(i) / valAt(i) / liveAt(i)   /* 按桶位扫，i 走 [0, capOf()) */
clone()
```

**没有** `slotHandle`、**没有** `entry`、**没有**返回 `ref V` 的迭代器、**没有**稠密值列。

## 5 索引、删除、增长

- 索引：`bucketOf(h, cap) = ((h >> 31) * cap) >> 32` —— 只做 64 位乘法（语言里没有 128 位），`cap` 因此可以不是 2 的幂；装载率不必被 pow2 浪费。
- 探测：线性、步长 1、回绕；按机器字一次读 8 个桶（头/尾字用移位掩码裁掉区间外的字节），空桶与候选各用一次零字节检测定位；命中判定先看控制字节再看 `k == k`（见 §9）。
- 删除：**回移**（Knuth TAOCP 3 §6.4 alg R）—— 把洞后面的元素往前挪，不留墓碑，因此没有 `dead` 计数，也没有「整表重建来清墓碑」。
- 增长：新三列按 I3 的容量，活桶逐个 `take` 出来再 `put` 进新列（**是移动**），旧列当场 `release`。

## 6 为什么增长是全量重哈希

| 方案 | 单步 | 峰值 | 代价 |
|---|---|---|---|
| 全量重哈希（本稿） | O(n) | 旧 + 新（瞬时） | 与 C++ `unordered_map`、Rust `std::HashMap` 同一档；`withCap` 是逃逸门 |
| 增量迁移（双表） | O(批量) | 旧 + 新（全程） | 原型 83.9 B/元素 —— 等于没省，且旧表未迁完时探测链会断 |
| 页粒度分裂 | O(一页) | 等于稳态 | 需要「第 i 页在 `base + i * 4096`」= 指针算术；语言没有 ⇒ 要么加编译器原语（特例），要么每页一个 GC 对象（引入 GC 依赖） |

## 7 删掉什么（这一节是设计的主体）

| 删 | 为什么它存在过 |
|---|---|
| `slots<T>` 的槽元数据（活槽编码、洞链 `holeHead`、`cursor`） | 池板块会复用 ⇒ 需要世代判陈旧；块不会被复用，句柄也没了 |
| `slotHandle`（槽号 + 世代） | 元素被搬走/删掉后旧句柄要能失效；现在不承诺地址，也不需要失效检查 |
| `slot` 列、`bucketOfDense` 反向列、稠密值列 | 值内联进桶之后这三列没有对应物 |
| `pStale` / `pPoison` / `pidGen` | 同上：世代与中毒都是池块复用的产物 |
| `rebuild` / `adopt` / `dead` / 2 的幂容量算术 | 换成按装载线的增长 + 乘取高位索引 + 回移删除 |
| API `at(slotHandle)` / `slotOf()` / `remove(h)` | 换成吃键的 `get(k)` / `remove(k)` / `take(k)` |

编译器的 **pool 特例族**（`isPoolPrimitiveName` / `checkPoolPrim` / `@poolObject` / `growMethodName` 的池分支）随池退场整族消失；本稿不新增任何特例。

## 9 J2 的解法：控制字节按字打包（2026-12，已落地）

**前置归因**（2026-12，callgrind + 装载率扫描）：缺口全部来自装载率，不在代码生成。

| 臂 | 装载率 | h5 墙钟 | h5 峰值 | Ir/op（12M 次操作） |
|---|---|---|---|---|
| 逐字节实现 | 17/20 = 0.85 | 0.59 s | 81,780 kB | 338.4 |
| 逐字节实现，17/20 → 14/20 | 0.70 | 0.40 s | 98,168 kB | 123.7 |
| 池底实现 | 0.70 | 0.51 s | 201,732 kB | 142.5 |
| `flat` 手写表 | 0.50 | 0.31–0.32 s | 143,1xx kB | 49.4 |

- 不命中的期望探测数约 (1 + 1/(1-α)²)/2：α=0.85 时 22.7 次，α=0.70 时 6.06 次，差 3.75×。装载率从 0.85 调到 0.70，Ir 掉 2.73×（338.4→123.7），墙钟掉 1.48×（0.59→0.40 s）—— 墙钟近线性于期望探测数（8M 次查询上每多一次期望探测约 0.55 ns）。
- 同一装载率下逐字节实现比池底快（0.40 vs 0.51 s），所以「池的稀疏桶更好摸到空槽」不是原因，基质与布局都不是原因。
- 本节原来列的三条候选在 -O2 下都不成立：`find` 全内联进 `main`（callgrind 里没有独立函数），哈希与桶位算在必需的一次乘法里，键比较是内联的等号。池底反而有独立的 `hashMap$..._find` 占 28.4% Ir。
- 剩下的 2.5× 指令差（123.7 vs 49.4）来自逐字节探测本身：每探一个桶都要读控制字节、判空、判 h2、再回绕。

**判据的两端在逐字节探测下不可同时满足**：

| 装载率 | 期望探测数 | h1 峰值 | J1（≤85 MB） | h5 墙钟 | J2（≤1.3× flat，约 0.40 s） |
|---|---|---|---|---|---|
| 0.85 | 22.7 | 81,784 kB | PASS | 0.59 s | FAIL |
| 0.82 | 15.9 | 85,880 kB | PASS（贴边） | 0.53 s | FAIL |
| 0.80 | 13.0 | 89,976 kB | FAIL | 0.50 s | FAIL |
| 0.70 | 6.06 | 98,168 kB | FAIL | 0.40 s | PASS（贴边） |

装载率同时决定峰值内存（桶数 ∝ 1/α）与不命中成本（探测数 ∝ 1/(1-α)²）：J1 要求 α ≥ 0.82，J2 要求 α 约 0.70。把 α 留在 0.85、让一次探测覆盖多个桶，是唯一不必在这条权衡上选边的路。

**落地形态**：`tag` 从 `block<u8>` 改成 `block<u64>`，每字节一个桶，桶 `j` 是第 `j / 8` 字的第 `j % 8` 个字节（按位序定义，与端序无关）。控制字节改成 `128 + ((h >> 20) & 127)`（最高位恒为 1，永不与 0 冲突），空桶仍是 0。于是一次按字探测只需要：

- 空桶检测：`emp = (x ^ ones) & 0x8080...80`，`ctz(emp) >> 3` 就是第一个空桶的字节偏移；
- 候选检测：`zeroBytes(x ^ bc)`（`bc` 是控制字节广播到 8 个字节），`ctz` 给第一个候选；
- 谁在前谁就是答案；候选在前再比一次键。头字与尾字用移位掩码把区间外的字节裁掉（`m = ones << (off * 8)`，尾字再 `m &= ones >> ((8 - (hi - base)) * 8)`），因此 `cap` 仍可任意、不必是 8 的倍数。

装载率没有降：同轮 `run-flat.sh --reps 7` 下 h5 0.363 s / flat 0.318 s = **1.14×**，h1 0.315 / 0.250 = **1.26×**，峰值仍是 81,780 kB。J1 与 J2 同时 PASS。

两次否定（留在设计史里，避免重复踩）：

| 版本 | 做法 | 结果 |
|---|---|---|
| v2 | 先按区间掩码/移位再取最低置位 | **正确性错**：区间头之外的低位借位会把高位非零字节误报成零字节 ⇒ 空桶判错、覆盖活键。改成头尾逐桶后正确，但每步要一次有符号除法（`i / 8`），全面退步（h5 仍 0.58×、h1 0.74×） |
| v3 | 头尾逐桶 + 高位置 1 标记 | 正确，但仍慢（h5 0.561 s）—— 逐桶路径的 `i / 8` 比字级扫描贵，per-op 指令数没有降 |
| v4（当前） | 完全取消逐桶路径：头字、尾字都用移位掩码 | h5 0.354 s（min-of-7 A/B）、h1 0.309 s，见下表 |

**必须开 `@inline`**：extC 的 `@inline` 是源码级内联。`probeRange` / `slotRange` / `findH` / `find` / `slotFor` 任一不开，h5 就回到 0.65× —— 函数调用与跨函数传参会把字级扫描的收益吃掉。`ctz64` 加不加 `@inline` 无差别。

代价（同轮 A/B，min-of-7 交错）：

| 形状 | 逐字节 | 按字打包 | 比 |
|---|---|---|---|
| h5 全不命中 | 0.594 s | 0.354 s | 0.60× |
| h1 全量命中 | 0.310 s | 0.309 s | 1.00× |
| h6 只插入 | 0.118 s | 0.106 s | 0.89× |
| h3 增删改混合 | 0.224 s | 0.215 s | 0.96× |
| h2 从 8 长起来 | 0.331 s | 0.352 s | 1.06× |
| h4 两遍全表遍历 | 0.049 s | 0.057 s | 1.16× |

两格退步是本轮引入的：h2 每次 `put` 在增长路径上多一遍字级探测；h4 的 `liveAt` 没被 GCC 内联（按字打包后 `main` 变大），callgrind 里它成了独立函数占 103.5M Ir。绝对量都很小（+21 ms / +8 ms），换 h5 的 −240 ms。

**放弃的一条：`put` 合并探测。** 让 `probeRange` 顺带返回第一个空桶号、`put` 一次扫描同时拿到「命中位置或插入位置」，可以省掉 `slotFor` 的第二次探测（实测 h6 0.81×、h4 1.10×）。但 h3_churn 的输出变了：`n=664485 repl=2223434`（对照 `n=664484 repl=2223435`），即插入了一个重复键；`t7` 逐 op 自校验两臂都自洽、最终长度差 1 ⇒ 约 8M 次操作漏判一次「键已存在」。根因未定位（疑在空桶编码 `-1 - 桶号` 与「区间走完」`-2` 的解码边缘），本条**不采用**；`put` 保持两次探测。

J2 最终口径：h5 0.363 / 0.318 = **1.14×**、h1 0.315 / 0.250 = **1.26×**，都 ≤ 1.3× ⇒ **PASS**。J3（插入 ≤1.2× flat）也随之为 0.108 / 0.151 = 0.72×。
## 10 边界

- **值含 `@drop`**：`clear`/`compact`/`release`/`remove` 要逐桶跑钩子（有界、可预算）。整表丢弃不是丢引用而是走 `release`。
- **大值**：一律内联（`V` 大于一两个 cache line 时桶变稀疏；桶存指针的形态不在本稿）。
- **迭代**：按桶位扫（`keyAt`/`valAt`/`liveAt`），桶位随重哈希变；要一份独立的表用 `clone()`。
- **跨修改持引用**：不支持，用 `std::weak`。

## 11 落地状态

- 存储与 API 已落（`stdlib/std/data/hashMap.extc`）：`keys: block<K>` / `vals: block<V>` / `tag: block<u64>`（每字节一个桶，按机器字打包），`hashMap<K,V>` 泛型键（`hash()` + `==`），`hashMapI64<V>` 与 `hashSetI64` 是薄包装。
- 探测定位于 `probeRange` / `slotRange` / `findH`，全部 `@inline`；`put` 走两次探测（命中与空桶分开），`remove` 是 Knuth 回移，`grow` 全量重哈希。
- 调用方已换：`datalog_lite`（改桶位扫描、并列最大覆盖取最小键）、`tests/hashmap`、`tests/map`、`bench/containers`。
- 判据：J1 PASS（81,788 kB）、J2 PASS（h5 1.14× flat）、J3 PASS（0.72×）、J5 PASS（29,480 kB）、J6/J7 PASS。J4 的「重哈希次数与累计毫秒作为固定输出」仍未做。
- 池特例族、`slots<T>`、`slotHandle` 已随池退场删除；`map`/`set` 走 `block<T>` 平坦块（见 `docs/design/CONTAINER-OWNERSHIP.md` 与 `MEMORY-MODEL-CURRENT.md`）。
