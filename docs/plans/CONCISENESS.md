# 简洁度：口径、基线、糖的清单

> 状态：**计划** —— 不是现状；已经做完的部分在文内标了，剩下的按它排期。

这一页回答一个问题：**同样的活，extC 要比 Python 多写多少，多出来的部分是哪几类。**
它是量尺，不是目标本身——extC 不追隐式分配与 GC，目标是"没有一行是仪式"。

## 口径

`docs/conciseness/` 下是成对的练习：`<name>.extc` 与 `<name>.py` 输出逐字节相同。度量三个数：

| 指标 | 含义 |
| --- | --- |
| lines | 原始行数（含空行与注释） |
| code | 去掉空行与纯注释行之后的行数 |
| tokens | 词元数（标识符 / 数字 / 每个非空白非单词字符各一个） |

`lines` 会被"Python 用推导式一行干完"这件事放大，所以**看趋势看 tokens，看结构看 code**。
语料小（4 对），比率是取样不是统计结论；加练习就当加样本。

复测：

```text
python3 tools/conciseness.py
```

读数：同一个问题、同一份输出（`python3 tools/conciseness.py --check` 逐字节核对），
行数 105 → 71、tokens 1154 → 705；四份语料里**只剩下 `var s: i64 = 0` 这一种注解**
（累加器要和 `i64` 乘积相加，而字面量默认是 `i32`）。剩下的差距来自两处：①字面量的默认宽度

"extC 现在能写多短"，不是"编译器把旧写法变短了"。

## 噪音测量：`i64(...)` 包字面量

全库扫描（`stdlib` / `tests` / `examples` / `bench` 的 `*.extc`，2026-10-30）：

| 目录 | 行数 | `i64(` 总数 | 其中包字面量的 |
| --- | --- | --- | --- |
| stdlib | 10,299 | 2,130 | 1,990 |
| tests | 24,464 | 2,486 | 2,218 |
| examples | 5,123 | 201 | 162 |
| bench | 7,768 | 956 | 821 |
| 合计 | 47,654 | 5,773 | 5,191 |

而字面量在上下文里本来就能定类型：

```text
let x: i64 = 7          // 注解定类型
var y: i64 = x + 1      // 参与运算的一侧是 i64
if x < 5 { }            // 比较另一侧是 i64
v[0] = 1                // 索引接受任意整数
s = s + 1.0             // 另一侧是 f64
```

⇒ 包字面量的 `i64(...)` 是仪式。保留它的两种情况：

1. `for i in i64(0)..i64(8)` —— 端点的类型决定循环变量类型，去掉会退化成 `i32` 循环；
2. 泛型实参推不出类型（`seq::count(ys, 5)` 报"推不出 T"，写 `i64(5)` 才过）—— 这是真缺口，见第 1 层 A。

## 第 0 层：清掉自己写出来的仪式（不改编译器）

1. `i64(<整数字面量>)` 删掉，按上面的两条例外保留；
2. `var idx: [8]i64` 直接声明就是零初始化，不写 `[i64(0), …×8]` 字面量；
3. 定长数组整体赋值即拷贝：`var c: [8]i64 = w.shape`，不写逐元素拷贝循环；
4. 同一批清理顺手把 `stdlib` 里"为了让类型通过"而存在的多余 `view()` / `ref` 拿掉——每次都用 tests 兜。

验收：`i64(<字面量>)` 计数从 5,191 降到 ≤ 600；行数与 tokens 比不升；`./tests/run.sh`、
`smoke`、`nobench`、`docs` 全绿。

## 第 0 层的执行结果

全库 `i64(<整数字面量>)` 从 5,191 处降到 **91** 处；随后第 1 层 A 的两刀（字面量不再替类型参数
作主、上下文补型与运算符按宽度找重载）拿掉一批，再两轮机械清理（十六进制字面量、切片两端、
以及"左侧/上下文已经定死 i64"的普通位置）把仪式性 cast 清到 **6** 处（不含注释）：

| 目录 | 包字面量的 `i64(` | 剩下的都是什么 |
| --- | --- | --- |
| stdlib | 1 | `i64(1) << HANDLE_EPOCH_BITS`：移位的左操作数（宽度决定结果） |
| tests | 5 | 移位左操作数 2 行、`i64` 边界值 2 行（裸字面量超出 i32）、自定义流只定义了 `<<(i64)` 的 1 行（运算符按右操作数精确匹配，`42` 不隐式变 i64） |
| examples | 0 | — |
| bench | 0 | — |
| 合计 | 6 | |

第三轮清理的两条规则（纯机械、不动语义）：`i64(0x80)` 这类**十六进制字面量**直接裸写
（`0x80` 本就能放进 i64）；**切片两端**的 `i64(0)`/`i64(1)` 裸写（端点只要求整数，两个端点
类型不同也照常编译），`for i in …` 的端点除外（循环变量类型由下界决定，是语义位置）。

剩下这批集中在五类位置，其中前两类已经修掉（见下一节），后三类仍按原样写 cast：

1. ~~显式给泛型实参、实参是字面量~~：`m<i64>(3)`、`wrap<i64>(8)` 已能编（字面量按写出的类型实参
   适配）。
2. ~~泛型函数/方法的实参推断~~：`seq::count(ys, 5)` 已能编 —— `T` 由别的实参定，字面量只要求
   "能放进 `T`"。
3. ~~泛型结构体字面量的字段~~：`var c: box<i64> = box { v: 2 }` 已能编 —— 字面量的名字只决定
   "哪个结构体"，类型实参由期望类型给全；无上下文时仍报 `box is generic and needs type arguments`。
4. ~~重载只看实参类型~~：同一个类型同时定义 `*(vec2, f64)` 与 `*(vec2, i64)` 时，`v * 2` 命中
   `*(vec2, i64)`（字面量按"能放进哪些宽度"找），`v * 2.5` 命中 `*(vec2, f64)`。
5. ~~移位表达式的操作数~~：字面量移位量现在**编译期**按左操作数位宽核对，越界直接报错并提示
   `i64(1) << 32`（要 64 位结果仍得写宽左操作数；变量移位量照旧运行期检查）。

## 第 1 层 A 的进展：字面量不替类型参数作主

**规则**（六条，都是"字面量没有自己的类型"这一件事的推论）：

1. **推断**：字面量实参不参与"从实参推断类型参数"的绑定。推断先看非字面量实参；字面量只做
   "能不能放进已定的类型"这一件事。若字面量是某个类型参数唯一的见证（`f(5)`），仍按旧行为用
   它的默认类型推断（`T = i32`），所以既有程序不变。
2. **内建参数**：`parallel::run` 的 `n` / `threads` 直接收裸整数字面量（该位置只能是 i64）。
3. **结构体字面量**：`box { v: 2 }` 在 `box<i64>` 上下文里就是 `box<i64>`；名字只决定"哪个结构体"，
   类型实参由期望类型给全。
4. **运算符**：运算符按右操作数类型精确匹配，字面量因此按"能放进哪些宽度"去找重载
   （`v * 2` 命中 `*(vec2, i64)`，`v * 2.5` 命中 `*(vec2, f64)`）。候选集合由字面量的值决定，
   不是重载排序。
5. **方法接收者**：整数字面量当方法接收者时，按"字面量放得进的宽度"找方法集
   （`5.triple()` 命中 `impl u32` 的方法，`41.base()` 仍命中 i32），与运算符同一条规则。
6. **上下文返回类型**：实参带不出的类型参数，用上下文期望的（返回）类型补
   （`let p: pair<i64, u8> = dup(3, u8(4))`）。期望只做提示：实参先推断，实参推不出的才用它补，
   两边对不上仍由赋值/返回那一步报"期望什么、实得什么"。


**为什么值得**：这是"字面量没有自己的类型"的直接推论。`seq::count(xs, 5)` 里那个 `5` 的上下文
就是 `xs` 的元素类型，用户没有理由写 `i64(5)`。落地后 examples 的两个泛型示例与 `tests/stl/seq.extc`
都去掉了 cast。

**代价**：推断多了"推迟字面量"的一趟（同一批实参类型复用，不重复求值，所以没有副作用问题）；
诊断不变 —— 字面量放不进去时仍报 `cannot infer type parameter(s)`。

**仍然要写 cast 的地方**：字面量没有任何别的见证（既没有标注、也没有能定型的实参）、而目标
类型不是默认类型时（`f<u8>(200)` 里写 `200` 可以，`f<u8>(300)` 不行 —— 会报推断失败，要写
`u8(300)` 或用标注）。这条边界写在 `tests/sugar/sugar_generic_literal.extc` 的注释里；有标注时
第 5 条会补上（`let x: box<u8> = mk()` 不再需要 `mk<u8>()`）。
**第 1 层 C 的另一笔（`?` 不再需要先绑临时量）**：`?` 原先只允许整条语句能被重写的位置
（声明 / 赋值 / 返回 / 裸调用），`f(g()? + 1)` 要写成 `let t = g()?` 再拼。现在检查器把语句值位置里
嵌套的 `e?` 提前成一条 `var __extc_tqN = e?` 插在语句之前，求值次数与时机不变；`&&`/`||`/`??`
的右侧、`while` 条件、lambda 体仍拒绝（见 `docs/usage/language.md` §9.5、`tests/ops/try_expr.extc`
与 `tests/errors/try_{short_circuit,while_cond}.extc`）。零开销有闸门：
`tests/ops/run.sh` 的 `try_hoist_zero_cost` 拿"糖写法"与"手写临时量"的生成 C 逐字节对比。
两/三下标糖的接收者也可以直接是 `ndarray<T>`（编译器按需借出 `view()`/`viewMut()`），
不必先写一行 `var g: ndview<T> = grid.viewMut()`；判据是 `tests/stl/nd_direct.extc`。

## 字符串与 IO：现状与目标形状

今天能用的东西：

- `std::text::string`：`new` / `withCap` / `from(slice<u8>)` / `fromI64`；方法 `len`、`snapshot`、`clone`、
  `push`、`append`、`concat`、`concatBytes`、`sub`、`at`、`find`、`contains`、`startsWith`、
  `endsWith`、`removeFront`、`clear`、`hash`、`==`（`string` 与 `slice<u8>` 各一套）、`<`。
- `std::text::stringio`（`impl string`）：`readLineFrom` / `readAllFrom` / `writeTo` / `writeLineTo`；
  对 `io::istream` 与 `fs::ifstream` 也有 `impl`。
- `std::io`：`cout <<`（`i32`/`i64`/`f64`/`bool`/`slice<u8>`）、`writerOf(fd)`、`readerOf(fd)`、
  `readSome`、`flush`；`io::reader` 的 `nextByte` / `nextLine` / `nextI64` / `avail` / `fill`；
  标准输入的 `inSync()`；格式化助手 `fmtI64` / `pFmtF` / `pPadText` / `padText` / `padInt` / `padF`。

痛点（都是"有模板但难用"的具体形态）：

1. `f"…"` 只能作 `<<` 的右操作数 ⇒ 想要一个字符串值，就得 `string::new()` 加一串 `append` / `fromI64`；
2. 字面量是 `slice<u8>`、拥有者是 `string`，转换靠 `from` / `snapshot`，比较还分两套 `==`；
3. 没有 `split`、没有通用的 `parse<T>`（只有 `toI64`）⇒ 切分隔符要手写下标循环；
4. 没有 `print` / `println` ⇒ 输出只能 `<<` 链，链一长就难读，且必须写在一行；
5. 读输入得拿 `io::reader` 的 `nextLine` / `nextI64` 再 `match` 错误，逐行循环要自己搭。

目标形状（第 1 层 B 的验收面）：

```text
let s: string = f"{name}: {n}"            // f-string 落在值位置
var parts = s.split(", ")                  // 视图数组，零拷贝
let n = str::parseI64(parts[0]) ?? i64(0)  // 已有 toI64，补通用 parse
io::println(s)                             // 一行输出，不要求 << 链
for line in io::lines() { ... }            // 逐行迭代，错误在迭代器里收
```

### 第 1 层 B 的进展（字符串与 IO）

- `std::text::string::split(s, sep)`：按字节分隔符切分，每段是零拷贝视图（`varArray<slice<u8>>`）。
  替掉"手写两层 while 找分隔符"约 8–12 行。
- `io::print(s)` / `io::println(s)`：不用链式写法的一行输出，替掉 `io::cout << s << "\n"`。

第一刀（`8cead15`）加了 `string::split` + `io::print` / `io::println`；第二刀（本次）加：

- `string::join(parts, sep)`：把 `split` 的段拼回去（一次按总长分配）。
- `string::trim` / `trimStart` / `trimEnd`：去两端 ASCII 空白，返回原缓冲视图（零拷贝）。
- `string::readLine()` / `readAll()`：控制台读一句版（内部做 `io::inSync()` 与 `inSave` 的
  取还，调用点不用再记那两行样板；空行给 `some("")`，只有 EOF 给 `none`）。

数字进字符串不必先转成 `string` 再切视图：`s.appendI64(n)`、`s.appendF64(x, 2)` 直接追加
（`appendI64` 在 `std::text::string`、`appendF64` 在 `std::text::stringio`，后者要 I/O 层的格式化）。
循环里拼 `csv` 这种形状因此是一行一个调用。

字符串拼接有运算符写法：`let s = str::from("a") + "=" + v`（`fn +` 返回新值；右操作数是
`slice<u8>` 或 `string`）。运算符方法因此也能分配：运算符调用点与方法调用共用同一套 zone 记账。

数字与布尔也能直接接在 `+` 后面：`let s = str::from("a=") + n`（整数按十进制、`f64`/`f32` 六位
小数、`bool` 给 `true`/`false`）；`io::cout << s` 也能直接吃 `string`，不用再写 `s.snapshot()`。
这两项让"用字符串拼一行"彻底不需要临时视图。

**f-string 落在值位置**：`let s: string = f"{name}: {n}"` 展开成
`std::text::string::from("…") + 槽 + …` 的 `+` 链（要求 `std::text::string` 被 import）。
`let s = f"…"` 不写注解也能推成 `string`。

**值位置也吃格式说明符**：`let s = f"[{n:>4}][{x:8.2f}]"` 里的槽按**槽值的静态类型**落成
`std::text::string::padI64` / `padF64` / `padText` 调用（所以带说明符时还要 import `std::text::stringio`），
语义与 `<<` 右侧的说明符逐条相同 —— 报表/日志不需要再为排版退回 `<<`。

本段又补：`io::eprint` / `io::eprintln`（诊断通道的一句版）、`string::fromF64(x, prec)`（定点浮点
转字符串，复用 `io::pFmtF`；容器不认识"小数点后几位"，所以放 stringio 层）。

还缺的（第 1 层 B 后续）：`varArray`→`slice` 之外的容器转视图（`vector` 的 `snapshot` 仍是显式）。

### 第 1 层 B 的进展（二）：把默认路径变短

这一轮不做新语法，只把"最常写的那几行"改短（判据仍是"同一语义不加第二种写法"）：

- **`for` 接受右值主语**：`for part in string::split(line, ",")` 直接可用（不是 place 时编译器先
  收进隐藏绑定、只求值一次）。
- **容器自动借出**：`for d in va` 等价于 `for d in va.view()`；任何有 `view()` 的类型都能
  直接迭（`vector` 仍显式 `snapshot()`，因为它故意不交出零拷贝视图）。
- **表达式位置也自动借出**：`println(f"…")`、`take(f"seven")`、`s.append(bytes)` 都不用先写
  `view()`（判据与参数借出同一条：签名里返回视图）。
- **`?? break` / `?? continue`**：`let v = maybe(i) ?? continue` 一行写完"求值一次、没有就跳"。
- **`string::toF64(b)`**：与 `toI64` 同位置，`f64(string::toF64(t) ?? 0.0)` 是"读一行再解析"的
  主路径（不再需要 `io::cin >>`）。
- **`print` / `println` 恢复可用**：内建两条路都行（stdio vs `io::cout` 的 fd 流），生成的 C 在
  每次内建打印末尾补 `fflush(stdout)`，混写顺序与源码一致；`string` 实参按字节写出。

已补：`varArray` / 定长数组传给**只读视图参数**时，调用位置自动借出（`total(va)` 就是
`total(va.view())`、`total(a)` 就是 `total(a[..])`），借用与生命周期照常检查；写权限
（`mut slice<T>`）仍要写在调用点。

## 第 1 层 C 的进展（多下标与切片糖）

`v[i, j]` 与 `v[r0..r1, c0..c1]` 现在直接可用（`use std::nd` 之后）：

<!-- fragment -->
```extc
let x: f64 = v[1, 2]                     // 读一个元素（越界 trap）
let sub: ndview<f64> = v[1..3, 1..3] ?? v  // 二维子视图（越界给 none）
```

三条糖都**直译成库函数**（`nd::at2` / `nd::set2` / `nd::slice2`），没有新的语法节点、没有新的
运行期形状，所以在转置/步长视图上也一样成立。第一版只做 rank-2 的两下标（更高维用视图构造器）；赋值与复合赋值（`v[i, j] = x` /
`v[i, j] += x`）都在，元素只读一次。

顺带修掉一个解析器 bug：槽里的模块路径（`f"{nd::at2(v, 0, 1)}"`）曾被当成格式说明符的开头
（`::` 的第一个 `:` 触发"unexpected `:` in a format specifier"），现在 `::` 按路径分隔符跳过。

## 第 1 层 D 的进展（fn 形参的效果摘要）

第 1 层 D 那格说的是：`fn` 形参（回调）会让"收回调的库函数"的效果摘要**永远**不完整，于是
调用点传帧内的视图就报

```text
argument 1 of `apply` carries a reference into a deeper scope (depth 1) than the place the
callee may store it (depth 0); the callee's effects could not be fully analyzed
```

**判据**（`src/check/check_top.c` 的 `fnTypeCarriesNoRef`）：回调签名里**既没有引用形参、也没有
引用返回值**（每个形参类型、返回类型都不含引用）⇒ 这个间接调用拿不到调用方的引用、也交不出
引用 ⇒ 它不可能把调用方的引用发布到别处 ⇒ 摘要保持完整，调用点按真实效果检查。签名里带引用的
`fn` 值仍然按最坏情况处理（保守方向不变）。

```extc
fn apply(v: mut slice<i64>, f: fn(i64) -> i64) { for i in 0..v.len { v[i] = f(v[i]) } }
fn inc(x: i64) -> i64 { return x + 1 }
fn main() -> i32 {
    var buf: mut slice<i64> = new i64[4]
    for i in 0..4 { buf[i] = i64(i) }
    apply(buf, inc)                     // 签名不带引用 ⇒ 这里按真实效果检查
    return 0
}
```

回归：`tests/ops/fn_callback_view.extc`（帧内视图 + 块内视图各一次，先红后绿）。

## 第 2 层：整数组表达式与融合（结构调整）

`docs/design/ARRAY.md` 的 M3 与 `docs/design/FUSION.md` 的 S1–S3：`c = a + b`、`sum(c)` 由编译器降成融合循环，
不留临时数组。做完之后 `stdlib/stl/nd.extc` 里手写的逐元素内核可以删掉（库只剩描述符与归约），
数组代码的形状与 Python 一致而仍然零临时分配。

### 第 2 层的进展：S1 元素链融合（已落地）

编译器现在把**相邻的"写临时视图 / 按同一下标读它"两个循环**合并成一个，临时视图整趟消失。
用户写法不用改，只是生成 C 里少一趟写和一趟读：

<!-- fragment -->
```extc
var tmpv: mut slice<f64> = new f64[n]
for i in 0..n { tmpv[i] = a[i] * 2.0 + 1.0 }   // A：写临时视图
for i in 0..n { out[i] = tmpv[i] + 10.0 }      // B：相邻、同下标读 ⇒ 与 A 合并，tmpv 消失
```

- **替掉哪一行仪式**：不再需要手写 `out[i] = a[i] * 2.0 + 11.0` 这种"人肉融合"来避免分配临时数组。
- **代价 / 不能用的情况**：判据窄且保守 —— 两循环必须相邻、循环变量同名、上下界结构相等；A 体
  恰好是"写 tmp 的一格 = 纯表达式"（右值不含调用/分配/切片/trap）；B 里 tmp 只能以 `tmp[i]` 读出现；
  B 的写名与读名不相交；tmp 在本块其它地方（含子块/分支/match 臂）没有任何引用；不跨 `par`、不在
  协程/并行 worker 体里。任一不满足就**原样保留**，不做部分融合。
- **判据**：`tests/fuse/`（正例两臂逐字节相同且生成 C 里没有临时视图；四条反例必须不融合）；
  `bench/fusion/` 同一份源码开/关 `--no-fuse`：n=1M、iters=8 实测 16.98 ms vs 30.63 ms（快 1.80×）。
  开关是 `--no-fuse`（测试与对拍用）。
#### 第 2 层的进展（三）：跨函数的 `seq::sum`

写 `let s = seq::sum(tmp) ?? 0` 时，编译器认出这是"对刚写出的临时视图求和"，把它改写成
`var acc: T = 零` + 索引形式的归约循环，再交给 S2 折进写循环：临时视图不落内存，热路径是一条
循环里累加。资格比 S2 多一条 —— **兜底值必须是零**（`?? 0` / `?? 0.0`），否则空输入上的语义
与"零累加"不同。

#### 第 2 层的进展（四）：跨函数的 `seq::max` / `seq::min`

写 `let mx = seq::max(tmp) ?? fb` 时同样是"对刚写出的临时视图取极值"，改写成写循环里顺手维护的
`found`/`acc`（第一次赋值、之后按 `>` 或 `<` 比较），循环结束后 `found` 决定取极值还是取 `fb`。
**兜底值不再是零特例**（两段互不影响），所以 `?? -1`、`?? (0.0 - 6.0)` 都行。实参必须是裸名字
`seq::max(tmp)`；`seq::max(tmp[..])` 与"同一临时视图有两个消费者"都不折。

- **判据**：`tests/fuse/extremum_max.extc`（`mx=-2`）、`extremum_min.extc`（`mn=-18`）、
  `extremum_empty.extc`（空输入走兜底，`empty=-6`）与两条反例（`tmp[..]` 实参、两个消费者）；
  正例要求生成 C 里没有临时视图。
- **还没做**：跨 `par` 融合、`ndview` 上的归约（`seq::sum`/`max`/`min` 只认 `slice<T>`）。

## 第 2 层的进展（二）：S2 归约融合与 S3 流式归约（已落地）

S1 之后再进一步：`var acc = init` 与"升序单累加器归约循环"也折进写循环 ——

<!-- fragment -->
```extc
// 改前：写临时视图，再从头读一遍累加
var tmpv: mut slice<f64> = new f64[n]
for i in 0..n { tmpv[i] = a[i] * 2.0 + 1.0 }
var cs: f64 = 0.0
for i in 0..n { cs = cs + tmpv[i] * 0.5 }

// 改后：一趟，tmpv 不存在；累加顺序仍是 i 递增（逐位相同）
var cs: f64 = 0.0
for i in 0..n { cs = cs + (a[i] * 2.0 + 1.0) * 0.5 }
```

- **替掉哪一行仪式**：`sum(tmp)` 前那趟"先落数组再从头读"的中间物化（以及为此分配的临时视图）。
- **代价 / 不能用的情况**：累加器必须是标量、声明紧挨着写循环（写在两者之间）；只认 `+` 且
  累加器在左边；归约必须是升序（区间 `for` 天然如此）；写侧的右值不许读累加器（否则会把两段
  交错）；`*` 与跨元素依赖仍不认。
- 归约循环也可以写成容器形式 `for v in tmp { acc = acc + v }`：检查器先把它改写成与写循环同一
  迭代空间的索引循环（要求写循环的上界就是 `new T[len]` 的 `len`），再交给 S2 折叠；元素必须以
  `v` 本身参与累加，否则不融合。
- S1 + S2 串起来就是 S3（`bench/fusion` 的 `stream` 形状）：两层元素链 + 归约，三处全化掉。
- **判据**：`tests/fuse/` 增 `reduce.extc`（S2）、`stream.extc`（S3）与两条反例（`*`、累加器在
  右边）；`bench/fusion` 三臂：S1 19.05 vs 38.40 ms（2.02×）、S3 11.86 vs 77.15 ms（6.5×），
  融合与手写融合相差 ~2–5%，三臂 `cs` 相同。
### 第 2 层的进展（三）：整数组表达式 `out = a + b`（已落地，rank-1）

写循环这一行仪式本身也去掉了：目标是可写 `slice<T>`、右边是逐元素运算时，编译器直接把它
降成写循环。

<!-- fragment -->
```extc
// 改前：三行（循环头、循环体、没有别的）
for i in 0..n { out[i] = a[i] + b[i] * k }

// 改后：一行
out = a + b * k
```

- **替掉哪一行仪式**：逐元素写循环的循环头与 `[i]` 下标；临时视图本来就不用写（融合负责）。
  累加形式也一并：`out += a * 2` 就是 `out = out + a * 2` 的逐元素版本。
- **代价 / 不能用的情况**：目标必须是 `mut slice<T>` 变量本身（结构体字段位置暂不认）；右值只认
  `+ - * /`、一元 `+ -`、视图名、标量名与字面量的组合，任何调用/`new`/下标/切片/字段都不认；
  每个参与视图必须与目标等长（运行时守卫，不等就 trap，不静默截断）；裸视图名 `buf = t` 仍是
  视图值赋值，不是逐元素拷贝；`par` 体里仍写显式 `out[i] = …`。
- **判据**：`examples/array-expr.extc`（两种形状的期望输出）、`tests/traps/arrexpr_len.extc`
  （长度不一致必须 trap）、`docs/usage/language.md` §7.4 的完整程序；实测 AXPY 与手写 C 同量级
  （1M 元素 ×200 轮：extC 0.97–1.01 s vs C 1.06–1.07 s）。
- 跨函数 `seq::sum` / `seq::max` / `seq::min` 的识别已落地（见进展（三）（四））；多下标与
  `ndview` 形状的整数组表达式也已落地（rank-2/rank-3 直译成 `nd::*Into` 内核）。
- 还没做：跨 `par` 融合、`ndview` 上的归约（`seq::sum` 只认 `slice<T>`）、`vector::snapshot` 仍是
  显式拷贝（故意如此：它是拷贝，不是借出）。

**下一里程碑（不在这一轮的范围里）**：跨 `par` 融合（`par` 写临时视图 + 归约合成两次遍历）、
`ndview` 上的归约（`seq::sum`/`max`/`min` 只认 `slice<T>`，`nd::sumv` 还没有跨函数识别）、
`vector::snapshot` 是**故意**显式（拷贝语义要写出来，不做隐式转换）。

## 不做的

- 不追隐式分配、GC、惰性求值：`c = a + b` 的"顺手分配"不进入语言，只做"降低成循环"；
- 不为了短而把所有权藏起来：`mut`、`ref`、视图的生命周期仍然写在类型里；
- 同一语义不加第二种写法：新糖落地时，旧写法要么删掉要么写进本文的"为什么不能再简"。
