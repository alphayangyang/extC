# CodeGen 评审与修理（2026-10-05）

> 本文是**今天的施工图**：先记 bug，再记"为什么这套机制难维护"（都是代码本身的事实），

## BG-1：`extc_print` 未使用却被发射（2026-10-04 发现，2026-10-05 记录）

### 症状

一个**不打印结构化类型**的程序，生成物里仍然有 `extc_print`（只被它自己函数体里的递归调用
提到 ⇒ 没有外部使用者）⇒ `clang`/`gcc` 的 `-Wall -Wextra -Werror` 报
`unused-function`（clang 另报 `-Wunneeded-internal-declaration`）✗。
实测触发：往 `stdlib/std/io.extc` 加几个无害的 helper，`tests/coro` **六个夹具全灭**。

### 根因（一行）

```c
/* src/back/codegen.c:8665 一带 */
if (g.needRuntime || g.eqNeed.len) bufPuts(out, bufCstr(&g.rt));      /* 块 A */
if (g.needRuntime)                 bufPuts(out, bufCstr(&g.rtPrint)); /* 块 B：extc_print 在这里 */
```

`rtPrint` 与 `rt` **共用 `needRuntime` 这一个粗旗子**，而两者的需求**不同**：
任何需要 `rt` 的程序都会把 `rtPrint` 一起发出去 ✗。

### 为什么这条 pass 救不了它

运行时块里"没人用就删"的规则**本来就有**，而且是对的（`dropRuntimeDefs`，codegen.c:5904 起）：

```c
size_t total  = countMentions(text, name);             /* 整篇里出现几次 */
size_t inside = countMentionsIn(g, ln, span, name);     /* 它自己那段片段里出现几次 */
if (total == inside) { ...删掉... }                      /* 除了它自己 ⇒ 删 ✓ */
```

自递归的调用就在 `span` 之内 ⇒ 天然不算"外部使用" ✓。**但这条 pass 只扫 `g->primText`**，
而 `extc_print` 住在 `g->rtPrint` ⇒ **它从来没被看见** ✓✓。

### 两个加重症状的细节

1. 描述符表的**注释**里曾写着 `extc_print` 这个名字，而判定是**文本计数** ⇒ 注释里提一次
   = 一次"外部使用" ⇒ 即使进了那条 pass 也删不掉 ✗（**已修**，2026-10-04）；
2. 兜底（现在仍在）：给它的定义加 `__attribute__((unused))`。为什么不用
   `static inline`：GCC 认，Clang 反手报 `-Wunneeded-internal-declaration` ✗。

### 正解

**不要修 `needRuntime` 的粒度**（它的注释里写着真出过 bug：漏发 = 生成物坏掉 ✗），
而是让这个块**进入"被引用才发"的机制**：块级判定改为"这个块里有没有被引用到的片段"，
再把块里的片段交给同一套删除逻辑（见下面的施工步）。

### 为什么它这么久没被发现

**没有任何判据断言过"产物里的符号该不该在"**：全语料只验"是合法 C"，
`-Werror` 只用在**一个**夹具上 ✗。所以"删不掉"完全不可见，"删错了"要靠运气撞见。
（这是"为什么没发现"的解释，**不是**质量依据 —— 见开头的原则。）

## 维护性：为什么这套机制难改（今天的重点）

| # | 事实（代码本身） | 数字 | 后果 |
|---|---|---|---|
| ① | `dropRuntimeDefs` 是一个**266 行**的函数，要同时握住：anchor 技巧（**拿缓冲区第一行当锚**）、6 条行形规则、宏的 guard/define 覆盖、大括号配对量 span、`span=0` 的语义、游标推进陷阱、"砍一次重扫整篇" | 6 条规则 | 无法局部推理 ✗ |
| ② | **同一件事两处知识**：发射端知道"定义长什么样"，删除端另有一套"怎么认出一个定义" | 2 处 | 谁改了另一边**不报错**：静默"删不掉"或**删错** ✗✗ |
| ③ | 手维护旗子 | **15** 个声明 · **41** 处置位 · **21** 处发射门控 | 加一个运行时助手要同时改对两个**条件不同**的地方 ✗（BG-1 就是） |
| ④ | 删除是多轮重扫：两处 `for(;;)` + `!cut ⇒ break`，每轮每候选做整篇 `countMentions` | 2 处 | 运行时间不可预测（`` #define EXTC_ZON `` 让 `hashSet.extc` 烧 15 分钟 ✗） |

**结论：问题不是"判据没覆盖"，而是这套机制把"活跃性"放进了"文本"里** —— 结构性的不可维护。
疤痕注释已有 **46** 条，且还在增加。**烂的是策略层（≈600–700 行），不是 C 发射层**。

## 施工步（按维护性，不按判据）

| 步 | 内容 | 消掉 | 量 |
|---|---|---|---|
| **S1** | **运行时片段走登记 API**：发射时就地登记 `{name, kind, 偏移}`；删除端**直接用登记信息**，不再从行形猜；块级门控 = "本块有没有被引用的片段" | ②③、④大部分 | 中 |
| **S2** | **活跃性搬回编译器数据结构**：发射前从入口做可达性（`plan` 里已有 `used`），只发可达者 ⇒ 删除 pass 退成"断言者"或删除 | ①②③④ | 大 |

### S0（先做）：把"改动效果"变成可观测的

今天要动 codegen，**先取一份当前产物的指纹**（全语料逐个编译 + 哈希），这样每一步改动
"到底改了什么"是可测的 —— 这是**数据**，不是判据。
