## 0. 使用规则

### 0.1 决策优先级（本文确立，仓库此前从未写明）

审计中发现同一问题在不同文档里有**互相矛盾**的口径（例：移位超宽，`DECISIONS.md` 2026-09-18 建议"按位宽取模"，
而更新的 `manual/01-safety.md` 与代码都是 **trap**）。为消除这种不确定性，确立以下优先级：

| 顺位 | 依据 | 说明 |
|---|---|---|
| ① | **本文的裁定** | 本文件是审计后的一次性收敛；与它冲突的旧文一律失效 |
| ② | **较新的决策** | 同一问题有新、旧两条决策时**取新**（按文档日期 / 定案序号；无日期的按所在文件的"最后更新"与引用关系判断） |
| ③ | **上位原则**（`SPEC.md` §0.5 / §1："凡是编译期能证明的，运行时不留痕迹"；"不能证明的，语法上必须看得见"） | 旧决策若与上位原则冲突，作废 |
| ④ | **代码与实测** | 代码是"已经实现成什么样"的**事实准绳**；不是"应该怎样"的准绳。裁定与代码不一致时，改代码而不是改裁定 |

> 为什么把"代码"排在最后：审计已经证明，代码里存在大量**与它自己的文档相反**的行为
> （例：`-w` 不作用于模块；`effects` 缺省值与 `ast.h` 的文档相反）。
> 若以代码为准，就会把 bug 固化成设计。

### 0.2 每条裁定的格式（R1–R18）

```
R<n> · 标题
  问题      —— 一句话，说清"没定/过时/含糊"的是什么
  相关审计  —— P0-x / P1-x / 条目位置
  既有决策  —— 引用新旧决策（含冲突），并注明本文取哪条、覆盖哪条
  裁定      —— 必须可执行：约束到接口/不变量/pass
  理由      —— 为什么这样对（优先引上位原则或形式化结论）
  代价      —— 明确的损失（精度、性能、代码量、迁移成本）
  落地      —— 步骤（改哪个文件/哪个 pass）
  判据      —— 双向验收：该挡的要挡 / 该放的要放
```

### 0.3 与审计报告的关系

审计报告回答"**哪里坏了**"；本文回答"**应该是什么样**"。
审计 §8 的六批修复顺序不变，但每一批开工前先读本文对应条目。

## 1. R1 · 分析类 pass 的正确性契约（记账不变式）

**问题**：逃逸/生命周期分析（`check_escape.c` + `check_top.c` 的效果摘要 + `dataflow.c` 的深度不动点）
在文档里有一条核心纪律（`ARENA-FORMAL.md:358` 的 **(S3)**："任何能让某个值的内容发生变化的规则，
都必须把写进去的东西的深度取上界记回那个值（`max`，不是覆盖）"），
但**它只是注释级的愿望**：没有任何断言、没有判据、没有测试在守它。
`ARENA-SOUNDNESS.md` §4 已证伪两条不变量，本文审计又找到 8 类新洞——
它们全部是同一个形状：**"记账比真实情况小"**（记小 = 洞；记大 = 只是误拒）。

**相关审计**：P0-1（`EX_TRY` 不进逃逸集合）、P0-2（`0` 当哨兵⇒求成最大值）、P0-6（四条载体/身份/早退漏洞）、
P0-16（出参写入不产生 publication）、P0-17（路径非空证明不失效）、P1-1/P1-2/P1-3（逃逸族）、
P1-4（32 位掩码）、P1-5（`fresh` 集合不失效）、P1-6/P1-7（trait 一致性跳过）。
另有 `ARENA-SOUNDNESS.md` §5 的 7 个反例（A–G，全部实测 UAF）。

**既有决策**：
- `ARENA-FORMAL.md:358` (S3) 不变式 + §6.6"留给将来的记账不变式"（本文引用为 **INV-M**）；
- `ARENA-SOUNDNESS.md` §7.1 的 P1/P2/P3（上界性 / 单调性 / 写点完整）与 §7.2 的可行性实测
  （补 P1+P2 的一部分：9 个反例修好 7 个，`tests/run.sh` 256 通过 / 1 失败，失败的是被牺牲的"强更新"精度）；
- `ARENA-FORMAL.md` §7.4"没有别名信息 ⇒ 只能用弱更新"（硬门槛）、§8.4 分档落地（档 1/2/3）。
- **无新旧冲突**：这些是同一方向上的递进，本文全部采纳并扩展。

**裁定**：把下面 9 条写成**可执行契约**（不是注释），并配断言 + 双向判据。

| 编号 | 不变式 | 内容 | 违反时的方向 |
|---|---|---|---|
| **INV-H** | 上界性 | 任何表达式/绑定的记账深度 ≥ 真实层号 | 记小 ⇒ 不健全，必须拒绝提交 |
| **INV-M** | 单调性 | 任何"改一格"只许 `max(旧, 新)`；禁止覆盖式更新 | 覆盖 ⇒ 可能记小 |
| **INV-I** | 身份 | 一切判定按**符号（`Sym *`）/来源链**，不按名字字符串；名字只用于诊断 | 同名遮蔽 ⇒ 判错对象 |
| **INV-C** | 载体穿透 | 每个"包装型"表达式节点都必须穿透（`EX_TRY`/`EX_DEREF`/`EX_STRUCTLIT`/`EX_ARRAYLIT`/`EX_CONV`/`EX_LAMBDA`/`EX_METHOD`…）；新增 `ExprKind` 时若未在穿透表里登记，**编译期报错** | 漏一个 ⇒ 洗白通道 |
| **INV-F** | 生命周期 | 集合（`escapees`/`fresh`）与摘要必须在**写点失效**，或对整个函数体迭代到**不动点**；只建一遍 = 违规 | 不失效 ⇒ 旧事实当新事实 |
| **INV-S** | 哨兵 | "未设置"与"最浅（0）"必须是**两个可区分的表示**（`bool seen` 或 `INT_MAX`），不许用 `0` 兼任 | 兼任 ⇒ 取 min 变成取 max |
| **INV-K** | 写点完整 | **每一条**写入路径都产生 publication：直接赋值、字段/元素写、字面量初始化、`mut ref` 出参（经被调方效果摘要回报）、`@overwrite` 目标、协程跨挂起点的局部 | 漏一条 ⇒ 目的绑定停在旧深度 |
| **INV-P** | 参数索引 | 效果摘要按**参数下标**索引；位掩码设显式上限（建议 64）并在超限时**编译期报错**（或改数组）；缺省值取**保守**（`Thread=1`） | 越界/缺省 ⇒ 检查整段失效 |
| **INV-U** | 未知保守 | 判定不出来的地方一律按**更保守**方向（深度记**大**、可达记**是**），不许 `return 0`/`return false` 兜底 | 兜底即 fail-open |

**理由**：这是"承诺 9（引用不能活得比被指对象长）"的全部实现基础。
上位原则 P：能证明的不留运行时痕迹 ⇒ 证明必须**真**；P′：不能证明的语法上看得见 ⇒ 证不出来时必须拒绝或要求显式签字。
`ARENA-FORMAL.md` §7.2 已证明"放大区域永远安全"⇒ **精度只买内存，soundness 不靠精度**，
所以任何一处拿不准都可以保守，不需要新的设计。

**代价**：补 INV-H/M/K 会牺牲一部分"强更新"精度（`ARENA-SOUNDNESS.md` §7.2 实测：1 个例子从接受变误拒），
必须按 `ARENA-FORMAL.md` §7.3 的格式记进 `PLAN.md`；INV-F 的不动点会让编译时间上升（用 worklist + 轮数上限控制）。

**落地**：
1. 在 `check_internal.h` 里把 9 条写成注释块 + 对应断言宏（`EXTC_SELFCHECK` 下启用）；
2. `check_escape.c`：`exprRefDepth`/`placeDepth`/`exprBorrowed`/`valTracesToParam`/`destIsParam`
   改成符号身份 + 统一"载体穿透"函数（INV-C/I）；`placeDepth` 的兜底改记最深（INV-U）；
3. `check_top.c`：`escapees`/`fresh` 改成"写点失效 + worklist 不动点"（INV-F）；
   调用点深度求解的哨兵改 `bool seen`（INV-S）；摘要掩码改 64 位 + 上限断言（INV-P）；
4. `check_stmt.c`：所有写路径统一走一个 `noteStore()`（INV-K），出参写入由调用点按效果摘要补 publication；
5. 判据：`ARENA-SOUNDNESS.md` §7.3 的四条 + 本文新增反例（P0-1/2/6/16/17 的最小程序）全部变成编译错误；
   `examples/`、`tests/asan/`、`tests/arena/`、`tests/arena-promoted/` 全绿。

## 2. R2 · 身份：符号，不是名字

**问题**：多处分析用**名字字符串**当身份。参数遮蔽是合法且文档化的（`examples/shadowing.extc` 第 4 条），
一旦遮蔽，`strcmp(param->name, root)` 就指向了错的参数。

**相关审计**：P0-6(d)（`check_escape.c:726` 按名字匹配参数）、P1-2、以及 `check_top.c:2397` 的效果收集
（`paramIndex` 按名字）、P2（`isStdlibFile` 用路径前缀字符串比较 ⇒ 一个 `-I` 拼写即可绕过特权闸门）。

**既有决策**：`DECISIONS.md` 定案 97（"新绑定路径必须复用 `declare` 的收窄契约"）与定案 96（特权层只有标准库能碰）
方向一致；未发现相反决策。

**裁定**：
1. 语言侧身份一律用 `Sym *`（绑定）与**来源链**（`EX_FIELD`→obj、`EX_INDEX`→obj、`EX_DEREF`→operand…）；
   名字只在诊断里出现。
2. 需要"跨 pass 记住一个名字"的地方（如 `DeadLocal.funcName`、`fresh` 集合）必须改成记住
   `Sym *` 或**稳定 ID**（`cname` 只在同一函数内唯一 ⇒ 可以，但要配"同一函数"断言）。
3. 敏感判定（`isStdlibFile`、`@builtin` 闸门）必须用**规范化后的真实路径**（`realpath`）比较，
   不用前缀字符串。

**理由**：名字是**语法**，符号是**语义**；所有"记小了就是洞"的失败模式里，身份错配占了三类（遮蔽/别名/前缀）。

**代价**：`Sym` 生命周期与 arena 绑定（进程级），跨编译单元无影响；改动集中在 `check_escape.c`/`check_top.c`/`check_lookup.c`。

**判据**：`examples/shadowing.extc` 编译行为不变；P0-6(d) 的 `m3.extc` 变成编译错误；
`isStdlibFile` 的绕过用例（`-I <stdlib 前缀>+后缀`）被拒。

## 3. R3 · 集合与摘要的生命周期：失效或不动点

**问题**：`escapees`（逃逸集合）、`fresh`（新分配局部集合）、效果摘要（`addrMask`/`contMask` 等）
都是"一遍扫描边扫边记"，**没有任何失效机制，也不是不动点**。程序形状一旦要求"后来才发现某名字也逃逸"，
记录就不再更新；反过来，一个名字被重新指向之后，旧记录仍然被当成事实。

**相关审计**：P0-1（`EX_TRY` 没进集合）、P0-3（自由泛型函数的零值检查从不记录）、P0-5（延迟调用单趟）、
P1-5（`fresh` 不失效）、P1-4（掩码越界）、以及 `P2`（level pass 恒跑满 32 轮）。

**既有决策**：`ARENA-FORMAL.md` §5.1（故意保留的近似四处）、§8.5（"不动点 × 泛型实例数"的代价讨论）、
`ARENA-SOUNDNESS.md` §3（"记账有哪些数：谁写、谁读、答哪个问题"）都指向同一条路；无相反决策。

**裁定**：
1. **函数级**：逃逸集合与效果摘要用 **worklist 不动点**：
   - 初值 = 保守（不假设任何东西"不逃逸"）；
   - 工作项 = （名字/符号，新事实）；事实只允许**变大**（更保守）；
   - 每轮重扫受影响的语句；轮数上限（如 64）到达即**保持保守值**并记一条 `[budget]` 诊断（不是报错）；
   - 单调性由 INV-M 保证 ⇒ 必然收敛。
2. **写点失效**：`fresh` 一类"某名字当前指向新分配"的事实**必须在任何再赋值/字段写/出参写时撤销**
   （实现：把事实挂在 `Sym` 上，写点直接清）。
3. **跨函数**：效果摘要是调用图上的闭包 ⇒ 按**拓扑序**（有环时 SCC 缩点）迭代到不动点；
   泛型实例化与摘要计算共享同一轮不动点（这正是 P0-5 缺的东西）。
4. **禁止"单趟"假设**：任何"边扫边定"的分析必须在注释里写明失效条件，并有一条测试覆盖"后来才成立"的形状。

**理由**：INV-H + INV-M 只保证"不记小"，不保证"记全"；记不全 = 漏报 = 洞。
上位原则要求"能证明的不留痕迹"，而"证明"必须覆盖整个函数，不是扫描顺序的第一个前缀。

**代价**：编译时间上升（实测同类不动点在 level pass 上是 O(轮数 × 函数体)）；
用 worklist + "只处理受影响的语句"摊平。允许"轮数到顶仍保守"⇒ 只会多误拒，不会漏。

**判据**：P0-1 的 `tryb3.extc`、P1-5 的 `fresh2.extc` 变成编译错误；
`tests/arena-promoted/` 22 例从"全部通过"扩展到"含 `?`/`??`/`@overwrite` 的变体全部通过"；
`-w` 之外不得新增警告噪音。

## 4. R4 · 泛型：实例化的不动点与名字保留

**问题**：两件事没定清楚，导致 5 条 P0/P1：
(a) 延迟调用点**只解析一遍**，于是"内层模板先声明"的程序生成对未定义 `f_T` 的调用（P0-5）；
(b) 编译器合成的 C 名（实例名、帧名、数组类型名、枚举实例名、句柄辅助名）**没有保留表**，
   用户声明可以与之相撞，或者 typedef 被门控在一个"只有取值用法才置位"的 flag 上（P0-9、P1-8/9/10/11、
   genwarn 1/2/3/5、types 单元 2 条）。

**相关审计**：P0-4（实例数上限后返回 NULL 被解引用）、P0-5、P0-9、P1-7、P1-8…P1-13、P1-19、
`codegen-4` 的实例名守卫、`types` 单元的数组/枚举实例名冲突、`genwarn` 的四条"名字发了、定义没发"。

**既有决策**：`HARDENING.md` H8（自递归实例化失控 ⇒ 上限）、H9（泛型返回 T 的零值用模板名）、
H10（用户类型名撞实例 C 名 ⇒ 生成非法 C，"已落地，兜底"）——注意 **H10 自认只是兜底**，
且审计证明兜底只覆盖了 `TY_GENERIC && sdef` 一类（数组与枚举实例漏掉）。取"H10 的精神"、补全其覆盖面。

**裁定**：
1. **实例集合 = 不动点**：`已实例化集合 + 待处理工作项`，每轮把"新实例体内的调用点"加进工作项，
   直到没有新实例；延迟调用批处理**不得**依赖记录顺序（修 P0-5）。
2. **上限语义**：达到 `TYPE_DEPTH_LIMIT`/`FUNC_INST_LIMIT`/轮数上限时，
   **返回一个哨兵实例（`isError`）并让调用方短路**，绝不允许返回 `NULL` 被解引用（修 P0-4）。
3. **保留表**：编译器合成的一切 C 名进入一张**保留表**（`CG.reservedNames` 或 `TypeTable` 侧）：
   `array_<n>_<elem>`、`<enum>_<arg>`、`<fn>$frame`、`<fn>$step`、`c$frame`、`extc_*`、`__extc_*`、`Extc*`。
   用户声明与保留表冲突 ⇒ **编译错误**（给出"请改名"与冲突来源），不是静默重定义。
4. **名字只有一处来源**：帧结构名、`$step`/`$next`/`$value`/`$send` 辅助名、dyn 表名、描述符名
   由**同一个函数**产生（`coroFrameName()` / `instanceName()` / `typeName()`），checker 与 codegen 都调它；
   禁止在 codegen 里用 `cFuncName` 与 `cType` 各拼一次（这是 P1-8 的根因）。
5. **发射与门控**：任何"名字被发射"与"定义被发射"必须由**同一个条件**决定；
   做法：把"需要什么"收集成一个**需求集合**（descriptors/typedefs/frames/dyn tables），
   在发射前统一求闭包，而不是散落的 `needX` 布尔。`--check-c` 必须覆盖"只用不构造"的数据位置
   （genwarn 的四条正是这个形状）。
6. **实例命名可读性**：实例名继续沿用现有 mangle 风格（人可读、稳定），但**不再承担唯一性**
   （唯一性由保留表 + 冲突检测保证）。

**代价**：不动点会稍微增加编译时间；保留表可能拒绝一些今天能编译（但产物非法）的程序——这是**修 bug**，
不是破坏兼容。跨模块的实例名需要模块前缀（已有 mangle 机制）。

**判据**：`g3.extc`（声明顺序）与 `g3r.extc`（反序）**都**编译通过且产物可编译；
`tests/generics/`、`tests/impl/`、`tests/genmatrix/` 全绿；
`struct array_3_i32` 与 `[3]i32` 同时出现的程序报"名字冲突"；
`struct holder { h: coroutine<i64> }`、`[2]dyn Tag`、`box<coroutine<i64>>` 的产物可编译（genwarn 1/2/3）。

## 5. R5 · 算术与转换语义（把"待定"正式定案）

**问题**：`DECISIONS.md:29-41` 明确把**整数算术语义列为"待定"**，并给了一条 2026-09-18 的建议
（绕回 + 除零 trap + **移位取模**）。此后手册与代码把"移位超宽"改成 **trap**，但**没有任何文档正式关闭这个待定项**；
更严重的是**窄类型（i8/i16/u8/u16）的运算宽度从未被规定**，而代码在 C 的 `int` 宽度上算且不回截 ——
于是 `a: i8 = 100; a+a` 得到 200（超出 i8），`var x: i8 = a+a` 得到 −56，`a+a == x` 为 **false**（P0-18）。

**相关审计**：P0-18（窄类型不回截）、P0-12（f64 整数值字面量发成整型）、P0-19（`?` 载荷静默窄化）、
P1-19（64 位换符号不 trap）、P1-20（`(double)INT64_MAX` 上界）、P1-21（`extc_arena_alloc` 尺寸溢出）、
differential 的 `1e9*1e9` 溢出。

**既有决策与冲突（本文按"取新"处理）**：
- `DECISIONS.md:36` 有符号溢出 **绕回**（`-fwrapv`）——采纳；
- `DECISIONS.md:38` 移位 ≥ 位宽 **建议取模** ← **旧**；`manual/01-safety.md:40,132` 与代码是 **trap** ← **新** ⇒ **取 trap**；
- `manual/04-types.md:69` 整数收窄/换符号 **装不下 ⇒ trap（带位置）** ⇒ 采纳；
- `manual/04-types.md:71-73` 浮点→整数 **超范围/NaN ⇒ trap，向零截断**；浮点之间**不检查**（±inf）⇒ 采纳。

**裁定**：
1. **宽度是值的属性**：`i8 + i8` 的类型是 `i8`，**结果按 `i8` 回绕**（模 2^8）。
   实现：窄于 32 位的算术在发射时回截到声明宽度（`(int8_t)(a + b)`），
   比较/提升按语言既有规则先拓宽再比。这条**同时**修 P0-18 与"类型系统自相矛盾"。
2. **有符号溢出 = 按该类型的宽度回绕**（i32/i64 由 `-fwrapv` 保证；窄类型由回截保证）。
   **编译器必须保证生成的 C 不依赖 UB**：核对我们自己的发射（含一元负、`<<`、窄类型提升）。
3. **除法**：除零 trap（现状）；**溢出除法（`INT_MIN / -1`）在所有宽度都 trap**（今天只有 i64 检查 ⇒ P1-19 家族）；
   取余同理。
4. **移位**：负数移位数或 ≥ 位宽 ⇒ trap（覆盖 09-18 的"取模"建议，理由：与手册一致、且"静默取模"属于 P′ 禁止的静默行为）。
5. **转换**：收窄/换符号/浮点→整数一律"装不下 ⇒ trap"；**检查在源域做**（不许先把源值 cast 进目标域再查）；
   64 位换符号两个方向都要真检查；
   浮点上界用**可精确表示**的界（`i64` 的上界写成 `< 9223372036854775808.0`，不是 `<= (double)INT64_MAX`）。
6. **字面量保持类型**：浮点字面量无论数值形态都必须发射为 C 浮点常量（整数值补 `.0`）；
   字符串字面量的字节必须与词法器的解码**逐字节一致**（含 `\x`、裸 NUL）。
7. **常量折叠与运行时一致**：编译期能证的溢出/越界/除零报编译错误（既有口径），
   运行时路径一律 trap；两者不得给出不同结果。

**理由**：上位原则 P（能证明不留痕迹）与 P′（不能证明语法上看得见）。
"窄类型在 int 宽度算"直接违反类型系统自身的承诺；`DECISIONS.md` 的待定项必须关闭，否则每个 pass 都可以自行解释。

**代价**：窄类型程序可能出现新的 trap（以前静默回绕）——这是**修正**，需要在 `manual/04-types.md` 明确写出来
并加例子；常量折叠路径需要复核（避免把合法的 `i8` 常量运算报错）。

**判据**：新增 `tests/traps/narrow_div_overflow.extc`、`tests/ops/narrow_wrap.extc`；
`a+a == x` 必须为 `true`；`1.0/2.0 == 0.5`；`-0.0` 打印 `-inf` 的倒数；
`u64(i64(-1))` 与 `i64(u64max)` 都 trap；差分 fuzz（900 例）零 mismatch。

## 6. R6 · 求值顺序与临时量（前缀契约）

**问题**：语句前缀（`pfLine`）里的临时量被**提前冲刷**，而 `while` 条件每轮都要重新求值 ⇒
条件里的调用只执行一次（P0-7）。同类问题在 `??`、重载运算符、数组 `==`、`trap(new ...)` 上都出现过。
契约只对 `??` 做了特判，没有一般化。

**相关审计**：P0-7（数组 `==` 提升出 `while`）、P1-17（前缀/冲刷顺序错 ⇒ 未声明标识符、
`a += (get() ?? ...)` 的临时量声明在使用之后）、P2（`??` 的求值次数）。

**既有决策**：`check_stmt.c:894` 的 `noHoist` + `check_expr.c:2624` 对 `??` 的拒绝 —— 这是**特例**，说明方向已被认可；
需要把它一般化。

**裁定**：
1. **契约**：一个表达式在**每次被求值**时，其副作用必须恰好发生一次；
   **禁止**把"求值该表达式所需的语句"提升到"重复求值该表达式"的作用域之外
   （循环条件、短路右操作数、`match` 守卫、循环体但条件在外）。
2. **实现**：给表达式发射引入 `cgEval(expr)`，语义 = "先冲刷前缀，再求值"；
   所有需要"语句 + 表达式"混合的地方（比较、运算、调用、赋值）统一走它；
   在前缀非空却要生成"必须每轮执行"的位置时，改用**逗号表达式/内联函数**而不是前缀。
3. **检查器兜底**：`noHoist` 从"只有 `??`"扩展到"一切可能产生临时量的表达式"，
   在循环条件/短路右操作数处给出**编译错误**（信息：把该表达式提到循环外并显式重算）。

**理由**：C 的求值语义就是"每次求值都执行"；前缀提升是发射器的**内部优化**，不能改变语义。
上位原则：不能证明"提升后语义不变"就不许提升。

**代价**：部分循环条件需要改写（今天能编过的少数形状会变成明确错误，附改写建议）。

**判据**：`i_while2.extc` 打印 `rounds=1`；`i_while.extc` 不再死循环；
`trap(new u8[n()])`、`a += (get() ?? vec2{...})` 的产物可编译；`tests/traps/`、`tests/ops/` 全绿。

## 7. R7 · 生成 C 的发射契约

**问题**：编译器的中心承诺是"类型检查通过 ⇒ 生成物能编译"，但审计找到 **13 条**"extc 退出码 0、产物编不过"，
以及若干"产物含 UB"（NULL `memmove`、`__extc_a[2]` 越界、`(1/2)`、窄类型算术、`i8` 位运算…）。
根因有三：名字/定义门控不一致（R4）、前缀契约（R6）、以及**发射阶段缺少统一的自检**。

**相关审计**：P0-8、P0-11、P0-9、P1-8…P1-18、P1-22、genwarn 全部、`--check-c` 全语料扫描发现的
`stdlib/std/coro/scheduler.extc`。

**既有决策**：`manual/12-driver.md` 的 `--check-c` 是"生成后再做一次 `cc -fsyntax-only`"（2019 口径）；
`HARDENING.md` §0.4"不能破的约定"。**冲突**：`-fsyntax-only` 看不到中端告警（审计实测），
且默认不开启 ⇒ 承诺没有闸门。

**裁定**：
1. **承诺**：`./build/extc f.extc` 成功 ⇒ `cc -std=c11 -O2 -Wall -Wextra -c f.c` 必须成功且**无本文列出的告警类别**
   （未初始化、越界、`stringop-*`、严格别名、移位、`null-dereference`、整型转换、隐式声明、除零、溢出）。
2. **闸门**：`check.sh` 增加"全语料 `--check-c`"节，`--check-c` 内部从 `-fsyntax-only` 升级为
   `-c -O2 -Wall`（`-w` 只降噪不降类），并同时用 gcc 与 clang（`CC` 可覆盖）。
3. **单一定义源**：见 R4.4/R4.5。
4. **产物不得有 UB**：生成物里凡"可能 UB"的构造都必须由运行期检查兜住
   （NULL view、尺寸溢出、除零/溢出除法、移位、越界），或由编译期证明排除。
5. **`-O0` 与 `-O2` 语义一致**：同一程序在两个优化级别下必须给出相同输出（审计已见两处相反：
   NULL `memmove` 在 `-O2` 被删、`f64→i64` 越界在两级不同值）。把"双级别对拍"加进闸门。

**代价**：闸门会让 CI 变慢（全语料两遍 C 编译，实测约几分钟）；`--check-c` 变慢是用户可感知的（只在显式开启时）。

**判据**：全语料 `--check-c`（gcc+clang，`-c -O2`）零失败；`-O0/-O2` 对拍零差异。

## 8. R8 · 编译器自身的资源上限（**本裁定为新拍板**：登记册无相关定案）

> **2026-09-30 已落成定案 100**：上限**暂定** 64 层（块/表达式）、96 层（类型），实测校准
> （release ~250 崩、ASan ~96 崩），作为成文限制进手册；主人口径「暂时接受，之后再提升」
> —— 提升路径是 parser/dataflow/checker/codegen 迭代化（显式栈），列入 P4 手术。

**问题**：编译器对输入规模没有预算：parser 递归（16000 层括号 SIGSEGV）、dataflow 互递归（~200 层块 SIGSEGV，
帧 41 KB）、`blkMaxOfBlock` 指数（30 层 5.5 s、40 层挂死）、`funcReachesItself` 指数（34 层 36 s）、
level pass 平方、以及 `dropRuntimeDefs` 的**死循环**（P0-22，52 行输入 >15 分钟不返回）。
共同形状：**循环/递归没有"必须推进"的证明，也没有预算**。

**相关审计**：P0-10（两类栈溢出）、P0-22（死循环）、§6.1–6.9（性能族）、P2（`funcReachesItself`、level pass）、
`dataflow` 单元（`depth` 参数从不比较）。

**既有决策**：`PLAN #59`（泛型 fold 曾让层号求解器走 2^32 条路径 ⇒ 不返回、零诊断）说明"必须给诊断"的口径；
`check_top.c:3091` 的 `LVL_STEP_BUDGET` 只打印不停（审计 P2）。无相反决策。

**裁定**：
1. **一切循环必须有推进证明**：`for(;;)`/`while` 的每个"不删除、不前进"的分支都要推进游标；
   代码评审清单 + 静态检查脚本（`tools/check_loops.py`：扫描带 `memmove`/`strstr` 的循环，提示手工确认）。
2. **显式预算**（每个都有：上限值 + 超限行为 + 诊断文案 + 位置）：
   | 预算 | 上限（建议） | 超限行为 |
   |---|---|---|
   | parser 嵌套深度 | 512 | 编译错误："nesting too deep (limit 512)" |
   | dataflow 递归深度 / 帧大小 | 128 层 或 将 `Facts` 移出栈 | 保守结果 + `[budget]` 警告 |
   | `blkMax*` | 不再指数（去重 + 记忆化） | —— |
   | 泛型实例数/类型深度 | 现有 `TYPE_DEPTH_LIMIT`/`FUNC_INST_LIMIT` | 哨兵实例 + 错误（见 R4.2） |
   | 不动点轮数（逃逸/实例/level） | 64 | 保持保守值 + `[budget]` 诊断 |
   | `funcReachesItself` | visited 集（不是深度上限） | —— |
   | 单文件编译时间 | 可选 `--time-budget`（默认关） | 超时诊断 |
3. **诊断优先于崩溃**：任何预算触发都必须**先报错**（带位置、带"这是编译器限制，请上报/请简化"），
   禁止 SIGSEGV/无限循环。
4. **规模用例**：新增 `tests/scale/`（深嵌套、长表达式、多实例、长语句链），断言"要么快、要么给出诊断"（审计 §7 闸门④）。

**理由**：编译器的可用性下限是"任何输入都能在有限时间给出结论"；上位原则不要求快，但要求**有结论**。

**判据**：审计 §6 的全部输入都在 1 s 内给出诊断；`tests/scale/` 全绿；`hashSet.extc` 编译在毫秒级完成。

## 9. R9 · 脱糖契约

> **2026-09-30 定案 101 补两条**：① `for i in lo..hi` 的上界**进入循环时求值一次**（存进隐藏 `let`，
> 不再每轮重算）；② **循环条件里的分配按轮释放**（条件单独一层 arena，每轮一次 release）。
> 前者是语义收紧（`for i in 0..f()` 的 `f()` 只调一次），后者防「条件里分配跨轮累积」。

**问题**：`for` 被脱糖成 `while cond { BODY; step }`，`continue` 跳过 `step` ⇒ 死循环（P0-15）。
`?` 的展开把载荷直接赋给返回槽，没有走 `checkAssignable`（P0-19）。

**相关审计**：P0-15、P0-19、differential 的两条 HANG、P1（`return e?` 1000→232）。

**既有决策**：无专门决策；`?`/`??` 的展开语义散在 `manual/06-expr.md` 与 `manual/15-errors.md`。

**裁定**：
1. **语义以"未脱糖"为准**：`for` 的三段（初始化/条件/步进）与 `continue` 的关系按 C 的 `for` 定义；
   数组/迭代器形式按"每轮迭代推进一次"定义。**脱糖实现必须保证这条**（把步进放进 `continue` 的落点，
   或让 `for` 在 AST 里保留自己的 kind，由检查器/代码生成共同处理）。
2. **`?` 是"早退 + 载荷转换"**：载荷必须走 `checkAssignable`（对 `option`/`result` 的**实例**比较，
   不是只看 `TY_GENERIC`），错误路径最短（现有三句语句展开可保留）。
3. **`??` / `?` / `!` 的求值次数**：操作数恰好求值一次；`!` 只改变检查、不改变求值。
4. **脱糖产物不许逃过检查**：新增脱糖形状时必须有"脱糖后每个节点都过检查器"的断言
   （审计见 `opExpr`/`EX_BIN.func` 因不在 walker 里而漏检 ⇒ 与 R1 INV-C 合并处理）。

**判据**：`for` + `continue` 输出 `0 1 3 4`；`option<i64>`→`option<u8>` 报编译错误；
`a += b` 的重载运算符调用进入所有 walker（`__extc_a` 未声明类错误消失）。

## 10. R10 · 零值与默认初始化

**问题**："哪些类型没有零值"的判定不完整：`fn` 字段、`ref`/`?ref`、**协程/`dyn` 句柄**、
以及**泛型实例的聚合**都能漏过，生成 `(T){0}` 并导致空函数指针调用或空帧驱动（P0-3、lookup 单元 2 条）。
自由泛型函数的延迟检查从不记录（P0-3）。

**相关审计**：P0-3、P0-19、`lookup`（聚合里的句柄）、`genwarn`（泛型实例含协程的零值设计符错）、

## 11. R11 · trait/impl 一致性（**本裁定为新拍板**：登记册无正面定案）

**问题**：一致性检查有四个洞：返回类型"两边都非 NULL 才比"（`void` 逃过）、
没有 `StructDef` 的目标（内建/视图）整段跳过、参数比较从下标 1 开始（无接收者时漏第一个）、
effects 不算签名（trait 签 `Ret=0`，impl 可以不遵守，而 dyn 调用点**信了** trait 的摘要 ⇒ ASan UAF）。

**相关审计**：P1-6、P1-7、P3（参数下标）、escape-2 的 `parser.c:1088`（trait `effects Ret=0` 被 dyn 轻信）。

**既有决策**：`DECISIONS.md` 定案 82（运算符重载 = 方法名写成运算符 + 实例化时检查）、
`topics/TRAITS.md`（若有相关口径）——审计未发现相反决策。

**裁定**：
1. **签名的定义**包含：方法名、参数类型（含 `ref`/`mut ref` 位）、返回类型（`NULL` 与 `void` 规范化为同一表示）、
   **effects 子句**（`Addr`/`Cont`/`Ret`/`Thread`）。四者都要比。
2. **比较规则**：impl 的摘要必须**不弱于** trait（`Addr`/`Cont` 的位集合是 trait 的超集；
   `Ret=0` 必须一致或更保守；`Thread` 必须 ≥）。不一致 ⇒ 编译错误，指向 impl 那一行。
3. **覆盖面**：目标没有 `StructDef`（内建、视图、枚举实例）时**同样**走这套比较（用 trait 侧的签名即可）。
4. **dyn 调用点不许轻信**：调用点的效果判定必须用**实现者的摘要**（或保守取 trait∩impl），
   而不是只看 trait 声明（修 escape-2 的 P1）。

**判据**：`tr2`/`tr3`/`tr4`/`tr6` 全部变成编译错误；`tests/impl/`、`tests/dyn/` 全绿；
trait `Ret=0` + impl 返回借用值的程序被拒。

## 12. R12 · 协程与"任务的地方"：所有权与非 LIFO 释放（**本裁定为新拍板**：登记册 0 条，依据 `CONCURRENCY.md` 专题）

**问题**：`topics/CONCURRENCY.md` 已经有明确决策（"**任务 = 地方根**"，作者拍板 **B**）：帧里存自己的 zone id、
恢复点只读字段、任务结束由调度器/任务表**一次性回收** `zoneLeaveTo(mark)`。
但实现走的是"全局 zone 栈 + 按 LIFO 弹"，而**任务的存活顺序不是 LIFO** ⇒
(a) boxed 任务结束时弹掉**仍存活**的任务 zone（ASan heap-use-after-free，P0-20）；
(b) 反方向：调用者 zone 更低时一个都不弹 ⇒ 每个结束任务泄漏约 4.2 KB（P1-14，实测 20000 个结束任务 85.9 MB）；
(c) 泛型协程句柄**从不调 `extc_task_end`** ⇒ 任务 arena/zone 全泄漏（P1-13，30 万次 57 MB）。

**相关审计**：P0-20、P1-13、P1-14、P1-12（递归计数不配对）、P1-8/P1-9/P1-10/P1-11/P1-22（帧/句柄合成）、
`coro` 单元 8 条（`extc_unix_` 前缀漏发、`inet_pton` 头、epoll 静态队列、任务表只增不减、`http_date` 越界写）。

**既有决策**：`CONCURRENCY.md:443-506`（任务 = 地方根 B、J1 收紧、帧布局断言 ④⑤）——
**本文直接采纳为设计**，实现按它对齐。冲突项：文档 §规则1 说"任务在被步进者的地方里分配"（旧，单栈假设），
与 B 冲突 ⇒ **取 B**。

**裁定**：
1. **所有权**：任务的存储属于**任务自己**（它自己的 arena + zone 链）；`spawn` 把"创建时的 zone"写进帧字段；
   任务体不得直接改全局 `extc_zoneTop`（J1）。

> **2026-09-30 已由主人拍板并落成定案 99**：机制取 **A**（每任务一只独立 arena，结束时
> `extc_arena_destroy` 整只销毁，不再依赖全局 zone 栈的 LIFO）；对外语义取 **A**（任务存储随任务结束
> 整只回收，**能逃出任务的引用一律编译错误**）。配套义务：`extc_task_end` 在 boxed/unboxed 两条路都要
> 走到；逃逸分析的 soundness（R1/R3 的六条出口）紧随其后 —— 在它落地前，已知的「跨任务引用」形状
> 必须进 ASan 闸门与回归用例。
2. **释放**：`extc_task_end` 必须**只释放属于该任务的存储**：
   - 实现选择（推荐 **A**）：每个任务一只**独立 arena**（`extc_arena_destroy` 整只销毁），zone/pool 挂在该 arena 上；
   - 备选 **B**：保留全局 zone 栈，但记录 (id → mark, owner)，结束时**校验并精确归还**，
     若目标 mark 不在栈顶（非 LIFO）则先归还到该任务的 mark 而**不越过更高存活任务的段**。
   A 更简单、无 LIFO 依赖；B 省内存但需要所有权校验。**推荐 A**，并保留 B 作为后续优化。
3. **句柄与帧**：`$step`/`$next`/`$value`/`$send`、帧结构、arena/zone 参数由**同一合成器**产生（R4.4）；
   `$next` 负责在任务结束时调 `extc_task_end`（boxed 与 unboxed 两条路都要走）。
4. **递归计数**：`extc_rec_enter`/`cgRecLeave` 在所有出口（含协程分支、异常式早退）配对；
   深度计数按**逻辑调用深度**，不是"创建过的任务数"（修 P1-12）。
5. **事件层按需发射**：前缀名单从"枚举几个前缀"改为**注册表**（`extc_unix_` 漏发即此类），
   `--check-c` 全语料是判据。
6. **任务表**：槽位复用（或改为按 live 计数分配），`extc_task_live` 不得是 O(累计)。

**代价**：方案 A 每任务一只 arena ⇒ 每任务一次 calloc（现有实现已经 calloc 帧块，成本可接受）；
非 LIFO 场景下内存峰值可能略高（但**不再泄漏**、不再 UAF）。

**判据**：`z2.extc` ASan 干净；30 万次 spawn 的 RSS 平（±5%）；
`coro_recguard` 不再出现假 `recursion too deep`；`tests/coro/`、`tests/dyn/`、`tests/http` 全绿；
`extc_unix_*`-only 程序链接成功。

## 13. R13 · 效果摘要与线程模型

**问题**：`effects Thread=` 的**缺省值**在文档（`ast.h`）里是 1（保守：碰共享状态），
但代码只在**存在 `effects` 子句时**才置 1 ⇒ 没写子句的 `extern!` 被读成"不碰共享状态"，
worker 可以静默调用它（TSan 实测 data race）。
另外 `parallel::run` 的 worker 检查是**函数级标志**（`parTlsArena` 打在整条调用链上），
共享 helper 被主线程调用时解引用 NULL 的 TLS arena（P0-21）。

**相关审计**：P0-21、P1（`extThreadMask` 缺省）、P2（`EX_GENCALL` 池原语不在 worker 白名单）、
`ast`/`internal` 单元的相关条目。

**既有决策**：`DECISIONS.md` 定案 96（特权层只有标准库能碰）、`topics/CONCURRENCY.md`（worker 允许调用什么）
——方向一致；缺省值是**实现与文档不符**，按"文档即意图"修代码（INV-P 的缺省保守）。

**裁定**：
1. **缺省 = 保守**：任何没有 `effects` 子句的 `extern!`/`@builtin` 一律 `Thread=1`（碰共享状态），
   worker 里出现即编译错误（要求作者签字 `Thread=0`）。**实现侧**在解析 `extern!` 时无条件置 1。
2. **签名粒度**：`Thread` 是**调用事实**（0/1），不是按参数的位掩码（现状正确，文档写清）。
3. **TLS arena 的适用条件**：只对"**只在 worker 上下文里执行**"的函数体生效。
   判定必须是**过程间**的（从 `parallel::run` 的 worker 参数出发的可达集，且该函数不被非 worker 上下文调用）；
   不满足 ⇒ 不替换（用普通 arena），或生成物用 `extc_tls_arena ? *extc_tls_arena : <当前 arena>` 兜底。
   **推荐**：可达集 + "不被其它上下文调用"两个条件都满足才替换；否则兜底。
4. **白名单完整性**：worker 体内的**所有**分配/池原语（含 `EX_GENCALL` 形状的 `poolSlice`/`poolResize`/`poolGive`）
   都走同一条检查；名单由"内建原语表"驱动，不手写 switch。
5. **判据**：TSan 对 `tests/` 里所有并行用例零报告；`par2.extc` 不再崩；
   未签字的 extern 在 worker 里报编译错误。

- **撞号**：`52/52′/53/53′/54/55` 各指两件不同的事（早期批次表行 vs 后来的 `## 定案 NN`）；
- **缺号与悬空引用**：`定案 38`/`39` 被引用但正文没有；`定案 1.3`（`DECISIONS.md:1552`）无定义；
- **一码两义**：`定案 27` 在 `DECISIONS.md:210/413` 与 `manual/17-undecided.md:11` 指两件事；
- **顺序错乱**：`DECISIONS.md` 的文件顺序与编号顺序不一致（例如 73 排在 97 之前、89–93 在 2801+ 而 94–97 在 3400+）；
- **无日期条目**：早期批次（N01–N51）大量条目没有日期，"取新"无法机械执行。

**裁定**：
1. **每条决策四个必备字段**：全局唯一编号、**日期**、**状态**（`现行` / `已被 <编号> 取代` / `提案` / `已撤回`）、
   **取代关系**（`supersedes` 列表）。历史撞号条目正文保留，但在标题上标"历史编号（与 N 撞号）"。
2. **编号只增不改**：新决策从 **98** 起（本文 R1–R18 确认后按序并入）；已发出的编号永不重用。
3. **状态只写一处**：`DECISIONS.md` 每条的状态行是唯一真源；其他文档引用时必须重复该状态与日期摘要。
4. **加一个机器闸门** `tools/check_decisions.py`（进 `check.sh`）：编号唯一、日期存在、
   `supersedes`/`superseded-by` 双向一致、正文引用的每个编号都存在（消灭悬空引用）、
   被取代的条目其状态行已标注。
5. **本文并入方式**：主人逐条确认后，每条 R 变成一条定案（98、99、…），
   并在本文每条标题旁回填编号，本文从此降级为"索引/说明"，不再作为裁定源。

**理由**：这一条不是洁癖——审计里"按文档口径判"产生的分歧（例如 `-w` 到底关什么、
移位是 trap 还是取模）**全部**源于登记册不可判定。治理成本一次性，收益是每一轮后续工作。

**判据**：`tools/check_decisions.py` 零报错；随机抽 10 条决策，能在 10 秒内回答"是否现行、被谁取代、哪天定的"。

**问题**：提取发现至少 20 处"文档已被后来的决策或实现推翻、正文没改"，

**裁定**：

   不允许只在新文档里说，旧文档照旧。
2. **顺带修事实性错误**（不是被推翻，而是从来没对过）：例如诊断里把不存在的 `str` 列为内建类型、
   `--help` 漏 `--explain-memory`、`manual/16` 的移位口径、`modules.c` 头注释。

   回填是**纯文档改动**，可以独立于代码修复先做（也应当先做：它让后续每一轮判断都更便宜）。
4. **不新造历史**：旧口径即使错了也保留（审计需要），只加标注，不删。

**代价**：一轮文档工作量（估计半天到一天）；换来的是"下一轮审计不必再花一天交叉验证文档"。

**判据**：附录 D 清单逐条有标注；新一轮随机抽查 10 处旧文本，能看出它是否仍然有效。
