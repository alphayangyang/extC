# 元素引用（对容器里的东西取引用）

这份文档回答一个问题：**库里的容器能不能把手里的元素"借"给调用方，而不是拷一份出去。**
答案分三步：先给稳定存储上的元素引用（不用新概念），再给可增长容器一个显式的借用区间，
把"长寿命别名"留到最后、用世代号兜底。明确不做的是 Rust 式借用检查 —— 这门语言允许别名，
视图是窗口而不是快照。

## 缺的是什么

语言对"看内容"这件事已经有两套说法：帧里的存储能借出视图（`slice<T>`，拷贝为零），拥有
身份的存储用句柄访问（`dyn`、值池的槽）。两套都缺一角：

- **视图借不到容器里。** 想让调用方直接读容器，唯一的路是拷一份出来；在循环里拷、又只读一遍，
  代价是"每次拷贝都活到函数退出"—— 二十万轮约 52 MB，随轮数线性涨。
- **句柄绕不开间接。** 读-改-写一条记录要两次探测加一次整值进出拷贝。四个 workload 的横评里，
  唯一落后的那一项（回收轴，约 8%）差的正是这个：C++ 的下标返回引用，一次探测、零拷贝。

所以缺的不是能力，而是**一条"这个位置里的东西，地址是稳的"的说法**。

## 为什么现在取不到

对位置取引用只接受有稳定地址、且被名字或指针点名的表达式：变量、字段、解引用。下标不在其中 ——
被检查过的下标访问交出的是值。根本原因是**可增长容器的存储会搬家**：扩容要向池原地加长，
装不下时由分配器换一块更大的；静态上没有东西能证明"我手里这个地址在下次扩容后还成立"。

## 三条设计（按落地成本排序）

### 一、稳定存储上的元素引用

对"地址在生命周期内不会变"的存储，直接允许 `ref v[i]` 与 `mut ref v[i]`：定长数组、帧里
`new` 出来的切片、以及它们的视图。引用的有效期跟视图同一条规则 —— 不超过存储所在的位置，
位置退出即失效，越界与越活越界都是编译错误。

这条不需要新概念：只是放宽"对哪些位置可以取引用"，深度取自存储的所有者。收益是"拷出去、
改一改、写回来"这一大类形状直接消失。

### 二、可增长容器的借用区间

可增长容器要借元素，就得把"借的这段时间里不换存储"说出来。写法是显式区间：

```
borrow v as e {
    ...  e 可以读、可以按元素写（若声明为 mut） ...
}
```

区间内**这个名字**只能用只读的方式（另一个视图、只读方法），任何可能换存储的动作都是编译错误；
出区间引用失效。这是名字级的语法约束，不需要别名分析，因此能落在一个没有借用检查的语言里。
区间可以只读（`borrow v as e`）也可以可写（`borrow mut v as e`），后者禁止区间外同时用同一个名字。

### 三、世代校验的元素引用（不做）

让引用自带存储世代号（扩容换一代，解引用时比较）这条路线
**不采用** —— 它把"扩容期间还握着地址"从编译错误变成运行期随机 trap，而那正是不该有的
失败模式。语言的选择是让这种程序编译不过：借用窗口里写不出扩容，被 `ref` 过的容器不许开窗口。

## 失效规则（三条共同的合同）

| 借自 | 什么时候失效 | 谁保证 |
|---|---|---|
| 定长数组、帧里 `new` 的切片 | 所在位置退出 | 静态（深度检查） |
| 可增长容器（借用区间） | 出区间 | 静态（作用域 + 名字级只读约束） |
| 可增长容器（世代引用） | 容器换存储的动作 | 动态（世代比较，失配即 trap） |

别名照旧允许：两个 `mut ref` 可以指向同一个元素 —— 与语言其它部分一致。并发不因此变松：
`par` 里"每个 worker 只写自己那一格"的规则仍在，元素引用不提供任何跨线程的许可。

## 落地顺序与判据

1. **稳定存储的元素引用。** 放宽位置文法 + 深度取自存储所有者；诊断"这个位置没有稳定地址"
   （例如对容器直接取引用时提示改用借用区间）。判据：定长数组、帧内切片、它们的视图上能取读写
   引用并且改得回去；位置退出后再用是编译错误；既有回归不降；ASan 一格干净。
2. **借用区间。** 文法 + 名字级只读约束 + "区间内换存储"的拒绝。判据：区间内读、区间内按元素写、
   区间内 `push` 必须被拒、区间外恢复正常。
3. **世代引用。** 只在有真实需求时做；判据是"扩容后再解引用必须 trap，而不是读到旧内容"，
   并量出它相对拷贝的收益。

## 现在的进度

第一步（稳定存储）已经落地：定长数组 `[N]T` 的元素是位置，`ref a[i]` / `mut ref a[i]` 可用，
越界在取引用处报错或 trap，跨帧返回仍是编译错误。视图的元素与可增长容器的元素继续拒绝，诊断
会说明存储可能搬家。

接下来按同一份判据往前走：本帧 `new T[n]` 得到的切片与视图（存储同样不搬家），然后是借用
区间。三代校验的形态不采用，理由见上一节。

## 一条不变量：扩容期间不持有元素地址

元素引用的地址只在"存储不会搬家"的前提下成立。这条不变量没有运行期兜底 —— 不是"扩容时给你
一个可预测的 trap"，而是**扩容在可取引用的窗口里根本写不出来**：借用窗口用只读视图遮住容器名，
窗口里任何扩容操作都是普通的"没有这个方法"错误；被 `ref` 过的容器也不许开窗口（另一个名字
仍能扩容）。语言不做世代校验的元素引用：程序不该在随机时刻 trap，该在编译期被拒绝。

## 进度

- 定长数组的元素引用可用了：`ref a[i]` 是位置，读写与传参都走地址。
- 本帧 `new T[n]` 得到的视图（以及它的窗口）里的元素也可以取引用；容器板块上的视图仍然拒绝。
- 借用窗口可用了：`borrow v as e { … }` 在窗口里让 `e` 的元素可取引用，`v` 被只读视图遮住所以没法扩容。

判据（性能不受影响）：同一段"逐元素加一"的循环，用下标写 `a[i]` 与用引用写 `*p` 各跑 5000 轮
×4096 个元素，耗时落在同一个噪声带内（`idx_us` 125k–134k 对 `ref_us` 123k–126k），生成 C 里
引用就是一次地址计算，没有额外间接层。
- 不做：世代校验的元素引用（`refAt` 形态）。它把"扩容时还握着地址"变成运行期随机 trap，
  那是不可预测的失败模式；语言的选择是让这种程序编译不过。

## 第三步的落地细节（冻结式借用）

可增长容器的元素引用不需要新语法：容器已经有 `asSlice()` / `asMutSlice()`，借用区间可以就是
"从这个绑定声明起，到它所在块结束"。缺的是一条**冻结规则**：

- 建一个指向容器 `v` 的可写视图绑定时，`v` 进入冻结状态；冻结期间 `v` 不能被"会搬存储"的
  操作碰：`push` / `pop` / `insert` / `remove` / `put` / `clear` / `shrink` / `release` /
  `reserve` 这些方法，赋值给 `v`，以及把 `v` 传给别的函数（保守：任何实参位置都算）。
- 冻结期间允许：读 `v.len` / `v.cap` 这类只读字段，以及经那个视图读写元素。
- 视图绑定出自己的块就解冻：块结束时引用失效，容器又能长。

为什么这样就够安全：板块不被 resize ⇒ 视图的数据指针不动 ⇒ 元素的地址稳定；视图本身带着
深度，跨块逃出去仍由既有的深度检查拒绝。

落地时可以比上面更省：**用遮蔽代替冻结检查**。把 `borrow v as e { body }` 展开成
`{ let v: slice<T> = v.asSlice()  var e: mut slice<T> = v.asMutSlice()  body }` ——
区间里 `v` 这个名字已经被只读视图遮住了，于是 `v.push(1)` 走的是"切片没有 push 方法"的普通
解析错误，赋值和传参也都不再需要专门的冻结检查；`e` 则因为"它的存储在本帧、且区间内没人能
resize"而成为可索引的位置。这样只需要一处标记（视图绑定"存储稳定"）与 `isLvalue` 里的一条
条件，不新增 AST 节点、不加运行期开销。

要改的地方（都不新增 AST 节点）：
1. 绑定上记两件事 —— 视图绑定记"我借的是哪个容器"，容器绑定记"正被谁借"；
2. 建视图绑定时互相登记（`asSlice` / `asMutSlice` 的接收者是 `EX_IDENT` 时）；
3. 四处写操作入口做冻结检查：方法调用的接收者、赋值的左值、调用的实参、`ref` 的操作数；
4. 元素引用放行条件加一条"视图的来源容器处于冻结状态"。

判据矩阵（先红后绿）：
- 正例：`let e: mut slice<i64> = v.asMutSlice()` 之后的 `ref e[0]` 可写，且与 `v[i]` 逐字节同结果；
- 反例：冻结期间 `v.push(1)` 报错、`v = other` 报错、`f(v)` 报错、把 `v` 交给方法报错；
- 反例：视图块结束后再对容器取元素引用仍然拒绝（不是"块外也行"）；
- 回归：现有 `asMutSlice()` + `push` 的写法若在冻结窗口外，行为不变。
