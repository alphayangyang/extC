# 内存回收：怎么回事、什么时候用得上

extC 里没有 `free`，也没有那种"停下来把整个堆扫一遍"的垃圾回收。内存的寿命先由**作用域**决定；回收器只接手那些真正活过了作用域的对象，并且把工作切成小步，穿插在程序运行当中。

这一页用日常说法讲清这套做法，机制细节与还没做的事在[回收机制与待做](../RECLAMATION.md)。

**一句话**：作用域是地基（分配几乎免费、退出整片归还），回收器只是兜住"活过了作用域"的那一部分。

## 一、地基：作用域就是寿命

每个块（函数体、`if` 体、循环体）自带一片内存，`new` 从当前块的这片内存里往下发。

```extc
use std::io

struct node { value: i64  next: ?ref node }

fn main() {
    var total: i64 = 0
    for i in 0..3 {
        var a = new node
        var b = new node
        a.value = i
        b.value = i * 10
        a.next = b
        total += a.value + b.value
    }
    io::cout << "total = " << total << "\n"
}
```

这段程序会印出 `total = 33`。它说明三件事：

* **分配就是把指针往前挪一格。** 对象的内存是清零的，不需要在堆里找空位，也不需要当场决定谁负责释放。
* **退出块就是整片归还。** 不遍历、不逐个释放，也不用知道里面哪些对象还活着。
* **块内可以随便互相引用、随便覆盖。** 这一层不需要运行期记账。

代价是它只解决"活得正好和块一样久"的对象。

## 二、只有作用域不够的两件事

**第一件：对象活过了它出生的块。** 被返回、被存进更长命的地方 —— 如果它还待在原块，块一退就没了。要求编译器静态证明"谁逃逸"很难做全；extC 的做法是**提权**：逃逸这个动作真的发生时，把这份存储挪到外层区域，**地址不变**。对程序来说什么都没发生。

```extc
use std::io

struct node { value: i64  next: ?ref node }

fn make(v: i64) -> ref node {
    var n = new node
    n.value = v
    return n
}

fn main() {
    var head: ref node = make(7)
    io::cout << "head = " << head.value << "\n"
}
```

`n` 出生在 `make` 的块里，被返回 ⇒ 提权到调用者那一层；`head` 拿着它一直有效。

**第二件：长命槽被反复覆盖。** 下面这个循环每轮都新造一个节点、都往同一个槽里放，但真正被留下的只有最后一个。没有回收器的话，存储会随轮数一直涨。

```extc
use std::io

struct node { value: i64  next: ?ref node }

fn main() {
    var saved: ?ref node = null
    var i: i64 = 0
    while i < 1000000 {
        var p = new node
        p.value = i
        saved = p
        i = i + 1
    }
    var last: i64 = 0
    if saved != null { last = saved.value }
    io::cout << "last = " << last << "\n"
}
```

一百万轮、每个节点 16 字节，实测峰值内存 **2.8 MB**、墙钟中位 **5.0 ms**（回收片合计 1.5 ms，共 2055 片，最慢一片 9.6 µs）。用编译开关 `EXTC_RECLAIM=0` 把回收关掉跑同一份代码：**17.0 MB**、6.6 ms —— 正好是"一百万个节点原样躺着"的大小。

要的就是这个：**不可达却还占着内存的对象，总量有界，而且这个界与循环轮数无关。**

## 三、回收器补上的最后一段

| 什么时候 | 做什么 | 花多少 |
|---|---|---|
| 离开块 | 整片归还 | 指针拨回去，几乎免费 |
| 真的逃逸了 | 把这份存储挪到外层 | 一次指针操作，地址不变 |
| （可选）最后一个持有者没了 | 当场释放那一个对象 | 每次指针赋值动一次计数 |
| 内存压力超过限 | 扫这个区域，放掉不可达的 | 扫一个区域，切成小步 |

前三层处理掉绝大多数对象；最后一层只负责**环**和计数饱和掉的那一小部分。

**默认口径：不做持有者计数。** 兜底完全靠区域清扫，所以写密集的程序不会为计数付税；少掉的只是"最后一个持有者一死就立刻回收"这条快路。编译时把计数打开（`EXTC_RC_NOCOUNT=0`），就多出上面第三层：

<!-- fragment -->
```extc
var p = new node
var q: ?ref node = p     // 计数 2
outer = p                // 计数 3
outer = null             // 计数 2 —— 还有 q，不放
q = null                 // 计数 1 —— 还有 p，不放
p = null                 // 计数 0 —— 放
```

* **只挂在"指向关系改变"上。** 数据字段赋值不记；引用赋值记两次（目标加一、旧值减一）。
* **到顶就锁住、此后不再减。** 宁可交给清扫，也不能提前释放。
* **环永远不会归零**，交给清扫 —— 这是引入计数换来的：程序不需要自己标记环。

清扫不需要扫栈，因为它只要两样东西：

* **起点（根）是编译器静态给的。** 触发点在分配处，那一刻哪些引用槽是活的编译器知道，于是根表直接发射出来，不需要影子栈、也不保守扫描。
* **下一层怎么找是编译期给的。** 每个槽里装了哪个类型、里面几个引用，都是生成的描述符 ⇒ 顺着走就行。
* **只扫"自己这一帧拥有的区域"。** 看见别人的区域只记一笔账，等它的主人下次用之前再销账；种子不完整时宁可不动手，也不能把活对象当垃圾放掉。
* **触发看内存压力，而且会自己退场。** 一次清扫一无所获就把该区域的阈值翻倍（学会"这里没有环"），真收到东西就复位。**没有环的程序永远不会进入清扫。**

## 四、为什么几乎没有"GC 停顿"

* **每一步都有预算。** 这一片最多弹出多少对象、最多扫多少个位图字，做完就回去干活。
* **不搬对象。** 引用永远有效，也就不需要"停下来搬完再放行"。
* **根表是静态的**，不需要为了安全暂停别人；也没有独立的 GC 线程 —— 回收就在当前线程上做，做成很多小片。
* **触发按内存压力看，而不是"堆满了"。**

在四档横评形状上，extC 的单次停顿中位数 0.70–1.40 µs、p99 ≤ 2 µs；除一次被操作系统抢走 CPU 的 2.36 ms 之外，最慢的一片不超过 115 µs（同一批里 Java 有 45 ms、Node 有 84 ms 的单次停顿）。上面那份一百万轮的例子里，2055 片里没有一片超过 16 µs。

想自己看：给程序设 `EXTC_RC_PAUSE=1`，它会报每片的时长与停顿窗口 —— 这是给用户看的诊断，不是内部工具。

## 五、边界与代价

* **指向对象内部的地址不算引用。** 回收器只认"槽的开头"；`&v[1]` 这样的内部地址不会让对象活下来。这也是"单个元素取引用"这个形状还没开放的原因之一。
* **容器扩容会让旧视图分叉。** `varArray` 扩容会换一块缓冲区，之前拿到的视图还指着老的 ⇒ 往里写看不到。
* **大活集、纯环垃圾的形状上，回收是净开销。** 四个横评形状里，`chase`（六万多节点的大图）与 `cycleratio`（全是环）上回收档比把回收关掉更慢；垃圾多的 `promote`、`sizeratio` 上则又快又省内存。
* **计数默认关闭**，所以"最后一个持有者死了"不会当场回收，要等清扫。
* **线程还没做**：区域与根表的账都是按单线程算的。
* **它不是零成本。** 允许别名、能收环、停顿与堆大小无关，这三件事换来的代价是"指针赋值可能要动一次记账"。

## 六、数字怎么读

三把尺一起看：

1. **墙钟**：多次运行取中位（同一台机器、钉一个核）。
2. **峰值内存**：内核给的 `ru_maxrss`。
3. **停顿的分步分布**：分位数 + 超过阈值的片数，**不看最大那一次**（那一次多半是被别的进程抢了 CPU）。

一条纪律：**占比要配内存读。** "回收花了多少时间"只说明这次运行里它干了多少活 —— 占比高往往是把活干了、换来了低内存；占比低可能是便宜，也可能是**根本还没回收**，内存全靠堆头寸顶着。

## 七、现在的成绩

四个形状、六种语言、同一台机器、每格墙钟中位 / 峰值内存（毫秒 / MB）。"回收关掉"是把回收编译掉的同一份 extC 程序 —— 那个开关同时把分配器换成纯 bump，所以它不是"纯 GC 税"的对照，看它主要看内存差多少。

| 形状 | extC | 回收关掉 | Go | Java | Rust | Node | C++ |
|---|---|---|---|---|---|---|---|
| promote（分代假设：多数短命、少数提升） | **51 / 7.4** | 74 / 107.0 | 104 / 7.7 | 89 / 110.9 | 37 / 7.3 | 100 / 75.9 | 94 / 143.1 |
| sizeratio（四种尺寸类） | **29 / 7.1** | 58 / 154.2 | 43 / 7.5 | 83 / 109.2 | 20 / 7.3 | 78 / 72.3 | 69 / 187.1 |
| chase（六万多节点的大图，指针追逐） | 136 / 73.7 | **91 / 60.7** | 135 / 64.6 | 283 / 172.3 | 199 / 90.1 | 981 / 288.5 | 112 / 79.6 |
| cycleratio（全是环的垃圾） | 36 / 7.5 | **25 / 43.4** | 33 / 7.4 | 73 / 104.2 | 18 / 7.3 | 58 / 71.0 | 35 / 7.1 |

从这张表能读出三件事：

* **垃圾多的形状上，回收是赚的。** `promote`：比关掉快 1.45×、内存省 14×；`sizeratio`：快 2.01×、内存省 22×。
* **大活集与纯环形状上，回收是净开销**（关掉更快），换来的是"以后一定还回来"的内存 —— 这正是"什么时候用得上"的答案：垃圾比例高、对象短命，回收才划算。
* **跨语言看内存**：extC 峰值 7.1–73.7 MB，Go 7.4–64.6 MB，Java 104–172 MB，Node 71–288 MB。

停顿方面：extC 的每一片都是"干活的时间"（它没有独立 GC 线程，回收工作全在这些片里）；Go 的停止时间只有几微秒，但它的 GC 工作放在了并发阶段，占墙钟的量反而更大（28–49%，extC 是 4.5–36%）。这两个口径不是同一件事，别直接对着比。
