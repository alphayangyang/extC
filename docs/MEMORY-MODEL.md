# 内存模型：寿命由"住哪儿"决定

extC 没有 `free`，也没有垃圾回收器。`new` 出来的东西只可能住在三种地方，**住哪儿决定了它能活多久、也决定了用起来贵不贵**。选错地方不会编译报错，只会让内存数字看不懂 —— 这一页就是那张对照表。

回收机制本身（四层、什么时候才真正跑回收器）在[回收机制与待做](RECLAMATION.md)；日常说法在[内存回收：怎么回事](usage/reclamation.md)。

## 一、三种地方

| 地方 | 形状 | 什么时候归还 | 适合 | 不适合 |
|---|---|---|---|---|
| **帧**（块自带的内存） | 一块一块往上摞的栈，分配只是挪指针 | 离开块时整片归还，保留一块备用 | 大小已知、只在块内活的临时数据 | 长度会变的东西 |
| **板块**（容器自己的存储） | 容器持有的一串独立分配，能原地长、能随时还 | 容器换缓冲/缩小时当场归还；容器没了整批还 | 会变长、要活一阵的存储（`vector`、`string`、`hashMap`） | 想让它跟着块退出自动收走的东西 |
| **对象表**（按句柄寻址的槽表） | 槽数组 + 世代；句柄是"槽号 + 世代" | 槽可回收；回收后旧句柄读到的是"没有"，不是悬垂 | 需要身份、要活过出生位置的值（`dyn` 值、`pool<T>`） | 热循环里的逐次读写（每次都要过世代检查） |

三者的关系是**分工**，不是三套竞争方案：

- 帧是地基。绝大多数分配落在这里，代价接近零：不记账、不扫描、退出不遍历。
- 板块是"会变长的东西"的存储。它属于某个容器，容器换掉旧缓冲时旧缓冲**当场**就还了。
- 对象表只在"值必须有身份、且身份要离开创建它的地方"时才值得用；它买的是"读不到"而不是"读坏"。

## 二、一条判据

| 你要的是 | 用什么 |
|---|---|
| 块里用一下就算完的临时量 | `new T[n]`、定长数组、局部变量 |
| 长度会变，或者在函数之间传递一段存储 | `vector`、`string`、`hashMap` —— 它们自带板块 |
| 值要活过创建它的位置，而且要被别处记住 | `dyn` 值，或 `pool<T>` 的句柄 |
| 只是"看看"别处的数据 | `slice<T>` 视图：零拷贝、不拥有、不负责归还 |
| 要在大块数据上原地算，不复制 | `slice<T>` 视图 + 接收视图形参的函数 |

一句话：**先问"它活多久"，再问"长度会不会变"，这两个答案合起来只对应一种存储。**

## 三、为什么可增长的容器必须拥有板块

增长是**乱序死亡**：新缓冲在旧缓冲之上分配，被替换的那一块死在它下面。而帧是栈 —— 只能从顶上往下退，退不了下面的。所以被替换的缓冲会一直占着，直到它所在的块退出。

两个实测（同一台机器，2,000,000 条记录尺度上的同族负载）：

| 写法 | 峰值内存 | 墙钟 |
|---|---|---|
| 在帧里自己搓可增长数组（每次增长换一块新缓冲） | 增长到八百万个 `i64` 时 **129.5 MB**（历代旧缓冲之和，约 2 倍） | 57 ms |
| `vector<i64>`（拥有板块，原地长 1.5 倍） | **64 MB** | 28 ms |

反复建了又丢的负载差别更大：一百次"分配 1 MiB 再丢弃"，用板块的容器稳态只要 **2.5 MB**，而在帧里换缓冲的写法要 **103.8 MB**（一比一保留）。

这就是规则：**容器拥有存储，存储才可能在容器替换它的那一刻被还掉。** 帧只适合"和块同寿命"的东西。

## 四、四个会咬人的写法

**① 在帧里手搓可增长容器。** 见上表：内存是"历代之和"，翻倍增长约 2 倍，按固定步长增长是二次增长。正确做法是换成 `vector`/`string`，或者自己写容器时也让它拥有板块。

**② 循环里分配、循环外的变量接住。**

```
var b: mut slice<u8> = new u8[1024]
for ... {
    b = new u8[1024 * 1024]     // 旧缓冲退不掉：它在这个块里
    ...
}
```

一百轮之后峰值 **103.8 MB**。把同一行写进循环体（每轮一个新变量），峰值 **2.4 MB** —— 因为每轮结束时整块被归还。这条判据很好记：**变量的块比循环长，旧缓冲就会攒。**

**③ 把拷贝来的视图丢掉。** `toSlice()` 是拷贝，拷贝的存储会被提到调用者的位置（这样它才能被存下来、被返回）。所以 `for ... { let s = v.toSlice() }` 会让每轮的拷贝都活到函数退出 —— 二十万轮约 **52 MB**，而且随轮数线性增长。热循环里不要制造要逃逸的拷贝；需要看内容就直接读容器的 dense 前缀。

**④ 长命位置里的 `dyn` 垃圾。** `dyn` 的 payload 由它所在位置的对象表持有，槽可以回收，**payload 的字节随位置一起还**。`main` 的位置活到程序结束，所以在一个长命位置里不断产生又丢弃 `dyn` 值，内存是历史高水位。这是当前实现的边界：`dyn` 适合"数量有界、有身份"的用途，不适合当"每轮丢一个"的槽位。

## 五、碎片

没有经典意义上的碎片，因为**没有共享大堆**：帧是栈（天然没有洞），板块是每个容器自己的独立分配（换掉就还，归还交给系统分配器），对象表的槽按类型/尺寸分组复用。三者都不需要"合并相邻空洞"，也就不需要搬动（compaction）。

剩下的只是三种**内部余量**，都是有界的：

- 帧的块尾余量：一块之内用不完的那点，量级是"每块几十字节到一块"；
- 容器容量余量：`vector` 按 1.5 倍长，最坏 50%；`hashMap` 还有墓碑，按装载比例重建；
- 对象表的槽余量：回收的槽留在表里复用，表不会立刻缩。

稳态实测（同一个进程里反复建、反复丢）：一百个 1 MiB 容器 = **2.5 MB**；两千轮、每轮三个不同尺寸的容器同时活 = **1.5 MB**；两百次 4 MiB 的帧内分配 = **5.6 MB**。都不随轮数增长。

## 六、和"有垃圾回收的语言"差在哪

会做回收的语言（比如 Go）解决的是**任意时刻、任意顺序的死亡**：`append` 越界时新开一块、拷过去，旧的那块变成不可达，下一次标记清扫把它收回空闲链复用。所以"分配完就丢"的形状它也能稳态在几个 MB。

我们解决的是**词法边界 + 静态证明**：不问"还有没有引用"，只问"是不是退出了这个块"。好处是分配免费、没有写屏障、没有停顿；代价是"乱序死亡"没人管 —— 而这恰好是可增长容器天生制造的形状。

所以对比要分两件事看：

- **丢弃即回收**：有回收器的语言赢（一百次 1 MiB 的 churn，它们几 MB，帧里换缓冲的写法 103.8 MB）；
- **增长的峰值**：两边一样（都是拷贝瞬间两份都活，约 2 倍）。有回收器的语言不会让增长更省，只是不用你操心旧的那份。

结论：**帧不是"更差的堆"，它是另一种形状。** 长度会变的存储必须交给拥有板块的容器；把这件事做对，稳态内存和速度都能追上有回收器的语言。

## 七、想自己写容器

板块不是只给内置容器用的：语言里"拥有一个池"这件事是公开的 —— 给结构体标上 `@poolObject`，它就带着自己的池和板块活；向池要存储、原地长、还回去各有对应的原语。`vector` 就是这套动作的完整样板：初始化时给个容量，长的时候原地长，取内容时明确知道自己拿到的是一份拷贝，用完 `release()`。

写自己的可增长容器要做四件事：**拥有**一块池（`@poolObject` 结构体 + 建池时的世代号）、**要**存储（按容量向自己的池要一段）、**长**（容量不够时向同一个池原地加长，1.5 倍是合适的因子）、**守卫与归还**（比较池的世代号判断这一份是否还指着自己的池；归还时先收成 0 长度，再把池重置、丢弃）。四步写全了，"自己搓一个 `vector`"就不会掉进第四节第①条：手写的 800 万个 `i64` 容器实测峰值 64 MB，与内置 `vector` 相同。逐步写法见[标准库](usage/stdlib.md)里"自己写一个板块底的容器"一节。

不做这四步会怎样：没有世代守卫，一次别名 + `release` 之后另一份就在写已经还掉的内存，而且不开 ASan 时打印完全正常；不做原地长而是每轮新分配，就退回第四节第①条。

## 八、要记的三句话

1. **先看寿命，再看长度**：块内 → 帧；会变长 → 板块；要身份 → 对象表。
2. **谁的块退，谁的内存还**：变量的作用域比循环长，旧缓冲就会攒。
3. **拷贝要记账**：`toSlice()` 的存储活在调用者的位置，热循环里它就是你写的每一次分配。
